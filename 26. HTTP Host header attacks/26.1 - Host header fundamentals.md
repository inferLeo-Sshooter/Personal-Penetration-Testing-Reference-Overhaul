## TL;DR

- Every HTTP/1.1 request carries a `Host` header saying **which website** the client wants.
- The client controls that header, so an attacker can put anything in it.
- If the server or app **trusts it blindly**, the attacker can poison emails, poison caches, reach internal systems, and more.
- The best fix: **don't use the Host header in your code**. Use a configured, trusted domain value instead.

---

## 1. What is the Host header?

It's a line in an HTTP request that names the site being requested. HTTP/1.1 requires it.

When you open `https://example.com/products`, your browser sends:

```http
GET /products HTTP/1.1
Host: example.com
```

Sometimes a middle system (like a proxy) rewrites the value before it reaches the final server.

---

## 2. Why does it exist?

Long ago, one IP address meant one website. Today, many sites share one IP. Two common setups cause this:

**Virtual hosting** — one server runs many sites.

```
                  ┌── shop.example.com   (site A)
Client ─► Server ─┤
  (one IP)        └── blog.example.org   (site B)
```

**Intermediary routing** — a load balancer, reverse proxy, or CDN sits in front of many back-end servers.

```
                      ┌─► Backend 1 (shop.example.com)
Client ─► Reverse ────┤
          proxy       └─► Backend 2 (blog.example.org)
```

In both cases, the server receiving the request needs to know which site you meant. The `Host` header answers that.

**Analogy:** An apartment building has one street address, but the letter needs an apartment number so it reaches the right person. `Host` is the apartment number.

---

## 3. What is a Host header attack?

It happens when an app **trusts the Host header without checking it**. Since the client sets that header, an attacker can send whatever they like:

```http
GET / HTTP/1.1
Host: evil.com
```

If the server uses that value in emails, links, database queries, or routing decisions, things go wrong. Sending malicious data through this header is often called **Host header injection**.

### Why do apps use it in the first place?

Many ready-made apps don't know their own domain. When they need to build a full link (say, for an email), they grab it from the request:

```php
// Risky: builds a link from whatever the client sent
$link = "https://" . $_SERVER['HTTP_HOST'] . "/support";
echo "<a href='$link'>Contact support</a>";
```

If the attacker sends `Host: evil.com`, the link points to `evil.com`.

---

## 4. Why do these bugs happen?

1. **Wrong assumption** — developers think users can't change the header. They can, trivially, using tools like Burp Suite.
2. **Hidden override headers** — even if `Host` is handled safely, other headers such as `X-Forwarded-Host` may replace it. These are often enabled by default and forgotten about.
3. **Bad configuration** — many cases aren't code bugs at all. Teams plug in third-party components (proxies, CDNs, frameworks) without fully understanding their settings.

## 5. What can attackers do with it?

### 5.1 Password reset poisoning

Many sites email a password-reset link built from the Host header.

**Normal flow:**

```http
POST /forgot-password HTTP/1.1
Host: shop.example.com
Content-Type: application/x-www-form-urlencoded

email=victim@mail.com
```

The victim gets:

```
https://shop.example.com/reset?token=abc123
```

**Attack:** the attacker triggers a reset for the victim's email but changes the Host:

```http
POST /forgot-password HTTP/1.1
Host: evil.com
Content-Type: application/x-www-form-urlencoded

email=victim@mail.com
```

The victim now receives:

```
https://evil.com/reset?token=abc123
```

If they click it, the secret token lands in the attacker's server logs. The attacker then uses it on the real site to take over the account.

### 5.2 Web cache poisoning

If a cache stores a response that was influenced by the Host header, an attacker can slip in bad content that then gets served to everyone.

```http
GET / HTTP/1.1
Host: shop.example.com
X-Forwarded-Host: evil.com
```

Imagine the app builds a script tag from that header:

```html
<script src="https://evil.com/static/app.js"></script>
```

If the cache doesn't treat the header as part of its lookup key, it saves this page and serves it to normal visitors. Now they all load the attacker's script.

### 5.3 Classic server-side bugs

The Host value might end up in a database query, a shell command, or a template. If it isn't escaped, normal injection flaws (like SQL injection) become possible:

```http
GET / HTTP/1.1
Host: x' OR '1'='1
```

(Simplified illustration: the point is that Host is *user input*, just like a form field.)

### 5.4 Bypassing access restrictions

Some apps only allow certain features when the request seems to be from an internal source, and they judge that by the Host value.

```http
GET /admin HTTP/1.1
Host: internal-admin.local
```

If the check is based only on that header, it's easy to fake.

### 5.5 Virtual host brute-forcing

Companies sometimes run internal sites on the same server as public ones. Their domains don't appear in public DNS, but an attacker can **guess names** and see which ones respond:

```http
GET / HTTP/1.1
Host: intranet.example.com
```

```http
GET / HTTP/1.1
Host: staging.example.com
```

A different response for a guessed name reveals a hidden site.

### 5.6 Routing-based SSRF

If a reverse proxy sends traffic to whichever back-end the Host header names, an attacker can steer requests **into the internal network**:

```http
GET / HTTP/1.1
Host: 192.168.0.1
```

The proxy might forward this to an internal machine that outsiders should never reach. This is a form of server-side request forgery (SSRF).

### 5.7 Connection state attacks

Some servers only check the Host header on the **first** request of a reused connection, then relax. An attacker can send a harmless first request, then a malicious second one on the same connection, and slip past the check.

```
Request 1: Host: public-site.com     ← validated, looks fine
Request 2: Host: internal-site.local ← not re-checked
```

### 5.8 SSRF via malformed request line

Instead of a normal path, the request line includes a full URL. Some proxies then route using that URL and ignore the Host header:

```http
GET https://internal-site.local/ HTTP/1.1
Host: public-site.com
```

## 6. How attackers test for it

A rough checklist:

1. **Change the Host to something random.** Does the site still respond?
2. **Look for weak validation.** Does it accept extra characters, port numbers, or sub-domain tricks?
3. **Send confusing requests.** For example, two Host headers, or an indented one.
4. **Try override headers:**

```http
X-Forwarded-Host: evil.com
X-Host: evil.com
X-Forwarded-Server: evil.com
X-HTTP-Host-Override: evil.com
Forwarded: host=evil.com
```

## 7. How to defend

| Defense | What it means | Example |
|---|---|---|
| **Avoid the Host header** | Use relative URLs where possible | `<a href="/support">` instead of an absolute link |
| **Hard-code your domain** | Store the site's domain in config, not from the request | `BASE_URL = "https://shop.example.com"` |
| **Validate Host against an allow-list** | Reject anything unexpected | Django `ALLOWED_HOSTS` |
| **Disable override headers** | Don't honor `X-Forwarded-Host` unless you truly need it | Strip it at the edge |
| **Allow-list proxy targets** | Load balancers should only forward to known back-ends | Proxy config |
| **Separate internal apps** | Don't host internal sites on the same server as public ones | Use different servers or networks |

### Code examples

**Safe link building (config-based):**

```python
# settings / config
SITE_URL = "https://shop.example.com"

# in code
reset_link = f"{SITE_URL}/reset?token={token}"
```

**Django allow-list:**

```python
# settings.py
ALLOWED_HOSTS = ["shop.example.com", "www.shop.example.com"]
```

**Nginx: reject unknown hosts:**

```nginx
# Catch-all server: drops requests for unrecognized hosts
server {
    listen 80 default_server;
    return 444;
}

# Only this host is served
server {
    listen 80;
    server_name shop.example.com;
    # ...
}
```

**Strip a risky override header at the proxy:**

```nginx
proxy_set_header X-Forwarded-Host "";
```

---

## 8. Key takeaways

- **Treat `Host` like any other user input.** It's attacker-controlled.
- **Don't build important links or logic from it.** Use a configured domain.
- **Check your infrastructure**, not just your code. Proxies and frameworks often support extra headers you didn't know about.
- **Keep internal and public sites apart.**
- **Validate against an allow-list** whenever you must use it.
