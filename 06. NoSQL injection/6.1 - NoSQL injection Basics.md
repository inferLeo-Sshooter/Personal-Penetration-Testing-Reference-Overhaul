



# NoSQL Basics

## Overview

**NoSQL injection** occurs when an attacker interferes with an application's NoSQL database queries, potentially allowing them to bypass authentication, extract or modify data, cause denial of service, or execute server-side code.

Unlike SQL databases, NoSQL databases use varied query languages and have fewer relational constraints. There are two main attack types:

- **Syntax injection** – Breaking the query syntax to inject a malicious payload, similar to SQL injection but varying by database type.
- **Operator injection** – Abusing NoSQL query operators to manipulate queries.

---

## NoSQL DB

**NoSQL databases**

NoSQL databases store and retrieve data in formats other than traditional relational tables, designed to handle large volumes of unstructured or semi-structured data. Compared to SQL, they have fewer relational constraints and consistency checks, offering notable benefits in scalability, flexibility, and performance.

Users interact with NoSQL databases through queries passed from the application, but unlike SQL's universal standard, each NoSQL database may use its own custom query language or a common format like XML or JSON.

**NoSQL database models**

Understanding the model framework and language of a NoSQL database helps in detecting its vulnerabilities. Common types include:

- **Document stores** – Store data in flexible JSON, BSON, or XML documents, queried via an API or query language. Examples: `MongoDB`, Couchbase.
- **Key-value stores** – Store data as unique key-value pairs, with values retrieved by their key. Examples: Redis, Amazon DynamoDB.
- **Wide-column stores** – Organize related data into flexible column families rather than rows. Examples: Apache Cassandra, Apache HBase.
- **Graph databases** – Use nodes for data entities and edges for relationships between them. Examples: Neo4j, Amazon Neptune.

## MongoDB

Like MySQL, MariaDB, or PostgreSQL, MongoDB is a database for storing and retrieving data in a quick, structured way. The key difference from relational databases is that data is stored in **documents** rather than tables.

Documents function as simple key-value pair dictionaries — similar to records in a relational database, just stored differently. For example, an HR web app might store employee data like this:

`{"_id" : ObjectId("5f077332de2cdf808d26cd74"), "username" : "lphillips", "first_name" : "Logan", "last_name" : "Phillips", "age" : "65", "email" : "lphillips@example.com"}`

Each document is an associative array with an arbitrary number of fields. Multiple related documents are grouped into **collections**, which are the equivalent of tables in relational databases.

Continuing with our **HR example**, all the employee's documents would be conveniently grouped in a collection called "people" as shown in the diagram below.

Multiple collections are finally grouped in databases, which is the highest hierarchical element in MongoDB. In relational databases, the database concept groups tables together. In MongoDB, it groups related collections.

**Querying the database:**

As with any database, a special language is used to retrieve information from the database. Just as relational databases use some variant of SQL, non-relational databases such as MongoDB use NoSQL. In general terms, NoSQL refers to any way of querying a database that is not SQL, meaning it may vary depending on the database used.

With MongoDB, queries use a structured associative array that contains groups of criteria to be met to filter the information. These filters offer similar functionality to a where clause in SQL and offer operators to build complex queries if needed.

To better understand NoSQL queries, let's start by assuming we have a database with a collection of people containing the following three documents:

<img width="899" height="216" alt="image" src="https://github.com/user-attachments/assets/aad0d0f8-7331-4062-b295-a74a9fdb88c5" />

If we wanted to build a filter so that only the documents where the `last_name is "Sandler"` are retrieved, our filter would look like this:

```
**['last_name' => 'Sandler']**
```

As a result, this query only retrieves the second document.

If we wanted to filter the documents where the `gender is male`, and the `last_name is Phillips`, we would have the following filter:

```
**['gender' => 'male', 'last_name' => 'Phillips']**
```

This would only return the first document.

If we wanted to retrieve all documents where the `age is less than 50`, we could use the following filter:

```
**['age' => ['$lt'=>'50']]**
```

This would return the second and third documents. Notice we are using the `$lt` operator in a nested array. Operators allow for more complex filters by nesting conditions. A complete reference of possible operators can be found on the following link:

[MongoDB query reference](https://www.mongodb.com/docs/manual/reference/mql/query-predicates/)

## NoSQL syntax injection

As mentioned above, `Syntax injection` occurs when you can break the NoSQL query syntax, enabling you to inject your own payload.
- The methodology is similar to that used in `SQL injection`.
- However the nature of the attack varies significantly, as **NoSQL databases use a range of query languages, types of query syntax, and different data structures**.

To do this, 
- Systematically test each input by submitting fuzz **strings** and **special characters** that trigger a database `error` or some other `detectable behavior` if they're **not** adequately sanitized or filtered by the application.
- If you know the API language of the target database, use **special characters** and fuzz strings that are relevant to that language.
- Otherwise, use a variety of fuzz **strings** to target **multiple API languages**.

### Detecting syntax injection in MongoDB steps

**Step 1: Observe the normal request**

Select a category (e.g. *Fizzy drinks*) and note the URL your browser sends:
`https://insecure-website.com/product/lookup?category=fizzy`

The application translates this into a MongoDB query:
`this.category == 'fizzy'`

---

**Step 2: Submit a fuzz string**

Inject the following MongoDB fuzz string into the `category` parameter:
`'"`{ ;$Foo} $Foo \xYZ`

Construct and send the URL-encoded attack URL:
`https://insecure-website.com/product/lookup?category='%22%60%7b%0d%0a%3b%24Foo%7d%0d%0a%24Foo%20%5cxYZ%00`

If the response changes, user input may not be properly filtered or sanitized.

> **Note:** Adapt your fuzz strings to the injection context. If injecting via a JSON property instead of a URL, use: `'"\`{\r;$Foo}\n$Foo \\xYZ\u0000`

---

**Step 3: Identify which characters are processed**

Inject individual characters to find which ones break query syntax. Start with a single quote `'`, producing:
`this.category == '''`

If the response changes, the `'` likely caused a syntax error. Verify by escaping the quote:
`this.category == '\''`

If this returns a normal response without errors, the application is likely vulnerable to injection.

---

**Step 4: Test conditional behavior**

Send two requests using false and true conditions to check if you can influence query logic:

- **False condition:** `https://insecure-website.com/product/lookup?category=fizzy'+%26%26+0+%26%26+'x`
- **True condition:** `https://insecure-website.com/product/lookup?category=fizzy'+%26%26+1+%26%26+'x`

If the application responds differently to each, the injected syntax is affecting the server-side query.

---

**Step 5: Override existing conditions**

Inject a JavaScript condition that always evaluates to true, such as `'||'1'=='1`:
`https://insecure-website.com/product/lookup?category=fizzy%27%7c%7c%27%31%27%3d%3d%27%31`

This transforms the MongoDB query into:
`this.category == 'fizzy'||'1'=='1'`

Since the condition is always true, the query returns all items — including hidden or unknown categories.

> **Warning:** Be cautious with always-true conditions. Applications often reuse request data across multiple queries. If the same input is used in an update or delete query, injecting an always-true condition could cause accidental data loss.
