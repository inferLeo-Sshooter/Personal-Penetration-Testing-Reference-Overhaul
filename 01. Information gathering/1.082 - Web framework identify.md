
## 1. Headers (check even if the tools missed something)

Tools sometimes miss headers that *are* there, or the site strips the obvious ones but leaves subtler ones:

```http
Server: Apache/2.4.41 (Ubuntu)      # sometimes present, sometimes blank/faked
X-Powered-By: PHP/8.1.2             # PHP
X-Powered-By: ASP.NET               # .NET
X-AspNet-Version: 4.0.30319         # .NET
X-AspNetMvc-Version: 5.2            # .NET MVC
```

Even a faked or removed `Server` header can leak info through **header capitalization/order**. Burp's raw response view shows header order, which differs between stacks (IIS, Apache, nginx, and various frameworks each have characteristic default orderings).

## 2. Default / framework error pages

Trigger and compare in [oxdf cheatsheet](https://0xdf.gitlab.io/cheatsheets/404)

- **IIS / .NET**: Unhandled exceptions often show a yellow screen of death with `Server Error in '/' Application`, a stack trace, and `Version Information: Microsoft .NET Framework Version:...`
- **PHP**: Fatal errors show `Fatal error: ... in /var/www/html/file.php on line 12` if `display_errors` is on — this leaks the full server path style (`/var/www/...` = Linux+Apache/nginx typical layout).
- **Apache default 403/404**: `Forbidden — You don't have permission to access ... on this server. Apache/2.4.41 (Ubuntu) Server`
- **Nginx default 404**: Plain `404 Not Found` followed by `nginx` or `nginx/1.18.0` in small text.
- **Rails**: a distinctive pink/red error page with `ActionController::RoutingError`.
- **Express/Node**: raw stack traces mentioning `at Layer.handle` or `node_modules`.

Try to actually **trigger an error**: request a nonexistent file with a weird extension, send a malformed header, send an overlong URL, or request a path with directory traversal characters (`../../`) — many stacks differ wildly in how they respond to this.

## 3. Case sensitivity of the URL path

This is cheap and very reliable:

```
GET /Login HTTP/1.1      → 200 (file found)
GET /login HTTP/1.1      → 200
```

- **IIS/.NET on Windows**: filesystem is case-*insensitive*, so `/Login`, `/LOGIN`, `/login` often all resolve the same.
- **Apache/nginx on Linux**: filesystem is case-*sensitive*, so changing case usually 404s.

This single test alone often tells you Windows+IIS vs. Linux+Apache/nginx.

## 4. Default/well-known file & directory probes

Try requesting stack-specific default files/paths:

```
/web.config            → IIS/.NET giveaway (even a 403 confirms the file exists)
/Web.config
/.htaccess              → Apache (usually 403, but confirms Apache is parsing it)
/.user.ini               → PHP-FPM/Apache
/wp-login.php            → PHP/WordPress
/index.php               → PHP
/index.aspx, /Default.aspx → .NET
/server-status            → Apache mod_status
/nginx_status              → Nginx stub_status
/phpinfo.php, /info.php    → sometimes left exposed, instantly confirms PHP + version
```

## 5. Cookie names (often untouched by WAFs/CDNs)

```
ASP.NET_SessionId=...         → .NET
ASPSESSIONID...                → Classic ASP
PHPSESSID=...                  → PHP
JSESSIONID=...                 → Java (Tomcat/JBoss/etc.)
```

## 6. OPTIONS / TRACE / unusual methods

```http
OPTIONS / HTTP/1.1

HTTP/1.1 200 OK
Allow: GET, HEAD, POST, OPTIONS, TRACE   # Apache often lists TRACE
```

IIS historically responds differently to `DEBUG`/`TRACK` methods; the exact `Allow:` list and its ordering varies by stack and is a decent fingerprint on its own.

## 7. Response to malformed/edge-case requests

This overlaps with what you already know (path normalization), but broaden it beyond just normalization:

- **Trailing dot / trailing slash handling**: `GET /page.` on IIS often behaves differently than on Apache (Windows strips trailing dots from filenames).
- **Null byte / encoded null**: `/page.php%00.jpg` — legacy PHP handling vs. others.
- **Double encoding**: `/..%252f..%252f` behaves differently across Apache/nginx/IIS URL decoders.
- **Backslash vs. forward slash**: IIS/.NET often treats `\` as a path separator; Apache/nginx usually don't.
- **Case of HTTP method**: some stacks (ASP Classic) are method-case-sensitive.


## 8. Timing / banner-grabbing at the TCP level (not HTTP)

If you have the ability to connect directly to the origin IP (bypassing a CDN), a raw `openssl s_client` or `nc` connection plus a malformed request line can sometimes get you an unfiltered banner the CDN would otherwise strip. Not always legal/appropriate depending on scope, so only do this on targets you're authorized to test this way.

---

One practical note: when WhatWeb/Wappalyzer "don't work," it's almost always because a **CDN or WAF (Cloudflare, Akamai, Fastly, etc.) sits in front of the origin** and normalizes/strips headers before they reach the tool. In that case, the techniques above that rely on **behavioral differences** (case sensitivity, error pages, default files) tend to survive the CDN layer, while header-based fingerprinting won't — which is exactly why they're worth trying first.
