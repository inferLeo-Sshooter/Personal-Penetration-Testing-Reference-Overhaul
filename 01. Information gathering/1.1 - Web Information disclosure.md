



# 1. Information Disclosure

Information disclosure (or information leakage) occurs when a website unintentionally reveals sensitive data, including:

* User data (usernames, financial info)
* Business/commercial data
* Technical details about the website or infrastructure

While leaking user or business data carries obvious risks, exposing technical information can be equally dangerous — it may reveal attack surfaces or provide the missing piece needed to execute complex, high-severity attacks.

Such leaks can happen passively during normal browsing, but attackers more commonly trigger them by interacting with the site in unexpected or malicious ways, then analyzing the responses for exploitable behavior.

---

## Examples of information disclosure

Some basic examples of information disclosure are as follows:
- Revealing the names of hidden directories, their structure, and their contents via a `robots.txt` file or directory listing
- Providing access to source code files via temporary backups
- Explicitly mentioning database table or column names in error messages
- Unnecessarily exposing highly sensitive information, such as credit card details
- Hard-coding API keys, IP addresses, database credentials, and so on in the source code
- Hinting at the existence or absence of resources, usernames, and so on via subtle differences in application behavior

---

## How Information Disclosure Vulnerabilities Arise

These vulnerabilities typically stem from three root causes:

* **Leftover internal content** — e.g. developer comments in markup that remain visible in production
* **Insecure configuration** — e.g. enabled debugging features or verbose error messages that hand attackers useful information
* **Flawed application behavior** — e.g. distinct responses for different error states, which can allow attackers to enumerate sensitive data like valid credentials

---

## Impact of Information Disclosure Vulnerabilities

The impact can be direct or indirect depending on what's exposed:

* **Sensitive user/business data** (e.g. credit card details) — high direct impact on affected parties
* **Technical information** (e.g. directory structure, third-party frameworks) — little direct impact, but can enable further exploits

**Assessing Severity**
Severity depends heavily on context and exploitability. Technical disclosures are rarely high-severity on their own — what matters is what an attacker can do with the information. For example, knowing a site's framework version is insignificant if patched, but critical if a known exploit exists for that version.

When testing, focus on **impact and exploitability** rather than flagging information disclosure in isolation — unless the leaked data is sensitive enough to warrant attention by itself.

# 2. Finding and Exploiting information disclosure

## 2.1 - Fuzzing

Submit unexpected data types and fuzz strings to interesting parameters, then observe responses closely — useful information can appear as explicit error messages, subtle behavioral differences, or even variations in response time.

Tools like **Burp Intruder** automate this process, allowing you to:
* Test high volumes of inputs using payload positions and pre-built wordlists
* Compare responses by status code, length, and response time
* Identify keywords (e.g. `error`, `SQL`) via grep matching
* Extract and compare interesting response content with grep extraction rules

The **Logger++** BApp extension is also useful, offering advanced filtering and highlighting to surface leaked sensitive data across all Burp tools.

> **Use BurpSuit for an general look, logging requests and first engage. Fuzzing with `ffuf` (check otehr files for `ffuf` useage)**

## 2.2 - Tools

### BurpSuite Pro Scanner

Burp Suite Professional's **Burp Scanner** automates vulnerability detection through live scanning while browsing or scheduled crawl-and-audit scans. It automatically flags information disclosure issues such as:

* Sensitive data in responses (private keys, email addresses, credit card numbers)
* Backup files and directory listings

### BurpSuite engagement tools

Accessible by right-clicking any HTTP message, Proxy entry, or site map item, these tools are particularly useful for finding information disclosures:

* **Search** — locate specific keywords or expressions using advanced options like regex or negative search
* **Find Comments** — extract developer comments from selected items, with direct access to the corresponding HTTP request/response
* **Discover Content** — uncover hidden directories and files not linked from the site's visible content

---

### Engineering Informative Responses

Beyond passively observing error messages, you can actively manipulate inputs to extract data through them. By studying how error messages change in response to different inputs, you can sometimes trigger the application into revealing arbitrary data.

One common technique is provoking invalid actions on specific data — for example, submitting an invalid parameter value to trigger a stack trace or debug response that exposes sensitive details.

# 3. Common sources of information disclosure

### Files for Web Crawlers
`/robots.txt` and `/sitemap.xml` often list directories crawlers should skip — frequently because they contain sensitive information. These files won't always appear in Burp's site map, so navigate to them manually.

### Directory Listings
Web servers misconfigured to list directory contents can expose sensitive files (e.g. temp files, crash dumps) not intended for public access. While not a vulnerability on their own, directory listings become a serious issue when combined with poor access controls.

### Developer Comments
Inline HTML comments are sometimes left in production code by mistake or oversight. Invisible on the rendered page but easily accessed via Burp or browser dev tools, they may hint at hidden directories or reveal application logic.

### Error Messages
Verbose error messages are one of the most common sources of information disclosure. They can reveal:
* Expected input types, helping narrow down exploitable parameters
* Technologies in use (template engines, databases, server versions) — useful for finding documented exploits or misconfigurations
* Open-source frameworks, whose public source code can aid in crafting exploits
* Differences in application behavior, which underpin techniques like SQL injection and username enumeration

```
# Break the query

GET /product?productId=1

GET /product?productId=invalid-chars
```

### Debugging Data
Debug messages and logs, if exposed in production, can provide attackers with highly valuable information including:

* Key session variable values manipulable via user input
* Back-end hostnames and credentials
* Server-side file and directory names
* Encryption keys for client-transmitted data

If debug output is written to a separate log file and an attacker gains access, it can reveal the application's runtime state and guide them in crafting input to manipulate application behavior.

### User Account Pages
Account pages contain sensitive data (email, phone, API keys) but are generally safe since users only access their own. However, logic flaws can allow attackers to view other users' data.

For example, if a site loads account data via a `user` parameter:

`GET /user/personal-info?user=carlos`

While full account takeover may be prevented, individual data-fetching logic is sometimes less robust. An attacker might not load another user's full profile, but could still manipulate the `user` parameter to retrieve specific data — like another user's email address — if that request lacks proper session validation.

This relates closely to access control and IDOR vulnerabilities, covered separately.

### Source Code Disclosure via Backup Files
Source code access makes it far easier for attackers to understand application behavior and launch high-severity attacks — especially since sensitive data like API keys and credentials are sometimes hard-coded.

While servers typically execute code files (e.g. `.php`) rather than returning them as text, backup files created by text editors (e.g. appending `~` or a different extension to the filename) may bypass this. Requesting a code file using its backup extension can sometimes return the raw source code in the response.

### Information Disclosure via Insecure Configuration
Misconfiguration is a common vulnerability source, often arising from poorly understood third-party technology settings or debugging options left enabled in production.

One example is the HTTP `TRACE` method — designed for diagnostics, it echoes back the exact request received. If left enabled, it can expose sensitive details such as internal authentication headers appended by reverse proxies.

### Version Control History
If a site exposes its `.git` directory in production (accessible via `/.git`), attackers can download it and open it locally to review version control history, including commit logs and changes.

This may not reveal the full source code, but diffing commits can expose code snippets and potentially hard-coded sensitive data within changed lines.

> If the **.git** directory is exposed, we can download it to our local git environmetn. (If using linux, try command `wget` to download).
> Once download, we can investigate further (If using linux, try tool called **git-cola** - UI friendly, then try to access version control history (**View → DAG**), revoke some commits to see more information, ...)
> Or launch `git dag` from the terminal in your repo). This opens the commit graph showing full version control history, where you can browse commits, view diffs, and inspect changed files.
