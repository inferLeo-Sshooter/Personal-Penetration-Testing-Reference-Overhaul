When testing for `reflected` and `stored XSS`, a key task is to identify the `XSS context`:
- The location within the response where attacker-controllable data appears.
- Any input validation or other processing that is being performed on that data by the application.
Based on these details, you can then select one or more candidate XSS payloads, and test whether they are effective.

### Tips:
1. Start small, from 1 simple syntax (`<`, `>`), tag (`<h1>`) to 1 payload, troubleshoot until it work
2. If the target blocks certain tags, then fuzz with [cheatsheet](https://portswigger.net/web-security/cross-site-scripting/cheat-sheet)
3. URL encode special chars when hosting your payload.

# 1. XSS between HTML tags

When the XSS context is text between HTML tags, you need to introduce some new HTML tags designed to trigger execution of JavaScript.

Some useful ways of executing JavaScript are:
```
"><svg/onload=confirm(1)>
<script>alert(document.domain)</script>
<img src=1 onerror=alert(1)>
```

# 2. XSS in HTML tag attributes

When the XSS context is into an HTML tag attribute value, you might sometimes be able to terminate the attribute value, close the tag, and introduce a new one. For example:
```html
"><script>alert(document.domain)</script>
```

More commonly in this situation, angle brackets (`<`, `>`) are **blocked or encoded**, so your input cannot break out of the tag in which it appears. Provided you can terminate the attribute value, you can normally introduce a new attribute that creates a scriptable context, such as an event handler. For example:
```html
" autofocus onfocus=alert(document.domain) x="
```

The above payload creates an `onfocus` event that will execute JavaScript when the element receives the focus, and also adds the `autofocus` attribute to try to trigger the `onfocus` event automatically without any user interaction. Finally, it adds `x="` to gracefully repair the following markup.

---

## 2.1 - XSS in scriptable context

Sometimes the XSS context is into a type of HTML tag attribute that itself can create a scriptable context. Here, you can execute JavaScript without needing to terminate the attribute value. For example, if the XSS context is into the `href` attribute of an anchor tag, you can use the `javascript` pseudo-protocol to execute script. For example:
```html
<a href="javascript:alert(document.domain)">
```

## 2.2 - XSS in Hidden Input Fields

You might encounter websites that **encode** angle brackets (`<`, `>`) but still allow you to inject attributes. Sometimes, these injections are possible even within tags that don't usually fire events automatically, such as a **canonical tag**:
```html
<head>
  <link rel="canonical" href="https://example.com/preferred-page">
</head>
```

You can exploit this behavior using `access keys` and user interaction on Chrome:
```html
<body>
  <a href="https://example.com" accesskey="h">Home</a>
</body>
```

`Access keys` allow you to provide keyboard shortcuts that reference a specific element. The `accesskey` attribute allows you to define a letter that, when pressed in combination with other keys (these vary across different platforms), will cause events to fire. Example payload:
```html
<input type="hidden" accesskey="X" onclick="alert(1)">

<link rel="canonical" accesskey="X" onclick="alert(1)" />
```

### What to look for

**Note**: This technique applies whenever you can inject **attribute content** into an element, but **not** break out into a new visible/interactive element or inject a `<script>` tag. Classic candidates:
- `<input type="hidden" ...>` fields that reflect user input in value, name, or a custom attribute
- `<link>` tags (e.g. `rel="canonical"` reflecting a URL parameter)
- `<meta>` tags reflecting query-string values
Any tag where your input lands **inside the tag's attribute list**, but output encoding/filtering prevents you from closing the tag and adding a new `<script>` element, or from using typical visible-element event handlers

### Requirements to work

For this technique to work, you need:

1. **An injection point inside an HTML tag's attribute area** (not inside a quoted attribute value you can't escape from — you need to be able to break out of the current attribute and add new ones).
2. **No filtering/encoding that blocks the `accesskey` and `onclick` attribute names**, or the characters needed to inject them (spaces, quotes, `=`).
3. **A CSP or attribute-based defense that doesn't specifically block inline event handlers** (if CSP disallows inline scripts/`unsafe-inline`, `onclick` won't execute).
4. **User interaction** — the victim must press the access key combination, so this is generally chained with social engineering (e.g., "Press `Alt+Shift+X` to continue") or delivered as part of a broader phishing/CSRF-style attack rather than a silent/zero-click exploit.

### Payload

1. **Confirm you can break out of the attribute**. Try injecting a quote to see if it breaks the HTML:
```html
xsstest123"
```
2. **Inject the payload**. If you can break out of the attribute, inject:
```html
" accesskey="x" onclick="alert(document.domain)" x="
```
- `"` — closes the existing attribute (e.g., `value="`)
- `accesskey="x"` — binds the element to a key combo
- `onclick="alert(document.domain)"` — your JS payload, fires when the access key is triggered
- `x="` — reopens a dummy attribute so the rest of the original markup (the closing `"` and `/>`) doesn't break the tag
3. For a **single-reflection point** where you don't need to worry about a second closing quote, the minimal payload is just:
```html
accesskey="X" onclick="alert(1)"
```
4. **Troubleshoot, trigger and verify**.
- If the same parameter is reflected more than once on the page, your injected `x="` needs to correctly consume the next reflection's leading content so it doesn't prematurely close things or generate broken HTML that gets sanitized.
- Adjust the dummy attribute's trailing quote/value based on what follows in the second reflection — test iteratively in the browser dev tools until the DOM parses cleanly with your `onclick` intact.
- Test the actual DOM behavior, **Windows/Linux**: `Alt + Shift + X`
- Test the actual DOM behavior, **macOS**: `Ctrl + Alt + X`

Overall, the output should look like this when you inspect it:
```html
<input type="hidden" accesskey="X" onclick="alert(1)">

# or

<link rel="canonical" accesskey="X" onclick="alert(1)" />
```
