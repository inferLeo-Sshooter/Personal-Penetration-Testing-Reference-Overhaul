# 1. Definition

## 1.1 - What is clickjacking?

Clickjacking is a trick where an attacker gets you to click something you can't actually see. You think you're clicking one thing on a normal-looking page, but you're really clicking a hidden button from a *different* website that's invisibly stacked on top.

<img width="635" height="406" alt="image" src="https://github.com/user-attachments/assets/cac54b4f-5253-4e37-9f53-cc0de02507e4" />

**Example:** You click a "Claim your prize!" button on some site. In reality, that button was invisible and stacked over the real "Send Payment" button of your bank's website (which was secretly loaded in the background). Your click "wins the prize," but it also just authorized a payment you never meant to make.

The trick works by layering:
1. An **invisible iframe** loading the real target site (e.g., your bank) on top
2. A **decoy page** underneath with fake content (like a "click to win" button)

**How is this different from CSRF?**
- **CSRF** forges an entire request silently — no click needed from you at all.
- **Clickjacking** *needs* you to actually click something — it just tricks you about what you're clicking on.

Because of this, CSRF tokens don't stop clickjacking — the request is 100% legitimate (it really is your logged-in session, on the real domain, in the real page). You're just clicking on it without knowing it.

## 1.2 - How to construct a basic clickjacking attack

Attackers use CSS to stack two layers:

```html
<head>
  <style>
    #target_website {
      position: relative;
      width: 128px;
      height: 128px;
      opacity: 0.00001;   /* nearly invisible */
      z-index: 2;         /* on top */
    }
    #decoy_website {
      position: absolute;
      width: 300px;
      height: 400px;
      z-index: 1;         /* underneath */
    }
  </style>
</head>
<body>
  <div id="decoy_website">
    ...fake "click here to win" content...
  </div>
  <iframe id="target_website" src="https://vulnerable-website.com">
  </iframe>
</body>
```

What each piece does:

| Property | Purpose |
|---|---|
| `opacity: 0.00001` | Makes the real (target) site's button invisible, but still clickable |
| `z-index: 2` vs `1` | Puts the invisible target on top of the decoy visually |
| `position` + `width/height` | Aligns the invisible real button exactly over the fake button so your click lands on the real one |

Some browsers (like Chrome) detect and block iframes that are *too* transparent, as a defense — so attackers tweak the opacity just enough to stay invisible without tripping that detection. Firefox historically didn't have this protection.

**How's the payload looks like on PortSwigger's Exploit Server:**
```html
<style>
    iframe {
        position:relative;
        width:$width_value;
        height: $height_value;
        opacity: $opacity;
        z-index: 2;
    }
    div {
        position:absolute;
        top:$top_value;
        left:$side_value;
        z-index: 1;
    }
</style>
<div>Test me</div>
<iframe src="YOUR-LAB-ID.web-security-academy.net/my-account"></iframe>
```
**Note:**
- **Render and test** the values for the `$height_value` and `$width_value` variables for suitable pixel value. (recommend starting from `1400px` and `500px`)
- Do the same with `$top_value` and `$side_value` variables of the **decoy web content**. (Start from `300px` and `60px`, then render and adjust until it's fit)
- While testing, set `$opacity` to `0.5` for better visual while you align the `iframe` actions and adjust the position values as necessary. For the submitted attack a value of `0.0001` will work.

**Good to know:**
Instead of fixed pixel values, you can use viewport-relative units so the iframe scales with whatever window size the victim has (**Note: If you use % viewport, you must apply to both target and decoy, in order to work correctly**):

```css
iframe {
    position: relative;
    width: 100vw;   /* 100% of viewport width */
    height: 100vh;  /* 100% of viewport height */
    opacity: $opacity;
    z-index: 2;
}
```

**Common scaling options:**

| Unit | Meaning |
|---|---|
| `100vw` / `100vh` | 100% of the visible browser viewport width/height — resizes live as the window resizes |
| `100%` | 100% of the parent container's size (only works if parent is also sized to fill screen, e.g. `html, body { width:100%; height:100%; margin:0; }`) |
| `100dvw` / `100dvh` | "Dynamic viewport" units — like `vw`/`vh` but account for mobile browser UI (address bars) appearing/disappearing, more reliable on mobile |

**Why this matters for alignment:**

The core problem with fixed `px` values is that the invisible iframe and the decoy content underneath need to line up **exactly**, but screen sizes, zoom levels, and devices vary. Using `vw`/`vh` (or `%`) means both layers scale together proportionally, keeping the overlay aligned across different screens rather than only working on one specific resolution.

For precise alignment of a *specific* button inside that iframe (rather than filling the whole screen), attackers combine viewport units for the iframe container with percentage-based `top`/`left` positioning for the decoy divs, so both scale together:

```css
.firstClick {
    position: absolute;
    top: 60%;   /* percentage instead of fixed px */
    left: 10%;
}
```

### Clickbandit

Although you can manually create a clickjacking proof of concept as described above, this can be fairly tedious and time-consuming in practice. Try using [Burp's Clickbandit](https://portswigger.net/burp/documentation/desktop/tools/clickbandit) tool instead. 

This lets you use your browser to perform the desired actions on the frameable page, then creates an HTML file containing a suitable clickjacking overlay. You can use this to generate an interactive proof of concept in a matter of seconds, without having to write a single line of HTML or CSS.

## 1.3 - How to prevent clickjacking attacks

There's an older browser-side trick called "frame-busting scripts" (JavaScript that tries to detect if a page is loaded in an iframe and breaks out of it). The problem is attackers have plenty of ways to defeat these scripts, so they're not reliable on their own.

The better approach is **server-side protection**: your server tells browsers "don't allow my page to be put inside an iframe" (or only allow it under specific conditions). This only works if browsers actually respect and enforce that instruction — but modern browsers do, which makes this the recommended defense today. There are two main mechanisms:

### X-Frame-Options header

This header lets a website say "here's who's allowed to frame me." It started as an unofficial Internet Explorer feature but got picked up everywhere.

**Block framing entirely:**
```
X-Frame-Options: deny
```

**Only allow your own site to frame itself:**
```
X-Frame-Options: sameorigin
```

**Only allow one specific trusted site to frame you:**
```
X-Frame-Options: allow-from https://normal-website.com
```

⚠️ Catch: browser support isn't fully consistent — for example, `allow-from` isn't supported in some versions of Chrome or Safari. So it shouldn't be your *only* line of defense.

### Content Security Policy (CSP)

CSP is a broader security header that also protects against other attacks like XSS, and it's the **currently recommended** way to prevent clickjacking, via the `frame-ancestors` directive.

It looks like this:
```
Content-Security-Policy: policy-here
```

Where `policy-here` is a set of rules separated by semicolons.

**Equivalent behaviors to X-Frame-Options:**

| X-Frame-Options | CSP equivalent | Meaning |
|---|---|---|
| `deny` | `frame-ancestors 'none'` | No one can frame this page |
| `sameorigin` | `frame-ancestors 'self'` | Only your own domain can frame it |

**Only allow your own domain:**
```
Content-Security-Policy: frame-ancestors 'self';
```

**Only allow a specific named site:**
```
Content-Security-Policy: frame-ancestors normal-website.com;
```

### Bottom line
- Frame-busting JS = weak, easily bypassed, don't rely on it alone.
- `X-Frame-Options` + CSP's `frame-ancestors` = the real defense, used together as layered protection.
- CSP needs to be carefully written and tested (a misconfigured policy can break your site or leave gaps), so treat it as one part of a broader security strategy, not a copy-paste fix.

A quick way to check whether a live site currently sends these headers (Look at or **Response Headers** for `x-frame-options` or `content-security-policy`):
```bash
curl -sI https://example.com | grep -i -E "x-frame-options|content-security-policy"
```
**If protected, you'll see something like:**
```
x-frame-options: SAMEORIGIN
content-security-policy: frame-ancestors 'self';
```
**If nothing prints at all** → the site isn't sending either header, meaning it likely has no clickjacking protection.

# 2. Exploitation

## 2.1 - Clickjacking with prefilled form input

Some forms let you pre-fill the fields using URL parameters (via GET), before the user even submits. This creates a nasty variant of clickjacking: the attacker doesn't just trick you into clicking submit — they also **pre-fill the form with data of their choosing.** You just provide the click.

**Example scenario:** A site lets you update your account email via a URL like:
```
https://victim-website.com/my-account?email=newemail@example.com
```

An attacker can put *their own* email address in that URL, load it invisibly in an iframe, and trick you into clicking the (invisible) "Save" button. Result: your account email silently gets changed to the attacker's email — often step one before a password reset takes over your account.

### Example attack page

```html
<style>
    iframe {
        position: relative;
        width: $width_value;
        height: $height_value;
        opacity: $opacity;   /* near-invisible */
        z-index: 2;          /* on top */
    }
    div {
        position: absolute;
        top: $top_value;
        left: $side_value;
        z-index: 1;          /* underneath, visible decoy */
    }
</style>

<div>Test me</div>

<iframe src="YOUR-LAB-ID.web-security-academy.net/my-account?email=hacker@attacker-website.com"></iframe>
```

### What's happening here

| Piece | Role |
|---|---|
| `<iframe src="...?email=hacker@attacker-website.com">` | The real site, loaded invisibly, **with the email field already pre-filled** using the attacker's chosen value in the URL |

So the victim thinks they're clicking a harmless button, but they're actually clicking **Submit** on a form that was already loaded with the attacker's data. One click, and their account setting just got changed to whatever the attacker wanted — no password, no visible page, no warning.

The basic clickjacking example tricks you into performing *an* action. This version goes further — the attacker also controls the *data* behind that action, which is often more dangerous (e.g., hijacking account recovery by swapping your email, not just liking a post or claiming a "prize").

## 2.2 - Frame busting scripts

Since clickjacking relies on a site being loaded inside someone else's iframe, one obvious fix is to stop your site from being frameable in the first place. One older way people tried to do this was with **frame busting scripts** — JavaScript that runs in the browser and tries to detect "am I being framed right now?"

These scripts (sometimes via browser extensions like NoScript) typically try to do things like:

- Check whether the page is the **top-level window** (i.e., not stuck inside someone else's frame)
- Force any frames to be **visible** instead of hidden
- **Block clicks** on invisible frames
- **Warn the user** if something suspicious looks like an attack

### The problem: attackers can bypass this pretty easily

A few reasons frame busters are unreliable:

- They behave differently across browsers/platforms — no consistent standard
- They're just JavaScript, so if the browser has JS disabled or restricted, the protection simply doesn't run
- HTML gives attackers a built-in workaround: the iframe `sandbox` attribute

### The classic bypass

Attackers can load the victim site in a sandboxed iframe like this:

```html
<iframe 
  id="victim_website" 
  src="https://victim-website.com" 
  sandbox="allow-forms">
</iframe>
```

Here's the trick: the `sandbox` attribute restricts what the framed page can do. If the attacker includes `allow-forms` or `allow-scripts` — but *deliberately leaves out* `allow-top-navigation` — the framed page still functions normally, **but it loses the ability to check whether it's the top window.**

Since that self-check is exactly what frame-busting scripts depend on to detect the attack, the sandbox quietly disables the defense while keeping the site usable enough for the attack to work.

| Value included? | Effect |
|---|---|
| `allow-forms` / `allow-scripts` | Lets the iframe still function (forms/scripts work) |
| `allow-top-navigation` (omitted) | Framed page **can't** tell if it's the top window → frame buster is blind |

### Takeaway

Frame busting is a **band-aid, not a real fix** — it runs client-side, depends on JavaScript, and has known, simple bypasses. This is exactly why the server-side headers (`X-Frame-Options` and CSP's `frame-ancestors`) covered earlier are the recommended real defense — the browser enforces them before the page (and any attacker-controlled JS trick) even gets a chance to run.

**Example attack page:**
```html
<style>
    ...< SIMILAR TO A BOVE >...
</style>
<div>Test me</div>
<iframe sandbox="allow-forms"
src="YOUR-LAB-ID.web-security-academy.net/my-account?email=hacker@attacker-website.com"></iframe>
```
- Notice the use of the `sandbox="allow-forms"` attribute that neutralizes the frame buster script.

## 2.3 - Combining clickjacking with a DOM XSS attack

So far, clickjacking has been treated as a standalone trick — like tricking someone into liking a Facebook page they never meant to. But clickjacking gets much more dangerous when it's used as a **delivery method** for a separate vulnerability, like DOM-based XSS.

The idea: if the attacker has already found an XSS bug on the target site (a way to inject malicious script through a URL parameter, for example), they don't need to trick the victim into visiting a suspicious XSS link directly — victims are often wary of that. Instead, they hide it inside a normal-looking clickjacking setup. The victim just clicks what looks like an innocent button, and that click silently triggers the XSS payload sitting in the invisible iframe underneath.

### Example attack page

```html
<style>
    ...< SIMILAR TO A BOVE >...
</style>

<div>Test me</div>

<iframe src="YOUR-LAB-ID.web-security-academy.net/feedback?name=<img src=1 onerror=print()>&email=hacker@attacker-website.com&subject=test&message=test#feedbackResult"></iframe>
```

### What's happening here

This looks almost identical to the earlier prefilled-form example — same overlay setup — but look closely at the `name` parameter in the iframe's URL:

```
name=<img src=1 onerror=print()>
```

That's not a normal name. It's an XSS payload:
- `<img src=1 ...>` — an image tag with a broken/fake source (`src=1`), so the image **fails to load**
- `onerror=print()` — when the image fails to load, this JavaScript runs instead

So instead of just changing a form value like before, this payload **injects and executes actual JavaScript** on the real site — in this demo it just pops the browser's print dialog (a harmless way to prove code execution), but in a real attack it could steal cookies, session tokens, or do anything else JS can do in that user's logged-in session.

### Why the combo is dangerous

| Step | What the victim experiences | What's actually happening |
|---|---|---|
| 1 | Sees an innocent-looking "Test me" button | Real vulnerable page is loaded invisibly underneath, with the XSS payload already baked into the URL |
| 2 | Clicks the button (e.g., to submit a form) | Click lands on the invisible page's real submit button |
| 3 | Nothing seems to happen | The feedback form submits with the malicious `name` field → XSS payload executes in the context of the real site |

**The key insight:** clickjacking isn't just "trick a click" — it's a *delivery mechanism*. Any attack that normally needs the victim to click something (submit a form, trigger a script via an injected parameter) can be smuggled in this way, making the payload invisible and the victim's involvement seem completely normal.

## 2.4 - Multistep clickjacking

Not every attack is a single click. Sometimes the attacker needs the victim to perform a whole *sequence* of actions — for example, tricking someone into buying a product means they'd first need to add it to their cart, *then* click "place order." A single hidden button isn't enough for that.

The solution: stack **multiple** invisible decoy targets, one for each step, and line each one up with a different real button on the page underneath — all within the same invisible iframe. As the victim clicks around what looks like a normal little game or page, they're actually walking through a multi-step process on the real site behind the scenes.

### Example: tricking a user into deleting their account

```html
<style>
    iframe {
        position: relative;
        width: $width_value;
        height: $height_value;
        opacity: $opacity;
        z-index: 2;
    }
    .firstClick, .secondClick {
        position: absolute;
        top: $top_value1;
        left: $side_value1;
        z-index: 1;
    }
    .secondClick {
        top: $top_value2;
        left: $side_value2;
    }
</style>

<div class="firstClick">Test me first</div>
<div class="secondClick">Test me next</div>

<iframe src="YOUR-LAB-ID.web-security-academy.net/my-account"></iframe>
```

### How the pieces fit together

| Element | Purpose |
|---|---|
| `.firstClick` div | Decoy positioned exactly over the real **"Delete account"** button |
| `.secondClick` div | Decoy positioned exactly over the **"Yes"** confirmation button that appears *after* the first click |
| One shared `iframe` | The real account page — reused for both steps, since clicking "Delete account" reveals the confirmation dialog in the same page |
| `top` / `left` per div | Each decoy needs its *own* coordinates, since the two real buttons are in different spots on the page |


### How you'd verify alignment is correct

Since the iframe is invisible, you can't just "see" whether the decoy lines up with the real button — you have to test it indirectly:

1. **Hover over "Test me first"** — if your cursor changes to a hand/pointer, that confirms the div is sitting exactly on top of a clickable element (the real "Delete account" button). If it doesn't change, the coordinates are off — adjust `top`/`left` in `.firstClick`.
2. **Click "Test me first"**, then **hover over "Test me next"** — same check, but now for the confirmation "Yes" button that only appeared after step 1. Adjust `.secondClick`'s coordinates if the hand cursor doesn't appear.

### Why this is trickier for attackers to pull off

- Alignment has to be **pixel-precise for every step**, not just one button
- Later steps often only appear *after* earlier ones (like a confirmation dialog) — so the attacker needs to know the exact resulting page layout at each stage
- Any layout shift (different browser, screen size, zoom level) can break the whole chain and either fail silently or accidentally expose the attack

This is also exactly why the defenses covered earlier — `X-Frame-Options` and CSP's `frame-ancestors` — are so effective: blocking framing at all stops the entire multi-step chain in one move, no matter how many steps the attacker chained together.
