# 1. Path Traversal & File Inclusion

Path traversal (also known as directory traversal) and file inclusion are closely related web application vulnerabilities that both stem from `improper input validation` and `insufficient sanitization` of user-supplied file path parameters. While they share a common root cause and are frequently chained together in real-world attacks, they differ meaningfully in their mechanism and security impact.

---

### Path traversal

**Path traversal** - allows an attacker to read arbitrary files on the server by manipulating file path inputs using sequences such as `../` to escape the application's intended directory scope. The attacker is not executing anything — they are simply forcing the application to *read* files it should not expose. 

This commonly targets sensitive resources such as application **source code** and **data**, **back-end credentials** and **configuration files**, and OS-level files like `/etc/passwd` (Linux) or `C:\Windows\boot.ini` (Windows). 

In more severe cases, if the application also permits file writes, an attacker may modify application behavior or data and ultimately achieve full server compromise.

---

### File inclusion

**File inclusion** - goes a step further: rather than simply reading a file, the application `loads and evaluates` it as executable code. This comes in two forms — **Local File Inclusion (LFI)**, where the attacker forces the application to include a file already present on the server, and **Remote File Inclusion (RFI)**, where a remotely hosted malicious file is included. 

LFI commonly surfaces in templating-based architectures where applications dynamically load page content via URL parameters — for example, `/index.php?page=about` or `/index.php?language=es.php`. When such a parameter lacks proper validation, it becomes an inclusion vector. The security impact of file inclusion extends significantly beyond information disclosure and can lead to **source code** disclosure, sensitive **data exposure**, and — critically — Remote Code Execution (RCE), often resulting in full server compromise.

---

**The key distinction** lies in whether the file is `read` or `executed`: `path traversal` is primarily an **information disclosure** vulnerability, while `file inclusion` enables **code execution**. That said, the two are frequently chained — an attacker might first exploit path traversal to exfiltrate a configuration file or database credentials, then leverage LFI to include a log file containing previously injected PHP code (a technique known as log poisoning) to achieve RCE. A concrete example of the combined attack surface:

```
# Basic LFI / path traversal — Linux
/index.php?language=/etc/passwd
/index.php?language=/../../../etc/passwd

# Basic LFI / path traversal — Windows
/index.php?language=C:\Windows\boot.ini
/index.php?language=/../../../C:\Windows\boot.ini
```

Mitigating both classes of vulnerability requires strict input validation, whitelisting of permitted file paths or identifiers, and avoiding the direct use of user-controlled input in filesystem operations.

## 1.1 - Path Traversal: Reading Arbitrary Files

Path traversal exploits the way web applications construct file paths by appending user-controlled input to a predefined base directory. Consider a shopping application that serves item images via a URL parameter:

```
https://insecure-website.com/loadImage?filename=218.png
```

Internally, the application resolves this by appending the supplied filename to a base path, reading from:

```
/var/www/images/218.png
```

When no input validation is in place, an attacker can manipulate the `filename` parameter to escape the intended directory. Supplying a direct absolute path like `/etc/passwd` won't work as-is — the application would look for `/var/www/images//etc/passwd`, which resolves incorrectly. The correct technique is using `../` sequences (parent directory references) to traverse *upward* through the directory tree until reaching the filesystem root, then specifying the target file:

```
https://insecure-website.com/loadImage?filename=../../../etc/passwd
```

The application then reads from:

```
/var/www/images/../../../etc/passwd
```

Each `../` steps one directory level up — from `images/` → `www/` → `var/` → filesystem root — ultimately resolving to `/etc/passwd`, a standard Unix file containing registered system user details. On Windows, both `../` and `..\` are valid traversal sequences, and the same technique applies:

```
https://insecure-website.com/loadImage?filename=..\..\..\windows\win.ini
```

A few practical notes on using traversal sequences:

- **Overshooting is safe** — once you reach the filesystem root `/`, any additional `../` sequences are silently ignored, so using more than necessary causes no errors.
- **Minimum depth** — for efficiency, calculate the exact depth needed. For a base path of `/var/www/html/`, three `../` sequences are sufficient to reach root.
- **Universal applicability** — this technique works regardless of whether the input is used directly as a path or appended to an existing base directory string.

# 2. Common obstacles

## 2.1 - Filename Prefix

When input is used within a filename prefix pattern:
```php
include("lang_" . $_GET['language']);
```

Standard path traversal (`../../../etc/passwd`) fails because it creates an invalid filename: `lang_../../../etc/passwd`

### Solution
Prefix your payload with `/` to treat the prefix as a directory:
```
language=/../../../etc/passwd
```

This converts `lang_/` into a directory component rather than part of the filename.

**Note:** This approach has limitations:
- May fail if the prefixed directory doesn't exist
- Can interfere with advanced techniques like PHP wrappers or RFI

This approach effectively bypasses the directory restriction by stepping out of the intended directory context.

---

## 2.2 - Appended Extensions

When the server automatically adds an extension to your input:
```php
include($_GET['language'] . ".php");
```

Basic LFI attempts fail because `/etc/passwd` becomes `/etc/passwd.php`

This is a common practice for:
- Convenience (users don't need to specify extensions)
- Security (limiting inclusion to specific file types)

When the application forces a `.php` extension, direct system file reading becomes more challenging as most system files don't have this extension.

This requires more advanced techniques beyond basic path traversal to bypass.

### Bypassing Appended Extensions

When applications force extensions (e.g., `.php`), two historical techniques may help bypass restrictions on older PHP versions.

### 1. Path Truncation (PHP pre-5.3/5.4)
- Exploits PHP's 4096 character string length limit
- PHP truncates strings exceeding this limit
- Attack method:
  ```
  ?language=non_existing_directory/../../../etc/passwd/./././[REPEATED to reach ~4096 chars]
  ```
- Generation example:
  ```
  echo -n "non_existing_directory/../../../etc/passwd/" && for i in {1..2048}; do echo -n "./"; done
  ```
- The appended `.php` extension gets truncated from the final processed path

### 2. Null Byte Injection (PHP pre-5.5)
- Exploits how PHP handled string termination
- Adding `%00` (null byte) at the end of a string terminates it
- Example: `/etc/passwd%00` causes `.php` to be ignored
- The server processes this as `/etc/passwd%00.php` but treats it as `/etc/passwd`

**Note:** These techniques are ineffective on modern PHP installations but may work on legacy systems.

---

## 2.3 - Second-Order attack

Second-order LFI attacks occur when applications securely handle direct user input but insecurely use stored values to access files.

**Key characteristics:**
- The payload is stored in one location (e.g., database) then used elsewhere
- Developers often secure direct input but trust database values

**Example scenario:**
- Web app allows downloading avatars via `/profile/$username/avatar.png`
- If username contains `../../../etc/passwd`, accessing the avatar URL may return system files
- The attack succeeds because the application treats database values as trusted

These attacks are particularly effective because the malicious input and the vulnerability exploitation happen at different stages, making them harder to detect during security reviews.

---

## 2.4 - Non-Recursive Path Traversal Filters

Basic LFI prevention often uses simple string replacement to remove path traversal sequences:

```php
$language = str_replace('../', '', $_GET['language']);
```

**Key vulnerability:** These filters typically run only once on the input string, not recursively on the result.

**Bypass techniques:**
- Using nested traversal patterns that produce valid traversal after filtering
- Example: `....//` becomes `../` after filtering
- Successful bypass: `....//....//....//....//etc/passwd`

**Other effective bypass patterns:**
- `..././` (becomes `../` after filtering)
- `....\/` (using escaped slash)
- `....////` (using multiple slashes)

These work because the filter processes the string only once, allowing specially crafted inputs to produce valid traversal sequences after the filtering operation.

---

## 2.5 - Encoding Bypass for Path Traversal Filters

Some web applications block specific characters like `.` or `/` to prevent path traversal attacks. These filters can often be bypassed using URL encoding techniques.

**Basic encoding bypass:**
- URL encode the path traversal characters
- `../` becomes `%2e%2e%2f`
- Example: `%2e%2e%2f%2e%2e%2f%2e%2e%2f%2e%2e%2f%65%74%63%2f%70%61%73%73%77%64` to access `/etc/passwd`

**Double encoding bypass:**
- Double URL encoding `../` characters. This results in `%2e%2e%2f` and `%252e%252e%252f` respectively.
- Various non-standard encodings, such as `..%c0%af` or `..%ef%bc%8f`, may also work.

**Important notes:**
- Encode ALL characters including dots (some encoders skip them)
- Double encoding (encoding an already encoded string) may bypass more sophisticated filters
- This technique is particularly effective against older PHP versions (pre-5.3.4) but works on newer systems with custom filters

URL encoding transforms blocked characters into their hexadecimal representation, which may pass through filters but get decoded before file inclusion occurs.

---

## 2.6 - Approved Paths Restrictions

Some applications use regex to limit file inclusion to specific directories:

```php
if(preg_match('/^\.\/languages\/.+$/', $_GET['language'])) {
    include($_GET['language']);
} else {
    echo 'Illegal path specified!';
}
```

**Bypass strategy:**
- Start with the approved path to satisfy the regex check
- Then use path traversal to escape the restricted directory
- Example: `./languages/../../../../etc/passwd`, `filename=/var/www/images/../../../etc/passwd`

**Discovery methods:**
- Analyze existing form submissions to identify approved paths
- Fuzz different directories until finding one that passes validation

**Combined defenses:**
- When multiple filters exist, combine bypass techniques
- Example: Start with approved path + URL encoding or recursive patterns

This technique works across various programming languages and frameworks since it exploits the fundamental path resolution mechanism rather than language-specific features.
