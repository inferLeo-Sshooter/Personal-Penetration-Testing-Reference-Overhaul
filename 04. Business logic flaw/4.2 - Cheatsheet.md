# Business Logic Vulnerability — Cheatsheet & Testing Checklist

---

## How to use this document

1. Run the **Global Recon Checklist** once per application/feature area.
2. For every flag raised, jump to the matching **flaw-type section** below and run its mini-checklist.
3. Log anything you exploit (or suspect but can't confirm) in the **Findings Log** template at the end.

---

## 0. Global Recon Checklist (run first, every time)

Walk every state-changing feature (cart, checkout, registration, password reset, admin actions, coupons, file upload, messaging) and ask:

- [ ] What does this feature *assume* about the user, the input, or the order of operations?
- [ ] Where is validation happening — client-side, server-side, or both?
- [ ] Is there a multi-step process? Map every step and every parameter at each step.
- [ ] Are there two or more code paths that *should* enforce the same rule? (e.g. registration vs. email-change, both gating access by domain)
- [ ] Does anything get encrypted/signed and handed back to the client? Note the cookie/token names.
- [ ] Are there discount, credit, loyalty-point, or "X for Y" mechanics?
- [ ] Is there a parser involved (email, URL, file type, JSON) that another part of the app re-parses independently?

**General technique, applicable everywhere:**
- [ ] Intercept every request with a proxy; replay with parameters removed, duplicated, reordered, or set to extreme values.
- [ ] Try negative numbers, zero, floats, huge integers, empty strings, null, arrays-where-scalar-expected.
- [ ] Skip steps in a workflow by jumping straight to a later endpoint.
- [ ] Repeat steps that should only be allowed once.
- [ ] Go backward — return to an earlier step after completing a later one.
- [ ] Watch for verbose errors/stack traces when input is malformed — they leak backend assumptions.
- [ ] If one form/endpoint mishandles something, check siblings (other forms touching the same backend logic likely share the bug).

## 1. Excessive Trust in Client-Side Controls

**Flawed assumption:** users only interact through the rendered UI, so client-side checks (disabled buttons, JS validation, hidden fields, dropdown-only values) are "good enough."

### Checklist
- [ ] Identify every client-side restriction: greyed-out buttons, JS min/max, read-only/hidden fields, dropdown/radio constrained values.
- [ ] Intercept the corresponding request and submit a value the UI would never allow (e.g. price, role, productId, discount flag).
- [ ] Check hidden form fields and disabled inputs — they're still submitted or can be edited and submitted.
- [ ] Confirm server re-validates types, ranges, and ownership (not just "is this field present").

### Example payload pattern
```
productId=1&redir=PRODUCT&quantity=1&price=1
→ productId=1&redir=PRODUCT&quantity=1&price=free   # or 0, or negative
```

### Verify/exploit
- [ ] Does the server accept the tampered value at face value?
- [ ] Does it produce a real business effect (price change, role change, item state change)?

## 2. Failing to Handle Unconventional Input

**Flawed assumption:** users will only ever submit "sane" values within expected ranges.

### Checklist
- [ ] For every numeric field (quantity, amount, balance, transfer): try negative numbers, zero, decimals, scientific notation, very large integers.
- [ ] For every string field: try empty string, extremely long strings, unicode/emoji, null bytes, type confusion (string where int expected).
- [ ] Ask: is there a min/max enforced? What happens exactly at the boundary, and one past it?
- [ ] Check for **integer overflow**: does the backend use a fixed-width integer (e.g. signed 32-bit) for money/counts? Push cumulative totals past the max to see if it wraps negative.
- [ ] Check for **truncation**: does the backend silently truncate long strings (emails, names, IDs) without re-validating the truncated result? If something meaningful (like a domain restriction) is checked *before* truncation but used *after*, that's exploitable.
- [ ] Re-test the same unconventional input across *every* form that shares the underlying field/logic — one weak handler often means several.

### Example reasoning
```
if ($transferAmount <= $currentBalance) { // process transfer }
```
A negative `$transferAmount` always satisfies this check and can reverse the direction of value flow.

### Verify/exploit
- [ ] Does the unconventional input bypass a limit, balance check, or validation gate?
- [ ] Does it cause a state the business never intended (negative total, reversed transfer, truncated identity match)?

## 3. Flawed Assumptions About User Behavior

Three common sub-patterns. Test all three on every authenticated/multi-step flow.

### 3a. "Trusted users stay trustworthy"
- [ ] Find any access control based on an *attribute* of the account (email domain, verified status, tier) rather than a fixed role.
- [ ] Check whether that attribute can be changed *after* the initial check (e.g. email change, profile edit) without re-verification.
- [ ] If changeable, change it to a privileged value and re-test the gated resource.

### 3b. "Users will always supply mandatory input"
- [ ] For every multi-parameter request, remove parameters **one at a time** (both name and value).
- [ ] Apply to URL params, POST body params, **and cookies**.
- [ ] Watch for: does removing a parameter skip a check that's conditionally executed only "if present"? (classic: `if (current-password) { verify }` — omit it, verification never runs)
- [ ] Follow the entire multi-step process to completion after tampering — effects may only appear later.

### 3c. "Users will follow the intended sequence"
- [ ] Map the full intended flow (step 1 → step 2 → ... → completion).
- [ ] Try jumping directly to the final/confirmation endpoint, skipping intermediate steps (payment, 2FA, role selection, verification).
- [ ] Try repeating an early step after a later one has already completed.
- [ ] Try going back to an earlier step after finishing the flow.
- [ ] During out-of-sequence testing, capture any errors — null/uninitialized value exceptions often reveal exactly what server-side state the next step assumed was already set.
- [ ] Specifically check: does a "default" state (e.g. default role, default cart total) favor the attacker if a step is skipped?

### Verify/exploit
- [ ] Confirm the bypassed/skipped step had a real enforcement purpose (payment, identity check, authorization).
- [ ] Confirm reaching the end state without it produces full business impact (privilege escalation, free order, account takeover).

## 4. Domain-Specific Flaws

These require understanding *what the business logic is supposed to guarantee*, not just generic input fuzzing.

### Checklist
- [ ] Identify every value that's calculated once based on a condition (discount %, shipping cost, loyalty tier, interest rate) and ask: **is the condition re-validated at the point the value is actually applied/redeemed?**
- [ ] For discount/coupon systems:
  - [ ] Does meeting a threshold (cart total, item count) get "locked in" even if the cart changes afterward?
  - [ ] Is "already used" tracked per-code, or could alternating between two+ valid codes bypass a same-code-reuse check?
  - [ ] Can a discount be combined with a redeemable instrument (gift card) to create a net-profit loop? (buy discounted gift card → redeem for full value → repeat)
- [ ] For any loop-able cycle (purchase → redeem → credit → purchase again): is there a rate limit, daily cap, or single-use enforcement, or can it be automated indefinitely?
- [ ] If the domain is unfamiliar (finance, supply chain, healthcare, etc.), research the domain's normal rules first — the bug is usually "the app forgot rule X applies at point Y," and you can't see that without knowing rule X.

### Verify/exploit
- [ ] Can you reproduce the cycle/bypass more than once?
- [ ] Does repeating it scale the impact (unlimited credit, unlimited discount) rather than being a one-off quirk?

## 5. Providing an Encryption Oracle

**Flawed assumption:** an encryption/decryption endpoint that reflects user input back as ciphertext (or vice versa) is "just" a notification/error feature — not a cryptographic primitive exposed to the attacker.

### Concept
- An **encryption oracle**: you control plaintext, the app encrypts it with its real key/algorithm and hands you the ciphertext.
- A **decryption oracle**: you control ciphertext, the app decrypts it and shows you the plaintext (confirms format, doesn't even need to be exploitable on its own).
- **Danger condition:** the *same key + algorithm* is reused for something sensitive (auth cookie, signed token, internal state) elsewhere in the app.

### Checklist
- [ ] Inventory every cookie/token the app issues. Are any clearly encrypted (high entropy, fixed block-size multiples, changes per session)?
- [ ] Look for any feature that reflects user input back inside an encrypted/signed blob — error messages, notifications, "remember this" features, preference cookies.
- [ ] Test: does changing your input change the *ciphertext* in a way that suggests it's directly encrypted (not just hashed/opaque ID)?
- [ ] Check ciphertext length behavior as you change plaintext length — block-aligned jumps (e.g. every 16 bytes) strongly suggest a block cipher (commonly AES) in a mode like CBC/ECB.
- [ ] Confirm whether the *same* key/algorithm secures something valuable (session/auth cookie, password reset token, role claim).
- [ ] If you can decrypt your own legitimate token via the oracle, do so — learn the **exact plaintext format** (delimiters, field order, e.g. `username:timestamp`).
- [ ] Check whether the oracle prepends/appends a fixed string before encrypting your input (e.g. an error message prefix). If so, that fixed prefix consumes whole cipher blocks predictably — work out the prefix length and how much padding you need to push your *controlled* content to a clean block boundary.
- [ ] Once aligned to a block boundary, determine whether you can isolate/strip the known prefix blocks from the ciphertext and leave only your forged content as a standalone valid ciphertext (classic CBC byte-block manipulation).
- [ ] Reassemble: take your forged ciphertext for a privileged plaintext (e.g. `administrator:<valid-timestamp>`) and substitute it into the sensitive cookie/token.

### Verify/exploit
- [ ] Submit the forged token in place of the legitimate one.
- [ ] Confirm the application decrypts and trusts it without additional integrity checks (no HMAC/signature validation, or the signature is derived from the same flawed scheme).
- [ ] Confirm real privilege change (e.g. admin session) results.

### Key things that make this exploitable (root causes to call out in a report)
- [ ] Key/algorithm reuse across unrelated security contexts.
- [ ] No authenticated encryption (no MAC/AEAD) — ciphertext can be tampered with and still decrypts "successfully."
- [ ] Predictable structure / fixed prefixes in the plaintext before encryption.
- [ ] No server-side semantic validation of the decrypted content (e.g. doesn't verify the user actually has the claimed role elsewhere).

## 6. Email Address Parser Discrepancies

**Flawed assumption:** every part of the application parses an email address the same way.

### Checklist
- [ ] Identify where email-domain checks gate access (admin registration, allow-listed domains, SSO routing).
- [ ] Identify all the *different* components that touch the email: the validator/registration check, the mail-sending/SMTP logic, any downstream display.
- [ ] Confirm baseline: does an obviously off-domain address get rejected?
- [ ] Test encoded-word syntax (`=?charset?encoding?text?=`) with common encodings (Q, Base64/B, UTF-8) — see if any get blocked as "suspicious" while others slip through.
- [ ] Specifically test less-common charsets (e.g. UTF-7) that can encode special characters like `@` or space within the encoded-word — these are less likely to be on a validator's blocklist.
- [ ] Craft a payload where the **visible/decoded-by-validator** string satisfies the domain check, but the **actual mail-routing** parser decodes a different `@`-target (your own mail server).
- [ ] Confirm delivery: does the confirmation/activation email actually land in your inbox even though the stored/displayed address shows the restricted domain?

### Verify/exploit
- [ ] Complete the full account flow (register → receive mail at your server → click confirmation) using the crafted address.
- [ ] Confirm the account now has whatever privilege the domain restriction was meant to gate (e.g. admin panel access).

### Root cause to call out
- [ ] Two independent email parsers (validation vs. delivery) with different RFC-compliance/strictness, and no canonicalization to a single parsed representation used consistently everywhere.

## Cross-Cutting Red Flags (any category)

While testing any feature, these signals usually mean "dig here":

- [ ] A value is checked once and trusted for the rest of a session/flow.
- [ ] Two code paths enforce the "same" rule but were clearly written/maintained separately.
- [ ] A feature reflects your input back to you in any transformed (encoded, encrypted, parsed, truncated) form.
- [ ] Verbose errors appear only under abnormal/out-of-sequence input.
- [ ] A discount, credit, or reward mechanism exists with multiple stacking/automatable steps.
- [ ] Anything client-side that *could* be the only enforcement (disabled button, hidden field, JS validation, dropdown-restricted value).
