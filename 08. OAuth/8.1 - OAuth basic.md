



# 1. OAuth definition

## 1.1 - What is OAuth?

OAuth is an authorization framework that lets websites request limited access to a user's account on another application — without exposing their login credentials. Users control exactly which data they share, avoiding full account handover to third parties.

It's commonly used to integrate third-party features (like accessing your contacts to suggest connections) and to enable "log in with [platform]" authentication flows.

**Example: Logging into Spotify with Google**

1. You click "Log in with Google" on Spotify
2. Spotify redirects you to Google's login page
3. You log in to Google (Spotify never sees your password)
4. Google asks: *"Allow Spotify to access your name and email?"*
5. You click "Allow"
6. Google sends Spotify a token — a temporary key proving you approved access
7. Spotify uses that token to grab only what it needs, nothing more

At no point does Spotify know your Google password. If you later want to revoke access, you just remove Spotify from your Google account's connected apps — no password change needed.

> **Note:** Although OAuth 2.0 is the current standard, some websites still use the legacy version 1a. OAuth 2.0 was written from scratch rather than being developed directly from OAuth 1.0. As a result, the two are very different.
> The term **"OAuth"** refers exclusively to **OAuth 2.0** throughout these materials.

---

## 1.2 - How it works

OAuth 2.0 is a widely-used authorization framework that enables applications to obtain limited access to user data without exposing credentials. It works by defining a structured set of interactions between four distinct entities.

---

### Entities

| Entity | Role |
|---|---|
| **Resource Owner** | The user who owns the data and grants access to it |
| **Client** | The application requesting access to the resource on behalf of the resource owner |
| **Authorization Server** | Authenticates the resource owner and issues access tokens to the client |
| **Resource Server** | Hosts the protected resources that the client wants to access |

> **Note:** These entities don't have to be physically separate systems. For example, the Authorization Server and Resource Server are often the same system.

---

### Abstract Communication Flow

At a protocol level, OAuth 2.0 follows this sequence of interactions:

1. The `client` requests authorization from the `resource owner`
2. The `client` receives an authorization grant from the `resource owner`
3. The `client` presents the authorization grant to the `authorization server`
4. The `client` receives an access token from the `authorization server`
5. The `client` presents the access token to the `resource server`
6. The `client` receives the requested resource from the `resource server`

### User-Facing Flow

From a practical standpoint, here is what the above typically looks like from the user's perspective:

1. The `client` application requests access to a subset of the `resource owner`'s data, specifying the grant type and scope of access needed
2. The `resource owner` is prompted to log in to the OAuth service and explicitly grant consent for the requested access
3. The `client` receives a unique access token proving it has the `resource owner`'s permission — exactly how this happens varies by grant type
4. The `client` uses the access token to make API calls to the `resource server` and fetch the relevant data

---

### Example

We will consider the following entities:
- `Resource owner`: The user, who we will name `John`
- `Client`: An imaginary cybersecurity training platform called `academy.htb`
- `Authorization Server`: An imaginary platform for version control called `hubgit.htb`
- `Resource Server`: For simplicity's sake, this is the same as the authorization server: `hubgit.htb`

Let us assume that `John` wants to login to `academy.htb` using his `hubgit.htb` account.Then, the communication flow may look like this:

1. `John` clicks `Login with hubgit.htb` on `academy.htb`. He is redirected to the login page of `hubgit.htb`.
2. `John` logs in to `hubgit.htb` and consents to giving access to his profile to the third-party service `academy.htb`. Afterward, `hubgit.htb` issues an authorization grant to `academy.htb`
3. `academy.htb` presents the authorization grant to `hubgit.htb`
4. `hubgit.htb` validates the authorization grant and issues an access token that enables `academy.htb` to access `John's profile`
5. `academy.htb` presents the access token to `hubgit.htb` in a request to an API endpoint that accesses `John's profile information`
6. `hubgit.htb` validates the access token and provides `academy.htb` with `John's profileinformation`

<img width="1264" height="696" alt="image" src="https://github.com/user-attachments/assets/33a3beb4-1f80-4278-9233-be80e6913a69" />

After the exchange, `academy.htb` can access `John's profile information` on `hubgit.htb`,i.e., make requests to `hubgit.htb` in `John's name`. This is achieved without sharing `John'scredentials` with `academy.htb`.

OAuth defines different `grants` used for different contexts and use cases. We will only lookat the two most common grant types, the `authorization code` grant and the `implicit` grant. 

For more details on the less common grant types, look at the `OAuth standard`. 

**Remember that not all requests are initiated from the user's browser. Some requests happendirectly between the client and resource server and are thus transparent to the user.**

---

### Summary

OAuth 2.0 separates the concerns of **authentication** (proving who you are) and **authorization** (granting access to specific resources), allowing users to give third-party applications limited access to their data without ever sharing their passwords.

# 2. OAuth Grant Types (Flows)

OAuth 2.0 can be implemented in several ways, known as **grant types** or **flows**. The grant type determines the exact sequence of steps in the OAuth process — including how the client communicates with the OAuth service and how the access token is ultimately delivered. The client specifies its desired grant type in the initial authorization request, provided the OAuth service has been configured to support it.

The two most common grant types are:

- **Authorization Code** — The most secure flow; suited for server-side applications
- **Implicit** — A simplified flow historically used for client-side (browser-based) apps

---

## 2.1 - OAuth scopes 

The `scope` parameter in an authorization request defines what data the client wants to access and what operations it can perform.

Scope names are arbitrary strings that vary significantly between providers — some use simple labels, others use full URIs:

`scope=contacts` `scope=contacts.read` `scope=contact-list-r` `scope=https://oauth-authorization-server.com/auth/scopes/user/contacts.readonly`

When OAuth is used for authentication, standardized **OpenID Connect** scopes are typically used instead — for example, `openid profile` grants read access to basic user info such as email and username.

---

## 2.2 - Authorization code grant

The **authorization code grant** is the most common and most secure OAuth 2.0 grant type. It is best suited for server-side applications where the source code is not publicly exposed.

What makes it secure is its use of a **back-channel**: starting from Step 4, all sensitive communication (exchanging the authorization code for an access token, and fetching user data) happens directly between the `client` and the `authorization server` — server-to-server, never through the user's browser. This means an attacker watching browser traffic cannot intercept the access token.

> **New to OAuth?** Before reading this, make sure you're familiar with the four OAuth entities: `resource owner`, `client`, `authorization server`, and `resource server`. The flow below involves all of them.

---

## Hostname Reference

The HTTP examples in this document use two concrete hostnames to make the flow easier to follow:

| Hostname | Role |
|---|---|
| `hubgit.htb` | Acts as both the `authorization server` and `resource server` |
| `academy.htb` | Acts as the `client` application |

In real-world OAuth, these would be services like `accounts.google.com` (authorization server) and `yourapp.com` (client).

---

## The 7-Step Flow

### Step 1 — Authorization Request

The `client` (`academy.htb`) initiates the flow by redirecting the user's browser to the `authorization server`'s (`hubgit.htb`) `/auth` endpoint:

```
GET /auth?
  client_id=1337
  &redirect_uri=http://academy.htb/callback
  &response_type=code
  &scope=user
  &state=a45c12e87d4522 HTTP/1.1
Host: hubgit.htb
```

> In generic terms: `GET /authorization?... HTTP/1.1 Host: oauth-authorization-server.com`

**Parameters:**

- `client_id` — The unique identifier for the `client`. Assigned when the client registers with the `authorization server`
- `redirect_uri` — Where the browser will be redirected after the `resource owner` approves (or denies) access. Also called the *callback URI*. Many OAuth vulnerabilities target this parameter
- `response_type` — Always set to `code` for this grant type, telling the server to return an authorization code
- `scope` — What resources the `client` is requesting access to (e.g. `user`, `openid profile`). Optional — if omitted, the server may apply a default scope
- `state` — A random value generated by the `client`, tied to the current session. Acts like a CSRF token to prevent request forgery. Optional but strongly recommended

---

### Step 2 — Resource Owner Authentication & Consent

The `authorization server` (`hubgit.htb`) presents the `resource owner` with a login page. After logging in, the user is shown a consent screen listing what the `client` is requesting access to, based on the `scope` parameter.

The user can choose to **approve or deny** the request.

> **Note:** On repeat visits, if the user already has a valid session and has previously approved the same scope, this step is skipped automatically — the user is logged back in with a single click.

---

### Step 3 — Authorization Code Grant

If the `resource owner` approves, the `authorization server` redirects the browser to the `redirect_uri` specified in Step 1, attaching a short-lived authorization code:

```
GET /callback?code=ptsmyq2zxyvv23bl&state=a45c12e87d4522 HTTP/1.1
Host: academy.htb
```

> In generic terms: `GET /callback?code=a1b2c3d4e5f6g7h8&state=ae13d489bd00e3c24 HTTP/1.1 Host: client-app.com`

**Parameters:**

- `code` — The authorization code issued by the `authorization server`. Short-lived and single-use
- `state` — Must match the `state` value from Step 1 — the `client` should verify this to confirm the request is legitimate

> The authorization code is **not** the access token. It is only a temporary code used to obtain the real token in the next step.

---

### Step 4 — Access Token Request

The `client` now exchanges the authorization code for an access token. This is the first **server-to-server** request — it goes directly from `academy.htb` to `hubgit.htb`, bypassing the browser entirely:

```
POST /token HTTP/1.1
Host: hubgit.htb

client_id=1337
&client_secret=SECRET
&redirect_uri=http://academy.htb/callback
&grant_type=authorization_code
&code=ptsmyq2zxyvv23bl
```

> In generic terms: `POST /token HTTP/1.1 Host: oauth-authorization-server.com`

**New parameters introduced here:**

- `client_secret` — A secret key assigned to the `client` during registration. Authenticates the `client` to the `authorization server` and is never exposed to the browser
- `grant_type` — Always set to `authorization_code` for this flow

> From this point on, all communication happens over a secure back-channel. An attacker monitoring browser traffic cannot see or tamper with these exchanges.

---

### Step 5 — Access Token Grant

The `authorization server` validates the request and responds with an access token:

```json
{
  "access_token": "RsT5OjbzRn430zqMLgV3Ia",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "user"
}
```

- `access_token` — The token the `client` will use to access protected resources
- `token_type` — Almost always `Bearer`, meaning whoever holds this token can use it
- `expires_in` — Token lifetime in seconds (here: 1 hour)
- `scope` — Confirms what access the token grants

---

### Step 6 — Resource Request

The `client` uses the access token to request the `resource owner`'s data from the `resource server`:

```
GET /user_info HTTP/1.1
Host: hubgit.htb
Authorization: Bearer RsT5OjbzRn430zqMLgV3Ia
```

> In generic terms: `GET /userinfo HTTP/1.1 Host: oauth-resource-server.com`

The token is passed in the `Authorization: Bearer` header — this proves to the `resource server` that the `client` has the `resource owner`'s permission.

---

### Step 7 — Resource Response

The `resource server` validates the token and returns the requested data:

```json
{
  "username": "john",
  "email": "[email protected]",
  "id": 1337
}
```

The `client` can now use this data for its intended purpose — for example, using the `id` or `email` as an identifier to create an authenticated session and log the user in.

---

<img width="837" height="607" alt="image" src="https://github.com/user-attachments/assets/847e1f31-ffef-46e1-a2b6-4b587ce42250" />

> Everything from step 4 onward happens over a secure back-channel — invisible to the browser and the end user.

> **In step 1**: *"Many OAuth vulnerabilities target this parameter"* — referring to `redirect_uri`.

But more broadly, the problematic steps are:

**Step 1 — `redirect_uri` validation**
If the `authorization server` doesn't strictly validate the `redirect_uri`, an attacker can swap it for a URL they control. The authorization code then gets delivered to the attacker instead of the legitimate `client`.

**Step 3 — `state` parameter**
If the `client` doesn't generate or verify the `state` value, the flow is vulnerable to CSRF — an attacker can trick a user into completing an OAuth flow that the attacker initiated.

**Step 4 — `client_secret` exposure**
If the `client` is a browser-based or mobile app, there's no safe place to store `client_secret` — it can be extracted. This is actually why the **Implicit grant type** exists as an alternative for those cases, trading security for practicality (and why it's now discouraged).

---

The biggest and most exploited one in practice is **Step 1 (`redirect_uri`)** — it's the entry point for authorization code interception attacks, which is one of the most well-known OAuth attack classes. Steps 3 and 4 follow closely behind.

---

## 2.3 - Implicit Grant

The **implicit grant** is a simplified OAuth 2.0 flow where the `client` receives an access token **immediately** after the `resource owner` gives consent — skipping the authorization code exchange step entirely. This makes it shorter and easier to implement than the authorization code grant, but at the cost of significantly lower security.

> **New to OAuth?** The implicit grant is best understood by contrast with the authorization code grant. The key difference is that there is **no back-channel** here — all communication, including the access token itself, travels through the browser.

---

## When is it Used?

The implicit grant was designed for cases where the `client` **cannot securely store a `client_secret`** on a back-end — most commonly:

- Single-page applications (SPAs)
- Client-side JavaScript applications
- Native desktop applications

Because these environments have no safe server-side storage, they cannot use the authorization code grant's server-to-server token exchange. The implicit grant trades back-channel security for practicality in these scenarios.

> **Deprecation notice:** OAuth 2.1 (currently in draft) removes the implicit grant entirely due to its security shortcomings. Use the authorization code grant with PKCE instead if your environment supports it.

---

### How it Differs from the Authorization Code Grant

| Aspect | Authorization Code Grant | Implicit Grant |
|---|---|---|
| Steps | 7 | 5 |
| Authorization code exchange | ✅ Yes | ❌ No — skipped |
| Back-channel (server-to-server) | ✅ Yes (from Step 4) | ❌ No — all via browser |
| Access token in browser | ❌ No | ✅ Yes — in URL fragment |
| `client_secret` required | ✅ Yes | ❌ No |
| Security level | Higher | Lower |

### The 5-Step Flow

### Step 1 — Authorization Request

The `client` (`academy.htb`) redirects the user's browser to the `authorization server` (`hubgit.htb`), just like in the authorization code grant — with one key difference: `response_type` is set to `token` instead of `code`:

```
GET /auth?
  client_id=1337
  &redirect_uri=http://academy.htb/callback
  &response_type=token
  &scope=user
  &state=a45c12e87d4522 HTTP/1.1
Host: hubgit.htb
```

> In generic terms: `GET /authorization?... HTTP/1.1 Host: oauth-authorization-server.com`

**Parameters:**

- `client_id` — Unique identifier for the `client`, assigned during registration
- `redirect_uri` — Where the browser will be sent after authorization. A common target for OAuth attacks
- `response_type` — Set to `token` to signal the implicit flow. This is what distinguishes it from the authorization code grant
- `scope` — The resources the `client` is requesting access to. Optional
- `state` — A random value acting as a CSRF token, tying the request to the current session. Optional but strongly recommended

---

### Step 2 — Resource Owner Authentication & Consent

The `authorization server` (`hubgit.htb`) prompts the `resource owner` to log in and presents a consent screen based on the requested `scope`. This step is identical to the authorization code grant.

The user can choose to **approve or deny** access.

---

### Step 3 — Access Token Grant

This is where the implicit grant diverges significantly. Instead of returning an authorization code, the `authorization server` sends the **access token directly** in the browser redirect — embedded as a **URL fragment** (after the `#`):

```
GET /callback#access_token=RsT5OjbzRn430zqMLgV3Ia&token_type=Bearer&expires_in=3600&scope=user&state=a45c12e87d4522 HTTP/1.1
Host: academy.htb
```

> In generic terms: `GET /callback#access_token=z0y9x8w7v6u5&token_type=Bearer&... HTTP/1.1 Host: client-app.com`

**Parameters in the fragment:**

- `access_token` — The token the `client` will use to access protected resources
- `token_type` — Always `Bearer`
- `expires_in` — Token lifetime in seconds
- `scope` — Confirms what access the token grants
- `state` — Must match the value from Step 1; the `client` should verify this

> **Important:** URL fragments are never sent to the server by the browser — they exist only on the client side. The `client` application must use JavaScript to extract the token from the fragment and store it in memory. This also means the token is **directly exposed in the browser**, making it vulnerable to interception via browser history, referrer headers, or malicious scripts.

---

### Step 4 — Resource Request

The `client` uses the extracted access token to request the `resource owner`'s data from the `resource server`. Unlike the authorization code grant, **this request also happens via the browser**:

```
GET /user_info HTTP/1.1
Host: hubgit.htb
Authorization: Bearer RsT5OjbzRn430zqMLgV3Ia
```

> In generic terms: `GET /userinfo HTTP/1.1 Host: oauth-resource-server.com`

---

### Step 5 — Resource Response

The `resource server` validates the token and returns the requested data:

```json
{
  "username": "john",
  "email": "[email protected]",
  "id": 1337
}
```

The `client` uses this data for its intended purpose — typically to create an authenticated session and log the user in.

### Security Considerations

The implicit grant exposes the access token in the browser at Step 3, which introduces several risks:

- **Token leakage via browser history** — URL fragments can be stored in browser history
- **Token leakage via referrer headers** — If the page loads external resources, the fragment may be exposed
- **No `client_secret`** — The `client` cannot authenticate itself to the `authorization server`, reducing trust
- **XSS exposure** — If the page has any cross-site scripting vulnerability, an attacker can steal the token from memory or the URL

For these reasons, the implicit grant should only be used when the authorization code grant is genuinely not possible, and only after the security trade-offs have been carefully evaluated.
