# 1. Access control

**Access control** restricts who or what can perform actions or access resources. In web applications, it works alongside two related concepts:

- **Authentication** — confirms a user is who they claim to be.
- **Session management** — links subsequent requests to that authenticated user.
- **Access control** — determines whether the user is permitted to perform a given action.

Broken access control is a common and often critical vulnerability. Because access control design must encode business, organizational, and legal rules into technical implementation, it's a complex, human-driven process prone to error.

## Vertical Access Controls
Restrict sensitive functionality to specific user types. For example, only administrators can modify or delete other users' accounts. Vertical controls often implement security principles like separation of duties and least privilege.

## Horizontal Access Controls
Restrict access to a subset of resources within the same category, based on user identity. For example, a banking app lets users view and pay from their own accounts only, not other users' accounts.

## Context-Dependent Access Controls
Restrict actions based on application state or workflow sequence, preventing actions performed out of order — e.g., blocking cart modifications after payment has been completed.

# 2. Examples of broken access controls

Broken access control vulnerabilities exist when a user can access resources or perform actions that they are not supposed to be able to.

## 2.1 - Vertical privilege escalation

- Occurs when users gain access to functionality above their permission level. For example, a regular user accessing an admin page to delete accounts represents vertical privilege escalation.

---

### Unprotected functionality

At its most basic, vertical privilege escalation occurs when an application fails to enforce protection on sensitive functionality. Admin features might only be *linked* from an admin's interface, but if the underlying URL isn't actually secured, any user can reach it directly:

```
https://insecure-website.com/admin
```

Such URLs can also leak through other channels, like `robots.txt`:

```
https://insecure-website.com/robots.txt
```

Even without disclosure, an attacker can often brute-force hidden paths using a wordlist.

#### Security Through Obscurity

Some applications try to hide sensitive functionality behind an unpredictable URL instead of properly restricting access:

```
https://insecure-website.com/administrator-panel-yb556
```

While not directly guessable, this approach is still insecure — the URL can leak in other ways. A common example is client-side JavaScript that builds the UI conditionally based on role:

```javascript
var isAdmin = false;
if (isAdmin) {
    var adminPanelTag = document.createElement('a');
    adminPanelTag.setAttribute('href', 'https://insecure-website.com/administrator-panel-yb556');
    adminPanelTag.innerText = 'Admin panel';
}
```

Even though the link only *renders* for admins, the script itself — including the hardcoded URL — is sent to and visible by every user, regardless of role. Obscurity is not a substitute for real access control.

---

### Parameter-based access control methods

Some applications determine a user's role or access rights at login, then store that value in a location the user can control — such as a `hidden field`, a `cookie`, or a `query string parameter`:

```
https://insecure-website.com/login/home.jsp?admin=true
https://insecure-website.com/login/home.jsp?role=1
```

The application then bases access control decisions on this submitted value. This is insecure: since the user controls the parameter, they can simply modify it (e.g., changing `admin=false` to `admin=true`) to gain unauthorized access to restricted functionality.

---

### Platform misconfiguration

Some applications enforce access control at the platform layer, restricting access to specific URLs and HTTP methods by user role. For example:

```
DENY: POST, /admin/deleteUser, managers
```

This denies `managers` from issuing `POST` requests to `/admin/deleteUser`. Several misconfigurations can undermine rules like this.

#### URL Override Headers

Some frameworks support non-standard headers — such as `X-Original-URL` or `X-Rewrite-URL` — that override the URL in the original request. If front-end access controls check only the visible URL but the backend honors these override headers, an attacker can bypass restrictions:

```
POST / HTTP/1.1
X-Original-URL: /admin/deleteUser
```

#### HTTP Method Switching

Access rules are often tied to a specific HTTP method (e.g., blocking `POST` but not `GET`). If the application accepts an alternate method to perform the same restricted action, an attacker can simply switch methods — for example, using `GET` instead of `POST` — to bypass the platform-layer control entirely.

---

### URL-matching discrepancies

Inconsistencies between how a website routes requests and how it enforces access control can create bypass opportunities.

**Case sensitivity:** A website's routing layer may tolerate inconsistent capitalization — mapping `/ADMIN/DELETEUSER` to the same endpoint as `/admin/deleteUser`. If the access control layer is stricter and treats these as separate endpoints, it may fail to apply restrictions to the variant.

**Suffix pattern matching:** In Spring applications with `useSuffixPatternMatch` enabled (the default prior to Spring 5.3), a request like `/admin/deleteUser.anything` still matches the `/admin/deleteUser` route, regardless of the arbitrary extension — potentially slipping past access controls.

**Trailing slashes:** Some systems inconsistently treat `/admin/deleteUser` and `/admin/deleteUser/` as distinct endpoints, allowing access controls to be bypassed simply by appending a trailing slash.

## 2.2 - Horizontal privilege escalation

Horizontal privilege escalation occurs when a user can access another user's resources rather than just their own — for example, an employee viewing another employee's records.

It often exploits the same mechanisms as vertical privilege escalation. If a user accesses their account via:

```
https://insecure-website.com/myaccount?id=123
```

an attacker may simply change the `id` value to access another user's account, data, and functions.

**Unpredictable identifiers:** Some applications use GUIDs instead of sequential IDs to prevent guessing. However, these GUIDs can still leak elsewhere in the app — e.g., in user messages, reviews, or other places that reference users.

**Partial leaks despite redirects:** Even when an application correctly detects unauthorized access and redirects to a login page, the redirect response may still contain sensitive data belonging to the targeted user — meaning the attack can succeed despite the apparent protection.

---

## 2.3 - Horizontal to vertical privilege escalation

A horizontal privilege escalation attack can often be escalated into a vertical one by targeting a more privileged user. If an attacker uses parameter tampering to access another user's account — and that user happens to be an administrator — they may gain administrative access.

For example, applying the same `id` manipulation used in horizontal attacks:

```
https://insecure-website.com/myaccount?id=456
```

If `id=456` belongs to an admin, the attacker could gain access to a page that discloses the admin's password, allows it to be changed, or grants direct access to privileged functionality — converting a horizontal exploit into full vertical escalation.

---

## 2.4 - Access control vulnerabilities in multi-step processes

Many sensitive functions are implemented as multi-step workflows — useful when capturing varied inputs or requiring user confirmation. For example, updating user details might involve:

1. Load the form with the user's current details.
2. Submit the changes.
3. Review and confirm.

Access control flaws arise when a website rigorously secures some steps but not others. If steps 1 and 2 are properly protected but step 3 isn't, the application is implicitly assuming users can only reach step 3 after completing the earlier, protected steps. An attacker can bypass this assumption entirely by skipping straight to step 3 and submitting the required parameters directly — gaining unauthorized access to the function.

---

## 2.5 - Referer-based access control

Some websites base access control decisions on the `Referer` header — a browser-supplied header indicating which page initiated a request.

For example, an application might robustly secure `/admin` itself, but for sub-pages like `/admin/deleteUser`, only check whether the `Referer` header points back to `/admin`. If it does, the request is allowed.

This is insecure because the `Referer` header is fully attacker-controlled. An attacker can simply forge a direct request to the sensitive sub-page with a fabricated `Referer` value, bypassing the check entirely and gaining unauthorized access.
