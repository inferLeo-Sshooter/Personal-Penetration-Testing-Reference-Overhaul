# 1. Core concepts

## 1.1 - What is a Race Condition?

A race condition happens **when**:
- a site `handles multiple requests at the same time without proper safeguards`.

**Cause**:
- threads to `collide` on the same data and `trigger unintended behavior`.

Attackers exploit this by sending precisely timed requests to force these collisions.

The brief moment when a collision can occur is called the **`race window`** — often just a fraction of a second. Like other logic flaws, the impact varies depending on where and how it occurs in the application.

---

## 1.2 - What is a Sub-State / Race Window?

**`Sub-state`** and a **`race window`** are closely related concepts that describe the temporary vulnerabilities created during concurrent request processing.

### Sub-State
A **sub-state** is a hidden, temporary state an app passes through 
*between* the start and end of processing a request.

From the outside it looks like one action — but internally it's multiple steps, and each step briefly changes the app's state.

```
User sees:   | POST /apply-coupon ---------> 200 OK |

Server does: | CHECK | APPLY | UPDATE |
                       ^-----^
                      sub-state
                     (race window lives here)
```

**Examples:**
- MFA login: session is valid, but MFA not yet enforced
- User registration: user exists in DB, but API key not initialized yet

### Race Window
The **race window** is the time gap *during* a sub-state where a collision is possible — typically milliseconds. The transition through a `sub-state` is what creates the `race window`

> Sub-state = **what** is temporarily vulnerable  
> Race window = **when** it's vulnerable

---

## 1.3 - TOCTOU

**Time-of-Check to Time-of-Use (TOCTOU)** is a type of race condition vulnerability that occurs when an application performs a security check and then acts on the results of that check, but the state of the data **changes in between the "check" and the "use"**.

In simple terms, a TOCTOU flaw follows this logic:
1.  **Check:** The application verifies a condition (e.g., "Is this discount code still valid?").
2.  **Window:** A small gap in time exists between the check and the next action.
3.  **Use:** The application performs an action based on the result of the initial check (e.g., applying the discount).

The vulnerability exists because an attacker can send a second, parallel request that arrives during the **race window**—the period after the first request's "check" but before it completes its final "update". This allows the attacker to **interact with the same data at the same time**, causing a "collision" where the second request is processed as if the first one never happened.

**Example of a TOCTOU Flaw:**
Consider a one-time use coupon:
*   **Step 1 (Check):** The server checks if the coupon has been used. It hasn't.
*   **Step 2 (Use):** The server applies the discount to the order.
*   **Step 3 (Update):** The server marks the coupon as "used" in the database.

```
Request 1:  [CHECK ✓] -----> [USE] -----> [UPDATE ✗ too late]
Request 2:  -------> [CHECK ✓] -----> [USE] -----> [UPDATE]
                          ^
                     race window
                  (R1 hasn't updated yet)
```

If you send two requests at nearly the same time, the second request might perform its **Check** (Step 1) before the first request has finished its **Update** (Step 3). Because the "check" and "use" are not atomic—meaning they don't happen as one inseparable operation—the application incorrectly allows the coupon to be used twice.

# 2. Tooling

> **Goal:** Understand *how* to send parallel requests before attempting any attack.  
> Without the right technique, your requests won't hit the race window reliably.

## Quick Reference

```
Target supports HTTP/2?
    YES --> Single-Packet Attack (Burp Repeater, auto)
    NO  --> Last-Byte Sync (Burp Repeater, auto fallback)

Attack is complex / needs 100+ requests?
    YES --> Turbo Intruder
    NO  --> Burp Repeater is enough
```

---

## 2.1 - Single-Packet Attack (HTTP/2)

Sends **20–30 requests inside one TCP packet**, so they arrive and get processed at virtually the same time.

This eliminates **network jitter** — the unpredictable per-request delay that normally prevents parallel requests from hitting the race window together.

```
Normal (sequential):   REQ1 --> [delay] --> REQ2 --> [delay] --> REQ3
                                  ^                    ^
                             jitter kills          race window
                             the timing              missed

Single-packet:         [ REQ1 | REQ2 | REQ3 | ... | REQ30 ]  <- one TCP packet
                           |       |       |
                           v       v       v
                        server processes all ~simultaneously
```

> **This is the preferred technique.** Use it whenever the target supports HTTP/2.

---

## 2.2 - Last-Byte Sync (HTTP/1 fallback)

HTTP/1 can't bundle requests in one packet, so Burp uses a workaround:

1. Send all requests with **everything except the last byte**
2. Hold them in a "ready" state
3. Fire **all final bytes at once** — forcing near-simultaneous arrival

```
REQ1:  [headers..................body] [last byte] -+
REQ2:  [headers..................body] [last byte] -+--> fired together
REQ3:  [headers..................body] [last byte] -+
                                        ^
                                   held, then released simultaneously
```

Less reliable than the single-packet attack, but works when HTTP/2 isn't supported.

---

## 2.3 - Burp Repeater vs Turbo Intruder

Burp Suite provides two tools for sending parallel requests. Choose based on what the attack needs:

| | Burp Repeater | Turbo Intruder |
|---|---|---|
| **Best for** | Quick tests, confirming a race | Complex, large-scale attacks |
| **Setup** | No config needed | Requires Python |
| **Request count** | Small groups | Hundreds+ |
| **Technique** | Auto (HTTP/2 → HTTP/1 fallback) | Manual control via `gates` |
| **Connection warming** | Manual | Built-in support |
| **Use when** | Exploring and validating | Exploiting reliably at scale |

### How to use Burp Repeater
- Add target requests into a **tab group**
- Select **"Send group in parallel"**
- Burp automatically picks single-packet or last-byte sync based on the server's HTTP version

### How to use Turbo Intruder
- Install via BApp Store
- Configure the request engine and use **`gates`** to queue and release requests simultaneously
- Useful for attacks requiring staggered timing, retries, or **connection warming** (sending a throwaway request first to pre-establish the back-end connection)

> **Rule of thumb:** Start with Repeater. Move to Turbo Intruder only when Repeater isn't enough.

## 3.1 - Limit Overrun

The most common race condition. Occurs when an attacker exceeds a limit imposed by the app's business logic by hitting the gap between **check** and **update**.

### Attack Flow

```
Request 1:  [CHECK ✓] ──────────────────────> [USE] ──> [UPDATE ✗ too late]
Request 2:       [CHECK ✓] ──> [USE] ──> [UPDATE]
                      ^
                 R1 hasn't updated yet —
                 both requests pass the check
```

### Common Targets

| Target | Example |
|---|---|
| Discount codes | Redeem a one-time coupon twice |
| Gift cards | Apply the same gift card value multiple times |
| Account balance | Withdraw more than the available balance |
| Rate limits | Bypass brute-force protection |
| User interactions | Rate a product multiple times |
| CAPTCHA | Reuse a single CAPTCHA solution across requests |

> Limit overrun is a subtype of TOCTOU — see section 1.3.

## 3.2 - Single-Endpoint Race

Sending **parallel requests with different values to the same endpoint** to cause a collision in how the app handles state during concurrent processing.

### Attack Flow

Classic example — password reset token hijack:

```
Attacker sends two reset requests from the same session simultaneously:

REQ1 [user=attacker] ──> write user_id=attacker ──────────────────>
REQ2 [user=victim]   ──────────> write user_id=victim
                                  ^
                             overwrites REQ1
                             before token is generated

Token generated AFTER collision:

  session.user_id = victim   ← from REQ2
  reset token     = abc123   ← generated once, tied to session

Result:

  token abc123 ──> sent to attacker's email  (REQ1 triggered the send)
  session      ──> holds victim's user_id

  Attacker resets victim's password using abc123.
```

### Why It's Hard to Trigger

- Internal operations must overlap in a **very specific order**
- Not always deterministic — requires **multiple attempts**
- **Email-based endpoints** are the best targets: emails are sent in a background thread *after* the HTTP response, which widens the race window

---

### 3.2.1 - Example — Single-Endpoint Race Condition (Email Claim)

#### Description
The email change feature stores only one pending address at a time, updating the same database entry on each request. A race window exists between when the confirmation email task is kicked off and when the template is rendered using the stored address. Sending two conflicting change requests in parallel can cause a confirmation email for `carlos@ginandjuice.shop` to be delivered to your own inbox.

#### Steps
- Send `POST /my-account/change-email` to Repeater and create a group with two tabs
- Set one request to your own exploit server address, the other to `carlos@ginandjuice.shop`
- Send in **parallel** — the race causes the confirmation email template to be rendered with the mismatched pending address
- Check your inbox: if the confirmation email body contains `carlos@ginandjuice.shop`, click the link to claim the address
- If not, resend in parallel and retry until the mismatch occurs
- Access the admin panel from your account page and delete `carlos`

#### Payloads

```http
# Request 1 — your address (triggers the email send)
POST /my-account/change-email HTTP/2
Host: <lab-id>.web-security-academy.net
Cookie: session=<your-session-token>
Content-Type: application/x-www-form-urlencoded

csrf=<csrf-token>&email=attacker@exploit-<YOUR-EXPLOIT-SERVER-ID>.exploit-server.net
```

```http
# Request 2 — target address (overwrites DB entry during race window)
POST /my-account/change-email HTTP/2
Host: <lab-id>.web-security-academy.net
Cookie: session=<your-session-token>
Content-Type: application/x-www-form-urlencoded

csrf=<csrf-token>&email=carlos@ginandjuice.shop
```

## 3.3 - Multi-Endpoint Race

Sending requests to **multiple different endpoints simultaneously** to exploit a logic flaw across a multi-step workflow.

### Attack Flow

Classic example — e-commerce checkout:

```
Normal flow:
  [add items] ──> [validate payment] ──> [confirm order]

Attack:
  [validate payment] ──────────────────────────> [confirm order]
       [add more items to basket] ──^
                                    │
                               race window:
                          payment validated but
                          order not yet confirmed
```

### Aligning Race Windows

When requests don't naturally hit the window together, use these techniques:

```
Requests not hitting the window together?
    │
    ├─> Caused by connection setup delay?
    │       YES --> Connection Warming
    │               Send 1-2 throwaway GET requests first
    │               to pre-establish the back-end connection
    │               before firing the real attack
    │
    └─> Endpoints process at different speeds?
            YES --> Abuse Rate / Resource Limits
                    Flood server with dummy requests to
                    trigger an intentional server-side delay,
                    making the single-packet attack viable
                    for slower endpoints
```

## 3.4 - Hidden Multi-Step Sequences

A single HTTP request can trigger **multiple hidden internal steps**, passing through sub-states before completing. If two requests overlap during these transitions, security logic can be bypassed entirely.

### Attack Flow

Classic example — MFA bypass:

```
Normal login flow (internal steps):
  [Step A] set user_id in session
  [Step B] enforce MFA flag
  [Done]   user is fully authenticated

Attack:
  REQ1 (login)              ──> [Step A: user_id set] ──> [Step B: MFA enforced]
  REQ2 (sensitive endpoint)       ──────────^
                                    hits here — after Step A,
                                    before Step B

  Result: REQ2 is processed as fully authenticated.
          MFA is bypassed.
```

### Why This Is Harder Than Limit Overrun

- The sub-state window is often **microseconds wide**
- The vulnerability is invisible from outside — requires inferring internal steps
- Any sensitive endpoint that involves multi-step state changes is a candidate

---

## 3.5 - Partial Construction

Occurs when an app creates an object across **multiple separate steps**, leaving a brief window where the object exists but is **not yet fully initialized**. An attacker can inject values that match the uninitialized state to pass security checks.

### Attack Flow

Classic example — API key during user registration:

```
Normal registration (internal steps):
  [Step 1] INSERT user record into DB
  [Step 2] SET api_key for that user     <-- separate SQL statement

              race window
         ┌────────┴────────┐
         │  api_key = null │  user exists, but key not set yet
         └────────┬────────┘
                  v
  Attacker sends: GET /api/user/info?user=victim&api-key[]=

  Server compares:
    attacker input ──> [] (empty array / null equivalent)
    DB value       ──> null (uninitialized)
                       match --> access granted
```

### Matching Uninitialized Values

| Framework | Syntax | Server receives |
|---|---|---|
| PHP | `param[]` | empty array |
| Ruby on Rails | `param[key]` (no value) | `nil` object |
| Generic | `param=` | empty string |

> Passwords can theoretically be targeted too, but are harder —  
> the injected value must generate a hash matching the uninitialized state.

# 4. Advanced Cases

> **Goal:** Understand two edge cases that aren't attack types themselves, but will block or mislead you during testing if you don't know about them.


## Quick Reference

```
Parallel requests processing sequentially?
    └─> Session-based locking — bypass with unique session tokens per request

App uses timestamps for token generation?
    └─> Time-sensitive attack — force same-millisecond arrival
        to generate identical tokens across accounts
```

---

## 4.1 - Session-Based Locking

Some frameworks process only **one request per session at a time**. This queues parallel requests from the same session and forces them to run sequentially — which makes race conditions impossible to trigger without knowing why.

### What It Looks Like

```
Normal (no locking):
  REQ1 ──────────────────>
  REQ2 ──────────────────>  <- processed concurrently
  REQ3 ──────────────────>

Session-based locking (PHP):

REQ1 [session=abc] ──>[LOCK]────────────────>[RELEASE]
REQ2 [session=abc]              ──>[LOCK]───>[RELEASE]
REQ3 [session=abc]                           ──>[LOCK]──>[RELEASE]
                    ^            ^            ^
                queued        queued       queued
                waits R1      waits R2     waits R3

```

### How to Bypass It

Send each parallel request with a **different session token**.

```
Bypass (unique sessions):

REQ1 [session=aaa] ──>[LOCK]──>[RELEASE]
REQ2 [session=bbb] ──>[LOCK]──>[RELEASE]  <- no shared queue
REQ3 [session=ccc] ──>[LOCK]──>[RELEASE]     processed concurrently
```

> The framework only locks requests that share the same session.  
> Different sessions = no queue = race window restored.

### Why This Matters

Session-based locking **masks race conditions** — if you don't account for it, you'll incorrectly conclude an endpoint isn't vulnerable when it actually is.

```
Requests processing sequentially despite parallel send?
    └─> Suspect session-based locking
        Fix: assign a unique session token to each request,
             then retest
```

---

## 4.2 - Time-Sensitive Attacks

Not a race condition in the traditional sense — but uses the **same parallel request techniques** to exploit apps that generate security tokens from timestamps instead of cryptographically secure randomness.

### The Core Flaw

```
Secure token generation:
  token = cryptographic_random()  <- unpredictable, unique every time

Vulnerable token generation:
  token = hash(current_timestamp) <- same input = same output
```

If two requests hit the server **at the exact same millisecond**, they get the **same timestamp** — and therefore the **same token**.

### Attack Flow

Classic example — password reset token prediction:

```
Attacker sends two reset requests simultaneously:

  REQ1 (attacker's account) ──┐
                               ├──> arrive same millisecond
  REQ2 (victim's account)   ──┘

  Server generates:
    REQ1 token = hash(14:23:05.381) = a3f9...
    REQ2 token = hash(14:23:05.381) = a3f9...  <- identical

  Attacker receives: a3f9... (for their own account)
  Victim receives:   a3f9... (same token)

  Attacker uses their token to reset the victim's password.
```

### Key Difference from Race Conditions

| | Race Condition | Time-Sensitive Attack |
|---|---|---|
| **Goal** | Cause a state collision | Predict or duplicate a token |
| **Technique** | Parallel requests | Parallel requests |
| **Exploits** | Processing gap between steps | Predictable token generation |
| **Result** | Logic bypass, limit exceeded | Account takeover via token match |

> The tooling is the same — single-packet attack, Burp Repeater — but the vulnerability being exploited is fundamentally different.

# 5. Methodology & Defense

> **Goal:** A repeatable process for finding and proving race conditions, plus how to fix them.

---

## 5.1 - Predict, Probe, Prove

The three-step framework for detecting and exploiting race conditions — especially hidden multi-step sequences.

---

### Step 1 — Predict

Don't test every endpoint. Focus on where collisions are *likely*.

```
Good candidates:
    ├─> Security-critical endpoints
    │       authentication, MFA, password reset,
    │       financial transactions, privilege checks
    │
    └─> Endpoints where parallel requests touch the same record
            e.g. two reset requests that both write to the same session
```

**Ask:** *If two requests hit this endpoint at the same time, do they interact with the same data?*  
If yes — it's worth probing.

---

### Step 2 — Probe

Establish a baseline, then look for anything that deviates.

```
1. Send requests sequentially
   (Burp Repeater → "Send group in sequence")
   └─> Record the normal response, state, emails, etc.

2. Send the same requests in parallel
   (Burp Repeater → "Send group in parallel")
   └─> HTTP/2: single-packet attack (preferred)
       HTTP/1: last-byte sync (fallback)

3. Compare:
   Any difference = a clue

   Clues include:
     - Different HTTP response codes or bodies
     - Different email contents received
     - Unexpected change in application state
     - One request succeeds where it normally wouldn't
```

> You can also use the **"Trigger race conditions"** custom action in Burp Suite to send parallel requests in one click.

---

### Step 3 — Prove

Confirm the vulnerability is real and reproducible.

```
1. Remove superfluous requests
   └─> Isolate only the requests involved in the collision

2. Reproduce the effect consistently
   └─> A one-time fluke is not a proven race condition

3. Map the impact
   └─> Race conditions are structural weaknesses —
       think about what the resulting application state
       actually allows an attacker to do
```

---

## 5.2 - Limit Overrun: Simpler Flow

For basic limit overruns, the process is more direct:

```
1. IDENTIFY
   └─> Find a single-use or rate-limited endpoint
       with security impact (coupon, withdrawal, etc.)

2. EXECUTE
   └─> Send multiple parallel requests to the same endpoint

3. VERIFY
   └─> Did you exceed the intended limit?

Primary challenge: aligning the race window
(often only a few milliseconds wide)
```

---

## 5.3 - Alignment Troubleshooting

If your parallel requests aren't hitting the race window together, work through this in order:

```
Requests not colliding?
    │
    ├─> Back-end connection delay?
    │       └─> Connection Warming
    │           Send a throwaway GET request first
    │           to pre-establish the connection,
    │           then fire the real attack
    │
    ├─> Endpoints processing at different speeds?
    │       └─> Abuse Rate / Resource Limits
    │           Flood with dummy requests to trigger
    │           a server-side delay on the faster endpoint,
    │           bringing it in line with the slower one
    │
    └─> Requests processing sequentially despite parallel send?
            └─> Session-Based Locking
                Assign a unique session token to each request
                to force concurrent processing
```

---

## 5.4 - Prevention

Race conditions are caused by **non-atomic state changes** — fixing them means eliminating sub-states on sensitive endpoints.

| Problem | Fix |
|---|---|
| Check → use → update gap | Wrap in a single DB transaction (atomic) |
| Duplicate actions possible | Add a DB uniqueness constraint |
| Mixed storage layers | Keep state in one consistent layer |
| Timestamp-based tokens | Use cryptographically secure random values |
| Session state mid-flight | Handle session consistency server-side |

```
Core principle:
    State changes on sensitive endpoints must be ATOMIC —
    all steps succeed together, or none of them do.
    No sub-states = no race window = no collision.
```
