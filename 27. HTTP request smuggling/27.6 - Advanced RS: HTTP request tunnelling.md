# HTTP request tunnelling

Every technique we've covered so far (response queue poisoning, request splitting, etc.) depends on one key thing: the front-end and back-end **reuse the same connection** across multiple different users' requests. That's what lets you mess with *other people's* traffic.

But what if the servers don't reuse connections that way? **Request tunnelling** is the answer for that scenario — a more limited, but still dangerous, technique that works even when connections are never shared between users.

---

## The Setup: When Connection Reuse Isn't Available

Some servers reuse connections freely. Others are stricter — for example, only reusing a connection for requests from the *same* client/IP, or not reusing it at all.

```
Strict setup:
You  ──(your own private connection)──>  Back-end
Someone else ──(their own private connection)──>  Back-end
```

If every user gets their own private connection, classic request smuggling loses its power — you have no way to "poison" a queue that only you are using. There's no one else's traffic sharing your pipe to interfere with.

**But here's the loophole:** even on your own private connection, you can still trick the back-end into treating **one request you sent as two**. The back-end will then send back **two responses** — even though the front-end only asked for one.

```
You send:        [ One request, cleverly split ]
Back-end sees:    [ Request A ][ Request B ]
Back-end sends:   [ Response A ][ Response B ]
Front-end expects: [ One response ]
```

This means you can potentially **hide an entire second request (and its response) from the front-end** — smuggling it through without the front-end's security controls ever inspecting it. That's request tunnelling: not powerful enough to attack *other users*, but still powerful enough to **sneak your own hidden request past front-end defenses**, including some that were specifically built to stop smuggling.

---

## Why HTTP/2 Makes This Easier to Detect

Request tunnelling works over both HTTP/1 and HTTP/2, but it's much easier to *confirm* over HTTP/2.

- **In HTTP/1:** connections are often kept alive (`keep-alive`) and reused for several exchanges anyway. So getting back two responses doesn't necessarily *prove* you tunnelled a request — it might just be normal keep-alive behavior.
- **In HTTP/2:** each "stream" (HTTP/2's term for one request/response exchange) is supposed to carry **exactly one** request and **one** response — no exceptions. So if you send one HTTP/2 request and get back a response that has what looks like a *whole extra HTTP/1-style response* stuffed inside its body, that's a dead giveaway: you successfully tunnelled a second request through.

## Leaking Internal Headers via Tunnelling

Earlier techniques for revealing "hidden" internal headers (headers the front-end adds automatically, like internal auth tokens) relied on connection reuse. Since tunnelling doesn't have that available, here's a different trick that works using HTTP/2 downgrading instead.

**The idea:** trick the front-end and back-end into disagreeing about **where the headers end and the body begins.**

### Example

**What's sent over HTTP/2:**

| Field | Value |
|---|---|
| `:method` | `POST` |
| `:path` | `/comment` |
| `:authority` | `vulnerable-website.com` |
| `content-type` | `application/x-www-form-urlencoded` |
| `foo` | `bar\r\nContent-Length: 200\r\n\r\ncomment=` |
| `x` | `1` |

Both servers agree there's only **one** request here — but they disagree about **where the header section stops**:

- **Front-end's view:** it sees `foo`'s value as just a normal (if weird) header value. So it treats everything as headers, and appends any *internal* headers it wants to add (like an internal auth token) **after** the `comment=` text — because as far as it's concerned, that text is still part of the header section.
- **Back-end's view:** it sees the `\r\n\r\n` sequence inside `foo`'s value and interprets that as "headers are done, body starts now." So everything from `comment=` onward — including whatever internal headers the front-end just tacked on — gets swallowed into the **body**, as the value of a `comment` parameter.

**What the back-end actually receives:**

```http
POST /comment HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 200

comment=X-Internal-Header: secretContent-Length: 3
x=1
```

The internal header (`X-Internal-Header: secret`) — something the front-end normally adds silently and strips out before you'd ever see it — has now leaked straight into the `comment` field, where the application will likely just... display it back to you. 🎯

## Blind Request Tunnelling

Once you've tunnelled a request, you obviously want to *see* the response to it. But that's not guaranteed:

- **Some front-ends forward everything** they receive from the back-end. If you tunnel a request, both responses get bundled together and sent back to you — with the tunnelled response nested inside the body of the main one. 👍 Easy.
- **Other front-ends only read exactly as many bytes as the `Content-Length` header says.** In this case, only the *first* response gets forwarded to you — the second (tunnelled) response is generated by the back-end, but you never actually see it.

That second scenario is called **blind request tunnelling** — you know you successfully tunnelled a request (because, say, it triggers a side effect), but you can't directly read its response.

---

## Making It Non-Blind Using HEAD Requests

There's a clever workaround for blind tunnelling: using `HEAD` requests to trick the front-end into over-reading the response.

**Background:** a response to a `HEAD` request normally has **no body** — but it still often includes a `Content-Length` header, showing what the body length *would* be if you'd sent a `GET` request instead. Some front-ends get sloppy here: they see that `Content-Length` value and try to read that many bytes anyway, even though a `HEAD` response is never supposed to actually contain a body.

**How to abuse this:** if you tunnel a request behind a `HEAD` request, the front-end's buggy "over-reading" behavior can accidentally pull in bytes from the response to your **tunnelled** request — letting you read at least part of it.

### Example

**Request sent:**

| Field | Value |
|---|---|
| `:method` | `HEAD` |
| `:path` | `/example` |
| `:authority` | `vulnerable-website.com` |
| `foo` | `bar\r\n\r\nGET /tunnelled HTTP/1.1\r\nHost: vulnerable-website.com\r\nX: x` |

**What comes back:**

```
:status         200
content-type    text/html
content-length  131

HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 4286

<!DOCTYPE html>
<h1>Tunnelled</h1>
<p>This is a tunnelled respo
```

Notice the response got **cut off mid-sentence** (`"...tunnelled respo"`). That's because the front-end used the `content-length: 131` from the `/example` `HEAD` response to decide how many bytes to read — but that number has nothing to do with the *actual* tunnelled response's real length. It's essentially reading the wrong ruler.

### The Balancing Act

This technique is finicky because you're mixing a `Content-Length` value from **one** response with the actual body of a **different** response:

- If the `HEAD` endpoint's "would-be" length is **too short** → your tunnelled response gets truncated (cut off early), like in the example above.
- If it's **too long** → the front-end waits around for bytes that will never arrive, and you get a timeout.

### Fixes / Workarounds

- **Pick a different endpoint** for your `HEAD` request — one whose resource length happens to better match what you need.
- **If too short:** find some reflected input on the `HEAD` endpoint (like a query parameter that gets echoed back) and use it to pad out the *apparent* content-length, even though you won't see that padding reflected yourself.
- **If too long:** similarly, use reflected input inside the *tunnelled* request to artificially inflate the length of the tunnelled response, so it meets or exceeds what the front-end expects.

With some trial and error, this lets you dial in the numbers and read out the full tunnelled response.

## Web Cache Poisoning via Tunnelling

Here's where non-blind tunnelling gets seriously dangerous: you can effectively **mix the headers from one response with the body of a completely different one.**

**The key insight:** if the *tunnelled* response contains unescaped user input (like a JSON field reflecting something you typed), but is normally served with a "safe" content type like `application/json`, browsers won't execute it as HTML/JS — JSON isn't runnable. Harmless, right?

### Example — before tunnelling (harmless on its own)

```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "name" : "test<script>alert(1)</script>" }
```

Since the `Content-Type` says `application/json`, the browser just displays this as text — the `<script>` tag never executes.

### Example — after tunnelling (dangerous!)

But if you **tunnel** the request that generates this response, it ends up nested inside the *body* of a different response — one that inherited a **different** `Content-Type`, like `text/html`:

| Field | Value |
|---|---|
| `:status` | `200` |
| `content-type` | `text/html` |
| `content-length` | `174` |
| *(body)* | `HTTP/1.1 200 OK`<br>`Content-Type: application/json`<br><br>`{ "name" : "test<script>alert(1)</script>" }` |

Now the browser thinks it's looking at an HTML page — and the same `<script>` payload that was harmless a moment ago **now executes**, because it's being interpreted as real HTML content.

**Why this is extra severe:** since caching typically happens at the front-end layer, if this poisoned response gets cached, **every other visitor** who requests that same cached resource could also receive (and execute) the malicious payload — turning a single tunnelling exploit into a persistent, site-wide XSS attack.

## Summary Table

| Concept | What It Means |
|---|---|
| **Request tunnelling** | Sneaking a second, hidden request/response past the front-end, using only your *own* connection (no need for connection reuse) |
| **Why it's more limited** | You can't interfere with *other users'* traffic — only hide extra requests within your own |
| **HTTP/2 detection** | A "stream" should only ever hold one request/response — finding two proves tunnelling worked |
| **Leaking internal headers** | Exploit a front-end/back-end disagreement on where headers end, to leak internal headers into a body param |
| **Blind tunnelling** | You tunnel a request successfully, but can't see its response (front-end only reads the declared `Content-Length`) |
| **Non-blind via HEAD** | Abuse a front-end that over-reads based on a `HEAD` response's (bodyless) `Content-Length`, leaking part of the tunnelled response |
| **Cache poisoning via tunnelling** | A tunnelled response's body can "inherit" a different, more dangerous `Content-Type` — turning safe JSON into executable HTML, then caching it for everyone |
