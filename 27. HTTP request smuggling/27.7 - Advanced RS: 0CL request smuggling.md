# 1. What Does "0.CL" Mean?

**`0.CL` means something different: the front-end doesn't use *any* length header at all.** It treats the request as having **zero** body length (hence the `0`) — effectively ignoring the `Content-Length` header entirely. Meanwhile, the back-end **does** read and trust that `Content-Length` header, and expects a body of whatever size it specifies.

```
Front-end's view:  "This request has no body. Done."
Back-end's view:   "Content-Length says there's a body coming. I'll wait for it."
```

---

## Why This Was Considered "Unexploitable": The Deadlock

Here's the problem that stumped everyone for years.

Imagine the attacker sends a request where the front-end thinks there's no body, but the back-end (correctly reading `Content-Length`) is now waiting for one.

### Example

```http
GET /Logon HTTP/1.1
Host: vulnerable-website.com
Content-Length:
 7

GET /404 HTTP/1.1
X: Y
```

(Note: the `Content-Length` header value is split onto the next line with a leading space — a subtle formatting trick some front-ends fail to recognize as a valid header, causing them to miss it entirely.)

**What happens on each side:**

- **Front-end:** since it never "saw" a valid `Content-Length`, it assumes the request ends right after the headers. It treats the trailing text (`GET /404 HTTP/1.1...`) as the start of a **second, separate request** — and holds onto it, waiting to send it along once the first request's turn is done.
- **Back-end:** it *did* see `Content-Length: 7`, so it thinks there's a 7-byte body still coming. It just... waits for those bytes to arrive.

Now both sides are stuck:

```
Front-end: "I'm not sending anything else until I get a response to request #1."
Back-end:  "I'm not responding to request #1 until I receive its 7-byte body."
```

Nobody moves. Eventually one side gives up (times out) and the connection gets killed. **This deadlock is why 0.CL was long assumed to be a dead end** — you could find the bug, but you could never actually *do* anything with it.

---

# 2. Breaking the Deadlock

Researchers eventually found a way around this using two key tricks combined: an **early-response gadget**, followed by a **double desync**.

## Trick #1: The Early-Response Gadget

The core problem is that the back-end *waits* for the body before responding. So — what if you could make the back-end respond **before** it finishes waiting for that body?

That's exactly what an **early-response gadget** is: any quirky server behavior that causes it to send back a response **immediately**, without waiting for the rest of the request to arrive.

One real-world example researchers found: some servers (like IIS on Windows) have legacy quirks around certain reserved filenames — like `CON`, `PRN`, `AUX`, `NUL` — which are reserved at the operating-system level for historical reasons. Requesting a path like `/con` can trigger an immediate error response from the server, **without it waiting for the rest of the request body** — breaking it out of the "patiently waiting" deadlock state.

```
GET /con HTTP/1.1
Host: vulnerable-website.com
Content-Length:
 7

```

→ The back-end immediately replies (e.g. with a `200 OK`) **without waiting** for those promised 7 bytes of body — and crucially, it leaves the connection **open** for the next request.

Different servers have different quirks that can act as this kind of gadget — sometimes it's a weird filename, sometimes it's a built-in redirect behavior. The key requirement is just: *something* that makes the back-end jump ahead and respond early.

## Trick #2: The Double Desync

Getting an early response breaks the deadlock, but on its own it just proves the bug exists — it doesn't give you a *useful*, repeatable attack yet. For a real exploit, attackers need to convert this fragile, one-off 0.CL glitch into something more stable and controllable: a **CL.0 desync** (the reverse scenario, which is much easier to weaponize).

This conversion is done using a **double desync** — essentially a two-step combo attack:

1. **First request:** poisons the connection using the 0.CL bug (with the early-response trick to avoid deadlocking).
2. **Second request:** because the connection is now already "confused" from step 1, this second request gets desynced too — but this time, it flips into the more useful **CL.0** pattern, letting the attacker plant a malicious prefix.
3. **That malicious prefix** then latches onto whatever the *next real visitor* sends — corrupting their request/response just like classic request smuggling.

```
Step 1 (0.CL + early-response gadget)
        │
        ▼
   Breaks the deadlock, poisons the connection
        │
        ▼
Step 2 (desynced into CL.0 this time)
        │
        ▼
   Plants a malicious prefix
        │
        ▼
Step 3: Victim's request arrives → gets glued to the malicious prefix
        │
        ▼
   Victim gets a corrupted/hijacked response
```

In practice, getting this exactly right is fiddly — it depends on carefully predicting how many bytes of "extra" headers a front-end server will quietly insert into the rewritten request (things like forwarded-IP headers), since guessing wrong throws off the byte-counting needed to cleanly separate the smuggled requests. Researchers found that positioning the smuggled request to start *before* where servers typically insert their own extra headers makes the attack far more reliable.

## Summary Table

| Concept | What It Means |
|---|---|
| **0.CL** | Front-end ignores length entirely (treats body as zero); back-end trusts `Content-Length` |
| **The deadlock** | Front-end waits for a response; back-end waits for a body that will never come — normally ends in a timeout |
| **Early-response gadget** | A quirky server behavior (e.g. hitting a reserved filename like `/con`) that makes the back-end respond before the body finishes, breaking the deadlock |
| **Double desync** | Using two chained requests to convert the fragile 0.CL bug into a more controllable CL.0 desync with a malicious prefix |
| **End result** | A previously "unexploitable" bug class becomes a real, weaponizable request smuggling attack |
