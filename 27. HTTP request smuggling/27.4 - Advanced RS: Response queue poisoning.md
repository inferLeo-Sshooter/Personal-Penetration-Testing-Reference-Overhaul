This is one of the most damaging outcomes of request smuggling. The short version: **the front-end gets confused about which response belongs to which request**, and starts handing out *other people's* responses to *your* requests (and vice versa).

---

# 1. The Core Idea

Normally, a front-end/back-end pair works like a polite queue at a coffee shop:

```
You ask for a coffee  →  You get a coffee
```

One request in, one response out, matched up correctly.

**Response queue poisoning breaks this matching.** If an attacker can sneak a *hidden, complete* extra request past the front-end (one the back-end sees, but the front-end doesn't know about), the back-end will send back **two responses** — while the front-end is only expecting **one**.

That one extra, unclaimed response doesn't disappear. It gets stuck waiting in line. And the *next* real visitor's request accidentally "claims" it instead of getting their own response.

```
Expected:   Request A  →  Response A
            Request B  →  Response B

Poisoned:   Request A  →  Response A  (+ hidden extra response queued up)
            Request B  →  (gets the hidden extra response instead of Response B!)
            Request C  →  (gets Response B instead of Response C!)
            ...and so on, shifting forever
```

Every single response from then on is **one slot off** — shifted onto the wrong person — until the connection closes.

---

## Why This Is So Dangerous

- **Full account takeover risk:** An attacker can keep sending requests and simply collect whatever responses land in their lap. Since real users' responses often contain session tokens, personal data, or account details, this can hand over enough info to hijack someone else's session.
- **Breaks the site for everyone:** Every other visitor sharing that same connection between front-end and back-end starts getting bizarre, mismatched responses — pages that don't match what they asked for, broken logins, etc. It's not just one victim; it's ongoing chaos for anyone unlucky enough to share that connection.

---

# 2. Requirements to Work

Three conditions need to line up:

1. **Connection reuse** — the front-end and back-end must reuse the same TCP connection for multiple requests (this is normal/common for performance reasons).
2. **A smuggled *complete* request** — the attacker must be able to sneak in a full, standalone request that gets its own separate response from the back-end (not just a broken fragment).
3. **No connection reset** — the attack must not cause either server to see an invalid/broken request, because servers usually just kill the connection when that happens (which would reset everything and ruin the attack).

---

## Step 1: Why Smuggling a "Prefix" Usually Isn't Enough

Classic request smuggling often smuggles a **partial** request — just the start of one, which then gets glued onto the front of whatever the *next* real visitor sends. This is often called smuggling a "prefix."

**Problem:** if your smuggled fragment includes a body (not just headers), the next real request gets appended into that body — and often gets **cut off / truncated** based on a `Content-Length` value. This leaves broken, leftover bytes that don't form a valid request. The back-end chokes on it, throws an error, and — bang — the connection gets closed. Attack over before it even started.

### Example of the "broken prefix" problem

**What travels down the connection (the attacker's payload, followed by the *next* request on that connection):**

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Type: x-www-form-urlencoded
Content-Length: 120
Transfer-Encoding: chunked

0

POST /example HTTP/1.1
Host: vulnerable-website.com
Content-Type: x-www-form-urlencoded
Content-Length: 25

x=                              <-- attacker's payload ends here
GET / HTTP/1.1                  <-- the NEXT request on the connection,
Host: vulnerable-website.com        glued on right after the payload
```

**What the back-end actually parses this as (3 pieces, and the 3rd is garbage):**

1. The real `POST /` request
2. The smuggled `POST /example` request, whose body is **exactly 25 bytes** (per its `Content-Length`). The back-end takes the first 25 bytes after the blank line:
   ```
   x=GET / HTTP/1.1\r\nHost: v
   ```
   (2 bytes for `x=` + 16 for `GET / HTTP/1.1\r\n` + 7 for `Host: v` = 25)
3. **Whatever is left over** after those 25 bytes: `ulnerable-website.com\r\n\r\n`. The back-end tries to read this as the start of a brand-new request, but it isn't one.

The smuggled request's body swallows the next request only *partially* because of the `Content-Length: 25` cutoff. 

The leftover tail (`ulnerable-website.com...`) is not a valid request line → the server errors out → connection closes. Not useful for poisoning the queue.

---

## Step 2: The Fix — Smuggle a *Complete* Request Instead

The trick is to be more careful and smuggle **exactly two full, valid requests** glued together — no leftover fragments. If you get this right, any request that comes *after* yours on the same connection stays completely untouched and valid.

### Example

**What gets sent to the front-end (looks like one request, using Content-Length):**

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Type: x-www-form-urlencoded
Content-Length: 61
Transfer-Encoding: chunked

0

GET /anything HTTP/1.1
Host: vulnerable-website.com

GET / HTTP/1.1
Host: vulnerable-website.com

```

**What the back-end parses this as (using Transfer-Encoding instead):**

- **Request #1 (the "wrapper"):** `POST /`
- **Request #2 (the smuggled one):** `GET /anything`

Both are complete, valid requests. Nothing is broken. The connection stays open. 🎯

---

## Step 3: How the Response Queue Actually Gets Desynced

Here's the mismatch in action:

- The **front-end** thinks it sent **one** request (the outer `POST /`), so it's expecting **one** response back.
- The **back-end** actually received **two** requests (`POST /` and the smuggled `GET /anything`), so it sends back **two** responses.

What happens next:

1. The front-end takes the **first** response and correctly matches it to the real `POST /` request → forwards it to the attacker. Normal so far.
2. The **second** response (meant for the smuggled request) has nobody waiting for it on the front-end's side — so it just sits in a queue, unclaimed.
3. Later, when an *unrelated, innocent* visitor sends their own request down this same connection, the front-end forwards it to the back-end as usual... but when a response comes back, the front-end grabs whatever is **next in the queue** — which is that leftover, unclaimed response from step 2. The innocent visitor gets a response meant for the attacker's smuggled request!
4. Meanwhile, the *real* response to the innocent visitor's request is now sitting in the queue, waiting for the *next* person after them.

This creates a chain reaction — everyone's responses are now shifted by one, indefinitely, until the connection finally closes.

---

## Step 4: Stealing Other Users' Responses

Once the queue is poisoned, exploitation is almost embarrassingly simple:

> The attacker just sends more requests — of literally any kind — and whatever response comes back actually belongs to whoever's turn it "stole" from.

The attacker doesn't get to choose *whose* response they steal — it's just whatever's sitting at the front of the queue at that moment. But that's easy to work around:

- Automate it. Use a tool like **Burp Intruder** to fire off the same harmless request over and over.
- Each time, you scoop up a new stolen response — some might be boring, but sooner or later you'll catch something juicy (session cookies, personal data, account info).

💡 **Practical tip from the source:** send your "collector" requests to a path that doesn't exist on the site. That way, *your own* responses always come back as a predictable `404`, making it obvious (by process of elimination) when you've actually captured someone else's real response instead.

### How long does this work?

As long as that specific front-end-to-back-end connection stays open. Servers often auto-close connections after some number of requests (commonly ~100), but that's not a real defense — the attacker can simply repoison a fresh connection once the old one closes.

---

# 3. Key Takeaway

Response queue poisoning turns a smuggling bug from a one-off trick into a **persistent, repeatable data-theft machine**. Because it exploits the fundamental request/response *counting* between servers (not just one malformed request), a single successful setup lets an attacker keep harvesting other users' responses over and over — until the connection closes, at which point they can simply do it again.

---

## Where This Applies

This attack works via:
- **Classic HTTP/1 request smuggling** (CL.TE / TE.CL style desyncs)
- **HTTP/2 downgrading vulnerabilities** (H2.CL / H2.TE, covered in the earlier docs)

Both give you the same core capability needed here: the ability to smuggle a complete, valid extra request past the front-end.
