# CL.0 Request Smuggling

This technique proves something important: you **don't need** chunked encoding (`Transfer-Encoding`) or HTTP/2 downgrading tricks to pull off request smuggling. Sometimes a perfectly normal, correctly-formatted `Content-Length` header is all it takes — if the back-end just decides to ignore it.

---

## What Does "CL.0" Mean?

**`CL.0` is the reverse of `0.CL`:**

- **Front-end:** uses the `Content-Length` header normally, as intended.
- **Back-end:** ignores `Content-Length` completely — it assumes every request's body is **zero bytes long**, full stop, regardless of what the header says.

```
Front-end's view:  "Content-Length: 34 — the body is 34 bytes. Got it."
Back-end's view:   "I don't care what Content-Length says. Body = 0 bytes. Request ends at the blank line."
```

---

## Why Does the Back-End Do This?

This isn't some obscure parsing bug — it's often just a server being lazy/efficient about how it handles requests it isn't expecting to have bodies at all.

**Common real-world cause:** the endpoint simply isn't expecting a `POST` request (or any request with a body). Think:
- A static file (like an image or stylesheet) being served
- An endpoint that just issues a server-level redirect

These endpoints logically assume "nobody sends a body to *this* kind of request," so some server implementations skip reading the body entirely — even if the request technically includes a `Content-Length` header claiming there's content there.

---

## Why This Is Exploitable

Exactly the same reason as every other smuggling variant: **the two servers disagree about where the request ends.**

- Front-end says: *"This request is 34 bytes of body long — I'll forward exactly that much, then move on to the next request."*
- Back-end says: *"I don't care, this request's body is 0 bytes — anything after the blank line is the start of a brand new request."*

That disagreement means whatever text the attacker stuffed into the "body" (according to the front-end) actually gets treated by the back-end as an **entirely separate request** — the exact same desync mechanism as CL.TE or TE.CL, just without needing to touch `Transfer-Encoding` at all.

---

## Testing for CL.0 Vulnerabilities

**The method:** send a request whose body contains what looks like the start of a second request, then immediately send a normal, harmless follow-up request on the **same connection**. If the back-end is vulnerable, your hidden "fake second request" will mess with how the follow-up request gets interpreted.

### Example

```http
POST /vulnerable-endpoint HTTP/1.1
Host: vulnerable-website.com
Connection: keep-alive
Content-Type: application/x-www-form-urlencoded
Content-Length: 34

GET /hopefully404 HTTP/1.1
Foo: xGET / HTTP/1.1
Host: vulnerable-website.com
```

Then send a normal follow-up request for the home page (`GET /`) right after, on the same connection.

**What you'd expect normally:** `GET /` → `200 OK`

**What you actually get if vulnerable:**

```http
HTTP/1.1 200 OK

HTTP/1.1 404 Not Found
```

That unexpected `404 Not Found` is the giveaway. It means the back-end treated `GET /hopefully404 HTTP/1.1` (buried inside what the front-end thought was just a request *body*) as its own standalone request — and it responded to *that* instead of your real, separate follow-up request for `/`.

**Important:** notice nothing was tampered with here — no obfuscated headers, no sneaky header folding. The `Content-Length: 34` is completely accurate and honest. The vulnerability is purely in the back-end's *choice* to ignore it.

### How to Test This in Practice

Since this depends on sending two requests back-to-back over the **same** connection (not two separate ones), here's the general workflow using a tool like Burp Repeater:

1. Set up one request containing your "poisoned" payload (as shown above), and a second, separate, normal follow-up request.
2. Group both requests together, in that order.
3. Use the option to send the whole group over a **single, shared connection** (rather than opening a fresh connection for each).
4. Make sure `Connection: keep-alive` is set, so the connection actually stays open between the two.
5. Send them and compare the follow-up response to what you'd normally expect.

## What If Nothing Looks Vulnerable? Try Eliciting the Behavior

Sometimes no endpoint obviously ignores the body on its own — but you can sometimes *provoke* this behavior artificially.

### Trick #1: Trigger an Early Error

Some servers, when they hit a problem while reading the **headers** (before ever getting to the body), respond with an error **immediately** — without bothering to read/consume the body bytes still sitting in the socket. If the server *also* doesn't close the connection afterward, those unread body bytes are now just sitting there, ready to be misinterpreted as the start of the next request. That's a usable CL.0-style desync vector.

### Trick #2: Obfuscate Content-Length on a GET Request

You can also try sending a `GET` request (which isn't supposed to have a body at all) along with a disguised/obfuscated `Content-Length` header. If you can make the back-end miss or ignore it, while the front-end still honors it, you get the same core discrepancy needed for a desync — similar to the header obfuscation tricks used for `TE.TE` style attacks (e.g. subtly malformed header names/casing designed to slip past one parser but not the other).

---

## Exploiting CL.0 Vulnerabilities

Once you've confirmed a CL.0 discrepancy, you're not limited to anything special — you can reuse the **same exploitation playbook** as classic request smuggling (CL.TE / TE.CL):

- Bypassing front-end security controls
- Capturing other users' requests
- Smuggling into reflected XSS
- Web cache poisoning
- Response queue poisoning

CL.0 is just a different *route* to the same underlying desync primitive — once you have it, everything downstream works the same way.

---

## Bonus: H2.0 Vulnerabilities

If you remember HTTP/2 downgrading from earlier docs (where a front-end translates HTTP/2 requests into HTTP/1.1 text for an older back-end), there's a matching variant here too: **H2.0**.

This happens when a website downgrades HTTP/2 to HTTP/1.1, and the **back-end** then ignores the `Content-Length` header on that rewritten HTTP/1.1 request — same root cause as CL.0, just arriving via the HTTP/2-downgrade path instead of a native HTTP/1.1 request.

## Summary Table

| Concept | What It Means |
|---|---|
| **CL.0** | Front-end uses `Content-Length` normally; back-end ignores it and treats body as 0 bytes |
| **Why it happens** | Often on endpoints that never expect a body (static files, redirects) |
| **No obfuscation needed** | Unlike CL.TE/TE.CL, the `Content-Length` header can be completely valid and unmodified |
| **Testing method** | Send a poisoned request + a normal follow-up on the same connection; look for a mismatched response |
| **Eliciting it** | Provoke an early error response, or obfuscate `Content-Length` on a `GET` request |
| **Exploitation** | Same techniques as any other smuggling primitive (hijacking requests, XSS, cache poisoning, etc.) |
| **H2.0** | The HTTP/2-downgrading equivalent of CL.0 |
