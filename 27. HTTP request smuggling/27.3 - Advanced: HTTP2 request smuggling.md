# 1. Recap and core idea

Request smuggling happens when a **front-end server** (like a load balancer or reverse proxy) and a **back-end server** disagree about where one HTTP request ends and the next one begins.

If an attacker can make the front-end think a request is one size, while the back-end thinks it's a different size, they can sneak ("smuggle") a hidden request into the stream — one that the back-end will process as if it came from someone else.

```
Front-end sees:  [ Request A ]
Back-end sees:   [ Request A-part-1 ][ Smuggled Request ]
```

---

## 1.1 - Why HTTP/2 Was Thought to Be Immune

HTTP/2 doesn't send plain text like HTTP/1. It sends everything in small binary chunks called **frames**, and every frame says exactly how many bytes it contains.

Think of it like shipping a package where the box itself is labeled "This box weighs exactly 4kg" — there's no ambiguity about where the package ends.

Because of this precise length system, people assumed: *if a site speaks HTTP/2 end-to-end, request smuggling should be impossible.*

**The catch:** Very few backend servers actually understand HTTP/2. So most infrastructure does something called **HTTP/2 downgrading**.

---

## 1.2 - HTTP/2 Downgrading (Where the Trouble Starts)

Many setups look like this:

```
Browser --(HTTP/2)--> Front-end proxy --(HTTP/1.1)--> Back-end server
```

The front-end receives a clean, unambiguous HTTP/2 request, then **rewrites it as an old-fashioned HTTP/1.1 text request** to forward it to the back-end. This rewriting step is where discrepancies can sneak back in — reopening the door to smuggling, even on "modern" HTTP/2 sites.

---

## H2.CL Vulnerabilities (Fake Content-Length)

**The setup:** HTTP/2 doesn't need a `content-length` header at all (frame sizes already say how long the message is) — but it's *allowed* to include one anyway.

**The bug:** When downgrading to HTTP/1, some front-ends just copy whatever `content-length` value the attacker put in the HTTP/2 request, without checking that it's actually correct.

So you get two different ideas about the body length:
- **Front-end:** uses the real HTTP/2 frame size to know where the request ends.
- **Back-end:** trusts the (fake) `Content-Length` header instead.

### Example

**What the attacker sends (HTTP/2):**

| Field | Value |
|---|---|
| `:method` | `POST` |
| `:path` | `/example` |
| `:authority` | `vulnerable-website.com` |
| `content-length` | `0`  ← lies about the body being empty |
| *(body)* | `GET /admin HTTP/1.1`<br>`Host: vulnerable-website.com`<br>`Content-Length: 10`<br><br>`x=1` |

**What the back-end reconstructs (HTTP/1.1):**

```http
POST /example HTTP/1.1
Host: vulnerable-website.com
Content-Length: 0

GET /admin HTTP/1.1
Host: vulnerable-website.com
Content-Length: 10

x=1GET / H...
```

Because the front-end said "0 bytes of body," it treats the whole thing as one harmless request and forwards it on. But the back-end, following the smuggled `Content-Length: 10`, chops the stream differently — and ends up treating `GET /admin ...` as a **separate, real request**.

💡 **Attacker tip from the source:** adding a fake trailing parameter (like `x=1`) plus a slightly-too-long `Content-Length` lets the *next real user's request* get appended onto your smuggled one — without causing header errors.

---

## H2.TE Vulnerabilities (Sneaking in Chunked Encoding)

**Background:** `Transfer-Encoding: chunked` is a way of sending a body in small labeled pieces instead of stating a total size up front. HTTP/2 doesn't support this concept, so the spec says: *if a client tries to send a `transfer-encoding: chunked` header over HTTP/2, the server should strip it or reject the request.*

**The bug:** Some front-ends don't strip it. So the header survives the downgrade, and the back-end (which does understand chunked encoding) starts interpreting the body completely differently.

### Example

**HTTP/2 request:**

| Field | Value |
|---|---|
| `:method` | `POST` |
| `:path` | `/example` |
| `transfer-encoding` | `chunked` |
| *(body)* | `0`<br><br>`GET /admin HTTP/1.1`<br>`Host: vulnerable-website.com`<br>`Foo: bar` |

**Reconstructed HTTP/1.1 on the back-end:**

```http
POST /example HTTP/1.1
Host: vulnerable-website.com
Transfer-Encoding: chunked

0

GET /admin HTTP/1.1
Host: vulnerable-website.com
Foo: bar
```

The `0` is a chunk-size marker meaning "end of body" in chunked encoding. So the back-end thinks the real request ends right there — and everything after it (`GET /admin ...`) becomes a smuggled second request.

Once you have either an H2.CL or H2.TE bug, you can chain it into the same kinds of attacks used in classic request smuggling (stealing sessions, bypassing auth, poisoning caches, etc.).

---

## 1.3 - Hidden HTTP/2 Support

Some servers actually *support* HTTP/2 but fail to properly announce it during the TLS handshake (a step called **ALPN**). Since browsers and tools normally only use HTTP/2 when a server says "yes, I support it," this hidden support goes unnoticed — and testers might skip checking for HTTP/2-specific bugs entirely, even though the vulnerable surface is right there.

**Fix if you're testing:** Tools like Burp Repeater let you force a connection to use HTTP/2 even if the server didn't advertise it, so you can check for this manually.

# 2. HTTP/2 exclusive attack vectors

Sneaky injection tricks that are **only possible in HTTP/2** — because HTTP/2 is a binary protocol instead of a plain-text one, it doesn't have the same strict syntax rules HTTP/1 relies on. That freedom, ironically, opens the door to attacks that simply can't exist in HTTP/1.

⚠️ Note: these techniques are officially against the HTTP/2 spec — but "against the rules" doesn't mean "blocked." Plenty of real servers don't enforce it properly.

### Why This Is Possible At All

In HTTP/1, everything is text, and specific characters have strict jobs:
- `:` separates a header **name** from its **value**
- `\r\n` (CRLF) marks the **end** of a header or request line

HTTP/2 sends headers as structured binary fields with explicit lengths, not raw text with delimiters — so `:` and `\r\n` have **no special meaning** inside an HTTP/2 header. You can freely put them in a header's name *or* value.

The **danger** shows up later: when a front-end proxy **downgrades** the HTTP/2 request back into HTTP/1 text for an older back-end, those characters instantly regain their old meaning. Whatever you buried inside a "value" or "name" field gets reinterpreted as real structure — new headers, split requests, etc.

Everything below is a different *place* to hide this injection.

---

## 2.1 - Request smuggling via CRLF injection 

> (in a header **value**)

```http
Foo: bar\nTransfer-Encoding: chunked
```

**HTTP/2 header field:**

| Name | Value |
|---|---|
| `foo` | `bar\r\nTransfer-Encoding: chunked` |

To HTTP/2, this is just one header called `foo` with a slightly weird value. But when the front-end downgrades this into HTTP/1.1 text format, that embedded `\r\n` becomes a **real line break** — splitting it into two separate headers:

```http
Foo: bar
Transfer-Encoding: chunked
```

The attacker just smuggled in a brand-new header (`Transfer-Encoding: chunked`) that wasn't supposed to be there — bypassing filters that only look for that header explicitly in the original request.

---

## 2.2 - Injecting via header names

Same idea as **2.1**, but the injection lives in the **name** field instead of the value. 

**The rule in HTTP/1:** a header name can never contain a colon (`:`) — that's literally what ends the name.

**The loophole in HTTP/2:** header *names* aren't restricted the same way. So you can stuff a colon and a CRLF (`\r\n`) sequence right into what's supposed to be just a header name.

### Example

**What you send as the HTTP/2 header name:**

```http
# Front-end (HTTP/2):

foo: bar\r\nTransfer-Encoding: chunked\r\nX: ignore
```

**What the back-end reconstructs (HTTP/1.1):**

```http
# Back-end (HTTP/1):

Foo: bar
Transfer-Encoding: chunked
X: ignore
```

You sent what looked like *one* header, but after downgrading, the back-end sees **three separate headers** — including a smuggled `Transfer-Encoding: chunked`, which can be used to desync the connection.

---

## 2.3 - Injecting via Pseudo-Headers

HTTP/2 doesn't have a traditional "request line" (like `GET /path HTTP/1.1`). Instead, that information is broken up into special fields called **pseudo-headers**, always prefixed with a colon:

| Pseudo-header | Roughly equivalent to... |
|---|---|
| `:method` | The HTTP method (`GET`, `POST`, etc.) |
| `:path` | The path + query string |
| `:authority` | The `Host` header |
| `:scheme` | `http` or `https` |
| `:status` | Status code (responses only) |

When the front-end downgrades an HTTP/2 request, it **rebuilds** the classic HTTP/1 request line using these values — and that **rebuilding step is where things can go wrong**.

### 1. Supplying an Ambiguous Host

You can still send a normal `host` header in HTTP/2 *alongside* the `:authority` pseudo-header. After downgrading, both may get turned into `Host:` headers — meaning the reconstructed HTTP/1.1 request could end up with **two `Host` headers**.

Why does this matter? Many front-ends specifically block requests that have duplicate `Host` headers, as a defense against smuggling and `Host` header attacks. But since HTTP/2 splits the host info across two *different* fields, that filter might never notice — letting you sneak a conflicting `Host` value through and potentially exploit `Host` header attacks that the site would normally be protected against.

### 2. Supplying an Ambiguous Path

HTTP/1 request lines can only have one path — trying to write two would just be invalid syntax. But since HTTP/2's path lives in a pseudo-header field, nothing stops you from sending the *same* pseudo-header **twice**:

```
:method     POST
:path       /anything
:path       /admin
:authority  vulnerable-website.com
```

If the security/access-control check looks at one `:path` value, but the actual routing logic uses the *other* one, you can potentially sneak requests through to endpoints (like `/admin`) that should be restricted.

### 3. Injecting a Full Request Line

During downgrading, whatever is in `:method` gets written at the very start of the new HTTP/1 request line. Normally `:method` is just `GET` or `POST` — but if the server doesn't validate that it can't contain spaces, you can smuggle an entire fake request line inside it:

**Front-end (HTTP/2):**

```
:method      GET /admin HTTP/1.1
:path        /anything
:authority   vulnerable-website.com
```

**Reconstructed Back-end (HTTP/1):**

```http
GET /admin HTTP/1.1 /anything HTTP/1.1
Host: vulnerable-website.com
```

As long as the back-end server ignores the weird trailing text (`/anything HTTP/1.1`), it will process this as a request for `/admin` — even though front-end filtering likely only checked `:path` (`/anything`).

### 4. Injecting a URL Prefix

The `:scheme` pseudo-header is normally just `http` or `https`. But if a server doesn't validate its contents and uses `:scheme` to dynamically build URLs (e.g., for redirects), you can smuggle arbitrary text into it — even a whole malicious prefix.

**Request sent:**

```
:method      GET
:path        /anything
:authority   vulnerable-website.com
:scheme      https://evil-user.net/poison?
```

**Resulting response:**

```http
HTTP/1.1 301 Moved Permanently
Location: https://evil-user.net/poison?://vulnerable-website.com/anything/
```

The server thought it was building a normal same-site redirect — but the attacker-controlled `:scheme` turned it into a redirect that sends victims to `evil-user.net` instead, with the real path awkwardly stuffed into the query string.

### 5. Injecting Newlines into Pseudo-Headers

If you want to sneak a `\r\n` into `:path` or `:method`, you have to be careful — a bare `\r\n` would just cut the HTTP/1 request line short and break the request entirely.

**The trick:** before your injected `\r\n`, make sure the text still forms a *complete, valid* request line first:

```
<method> + space + <path> + space + HTTP/1.1
```

Basically: finish the sentence properly, *then* start your injection.

### Example

**HTTP/2 sent (with a sneaky `:path` field):**

```
:method      GET
:path        /example HTTP/1.1\r\n
             Transfer-Encoding: chunked\r\n
             X: x
:authority   vulnerable-website.com
```

**Reconstructed HTTP/1.1:**

```http
GET /example HTTP/1.1
Transfer-Encoding: chunked
X: x HTTP/1.1
Host: vulnerable-website.com

```

Notice the clever bit: `X: x` was added purely as a "junk" header to **absorb** the leftover `HTTP/1.1` text that the front-end automatically appends after the path — keeping the final rewritten request clean and valid, while still carrying the smuggled `Transfer-Encoding: chunked` header.

---

### Summary Table

| Vector | Abused Field | What It Enables |
|---|---|---|
| **Header name injection** | Header *name* (not value) | Smuggle entirely new headers past filters that only check values |
| **Ambiguous Host** | `host` header + `:authority` | Duplicate `Host` headers bypass duplicate-header defenses |
| **Ambiguous Path** | Duplicate `:path` | Security check and routing logic see different paths |
| **Full request-line injection** | `:method` | Overwrite the entire rebuilt request line, changing method + path |
| **URL prefix injection** | `:scheme` | Hijack dynamically-built redirect URLs |
| **Newline injection** | `:path` / `:method` | Insert new headers by carefully completing the request line first |
