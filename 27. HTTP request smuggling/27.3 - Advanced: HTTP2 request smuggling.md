# 1. Recap and core idea

Request smuggling happens when a **front-end server** (like a load balancer or reverse proxy) and a **back-end server** disagree about where one HTTP request ends and the next one begins.

If an attacker can make the front-end think a request is one size, while the back-end thinks it's a different size, they can sneak ("smuggle") a hidden request into the stream — one that the back-end will process as if it came from someone else.

```
Front-end sees:  [ Request A ]
Back-end sees:   [ Request A-part-1 ][ Smuggled Request ]
```

---

## 1.1 - Why HTTP/2 Was Thought to Be Immune

HTTP/2 doesn't send plain text like HTTP/1. It sends everything in small binary chunks called **frames**, and every frame says exactly how many bytes it contains.

Think of it like shipping a package where the box itself is labeled "This box weighs exactly 4kg" — there's no ambiguity about where the package ends.

Because of this precise length system, people assumed: *if a site speaks HTTP/2 end-to-end, request smuggling should be impossible.*

**The catch:** Very few backend servers actually understand HTTP/2. So most infrastructure does something called **HTTP/2 downgrading**.

---

## 1.2 - HTTP/2 Downgrading (Where the Trouble Starts)

Many setups look like this:

```
Browser --(HTTP/2)--> Front-end proxy --(HTTP/1.1)--> Back-end server
```

The front-end receives a clean, unambiguous HTTP/2 request, then **rewrites it as an old-fashioned HTTP/1.1 text request** to forward it to the back-end. This rewriting step is where discrepancies can sneak back in — reopening the door to smuggling, even on "modern" HTTP/2 sites.

---

## H2.CL Vulnerabilities (Fake Content-Length)

**The setup:** HTTP/2 doesn't need a `content-length` header at all (frame sizes already say how long the message is) — but it's *allowed* to include one anyway.

**The bug:** When downgrading to HTTP/1, some front-ends just copy whatever `content-length` value the attacker put in the HTTP/2 request, without checking that it's actually correct.

So you get two different ideas about the body length:
- **Front-end:** uses the real HTTP/2 frame size to know where the request ends.
- **Back-end:** trusts the (fake) `Content-Length` header instead.

### Example

**What the attacker sends (HTTP/2):**

| Field | Value |
|---|---|
| `:method` | `POST` |
| `:path` | `/example` |
| `:authority` | `vulnerable-website.com` |
| `content-length` | `0`  ← lies about the body being empty |
| *(body)* | `GET /admin HTTP/1.1`<br>`Host: vulnerable-website.com`<br>`Content-Length: 10`<br><br>`x=1` |

**What the back-end reconstructs (HTTP/1.1):**

```http
POST /example HTTP/1.1
Host: vulnerable-website.com
Content-Length: 0

GET /admin HTTP/1.1
Host: vulnerable-website.com
Content-Length: 10

x=1GET / H...
```

Because the front-end said "0 bytes of body," it treats the whole thing as one harmless request and forwards it on. But the back-end, following the smuggled `Content-Length: 10`, chops the stream differently — and ends up treating `GET /admin ...` as a **separate, real request**.

💡 **Attacker tip from the source:** adding a fake trailing parameter (like `x=1`) plus a slightly-too-long `Content-Length` lets the *next real user's request* get appended onto your smuggled one — without causing header errors.

---

## H2.TE Vulnerabilities (Sneaking in Chunked Encoding)

**Background:** `Transfer-Encoding: chunked` is a way of sending a body in small labeled pieces instead of stating a total size up front. HTTP/2 doesn't support this concept, so the spec says: *if a client tries to send a `transfer-encoding: chunked` header over HTTP/2, the server should strip it or reject the request.*

**The bug:** Some front-ends don't strip it. So the header survives the downgrade, and the back-end (which does understand chunked encoding) starts interpreting the body completely differently.

### Example

**HTTP/2 request:**

| Field | Value |
|---|---|
| `:method` | `POST` |
| `:path` | `/example` |
| `transfer-encoding` | `chunked` |
| *(body)* | `0`<br><br>`GET /admin HTTP/1.1`<br>`Host: vulnerable-website.com`<br>`Foo: bar` |

**Reconstructed HTTP/1.1 on the back-end:**

```http
POST /example HTTP/1.1
Host: vulnerable-website.com
Transfer-Encoding: chunked

0

GET /admin HTTP/1.1
Host: vulnerable-website.com
Foo: bar
```

The `0` is a chunk-size marker meaning "end of body" in chunked encoding. So the back-end thinks the real request ends right there — and everything after it (`GET /admin ...`) becomes a smuggled second request.

Once you have either an H2.CL or H2.TE bug, you can chain it into the same kinds of attacks used in classic request smuggling (stealing sessions, bypassing auth, poisoning caches, etc.).

# 2. HTTP/2 exclusive vectors

---

## 2.1 - Request smuggling via CRLF injection

> **(Smuggling via Line Breaks)**

In HTTP/1, headers are separated by a specific sequence: `\r\n` (carriage return + line feed, often called **CRLF**). All HTTP/1 servers agree this marks the end of a header, so on its own, this doesn't cause disagreements.

**But HTTP/2 is different.** Since HTTP/2 doesn't use text delimiters to mark where a header value ends (it uses fixed byte-length fields), you can actually put a literal `\r\n` sequence *inside* a header's value, and HTTP/2 won't treat it as anything special.

### Example

**HTTP/2 header field:**

| Name | Value |
|---|---|
| `foo` | `bar\r\nTransfer-Encoding: chunked` |

To HTTP/2, this is just one header called `foo` with a slightly weird value. But when the front-end downgrades this into HTTP/1.1 text format, that embedded `\r\n` becomes a **real line break** — splitting it into two separate headers:

```http
Foo: bar
Transfer-Encoding: chunked
```

The attacker just smuggled in a brand-new header (`Transfer-Encoding: chunked`) that wasn't supposed to be there — bypassing filters that only look for that header explicitly in the original request.
