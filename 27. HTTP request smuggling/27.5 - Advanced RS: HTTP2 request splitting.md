# 1. Core idea

This technique is a close cousin of the "smuggle a complete request" trick used in `response queue poisoning` — but instead of splitting a request inside the **body**, it splits it inside the **headers**. That small change makes it much more flexible.

## Splitting in the Body (The Old Way)

Previously, you learned that if you smuggle a *complete* second request inside the **body** of a first request, the back-end will treat it as two separate requests — desyncing the response queue.

**Limitation:** this only works with request methods that are allowed to carry a body — mainly `POST`. A `GET` request isn't supposed to have a body, so this trick doesn't naturally apply to it.

---

## The New Way: Splitting in the Headers

Because HTTP/2 downgrading lets you inject a literal `\r\n` (CRLF) inside a header value (covered in the `HTTP/2-exclusive vectors`), you can use that same trick to split the request **before the body even starts** — right in the header section.

**Why this is better:** since the split happens in the headers, it doesn't matter whether the method normally supports a body or not. This means the trick now works even with a plain `GET` request.

### Example

**What's sent over HTTP/2:**

| Field | Value |
|---|---|
| `:method` | `GET` |
| `:path` | `/` |
| `:authority` | `vulnerable-website.com` |
| `foo` | `bar\r\n`<br>`\r\n`<br>`GET /admin HTTP/1.1\r\n`<br>`Host: vulnerable-website.com` |

**What the back-end reconstructs (HTTP/1.1) after downgrading:**

```http
GET / HTTP/1.1
Foo: bar

GET /admin HTTP/1.1
Host: vulnerable-website.com
```

Notice the blank line (`\r\n\r\n`) inside the `foo` header's value. In HTTP/1, a blank line means **"headers are done, this request is finished."** So the back-end reads this as **two separate, complete requests**:

1. `GET /` (a normal, harmless-looking request)
2. `GET /admin` (a smuggled request — maybe an admin-only endpoint that should be restricted)

🎯 **Bonus:** this also works well when the target validates `Content-Length` strictly, or when the back-end doesn't support chunked encoding — since this whole technique doesn't rely on the body or those headers at all.

# 2. The Tricky Part: Matching How the Front-End Rewrites Headers

**The Problem** — you're not just crafting a payload in a vacuum. The **front-end proxy** rewrites your HTTP/2 request into HTTP/1.1 text, and *where* it inserts things during that rewrite matters a lot.

### The specific problem: the `Host` header

In HTTP/2, there's no `Host` header — instead there's an `:authority` pseudo-header that serves the same purpose. When downgrading to HTTP/1.1, the front-end needs to convert `:authority` into a real `Host:` header.

**The issue:** different front-ends insert this new `Host:` header in different *positions* within the header list. If you don't know (or account for) where it gets inserted, your split request might end up **missing a required `Host` header** entirely — which most back-end servers will reject.

### Example of the problem

Take this payload:

| Field | Value |
|---|---|
| `:method` | `GET` |
| `:path` | `/` |
| `:authority` | `vulnerable-website.com` |
| `foo` | `bar\r\n`<br>`\r\n`<br>`GET /admin HTTP/1.1\r\n`<br>`Host: vulnerable-website.com` |

Some front-ends will **append** the new `Host:` header at the very *end* of the header list — which, in this case, is *after* your `foo` header (and therefore after the point where your payload splits the request in two).

That means when the back-end parses this:

- **Request #1** (`GET /`) → ends up with **no `Host` header at all** ❌
- **Request #2** (the smuggled `GET /admin`) → ends up with **two `Host` headers** (yours, plus the one the front-end tacked on) ❌

Neither of these is ideal — **Request #1** will likely get rejected by the back-end for missing a mandatory header.

### The Fix: Position Your Injected Host Header Correctly

Since you know the front-end will add its own `Host:` header *after* everything else, you can simply add your **own** `Host:` header *before* your split point — so it lands inside the *first* request instead.

**Corrected payload:**

| Field | Value |
|---|---|
| `:method` | `GET` |
| `:path` | `/` |
| `:authority` | `vulnerable-website.com` |
| `foo` | `bar\r\n`<br>`Host: vulnerable-website.com\r\n`<br>`\r\n`<br>`GET /admin HTTP/1.1` |

**Reconstructed HTTP/1.1:**

```http
GET / HTTP/1.1
Foo: bar
Host: vulnerable-website.com

GET /admin HTTP/1.1
```

Now:
- **Request #1** (`GET /`) → has a valid `Host` header ✅
- **Request #2** (`GET /admin`) → picks up the front-end's own auto-appended `Host:` header at the end, so it's fine too ✅

**The general rule:** figure out where the front-end inserts its rewritten headers (like `Host:`), then position any headers *you* need to inject relative to that — so each of your split requests ends up complete and valid.

# 3. Bonus Tip: Using This for Classic Prefix Smuggling Too

The example above creates two *complete* requests — great for response queue poisoning. But you can also use this same header-splitting trick the "classic" way: smuggling just a **prefix**, where the *next real user's request* gets appended onto the end of your payload.

**The catch:** if you do this, your injected headers might **collide** with the headers already present in the next request that gets glued on — causing:
- Duplicate header errors, or
- The request getting cut off in the wrong place

**The fix:** add a trailing dummy body parameter to your smuggled prefix, along with a `Content-Length` value that's *slightly longer* than that dummy body. This way:

- The victim's real request still gets appended right after your prefix (as normal).
- But because of your `Content-Length`, the back-end only reads a few bytes of the victim's request as "body" — and **truncates it before reaching their actual headers**.

This avoids the header-collision problem entirely, since the victim's headers never actually get parsed as part of your smuggled request.

### Example

Suppose you send this as the `foo` header value (splitting the request, same as before, but this time deliberately leaving it as an incomplete "prefix" rather than a clean second request):

| Field | Value |
|---|---|
| `:method` | `GET` |
| `:path` | `/` |
| `:authority` | `vulnerable-website.com` |
| `foo` | `bar\r\n`<br>`Host: vulnerable-website.com\r\n`<br>`\r\n`<br>`POST /admin HTTP/1.1\r\n`<br>`Host: vulnerable-website.com\r\n`<br>`Content-Type: application/x-www-form-urlencoded\r\n`<br>`Content-Length: 100\r\n`<br>`\r\n`<br>`x=` |

**Reconstructed on the back-end, with a real victim's request glued on right after:**

```http
GET / HTTP/1.1
Foo: bar
Host: vulnerable-website.com

POST /admin HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 100

x=GET /home HTTP/1.1              ← the next real user's request
Host: vulnerable-website.com          starts getting appended here...
User-Agent: Mozilla/5.0
Cookie: session=abc123
...
```

Here's the trick: `Content-Length: 100` tells the back-end that the smuggled `POST /admin` request has a **100-byte body**. Since `x=` is only 2 bytes, the back-end keeps reading into the victim's glued-on request to fill up those 100 bytes — swallowing `GET /home HTTP/1.1\r\nHost: vulnerable-website.com\r\n...` as pure body text, **before it ever reaches the victim's headers** (like `Cookie:` or further headers that might collide with yours).

Once exactly 100 bytes have been consumed, the back-end treats whatever comes *after* that cutoff as the start of a brand-new request — which is now just the tail end of the victim's original request, still perfectly valid and unaffected.

**Why this avoids collisions:** if you hadn't set `Content-Length`, the back-end would try to parse the victim's real headers (`Host:`, `Cookie:`, etc.) as literal text — potentially clashing with headers you already injected, or cutting the request off at the wrong point. By absorbing the first chunk of the victim's request as "body," you sidestep their headers entirely.

## Summary Table

| Concept | Body Splitting (old) | Header Splitting (new) |
|---|---|---|
| **Where the split happens** | Inside the message body | Inside the header section (before the body) |
| **Works with GET requests?** | ❌ No (GET can't have a body) | ✅ Yes |
| **Main risk** | Truncated/invalid trailing bytes | Missing or duplicate `Host` headers after rewriting |
| **Key requirement** | Careful `Content-Length` math | Knowing where the front-end inserts its rewritten `Host:` header |

---

## Key Takeaway

HTTP/2's ability to smuggle a literal `\r\n\r\n` into a header value means you can split a request into two **before the body even begins** — making this technique work with any HTTP method, including `GET`. The main skill involved isn't the injection itself, but **reverse-engineering how the front-end proxy rewrites headers during downgrading**, so you can position your injected headers (especially `Host:`) in exactly the right spot to keep both resulting requests valid.
