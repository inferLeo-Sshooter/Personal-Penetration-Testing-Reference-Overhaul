## Chapter 1: How Web Applications Work

### 1.1 The Client/Server Model
Web applications run on a **client/server model**:
- **Client** (your browser) generates requests for resources.
- **Server** processes those requests and sends resources back over a network.

A **static website** is typically read-only. A **web application** allows two-way communication, enabling **end-user interactivity** (e.g., posting, upvoting, commenting on Reddit) rather than just reading content.

> **Why it matters for hacking:** interactivity means the app accepts *input*, and input is the attacker's entry point.

### 1.2 URL Structure
| Component | Description | Example |
|---|---|---|
| Protocol | Communication rules | `http`, `https`, `ftp` |
| Hostname | Domain name of the server | `twitter.com` |
| Port | Communication channel | `80` (HTTP), `443` (HTTPS) |
| Path | Directory path to a resource | `/api/v3/users` |
| Query | Optional search/filter string | `?id=123` |
| Query Parameters | Values within the query | `id=123&sort=asc` |

### 1.3 HTTP Requests
A request sent by the client includes:
- **Method** — the intended action (e.g., `POST` to submit login data)
- **Path** — location of the resource requested
- **Headers** — metadata key-value pairs (`User-Agent`, `Cookie`, etc.)
- **Message Body** — the actual payload (e.g., username/password)

### 1.4 HTTP Responses
A response sent by the server includes:
- **Status Code** — outcome of the request (`200 OK`, `404 Not Found`, etc.)
- **Response Headers** — instructions for the client (e.g., `Set-Cookie`)
- **Response Body** — the requested data (e.g., HTML, JSON)

### 1.5 HTTP Methods (Verbs)
| Method | Purpose | Idempotent? |
|---|---|---|
| `GET` | Retrieve a resource | Yes |
| `POST` | Create a new resource | No |
| `PUT` | Replace/store a resource at a specific URL | Yes |
| `DELETE` | Remove a resource | Yes |

**Idempotent** = repeating the same request produces the same end state (no extra side effects after the first call). `POST` is the odd one out — repeating it can create duplicate resources, which is itself a useful thing to test for (e.g., duplicate order submission, race conditions).

> **Self-check — Why does POST's non-idempotency matter for testing?** Because replaying a `POST` isn't "safe" the way replaying a `GET` is. Resending the exact same `POST` (e.g., via Burp's Repeater, or a race-condition tool sending it many times in parallel) can create duplicate orders, double-spend a coupon, or mint multiple accounts — all real business-logic bugs that simply don't exist for idempotent methods.

### 1.6 Stateful vs. Stateless HTTP
HTTP itself is **stateless** by default — the server has no memory of you between requests.

- **Stateful connections**: use **cookies** so the server can "remember" you (e.g., shopping cart persistence).
- **Stateless connections**: no server-side session memory. **Every request must carry all context needed to authorize it** (e.g., a bearer token).
- **APIs are generally stateless** — this is why almost every API request needs its own auth token/key, rather than relying on a login session like a traditional web app might.

> **Self-check — Stateful vs. stateless, security-wise:** in a stateful flow, the *server* holds the session and a stolen cookie only works while that session is valid and server-side checks stay intact. In a stateless flow, the *token itself* is the only proof of identity — if it leaks, is predictable, or never expires, an attacker can replay it directly with no session to invalidate. That's why token handling (generation, expiry, storage) becomes such a central theme in API testing.

### 1.7 Web Server Databases
| Type | Structure | Example |
|---|---|---|
| **SQL** (relational) | Highly structured, table-based | MySQL, PostgreSQL |
| **NoSQL** (non-relational) | Unstructured, document/key-value based | MongoDB |

Data flows from the **frontend** (what the user sees — HTML/JS) to the **backend** (databases and server logic).

### 1.8 How APIs Fit In
APIs let applications communicate using standardized HTTP methods and status codes. They make software more powerful and modular, but each API endpoint is also a new **attack surface** — often larger and less visible than the web app's UI itself.

> **Self-check — Why do APIs expand the attack surface?** A web app's UI only exposes what's rendered on screen, but its API exposes every *endpoint* behind that UI — including ones with no corresponding button or page. More endpoints, methods, and versions all mean more places for access-control and input-validation bugs to hide, many of which a user would never stumble into just by clicking around.

## Chapter 2: The Anatomy of Web APIs

Think of an API as the **engine beneath a web app's GUI**: the buttons and images are the interface, but the API is what actually fetches and moves the data.

### 2.1 Why APIs Exist
APIs let different applications (e.g., a Python app and a Java app) exchange data without needing custom, one-off integration code. This lets developers plug in existing functionality — maps, payments, machine learning, authentication — instead of building it themselves.

**Analogy:** an API is like a waiter — you (the consumer) place a request, the waiter (API) carries it to the kitchen (server), the kitchen prepares it (processes the request), and the waiter returns with your order (the response).

### 2.2 Core Building Blocks
- **Provider** — the host/system offering the API
- **Consumer** — the person or system making requests
- **Endpoint** — a specific URL used to interact with the API (e.g., `https://example.com/api/v3/users/`)
- **Resource** — the data itself:
  - **Singleton resource** — one specific object (a single user)
  - **Collection** — a group of resources (all users)
- **API Gateway** — the entry point that filters bad requests, monitors traffic, and routes to the right backend service (think: bouncer)
- **Microservices** — modular backend components (payments, email, auth) that talk to each other via APIs

### 2.3 Example: Twitter API Request
```
GET /1.1/statuses/show.json?id=210462857140252672
Host: api.twitter.com
```
This requests a single tweet by ID and returns it in **JSON**.

### 2.4 The API Contract and CRUD
The **API contract** is the (usually human-readable) documentation describing how to use the API — endpoints, required parameters, variable placeholders (shown as `{}` or `:id`), and expected responses. Reading the contract is often step one of real-world API testing, since it maps the attack surface for you.

> **Self-check — Where's the API contract, and why check it first?** Look for it in API documentation portals, OpenAPI/Swagger/YAML spec files, Postman collections, or a developer portal. It matters early because it hands you a near-complete map of endpoints, parameters, and expected auth *before* you write a single request — turning blind discovery into a checklist, and often revealing endpoints or parameters you wouldn't have found by just clicking through the app.

Most APIs map their operations to **CRUD**:

| CRUD | HTTP Method(s) |
|---|---|
| **C**reate | `POST` |
| **R**ead | `GET` |
| **U**pdate | `PUT` or `POST` |
| **D**elete | `DELETE` or `POST` |

### 2.5 Standard API Types
| Type | Key Traits |
|---|---|
| **RESTful** | Architectural style built on six constraints — most notably **stateless** and a **uniform interface**; typically many endpoints, one per resource type |
| **GraphQL** | Single entry point (one URL), uses `POST`; consumer specifies exactly which fields to return, avoiding over-fetching |

*(Note: SOAP/XML-based APIs are older but still appear in enterprise environments — worth knowing they exist even though REST/GraphQL dominate modern apps.)*

### 2.6 API Headers
| Header | Purpose |
|---|---|
| `Authorization` | Carries credentials/tokens, e.g. `Authorization: Bearer <token>` |
| `Content-Type` | Describes the format of the request body, e.g. `application/json` |
| `X-*` (custom/middleware headers) | Used for rate limiting, metrics, or (sometimes carelessly) revealing backend tech, e.g. `X-Powered-By` |

**Security angle:** custom `X-` headers are a common source of accidental information disclosure — worth flagging every time you see one during recon.

### 2.7 Data Interchange Formats
| Format | Notes |
|---|---|
| **JSON** | Most common; key/value pairs, e.g. `"firstName": "James"`; lightweight and machine-friendly |
| **XML** | Tag-based like HTML; commonly paired with SOAP APIs |
| **YAML** | Indentation-based, human-readable; commonly used for API specifications (OpenAPI/Swagger) |

### 2.8 API Authentication and Authorization
Because APIs are stateless, identity must be proven on **every single request** — there's no persistent login session to lean on.

| Method | How it Works |
|---|---|
| **Basic Authentication** | Username:password, usually base64-encoded, sent in a header (weak — base64 is *encoding*, not encryption) |
| **API Keys** | Unique provider-issued strings used to authorize access |
| **JWT (JSON Web Token)** | Three parts — header, payload (claims/user data), signature — used to validate the token wasn't tampered with |
| **HMAC** | Uses a shared secret key to generate a hash/digest proving request integrity |
| **OAuth 2.0** | Delegated access standard — lets one service access another's data (e.g., LinkedIn reading your Twitter posts) via time-limited access tokens, without sharing passwords |

> **Authentication vs. Authorization** — worth keeping distinct as you move forward: authentication asks *"who are you?"*, authorization asks *"what are you allowed to do?"*. A huge share of real-world API vulnerabilities (like BOLA/BFLA in the OWASP API Top 10) come from systems that authenticate correctly but authorize sloppily.

> **Self-check — API key vs. JWT vs. OAuth access token:** an **API key** is just a static, opaque string issued by the provider — it proves *which app/consumer* is calling, not *which user*, and carries no built-in expiry or embedded data. A **JWT** is self-contained and signed — it carries the user's claims directly inside the token (readable by anyone, but only *trustable* if the signature checks out) and is commonly short-lived. An **OAuth 2.0 access token** is about *delegated* access — it's issued after a consent flow so one service can act on a user's behalf on another service, typically time-limited, without the user ever handing over their password.

## Chapter 3: Scoping an Engagement & Common API Vulnerabilities

### 3.1 Scoping an API Security Engagement
Before testing begins, the main question is: **what's the actual size of the work?** Scoping means inventorying unique endpoints, HTTP methods, API versions, authentication mechanisms, and privilege levels so you know what "done" looks like.

**Features worth scoping in:**

| Area | Why it matters |
|---|---|
| **Authentication & Authorization** | Test across *multiple* users and roles — most impactful bugs live in the gaps between privilege levels, not in a single user's session |
| **Mobile app APIs** | If a mobile app exists, its backend API is in scope too — test via manual code review, automated static analysis, and dynamic analysis (proxying the app's live traffic) |
| **API Documentation** | Docs are frequently stale or inaccurate. Auditing them against the real API often surfaces business logic flaws or accidental sensitive-data disclosure |
| **Rate Limiting** | Distinct from DoS testing — the goal here is bypassing monetization/anti-abuse controls (e.g., a "free tier" limit), not crashing the service |
| **WAFs (Web Application Firewalls)** | Not part of the API itself, but they *will* block your traffic. Best practice: request a WAF bypass so you're testing the API's real controls, not just the firewall's |

> **Takeaway:** scoping isn't paperwork — it's where you decide whether you're testing "the API" or "the API as protected by three other layers," which produces very different results.

> **Self-check — Why is rate-limit testing scoped separately from DoS testing?** They target different failure modes. Rate-limit testing asks "can I bypass a *business* control?" (e.g., a free-tier cap, a per-minute quota tied to monetization) without necessarily sending huge volumes of traffic. DoS testing asks "can I exhaust *infrastructure*?" by brute-force volume, which risks actually taking the service down. Most engagements explicitly scope DoS testing out (or heavily restrict it) because it can cause real outages, while rate-limit-bypass testing is safe to perform and still finds a real class of bugs.

### 3.2 The OWASP API Security Top 10 (and related risks)
These are the vulnerability categories the rest of the book builds toward. Each one below includes a concrete example so the concept sticks.

---

#### 1. Information Disclosure
Sensitive data leaks to users who shouldn't see it — via API responses, public repos, or verbose errors.

**Example:** A WordPress site unintentionally exposes all usernames through its default users endpoint:
```
GET /wp-json/wp/v2/users HTTP/1.1
Host: target.com
```
```json
[
  { "id": 1, "name": "admin", "slug": "admin" },
  { "id": 2, "name": "jsmith", "slug": "jsmith" }
]
```
Those usernames become a ready-made list for a password brute-force attack.

---

#### 2. Broken Object Level Authorization (BOLA)
The most common API vulnerability. The API fails to verify that the requesting user actually *owns* the object they're asking for.

**Example:** Swapping an object ID in the URL to view another user's data:
```
GET /api/users?id=5501 HTTP/1.1
Authorization: Bearer <your_token>
```
Change to:
```
GET /api/users?id=5502 HTTP/1.1
Authorization: Bearer <your_token>
```
If this returns user `5502`'s private data using *your* token, that's a BOLA.

---

#### 3. Broken User Authentication
Weaknesses in how identity is proven — predictable tokens, mishandled sessions, or reset flows with no brute-force protection.

**Example:** A 4-digit password reset code with no rate limiting:
```
POST /api/password-reset/verify HTTP/1.1
Content-Type: application/json

{ "email": "victim@target.com", "code": "0001" }
```
Looping through `0000`–`9999` (10,000 requests) with no lockout or throttling lets an attacker guess the correct code.

---

#### 4. Excessive Data Exposure
The endpoint returns *more* fields than the client actually needs, trusting the frontend to filter — but nothing stops an attacker from reading the raw response.

**Example:** A `/profile` endpoint meant to show a public username instead returns internal fields:
```
GET /api/profile/122 HTTP/1.1
```
```json
{
  "username": "jane_doe",
  "email": "jane@target.com",
  "isAdmin": false,
  "passwordHash": "5f4dcc3b5aa765d61d8327deb882cf99",
  "securityQuestion": "mother's maiden name"
}
```
The UI might only *display* the username, but the full object — including the password hash — was sent over the wire.

---

#### 5. Lack of Resources & Rate Limiting
No cap on request volume lets an attacker exhaust infrastructure — a Denial of Service (DoS) condition.

**Example:** Hammering an endpoint to see if the API pushes back:
```
for i in {1..5000}; do
  curl -s -o /dev/null -w "%{http_code}\n" https://target.com/api/search?q=test
done
```
A healthy API should start returning `429 Too Many Requests` well before 5,000 requests; if it just keeps returning `200 OK`, there's no effective throttling.

---

#### 6. Broken Function Level Authorization (BFLA)
A user can invoke *functionality* reserved for a higher-privileged role. (BOLA = wrong **data**; BFLA = wrong **action**.)

**Example:** A low-privileged user's token used against an admin-only action:
```
DELETE /api/admin/account/delete HTTP/1.1
Authorization: Bearer <low_privileged_user_token>
Content-Type: application/json

{ "userId": 9001 }
```
If the server executes this instead of returning `403 Forbidden`, that's BFLA.

> **Self-check — BOLA vs. BFLA in one line each:** BOLA — `GET /api/users?id=5502` with *your own* token returns *someone else's data* (wrong **data**). BFLA — `DELETE /api/admin/account/delete` with a *low-privileged* token still executes (wrong **action**). Same root cause (missing authorization checks), different thing being checked: object ownership vs. permitted functionality.

---

#### 7. Mass Assignment
The API blindly binds client-supplied JSON fields to an internal object instead of only accepting a whitelist of expected fields.

**Example:** Slipping an extra privileged field into a normal registration request:
```
POST /api/users/register HTTP/1.1
Content-Type: application/json

{
  "username": "attacker",
  "password": "SuperSecret123",
  "isAdmin": true
}
```
If the backend saves `isAdmin` straight onto the new user record because it wasn't filtered out, the attacker registers as an administrator.

> **Self-check — Why does Mass Assignment work?** The underlying mistake is a **missing whitelist**. Instead of the backend explicitly listing which fields a request is allowed to set (e.g., `username`, `password` only), it takes the entire client-supplied JSON object and binds it directly onto the internal model. Any field that happens to match an internal property name — `isAdmin`, `role`, `balance`, `accountLevel` — gets set, whether or not the developer meant to expose it.

---

#### 8. Security Misconfigurations
A broad bucket: misconfigured headers, HTTP instead of HTTPS, default credentials, overly verbose error output, etc.

**Example:** A response header leaking backend stack details:
```
HTTP/1.1 200 OK
X-Powered-By: Express/4.17.1
Server: Apache/2.4.29 (Ubuntu)
```
Knowing the exact framework and version lets an attacker go look up known CVEs for that specific build.

> **Self-check — Two ways a misconfiguration leaks backend info:** (1) **Headers**, as above — `X-Powered-By` or `Server` revealing exact framework/version. (2) **Verbose error messages** — an unhandled exception that echoes back a stack trace, file path, or database error (e.g., a raw `SQLSTATE` error) tells an attacker what language, ORM, or database engine is running under the hood, narrowing down which exploits to try.

---

#### 9. Injection
Unsanitized input gets interpreted as executable code by a downstream interpreter — SQL, NoSQL, OS commands, etc.

**Example:** Classic SQL injection through a query parameter:
```
GET /api/products?category=widgets' OR '1'='1 HTTP/1.1
```
If the backend concatenates this straight into a SQL query, the `OR '1'='1` condition can dump every row in the table. A verbose error like `SQLSTATE[42000]: syntax error near '1'='1'` in the response is a strong signal the input reached the database unsanitized.

---

#### 10. Improper Assets Management
Old, forgotten, or non-production API versions stay live and reachable — often with weaker protections than the current version.

**Example:** The current app uses `v2`, but `v1` is still reachable and unpatched:
```
GET /api/v2/users/5501 HTTP/1.1   → 403 Forbidden (BOLA protection in place)
GET /api/v1/users/5501 HTTP/1.1   → 200 OK (no BOLA check — legacy endpoint)
```
The deprecated `v1` endpoint becomes a bypass for a fix that only made it into `v2`.

---

#### 11. Business Logic Vulnerabilities
Abuse of *intended* functionality, exploiting the assumption that users will behave honestly.

**Example:** A file upload feature that checks the `Content-Type` header but not the actual file content/extension:
```
POST /api/upload HTTP/1.1
Content-Type: multipart/form-data; boundary=----X

------X
Content-Disposition: form-data; name="file"; filename="shell.php"
Content-Type: image/jpeg

<?php system($_GET['cmd']); ?>
------X--
```
By spoofing `Content-Type: image/jpeg` while uploading a `.php` file, an attacker can get a web shell onto the server if the app trusts the declared type over the real content.

---

> **Pattern to notice across all 11 (self-check — the common thread):** almost every category boils down to the API **trusting the client** — trusting it to only ask for its own data (BOLA), only call allowed functions (BFLA), only send expected fields (Mass Assignment), or only send well-formed input (Injection). Testing an API is largely the process of finding where that trust is misplaced.

## Section 4: Common API Types (Overview)

*Source: supplementary video transcript (translated from Vietnamese, condensed and technically verified) for §4.1–4.8; a personal pentesting-reference note (technically verified and reworked) for §4.9–4.10 — not from the Hacking APIs book itself, but useful context for Part I since it expands on the "Standard API Types" introduced in §2.5.*

This section is a broader survey of API architectures you'll encounter in the wild beyond REST — useful for recognizing what you're actually looking at during recon, since each type has a different attack surface and testing approach.

### 4.1 REST (Representational State Transfer)
The most widely used API style today. The classic analogy: a REST API is like a waiter — the client "orders" via a request, the server "kitchen" prepares it, and the response comes back with exactly what was asked for (in principle).

- Uses standard HTTP methods: `GET` (read), `POST` (create), `PUT`/`PATCH` (update), `DELETE` (remove)
- **Stateless** — each request is independent; the server holds no memory of previous requests, which lets it scale to handle huge numbers of concurrent clients without cross-request confusion
- Acts as a common language — web apps, mobile apps, and IoT devices can all talk to the same REST API
- **Trade-off:** simple and fast, but not strict enough for domains that need airtight guarantees (e.g., banking), which is where SOAP historically stepped in

```
GET /api/users/122 HTTP/1.1
Host: example.com
```

### 4.2 SOAP (Simple Object Access Protocol)
One of the oldest and strictest API standards, still dominant in banking, healthcare, and government systems where reliability and formal contracts matter more than speed.

If REST is a casual conversation, SOAP is a binding legal contract. Every message is standardized **XML** with a fixed structure:

| Part | Required? | Role | Analogy |
|---|---|---|---|
| **Envelope** | Required | Wraps the entire message; must declare a namespace attribute — this is what marks it as SOAP rather than generic XML | The outer shipping box |
| **Header** | Optional | Metadata — sender, receiver, security requirements, extensions | The shipping label |
| **Body** | Required | The actual payload — the procedure being called and its parameters | The contents inside the box |
| **Fault** | Optional (inside Body) | Carries structured error information when a call fails | A "delivery failed" slip inside the box |

- **Protocol-independent** — commonly runs over HTTP/HTTPS, but can also run over SMTP, TCP, and others
- Built-in standards for error handling, security, and transactional integrity
- **Example use case:** a bank-to-bank funds transfer is often still backed by a SOAP service under the hood, precisely because of this rigor
- Note: real-world SOAP envelopes vary slightly in namespace/formatting details between implementations, but the four-part anatomy above stays consistent

```xml
<soap:Envelope>
  <soap:Header>
    <Auth>token123</Auth>
  </soap:Header>
  <soap:Body>
    <TransferFunds>
      <From>ACC001</From>
      <To>ACC002</To>
      <Amount>500.00</Amount>
    </TransferFunds>
  </soap:Body>
</soap:Envelope>
```

### 4.3 gRPC
A high-performance evolution of the older RPC (Remote Procedure Call) model. Where classic RPC (XML-RPC, JSON-RPC) let you call a function on a remote server as if it were local — but was slow due to verbose text formats — **gRPC**, built by Google, fixes the performance problem.

- Uses **Protocol Buffers (protobuf)** instead of JSON/XML — data is serialized into a compact **binary** format
- Runs over **HTTP/2**, allowing multiple requests to be multiplexed over a single connection
- Supports four communication patterns:
  1. **Unary** — simple one request → one response (like REST)
  2. **Server streaming** — server continuously pushes data to the client
  3. **Client streaming** — client continuously sends data until finished
  4. **Bidirectional streaming** — both sides stream data to each other simultaneously in real time
- Commonly cited as **7–10x faster** than REST for comparable workloads
- Used heavily where low latency matters at scale: Netflix, Uber, high-frequency financial systems

```protobuf
service UserService {
  rpc GetUser (UserRequest) returns (UserResponse);
}
```

### 4.4 GraphQL
A query language for APIs, developed by Facebook, designed to fix two specific pain points in REST:

| REST Problem | Description |
|---|---|
| **Over-fetching** | Requesting a user's name and email, but the response also includes address, phone number, purchase history, etc. — wasted bandwidth |
| **Under-fetching** | A single endpoint doesn't return everything needed, forcing multiple chained API calls to assemble one screen |

GraphQL solves both with a **single endpoint** where the client specifies exactly which fields it wants, and gets back exactly that — no more, no less. It also ships with a built-in interactive explorer for browsing the schema and testing queries live.

```
POST /graphql HTTP/1.1
Content-Type: application/json

{ "query": "{ user(id: 122) { name email } }" }
```

Adopted widely by GitHub, Shopify, and Pinterest — especially popular for mobile-first apps that need to minimize payload size.

*(Note: GraphQL's single-endpoint, client-specified-query model is exactly why it has its own dedicated OWASP-style risks later in the book — e.g., overly complex queries used for denial of service, or introspection queries leaking the entire schema.)*

### 4.5 Webhooks
Traditional APIs are **pull-based** — the client has to keep asking, "anything new yet?" (like repeatedly checking a mailbox). A **webhook** flips this to **push-based**: the server notifies the client automatically the moment something happens, like a mail carrier knocking the instant a letter arrives.

**How it works:**
1. The client registers a **callback URL** with the provider.
2. When a defined event occurs (payment completed, form submitted, new comment), the provider sends an HTTP request — usually `POST` — to that callback URL with the event details.
3. The client's server processes it immediately and updates accordingly.

```
POST /webhooks/github HTTP/1.1
Content-Type: application/json

{
  "event": "push",
  "repository": "my-app",
  "pusher": "jdoe",
  "commits": 3
}
```

Real-world examples: GitHub fires a webhook on every new push; Shopify fires one on every completed order. This is core to workflow automation and keeping systems in sync in real time.

> **Security angle:** since a webhook is really just an unauthenticated `POST` request unless you secure it, callback endpoints need their own verification (e.g., signature headers like `X-Hub-Signature`) — otherwise anyone who finds the URL can forge fake events.

### 4.6 WebSocket
Where REST is like sending individual letters back and forth, **WebSocket** is like keeping a phone line open — a persistent, **full-duplex** connection where either side can send data at any time without waiting to be asked.

**Handshake process:**
1. The client sends a special HTTP request asking to "upgrade" the connection to WebSocket.
2. If the server agrees, the connection upgrades and stays open.
3. From that point on, data flows freely in both directions with no repeated request/response overhead.

```
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
```

This is what powers live stock tickers, real-time chat, and multiplayer game state — any data format can flow over it: plain text, JSON, or binary (images, video chunks).

### 4.7 WebRTC (Web Real-Time Communication)
More than a single API — a full framework letting browsers and mobile apps exchange data **directly, peer-to-peer**, without routing media through a central server. This is what powers video calls, screen sharing, and high-speed file transfer directly in the browser with no extra software installed.

- In a service like Google Meet, once the connection is established, video/audio travels **directly between the two devices** — no server sits in the middle recording or relaying the actual call content.
- *(Accuracy note: while the media stream itself is peer-to-peer, WebRTC still typically relies on a **signaling server** to help two devices discover and negotiate a connection — and on **STUN/TURN servers** to work around firewalls/NAT, especially when both peers are on different networks like 4G and coffee-shop Wi-Fi. So it's peer-to-peer for the actual media, not fully serverless end-to-end.)*
- WebRTC continuously monitors connection quality and dynamically adjusts video resolution — dropping quality to preserve a stable call rather than letting it freeze or disconnect.

This is the core technology behind essentially every in-browser video calling and real-time collaboration platform today.

### 4.8 Summary Table

| Type | Format | Best For | Key Trait |
|---|---|---|---|
| **REST** | JSON/XML over HTTP | General-purpose web/mobile APIs | Simple, stateless, widely supported |
| **SOAP** | Strict XML | Banking, healthcare, government | Rigid contract, protocol-independent |
| **gRPC** | Binary (Protocol Buffers) over HTTP/2 | Low-latency microservices at scale | 4 streaming modes, very fast |
| **GraphQL** | JSON, client-defined query | Mobile-first apps, flexible data needs | Single endpoint, no over/under-fetching |
| **Webhook** | HTTP callback (usually JSON) | Event-driven notifications | Push instead of poll |
| **WebSocket** | Persistent full-duplex connection | Real-time chat, tickers, gaming | Either side can push anytime |
| **WebRTC** | Peer-to-peer media/data | Video calls, screen sharing | Direct device-to-device, low latency |

### 4.9 Web Services vs. APIs — Clarifying the Terms
These two terms get used interchangeably, but they aren't quite the same thing.

- **Web Service** — standardized communication between different software applications across different platforms, languages, and frameworks, typically described in a machine-processable XML format. Classic example: a Java app on Linux talking to a C++ app on Windows over the network, each with a completely different tech stack underneath.
- **API** — a broader set of rules for how software exchanges data, with technical specifications dictating the exact request/response format. An API doesn't require a network at all.

**Relationship: web services are a type of API — not every API is a web service.**

| Dimension | Web Service | API (general) |
|---|---|---|
| **Network dependency** | Requires a network | Can work offline (e.g., a local library call) |
| **External developer access** | Rarely exposed to outside developers | Many APIs are built specifically to welcome external developers |
| **Common protocols** | Typically SOAP (chosen for its stronger built-in security model) | Broader mix — XML-RPC, JSON-RPC, SOAP, REST, GraphQL, gRPC |
| **Typical data format** | Usually XML | Commonly JSON, but also XML, YAML, or binary (protobuf) |

### 4.9.1 The Web Service "Family" of Approaches
Beyond REST and SOAP (§4.1–4.2), a few other approaches show up under the "web service" umbrella — worth recognizing them even briefly, since older/enterprise targets during recon may still be running them:

| Approach | Format | Notes |
|---|---|---|
| **XML-RPC** | XML | The oldest of the bunch — a single `<methodCall>` wrapping a `<methodName>` and optional `<params>`, sent as an HTTP `POST`. SOAP is essentially XML-RPC extended with stricter typing, headers, and fault-handling |
| **JSON-RPC** | JSON | Same remote-procedure-call idea as XML-RPC, just JSON instead of XML: a `method` name, `params`, and a client-supplied `id` used to match the response back to the request |
| **SOAP** | XML | Covered in §4.2 — adds header/body structure, optional WSDL contract, and works over multiple transports beyond HTTP |
| **WS-BPEL** | XML | "Web Services Business Process Execution Language" — sits on top of SOAP, used to describe and orchestrate multi-step business processes (e.g., chaining several service calls into one workflow) rather than a single call |
| **REST** | JSON or XML | Covered in §4.1 — the modern default; WSDL-style formal contracts are technically possible but rarely used |

**Minimal XML-RPC example** (a client asking a server for a US state name by ID):
```
POST /RPC2 HTTP/1.1
Content-Type: text/xml

<?xml version="1.0"?>
<methodCall>
  <methodName>examples.getStateName</methodName>
  <params>
    <param><value><i4>41</i4></value></param>
  </params>
</methodCall>
```
```xml
<?xml version="1.0"?>
<methodResponse>
  <params>
    <param><value><string>South Dakota</string></value></param>
  </params>
</methodResponse>
```

**Minimal JSON-RPC example** (calling a `sum` function):
```
POST /rpc HTTP/1.1
Content-Type: application/json-rpc

{"method": "sum", "params": {"a": 3, "b": 4}, "id": 0}
```
```json
{"result": 7, "error": null, "id": 0}
```

**Practical takeaway for testing:** the label doesn't change the fundamentals. Whether something is marketed as a "web service" or a "web API," if it's reachable over a network and exchanges structured data, the same basics apply — requests, responses, headers, authentication — and the same OWASP API Top 10 risk categories from §3.2 are fair game to test for.

### 4.10 WSDL (Web Services Description Language) — SOAP's "API Contract"
WSDL is used **exclusively with SOAP-based** web services (never with REST/GraphQL/gRPC). It's an XML file that formally describes every method a service exposes, where to reach them, and exactly how to call them — functionally, it's SOAP's version of the "API contract" from §2.4, except structured and machine-readable rather than prose documentation.

**Why it matters for testing:** developers sometimes hide the WSDL file (unusual filename, non-default location) hoping to obscure the service's full functionality — a form of "security through obscurity." That makes discovering it a genuine recon win: a hidden WSDL file often reveals administrative or debug operations that were never meant to be publicly reachable.

**Discovering a hidden WSDL file — worked example:**

Suppose a SOAP service is running on a target with no WSDL location disclosed. Directory fuzzing is the first move:
```
$ dirb http://TARGET:3002

+ http://TARGET:3002/wsdl (CODE:200 | SIZE:0)
```
An endpoint exists, but fetching it directly (`curl http://TARGET:3002/wsdl`) returns an **empty response** — the endpoint is real, but something else is needed to actually retrieve the definition. That's often a query parameter, so the next move is parameter fuzzing:
```
$ ffuf -w burp-parameter-names.txt \
       -u 'http://TARGET:3002/wsdl?FUZZ' -fs 0 -mc 200
```
This turns up `wsdl` itself as a valid parameter name. Requesting it directly returns the full definition:
```
$ curl http://TARGET:3002/wsdl?wsdl

<?xml version="1.0" encoding="UTF-8"?>
<wsdl:definitions targetNamespace="http://tempuri.org/" ...>
  ...
</wsdl:definitions>
```

> **Note:** WSDL files turn up under many different names and paths in practice — `/example.wsdl`, `?wsdl`, `?disco`, `/example.disco`, and others. (`.disco` is an older Microsoft technology for publishing/discovering web services, distinct from WSDL itself but serving a similar purpose.)

### 4.10.1 Reading a WSDL File
Once found, a WSDL file (v1.1) breaks down into these elements — worth being able to recognize each, since they map directly onto what you'd target during testing:

| Element | Purpose | What to look for |
|---|---|---|
| **`<definitions>`** | Root element — the service name, namespaces, and container for everything else | The overall service identity |
| **`<types>`** | Defines the data types used in requests/responses (via an embedded XML Schema) | Expected parameter types — useful for crafting valid-looking malicious input |
| **`<message>`** | Defines each operation's input and output as a named message | Which operations exist, and what each one sends/receives |
| **`<portType>`** (interface, in WSDL 2.0) | Groups the available operations together with their input/output messages | The functional "menu" of everything the service can do — including operations that may never be called from the normal client UI |
| **`<binding>`** | Maps operations to the actual SOAP transport details (encoding, transport protocol) | Confirms exactly how to format a real request for a given operation |
| **`<service>`** | The concrete address (URL) where the service can actually be reached | Where to send your crafted requests |

**Simplified example structure:**
```xml
<wsdl:definitions targetNamespace="http://tempuri.org/">

  <wsdl:types>
    <s:element name="LoginRequest">
      <s:complexType>
        <s:sequence>
          <s:element name="username" type="s:string"/>
          <s:element name="password" type="s:string"/>
        </s:sequence>
      </s:complexType>
    </s:element>
  </wsdl:types>

  <wsdl:message name="LoginSoapIn">
    <wsdl:part name="parameters" element="tns:LoginRequest"/>
  </wsdl:message>

  <wsdl:portType name="ServiceSoapPort">
    <wsdl:operation name="Login">
      <wsdl:input message="tns:LoginSoapIn"/>
      <wsdl:output message="tns:LoginSoapOut"/>
    </wsdl:operation>
  </wsdl:portType>

  <wsdl:binding name="ServiceSoapBinding" type="tns:ServiceSoapPort">
    <soap:binding transport="http://schemas.xmlsoap.org/soap/http"/>
    <wsdl:operation name="Login">
      <soap:operation soapAction="Login" style="document"/>
    </wsdl:operation>
  </wsdl:binding>

  <wsdl:service name="TargetService">
    <wsdl:port name="ServiceSoapPort" binding="tns:ServiceSoapBinding">
      <soap:address location="http://target/wsdl"/>
    </wsdl:port>
  </wsdl:service>

</wsdl:definitions>
```

> **Testing angle:** a WSDL file is essentially a menu of every callable operation on the service — including ones like an internal "execute command" or "admin login" operation that would never be discoverable just by browsing a web app's UI. Once you have the `portType` and `binding` sections, you have everything needed to hand-craft a raw SOAP request (§4.2) for *any* operation listed, not just the ones the front-end actually uses.
