# 1. How Web Applications Work

To understand how to hack web APIs, you must first understand the fundamental technologies that support them. This section covers the basics of web applications, the structure of HTTP communications, and how databases store the information these applications use.

### **1. Web Application Basics**
Web applications operate on a **client/server model**. In this model, your web browser (the **client**) generates requests for resources and sends them to computers called **web servers**. The server then sends those resources back to the client over a network.

Unlike a static website, which is typically read-only, a **web application** allows communication to flow in both directions, enabling **end-user interactivity**. For example, on a site like Reddit, you aren't just reading content; you are interacting by posting, upvoting, and commenting.

### **2. The URL (Uniform Resource Locator)**
The URL is the address used to locate unique resources on the internet. A standard URL consists of several key components:

*   **Protocol:** The rules computers use to communicate (e.g., `http`, `https`, or `ftp`).
*   **Hostname:** The domain name of the server (e.g., `twitter.com`).
*   **Port:** The specific communication channel (e.g., port 80 for HTTP, 443 for HTTPS).
*   **Path:** The directory path pointing to specific files on the server.
*   **Query:** An optional part used for searching or filtering, starting with a question mark (`?`).
*   **Query Parameters:** Values that describe what should be done with the query, often separated by an ampersand (`&`).

### **3. HTTP Requests**
When you navigate to a URL, your browser automatically generates an **HTTP request** for a resource, such as the files for a web page. This request includes:

*   **Method:** Tells the server what you want to do (e.g., `POST` to send login data).
*   **Path:** The location of the specific resource requested.
*   **Headers:** Key-value pairs that communicate metadata, such as the `User-Agent` (browser info) or `Cookie` (session info).
*   **Message Body:** The actual information being sent to the application, such as a username and password.

### **4. HTTP Responses**
The server processes your request and sends back an **HTTP response**. This response contains:

*   **Status Code:** A numerical code indicating how the server handled the request (e.g., `200 OK` for success, or `404 Not Found` if the resource is missing).
*   **Response Headers:** Instructions for the browser on how to handle the data or security requirements (e.g., `set-cookie`).
*   **Response Body:** The actual data requested, such as HTML code to render a page.

### **5. HTTP Methods (Verbs)**
HTTP methods indicate the desired action to be performed on a resource. The most common are:

*   **GET:** Used to retrieve resources from a server.
*   **POST:** Used to submit data to a server to create new resources.
*   **PUT:** Used to store or replace a resource at a specific URL.
*   **DELETE:** Used to remove a resource.

Some methods are **idempotent**, meaning sending the same request multiple times won't change the state of the resource after the first time (like `GET` or `DELETE`). **Non-idempotent** methods, like `POST`, can create multiple new resources if submitted multiple times.

### **6. Stateful vs. Stateless HTTP**
HTTP is naturally **stateless**, meaning the server doesn’t remember you between individual requests.

*   **Stateful Connections:** Use **cookies** stored on your browser to help the server "remember" your session, such as keeping items in a shopping cart as you move between pages.
*   **Stateless Connections:** The server doesn't store session data. Instead, **every request must contain all the information** (like an authorization token) needed for the server to recognize and authorize the requester. **APIs are generally stateless**.

### **7. Web Server Databases**
Web applications typically pass data from the **frontend** (what the user sees, like HTML/JavaScript) to **backend** databases for storage. There are two main types of databases used today:

*   **SQL (Relational):** Highly structured databases that use Structured Query Language.
*   **NoSQL (Nonrelational):** Distributed databases that handle unstructured data as documents or key-value pairs (e.g., MongoDB).

### **8. How APIs Fit In**
APIs (Application Programming Interfaces) are the technology that allows these different applications to communicate with each other. By using standardized HTTP methods and status codes, web APIs provide a streamlined way for machines to exchange information. While they make applications more powerful, they also significantly expand the **attack surface** that hackers can target.

# 2. The anatomy of Web APIs

To understand the anatomy of web APIs, think of them as the engine running beneath the surface of a web application's graphical user interface (GUI). While a regular user sees images and buttons, **web APIs perform the work of fetching and transferring that data over HTTP**.

Simply put, an API is a technology that enables communication
between different applications. When, for example, a Python application
needs to interact with the functionality of a Java app, things can get messy
very quickly. By relying on APIs, developers can design modular applications that leverage the expertise of other applications. For example, they no
longer need to create their own custom software to implement maps, payment processors, machine-learning algorithms, or authentication processes.

### **1. How Web APIs Work**
Like web applications, APIs function through a **client/server relationship** between the **provider** (host) and the **consumer** (the person or system making the request).

*   **Endpoints:** These are specific URLs used to interact with the API (e.g., `https://example.com/api/v3/users/`).
*   **Resources:** This is the data being requested. A **singleton resource** is a unique object (like one specific user), while a **collection** is a group of resources.
*   **API Gateway:** This acts as a "bouncer" or entry point, filtering bad requests, monitoring traffic, and routing requests to the correct services.
*   **Microservices:** These are modular pieces of an application that handle specific functions (like payments or email) and communicate via APIs.

#### APIs in a Nutshell

**APIs (Application Programming Interfaces)** are sets of rules that let different applications talk to each other and share data in a controlled way.

#### How They Work

Think of an API as a waiter in a restaurant:
- You (the application) make a request
- The waiter (API) takes it to the kitchen (server)
- The kitchen prepares your order (processes the request)
- The waiter brings back your food (returns the data)

#### Real Example: Twitter API

When you want to get a specific tweet, you send a request like:
```
GET /1.1/statuses/show.json?id=210462857140252672
Host: api.twitter.com
```

The API returns data in **JSON format** - a text-based way to structure data using:
- **Curly brackets `{}`** for objects
- **Square brackets `[]`** for lists  
- **Key-value pairs** like `"name": "Twitter API"`

#### Key Concepts

1. **Endpoints** - Specific URLs where you request different resources
2. **Parameters** - Details you include to specify what you want (like the tweet ID)
3. **Authentication** - Most APIs require access tokens or credentials to prove who you are
4. **Response formats** - Usually JSON or XML containing the requested data

**Bottom line**: APIs let your code use features from other applications without building everything from scratch - like plugging Lego blocks together to create something bigger.


### **2. The API Contract and CRUD**
An **API contract** refers to the human-readable documentation that explains how to use the API, including endpoint variables (often shown in `{}` or with a `:`) and required parameters. Most APIs follow the **CRUD** model for interacting with data:
*   **C**reate (POST)
*   **R**ead (GET)
*   **U**pdate (PUT or POST)
*   **D**elete (DELETE or POST)

### **3. Standard API Types**
While there are many styles, two dominate modern web applications:
*   **RESTful APIs:** Designed to be approachable and efficient, REST is an architectural style based on six constraints, most notably being **stateless** (the server doesn't remember you between requests) and having a **uniform interface**.
*   **GraphQL:** Unlike REST, which uses many URLs, GraphQL typically uses a **single entry point (URL) and the POST method**. It allows consumers to query for the exact fields they need, avoiding "superfluous information".

### **4. API Headers**
Headers are key-value pairs that help the consumer and provider "speak the same language".
*   **Authorization:** Passes tokens or credentials (e.g., `Authorization: Bearer <token>`).
*   **Content-Type:** Describes the media you are sending (e.g., `application/json`).
*   **Middleware (X) Headers:** Custom headers (starting with `X-`) used for metrics, rate limiting, or revealing backend technology (e.g., `X-Powered-By`).

### **5. Data Interchange Formats**
APIs use standardized formats to exchange data so different programming languages can understand each other.
*   **JSON (JavaScript Object Notation):** The most common format; it uses key/value pairs (e.g., `"firstName": "James"`) and is easily parsed by machines.
*   **XML:** Uses descriptive tags (like HTML) to wrap data; it is most commonly associated with older SOAP APIs.
*   **YAML:** Highly readable format that uses indentation instead of brackets; it is often used for **API Specifications** like OpenAPI (Swagger).

### **6. API Authentication and Authorization**
Because APIs are often stateless, the consumer must prove their identity in **every request**.
*   **Basic Authentication:** Sending a username and password (often base64-encoded) in a header.
*   **API Keys:** Unique, random strings generated by the provider to authorize access.
*   **JSON Web Tokens (JWT):** A common token-based method consisting of three parts: a header, a payload (user data), and a signature for validation.
*   **HMAC:** A method where a secret key is used to create a "hash" or message digest to ensure the request hasn't been tampered with.
*   **OAuth 2.0:** A standard that allows services to access each other's data (like allowing LinkedIn to see your Twitter posts) using time-based access tokens instead of sharing passwords.
