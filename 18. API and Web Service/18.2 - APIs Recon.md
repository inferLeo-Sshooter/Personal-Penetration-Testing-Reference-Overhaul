# 1. Passive Recon

**Passive Reconnaissance**

Before attacking an API, you need to find it and confirm it's live. Along the way, gather credentials, version details, documentation, and the API's business purpose — the more you know, the better your odds of finding exploitable flaws.

APIs built for public or partner use usually come with documentation describing endpoints and usage. Internal or restricted APIs are harder to spot — look for naming patterns, response headers like `Content-Type: application/json`, JSON/XML responses, and clues in JavaScript source files.

**What Passive Recon Is**

Passive recon means gathering intel without touching the target's systems directly, so the target stays unaware. It relies on open-source intelligence (OSINT) to map the attack surface: endpoints to target later, credentials for authenticated (ideally admin) access, version info pointing to known vulnerabilities, documentation showing how the API works, and business context that can reveal logic flaws.

Sometimes OSINT turns up outright wins — exposed API keys, JWTs, or leaked PII like SSNs, names, emails, or credit card data. Flag and report these immediately; they're critical findings.

**The Process**

1. **Cast a wide net.** Use search engines (Google, Shodan, ProgrammableWeb) for general info on the API's purpose, design, and documentation. Map the attack surface with tools like DNS Dumpster (shows related hosts) and OWASP Amass.

2. **Adapt and focus.** Narrow your searches based on what you've found. Check GitHub for related repos, and use tools like Pastehunter to catch leaked secrets.

3. **Document everything.** Log findings and screenshots, and build a task list to revisit during active exploitation — you don't want to miss something like an exposed API key sitting on GitHub.

Different tools often surface overlapping results, but using several in parallel helps confirm findings and catch what one tool alone might miss.

## 1.1 - Google Hacking

Google hacking (or "Google dorking") uses advanced search operators to surface public API-related intel — vulnerabilities, API keys, usernames, and details on how a target's industry uses APIs. A few key operators:

| Query operator | Purpose |
|---|---|
| `intitle` | Searches page titles |
| `inurl` | Searches words in the URL |
| `filetype` | Searches for specific file types |
| `site` | Restricts search to a specific site |

Start broad, then narrow. A search like `inurl:/api/` returns over 2 million results — far too many to be useful. Add the target's domain or name to cut this down, e.g. `intitle:"<targetname> api key"` for tighter, more relevant hits.

You can also draw on Offensive Security's **Google Hacking Database (GHDB)** (exploit-db.com/google-hacking-database), a curated set of queries for finding exposed systems and sensitive data.

| Query | Finds |
|---|---|
| `inurl:"/wp-json/wp/v2/users"` | Public WordPress API user directories |
| `intitle:"index.of" intext:"api.txt"` | Publicly exposed API key files |
| `inurl:"/includes/api/" intext:"index of /"` | Potentially interesting API directories |
| `ext:php inurl:"api.php?action="` | Sites vulnerable to XenAPI SQL injection |
| `intitle:"index of" api_key OR "api key" OR apiKey -pool` | Potentially exposed API keys |

## 1.2 - Shodan

Shodan is a search engine for internet-connected devices. It continuously scans the entire IPv4 space for open ports and publishes the results at shodan.io. Use it to find external-facing APIs and open port info on a target — handy when all you have is an IP or org name.

As with Google dorks, you can search casually by domain/IP or use targeted query parameters:

| Shodan query | Purpose |
|---|---|
| `hostname:"targetname.com"` | Basic search for the target's domain — combine with other queries below for specific results |
| `"content-type: application/json"` | Filters for responses set to JSON (typical for APIs) |
| `"content-type: application/xml"` | Filters for responses set to XML |
| `"200 OK"` | Filters for successful requests (a non-conforming API request often returns a 300 or 400 instead) |
| `"wp-json"` | Finds apps using the WordPress API |

You can combine these to find API endpoints even without standard naming conventions. For example, targeting eWise (ewise.com), a money management company:

`"ewise.com" "content-type: application/json"`

This surfaced a potential endpoint. Digging into the SSL certificate showed an Nginx server returning an `application/json` header and a 401 response — a common REST API pattern — revealing an API endpoint with no telltale naming at all.

`Shodan also offers browser extensions to check scan results on sites as you browse`.

## 1.3 - OWASP Amass

Amass is a command-line tool that maps a target's external network using OSINT from 55+ sources. It supports both passive and active scans — active mode pulls certificate info directly from the target; passive mode draws from search engines (Google, Bing, HackerOne), SSL certificate logs (GoogleCT, Censys, FacebookCT), search APIs (Shodan, AlienVault, Cloudflare, GitHub), and the Wayback Machine.

Example: a passive scan of twitter.com, filtered for API-related results:

```
$ amass enum -passive -d twitter.com |grep api
legacy-api.twitter.com
api1-backup.twitter.com
api3-backup.twitter.com
tdapi.twitter.com
failover-urls.api.twitter.com
cdn.api.twitter.com
pulseone-api.smfc.twitter.com
urls.api.twitter.com
api2.twitter.com
apistatus.twitter.com
apiwiki.twtter.com
```

This scan turned up 86 unique API subdomains, including `legacy-api.twitter.com` — worth flagging, since anything labeled "legacy" often points to an improper asset management issue (per the OWASP API Security Top 10).

**Useful commands:**

Collect SSL certs, reverse Whois records, and ASN IDs via `intel`:
```
$ amass intel -addr <target IP addresses>
```

Feed resulting domains back in for an active enumeration scan:
```
$ amass enum -active -d <target domain>
```

Add brute-forcing with a wordlist, and send output to a chosen directory:
```
$ amass enum -active -brute -w /usr/share/wordlists/API_superlist -d <target domain> -dir [directory name]
```

To visualize relationships in the data — DNS records, host dependencies, node relationships — generate an interactive web page:
```
$ amass viz -enum -d3 -dir <directory name>
```

## 1.4 - Exposed Information on GitHub

Even if your target doesn't develop its own software, GitHub is worth checking for sensitive disclosures — API capabilities, documentation, and secrets like admin-level keys, passwords, and tokens.

Start by searching the target's name alongside sensitive terms like "api-key," "password," or "token." Then dig into three key repository tabs:

**Code** — Shows current source, readmes, commit history, and contributors. Use CTRL-F to hunt for terms like "API," "key," or "secret," and check the **History** button for past commits — useful if an issue or comment hints at a since-"fixed" vulnerability that may still be exposed. The **Split** view lets you compare file versions side by side to pinpoint exact changes; one such case revealed a financial app's commit that removed a SonarQube private API key, exposing both the key and its associated endpoint.

**Issues** — Tracks bugs and feature requests. Open issues may point to still-live vulnerabilities; for closed ones, check the date and search the commit history around that time for the relevant fix.

**Pull Requests** — Shows proposed code changes, sometimes catching an API key mid-removal before the fix is finalized. The **Files Changed** tab pinpoints exactly what's being altered — for example, an exposed key on one line with its removal proposed on the next.

Even without finding an outright vulnerability, GitHub is useful for profiling your target: note the programming languages, API endpoint details, and documentation in use.

# 2. Active Recon

Passive recon relies on secondhand sources. To validate that information, you need direct interaction — port/vulnerability scanning, pinging, HTTP requests, API calls, and similar hands-on techniques.

**The Active Recon Process**

The process runs in three phases, each narrowing focus using results from the last:

- **Phase 1 — Detection scanning:** automated scans to find HTTP/HTTPS services
- **Phase 2 — Hands-on analysis:** manual inspection from both user and hacker perspectives
- **Phase 3 — Targeted scanning:** deeper, focused scans based on what you've learned

It's efficient because scans run in the background while you work — when analysis hits a dead end, check for new scan results. The process isn't linear: after each phase, analyze results and feed them back into further scanning. If you find a vulnerability, exploit it immediately, then return to the process as needed.

**Phase Zero: Opportunistic Exploitation**

If you spot a vulnerability at any point — seconds into a scan or months into research — exploit it right away, then resume the phased process. Experience teaches you when to chase a lead and when it's a rabbit hole.

**Phase One: Detection Scanning**

Run general scans to detect hosts, open ports, services, and OSes (see "Baseline Scanning with Nmap"). Once HTTP/HTTPS services turn up — the protocols APIs run on — let the scan continue and move to phase two.

**Phase Two: Hands-on Analysis**

Explore the web app manually via browser and API client, looking at requests, API links, documentation, and business logic. Examine the app from three angles:

- **Guest:** Can anonymous users interact with the API? Is documentation public? What can they do?
- **Authenticated user:** What extra access do they get — file uploads, new sections, API use? How does the app detect authentication?
- **Administrator:** Where do admins log in? What's revealed in page source, comments, languages used, or in-development sections?

Then intercept traffic with Burp Suite to catch API calls triggered by actions like searches or logins. When you stall, check phase-one scan results and move to phase three.

**Phase Three: Targeted Scanning**

Narrow your scans to the specifics: API type and version, web app framework, service versions, HTTP/HTTPS, active ports, and business logic details. For example, investigate nonstandard ports running an API, or check `/wp-json/wp/v2` if the site runs WordPress. From here, brute-force URIs to find hidden directories and files (see "Brute-Forcing URIs with Gobuster"), then loop results back into further hands-on analysis.

The following sections cover the tools involved: Nmap for detection scanning, DevTools for hands-on analysis, and Burp Suite/OWASP ZAP for targeted scanning.

---

## 2.1 - Baseline Scanning with Nmap

Nmap handles port scanning, vulnerability searches, service enumeration, and host discovery. It's the go-to tool for phase one detection scanning, and it's useful again later for targeted scanning.

For API discovery, run two scans:

**General detection scan** — uses default scripts and service enumeration, saving output in your chosen format(s) (`-oX` XML, `-oN` Nmap, `-oG` greppable, `-oA` all three):
```
$ nmap -sC -sV <target address or network range> -oA nameofoutput
```

**All-port scan** — checks all 65,535 TCP ports for running services, versions, and OS info:
```
$ nmap -p- <target address> -oA allportscan
```

Kick off the all-port scan as soon as the general scan starts returning results, then begin analyzing what comes in. APIs typically surface through HTTP-related results and other signs of web servers — usually on ports 80 and 443, though they can run on virtually any port. Once you find a web server, open it in a browser and start your hands-on analysis.

---

## 2.2 - Finding Hidden Paths in Robots.txt

`Robots.txt` is a common text file that tells web crawlers to omit results from the search engine findings. Ironically, it also serves to tell us which paths the target wants to keep secret. You can find the `robots.txt` file by navigating to the target’s `/robots.txt` directory (for example, `https://www.twitter.com/robots.txt`).

The following is an actual `robots.txt` file from an active web server, complete with a disallowed `/api/` path:
```
User-agent: *
Disallow: /appliance/
Disallow: /login/
Disallow: /api/
Disallow: /files/
```

## 1.3 - Finding Sensitive Information with Chrome DevTools

Chrome DevTools offers underrated tools for hunting through page source code to find sensitive information. Open your target page, launch DevTools (F12 or CTRL-SHIFT-I), go to the **Network** tab, and refresh.

**Network tab:** Look for interesting files — sometimes literally labeled "API." Right-click any JavaScript file of interest and choose **Open in Sources Panel** to view its code, or click **XHR** to see Ajax requests directly. Search the code for terms like "API," "APIkey," "secret," and "password" — this is how you might find an API call buried thousands of lines into a script.

**Memory tab:** Useful when static JS files are too large or unclear to trace manually. Instead of reading code, record how the app actually uses resources to interact with an API:

1. Click the **Memory** tab
2. Under Profiling Type, choose **Heap Snapshot**
3. Under JS VM Instance, select your target
4. Click **Take Snapshot**

Once compiled, select the snapshot and use CTRL-F to search for API path terms like "api," "v1," "v2," "swagger," "rest," or "dev" (the Assetnote API wordlists at wordlists.assetnote.io can help here too). This reveals API paths and lets you compare snapshots — useful for spotting differences between authenticated vs. unauthenticated states or across different app features.

**Performance tab:** Record specific actions (like a button click) and review them on a millisecond timeline to catch background API requests triggered by user events. Click record, perform the action, stop recording, then inspect the results. For example, recording a login click might reveal a POST request to `/identity/api/auth/login` under "Main" — a clear sign of an API call. Use the peaks in the timeline graph to quickly spot events worth investigating.
