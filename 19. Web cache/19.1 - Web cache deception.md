# 1. The Core Idea

A cache decides whether to store a response mainly by looking at the **request path** (and sometimes extension), not the actual content that comes back. WCD abuses that mismatch: you get a cache to store a **dynamic, sensitive, user-specific page** (like `/my-account`) under a URL that the cache *thinks* is a static file — then anyone who requests that same crafted URL gets served the victim's cached private data.

## Typical Attack Flow

1. **Find a sensitive dynamic page** that reflects user-specific data (e.g., `/my-account` showing API keys, session tokens, personal info).

2. **Craft a URL that looks static to the cache but still routes to the dynamic page on the backend.** Common tricks PortSwigger covers:
   - **Path mapping / extension confusion**: `/my-account/nonexistent.css` — some backend frameworks ignore the trailing junk and still serve the account page, but the cache sees `.css` and happily caches it as a static asset.
   - **Path parameter injection**: `/my-account;foo.css` or `/my-account/..%2fstatic.css` — using path syntax quirks so the origin still resolves to `/my-account` while the cache's path-matching logic treats it as a static resource.
   - **Delimiter confusion**: exploiting differences in how the cache vs. the origin server parse `?`, `#`, `;`, or encoded characters in the URL.

3. **Trick the victim into visiting that crafted URL** while they're logged in (via a link, XSS, phishing, etc.). Their authenticated session generates the sensitive response.

4. **The cache stores that response**, keyed to the crafted path, thinking it's a harmless static file.

5. **Attacker requests the exact same crafted URL** — no authentication needed — and gets served the victim's cached sensitive page straight from the cache.

# 2. Web cache

A web cache is a system that `sits between` the origin `server` and the `user`. 

<img width="909" height="455" alt="image" src="https://github.com/user-attachments/assets/795ccee1-586c-4f91-82c2-c8b4b9051ddd" />

1. When a client requests a `static resource`, the request is first directed to the `cache`.
2. If the `cache` doesn't contain a copy of the `resource` (known as a `cache miss`), the request is forwarded to the origin `server`, which processes and responds to the request.
3. The response is then sent to the `cache` before being sent to the `user`. The `cache` uses a preconfigured set of rules to determine whether to store the response.
4. When a request for the same `static resource` is made in the future, the `cache serves` the stored copy of the response directly to the user (known as a `cache hit`).


### 1. Why Web Caches Exist

Caching has become a common and crucial aspect of delivering web content, particularly with the widespread use of `Content Delivery Networks` (`CDNs`), which use caching to store copies of content on distributed servers all over the world. 

CDNs speed up delivery by serving content from the server closest to the user, reducing load times by minimizing the distance data travels.

Overall, the benefits of web cache include: 
- **Speed**: serve stored responses instead of regenerating them
- **Reduced origin load**: fewer requests hit the backend/database
- **Cost savings**: less compute/bandwidth needed
- **Scalability**: absorbs traffic spikes
- **Resilience**: can serve stale content if origin goes down

Caches make these decisions using **fast, shallow signals** (URL path, file extension) rather than deeply inspecting actual content — this shallow logic is the root cause of most cache-related vulnerabilities.

### 2. Who Controls the Cache
- **Third-party CDNs**: Cloudflare, Akamai, Fastly, CloudFront (most common)
- **Self-hosted reverse proxies**: Varnish, Nginx, Squid — site owner runs it themselves
- **Built into app/server stack** or load balancers
- Caching and load balancing are **different mechanisms** often bundled together but not the same thing

### 3. Who's Responsible for WCD
- Root cause: a **mismatch** between how the cache decides "is this cacheable" vs. how the backend actually routes the URL
- Can stem from: naive cache defaults, lenient backend path-parsing, or the *interaction* between the two
- **Responsibility generally falls on the web app owner/developer** — they must explicitly set `Cache-Control: no-store` (or similar) on sensitive dynamic pages, regardless of cache provider defaults

### 4. Who Uses Caching Most (WCD-relevant targets)
Sites that mix **static public content + dynamic authenticated content** on the same domain:
- E-commerce, news/media, SaaS platforms, social platforms, banking/fintech
- Any site behind widely-adopted CDNs (e.g., Cloudflare free tier)

---

## 2.1 - Cache keys

1. When a cache receives an HTTP request, it must decide whether to `serve a cached response` or `forward the request to the origin server`.
2. It makes this decision using a "cache key," generated from parts of the request—typically the `URL path` and `query parameters`, but sometimes also `headers`, `content type`, or other elements.
3. If a new request's cache key matches a previous one, the cache treats them as equivalent and serves the cached response.

---

## 2.2 - Cache rules

Cache rules define what gets cached and for how long. They typically target static resources (unchanging, reused across pages), while dynamic content is excluded since it may contain sensitive, user-specific data.

Web cache deception attacks exploit how these rules are applied, especially rules based on URL path strings:

* **Static file extension rules** – match file extensions like `.css` or `.js`.
* **Static directory rules** – match paths starting with a prefix like `/static` or `/assets`.
* **File name rules** – match specific common files like `robots.txt` or `favicon.ico`.

Caches may also use custom rules based on criteria like URL parameters or dynamic analysis.

---

# 3. Constructing a web cache deception attack

Basic steps:

1. **Find a target endpoint** returning dynamic, sensitive data. Check responses in Burp, since some data may not appear on the rendered page. Focus on `GET`/`HEAD`/`OPTIONS` endpoints, as state-changing requests usually aren't cached.
2. **Find a URL-parsing discrepancy** between cache and origin server — e.g., in resource mapping, delimiter handling, or path normalization.
3. **Craft a malicious URL** exploiting this discrepancy to get the cache to store a dynamic response. Once a victim visits it, their response gets cached. Use Burp (not a browser) to request the same URL and retrieve the cached data — browsers may redirect unauthenticated users or clear local data, masking the vulnerability.

---

## 3.1 - Using a cache buster

When testing for discrepancies and building an exploit, ensure each request has a unique cache key—otherwise you may just get served old cached responses, skewing results.

Since the cache key typically includes the URL path and query parameters, you can vary it by appending a different query string each time. Automate this with the Param Miner extension: go to **Param Miner > Settings** and enable **Add dynamic cachebuster**. Burp will then attach a unique query string to every request, viewable in the Logger tab.

---

## 3.2 - Detecting cached responses

You can identify cached responses by checking response headers and timing.

Headers to look for:

- The `X-Cache` header provides information about whether a response was served from the cache. Typical values include:
  - `X-Cache: hit` - The response was served from the cache.
  - `X-Cache: miss` - The cache did not contain a response for the request's key, so it was fetched from the origin server. In most cases, the response is then cached. To confirm this, send the request again to see whether the value updates to hit.
  - `X-Cache: dynamic` - The origin server dynamically generated the content. Generally this means the response is not suitable for caching.
  - `X-Cache: refresh` - The cached content was outdated and needed to be refreshed or revalidated.

- The `Cache-Control` header may include a directive that indicates caching, like `public` with a `max-age` higher than `0`. **Note that this only suggests that the resource is cacheable. It isn't always indicative of caching, as the cache may sometimes override this header**.

If you notice a big difference in `response time` for the same request, this may also indicate that the faster response is served from the cache.

# 4. Exploiting static extension cache rules

Cache rules often target static resources by matching common file extensions like `.css` or `.js`. This is the default behavior in most CDNs.

If there are discrepancies in how the cache and origin server map the URL path to resources or use delimiters, an attacker may be able to craft a request for a dynamic resource with a static extension that is ignored by the origin server but viewed by the cache.

## 4.1 - Path mapping discrepancies

URL path mapping associates URL paths with server resources (files, scripts, etc.). Two common styles:

- **Traditional mapping**: the path directly mirrors the file system, e.g. `http://example.com/path/in/filesystem/resource.html`, where the path leads straight to a file.
- **REST-style mapping**: the path represents logical API components rather than physical files, e.g. `http://example.com/path/resource/param1/param2`, where `param1`/`param2` are parameters, not file paths.

A web cache deception vulnerability can arise when the cache and origin server interpret the same URL differently. For example, with `http://example.com/user/123/profile/wcd.css`:

- The origin server (using REST-style mapping) may treat this as a request to `/user/123/profile`, returning user 123's profile data and ignoring `wcd.css`.
- The cache (using traditional mapping) may instead read this as a request for a file `wcd.css` inside `/user/123/profile/`. If it's set to cache anything ending in `.css`, it will cache the profile data as though it were a static stylesheet.

---

### Exploiting path mapping discrepancies

To test the origin server's mapping, append an arbitrary path segment to a target endpoint's URL. If the response still returns the same sensitive data, the server is likely abstracting the path and ignoring the extra segment—e.g., `/api/orders/123` → `/api/orders/123/foo` still returns order info.

To test the cache's mapping, add a static file extension to try matching a cache rule—e.g., `/api/orders/123/foo` → `/api/orders/123/foo.js`. If this response gets cached, it means:

- The cache reads the entire path, extension included.
- A rule exists to cache requests ending in `.js`.

Since caching rules often target specific extensions, test several (`.css`, `.ico`, `.exe`, etc.).

Once you confirm this, you can build a URL that causes a dynamic, sensitive response to be cached. Note that this only works for the tested endpoint, as the origin server's abstraction behavior often varies across endpoints.

> `Burp Scanner` automatically detects web cache deception vulnerabilities that are caused by path mapping discrepancies during audits. You can also use the `Web Cache Deception Scanner` BApp to detect misconfigured web caches.

---

## 4.2 - Delimiter discrepancies

**Delimiter discrepancies**

Delimiters mark boundaries between URL elements (e.g., `?` separates the path from the query string). While largely standardized, the permissive nature of the URI RFC means frameworks can still handle delimiters inconsistently—creating potential web cache deception vulnerabilities.

**Example: `;` character**
- Java Spring uses `;` to denote matrix variables. So `/profile;foo.css` gets truncated to `/profile` by a Spring origin server, returning profile data.
- Most other frameworks don't treat `;` this way, so a cache built on one of these may read the whole string, including `;foo.css`, as the path. If it caches responses ending in `.css`, it could store the profile data as a static file.

**Example: `.` character (Ruby on Rails)**
Rails uses `.` to indicate response format:
- `/profile` → returns HTML profile data via the default formatter.
- `/profile.css` → recognized as CSS, but no CSS formatter exists, so it errors out.
- `/profile.ico` → `.ico` isn't recognized, so Rails falls back to the default HTML formatter and returns profile data. If the cache stores responses ending in `.ico`, it could cache this as a static file.

**Encoded delimiters**
Encoded characters can also cause discrepancies. For `/profile%00foo.js`:
- OpenLiteSpeed treats `%00` as a delimiter, truncating the path to `/profile`.
- Most other frameworks error out on `%00`, but caches like Akamai or Fastly may instead treat `%00foo.js` as part of the path—leading to the same caching issue if a matching rule exists.

---

### Exploiting delimiter discrepancies

You can exploit a delimiter discrepancy to append a static extension that the cache sees but the origin server doesn't—by finding a character the origin server treats as a delimiter but the cache doesn't.

**Step 1: Find origin server delimiters**
Add an arbitrary string to your target endpoint, e.g. `/settings/users/list` → `/settings/users/listaaa`, and use the response as a baseline. (If it's identical to the original, the request is likely being redirected—pick a different endpoint.)

Then insert a possible delimiter between the path and the string, e.g. `/settings/users/list;aaa`:
- Response matches the base response → `;` is being used as a delimiter (server sees `/settings/users/list`).
- Response matches the `listaaa` version → `;` is not a delimiter (server sees the full string as the path).

**Step 2: Check if the cache also treats it as a delimiter**
Add a static extension after the injected string. If the response gets cached, it means the cache reads the whole path—delimiter included—and has a rule for that extension (e.g., `.js`). Test broadly: all ASCII characters and various extensions (`.css`, `.ico`, `.exe`, etc.). Burp Intruder speeds this up—just disable automatic payload encoding so delimiter characters aren't altered. A starter delimiter list is available in the [Web cache deception lab delimiter list](https://portswigger.net/web-security/web-cache-deception/wcd-lab-delimiter-list).

**Step 3: Build the exploit**
With a confirmed discrepancy, craft a payload like `/settings/users/list;aaa.js`, where `;` is an origin-server delimiter:
- Cache sees: `/settings/users/list;aaa.js`
- Origin server sees: `/settings/users/list`

The origin server returns dynamic data, which the cache then stores under the manipulated path. Since delimiter behavior is usually consistent server-wide, this technique often transfers across multiple endpoints.

**Note:** Some delimiters (like `{`, `}`, `<`, `>`, or `#`) get processed or stripped by the victim's browser before the request even reaches the cache, making them unusable directly—unless an encoded version survives and is later decoded by the cache or origin server.

---

## 4.3 - Delimiter decoding discrepancies

Special URL characters are usually encoded to preserve them as literal data. But some parsers decode certain characters before processing, which can turn them back into active delimiters—truncating the path.

Even when the cache and origin server agree on which characters act as delimiters, differences in *when or whether* they decode those characters can create discrepancies. Example: `/profile%23wcd.css` (URL-encoded `#`):

- The origin server decodes `%23` to `#` and treats it as a delimiter, so it interprets the path as `/profile` and returns profile data.
- The cache also treats `#` as a delimiter, but doesn't decode `%23`—so it sees the literal path `/profile%23wcd.css`. If a `.css` cache rule exists, it stores the response.

Another variation: some caches apply their rules to the *encoded* URL, then decode it before forwarding to the origin. Example: `/myaccount%3fwcd.css`:

- The cache evaluates the encoded path `/myaccount%3fwcd.css`, matches a `.css` rule, and caches it. It then decodes `%3f` to `?` and forwards `/myaccount?wcd.css` to the origin.
- The origin server treats `?` as a delimiter, interpreting the path as just `/myaccount`.

---

### Exploiting delimiter decoding discrepancies

Using an encoded delimiter, you may be able to append a static extension that only the cache—not the origin server—recognizes as part of the path.

Follow the same testing approach used for regular delimiter discrepancies, but this time test with encoded characters. Be sure to include encoded non-printable characters, especially `%00`, `%0A`, and `%09`, since decoding these can also truncate the URL path.

# 5. Exploiting static directory cache rules

It's common practice for web servers to store static resources in specific directories. Cache rules often target these directories by matching specific URL path prefixes, like `/static`, `/assets`, `/scripts`, or `/images`. These rules can also be vulnerable to web cache deception.

---

## 5.1 - Normalization discrepancies

Normalization converts different URL path representations into a standard format—potentially including decoding characters and resolving dot-segments (`..`)—but implementations vary widely between parsers.

If the cache and origin server normalize URLs differently, an attacker can craft a path traversal payload that each interprets differently. Example: `/static/..%2fprofile`:

- An origin server that decodes slashes and resolves dot-segments normalizes this to `/profile`, returning profile data.
- A cache that doesn't perform this resolution instead sees `/static/..%2fprofile` literally. If it caches anything under the `/static` prefix, it stores the profile response.

Note that each dot-segment must be encoded—otherwise the victim's browser resolves it before the request even reaches the cache. So exploiting this requires that either the cache or origin server both decodes the encoded characters *and* resolves dot-segments.

---

## 5.2 - Detect and Exploit normalization by the origin server

### Detect

To check how the origin server normalizes paths, send a request with a path traversal sequence and a leading arbitrary directory to a non-cacheable resource (e.g., one using a non-idempotent method like `POST`). For example, modify `/profile` to `/aaa/..%2fprofile`:

- If the response matches the base `/profile` response, the server decoded the slash and resolved the dot-segment, treating the path as `/profile`.
- If it doesn't match (e.g., a `404`), the server didn't fully normalize it and instead read the literal path `/aaa/..%2fprofile`.

**Note:** Start by encoding only the second slash in the sequence, since some CDNs specifically match the slash right after the static directory prefix. You can also try encoding the entire traversal sequence, or encoding a dot instead of a slash—this can affect whether the parser decodes it.

---

### Exploit

If the origin server resolves encoded dot-segments but the cache doesn't, you can exploit this using the structure:

```
/<static-directory-prefix>/..%2f<dynamic-path>
```

For example, `/assets/..%2fprofile`:

- Cache interprets it as: `/assets/..%2fprofile`
- Origin server interprets it as: `/profile`

The origin server returns the dynamic profile data, which the cache then stores under the static-looking path.

---

## 5.3 - Detect and Exploit normalization by the cache server

### Detect

There are a few ways to test how the cache normalizes paths. Start by finding likely static directories: in **Proxy > HTTP history**, filter for `2xx` responses with script, image, or CSS MIME types, and look for cached responses under common static path prefixes.

**Test 1: Traversal before the prefix**
Take a request with a confirmed cached response and add a traversal sequence plus an arbitrary directory before it, e.g. `/aaa/..%2fassets/js/stockCheck.js`:
- No longer cached → the cache isn't normalizing the path; caching is based on the `/assets` prefix.
- Still cached → the cache may have normalized the path to `/assets/js/stockCheck.js`.

**Test 2: Traversal after the prefix**
Modify `/assets/js/stockCheck.js` to `/assets/..%2fjs/stockCheck.js`:
- No longer cached → the cache decoded the slash and resolved the dot-segment, reading the path as `/js/stockCheck.js`; caching is based on `/assets`.
- Still cached → the cache likely left the slash/dot-segment unresolved, reading the literal path.

**Confirming the rule is prefix-based**
In either test, caching could be due to a different rule (e.g., file extension) rather than the directory prefix. Confirm by replacing the path after the prefix with an arbitrary string, e.g. `/assets/aaa`. If it's still cached, the `/assets` prefix rule is confirmed. Note: an uncached response doesn't necessarily rule out the prefix rule, since `404`s are sometimes excluded from caching.

**Note:** In some cases you won't be able to conclusively confirm whether the cache decodes and normalizes dot-segments without actually attempting an exploit.

---

### Exploit

If the cache resolves encoded dot-segments but the origin server doesn't, try a payload of the form:

```
/<dynamic-path>%2f%2e%2e%2f<static-directory-prefix>
```

**Note:** Encode every character in the traversal sequence—this avoids unexpected delimiter behavior, and there's no need for an unencoded slash after the prefix, since the cache will decode it itself.

However, path traversal alone usually isn't enough here. For `/profile%2f%2e%2e%2fstatic`:

- Cache interprets it as: `/static`
- Origin server interprets it as: `/profile%2f%2e%2e%2fstatic` (literally)—likely producing an error rather than profile data.

To make this work, you also need a delimiter that the origin server recognizes but the cache doesn't. Add it after the dynamic path and test:
- If the origin server uses the delimiter, it truncates the path and returns the dynamic data.
- If the cache doesn't recognize it, it still resolves and caches the full traversal path.

Example: `/profile;%2f%2e%2e%2fstatic`, where the origin server treats `;` as a delimiter:

- Cache interprets it as: `/static`
- Origin server interprets it as: `/profile`

The origin server returns the dynamic profile data, which the cache stores—making this a viable exploit payload.

# 6. Exploiting file name cache rules

Common files like `robots.txt`, `index.html`, and `favicon.ico` change infrequently, so caches often have rules that target them by exact file name.

To check for such a rule, send a `GET` request for the file and see whether the response comes back cached.

---

## 6.1 - Detecting normalization discrepancies

To test how the origin server normalizes the URL path, use the same method that you used for static directory cache rules -> [here](#52---Detect-and-Exploit-normalization-by-the-origin-server).

To test how the cache normalizes the URL path, send a request with a path traversal sequence and an arbitrary directory before the file name. For example, `/profile%2f%2e%2e%2findex.html`:
- If the response is cached, this indicates that the cache normalizes the path to `/index.html`.
- If the response isn't cached, this indicates that the cache doesn't decode the slash and resolve the dot-segment, interpreting the path as `/profile%2f%2e%2e%2findex.html`.

---

## 6.2 - Exploiting normalization discrepancies

Because the response is only cached if the request matches the exact file name, you can only exploit a discrepancy where the cache server resolves encoded dot-segments, but the origin server doesn't. 

Use the same method as for static directory cache rules - simply replace the static directory prefix with the file name, [here](#53--Detect-and-Exploit-normalization-by-the-cache-server).
