# The Core Idea

A cache decides whether to store a response mainly by looking at the **request path** (and sometimes extension), not the actual content that comes back. WCD abuses that mismatch: you get a cache to store a **dynamic, sensitive, user-specific page** (like `/my-account`) under a URL that the cache *thinks* is a static file — then anyone who requests that same crafted URL gets served the victim's cached private data.

## Typical Attack Flow

1. **Find a sensitive dynamic page** that reflects user-specific data (e.g., `/my-account` showing API keys, session tokens, personal info).

2. **Craft a URL that looks static to the cache but still routes to the dynamic page on the backend.** Common tricks PortSwigger covers:
   - **Path mapping / extension confusion**: `/my-account/nonexistent.css` — some backend frameworks ignore the trailing junk and still serve the account page, but the cache sees `.css` and happily caches it as a static asset.
   - **Path parameter injection**: `/my-account;foo.css` or `/my-account/..%2fstatic.css` — using path syntax quirks so the origin still resolves to `/my-account` while the cache's path-matching logic treats it as a static resource.
   - **Delimiter confusion**: exploiting differences in how the cache vs. the origin server parse `?`, `#`, `;`, or encoded characters in the URL.

3. **Trick the victim into visiting that crafted URL** while they're logged in (via a link, XSS, phishing, etc.). Their authenticated session generates the sensitive response.

4. **The cache stores that response**, keyed to the crafted path, thinking it's a harmless static file.

5. **Attacker requests the exact same crafted URL** — no authentication needed — and gets served the victim's cached sensitive page straight from the cache.

# Web cache

A web cache is a system that `sits between` the origin `server` and the `user`. 

<img width="909" height="455" alt="image" src="https://github.com/user-attachments/assets/795ccee1-586c-4f91-82c2-c8b4b9051ddd" />

1. When a client requests a `static resource`, the request is first directed to the `cache`.
2. If the `cache` doesn't contain a copy of the `resource` (known as a `cache miss`), the request is forwarded to the origin `server`, which processes and responds to the request.
3. The response is then sent to the `cache` before being sent to the `user`. The `cache` uses a preconfigured set of rules to determine whether to store the response.
4. When a request for the same `static resource` is made in the future, the `cache serves` the stored copy of the response directly to the user (known as a `cache hit`).


### 1. Why Web Caches Exist

Caching has become a common and crucial aspect of delivering web content, particularly with the widespread use of `Content Delivery Networks` (`CDNs`), which use caching to store copies of content on distributed servers all over the world. 

CDNs speed up delivery by serving content from the server closest to the user, reducing load times by minimizing the distance data travels.

Overall, the benefits of web cache include: 
- **Speed**: serve stored responses instead of regenerating them
- **Reduced origin load**: fewer requests hit the backend/database
- **Cost savings**: less compute/bandwidth needed
- **Scalability**: absorbs traffic spikes
- **Resilience**: can serve stale content if origin goes down

Caches make these decisions using **fast, shallow signals** (URL path, file extension) rather than deeply inspecting actual content — this shallow logic is the root cause of most cache-related vulnerabilities.

### 2. Who Controls the Cache
- **Third-party CDNs**: Cloudflare, Akamai, Fastly, CloudFront (most common)
- **Self-hosted reverse proxies**: Varnish, Nginx, Squid — site owner runs it themselves
- **Built into app/server stack** or load balancers
- Caching and load balancing are **different mechanisms** often bundled together but not the same thing

### 3. Who's Responsible for WCD
- Root cause: a **mismatch** between how the cache decides "is this cacheable" vs. how the backend actually routes the URL
- Can stem from: naive cache defaults, lenient backend path-parsing, or the *interaction* between the two
- **Responsibility generally falls on the web app owner/developer** — they must explicitly set `Cache-Control: no-store` (or similar) on sensitive dynamic pages, regardless of cache provider defaults

### 4. Who Uses Caching Most (WCD-relevant targets)
Sites that mix **static public content + dynamic authenticated content** on the same domain:
- E-commerce, news/media, SaaS platforms, social platforms, banking/fintech
- Any site behind widely-adopted CDNs (e.g., Cloudflare free tier)

## Cache keys

1. When a cache receives an HTTP request, it must decide whether to `serve a cached response` or `forward the request to the origin server`.
2. It makes this decision using a "cache key," generated from parts of the request—typically the `URL path` and `query parameters`, but sometimes also `headers`, `content type`, or other elements.
3. If a new request's cache key matches a previous one, the cache treats them as equivalent and serves the cached response.

---

## Cache rules

Cache rules define what gets cached and for how long. They typically target static resources (unchanging, reused across pages), while dynamic content is excluded since it may contain sensitive, user-specific data.

Web cache deception attacks exploit how these rules are applied, especially rules based on URL path strings:

* **Static file extension rules** – match file extensions like `.css` or `.js`.
* **Static directory rules** – match paths starting with a prefix like `/static` or `/assets`.
* **File name rules** – match specific common files like `robots.txt` or `favicon.ico`.

Caches may also use custom rules based on criteria like URL parameters or dynamic analysis.
