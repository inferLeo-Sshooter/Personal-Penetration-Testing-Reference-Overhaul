# 1. WCP basic

## 1.1 - The basic idea

Picture a cache as a photocopier sitting in front of a real employee (the server). To save time, the copier keeps copies of common answers on hand and hands those out instead of bothering the employee every time someone asks the same question.

**Web cache poisoning** is when an attacker tricks the employee into writing something malicious on a piece of paper — and then tricks the copier into saving *that* bad copy and handing it out to everyone who asks afterward.

It happens in two steps.

---

## Step 1 — Trick the server into producing a bad response

The attacker looks for some part of the request that the **server** reacts to, but that the **cache** ignores when deciding "have I seen this exact request before?" This ignored piece is called an **unkeyed input** — usually a header.

```http
GET /home HTTP/1.1
Host: example.com
X-Forwarded-Host: evil.com
```

If the server carelessly uses `X-Forwarded-Host` to build something on the page — like a link or a script tag — the response might now quietly contain:

```html
<script src="https://evil.com/script.js"></script>
```

The cache never looked at that header, so as far as it's concerned, nothing suspicious happened.

---

## Step 2 — Get that bad response cached

Since the cache only checks the parts of the request it actually cares about (usually the URL path and `Host` header), it sees a perfectly normal request for `/home` and stores the poisoned response as if it were the real one.

From that point on, **every future visitor** to `/home` — with no special header, no interaction with the attacker at all — gets served the malicious version straight from the cache.

---

## Why this is so dangerous

The attacker doesn't need to attack every visitor one by one. They poison the cache **once**, and the cache does the work of spreading the attack for them.

Depending on what gets injected, this can lead to:

- **XSS** — malicious JavaScript runs in every visitor's browser
- **Open redirect** — visitors get silently sent to a phishing site
- **JavaScript injection** — attacker-controlled scripts load on a page users trust

If the poisoned page is something high-traffic, like a homepage, this single crafted request could end up affecting thousands of users before anyone notices.

---

## How does a web cache actually work?

Back to the photocopier idea: if every single person who wanted a document had to wait for the employee to write it out by hand, the office would grind to a halt during busy hours. So instead, the copier keeps a stack of pre-made copies. When someone asks for something the copier already has on hand, it just hands over a copy — no need to bother the employee at all.

That's exactly what a cache does. It sits between the visitor and the real server, and:

1. Saves a response the server generated once
2. Hands that saved response to the next person who makes the "same" request
3. Never bothers the server again for that request until the saved copy expires

This means fewer duplicate requests reach the server, which keeps things fast and stops the server from getting overwhelmed.

## What counts as "the same request"? — Cache keys

The cache can't compare every single detail of two requests — that would defeat the purpose of being fast. Instead, it only looks at a chosen handful of parts, called the **cache key**. Usually this is just the request line (the path) and the `Host` header.

```http
GET /home HTTP/1.1
Host: example.com
```

If two requests have a matching cache key, the cache treats them as identical and serves the same saved response to both — even if the rest of the request is completely different.

Anything the cache key doesn't look at is called **unkeyed**. This matters a lot for poisoning attacks: the cache will ignore an unkeyed header entirely when deciding what to serve, even though the server behind it might still read that header and change its response because of it.

```http
GET /home HTTP/1.1
Host: example.com
X-Forwarded-Host: evil.com    <-- cache doesn't check this
```

The cache sees a normal request for `/home` and serves whatever it has stored — but if the server used `X-Forwarded-Host` to build the page, the *stored* response could already contain the attacker's payload.

## How bad can it get?

Two things decide how damaging a poisoning attack ends up being:

**1. How dangerous the injected payload is**
Poisoning a cache isn't an attack on its own — it's a delivery method. The real damage comes from whatever gets planted in the response (script tags, redirects, etc.), and it can even be chained with other attack types to make things worse.

**2. How much traffic the poisoned page gets**
Only people who visit the page *while it's poisoned* are affected. Poison an obscure page nobody visits, and the impact is basically zero. Poison a busy homepage, and thousands of visitors could be hit without the attacker lifting another finger.

One extra wrinkle: it doesn't matter much how long a single cached copy lasts, because an attacker can usually automate the attack to keep re-poisoning the cache over and over, indefinitely.

---

## Building a poisoning attack, step by step

There are three moving parts to pull this off:

```
1. Find an unkeyed input the server actually reacts to
2. Get the server to produce a harmful response using that input
3. Get that harmful response stored in the cache
```

### Step 1: Find inputs the cache ignores but the server doesn't

The hunt here is for **unkeyed inputs** — usually headers — that the server pays attention to even though the cache doesn't. You can find these by hand: throw random headers or values at a request and watch whether the response changes. Sometimes the effect is obvious (your input shows up directly in the page); other times it's subtle enough that you need a diffing tool to catch it.

Doing this manually for every possible header is slow, so testers usually reach for the **Param Miner** Burp extension instead. Right-click a request, choose "Guess headers," and Param Miner floods the server with a huge built-in list of header names to see which ones change the response — then logs anything interesting for you to review.

> ⚠️ **Careful when testing on a live site:** poisoning a real cache while you're just testing can accidentally serve your test payloads to real visitors. Always attach a unique "cache buster" (like a random query parameter) to your test requests so only you see the responses — Param Miner can automate this too.

### Step 2: Turn that input into a harmful response

Once you've found an input the server reacts to, figure out exactly *how* it reacts. If the server:

- reflects your input straight back into the page without sanitizing it, or
- uses it to build other dynamic content (like a link or script source),

...you likely have a way to sneak in something malicious, such as:

```html
<script src="https://evil.com/payload.js"></script>
```

### Step 3: Get that harmful version cached

Finding the injection point is only half the job — it's useless unless that specific poisoned response actually gets saved. Whether a response gets cached can depend on things like:

- the file extension
- the content type
- the URL/route
- the status code
- other response headers

This usually takes some trial and error across different pages to figure out what the cache will and won't store. Once you can reliably get your poisoned response cached, the attack is ready to fire at real visitors.

---

## How to defend against web cache poisoning

**The strongest fix: don't cache what you don't have to.** If caching was just switched on by default when you adopted a CDN, it's worth checking whether you actually need it, or at least scaling it back.

**If you must cache, cache only truly static content** — and be strict about what "static" really means. Make sure an attacker can't fool the server into serving a tampered version of a resource in place of the real one.

**Know your third-party tools.** Every CDN, proxy, or caching layer you adopt comes with its own default behaviors — including which headers it silently supports. A lot of poisoning vulnerabilities exist purely because a site enabled some third-party tech without realizing it accepted obscure, unnecessary headers by default. If a header isn't needed for your site to function, turn support for it off.

A few concrete precautions:

- **Don't exclude things from the cache key for speed and call it done** — if you need to ignore part of a request for performance, rewrite the request instead of just leaving that part unkeyed.
- **Reject "fat" `GET` requests** (GET requests with a body) — some tech stacks allow these by default, and they can open extra doors for injecting unkeyed data.
- **Fix client-side bugs even if they look unexploitable on their own.** A supposedly harmless client-side flaw can suddenly become exploitable once combined with a quirky cache behavior. It's often just a matter of time before someone finds the right combination.
