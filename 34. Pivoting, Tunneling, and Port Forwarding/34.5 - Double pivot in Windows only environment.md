## 1. Introduction

Every pivoting tool covered in the previous notes — Plink, Sshuttle, Chisel, ptunnel-ng — assumes SSH is at least available somewhere in the chain. Sometimes it isn't. In an all-Windows environment with no SSH server anywhere in reach, a different kind of tunnel is needed — one built entirely out of ordinary RDP sessions. This is exactly what [SocksOverRDP](https://github.com/nccgroup/SocksOverRDP) provides.

**Machine labels used throughout this section** (this scenario has one extra hop compared to earlier notes, since RDP itself becomes the tunnel):

| Label | Role |
|---|---|
| **HACKER** | Your own attack machine, on the outside network (`10.129.x.x`) |
| **FOOTHOLD** | A Windows machine you already have RDP access to, also on the `10.129.x.x` network — this is where the SocksOverRDP *client* plugin and Proxifier run |
| **PIVOT** | A Windows machine at `172.16.5.19`, reachable from FOOTHOLD over RDP — this is where the SocksOverRDP *server* component runs |
| **TARGET** | A further machine at `172.16.6.155`, reachable only from PIVOT — the ultimate destination of this whole chain |

## 2. What Is SocksOverRDP, and Why Use It?

**SocksOverRDP** is a Windows-specific tool that repurposes a legitimate RDP feature called **Dynamic Virtual Channels (DVC)**. DVC is part of Windows' Remote Desktop Service, and its normal job is to tunnel small amounts of auxiliary data over an existing RDP connection — for example, clipboard sharing (copy-pasting text between your machine and the remote session) or audio redirection (hearing sound from the remote session on your own speakers).

**The key insight SocksOverRDP exploits:** DVC doesn't actually care *what* data it's carrying — it's a generic channel within the RDP protocol. SocksOverRDP uses that same channel to tunnel arbitrary network packets instead of just clipboard or audio data, effectively turning a completely ordinary-looking RDP session into a SOCKS proxy tunnel. Since RDP is already a protocol that's expected and often permitted inside Windows networks, this blends in far better than trying to introduce SSH or some other obviously "foreign" protocol.

[Proxifier](https://www.proxifier.com/) — the same Windows tool introduced in the Plink notes — is used again here to actually route application traffic (like `mstsc.exe` itself) into the SOCKS proxy that SocksOverRDP exposes.

## 3. Setting Up SocksOverRDP

**Step 1 — On HACKER: download the required binaries.**

Two things are needed:
- [SocksOverRDP x64 binaries](https://github.com/nccgroup/SocksOverRDP/releases) (the plugin and server components)
- [Proxifier Portable](https://www.proxifier.com/download/#win-tab) (specifically the `ProxifierPE.zip` portable build, which needs no installation)

Having both downloaded to HACKER first means they're ready to transfer onward to whichever machine needs them, using any of the earlier file transfer techniques.

**Step 2 — From HACKER: RDP into FOOTHOLD, and copy the SocksOverRDP zip over.**

This uses `xfreerdp` (covered in earlier notes) to establish the RDP session, then a file is copied in — either via clipboard copy-paste or a mounted local drive, both covered in the earlier RDP file transfer notes.

**Step 3 — On FOOTHOLD: register the SocksOverRDP plugin DLL.**
```
C:\Users\Public\SocksOverRDP-x64> regsvr32.exe SocksOverRDP-Plugin.dll
```
- `regsvr32.exe` is Windows' built-in tool for registering DLL components with the operating system — this step makes the SocksOverRDP plugin available for use within RDP sessions started from FOOTHOLD.
> (Note: this is the same `regsvr32.exe` that showed up as a LOLBin-adjacent tool in the "Living off the Land" notes, though here it's being used for its actual intended purpose — registering a legitimate DLL.)

**Step 4 — From FOOTHOLD: connect to PIVOT over RDP using mstsc.exe.**

Connecting to `172.16.5.19` using the credentials `victor:pass@123` should trigger a prompt confirming the SocksOverRDP plugin is active, and that it's now listening locally on `127.0.0.1:1080`.

**Step 5 — Transfer the SocksOverRDP server component onto PIVOT.**

Either the full `SocksOverRDPx64.zip` or just `SocksOverRDP-Server.exe` needs to end up on PIVOT — again, using whichever file transfer method fits (RDP clipboard/drive, SCP, a quick web server, etc.).

**Step 6 — On PIVOT: run the server component with administrator privileges.**

Running `SocksOverRDP-Server.exe` as Admin on PIVOT activates the other half of the tunnel — the plugin on FOOTHOLD and the server on PIVOT now work together to carry SOCKS traffic over the RDP session connecting them.

**Step 7 — Back on FOOTHOLD: confirm the local SOCKS listener actually started.**
```
C:\Users\Public\SocksOverRDP-x64> netstat -antb | findstr 1080

  TCP    127.0.0.1:1080         0.0.0.0:0              LISTENING
```
- `netstat -antb` lists active connections along with the binary responsible for each one.
- `findstr 1080` filters that output down to just the line mentioning port 1080.
- Seeing `LISTENING` here confirms the SocksOverRDP tunnel is genuinely up and ready to carry traffic.

**Network flow (the tunnel itself):**
```
[FOOTHOLD] --- RDP session, DVC-tunneled SOCKS (via SocksOverRDP) ---> [PIVOT]
[FOOTHOLD] <----------- relayed SOCKS traffic via 127.0.0.1:1080 ----- [PIVOT]
```

## 4. Putting the Full Chain Together

With the tunnel itself established between FOOTHOLD and PIVOT, the next step is making actual applications route their traffic through it.

**Step 1 — Transfer Proxifier Portable onto FOOTHOLD.**

**Step 2 — On FOOTHOLD: configure Proxifier to forward traffic to the SocksOverRDP listener.**

Proxifier is set up to route all traffic through `127.0.0.1:1080` — the exact local port SocksOverRDP's plugin is listening on (confirmed in Step 7 of the previous section). From this point, any application launched under Proxifier's control has its network traffic transparently redirected into that SOCKS tunnel.

**Step 3 — On FOOTHOLD: start `mstsc.exe` through Proxifier, and connect further inward.**

Because Proxifier is now intercepting its traffic, `mstsc.exe`'s connection gets pivoted through `127.0.0.1:1080` → tunneled over the existing RDP session to PIVOT (`172.16.5.19`) → and from there, PIVOT's `SocksOverRDP-Server.exe` routes the traffic onward to TARGET (`172.16.6.155`).

**Full network flow, end to end:**
```
[HACKER] --- initial RDP ---> [FOOTHOLD] --- RDP + DVC/SOCKS (SocksOverRDP) ---> [PIVOT] --- routed via SocksOverRDP-Server.exe ---> [TARGET]
[HACKER] <-------------------- [FOOTHOLD] <---------------------------------------- [PIVOT] <------------------------------------- [TARGET]
```
*Every hop in this chain uses nothing but RDP sessions and Windows-native tooling — no SSH, no Linux pivot host, and no non-RDP protocol anywhere in the path. This is precisely the all-Windows scenario SocksOverRDP exists to solve.*

## 5. RDP Performance Considerations

Running multiple nested or simultaneous RDP sessions — as this chain inherently requires — can noticeably degrade performance, especially over higher-latency connections. One practical fix: inside `mstsc.exe`, open the **Experience** tab and set the performance profile to **Modem**.

*Counterintuitively, choosing a *lower*-bandwidth profile like "Modem" actually helps here — it tells the RDP client to disable bandwidth-heavy visual features (like desktop wallpaper, visual effects, and window animations) that aren't worth their cost when the connection is already being relayed through multiple tunneled hops. The result is a session that feels more responsive, even though the underlying network path hasn't changed at all.*

## 8. Big-Picture Takeaways

1. **SocksOverRDP exists specifically for all-Windows environments.** Every other pivoting tool covered in earlier notes leans on SSH somewhere — SocksOverRDP is the answer when SSH simply isn't an option anywhere in the chain, relying entirely on RDP and Windows-native tooling instead.
2. **A legitimate protocol feature doesn't have to be used for its intended purpose.** Dynamic Virtual Channels exist for clipboard sharing and audio redirection — SocksOverRDP repurposes that same generic data channel to carry arbitrary SOCKS traffic instead, echoing the same "legitimate feature, creative reuse" theme from the Living off the Land notes.
3. **This technique requires a client-and-server pairing, just like Chisel or ptunnel-ng.** The plugin DLL (registered on the "near" side, FOOTHOLD) and the server executable (run on the "far" side, PIVOT) both have to be in place and running for the tunnel to work — neither half alone is sufficient.
4. **Proxifier is the piece that actually makes the tunnel useful.** SocksOverRDP on its own just creates a SOCKS proxy on `127.0.0.1:1080` — Proxifier is what takes a normal application like `mstsc.exe` and transparently redirects its traffic into that proxy, exactly as it did for Plink's SOCKS tunnel in the earlier notes.
5. **Chained pivoting can extend arbitrarily far, hop by hop.** This example goes HACKER → FOOTHOLD → PIVOT → TARGET, with the RDP-based SocksOverRDP tunnel forming just one link in that chain — the same fundamental principle (each hop only needs to reach the next one) scales to even longer chains if needed.
6. **Performance tuning matters in multi-hop tunneling, not just raw connectivity.** Getting the tunnel working is only half the job — across several nested or relayed RDP sessions, a seemingly unrelated setting like the Experience tab's performance profile can make the difference between a usable and an unusably sluggish session.
