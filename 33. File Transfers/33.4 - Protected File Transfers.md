## 1. Introduction

Every file transfer technique covered so far — PowerShell, Bash, Netcat, FTP, mini web servers, and so on — has one thing in common: by default, none of them protect the *contents* of what's being sent. If someone is watching the network traffic (a defender with a packet capture tool, or another attacker on the same network), they can potentially read a plaintext file as it travels across the wire.

This section is about a different concern than *how* to move a file — it's about making sure that even if the transfer itself is somehow observed or intercepted, the contents remain unreadable. Think of it like the difference between sending a postcard (anyone who handles it along the way can read it) versus sending a sealed, locked box (even if someone intercepts the box, they can't see what's inside without the key).

**Machine labels used in this section:**

| Label | Role |
|---|---|
| **FOOT_HOLD** | The machine you have a shell on, holding the sensitive file |
| **HACKER** (a.k.a. Pwnbox) | Your own attack machine, where the file is ultimately headed |

## 2. Handling Sensitive Data Responsibly

Penetration testers routinely encounter extremely sensitive material during an assessment — things like user account lists, credentials (for example, pulling a copy of the **NTDS.dit** file, which stores Active Directory's user account and password hash data, for offline password cracking), and enumeration output that can reveal deep details about an organization's network layout and Active Directory environment.

Because of this, it's essential to either use an already-encrypted connection (SSH, SFTP, or HTTPS) or to encrypt the data yourself before sending it any other way. But those encrypted channels aren't always available in a given environment — which is exactly when manual file encryption becomes necessary.

> **Professional and ethical guardrail:** unless a client has specifically asked for it, actual sensitive data — personally identifiable information (PII), financial details like credit card numbers, trade secrets, and so on — should never be exfiltrated from a real client environment. If the goal is specifically to test Data Loss Prevention (DLP) controls or egress filtering, the right approach is to create a **dummy file** that mimics the structure or pattern of the sensitive data the client is trying to protect, rather than using real data.

Beyond the ethical dimension, there's a practical risk too: **data leakage during a penetration test can have serious consequences** — for the tester personally, for their employer, and for the client whose environment was being assessed. Acting professionally and taking every reasonable precaution to protect any data encountered during an assessment isn't optional — it's a core part of the job.

## 3. File Encryption on Windows

A simple, lightweight way to encrypt files on Windows is the [Invoke-AESEncryption.ps1](https://www.powershellgallery.com/packages/DRTools/4.0.2.3/Content/Functions%5CInvoke-AESEncryption.ps1) PowerShell script. It's small and handles encrypting both files and plain text strings, using **AES** (Advanced Encryption Standard, a widely trusted symmetric encryption algorithm — meaning the same password/key is used to both encrypt and later decrypt).

**Step 1 — On FOOT_HOLD: get the script onto the machine.**
Any of the file transfer techniques already covered (PowerShell web downloads, SMB, FTP, base64 copy-paste, and so on) can be used to move `Invoke-AESEncryption.ps1` onto the target — encryption is a separate concern from the transfer method itself.

**Step 2 — On FOOT_HOLD: load the script as a PowerShell module.**
```
PS C:\foot_hold> Import-Module .\Invoke-AESEncryption.ps1
```
*`Import-Module` loads the functions defined in the script file into the current PowerShell session, making the `Invoke-AESEncryption` command available to run, similar to how you'd `import` a library in a programming language before using its functions.*

**Step 3 — On FOOT_HOLD: encrypt a file.**
```
PS C:\foot_hold> Invoke-AESEncryption -Mode Encrypt -Key "p4ssw0rd" -Path .\scan-results.txt

File encrypted to C:\foot_hold\scan-results.txt.aes
PS C:\foot_hold> ls

    Directory: C:\foot_hold

Mode                 LastWriteTime         Length Name
----                 -------------         ------ ----
-a----        11/18/2020  12:17 AM           9734 Invoke-AESEncryption.ps1
-a----        11/18/2020  12:19 PM           1724 scan-results.txt
-a----        11/18/2020  12:20 PM           3448 scan-results.txt.aes
```
*`-Mode Encrypt` tells the script to encrypt (rather than decrypt). `-Key "p4ssw0rd"` sets the password used for encryption — this exact same password will be required later to decrypt the file, so it needs to be remembered or securely recorded. `-Path` points to the file to encrypt. The result is a new file with the same name plus a `.aes` extension (`scan-results.txt.aes`), while the original unencrypted file remains in place too — so it's worth deleting or securely handling the original separately if the goal is to avoid leaving a readable copy behind.*

> **Important practice:** use a strong, unique password for every single engagement/client. Reusing the same encryption password across multiple assessments means that if it's ever leaked or cracked once, every file ever encrypted with it — across every client — becomes exposed too.

## 4. File Encryption on Linux

**OpenSSL** is a toolkit that's included on most Linux distributions by default — system administrators commonly use it for generating TLS/SSL certificates, but it also doubles as a capable file encryption tool, usable in a similar "pipe-style" manner to how Netcat was used earlier for raw file transfers.

OpenSSL supports many different encryption ciphers (the specific encryption algorithm used) — the full list is documented in OpenSSL's own manual page. The example below uses **AES-256** (`-aes256`), a strong, widely trusted symmetric cipher.

**Step 1 — On FOOT_HOLD (or wherever the sensitive file currently sits): encrypt the file.**
```
$ openssl enc -aes256 -iter 100000 -pbkdf2 -in /etc/passwd -out passwd.enc

enter aes-256-cbc encryption password:                                                         
Verifying - enter aes-256-cbc encryption password:
```
*`enc` is OpenSSL's general-purpose encryption/decryption command. `-aes256` selects the AES-256 cipher. `-iter 100000` overrides the default number of "iterations" used when deriving the actual encryption key from your password — more iterations means it takes longer (and is more computationally expensive) for an attacker to brute-force guess the password, at the cost of taking a little longer for you too. `-pbkdf2` specifies using the Password-Based Key Derivation Function 2 algorithm for that key-derivation step, which is considered more secure than OpenSSL's older default method. `-in` and `-out` specify the input (plaintext) and output (encrypted) file paths. After running the command, you're prompted to type a password twice (once to set it, once to confirm it matches).*

**Step 2 — On HACKER (after the encrypted file has been transferred over): decrypt it.**
```
$ openssl enc -d -aes256 -iter 100000 -pbkdf2 -in passwd.enc -out passwd                    

enter aes-256-cbc decryption password:
```
*The `-d` flag switches the command from encrypt to decrypt mode. Every other option (`-aes256`, `-iter 100000`, `-pbkdf2`) must exactly match what was used during encryption, or the decryption will fail — think of these as the "settings" on a lock that both the locking and unlocking key need to agree on. `-in` and `-out` are reversed in purpose compared to Step 1: now `-in` is the encrypted file, and `-out` is where the decrypted result gets saved.*

> **Reminder:** just like with the Windows example, use a strong and unique password here — if an unauthorized party ever gets hold of the encrypted file, a weak or reused password is exactly what makes a brute-force cracking attempt feasible.

**Once a file is encrypted, it still needs to actually be moved** using one of the transfer techniques covered in earlier sections — Netcat, SCP, a web server, and so on all still apply here. That said, it's best practice to still prefer an already-secure transport method (HTTPS, SFTP, or SSH) even for an encrypted file, as a second layer of protection — encryption protects the file's contents, but a secure transport protocol additionally protects metadata like filenames and transfer patterns, and guards against the encrypted file being tampered with in transit.

## 5. Decision Flow: Do I Need to Encrypt This Transfer?

```
                ┌────────────────────────────────┐
                │ About to transfer a sensitive  │
                │ file off a target machine?     │
                └────────────────┬───────────────┘
                                 │
                ┌────────────────┴───────────────┐
                │                                │
    Secure channel available              No secure channel
    (SSH / SFTP / HTTPS)                    available
                │                                │
                ▼                                ▼
     ┌──────────────────────┐        ┌───────────────────────────────────┐
     │ Transfer directly —  │        │ Encrypt the file FIRST:           │
     │ the channel itself   │        │  • Windows → Invoke-AESEncryption │
     │ already protects the │        │  • Linux   → openssl enc -aes256  │
     │ contents in transit  │        │ Then transfer the encrypted       │
     └──────────────────────┘        │ file using any available method   │
                                     └───────────────────────────────────┘
                                                 │
                                                 ▼
                                   ┌───────────────────────────────┐
                                   │ On the receiving end, decrypt │
                                   │ using the matching password   │
                                   │ and the SAME cipher/options   │
                                   └───────────────────────────────┘

        ┌───────────────────────────────────────────────────┐
        │ Regardless of path: is this REAL client data      │

        │   → Only exfiltrate if explicitly authorized by   │
        │     the client. Otherwise, use dummy data that    │
        │     mimics it, especially when testing DLP/egress │
        │     filtering controls.                           │
        └───────────────────────────────────────────────────┘
```

## 6. Cheat Sheet

| Goal | Platform | Run on | Key Command |
|---|---|---|---|
| Load the AES encryption script | Windows | target | `Import-Module .\Invoke-AESEncryption.ps1` |
| Encrypt a file (AES, PowerShell) | Windows | target | `Invoke-AESEncryption -Mode Encrypt -Key "password" -Path .\file.txt` |
| Decrypt a file (AES, PowerShell) | Windows | wherever the .aes file is | `Invoke-AESEncryption -Mode Decrypt -Key "password" -Path .\file.txt.aes` |
| Encrypt a file (AES-256, OpenSSL) | Linux | source machine | `openssl enc -aes256 -iter 100000 -pbkdf2 -in file -out file.enc` |
| Decrypt a file (AES-256, OpenSSL) | Linux | destination machine | `openssl enc -d -aes256 -iter 100000 -pbkdf2 -in file.enc -out file` |

> Note: the Windows decrypt command above follows the same `-Mode`/`-Key`/`-Path` pattern as encryption, just switching `-Mode Encrypt` to `-Mode Decrypt`.

## 7. Big-Picture Takeaways

1. **Encryption and transfer are two separate problems, solved by two separate steps.** None of the file transfer techniques covered earlier (Netcat, FTP, mini web servers, etc.) encrypt data on their own — encrypting first and then transferring the already-encrypted result is what actually protects the contents in transit.
2. **Prefer encrypted channels when they're available, and encrypt manually when they're not.** SSH, SFTP, and HTTPS already provide transport-level encryption; AES-based tools (`Invoke-AESEncryption.ps1` on Windows, `openssl enc` on Linux) exist specifically for situations where none of those channels can be used.
3. **A password is only as strong as its uniqueness.** Reusing one password across every encrypted file, every engagement, or every client turns a single leaked password into a skeleton key for everything ever protected with it.
4. **Encryption settings must match exactly between encrypt and decrypt.** Cipher choice (`-aes256`), iteration count (`-iter 100000`), and key-derivation method (`-pbkdf2`) all have to agree on both ends, or decryption simply won't work.
5. **Encryption doesn't replace good judgment about what data to touch at all.** Even perfectly encrypted, real client PII or financial data shouldn't be exfiltrated without explicit authorization — dummy data that mimics the real thing is the appropriate stand-in when the actual goal is testing a client's DLP or egress-filtering controls.
6. **Professional responsibility is part of the technique, not separate from it.** Protecting sensitive data encountered during an assessment — through encryption, careful handling, and restraint — is as much a core skill for a penetration tester as knowing the commands themselves.
