# 1. JWT fundamentals

`JSON Web Tokens (JWTs)` are a standardized format for transmitting cryptographically signed `JSON` data between systems. A JWT consists of three parts — a `header`, a `payload`, and a `signature` — and can theoretically carry any kind of data, though it's most commonly used to send "`claims`" about users for **authentication, session handling, and access control**.

Unlike classic session tokens, a JWT stores all the data a server needs directly within the token itself (client-side), rather than relying on server-side session storage. This makes JWTs a popular choice for stateless authentication in highly distributed systems, where users need to interact seamlessly across multiple back-end servers.

---

## 1.2 - JWT format

A JWT consists of 3 parts: a `header`, a `payload`, and a `signature`. These are each separated by a dot, as shown in the following example:

<img width="997" height="383" alt="image" src="https://github.com/user-attachments/assets/6b43937c-5aee-4629-9e36-b015025d218e" />

The `header` and `payload` parts of a `JWT` are just `base64url-encoded JSON objects`. The `header` contains metadata about the token itself, while the `payload` contains the actual "claims" about the user. 

> **Note:** If you want to gain a better understanding of how JWTs are constructed, you can use the debugger on `jwt.io` to experiment with arbitrary tokens.

---

### JWT Header

The first part of the JWT is its `header`. It comprises metadata about the token itself, holding information that allows interpreting it. 

For instance, let us look at the header of our example token from before. After `base64-decoding` the first part, we are left with the following JSON object:
```js
{"kid":"9136ddb3-cb0a-4a19-a07e-eadf5a44c8b5","alg":"RS256"}
```

As we can see, the `header` only consists of two parameters in this case. 

The `kid` parameter - stands for **Key ID**. It's a header parameter in a JWT/JWS that identifies which specific cryptographic key was used to sign the token.

The `alg` parameter specifies the cryptographic signature or MAC algorithm the token is secured with. Valid values for this parameter are defined in the JWA standard:

|"alg" Parameter Value|Signature/MAC Algorithm|
|-|-|
|HS256|HMAC using SHA-256|
|HS384|HMAC using SHA-384|
|HS512|HMAC using SHA-512|
|RS256|RSASSA-PKCS1-v1_5 using SHA-256|
|RS384|RSASSA-PKCS1-v1_5 using SHA-384|
|RS512|RSASSA-PKCS1-v1_5 using SHA-512|
|ES256|ECDSA using P-256 and SHA-256|
|ES384|ECDSA using P-384 and SHA-384|
|ES512|ECDSA using P-512 and SHA-512|
|PS256|RSASSA-PSS using SHA-256 and MGF1 with SHA-256|
|PS384|RSASSA-PSS using SHA-384 and MGF1 with SHA-384|
|PS512|RSASSA-PSS using SHA-512 and MGF1 with SHA-512|
|none|No digital signature or MAC performe|

Our example token is secured with RSASSA-PKCS1-v1_5 using SHA-256 in this case. There are additional parameters that can be defined in the JWT header.

---

### JWT Payload

The `JWT payload` is the middle part and contains the actual data making up the token. This data comprises multipleclaims. Base64-decoding the sample JWT's payload reveals the following JSON data:
```
{
    "iss": "portswigger",
    "exp": 1648037164,
    "name": "Carlos Montoya",
    "sub": "carlos",
    "role": "blog_author",
    "email": "carlos@carlos-montoya.net",
    "iat": 1516239022
}
```

In most cases, this data can be easily read or modified by anyone with access to the token. Therefore, `the security of any JWT-based mechanism is heavily reliant on the cryptographic signature`.

---

### JWT signature

The final part of a JWT is its **signature**, which protects the integrity of the token. The issuing server generates it by hashing the header and payload together (and in some implementations, encrypting that hash) using a secret signing key and the algorithm specified in the header.

This mechanism gives the server two guarantees:

- **Tamper detection** — since the signature is derived directly from the header and payload, changing even a single byte of either results in a mismatched signature.
- **Authenticity** — without knowledge of the secret signing key, it isn't possible to compute a valid signature for a given header and payload.

Together, these properties mean any manipulation of the token's data will be detected, as the signature will no longer match.

---

### JWT vs JWS vs JWE

The JWT specification itself is minimal — it only defines a format for representing claims as a JSON object. In practice, JWTs aren't used standalone; the spec is extended by **JSON Web Signature (JWS)** and **JSON Web Encryption (JWE)**, which define how the token is actually constructed.

In other words, a JWT is typically implemented as either a JWS or a JWE token. When people say "JWT," they almost always mean a JWS token, where the contents are signed but still readable. A `JWE` token works similarly, except the contents are encrypted rather than just encoded.

---

## 1.3 - JWT attacks

JWT attacks involve a user sending modified JWTs to the server in order to achieve a malicious goal. Typically, this goal is to bypass authentication and access controls by impersonating another user who has already been authenticated.

**Impact:** The impact of JWT attacks is usually severe. If an attacker is able to create their own valid tokens with arbitrary values, they may be able to escalate their own privileges or impersonate other users, taking full control of their accounts.

**How it arise:**

JWT vulnerabilities typically stem from flawed handling within the application itself. The [related specifications](https://portswigger.net/web-security/jwt#jwt-vs-jws-vs-jwe) are flexible by design, leaving many implementation details up to developers — which can introduce vulnerabilities even when using battle-hardened libraries.

Most commonly, this means `the signature isn't verified properly, letting an attacker tamper with the token's payload`. But even with robust verification, security still hinges on the server's secret key staying secret. If it's leaked, guessed, or brute-forced, an attacker can forge valid signatures for any token, compromising the entire mechanism.

# 2. Exploiting flawed JWT signature verification

Servers typically don't store information about issued JWTs—each token is self-contained. This means the server has no record of a token's original contents or signature. So if signature verification isn't done properly, an attacker can freely modify the token's contents.

For example, consider a JWT with these claims:
```
{
  "username": "carlos",
  "isAdmin": false
}
```

If the server uses `username` to identify sessions, an attacker could change it to impersonate other users. Likewise, if `isAdmin` controls access, altering it could allow privilege escalation.

---

## 2.1 - Accepting arbitrary signatures

JWT libraries typically provide one method for verifying tokens and another that just decodes them. For example, the Node.js library `jsonwebtoken` has `verify()` and `decode()`.

Occasionally, developers confuse these two methods and only pass incoming tokens to the `decode()` method. This effectively means that the application doesn't verify the signature at all.

For example, in a request, by inspecting the JSON data in the Header and `Payload` fields:
```
# Selected text:
eyJpc3MiOiJwb3J0c3dpZ2dlciIsImV4cCI6MTc4Mzc2MDM3OCwic3ViIjoid2llbmVyIn0

# Decode from base64:
{"iss":"portswigger","exp":1783760378,"sub":"wiener"}
```

We notice that `sub` claim contains your username. We can change it to `administrator` and re-send the request. Since the back-end does not verify the signature at all, we would gain `admin` priv.

---

## 2.2 - Accepting tokens with no signature

The JWT header includes an `alg` parameter specifying the algorithm used to sign the token, which the server then uses to verify it:
```
{
  "alg": "HS256",
  "typ": "JWT"
}
```
This is flawed because the server implicitly trusts unverified, user-controllable input to decide how to check the token's trustworthiness—letting an attacker influence the verification process itself.

JWTs can also be left unsigned, with `alg` set to `none` (an "unsecured JWT"). Servers usually reject such tokens, but since this filtering often relies on string parsing, it can sometimes be bypassed with obfuscation tricks like mixed capitalization or unusual encodings.

**Note:** Even for unsigned tokens, the payload must still end with a trailing dot.

For example,

# 3. Brute-forcing secret keys

Algorithms like HS256 (HMAC + SHA-256) use an arbitrary string as the secret key. Like a password, this secret must be hard to guess or brute-force—otherwise an attacker could craft JWTs with any header and payload they like and re-sign them with a valid signature.

Developers sometimes forget to change default, placeholder, or copy-pasted example secrets. This makes it trivial for attackers to brute-force the key using a [wordlist of well-known secrets](https://github.com/wallarm/jwt-secrets/blob/master/jwt.secrets.list).

## Brute-forcing secret keys using hashcat

Using a valid, signed JWT and a [wordlist of well-known secrets](https://github.com/wallarm/jwt-secrets/blob/master/jwt.secrets.list), run:
```
hashcat -a 0 -m 16500 <jwt> <wordlist>
```

Hashcat signs the JWT's header and payload with each wordlist secret and compares the result to the original signature. On a match, it outputs:
```
<jwt>:<identified-secret>
```
(Use `--show` if re-running the command.)


Once you've found the secret, you can use it to sign a modified JWT with any header/payload values you want.

# 4. JWT header parameter injections

Per the JWS spec, only `alg` is mandatory, but headers often include other parameters attackers find useful:

* `jwk` – embeds the key directly as a JSON object.
* `jku` – provides a URL for fetching a set of keys.
* `kid` – identifies which key to use among multiple options.

Each of these user-controllable parameters tells the server which key to use for signature verification.

---

## 4.1 - jwk parameter

### Core Idea

`JWT`s are signed so that a server can trust their contents. Normally, the server has its own `secret/private key` stored securely, and it uses that to verify any `JWT signature`. The attacker shouldn't be able to influence which key is used for verification.

The `jwk` header parameter breaks this assumption if the server is `misconfigured`. It lets the `JWT` itself carry the `public key` that should be used to verify its signature. That's a reasonable feature in some legitimate use cases, but it becomes dangerous if the server blindly trusts whatever key is embedded, instead of checking it against a pre-approved list of trusted keys.

---

### Example

The JWS spec's optional `jwk` header lets servers embed a public key (in JWK format) directly in the token, e.g.:
```
{
    "kid": "ed2Nf8sb-sD6ng0-scs5390g-fFD8sfxG",
    "typ": "JWT",
    "alg": "RS256",
    "jwk": {
        "kty": "RSA",
        "e": "AQAB",
        "kid": "ed2Nf8sb-sD6ng0-scs5390g-fFD8sfxG",
        "n": "yy1wpYmffgXBxhAUJzHHocCuJolwDqql75ZWuCQ_cb33K2vh9m"
    }
}
```

Servers should verify signatures using only a whitelist of trusted keys, but misconfigured ones may accept whatever key is embedded in `jwk`. This lets an attacker sign a modified JWT with their own RSA private key and attach the matching public key via `jwk`.

If the server will verify a signature using whatever public key is embedded in the token's own header, then an attacker can:
1. Generate their own RSA key pair (public + private).
2. Modify the JWT payload however they want (e.g., change `"role": "user"` to `"role": "admin"`).
3. Sign this modified token using `their own private key` (not the server's secret).
4. Embed the matching `public key` into the `jwk` header of the token.
5. Send it to the server.

The server sees the `jwk` parameter, thinks "ah, here's the key to verify this signature with," uses it — and of course the signature checks out, because it was signed with the attacker's key that matches the embedded public key. The server never realizes this key isn't one it should trust.

---

### Using the JWT Editor extension:

1. **Generate a new RSA key** - In the JWT Editor Keys tab, [generate a new RSA key](https://portswigger.net/burp/documentation/desktop/testing-workflow/vulnerabilities/session-management/jwts#adding-a-jwt-signing-key) - this is the attacker's own keypair.
2. **Send a JWT-bearing request to Repeater** so you can manipulate it.
3. **Modify the payload** — this is where you'd change whatever claim you're trying to escalate (roles, user ID, permissions, etc.).
4. **Click Attack → Embedded JWK** — this automates steps 3 and 4 above: it signs the token with your private key and embeds the corresponding public key into the `jwk` header, formatted correctly.
5. **Send and observe the response** — if the server accepts the forged token, it's vulnerable.

> **Note:** sometimes you also need to update the `kid` (Key ID) header to match the `kid` of your embedded key, because some server implementations cross-check that the `kid` in the header matches the `kid` inside the `jwk` object before trusting it. The Burp extension handles this automatically, but if you were doing it manually, it's an easy thing to forget.

---

> **Root cause:** The vulnerability isn't in the `JWK/JWS` spec itself — the `jwk` parameter is a legitimate optional feature — the vulnerability is a `server trusting a self-declared key instead of validating it against a known, pre-approved set of keys`. (a "Trust me, bro" vuln)

---

## 4.2 - jku parameter

Instead of embedding a key directly, the `jku` header lets servers fetch a JWK Set from a specified URL when verifying a signature. Basically, the token just tells the server **where to fetch the key from**.

### Example

You get something like:
```
{
  "alg": "RS256",
  "kid": "75d0ef47-af89-47a9-9061-7c02a610d5ab",
  "jku": "https://trusted-server.com/.well-known/jwks.json"
}
```

The server reads `jku`, fetches that URL, gets back a `JWK Set` (an array of public keys, each with its own `kid`), finds the key whose `kid` matches the token's `kid`, and uses it to verify the signature.

A JWK Set is a JSON object containing an array of keys:
```
{
    "keys": [
        {
            "kty": "RSA",
            "e": "AQAB",
            "kid": "75d0ef47-af89-47a9-9061-7c02a610d5ab",
            "n": "o-yy1wpYmffgXBxhAUJzHHocCuJolwDqql75ZWuCQ_cb33K2vh9mk6GPM9gNN4Y_qTVX67WhsN3JvaFYw-fhvsWQ"
        },
        {
            "kty": "RSA",
            "e": "AQAB",
            "kid": "d8fDFo-fS9-faS14a9-ASf99sa-7c1Ad5abA",
            "n": "fc3f-yy1wpYmffgXBxhAUJzHql79gNNQ_cb33HocCuJolwDqmk6GPM4Y_qTVX67WhsN3JvaFYw-dfg6DH-asAScw"
        }
    ]
}
```

---

### Why this is exploitable

The security of this whole scheme depends entirely on the server only trusting `jku` URLs that point to `its own domain` (or otherwise designated trusted domains). If the server just blindly fetches whatever URL is in the `jku` header, an attacker can:
1. Generate their own RSA key pair.
2. Host a JWK Set on a server they control, containing their own public key.
3. Modify the JWT payload as desired.
4. Sign the token with their private key.
5. Set the `jku` header to point to their hosted JWK Set.
6. Set `kid` to match the `kid` of the key in their hosted set.

The server dutifully fetches the attacker's key set, finds a matching `kid`, verifies the signature — and it passes, because it was signed with the key the attacker just handed it.

> Same **root cause as `jwk`, a "Trust me, bro" vuln**

---

### URL Passing Bypass

Better-secured servers do try to restrict `jku` to trusted domains — e.g., checking that the URL starts with `https://trusted-server.com/`. But this check can sometimes be bypassed using URL-parsing quirks, similar to SSRF filter bypasses. For example, differences in how validation logic parses a URL vs. how the actual HTTP client resolves it can let an attacker sneak in something like:
```
https://trusted-server.com.evil.com/jwks.json
```

or exploit path/authority confusion, redirects, or DNS tricks — same category of bugs you'd see in SSRF filter evasion.

---

### Practical exploitation with Burp

1. Host a JWK Set containing your attacker-generated public key somewhere accessible (could even be a URL you control via Burp Collaborator or a simple web server).
2. Modify the JWT payload.
3. Sign it with your private key.
4. Set `jku` to your hosted JWK Set URL and `kid` to match.
5. Send and see if the server accepts it.

## 4.3 - kid parameter

This one is a bit different in flavor from `jwk` and `jku`. Instead of exploiting a mechanism that lets the attacker supply a key, this exploits a mechanism where the `kid` value is used to look up a key — and that lookup process itself is vulnerable.

Servers often manage multiple keys (maybe for different services, users, or key-rotation purposes). The `kid` header tells the server which one to use to verify this particular token, e.g.:
```
{ "kid": "775", "alg": "HS256" }
```

The server takes that `kid` value and does a lookup — maybe against a `JWK` Set, a `database row`, or a `file` on disk. **The JWS spec never defines how that lookup should happen — it's just an arbitrary string the developer decides on**. That flexibility is exactly what creates the risk: whatever lookup mechanism the developer chose, if it's built naively, it can be abused.

---

### Attack path 1: Directory traversal

If the `kid` value is used to reference a `file` on the filesystem (e.g., `"kid": "keys/775.pem"` used to build a file path), and the server doesn't sanitize it, an attacker can supply something like:
```
{
    "kid": "../../path/to/file",
    "typ": "JWT",
    "alg": "HS256",
    "k": "asGsADas3421-dfh9DGN-AFDFDbasfd8-anfjkvc"
}
```
or:
```
{ "kid": "../../../../dev/null", "alg": "HS256", ... }
```

The server then reads whatever file that path resolves to and uses its contents as the verification key.

### Why /dev/null specifically is the killer move

This is the clever part. On most Linux systems, `/dev/null` is a special file that's always empty — reading it returns an empty string. So combine two things:
1. Point `kid` at `/dev/null` via directory traversal.
2. Sign your forged JWT using `HS256` (a symmetric algorithm, where the same value is used both to sign and to verify) with the `secret set to an empty string` — because that's what the server will read from `/dev/null`.

The server reads `/dev/null`, gets `""` back as the "key", uses `""` to verify an HMAC signature — and since you signed the token with `""` too, it matches. You've just forged a fully valid signature without ever knowing the server's real secret.

---

### Attack path 2: SQL injection

If instead the `kid` is used to look up a `key from a database` (e.g., `SELECT key FROM keys WHERE kid = '<kid_value>'`), and the value isn't parameterized/escaped, then `kid` becomes an ordinary `SQL injection vector` — same principles as SQLi anywhere else, just delivered through a JWT header instead of a form field or URL parameter.

## 4.4 - Other interesting JWT header parameters

These two are a bit different from `jwk`/`jku`/`kid` — they're not really about tricking the server into using an attacker-chosen verification key. They're more like **secondary attack surface** that becomes relevant once you've already found *some* way to forge or tamper with a valid token (e.g., via one of the previous attacks, or a separate signature-verification bypass).

---

### cty (Content Type)

Normally, JWT payloads are just JSON. But the JWS spec allows a `cty` header to declare a different media type for the payload content — this exists because JWTs can technically wrap other kinds of data, not just plain claims.

Here's the exploitation angle: if you've found a way to get the server to accept a token you control (via a signature bypass), you can also inject a `cty` header telling the server's parser to treat the payload as something other than JSON — for example:

```json
{ "alg": "HS256", "cty": "text/xml" }
```

or

```json
{ "alg": "HS256", "cty": "application/x-java-serialized-object" }
```

If the underlying parsing library actually honors this header (many do, even though it's rarely used), it opens the door to attacks that have nothing to do with JWTs specifically, but are enabled by *making the server parse your payload differently than intended*:

- `text/xml` → potential **XXE** (XML External Entity) injection if the payload gets parsed as XML.
- `application/x-java-serialized-object` → potential **insecure deserialization**, which can sometimes lead to remote code execution depending on what's on the classpath.

So `cty` isn't a key-confusion trick — it's a **content-type confusion** trick that repurposes the JWT payload as an entry point into a totally different vulnerability class.

---

### x5c (X.509 Certificate Chain)

This header is meant to carry an X.509 certificate (or a full certificate chain) containing the public key used to sign the token — conceptually very similar to `jwk`, just using the X.509 certificate format instead of the raw JWK format.

Exploitation-wise, it follows the same logic as the `jwk` attack: if the server trusts whatever certificate is embedded in `x5c` instead of validating it against a known CA or a pinned certificate, an attacker can generate their own certificate, sign the token with the matching private key, and embed their self-signed cert in `x5c`.

There's a second angle mentioned too: X.509 is a notoriously complex format (chains, extensions, various encodings), and **parsing** it correctly is hard. That complexity has historically been a source of real vulnerabilities in libraries, independent of the "trust whatever's embedded" issue. The two CVEs referenced are good examples of this:

- [CVE-2017-2800](https://talosintelligence.com/vulnerability_reports/TALOS-2017-0293) — a certificate/chain validation flaw.
- [CVE-2018-2633](https://mbechler.github.io/2018/01/20/Java-CVE-2018-2633) — an Oracle Java/WebLogic vulnerability related to X.509 handling.

The material calls these out but doesn't go into per-CVE detail, and treats them as "beyond scope" — basically flagging that x5c parsing bugs are their own rabbit hole, distinct from the header-injection pattern covered elsewhere in the excerpt.

---

### Tying it back together

The common thread across the whole document is this: **JOSE headers carry metadata that influences how the token is verified and interpreted, and any of that metadata that's attacker-controllable is a potential lever** — whether it's supplying the key directly (`jwk`), pointing to a key (`jku`), naming a key (`kid`), or reinterpreting the payload's meaning entirely (`cty`, `x5c`).

# 5. JWT algorithm confusion

Even if a server uses robust secrets that you are unable to brute-force, you may still be able to forge valid JWTs by `signing the token using an algorithm that the developers haven't anticipated`. 

This is known as an algorithm confusion attack.

---

## 5.1 - Symmetric vs asymmetric algorithms
