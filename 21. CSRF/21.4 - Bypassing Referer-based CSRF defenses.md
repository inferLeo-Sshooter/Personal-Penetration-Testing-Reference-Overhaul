# Bypassing Referer-based CSRF defenses

Some applications use the HTTP `Referer` header instead of CSRF tokens to defend against attacks by verifying requests originate from their own domain. This approach is generally less effective and often bypassable.

**Referer header**: The HTTP Referer header (misspelled in the HTTP specification) is an optional header containing the URL of the page that linked to the requested resource. Browsers automatically add it when users trigger HTTP requests through links or form submissions. However, various methods allow pages to withhold or modify the `Referer` value, often for privacy reasons.

---

## Validation of Referer depends on header being present

Some applications only validate the `Referer` header *if it's present* — but skip the check entirely when it's missing.

That's an easy gap to exploit: an attacker just needs to make the victim's browser send the request *without* a `Referer` header at all, and the check never triggers.

The simplest way to strip the header is adding this meta tag to the page hosting the CSRF exploit:

```
<meta name="referrer" content="never">
```

> **Note:** To test for this, try to make change email request of your first with and without `Referer` Header.

## Validation of Referer can be circumvented

Some applications check the `Referer` header sloppily, which opens up ways to trick the check.

**Bypass 1: Checking if `Referer` *starts with* the expected domain**

If the app only checks that the value begins with its own domain, an attacker can make their domain a *subdomain* of the expected string:

```
http://vulnerable-website.com.attacker-website.com/csrf-attack
```

This starts with `vulnerable-website.com`, so a naive check passes — even though the real domain is `attacker-website.com`.

**Bypass 2: Checking if `Referer` *contains* the expected domain anywhere**

If the app just checks that the domain name shows up *somewhere* in the string, the attacker can stuff it into the query string instead:

```
http://attacker-website.com/csrf-attack?vulnerable-website.com
```

This "contains" the target's domain, so it slips past the filter too.

**A practical snag:** you might spot this flaw in Burp, but then find your proof-of-concept fails in an actual browser. That's because many browsers now strip the query string from `Referer` by default, as a privacy measure.

**Fix for testing it:** add this header to your exploit's response:

```
Referrer-Policy: unsafe-url
```

(Yes — spelled correctly as "Referrer" here, unlike the `Referer` header itself.) This forces the browser to send the *full* URL, query string included, so your bypass works as intended.

> - **Note**: To test for this, try making change email request of your first.
> - Then, try again but this time, in your Referer Head, change to: `Referer: https://test.com/?https://ORIGINAL-DOMAIN`
