`SameSite` is a browser security mechanism that controls when cookies are sent in cross-site requests, providing protection against CSRF, cross-site leaks, and some CORS exploits.

Since 2021, Chrome **defaults** to `Lax` `SameSite restrictions` when websites don't explicitly set their own level. Other major browsers are expected to follow this standard, making it crucial to understand how these restrictions work and can be bypassed for thorough cross-site attack testing.

---

# 1. WTF is a site in the context of SameSite cookies

## Definition

For SameSite cookie rules, a "site" isn't just the domain — it's the domain name plus its top-level extension (like `.com` or `.net`), together known as TLD+1. So `example.com` counts as one site, no matter what subdomain you're on (`app.example.com`, `shop.example.com`, etc. all belong to it).

But there's a catch: the protocol (`http` vs `https`) counts too. So even if the domain is identical, going from `http://app.example.com` to `https://app.example.com` is still treated as **cross-site** by most browsers — because the scheme changed.

## Site and origin diff

A "site" and an "origin" sound similar but mean different things — and mixing them up can cause real security bugs.

- **Site** = broader. It covers a whole family of subdomains under one domain. So `` `app.example.com` `` and `` `shop.example.com` `` both count as the same site.
- **Origin** = narrower. It's just *one* specific combination.

Two URLs share the same **origin** only if all three of these match exactly:
1. **Scheme** (`http` vs `https`)
2. **Domain name** (`example.com`)
3. **Port** (`80`, `443`, etc.)

So `` `https://app.example.com` `` and `` `http://app.example.com` `` are the *same site*, but *different origins* — because the scheme doesn't match.

One small note: you usually won't see the port written out, because it's implied by the scheme (`http` defaults to port 80, `https` to port 443).

# 2. How does SameSite work?

Before `SameSite` existed, browsers would attach a site's cookies to *every* request to that site — even ones triggered by some unrelated third-party page. `SameSite` fixes this by letting browsers and developers control which cross-site requests are still allowed to carry a given cookie.

This matters for CSRF because CSRF attacks work by tricking the victim's browser into firing a request that carries their authenticated `session cookie`. No cookie, no attack — the request just looks unauthenticated.

Browsers currently support three levels:
- `Strict`
- `Lax`
- `None`

Developers set this per-cookie using the `SameSite` attribute when the cookie is issued:

```
Set-Cookie: session=0F8tgdOhi9ynR1M9wa3ODa; SameSite=Strict
```

Worth noting: SameSite reduces CSRF risk, but it's **not a complete fix** — later labs show ways around it.

**One catch:** if a developer doesn't set `SameSite` at all, Chrome now defaults to `Lax` automatically. So the cookie still gets some cross-site restrictions even though nobody configured it. This is a newer standard, and other browsers are expected to follow.

---

**`Strict`**

The cookie is never sent on cross-site requests — period. If the site in the address bar doesn't match the site the request is going to, the cookie stays home.

Use this for sensitive cookies (auth, actions that change data). It's the safest option, but can break legitimate cross-site flows — e.g. a link from another site that expects you to already be logged in.

**`Lax`**

The cookie *is* sent cross-site, but only when **both** are true:
- The request is a `GET`
- It comes from the user actually navigating (e.g. clicking a link) — not a background request

So it's excluded from cross-site `POST` requests (the kind CSRF usually targets, since `POST` is meant for actions that change data) and from background requests like scripts, iframes, or image loads.

**`None`**

This turns SameSite off entirely. The cookie goes out on *every* request to its site, no matter where the request came from.

- This used to be the default everywhere except Chrome (which now defaults to `Lax`).
- It has legitimate uses — e.g. tracking cookies that don't touch anything sensitive.
- It's also worth checking: some sites set `SameSite=None` on *all* cookies (including sensitive ones) just as a lazy fix after Chrome's `Lax`-by-default change broke things. That's worth flagging if you find it.
- Technically required: any cookie set with `SameSite=None` must also include `Secure`, or browsers will reject it outright:

```
Set-Cookie: trackingId=0F8tgdOhi9ynR1M9wa3ODa; SameSite=None; Secure
```
