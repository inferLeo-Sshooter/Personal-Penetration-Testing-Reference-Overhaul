## 1. What is CSRF

Cross-site request forgery (CSRF) is a web security vulnerability that tricks users into unintentionally performing actions on a site where they're authenticated. It partially bypasses the **same-origin policy**, which normally stops sites from interfering with each other.

**Impact**
A successful attack makes the victim unknowingly perform an action—like changing their email, password, or making a transfer—potentially giving the attacker full account control. If the victim has elevated privileges, the attacker could compromise the entire application.

**How it works**
CSRF requires three conditions:
1. **A relevant action** – something worth triggering (privileged actions or user-specific changes like a password update).
2. **Cookie-based session handling** – the app identifies users solely via session cookies, with no other request-validation mechanism.
3. **No unpredictable parameters** – the attacker can determine/guess all values needed for the request (e.g., no need to know the current password).

**Example**
A normal request to change an account's email:
```
POST /email/change HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 30
Cookie: session=yvthwsztyeQkAPzeQ5gHgTvlyxHfsAfE

email=wiener@normal-user.com
```
This is vulnerable because: the action is valuable to an attacker (changing email enables account takeover via password reset), the app relies only on a session cookie, and the attacker knows all required parameters.

The attacker crafts a malicious page:
```html
<html>
<body>
<form action="https://vulnerable-website.com/email/change" method="POST">
  <input type="hidden" name="email" value="pwned@evil-user.net" />
</form>
<script>document.forms[0].submit();</script>
</body>
</html>
```
If a logged-in victim visits this page, their browser auto-sends the session cookie (unless SameSite cookies are enforced), and the site processes the request as if the victim made it—changing their email without their knowledge.

> **Note**: Although CSRF is normally described in relation to cookie-based session handling, it also arises in other contexts where the application automatically adds some user credentials to requests, such as HTTP Basic authentication and certificate-based authentication.

---

**Delivering a CSRF exploit**:

Delivery methods mirror those used for reflected XSS: the attacker hosts malicious HTML on their own site and lures victims there (e.g., via email or social media links), or plants it on a popular site (like in a comment) and waits for visitors.

Some CSRF exploits using the GET method can be self-contained in a single URL, requiring no external site—the attacker just sends victims a malicious link directly on the vulnerable domain. For the earlier email-change example, a GET-based attack could look like:
```html
<img src="https://vulnerable-website.com/email/change?email=pwned@evil-user.net">
```

This image tag automatically triggers the request when loaded, making it perfect for embedding in emails, forums, or any content the victim might view while logged into the target site.

## 3. XSS vs CSRF

### Key differences

- **XSS** lets an attacker run arbitrary JavaScript in a victim's browser. **CSRF** lets an attacker trick a victim into performing unintended actions.
- **Severity:** XSS is generally more serious. CSRF usually only affects a subset of actions (defenses often miss one or two), while XSS can typically be used to trigger *any* action the user can perform.
- **Direction:** CSRF is "one-way" — the attacker can trigger a request but can't read the response. XSS is "two-way" — injected script can issue requests, read responses, and exfiltrate data.

### Can CSRF tokens prevent XSS?

Sometimes, yes. Example vulnerable endpoint:
```
https://insecure-website.com/status?message=<script>/* Bad stuff here... */</script>
```
If the endpoint requires a valid CSRF token to process the request:
```
https://insecure-website.com/status?csrf-token=CIwNZNlR4XbisJF39I8yWnWX9wX4WFoz&message=<script>/* Bad stuff here... */</script>
```
...a properly validated token blocks trivial exploitation, since reflected XSS relies on a forged cross-site request.

**Caveats:**
- Any reflected XSS on an *unprotected* endpoint remains exploitable as normal.
- If an exploitable XSS exists anywhere on the site, it can fetch a valid CSRF token itself and then use it — bypassing the protection on other actions.
- CSRF tokens don't stop **stored XSS**: if a token-protected page also outputs stored malicious input, the payload still executes when visited.

## 4. Common CSRF defenses

Exploiting CSRF today usually means bypassing the site's or browser's anti-CSRF protections. Key defenses:

- **CSRF tokens** – A unique, unpredictable server-generated value the client must include in sensitive requests, making forged requests hard to construct.
- **SameSite cookies** – A browser mechanism controlling whether cookies are sent on cross-site requests. Since sensitive actions rely on session cookies, this can block cross-site attacks. Chrome has enforced `Lax` by default since 2021, and other browsers are expected to follow.
- **Referer-based validation** – Checks that requests originate from the app's own domain via the HTTP Referer header; less reliable than CSRF tokens.
