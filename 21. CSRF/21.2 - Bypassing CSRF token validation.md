# 1. What is a CSRF token

A CSRF token is a unique, secret, and unpredictable value that is generated by the server-side application and shared with the client. 

When issuing a request to perform a sensitive action, such as submitting a form, the client must include the correct CSRF token. Otherwise, the server will refuse to perform the requested action.

A common way to share CSRF tokens with the client is to include them as a hidden parameter in an HTML form, for example:
```html
<form name="change-email-form" action="/my-account/change-email" method="POST">
    <label>Email</label>
    <input required type="email" name="email" value="example@normal-website.com">
    <input required type="hidden" name="csrf" value="50FaWgdOhi9M9wyna8taR1k3ODOR8d6u">
    <button class='button' type='submit'> Update email </button>
</form>
```

Submitting this form results in the following request:
```
POST /my-account/change-email HTTP/1.1
Host: normal-website.com
Content-Length: 70
Content-Type: application/x-www-form-urlencoded

csrf=50FaWgdOhi9M9wyna8taR1k3ODOR8d6u&email=example@normal-website.com
```

When implemented correctly, CSRF tokens help protect against CSRF attacks by making it difficult for an attacker to construct a valid request on behalf of the victim. As the attacker has no way of predicting the correct value for the CSRF token, they won't be able to include it in the malicious request.

# 2. Common flaws in CSRF token validation

CSRF vulnerabilities typically arise due to flawed validation of CSRF tokens.

## 2.1 - Validation of CSRF token depends on request method

Some applications correctly validate the token when the request uses the POST method but skip the validation when the GET method is used.

In this situation, the attacker can switch to the GET method to bypass the validation and deliver a CSRF attack:
```
GET /email/change?email=pwned@evil-user.net HTTP/1.1
Host: vulnerable-website.com
Cookie: session=2yQIDcpia41WrATfjPqvm9tOkDvkMvLm
```

---

## 2.2 - Validation of CSRF token depends on token being present

Some applications correctly validate the token when it is present but skip the validation if the token is omitted.

In this situation, the attacker can remove the entire parameter containing the token (not just its value) to bypass the validation and deliver a CSRF attack:
```
POST /email/change HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 25
Cookie: session=2yQIDcpia41WrATfjPqvm9tOkDvkMvLm

email=pwned@evil-user.net
```

---

## 2.3 - CSRF token is not tied to the user session

Some applications do not validate that the token belongs to the same session as the user who is making the request. Instead, the application maintains a global pool of tokens that it has issued and accepts any token that appears in this pool.

In this situation, the attacker can log in to the application using their own account, obtain a valid token, and then feed that token to the victim user in their CSRF attack.
```
POST /email/change HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 25
Cookie: session=2yQIDcpia41WrATfjPqvm9tOkDvkMvLm

csrf=ATTACKER-CSRF-TOKEN&email=pwned@evil-user.net
```

---

## 2.4 - CSRF token is tied to a non-session cookie

Normally, a CSRF token should be cryptographically tied to the user's *session cookie* — the cookie that identifies who's logged in. That link is what makes the token trustworthy: if the token matches the session, the server knows the request really came from that logged-in user's browser.

In this variant, the application does check the CSRF token against *a* cookie — just not the session cookie. This tends to happen when a site bolts together two separate systems (say, one library for login sessions, another for CSRF protection) and nobody wired them together. So you end up with two independent cookies:

```
Cookie: session=pSJYSScWKpmC60LpFOAHKixuFuM4uXWF; csrfKey=rZHCnSzEp8dbI6atzagGoSYyqJqTz5dv

csrf=RhV7yQDO0xcq9gLEah2WVbmuFqyOq7tY&email=wiener@normal-user.com
```

- `session` → identifies who's logged in
- `csrfKey` → only used to validate the `csrf` token in the form body

The server checks "does `csrf` match `csrfKey`?" but never checks "does this pairing belong to *this* session?"

### Why that's exploitable

Because the two are disconnected, an attacker doesn't need to steal the victim's real token — they just need to get the victim's browser to accept the *attacker's own* `csrfKey`/`csrf` pair instead. Since the check only validates that the two match each other, not that they belong to the victim, a mismatched-but-mutually-consistent pair still passes.

### How to test

- To test for this variation, we can use 2 accounts: A and B.
- We'll attempt to change the email of 2 accounts.
- Assuming the request contains this: `Cookie: session=abc... csrfKey=qwe... <SNIP> email=abc.com&csrfToken=mnb....`
- We replace **both** `csrfKey` and `csrfToken` of A with B's, while keeping A's `session` cookie untouched:

```
Cookie: session=<A's session>; csrfKey=<B's csrfKey>
Body: csrf=<B's csrf token>&email=attacker@evil.com
```

- If the request gets accepted by the website, this means the CSRF token and key are not tied to the `session` cookie.
- It would resolve to a real vuln if we can somehow inject a cookie header into the victim's browser.

### The attack sequence

1. Attacker logs into the app with their own account, generating a valid `csrfKey` cookie + matching `csrf` token.
2. Attacker finds some way to plant a cookie in the victim's browser (e.g. a cookie-setting bug elsewhere on the site — this is the key extra requirement this attack needs).
3. Attacker uses that mechanism to overwrite the victim's `csrfKey` cookie with their own value.
4. Attacker builds a malicious page containing a form pre-filled with their own `csrf` token, and lures the victim into submitting it.
5. The victim's browser sends the request with the attacker's `csrfKey` cookie (planted in step 3) alongside the attacker's `csrf` token (embedded in step 4) — they match, so the server accepts the request, executing it in the context of the victim's *session* cookie.

**Bottom line:** tying the token to *some* cookie isn't enough — it has to be tied to the `session` cookie specifically, or an attacker who can inject any cookie at all can bypass the protection entirely.

> **Note:** The cookie-setting behavior does not even need to exist within the same web application as the CSRF vulnerability. Any other application within the same overall DNS domain can potentially be leveraged to set cookies in the application that is being targeted, if the cookie that is controlled has suitable scope.
> For example, a cookie-setting function on `staging.demo.normal-website.com` could be leveraged to place a cookie that is submitted to `secure.normal-website.com`.

### Worked example: PortSwigger — "CSRF where token is tied to non-session cookie"

This lab is a direct implementation of the theory above. It has two ingredients that map onto the "how to test" and "attack sequence" sections:

1. The `csrfKey`/`csrf` pair is validated independently of `session` (confirmed via testing, same as the A/B account swap method above).
2. A **secondary cookie-injection bug** elsewhere on the site (the search function) supplies the "some way to plant a cookie in the victim's browser" requirement from step 2 of the attack sequence.

**Credentials given:** `wiener:peter` and `carlos:montoya` — these play the role of accounts A and B from the testing method.

#### Step-by-step

**1. Confirm `session` vs `csrfKey` aren't linked.**

Log in, submit "Update email," send the request to Repeater. Changing `session` logs you out (as expected). Changing `csrfKey` alone just gets the token rejected — but doesn't kill the session. That asymmetry is the tell: `csrfKey` isn't part of session validation.

**2. Confirm the pair is swappable between accounts (the A/B test from the note).**

In a private window, log in as the second account, capture its own update-email request. Swap *that* account's `csrfKey` cookie + `csrf` body param into the first account's request (keeping the first account's `session` cookie). If accepted → confirmed, token is tied to `csrfKey` only, not `session`.

**3. Find the cookie-injection primitive.**

The lab's search feature reflects the search term into a `Set-Cookie` header with no CSRF protection of its own — meaning it can be triggered cross-site and used to set arbitrary cookies (including `csrfKey`) on the victim. This is the "some way to plant a cookie" step:

```
/?search=test%0d%0aSet-Cookie:%20csrfKey=YOUR-KEY%3b%20SameSite=None
```

(`%0d%0a` = CRLF injection into the response headers, smuggling in a second `Set-Cookie`.)

**4. Build the exploit.**

Base it on the standard "no defenses" CSRF PoC — an auto-submitting form with the attacker's own `csrf` token and a victim-bound `email` value. Replace the auto-submit `<script>` block with an image tag that first hits the cookie-injection endpoint, *then* submits the form on error/load:

```html
<img src="https://YOUR-LAB-ID.web-security-academy.net/?search=test%0d%0aSet-Cookie:%20csrfKey=YOUR-KEY%3b%20SameSite=None"
     onerror="document.forms[0].submit()">
```

This ordering matters — the cookie has to land in the victim's browser *before* the form submits, otherwise the victim's browser still has their own `csrfKey` and the swapped `csrf` token won't match.

**5. Deliver to victim.**

Their browser now carries the attacker's `csrfKey` (freshly planted) + attacker's `csrf` token (in the form) + the victim's own `session` cookie → request passes validation → email changed under the victim's session.

## 2.5 - CSRF token is simply duplicated in a cookie

Some applications skip server-side token storage entirely, instead just duplicating the token in both a cookie and a request parameter, then checking the two match on submission. This is the "double submit" defense — popular for being stateless and easy to implement:

```
Cookie: session=1DQGdzYbOJQzLP7460tfyiv3do7MjyPw; csrf=R8ov2YBfTYmzFyjit8o2hKBuoIjXXVpa

csrf=R8ov2YBfTYmzFyjit8o2hKBuoIjXXVpa&email=wiener@normal-user.com
```

It's still vulnerable if the site has any cookie-setting flaw. Since there's no server-side record, the attacker doesn't even need a real token — they can invent one (matching the expected format if needed), use the cookie-setting bug to plant it in the victim's browser, and embed the same value in their CSRF attack.

> Test this by changing both `csrf` value. If the request get accepted, then it is vuln `IF` you can inject cookie to the website
