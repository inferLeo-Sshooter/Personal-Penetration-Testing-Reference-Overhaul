# 1. Serialization & Insecure Deserialization

## What is serialization?

Imagine you have an object in your code — like a `User` with a name, email, and role. That object lives in your program's memory as a complex structure. But memory can't be emailed, saved to disk, or sent over the internet as-is.

**Serialization is the process of "flattening" that object into a simple stream of bytes (or text) so it can be:**
- Saved to a file or database
- Sent across a network (e.g., in an API request)
- Passed between different parts of an application

Think of it like packing a piece of furniture into a flat-pack box for shipping. The furniture (object) gets broken down into a transportable format, but all the pieces needed to rebuild it are still there.

**Example — a `User` object in memory:**
```
User {
  name: "Alice"
  email: "alice@example.com"
  role: "admin"
}
```

**Serialized into JSON (a common human-readable format):**
```json
{
  "name": "Alice",
  "email": "alice@example.com",
  "role": "admin"
}
```

**Or serialized into a language-specific binary/string format (like Java or PHP):**
```
O:4:"User":3:{s:4:"name";s:5:"Alice";s:5:"email";s:17:"alice@example.com";s:4:"role";s:5:"admin";}
```

Both versions preserve the object's **state** — its fields and their values — exactly as they were.

> 💡 Different languages have different names for this:
> - Python calls it **pickling**
> - Ruby calls it **marshalling**
> - They all mean the same thing: turning an object into a portable format.

Also note: serialization normally includes *all* fields — even private ones — unless a field is explicitly marked `transient` (i.e., "don't serialize me").

---

## Serialization vs. Deserialization

**Deserialization is the reverse process** — taking that flat stream of bytes/text and rebuilding it back into a fully working object, in the exact same state it was in before.

```
[Serialize]                          [Deserialize]
User object  →  bytes/JSON/string  →  User object
 (memory)         (portable)           (memory again)
```

Once deserialized, the application treats the object like any other — calling its methods, reading its fields, etc.

---

## What is insecure deserialization?

This is where things get dangerous.

**Insecure deserialization happens when a website deserializes data that came from the user — without properly trusting or verifying it.**

If an attacker can control the data being deserialized, they can potentially:
1. **Tamper with the object's fields** — e.g., change `"role": "user"` to `"role": "admin"`
2. **Swap in a completely different class** than the one the app expected — tricking the app into creating an object it never meant to create

This second point is why it's sometimes called an **"object injection"** vulnerability — the attacker injects an unexpected object into the application.

**Simplified attack example:**

Say a website stores a serialized session object in a cookie:
```
role=O:4:"User":2:{s:4:"role";s:4:"user";s:5:"admin";b:0;}
```

An attacker could modify the cookie before it's sent back to the server:
```
role=O:4:"User":2:{s:4:"role";s:5:"admin";s:5:"admin";b:1;}
```

If the server blindly deserializes this and trusts it, the attacker just gave themselves admin access — without ever logging in as an admin.

**It gets worse:** because deserialization instantiates objects and can trigger their built-in methods automatically (like constructors or "wake up" functions), damage can happen *during* the deserialization process itself — even before the application does anything with the object. So even strictly-typed, "safe" languages aren't immune.

---

## Why does this vulnerability happen?

A few common reasons:

| Cause | Explanation |
|---|---|
| **Lack of awareness** | Developers don't realize how risky deserializing user input is. Ideally, you should never deserialize untrusted data at all. |
| **False sense of security from validation** | Some teams try to "check" the object *after* deserializing it. But by then, the damage may already be done — validation is too late. |
| **Assuming binary = safe** | Binary formats look unreadable to humans, so developers assume attackers can't tamper with them. In reality, attackers can still reverse-engineer and manipulate binary data. |
| **Too many dependencies** | Modern apps use tons of libraries, each contributing many classes. An attacker can potentially instantiate *any* of these classes and chain together unexpected method calls — creating attack paths no one anticipated. |

**Bottom line:** Many security experts argue it's essentially impossible to *safely* deserialize untrusted/attacker-controlled input. The safest fix is to avoid it entirely.

---

## Quick Summary

| Term | Meaning |
|---|---|
| **Serialization** | Converting an object into a flat, transportable format (bytes/text) |
| **Deserialization** | Rebuilding that object back into working memory |
| **Insecure Deserialization** | Deserializing *untrusted/user-controlled* data, letting attackers manipulate or replace objects |
| **Object Injection** | A nickname for insecure deserialization, since attackers can inject unexpected object types |
| **Golden Rule** | Never deserialize data from an untrusted source. If you must, sign/encrypt it and use strict allow-lists for permitted classes. |

# 2. How to Identify Insecure Deserialization

The good news: spotting insecure deserialization isn't that hard, even if you don't have access to the source code. You're basically looking for one thing — **serialized data flowing into the website from the user** (cookies, form fields, hidden inputs, API request bodies, etc.).

Once you spot serialized-looking data, the next question is: *"Can I control or modify this?"* If yes, you may have found a vulnerability.

To do this well, it helps to recognize what serialized data actually *looks like* in different languages. Let's break down the two most common formats: **PHP** and **Java**.

> **Note:** For users of Burp Suite Professional, Burp Scanner will automatically flag any HTTP messages that appear to contain serialized objects.

---

## 2.1 - PHP Serialization Format

PHP's serialization format is (mostly) human-readable — it's just a compact string where **letters indicate the data type** and **numbers indicate the length** of each piece of data.

### Example

Imagine a `User` object like this in PHP:

```php
$user->name = "carlos";
$user->isLoggedIn = true;
```

When serialized, it turns into a string like this:

```
O:4:"User":2:{s:4:"name":s:6:"carlos";s:10:"isLoggedIn":b:1;}
```

At first glance this looks like gibberish, but it's actually very structured. Here's how to read it piece by piece:

| Segment | Meaning |
|---|---|
| `O:4:"User"` | This is an **O**bject, class name is 4 characters long, and the class is called `"User"` |
| `2` | The object has **2 attributes** |
| `s:4:"name"` | First attribute's key is a **s**tring, 4 characters long: `"name"` |
| `s:6:"carlos"` | Its value is a string, 6 characters long: `"carlos"` |
| `s:10:"isLoggedIn"` | Second attribute's key is a string, 10 characters long: `"isLoggedIn"` |
| `b:1` | Its value is a **b**oolean, `true` |

So the pattern is basically:
```
O:<name length>:"<class name>":<number of attributes>:{
  <key type>:<key length>:"<key>";<value type>:<value length or content>;
  ...
}
```

### 🚩 What to look for
If you see a string in a cookie, hidden field, or request parameter that starts with something like `O:4:"..."` or contains `s:` and `b:` markers — that's very likely **PHP serialized data**.

### 🔍 If you have source code access
Search for the native PHP functions:
- `serialize()` — converts an object *into* this string format
- `unserialize()` — converts the string *back* into an object

> Any use of `unserialize()` on user-controlled input is a major red flag worth investigating further.

---

## 2.2 - Java Serialization Format

Unlike PHP, Java typically serializes objects into **binary** — not readable text. This makes it trickier to spot, but there's a reliable trick: **serialized Java objects almost always start with the same fixed bytes**, like a signature or fingerprint.

| Encoding | Starts with |
|---|---|
| Hexadecimal | `ac ed` |
| Base64 | `rO0` |

### Example

If you're inspecting a cookie or request parameter and you see something like:

```
rO0ABXNyABFqYXZhLnV0aWwuSGFzaE1hcAUH2sHDFmDRAwACRgAKbG9hZEZhY3RvckkACXRocmVzaG9sZHhwP0AAAAAAAAx3CAAAABAAAAAA
```

That `rO0` at the start is your giveaway — this is very likely a **Base64-encoded serialized Java object**.

### 🚩 What to look for
- Base64 strings beginning with `rO0`
- Raw binary data beginning with hex bytes `ac ed`

### 🔍 If you have source code access
Look for:
- Classes that implement `java.io.Serializable` — these are eligible to be serialized/deserialized
- Any use of `readObject()` — this method reads and deserializes data from an `InputStream`, and is the key method to inspect for vulnerabilities

---

## Quick Reference Table

| Language | Format | Signature to Spot | Key Methods to Search For |
|---|---|---|---|
| **PHP** | Human-readable string | Starts with `O:<num>:"ClassName"`, contains `s:`, `b:`, `i:` markers | `serialize()`, `unserialize()` |
| **Java** | Binary | Hex: `ac ed` / Base64: `rO0` | `readObject()`, classes implementing `Serializable` |

---

## General Testing Approach

1. **Trace all user-controllable input** — cookies, hidden form fields, URL/query parameters, API payloads, etc.
2. **Scan for serialized-data patterns** using the signatures above.
3. **Check if you can modify it** — try changing a value (like `isLoggedIn` from `false` to `true`, or a role from `user` to `admin`) and see if the app accepts your tampered version.
4. **If you have source code**, search directly for the telltale functions (`unserialize()` in PHP, `readObject()` in Java) to find exactly where deserialization happens — this pinpoints your attack surface immediately.
